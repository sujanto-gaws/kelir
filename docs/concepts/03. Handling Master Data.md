Kept for the governance intent.**

The short answer is: **No, the Master Data itself should not be processed purely as a transactional document.** 

However, **the creation, modification, and deactivation of Master Data MUST be processed as documents driven by the workflow engine.**

This requires a **Hybrid Architecture** that separates the *Master Data Registry* (the source of truth) from the *Document Workflow* (the process of changing the truth).

---

# 1. The Core Distinction: Transactional vs. Master Data

To design this correctly, we must separate the two concepts:

| Feature | Transactional Document (e.g., Purchase Order) | Master Data (e.g., Supplier, Employee) |
| :--- | :--- | :--- |
| **Nature** | Represents a specific business event or transaction. | Represents a core business entity. |
| **Lifespan** | Has a clear start and end (Created → Approved → Archived). | Continuous lifecycle (Created → Active → Inactive → Obsolete). |
| **Volume** | High volume, generated daily. | Lower volume, relatively stable. |
| **Usage** | Processed once or a few times. | Referenced thousands of times across many documents. |
| **Storage** | Document Repository / Content Store. | Relational Database / Master Data Management (MDM) System. |

If you treat a Supplier purely as a "document", querying active suppliers for a dropdown menu will be incredibly slow, and maintaining referential integrity with Purchase Orders will be a nightmare.

---

# 2. The Hybrid Architecture: "Documents to Manage Master Data"

In this system, Master Data *changes* are managed using **workflow-driven change requests** (Create, Update, Deactivate). Read is not a workflow: reads are served directly by the Master Data Read API (see Section 4.2). 

Every time a Master Data record needs to be created or changed, a **Master Data Request Document** is generated and routed through the workflow engine.

### The Flow:
1. **The Request (Document):** A user fills out a "New Supplier Registration Form" (This is a document).
2. **The Process (Workflow):** The document goes through approvals (Procurement checks details, Finance checks bank details, Legal checks compliance).
3. **The Execution (System Task):** Upon final approval, the workflow engine triggers an automated system task.
4. **The Result (Master Data):** The system writes the approved data into the **Master Data Registry**, creating the "Golden Record" (the official Supplier profile).

# 3. Master Data Domains and Their Document Workflows

Here is how different master data entities are handled via document workflows:

## 3.1 Supplier / Vendor Master
* **Document Types:** Vendor Onboarding Request, Vendor Bank Detail Update, Vendor Deactivation Request.
* **Workflow:** Procurement → Compliance → Finance.
* **Result:** Updates the `mdm_suppliers` table.

## 3.2 Employee Master
* **Document Types:** New Hire Registration, Employee Promotion/Transfer, Employee Resignation, Personal Data Update (e.g., change of address or bank account).
* **Workflow:** HR → Department Manager → IT (for access provisioning).
* **Result:** Updates the `mdm_employees` table and triggers IT provisioning.

## 3.3 Facility / Asset Master (Offices, Warehouses, Buildings)
* **Document Types:** New Facility Registration, Facility Maintenance Contract Renewal, Facility Decommissioning.
* **Workflow:** Facilities Manager → Finance → Operations Director.
* **Result:** Updates the `mdm_facilities` table.

## 3.4 Product / Service Master
* **Document Types:** New Product Launch Request, Product Price Change, Service Discontinuation.
* **Workflow:** Product Manager → Finance (Pricing) → Sales Director.
* **Result:** Updates the `mdm_products` table.

# 4. System Components for Master Data

To support this, the architecture needs a dedicated **Master Data Management (MDM) Module** alongside the Document Module.

## 4.1 Master Data Registry (The "Golden Record")
This is a highly optimized, structured database (or microservice) that stores the active, approved master data.
* **Tables:** `mdm_suppliers`, `mdm_employees`, `mdm_facilities`, `mdm_products`.
* **Features:** Fast read access, strict data typing, hierarchical relationships (e.g., Building → Floor → Room), and version history of the data fields.

## 4.2 Master Data API (Read-Only for Documents)
When a user is filling out a *Purchase Order* (Transactional Document), the form needs to know who the supplier is.
* The Document Form calls the **Master Data API** to populate dropdowns.
* *Example:* `GET /api/mdm/suppliers?status=ACTIVE`
* This ensures users can only select approved, active master data.

## 4.3 Master Data Write API (Triggered by Workflow)
When a *Vendor Update Document* is finally approved, the workflow engine calls the **Master Data Write API**.
* *Example:* `POST /api/mdm/suppliers` or `PUT /api/mdm/suppliers/{id}`
* This API updates the Golden Record and publishes an event: `SupplierUpdated`.

# 5. Data Model Integration

How do Documents and Master Data link together in the database?

### 5.1 The Document Table (Adding Master Data Context)
Add fields to the `documents` table to link a workflow document to a master data entity.

```text
documents
--------------------------------------------------
document_id
document_type         (e.g., 'VENDOR_UPDATE_REQUEST')
status
entity_type           (e.g., 'SUPPLIER', 'EMPLOYEE', 'FACILITY')
entity_id             (e.g., 'SUP-1005' - The ID of the Master Data record)
target_action         (e.g., 'CREATE', 'UPDATE', 'DEACTIVATE')
form_data_json        (for master-data requests, the proposed changes waiting for approval live in form_data_json)
```

### 5.2 The Master Data Table (The Source of Truth)
```text
mdm_suppliers
--------------------------------------------------
supplier_id           (e.g., 'SUP-1005')
name
tax_id
bank_account
status                       (DRAFT, PENDING_APPROVAL, ACTIVE, SUSPENDED, INACTIVE, ARCHIVED)
created_by_document_id       (e.g., 'DOC-9921' - The onboarding document)
last_updated_by_document_id  (e.g., 'DOC-1045' - The bank update document)
```

### 5.3 The Linkage in Action
1. User creates a "Bank Update Request" for Supplier SUP-1005.
2. Document is created: `entity_type = 'SUPPLIER'`, `entity_id = 'SUP-1005'`, `status = 'PENDING'`.
3. The `mdm_suppliers` table remains untouched. The old bank account is still active.
4. Workflow approves the document.
5. Workflow Engine reads the proposed changes from the document's `form_data_json` and writes them to `mdm_suppliers`.
6. Document status changes to `COMPLETED`.

# 6. Handling "Draft" or "Pending" Master Data

Sometimes, a supplier needs to be visible in the system before they are fully approved (e.g., to allow a user to draft a Purchase Order for them).

**Solution: Master Data Statuses**
The Master Data Registry should support lifecycle statuses. The canonical status list (also used by the `status` column in Section 5.2) is: `DRAFT`, `PENDING_APPROVAL`, `ACTIVE`, `SUSPENDED`, `INACTIVE`, `ARCHIVED`.
* **DRAFT / PENDING_APPROVAL:** Created via a document, but workflow is not yet finished. Can be referenced in draft transactional documents, but blocked from final approval.
* **ACTIVE:** Fully approved via workflow. Can be used in all transactions.
* **SUSPENDED:** Temporarily blocked via a workflow document (e.g., compliance issue).
* **INACTIVE / ARCHIVED:** Deactivated via a workflow document.

# 7. User Interface Concept

The UI should clearly separate **Transactional Workspaces** from **Master Data Management**.

## 7.1 Master Data Management Portal (Admin/Power Users)
A dedicated module to view and manage the "Golden Records".
* **List View:** Grid of all Suppliers, Employees, Facilities with filters.
* **Detail View:** Shows the current active data.
* **Action Buttons:** Instead of "Edit", the buttons are "Request Update", "Request Deactivation", or "View History".
* **History Tab:** Shows a timeline of all *Documents* that have modified this Master Data record over time.

## 7.2 Document Workspace (Standard Users)
Where users initiate the workflows.
* **Forms:** "Register New Employee", "Add New Facility".
* **Lookups:** When filling out a form, the system fetches active Master Data for dropdowns (e.g., selecting a Facility for a Maintenance Request).

# 8. Workflow Engine Integration (Service Tasks)

The Workflow Engine (e.g., Camunda, Flowable) plays a critical role here using **Service Tasks** or **Integration Events**.

**Example Workflow: Employee Promotion**
1. **User Task:** HR fills out "Promotion Request" (Document).
2. **User Task:** Department Head Approves.
3. **User Task:** HR Director Approves.
4. **Service Task (System):** Workflow Engine calls `HRIS_API.promoteEmployee(entity_id, new_role, new_salary)`.
5. **Service Task (System):** Workflow Engine calls `IT_API.updateAccessRights(entity_id, new_role)`.
6. **End Event:** Document is marked Completed.

Note that the internal `mdm_employees` registry is the golden record within Kelir; the HRIS API call here is downstream propagation to an external system, consistent with the "execution layer" framing in Section 9.

If the Service Task fails (e.g., the HRIS system is down), the workflow engine catches the error, pauses the document, and alerts the administrator, ensuring the Master Data is never out of sync with the approval process.

---

# 9. Event-Driven Master Data Synchronization

When Master Data is updated via an approved document, it must notify the rest of the enterprise. The system should publish **Master Data Events** to an Event Bus (e.g., Kafka, RabbitMQ).

**Event Examples:**
* `Supplier.Created` (Triggers ERP vendor creation)
* `Employee.DepartmentChanged` (Triggers cost-center reallocation in Finance)
* `Facility.Deactivated` (Triggers cancellation of utility contracts)
* `Product.PriceUpdated` (Triggers update in the e-commerce catalog)

This ensures that the Document-Based System acts as the **governance and approval layer**, while the downstream systems (ERP, CRM) act as the **execution layer**.

---

# 10. Summary of Best Practices

1. **Never store Master Data purely as unstructured documents (like PDFs or generic JSON blobs).** Master Data must live in structured, queryable tables or an MDM system.
2. **Use Documents to govern the *lifecycle* of Master Data.** Every creation, update, and deletion of a Master Data record must be a document routed through the workflow engine.
3. **Enforce Referential Integrity.** Transactional documents (like Invoices) must link to the supplier's master data ID (`mdm_suppliers.supplier_id`), not the `onboarding_document_id`.
4. **Implement "Maker-Checker" Controls.** The person who creates the Master Data Request (Maker) cannot be the same person who approves the workflow to update the Master Data Registry (Checker).
5. **Maintain an Audit Trail linking both.** The Master Data record's history should clearly show: *"Field 'Bank Account' changed on 2026-08-05 via Document #DOC-9921 approved by Finance Director."*

By using this hybrid approach, you get the best of both worlds: **strict, auditable, workflow-driven governance** (from the document system) and **high performance, reliable, structured data** (from the Master Data Registry).
