# Sample Data Structures for System Overview

**Status:** Superseded · **Last updated:** 2026-08-12

> **Superseded in detail by [Database Schema](../design/02.%20Database%20Schema.md) and the [schema standards](../schema/). Its `snake_case` JSON samples predate the `camelCase` payload rule ([naming convention](../standards/02.%20Naming%20Convention.md) §5). Kept as an end-to-end walkthrough of how the pieces fit together.**

Below is a **sample conceptual data structure** for a document-based business application system where workflow and document flow are handled by a workflow engine.

This is not a final production database schema, but a practical overview of the main entities and relationships needed for the system.

---

# 1. High-Level Data Model Overview

The system can be divided into these major data domains:

```text
1. Identity and Organization
2. Master Data
3. Document Type Configuration
4. Document Management
5. Attachments and Related Documents
6. Comments and Collaboration
7. Workflow Engine
8. Activity Log and Audit Trail
9. Notifications
```

Core relationship:

```text
User / Role / Department
        ↓
Master Data (Supplier, Employee, Facility, Product, etc.)
        ↓
Document Type Configuration
        ↓
Document Instance
        ↓
Workflow Process Instance
        ↓
Tasks / Approvals / Decisions
        ↓
Attachments / Comments / Activity / Audit
```

# 2. Common Base Fields

Most tables should contain common audit and tenant fields.

```text
id                  unique identifier
tenant_id           multi-tenant identifier
created_by          user who created the record
created_at          creation timestamp
updated_by          user who last updated the record
updated_at          last update timestamp
deleted_at          soft delete timestamp
```

A record is considered soft-deleted when `deleted_at IS NOT NULL`.

Later table definitions list only domain fields; the base fields above are implied on every table.

Example:

```json
{
  "id": "DOC-2026-000123",
  "tenant_id": "TNT-001",
  "created_by": "user.john",
  "created_at": "2026-08-05T09:00:00Z",
  "updated_by": "user.sara",
  "updated_at": "2026-08-05T10:30:00Z",
  "deleted_at": null
}
```

```text

----------------------------------------
document_id
tenant_id

status

```

`entity_type` and `entity_id` identify the master-data record a document targets or primarily references; `target_action` is set only for master-data change requests.

Sample:


# 16. Final Concept

The system should use two main data patterns:

```text
1. Master Data Records
   → Structured, reusable, active/inactive records.
   → Example: Supplier, Employee, Customer, Facility, Product, Service.

2. Document Workflow Records
   → Transactional, process-driven, approval-based records.
   → Example: Purchase Requisition, Supplier Update Request, Employee Change Request.
```

Master data changes are created as documents:

```text
Master Data Change Request Document
        ↓
Workflow Approval
        ↓
Approved Master Data Update
        ↓
Master Data Registry Updated
        ↓
Activity / Audit Log Recorded
```

This gives the system both:

- **Document-based governance and auditability**
- **Structured master data that can be used reliably across business processes**
