External BPMN engines remain a possible later integration. This document is retained as conceptual background.

A **document-based business application system** is a platform where business processes are driven by documents such as forms, requests, contracts, invoices, applications, approvals, certificates, and reports.

In this concept, the system does **not** manage workflow manually inside each module. Instead, all **workflow and document flow are handled by a centralized workflow engine**. The workflow engine controls routing, approval, task assignment, status changes, escalations, deadlines, and document movement between people, departments, or external parties.

---

# 1. Core Idea

The system is built around one main principle:

> **Every business transaction is represented as a document, and every document moves through a controlled workflow.**

Examples:

| Business Process | Document Object |
|---|---|
| Leave request | Leave Application Form |
| Procurement | Purchase Requisition |
| Finance | Invoice / Payment Request |
| HR | Employee Onboarding Form |
| Legal | Contract / Agreement |
| Sales | Quotation / Sales Order |
| Compliance | Permit / License Application |
| Project | Approval Request / Change Request |

Each document has:

- Metadata
- Content or form data
- Attachments
- Status
- Version history
- Approval history
- Assigned workflow
- Audit trail

The workflow engine decides:

- Who should receive the document next
- What action is required
- Whether approval is needed
- When escalation happens
- Which department handles it
- When the document is completed or archived

The platform should enable organizations to:

1. **Digitize paper-based and manual document processes**
2. **Standardize business workflows**
3. **Track every document from creation to archive**
4. **Reduce process delays through automation**
5. **Maintain full auditability**
6. **Support compliance and governance**
7. **Allow low-code configuration of new document types**
8. **Integrate with existing business systems**

# 3. Main Design Principles

## 3.1 Document-Centric Architecture

The document is the central business object. All tasks, approvals, comments, and actions are linked to the document.

## 3.2 Workflow-Driven Processing

No module independently controls process flow. All routing and approvals are delegated to the workflow engine.

## 3.3 Metadata-Driven Classification

Documents are classified by type, category, department, priority, amount, risk level, and business unit.

## 3.4 Event-Based Processing

Document events trigger workflow actions.

Examples:

- Document submitted → start workflow
- Manager approved → move to finance
- Document rejected → return to initiator
- Payment completed → archive document
- Deadline exceeded → send escalation

## 3.5 Full Traceability

Every action is recorded:

- Who created the document
- Who viewed it
- Who edited it
- Who approved it
- Who rejected it
- When status changed
- Which version exists
- Which workflow step was completed

### Document States

A document may have states such as:

| Status | Meaning |
|---|---|
| Draft | Created but not submitted |
| Submitted | Sent into workflow |
| In Review | Being reviewed |
| Pending Approval | Waiting for approver |
| Approved | Approved by required parties |
| Rejected | Returned or denied |
| Returned to Initiator | Requires correction |
| Signed | Legally signed |
| Completed | Process finished |
| Archived | Stored for compliance |
| Cancelled | Process stopped |

The workflow engine controls these status transitions.

> **Superseded in detail:** the normative platform `documents.status` enum is defined in architecture document 02 §3.12 and does not include `Signed` — signing is a workflow state that maps onto `COMPLETED`. This table conveys the concept only.

# 6. Workflow and Document Flow Concept

The most important concept is that **document flow and workflow are synchronized**.

---

## 6.1 Document Flow

Document flow describes where the document goes.

Example:

```text
Employee creates document
        ↓
Department Head reviews
        ↓
Finance validates
        ↓
Director approves
        ↓
Document is signed
        ↓
Document is archived
```

---

## 6.2 Workflow Flow

Workflow flow describes what happens at each step.

Example:

```text
Start
  ↓
Validate form completeness
  ↓
If incomplete → return to employee
  ↓
If complete → assign to Department Head
  ↓
If amount > 10,000,000 IDR → assign to Director
  ↓
If rejected → notify employee
  ↓
If approved → move to next step
  ↓
End
```

---

## 6.3 Combined Document-Workflow Flow

```text
Document Event              Workflow Action
------------------------------------------------
Document created      →     Process instance prepared
Document submitted    →     Process instance started
Form validated        →     First task generated
Manager approved      →     Document routed to Finance
Finance rejected      →     Document returned with comment
Director approved     →     Final approval recorded
Document signed       →     Status changed to Completed
Retention period met  →     Document archived
```

# 7. Example Business Process: Purchase Requisition

## Process Name

**Purchase Requisition Approval**

## Document Type

Purchase Requisition Form

## Required Data

- Requester
- Department
- Item description
- Quantity
- Estimated cost
- Vendor
- Justification
- Attachment: quotation

---

## Workflow

```text
1. Employee creates Purchase Requisition
2. Employee submits document
3. System validates mandatory fields
4. If incomplete, return to employee
5. Department Manager reviews
6. If rejected, notify employee
7. If approved:
   - If amount <= 1,000,000 IDR: Finance Officer approval
   - If amount > 1,000,000 IDR and <= 10,000,000 IDR: Finance Manager approval
   - If amount > 10,000,000 IDR: Director approval
8. Procurement receives approved requisition
9. Procurement creates Purchase Order in ERP
10. Document status becomes Completed
11. Document is archived
```

---

## Status Flow

```text
Draft
  ↓
Submitted
  ↓
Department Review
  ↓
Finance Approval
  ↓
Director Approval
  ↓
Procurement Processing
  ↓
Completed
  ↓
Archived
```

Note: the path shown is the high-value case (amount > 10,000,000 IDR). For lower amounts the approval tiers are conditional and mutually exclusive, so the document skips the levels that do not apply per the rules above.

# 9. Workflow Engine Design

## 9.1 Process Definition

Each business process is defined as a workflow model.

A workflow definition contains:

- Process key
- Process name
- Version
- Start conditions
- Tasks
- Gateways
- Events
- Assignments
- Deadlines
- Notifications
- Business rules
- End conditions

---

## 9.2 Task Types

| Task Type | Description |
|---|---|
| User Task | Requires human action |
| Service Task | Calls external system |
| Script Task | Executes internal logic |
| Approval Task | Approve/reject action |
| Review Task | Review and comment |
| Signature Task | Digital signature |
| Wait Task | Waits for timer or event |
| Notification Task | Sends alert |
| Routing Task | Determines next route |

---

## 9.3 Approval Patterns

The workflow engine should support common approval patterns:

### Sequential Approval

```text
Manager → Finance → Director
```

### Parallel Approval

```text
       → Legal
Start  → Finance
       → Risk
       → End when all approved
```

### Conditional Approval

```text
If amount > 10,000,000 IDR → Director approval required
If amount <= 10,000,000 IDR → Finance approval only
```

### Delegation

```text
If manager is absent → delegate to assigned substitute
```

### Majority Approval

```text
At least 3 of 5 committee members must approve
```

### Escalation

```text
If no action within 48 hours → escalate to superior
```

---

## 9.4 Business Rules Engine

The workflow engine may call a rules engine to determine routing.

Example rules:

| Rule | Result |
|---|---|
| Amount > 10,000,000 IDR | Requires Director approval |
| Department = IT | Route to IT Manager |
| Contract type = international | Route to Legal Director |
| Risk level = high | Add Risk Officer approval |
| Employee grade < 3 | Requires Supervisor approval |

# 16. Workflow Engine Responsibilities in Detail

The workflow engine should act as the **central brain** of the system.

## It should manage:

### 1. Process Start

When a document is submitted, the engine determines which workflow definition applies.

Example:

```text
Document Type = Purchase Requisition
Amount > 10,000,000 IDR
Department = Finance

Selected Workflow = High-Value Purchase Approval Workflow v2
```

---

### 2. Task Generation

The engine creates tasks for users or groups.

Example:

```text
Task: Approve Purchase Requisition
Assignee: Department Manager
Due Date: +2 business days
Priority: Normal
Document: PR-2026-000123
```

---

### 3. Decision Evaluation

The engine evaluates user decisions.

Example:

```text
If decision = Approve
    Move to Finance Review

If decision = Reject
    Set document status = Rejected
    Notify initiator
    End process
```

---

### 4. Deadline Monitoring

The engine monitors due dates.

Example:

```text
If task not completed within 48 hours:
    Send reminder

If still not completed after 72 hours:
    Escalate to supervisor
```

---

### 5. Document Permission Update

At each workflow step, the engine can instruct the document module to update access rights.

Example:

```text
During Finance Review:
    Finance role = read/write
    Requester = read-only
    Other users = no access
```

---

### 6. History and Evidence

The engine stores all process evidence.

Example:

```text
Step: Department Manager Approval
User: John Doe
Action: Approved
Time: 2026-08-05 10:25
Comment: Budget available
Digital signature: Yes
```
