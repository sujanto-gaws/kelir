# Concept: Handling Attachments, Comments and Activity Log

**Status:** Draft · **Last updated:** 2026-08-05

Below is a practical concept for handling:

1. **Attachments**: files or other documents linked to a specific document.
2. **Comments**: user discussion, notes, remarks, or clarifications.
3. **Activity logs / audit trail**: every action performed on the document.

This fits into the earlier document-based business application concept where the **workflow engine controls document movement**, while the document module stores content, relationships, comments, and history.

---

# 1. Concept Overview

For every business document, the system should maintain four related collections:

```text
Document
  ├── Attachments / Files
  ├── Related Documents
  ├── Comments / Notes
  └── Activity Log / Audit Trail
```

Example:

```text
Purchase Requisition PR-2026-000123
  ├── Attachment: Quotation.pdf
  ├── Attachment: BudgetApproval.xlsx
  ├── Related Document: Vendor Master V-1005
  ├── Comment: Please use approved vendor.
  └── Activity Log: Submitted, Approved, Viewed, Downloaded
```

---

# 2. Attaching Files to a Document

There are two common types of attachments.

## 2.1 File Attachment

A file attachment is a physical file uploaded to the document.

Examples:

- PDF
- Word document
- Excel file
- Image
- Scanned document
- ZIP file
- Email file

Example:

```text
Document: Contract Request CR-2026-000789
Attachment: Draft Agreement.pdf
Attachment: Vendor Profile.pdf
Attachment: Risk Checklist.xlsx
```

---

## 2.2 Document Reference / Related Document

A document reference is a link to another document already registered in the system.

Examples:

- A purchase requisition linked to a vendor document.
- A contract linked to a legal policy document.
- An invoice linked to a purchase order document.
- A complaint linked to a previous case document.

Example:

```text
Invoice INV-2026-000456
Related Document: Purchase Order PO-2026-000123
Related Document: Goods Receipt GR-2026-000889
Related Document: Vendor Master V-1002
```

This is better than uploading duplicate files because the related document remains controlled by its own lifecycle, versioning, permissions, and workflow.

# 4. Related Document Data Model

Use a `document_relations` table to link one document to another.

```text
document_relations
--------------------------------------------------
relation_id
source_document_id
target_document_id
relation_type
created_by
created_at
remarks
```

Common relation types:

| Relation Type | Meaning |
|---|---|
| RELATED_TO | General relationship |
| SUPPORTS | Document supports another document |
| BASED_ON | Document is based on another document |
| SUPERSEDES | New document replaces old document |
| PARENT_OF | Document is parent of another document |
| CHILD_OF | Document is child of another document |
| REFERENCE | Read-only reference |
| REQUIRED_FOR | Required by another document |

Example:

```json
{
  "relation_id": "REL-5001",
  "source_document_id": "DOC-2026-000456",
  "target_document_id": "DOC-2026-000123",
  "relation_type": "BASED_ON",
  "created_by": "finance.ali",
  "created_at": "2026-08-05T10:15:00Z",
  "remarks": "Invoice INV-2026-000456 refers to approved purchase order PO-2026-000123."
}
```

# 5. Attachment Flow

## 5.1 Upload File to Document

```text
User opens document
  ↓
User clicks Attach File
  ↓
User selects file
  ↓
System validates file type and size
  ↓
System uploads file to storage
  ↓
System calculates checksum
  ↓
System creates attachment record with virus_scan_status: PENDING
  ↓
System links attachment to document
  ↓
System writes activity log
  ↓
System publishes event: Attachment.Added
  ↓
Virus scan completes asynchronously and updates virus_scan_status
```

The attachment is unavailable for download until the virus scan status is CLEAN.

---

## 5.2 Attach Existing Document

```text
User opens document
  ↓
User clicks Link Existing Document
  ↓
User searches for another document
  ↓
System checks permission to link
  ↓
System creates document relation
  ↓
System writes activity log
  ↓
System publishes event: Document.Linked
```

```http

```

The system must check:

- User has access to the parent document.
- User has permission to download the attachment.
- Attachment is not deleted.
- Attachment is not under legal hold.

## 6.4 Delete or Remove Attachment

Use soft delete instead of physical delete.

```http
DELETE /documents/{documentId}/attachments/{attachmentId}
```

Example response:

```json

  "status": "DELETED",
  "deletedAt": "2026-08-05T11:00:00Z",
  "deletedBy": "manager.sara"
}
```

For compliance, keep metadata and audit trail even if the file is removed.

# 8. Attachment Rules in Workflow

The workflow engine can enforce attachment requirements.

Example:

```text
Purchase Requisition Workflow

Before submission:
- At least one quotation attachment is required if amount > 1,000.
- Budget approval attachment is required if budget category is CAPEX.

Before final approval:
- Signed approval sheet must be attached.
```

Example workflow condition:

```text
IF document.amount > 10000
AND attachment.category = "Quotation" DOES NOT EXIST
THEN block submission
```

This ensures documents are complete before entering the workflow.

# 9. Commenting Concept

Comments are used for discussion, clarification, notes, and internal communication.

Important rule:

> Comments should not replace formal approval actions. Approvals and rejections should still be recorded through workflow tasks.

For example:

```text
Comment:
"Please confirm whether this vendor is approved."

Workflow action:
Approve / Reject / Return
```

# 11. Comment Types

Useful comment types (this is the canonical list referenced by the `comment_type` column in Section 10.1):

| Type | Purpose |
|---|---|
| COMMENT | General remark |
| NOTE | Informational note |
| QUESTION | Requires answer |
| ISSUE | Problem or concern |
| CLARIFICATION | Request for explanation |
| APPROVAL_NOTE | Explanation attached to approval |
| REJECTION_NOTE | Explanation attached to rejection |
| INTERNAL_NOTE | Not visible to requester or external users |

External visibility is not a comment type; it is controlled by the separate `visibility` column (internal, external, restricted).

# 13. Comments in Workflow

When an approver approves or rejects a task, the system can store the comment together with the workflow decision.

Example:

```text
Workflow Task: Department Manager Approval

Action: Approved
Comment: Budget is available. Please proceed.
```

The system should record both:

```text
Workflow decision:
Task approved by manager.sara

Comment:
"Budget is available. Please proceed."
```

This gives better audit evidence.

# 14. Activity Log Concept

Activity log records what happened to the document.

It is different from comments.

| Feature | Purpose |
|---|---|
| Comments | Human discussion |
| Activity Log | System and user actions |
| Audit Trail | Formal immutable compliance record |

# 17. Audit Trail vs Activity Log

For enterprise systems, separate them.

## Activity Log

User-friendly timeline.

Example:

```text
2026-08-05 09:00 - John created document
2026-08-05 09:05 - John uploaded quotation.pdf
2026-08-05 09:10 - John submitted document
2026-08-05 10:30 - Sara approved document
```

---

## Audit Trail

Formal, immutable, compliance-ready record.

Example:

```text
Event ID: AUD-100001
Document: PR-2026-000123
Action: APPROVED
Actor: manager.sara
Timestamp: 2026-08-05T10:30:00Z
Previous Status: PENDING_MANAGER
New Status: PENDING_FINANCE
Digital Signature: SIG-8891
Checksum: sha256:5c9e...
Previous Event Hash: sha256:aa34...
Current Event Hash: sha256:98fe...
```

The audit trail can be append-only and tamper-evident.

# 19. How to Record Activity Reliably

Use the **transactional outbox pattern**.

Flow:

```text
User performs action
  ↓
Application updates document data
  ↓
Application writes event to outbox table in same transaction
  ↓
Event publisher reads outbox
  ↓
Event is sent to activity log, search index, notification service
```

Example:

```text
Transaction:
1. Update document status
2. Create workflow task
3. Insert activity event into outbox
Commit

Then asynchronously:
4. Publish event
5. Update search index
6. Send notification
7. Store audit record
```

This prevents missing logs if a process fails.

# 23. Security Controls for Attachments

When accepting file uploads, apply these controls:

## File Validation

- Maximum file size limit
- Allowed file types
- MIME type validation
- File extension validation
- File name sanitization
- Malware scanning
- Password-protected file handling
- Duplicate detection using checksum

---

## Storage Security

- Store files outside web root
- Use object storage
- Encrypt files at rest
- Use HTTPS for download
- Use short-lived signed URLs
- Record download access
- Prevent direct public access

---

## Integrity

Store checksum:

```text
sha256
```

When downloading or auditing, verify:

```text
Stored checksum == Current file checksum
```

This proves the file has not been changed.

# 24. Document Version vs Attachment Version

Important distinction:

## Document Version

The main business document version changes.

Example:

```text
Contract Draft v1
Contract Draft v2
Contract Draft v3
```

## Attachment Version

A supporting file changes.

Example:

```text
Technical Specification v1
Technical Specification v2
```

If an attachment is a major controlled document, it may be better to register it as a standalone document and link it instead of treating it as a simple attachment.

Rule:

> If the file has its own workflow, approval, retention, or access control, make it a document.  
> If it is only supporting evidence, make it an attachment.

# 28. Best Practices

## For Attachments

1. Do not store large files directly in the main database.
2. Store file metadata in database and file content in object storage.
3. Use checksums for integrity.
4. Scan files for malware.
5. Keep attachment history if required for compliance.
6. Use soft delete, not hard delete.
7. Separate simple attachments from controlled documents.
8. Allow workflow rules to require certain attachments.

---

## For Comments

1. Use comments for discussion, not as final approval evidence.
2. Store approval comments with workflow task decisions.
3. Allow threaded comments.
4. Support mentions and notifications.
5. Allow internal-only and external-visible comments.
6. Do not hard delete comments in regulated environments.
7. Track edited comments.
8. Allow comments to be linked to tasks or attachments.

---

## For Activity Logs

1. Use append-only event storage.
2. Record who, what, when, where, and why.
3. Separate normal activity log from formal audit trail.
4. Include old and new values for important changes.
5. Store workflow events together with document events.
6. Use event correlation ID to trace related actions.
7. Protect audit logs from modification.
8. Provide timeline UI for users and detailed audit UI for auditors.

# 29. Final Concept Statement

In the document-based business application system:

> Each document can have attached files, linked documents, comments, and a complete activity history. Attachments are stored as metadata records linked to the document, with files kept in secure storage. Related documents are stored as document relationships. Comments are stored as discussion records linked to the document, task, or attachment. Activity logs and audit trails are event-based records that capture every user, system, and workflow action performed on the document.

This gives the system full traceability:

```text
What document?
Who acted?
What was attached?
What was commented?
What workflow step happened?
When did it happen?
What was the previous state?
What is the new state?
```
