# JSON Form Schema Specification (JFSS)
**Version:** 2.0.1  
**Status:** Final Standard  
**Target Stack:** Vue.js (Frontend), Rust (Backend)  
**Last updated:** 2026-08-21 (errata E-1; see Section 13)

---

## 1. Introduction

The JSON Form Schema Specification (JFSS) is a deeply nested, component-driven data structure used to define the layout, validation, conditional logic, and calculations of dynamic forms. It operates as a **single source of truth**, consumed natively by frontend rendering engines for UI generation and by backend services for strict payload validation and security enforcement.

### 1.1 Core Philosophy

- **Component-Driven:** Every visual and interactive element is a discrete, self-describing component.
- **Role-Based:** Components are strictly categorized by their functional role (`data`, `layout`, `display`, `action`).
- **Scoped Validation:** Validation rules are co-located with UI components, utilizing a strict scope taxonomy (`client`, `server`, `both`) to balance UX performance with backend security.
- **Tamper-Proof Calculations:** Mathematical aggregations and derived fields are defined via JSON Logic, evaluated reactively on the frontend, and strictly recalculated/overwritten on the backend.
- **Deterministic State Resolution:** A strict priority precedence governs how field values are initialized, computed, and persisted, eliminating ambiguity between default values, existing payloads, and calculations.
- **Polyglot Compatible:** The schema relies on standard data types, JSON Schema-aligned validation keywords, and JSON Logic for conditionals and calculations, ensuring identical parsing in a statically typed backend (Rust) and a reactive frontend (Vue).

### 1.2 Definitions, Acronyms, and Abbreviations

To ensure semantic clarity across all frontend and backend implementations, the following terms are strictly defined within the context of this specification.

#### 1.2.1 Acronyms and Abbreviations

| Acronym | Full Term | Context in JFSS |
| :--- | :--- | :--- |
| **JFSS** | JSON Form Schema Specification | The formal name of this document and the schema standard it defines. |
| **RBAC** | Role-Based Access Control | Used in the context of `server`-scoped validation rules (e.g., `authorized`). |
| **UX / UI** | User Experience / User Interface | Refers to the frontend Vue.js rendering and interaction layer. |
| **DOM** | Document Object Model | The browser's representation of the UI; JFSS components map to DOM elements. |
| **AST** | Abstract Syntax Tree | The deeply nested JSON structure of the form schema. |
| **CRUD** | Create, Read, Update, Delete | Standard database operations; JFSS payloads are designed to map cleanly to these. |

#### 1.2.2 Core Architectural Definitions

| Term | Definition |
| :--- | :--- |
| **Component** | The fundamental, discrete building block of the form schema. Every visual element, layout container, or data input is a Component. |
| **Role** | A strict categorical tag (`data`, `layout`, `display`, `action`) assigned to every Component, dictating how it is processed by the rendering engine and the backend parser. |
| **Node** | A single instance of a Component within the deeply nested JSON tree. |
| **Polyglot Parity** | The architectural guarantee that a schema definition yields the exact same behavioral and security outcomes whether evaluated in JavaScript (Vue) or Rust. Two runtimes, not three — but the guarantee is unchanged: the language boundary is where a schema silently means two different things. |
| **Single Source of Truth** | The principle that the JFSS JSON file is the only authoritative definition for both the UI layout and the data validation contract. |

#### 1.2.3 State and Data Definitions

| Term | Definition |
| :--- | :--- |
| **Payload** | The JSON object generated by the frontend upon form submission, containing the `key` of **every** `data` component, visible or not (S10.1). Flat except for array/repeater types, which submit an array of objects. |
| **Existing Payload** | The persisted data loaded from the backend database when opening a form in "Edit Mode". Consumed by Value Resolution (S4.2.3). |
| **Derived State** | A field carrying `calculate` with `calculateMode: "derived"` (the default). Recomputed whenever its dependencies change; the computed value *always* wins over user input, Existing Payload and `defaultValue` (S4.2.3, Case B). |
| **Generated State** | A field carrying `calculate` with `calculateMode: "generated"`, produced by a non-deterministic operator (e.g. `generateInvoiceId`). Evaluated *once*, and only when the Existing Payload is null or absent; a persisted value is never recomputed (S4.2.3, Case C). |
| **Value Resolution Precedence** | The decision procedure that determines a field's value, branching on whether it carries `calculate` and in which mode (S4.2.3). |
| **Dot-Notation Path** | A string format used to address deeply nested or array-specific data and errors (e.g., `line_items.2.product_sku`). |

#### 1.2.4 Security and Validation Definitions

| Term | Definition |
| :--- | :--- |
| **Scope Taxonomy** | The classification of validation rules into `client`, `server`, or `both` to optimize performance and enforce security boundaries. |
| **Tamper-Proof Pattern** | The security mechanism where the backend re-evaluates the `calculate` JSON Logic using raw payload data and overwrites the result before database insertion. |
| **Custom Operator** | A non-standard JSON Logic operator registered in the runtime libraries. Requires an explicit implementation on both sides — the Vue evaluator and the Rust one — or the expression means one thing in the browser and another in the database. |

### 1.3 Conformance

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **MAY**, and **OPTIONAL** in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

An implementation is **conformant** if it:

1. Accepts every form definition that validates against the JFSS Meta-Schema for its declared `version`, and rejects every one that does not.
2. Implements the Value Resolution Precedence of S4.2.3 exactly.
3. Enforces the Scope Taxonomy of S6.1, treating `server` and `both` rules as security boundaries rather than UX hints.
4. Produces identical validation outcomes to any other conformant implementation for the same schema and payload (**Polyglot Parity**, S1.2.2).

Where this document and the Meta-Schema disagree, **the Meta-Schema is normative**.

## 3. Component Taxonomy (Roles)

Every component must declare a `role`. This dictates how the frontend renderer processes the node, how state is bound, and how the backend parser extracts data.

| Role | Description | Produces Data? | Contains Children? |
| :--- | :--- | :--- | :--- |
| `data` | Input fields that collect, validate, and store user data. | **Yes** | No (except array/repeater types) |
| `layout` | Structural containers used to arrange and group child components. | No | **Yes** |
| `display` | Informational elements, static text, or computed read-only summaries. | No | No |
| `action` | Interactive triggers (buttons, links) that execute form logic. | No | No |

## 4. Component Properties

### 4.1 Base Properties (Inherited by All Roles)

| Property | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `id` | `string` | Yes | Globally unique identifier for the component *instance*. Used for UI tracking and Vue's `:key`. |
| `role` | `string` | Yes | Enum: `data`, `layout`, `display`, `action`. |
| `type` | `string` | Yes | The specific component type (e.g., `textfield`, `panel`, `button`, `datagrid`). |
| `conditional` | `object` | No | Rules dictating the runtime visibility or state (See Section 7). |

### 4.2 Data Components (`role: "data"`)

| Property | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `key` | `string` | Yes | The property name in the final submitted data payload. Must be unique across the form. MUST match `^[A-Za-z_][A-Za-z0-9_]*$`; `.` is reserved as the dot-notation path separator (S8.2, S10.3) and a key containing one is ambiguous. Form-wide uniqueness cannot be expressed in JSON Schema and MUST be enforced by the authoring tool. |
| `label` | `string` | Yes | Human-readable label for the UI. |
| `placeholder` | `string` | No | Helper text displayed inside the input when empty. |
| `description` | `string` | No | Contextual help text displayed below the input. |
| `defaultValue` | `any` | No | The initial value for the field when the form is first mounted or reset. Must match the `type` defined in `validation`. |
| `validation` | `object` | Yes | The basic validation contract (See Section 5). |
| `options` | `array` | Conditional | Required for `select`, `radio`. Array of `{label, value}` objects. |
| `rules` | `array` | No | Advanced validation rules with explicit execution scopes (See Section 6). |
| `calculate` | `object` | No | A JSON Logic expression to dynamically compute the value (See Section 8). |
| `calculateMode` | `string` | No | Enum: `derived`, `generated`. Declares how `calculate` participates in Value Resolution (S4.2.3). Defaults to `derived`. |
| `readOnly` | `boolean` | No | If `true` (or if `calculate` is present), the field cannot be manually edited. Note: for `calculateMode: "generated"` fields, `readOnly` means populated-once-by-server rather than classically read-only (S4.2.3, Case C). |
| `sequenceKey` | `string` | No | The `key` of a child `data` component to auto-populate with the 1-based row index. (Array/repeater types only). |
| `defaultItems` | `integer` | No | The number of empty item objects to initialize in the array on form mount if currently empty. (Default: `0`). |

#### 4.2.1 Auto-Sequencing & Initialization Rules
1. **Sequence Enforcement:** If `sequenceKey` is defined, the frontend engine *must* overwrite the value of that child key with `index + 1` whenever the array length changes or order changes.
2. **Backend Parity:** The backend *must not* trust the submitted `sequenceKey` values. Upon receiving the payload, the backend must re-evaluate the array order and overwrite the `sequenceKey` values to ensure strict sequential integrity.
3. **Initialization:** If `defaultItems > 0` and the incoming payload lacks this array, the backend must initialize it with `N` empty objects matching the child schema structure before processing.

#### 4.2.2 Default Value Rules
1. **Frontend Mounting:** When the Vue renderer initializes the form state, it must check for `defaultValue`. If the field key does not exist in the initial payload, it must be populated with this value.
2. **Type Safety:** The `defaultValue` must match the `type` defined in the `validation` object.
3. **Backend Merging:** If the backend receives a payload where a `required` field is missing but has a `defaultValue` defined, the backend *may* merge this default value before validation.

#### 4.2.3 Value Resolution Precedence

Resolution is **not** a single ordered list: a field's behaviour depends on whether it carries a `calculate` expression, and if so, in which mode. Implementations MUST apply the following decision procedure. It is written as a procedure precisely so that a Vue and a Rust implementation cannot diverge.

**Case A - `calculate` absent.** The field is user-editable. Resolve once, on mount, taking the first available of:

| Priority | Source | Notes |
| :---: | :--- | :--- |
| **1** | Runtime User Input | Any subsequent edit by the user wins permanently. |
| **2** | Existing Payload | Edit Mode pre-fill. |
| **3** | `defaultValue` | Create Mode fallback. |

**Case B - `calculate` present with `calculateMode: "derived"` (the default).** The field is *Derived State*. It MUST be `readOnly`, and the expression is re-evaluated whenever any of its dependencies change. The computed value **always wins** - over Runtime User Input, Existing Payload, and `defaultValue` alike. There is no priority list, because no other source may ever take effect.

**Case C - `calculate` present with `calculateMode: "generated"`.** The field is *Generated State* produced by a non-deterministic operator (e.g. `generateInvoiceId`). Non-deterministic operators are defined in the Calculation Rule Registry's "Generated (Non-Deterministic) Operators" tier. Resolve once, taking the first available of:

| Priority | Source | Notes |
| :---: | :--- | :--- |
| **1** | Existing Payload | A persisted generated value is **never** recomputed or overwritten. |
| **2** | `calculate` | Evaluated exactly once, only when the Existing Payload is null or absent. |
| **3** | `defaultValue` | Fallback if the operator yields null. |

**Why `calculateMode` is explicit.** In v2.0.0 the distinction between Derived and Generated state was inferred from whether the operators inside the expression were deterministic. That required every implementation, in every language, to maintain an identical operator classification, and to re-derive it by walking the whole expression tree on every resolution. The Calculation Rule Registry (v1.2.0) now includes a Generated (Non-Deterministic) tier alongside Base, Extended, and Forbidden, but the mode is still declared on the component rather than inferred: declaring `calculateMode` removes the need for every implementation to re-derive determinism by walking the expression tree. Implementations MUST treat a missing `calculateMode` as `derived`.

### 4.3 Layout Components (`role: "layout"`)

| Property | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `components` | `array` | Conditional | An ordered array of child Component Objects. Used by single-slot containers (e.g. `panel`, `fieldset`). |
| `columns` | `array` | Conditional | **Positional slots.** An ordered array of `{ "components": [...] }` objects, one per column. Used by `columns`. |
| `tabs` | `array` | Conditional | **Named slots.** An ordered array of `{ "title": string, "components": [...] }` objects, one per slot. Used by any type whose children are addressed by name — `tabs`, and sequential types such as `steps` where slot order is the step order. |
| `title` | `string` | No | Header text for containers like `panel` or `fieldset`. |
| `grid` | `object` | No | CSS Grid/Flexbox configuration (e.g., `columns`, `gap`). |

A layout component MUST declare **exactly one** of `components`, `columns`, or `tabs`.

#### 4.3.1 Child Container Shapes

These three shapes are the complete, closed set of ways a component may hold children. A conformant implementation MUST traverse all three wherever it walks the component tree - resolving `{"var": ...}` references, detecting duplicate `key`s, building the `calculate` dependency graph, and locating a node by `id`. Traversing only `components` will silently ignore every child nested inside a `columns` or `tabs` container.

A `data` component of an array/repeater type (e.g. `datagrid`) uses `components` to declare its **row template**; that array is a schema definition repeated per row, not a set of sibling fields.

### 4.4 Display Components (`role: "display"`)

| Property | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `content` | `string` | Conditional | The text or HTML content to render. Required for text-bearing display types (e.g. `heading`, `paragraph`) when `calculate` is absent. Purely presentational types that render no text (e.g. `divider`, `spacer`) MUST omit both. |
| `variant` | `string` | No | Styling variant (e.g., `info`, `warning`, `h1`, `p`). |
| `calculate` | `object` | No | A JSON Logic expression to dynamically compute the displayed value. |

Because `type` is an open vocabulary defined by each implementation's component registry, the Meta-Schema cannot decide which display types are text-bearing and therefore does not enforce this rule. It is a **registry-level** constraint: the authoring tool MUST reject a text-bearing type that has neither `content` nor `calculate`.

### 4.5 Action Components (`role: "action"`)

| Property | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `label` | `string` | Yes | The text displayed on the button/link. |
| `action` | `string` | Yes | The event to trigger (e.g., `submit`, `reset`, `navigate`). |
| `theme` | `string` | No | Visual styling (e.g., `primary`, `secondary`, `danger`). |

## 5. Basic Validation & Type System

The `validation` object within `data` components strictly adheres to standard JSON Schema keywords. These rules are implicitly scoped to **`both`**.

| Keyword | Type | Applies To | Description |
| :--- | :--- | :--- | :--- |
| `type` | `string` | All | Base data type: `string`, `number`, `integer`, `boolean`, `array`, `object`. |
| `required` | `boolean` | All | If `true`, the field must be present and non-empty in the payload. |
| `minLength` | `integer` | `string` | Minimum character count. |
| `maxLength` | `integer` | `string` | Maximum character count. |
| `minimum` | `number` | `number` / `integer` | Minimum numeric value. |
| `maximum` | `number` | `number` / `integer` | Maximum numeric value. |
| `pattern` | `string` | `string` | Regular expression the string must match (ECMA 262 standard). |
| `format` | `string` | `string` | Semantic format: `email`, `uri`, `date`, `time`, `date-time`, `uuid`. |
| `enum` | `array` | All | An exhaustive list of allowed values. |
| `uniqueItems` | `boolean` | `array` | Standard JSON Schema. If `true`, every item in the array must be distinct. |
| `uniqueBy` | `string` / `array` | `array` | **JFSS Extension.** Specifies the child key(s) that must be unique within the array. |
| `messages` | `object` | All | Custom error messages overriding defaults. |

## 7. Conditional Logic (JSON Logic)

Conditional logic dictates runtime behavior (e.g., visibility, enablement) without altering the underlying data schema. The schema adopts **JSON Logic** as the standard evaluation engine.

### 7.1 Core Definitions

| Property | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `action` | `string` | Yes | The runtime effect: `show`, `hide`, `enable`, `disable`. |
| `logic` | `object` | Yes | A valid JSON Logic expression evaluating to a boolean. |

### 7.2 Mapping Logic to Data

The `{"var": "..."}` operator accesses data. The string inside `var` **must exactly match the `key`** of a `role: "data"` component.

## 8. Computed Elements & Array Calculations

To support dynamic calculations, components use the `calculate` property, which holds a **JSON Logic expression**.

### 8.1 The Security Boundary (Tamper-Proof Pattern)

1. **Frontend:** Evaluates the `calculate` logic reactively to update the UI instantly.
2. **Backend:** **Must not trust** the calculated value submitted by the frontend. The backend must re-evaluate the exact same JSON Logic expression using the submitted raw data and **overwrite** the payload value before database insertion.

#### 8.1.1 Custom & System Operators
System generators (like Invoice IDs) are non-deterministic. A component whose `calculate` uses one MUST declare `calculateMode: "generated"` (S4.2.3, Case C): it is evaluated exactly once, during initial creation or when the existing payload value is null, and a persisted value is never recomputed.

Implementations MUST branch on the declared `calculateMode`, **not** on whether the operators inside the expression look deterministic. Inferring it would require every language to maintain an identical operator classification, and the Calculation Rule Registry does not carry one.

If the backend encounters an unknown custom operator, it MUST reject the payload with `400 Bad Request`.

### 8.2 Array Access & Aggregation

JSON Logic uses **dot-notation** for array access (zero-indexed). Array aggregation requires extended operators (`sum`, `map`) which must be implemented natively in all backend languages.

| Target | JSON Logic Expression |
| :--- | :--- |
| First element of `a` | `{ "var": "a.0" }` |
| Sum of computed line items | `{ "sum": [ { "map": [ { "var": "items" }, { "*": [ { "var": "unit_price" }, { "var": "quantity" } ] } ] } ] }` |

**Null-Safety Rule:** If an array is empty or contains non-numeric values, `sum` must return `0` (not `null` or `NaN`).

## 9. Cross-Language Implementation Guidelines

### 9.1 Frontend (Vue.js)

- **Rendering:** Recursive component switching on the `role` property.
- **State Management:** Bind `data` components to a centralized reactive store using the `key`. Use `id` for Vue's `:key`.
- **Value Resolution on Mount:** Follow the decision procedure in S4.2.3, branching on `calculate` and `calculateMode`.
- **Conditional & Calculation:** Use `json-logic-js`, wrapping evaluations in Vue `computed` or `watch`. Build the dependency graph once from every `{"var": ...}` reference - it is already required for cycle detection (S12.2) - and recompute only the fields downstream of a change. Re-evaluating every `calculate` on every keystroke is O(fields x rows) on a form containing a datagrid.
- **Validation:** Filter the `rules` array by `scope`. Build dynamic Zod/Yup schemas.
- **Array Sequencing & Uniqueness:** Intercept array mutations to enforce `sequenceKey` and real-time `uniqueBy` checks.

### 9.2 Backend (Rust)

- **Parsing:** Ignore `layout`, `display`, and `action` roles during payload validation.
- **Default Merging & Sequence Overwrite:** Apply `defaultValue` for missing keys. Overwrite `sequenceKey` values to guarantee sequential integrity.
- **Scoped Enforcement:** Filter the `rules` array by `scope`. Execute database queries for `server` rules.
- **Calculation Overwrite:** Re-evaluate every `calculate` in **topological order** of the dependency graph, so a chain (`c` depends on `b` depends on `a`) converges in a single pass. Overwrite the payload value for `calculateMode: "derived"` (the default); for `"generated"`, evaluate only when the existing payload value is null.
- **Conditional Stripping:** Re-evaluate every `conditional` against the **complete** submitted payload, then discard the value of each component that resolves to hidden - treating it as absent for validation and never persisting it. A hidden component's `key` being present is expected (S10.1) and MUST NOT by itself cause rejection; a user hiding a field after typing into it is a routine race, not an attack. An implementation MAY offer a strict mode that returns `400 Bad Request` when a hidden component carries a non-null value, but this MUST NOT be the default.

## 10. Payload Contract & Security Boundaries

### 10.1 Submission Shape

The frontend MUST submit a JSON object containing the `key` of **every** `role: "data"` component in the schema, visible or not, carrying its current value. The object is flat except for array/repeater types (e.g. `datagrid`), which submit an array of objects keyed by their child components - addressed thereafter by dot-notation path (S10.3).

#### 10.1.1 Why Hidden Fields Are Submitted

It is tempting to omit hidden fields, and v2.0.0 required exactly that. It is not implementable. Consider field `B` whose `conditional` depends on field `A`, where `A` is itself hidden:

- The **frontend** evaluates `B`'s condition against its full reactive state, where `A = 5`.
- The **backend**, having received a payload with `A` omitted, zero-fills it (S12.4) and evaluates the same condition against `A = 0`.

The two engines reach different conclusions about `B` from the same schema, which violates **Polyglot Parity** (S1.2.2) - and under the v2.0.0 rejection rule, turns that divergence into a `400` on a legitimate submission.

Submitting every key guarantees both engines evaluate identical inputs. The backend is then responsible for discarding the values of components it computes as hidden (S10.2), so hidden data never reaches storage. Implementations that must not transmit a particular hidden value MAY omit it, but MUST accept that no conditional may then depend on that field.

### 10.2 Separation of Concerns

- **UI Visibility:** Handled by `conditional`. The frontend submits hidden fields anyway (S10.1.1); the **backend** re-evaluates visibility against the complete payload and discards the values of hidden components before validation and persistence.
- **Data Integrity:** Handled by `validation` and `rules`. Backend enforces strictly.
- **Calculations & Sequencing:** Handled by `calculate` and `sequenceKey`. Backend overwrites to prevent tampering.

### 10.3 Error Response Mapping (Including Row-Level Errors)

When the backend rejects a payload, it must return a standardized error response using **Dot-Notation Paths** for array-level errors:

```json
{
  "status": 400,
  "error": "VALIDATION_FAILED",
  "details": [
    { "path": "email", "rule": "unique", "code": "DUPLICATE_VALUE", "message": "This email is already registered." },
    { "path": "line_items.2.product_sku", "rule": "uniqueBy", "code": "DUPLICATE_IN_ARRAY", "message": "Duplicate SKU. First seen in row 1." }
  ]
}
```
The `path` field carries a **Dot-Notation Path**, which for array rows is not a bare `key`; it is named `path` to keep it distinct from the `key` property defined in S4.2. `code` is a stable machine-readable identifier the frontend may use to localize the error; `message` is a server-rendered fallback. The Vue frontend must resolve `path` to the exact field's error state.

## 11. Companion Documents (The Registries)

To maintain strict polyglot parity, the JFSS relies on two companion documents:

1. **Validation Rule Registry** (`docs/schema/JFSS Validation Rule Registry.md`) - the allowed strings for the `rule` property (e.g. `matchesField`, `unique`), their `params` schema, execution scope, and implementation requirements.
2. **Calculation Rule Registry** (`docs/schema/JFSS Calculation Rule Registry.md`) - the allowed JSON Logic operators for `calculate`, marking which are natively supported and which require custom backend implementation.

A third artefact is normative per S1.3: the **Meta-Schema**, `docs/schema/jfss-meta-v2.0.1.json`. That file is canonical; the listing at the end of this document is a verbatim copy of it kept for readability. If the two ever differ, the file wins.

## 12. Architectural Best Practices & Guardrails

1. **Strict Identity Separation:** Never confuse `id` (UI instance) with `key` (data payload). Layout components must have an `id` but never a `key`.
2. **Circular Dependency Prevention:** A schema whose `calculate` or `conditional` expressions form a dependency cycle is **invalid**. Implementations MUST build the graph from every `{"var": ...}` reference in both properties and MUST reject a cyclic schema; authoring tools SHOULD surface the cycle before it is saved.
3. **Dynamic Option Generation:** If a `select` has an `enum` in `validation`, the Vue component should auto-generate its `options` array if `options` is omitted.
4. **Handle Missing Variables:** Because the frontend submits every data `key` (S10.1), a missing variable indicates a schema/payload mismatch rather than a hidden field. The Rust backend MUST still resolve a missing key to a defined value before running JSON Logic evaluation, so that evaluation cannot panic; with `serde_json` that is `Value::Null` rather than a typed zero, and the normalization rule in the Calculation Rule Registry S7.3 is what turns it into a number. It MUST NOT rely on that filling to stand in for a hidden field, as that is precisely the substitution that breaks Polyglot Parity.
5. **Standard Operators Only:** Do not register a custom JSON Logic operation unless it is implemented in **both** runtimes — Vue and Rust — and registered in the Calculation Rule Registry. An operator only one side knows is not an extension; it is a divergence with a name.
6. **Separation of System vs. User Data:** System-generated fields (e.g., `Invoice#`) should be `role: "data"`, `readOnly: true`, and populated via non-deterministic `calculate` operators. Non-deterministic operators such as `generateInvoiceId` are defined in the Calculation Rule Registry's "Generated (Non-Deterministic) Operators" tier and may appear only in `calculateMode: "generated"` fields.
7. **Avoid Circular Sequencing:** Never use `sequenceKey` in combination with a `calculate` property on the *same* child field.

## 13. Errata

This specification is a **Final Standard**: frozen at v2.0.1, errata only, and a successor takes a new major version ([naming convention](../standards/02.%20Naming%20Convention.md) §10.1). Errata correct statements about the specification without changing what it specifies. None of the entries below alter a component, property, validation keyword, or the meta-schema, so `jfss-meta-v2.0.1.json` is unchanged and documents declaring `"version": "2.0.1"` are unaffected.

| # | Date | Correction |
|---|---|---|
| **E-1** | 2026-08-21 | **The target stack named two backend languages; there is one.** Every reference to Go or Golang is replaced with Rust — the header target stack, the §1 polyglot-compatibility claim, the §2 Polyglot Parity definition and the Custom Operator entry, the §4.2.3 decision-procedure rationale, the §9.2 backend heading, and guardrails 4 and 5 in §12. Guardrail 4's "initialize the payload map with default zero-values" was a Go idiom and is restated for `serde_json`, where a missing key resolves to `Value::Null` rather than a typed zero. Kelir's backend is Rust ([SDD](../design/01.%20System%20Design%20Document.md) §2, [architecture 01](../architectures/01.%20Basic%20Framework%20Concept%20and%20Architecture.md)); no Go service exists or is planned, and a parity claim for a language nobody compiles is how the companion registries' Rust column came to be wrong (see the [operator-parity spike](../../projects/spikes/01.%20JFSS%20Operator%20Parity.md) §2.8). **Polyglot Parity is not weakened by this** — it was never about the count of languages. One JavaScript runtime and one Rust runtime evaluate the same schema, and the boundary between them is still where a schema can silently mean two different things. |
