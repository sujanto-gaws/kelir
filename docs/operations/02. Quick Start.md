# Kelir Quick Start

**Status:** Living · **Last updated:** 2026-09-12

The shortest path from a clone to a document you have created, submitted and approved in a browser. It takes one sitting, and it needs Docker and nothing else.

This document is deliberately one path. [Installation and Deployment](01.%20Installation%20and%20Deployment.md) is the reference — every shape Kelir runs in, every variable it reads, every way it breaks — and this is the one route through it that answers *does this thing work*. Where the two could disagree, document 01 wins and this gets fixed.

Everything below has been run. Where a step exists only over the API because no screen has been built for it, it says so rather than describing a screen you would go looking for.

---

## 1. Before You Start

| You need | Why |
|---|---|
| Docker Engine + Compose v2 | Runs all five services. Nothing else is required — the Rust and Node toolchains in [01 §2](01.%20Installation%20and%20Deployment.md) are for working on the code, not for running it |
| Disk, and more than you expect | The backend's `target/` lives in a named volume and grows to tens of gigabytes over a long working session ([01 §9](01.%20Installation%20and%20Deployment.md) measured 74 GB on one machine). For this document's one pass it is far less, but a nearly-full disk surfaces as a linker error that reads like a code fault |
| A few minutes for the first start | The backend compiles in its container and the frontend installs its dependencies. Both are cached, so later starts are quick |

You do **not** need PostgreSQL, MinIO, or a mail server installed. The development stack runs all three.

## 2. Start the Stack

```bash
git clone https://github.com/sujanto-gaws/kelir.git
cd kelir
```

**Before the first `up`, write the administrator into a `.env`.** This is the step that decides whether you can sign in at the end, and it is the one step of this document that cannot be skipped and recovered from easily:

```bash
cat > deploy/docker/.env <<'EOF'
KELIR_BOOTSTRAP_ADMIN_USERNAME=admin
KELIR_BOOTSTRAP_ADMIN_PASSWORD=a-real-bootstrap-password
KELIR_BOOTSTRAP_ADMIN_EMAIL=admin@localhost
EOF
```

The password must be at least 12 characters — the same floor the API enforces on anybody else's — and the backend refuses to start if it is set and shorter. Set one of the username and password without the other and it refuses that too, which is the failure you want: half a credential on an account holding every permission is worse than none.

`.env` is ignored by git (`.gitignore` excludes `.env` and `.env.*`, admitting only the `*.example` templates), so this password cannot be committed by accident. Pick a real one anyway, and see *Clear the file* below for why it should not outlive your first sign-in.

Then:

```bash
docker compose -f deploy/docker/docker-compose.yml up
```

The first start takes a few minutes: the backend compiles in its container and the frontend installs its dependencies. Both land in named volumes, so this is a one-time cost. Migrations run automatically, and the administrator is created at the end of them.

**Why this is a manual step rather than a default.** The account holds every permission in the catalogue, so a password shipped in a tracked file would be a known credential on every developer's machine and, eventually, on something reachable. The bootstrap runs **only while the `users` table holds no row at all** — any tenant, counting deleted rows — so it does nothing on any later start, and it will not resurrect an administrator you removed.

**Clear the file once you have signed in.** `rm deploy/docker/.env`, or empty the two values. An empty value is read as *not configured* rather than as a placeholder, so the stack starts exactly the same way afterwards. This takes the password out of the environment and closes the one case the paragraph above leaves open: a database whose `users` table is later emptied by a restore or an import would otherwise bootstrap again, from a file nobody remembers writing.

> Until 2026-09-12 `deploy/docker/docker-compose.yml` did not pass these three variables into the container at all, so the `.env` above would have had no effect and the stack would have come up with no way in. The staging compose file had passed them since the release stack was first run on 2026-08-21 ([01 §5](01.%20Installation%20and%20Deployment.md)); this one had the same fault in the shape that is hit far more often — every developer's first start, rather than a release rehearsal. It went unnoticed for as long as it did because no document walked this path end to end and stated what should be true at the end of it, which is the gap this one fills.

## 3. Sign In

Open <http://localhost:5173> and sign in with the username and password from §2.

| Service | Where | Credentials |
|---|---|---|
| Kelir | <http://localhost:5173> | Yours, from §2 |
| API | <http://localhost:8080> | `/health` and `/api/docs/openapi.json` answer unauthenticated |
| Mailpit | <http://localhost:8025> | none — every message the stack sends lands here and leaves the machine never |
| MinIO console | <http://localhost:9001> | `minioadmin` / `minioadmin` |

**There is no tenant field, and that is correct.** `KELIR_MULTI_TENANT` is off in this stack, so sign-in resolves the default tenant and ignores a tenant code sent by a caller rather than obeying it. The field appears only when the mode is on — see [01 §7.1](01.%20Installation%20and%20Deployment.md).

**There is no "change your password" screen yet.** The account is flagged as needing a password change and nothing in the interface acts on the flag: `POST /auth/change-password` exists and no page calls it. Use *Forgot your password* on the sign-in page — the mail arrives in Mailpit on <http://localhost:8025>, so the link is one click away on a development stack. This is a gap, not a security control; §7 lists it with the others.

If the sign-in is refused, **read the backend's startup log before anything else** — `docker compose -f deploy/docker/docker-compose.yml logs backend`. It says in plain words whether it created an administrator, declined to because users already existed, or warned that nobody can sign in.

## 4. A Document, End to End

Five screens, in this order. They build the smallest thing that proves the product works: a form, a type that binds it, a document filled against it, and an approval.

### 4.1 Build a form, and publish it

**Forms → New.** Add a field or two — a short text and a number are enough — and **publish** the revision.

**Publishing is what makes it bindable.** A document type chooses from published forms only, so a draft revision will not appear in §4.2's chooser and the trail goes cold with nothing on screen explaining why. A published revision is also immutable, which is the point: a document pins the exact revision it was filled against, and an old document re-renders against that revision rather than against whatever the type binds today (**ADR-0027**).

### 4.2 Create a document type, and bind the form to it

**Document Types → New.** Give it a code and a name, set **Status** to `Active`, and pick your published form as its **Form**.

- **`Active`, not `Draft`.** The new-document chooser offers `ACTIVE` types and nothing else, so a type left at `Draft` is configured, visible to an administrator, and invisible to the person trying to use it. `Deprecated` is the other end of the same control: it stops new documents from a type while its existing ones keep working, which is the alternative to deleting a type — refused while documents exist.
- A type that binds **no** form is offered and cannot be started from; the screen says which rather than hiding the type, because a type is often configured before its form exists.
- **Leave *Workflow* empty for now.** §4.5 explains what changes when it is set, and why this quick start does not set it.

### 4.3 Set its numbering rule

On the type's row, open **Numbering**. A template, a scope and a padding — `PO-{year}-{sequence}`, scope `Year`, padding `6` is a reasonable shape.

The template understands `{sequence}`, `{year}`, `{month}` and `{department}`. **`{sequence}` is required** and a template without it is refused at save: it would name every document of the type the same thing, and the unique index on the number would then refuse the second one at submit time, having already done the work. An unknown placeholder is left in the output rather than blanked — `PR-{quarter}-000001` says which mistake was made, where `PR--000001` looks like a formatting bug somewhere else.

**Do this before you submit anything.** A submit assigns the business number, and a type with no numbering rule refuses the submit with a message naming what an administrator has to fix. That refusal is the product working, but it is a confusing place to meet it for the first time, so it is a step here rather than a troubleshooting entry. A type with no rule is an ordinary state, not an error — the read answers 404 and the dialog treats it as *not configured yet*, because the numbering is usually decided after the type exists.

Scope decides when the sequence restarts (`Global`, `Year`, `Month`, `Department and year`); the gap policy decides whether a failed submission gives its number back (`Gapless`) or leaves a hole (`Allow gaps`).

### 4.4 Create, fill and submit

**Documents → New**, choose your type, and the workspace opens with your form rendered in it. Fill it in and **Save**, then **Submit**.

The submit does three things: it validates the payload against the form's rules **on the server** — the browser's copy of the rules is a convenience and never the answer — it assigns the business number from §4.3, and it moves the document from `Draft` to `Submitted`.

A refusal lands where it belongs. A missing required field lands on the field; a refusal about the type lands as a message naming what to fix. Neither is flattened into *something went wrong*.

### 4.5 Approve it

With no workflow bound, the workspace offers the moves the backend will accept from where the document is. From `Submitted` those are **In review**, **Approved**, **Rejected**, **Returned** and **Cancelled**. Press **Approved**.

Then look at the tabs: **History** is the status changes, one row per transition; **Activity** is everything that happened to the document from all four sources. They are one word apart and answer different questions.

**What a real deployment does instead.** Bind an `ACTIVE` workflow definition to the type, and a submit starts a process: the document goes to `Pending approval`, the transition buttons disappear, and the way on is a task in **My Tasks** — claim it, then approve, reject or return it, with a comment where the definition requires one. The workflow owns the document's status while a process is live and a manual transition is refused (**ADR-0020**), which is why the buttons are gone rather than merely ignored.

**This quick start does not do that, because there is no workflow builder screen.** `rad_forms`, `rad_lists`, `rad_menus` and the document types all have one; workflow definitions are created and published over `/api/v1/workflow/definitions` and nothing in the interface writes one. Writing a definition by hand means reading the [JSON Workflow Schema](../schema/JSON%20Workflow%20Schema.md), which is a longer sitting than this document is for. §7 lists it as the gap it is.

## 5. Stopping, and Starting Over

```bash
docker compose -f deploy/docker/docker-compose.yml down          # stop; keep the data and the build caches
docker compose -f deploy/docker/docker-compose.yml down -v       # stop; delete the database, the objects and the caches
```

`down -v` is the way back to §2 — with the `users` table gone, the bootstrap runs again and your `.env` takes effect a second time. It also deletes the compiled backend and the installed frontend dependencies, so the next start pays the first start's compile again. Use plain `down` unless you actually want a clean database.

## 6. When It Does Not Work

[01 §9](01.%20Installation%20and%20Deployment.md) is the full list. These four are the ones this path meets:

**The stack is up and the sign-in is refused.** Almost always the `.env` from §2 — written after the first `up`, so the `users` table was not empty when the bootstrap looked and it stood down. The backend's startup log says which of the three happened in plain words: it created the administrator, it declined because users already existed, or nobody configured one. Read it first — `docker compose -f deploy/docker/docker-compose.yml logs backend`. If the bootstrap stood down, `down -v` and start again, which is cheap on a stack this young.

**`port is already allocated`, usually 5432.** A natively installed PostgreSQL is on it — common on developer machines, and Windows can run several versions at once. Move the container: `KELIR_POSTGRES_PORT=55433 docker compose -f deploy/docker/docker-compose.yml up`. Every host port is configurable for this reason; [01 §3](01.%20Installation%20and%20Deployment.md) lists them.

**An attachment uploads and cannot be downloaded.** It has not been scanned yet. An attachment stays undownloadable until ClamAV has passed it and the scan worker looks every five seconds, so a file uploaded in the first half-minute of a cold stack waits for the scanner rather than for itself — the image ships its own signature set and is ready about 20 seconds after start. There is no switch that turns scanning off, deliberately: an unreachable scanner leaves every attachment pending rather than releasing it unscanned, which is the direction this has to fail in.

**The backend container restarts in a loop.** It runs migrations at startup and exits if the database is unreachable. `docker compose ... logs backend` gives the reason on the last line.

## 7. What This Path Does Not Reach

Named here because each is a screen a reader will go looking for and not find, not because each is a defect.

- **A workflow builder.** Definitions are API-only (§4.5). Every other configuration surface has a screen.
- **Changing your own password.** The endpoint exists, no page calls it, and the *must change password* flag is set and unenforced (§3). An administrator can reset another account's password; you cannot yet change your own except through *Forgot your password*.
- **A dashboard.** The landing page is a placeholder that proves the API client works. The widgets — pending tasks, recent documents, a status chart — are Phase 8.
- **Anything deployed.** This is the development stack, on `localhost`, over plain HTTP, with `KELIR_APP_ENV=development` and placeholder secrets it would refuse to start with anywhere else. [01 §5](01.%20Installation%20and%20Deployment.md) is the shape a release is checked in; production is not covered by either document, because nothing has been built for it.
