# Kelir Installation and Deployment

**Status:** Living · **Last updated:** 2026-08-12

How to run Kelir, from a developer's machine to a deployed host. Release *policy* — versioning, changelog, tagging, the checklist that gates a release — lives in the [release process](../standards/04.%20Release%20Process.md); this document is the mechanics.

Everything described here exists in the repository and has been run. Where something is not built yet, it says so.

---

## 1. Choosing a Shape

Kelir runs in three shapes. They share the same code and, from §4 onward, the same images.

| Shape | Address | TLS | Use it for |
|---|---|---|---|
| **Development stack** (§3) | `localhost`, one port per service | none | Writing code. Source is mounted; the backend and frontend hot-reload |
| **Local deployment** (§5) | `http://<host-ip>:<port>` | none | Trying a release candidate, or showing someone on your network, before a tag exists |
| **Staging** (§6) | `https://staging.kelir.gawshub.com` | automatic | The environment the release checklist requires a pass from |

The last two run identical artifacts and differ only in address, port and environment name. That is deliberate: a test environment that differs from the real one mostly proves the difference works.

Production is not covered — nothing has been built for it yet. [SDD §13.2](../design/01.%20System%20Design%20Document.md) sketches the intended topology.

## 2. Prerequisites

| Component | Version | Needed for |
|---|---|---|
| Docker Engine + Compose v2 | current | Every shape |
| Rust | 1.89+ (images pin `rust:1.89`; edition 2021) | Building the backend outside Docker |
| Node.js | 24 (CI and the frontend image pin 24) | Building the frontend outside Docker |
| PostgreSQL | 16 | Development stack runs it in a container; staging installs it on the host |
| Ubuntu Server | 24.04 LTS | The staging host only |

Only Docker is required for §3 and §5 — the toolchains are for working on the code.

## 3. Development Stack

Runs all five services with the source trees mounted, so changes reload without rebuilding.

```bash
git clone https://github.com/sujanto-gaws/kelir.git
cd kelir
docker compose -f deploy/docker/docker-compose.yml up
```

| Service | URL |
|---|---|
| Frontend | <http://localhost:5173> |
| Backend | <http://localhost:8080> — try `/health` and `/api/docs/openapi.json` |
| PostgreSQL | `localhost:5432`, database `kelir`, user and password `postgres` |
| MinIO | <http://localhost:9000>, console on 9001, `minioadmin` / `minioadmin` |
| Mailpit | <http://localhost:8025> |

The first start takes a few minutes: the backend compiles inside its container and the frontend installs its dependencies. Both are cached in named volumes, so later starts are quick.

Migrations run automatically when the backend starts.

### Changing ports

Every host port is configurable, because the defaults collide with common local services. Set any of these in the environment or in a `.env` beside `docker-compose.yml`:

```bash
KELIR_POSTGRES_PORT=55433 KELIR_MINIO_PORT=9100 KELIR_MINIO_CONSOLE_PORT=9101 \
  docker compose -f deploy/docker/docker-compose.yml up
```

`KELIR_FRONTEND_PORT` · `KELIR_BACKEND_PORT` · `KELIR_POSTGRES_PORT` · `KELIR_MINIO_PORT` · `KELIR_MINIO_CONSOLE_PORT` · `KELIR_SMTP_PORT` · `KELIR_MAILPIT_UI_PORT`.

### Running a stack natively instead

Useful when iterating on one side and you want a debugger or a faster loop. Start the dependencies from compose first (`up -d postgres minio mailpit`), then:

```bash
# Backend — KELIR_JWT_SECRET has no default and startup fails without it
cd kelir-backend
KELIR_JWT_SECRET=change-me cargo run

# Frontend
cd kelir-frontend
npm install
npm run dev
```

CORS applies here and only here: the Vite dev server on `:5173` and the API on `:8080` are different origins. The backend allows exactly the origin in `KELIR_FRONTEND_URL`. Deployed shapes serve both from one origin, so CORS does not arise there at all.

## 4. Building Release Images

Both shapes below run the same two images. Build them from a clean checkout:

```bash
VERSION=0.1.0
SHA=$(git rev-parse --short HEAD)

docker build -f deploy/docker/backend.Dockerfile \
  --build-arg KELIR_BUILD_SHA="$SHA" \
  -t kelir-backend:"$VERSION" kelir-backend

docker build -f deploy/docker/frontend.Dockerfile \
  -t kelir-frontend:"$VERSION" kelir-frontend
```

`KELIR_BUILD_SHA` is not optional: it is what `/version` reports, and the release checklist compares that against the tag being released. Without it the endpoint reports `unknown`.

The deploy scripts in §5 and §6 build these for you when they are missing, so you rarely run this by hand.

## 5. Local Deployment by IP

Runs the release stack on your machine, reachable from other machines on the network by IP.

```bash
cd deploy/staging
cp .env.staging.example .env          # then fill in the secrets, see below
./deploy-local.sh 0.1.0               # auto-detects the host IP, port 8080
```

```bash
./deploy-local.sh 0.1.0 9090          # a different port
KELIR_HOST_IP=192.168.1.50 ./deploy-local.sh 0.1.0
KELIR_DB_PORT=55440 ./deploy-local.sh 0.1.0    # PostgreSQL somewhere else
```

The script prints the address it will use, deploys, and smoke-tests it.

**PostgreSQL is not part of this stack.** It expects one reachable at `host.docker.internal:5432` — the host's own install. Point it elsewhere with `KELIR_DB_HOST` and `KELIR_DB_PORT`. The role and database must exist already:

```sql
CREATE ROLE kelir WITH LOGIN PASSWORD '...';
CREATE DATABASE kelir OWNER kelir;
```

Two things necessarily differ from staging, and both are why this shape is for testing only:

- **Plain HTTP.** No certificate can be issued for an IP address, so [NFR-SEC-010](../requirements/srs.md) is not satisfied.
- **`KELIR_APP_ENV=development`.** Staging refuses placeholder secrets, which is right for an internet-facing host and needless friction on a laptop. Pass `KELIR_EXPECTED_ENV=staging` to exercise the stricter path.

It builds from your working tree rather than a tag — the point is to try a candidate before tagging it — and reuses images already present at that tag unless you pass `KELIR_FORCE_BUILD=1`.

## 6. Staging on Ubuntu Server 24.04

`kelir-staging-01` serves <https://staging.kelir.gawshub.com>. PostgreSQL runs natively on the host; everything else runs in containers behind Caddy.

### 6.1 Provision the host, once

```bash
# on a fresh Ubuntu 24.04 host
sudo ./provision-ubuntu-24.sh
```

It installs Docker Engine and PostgreSQL, creates the `kelir` role and database, restricts `pg_hba.conf` to the Docker address pool with `scram-sha-256`, opens only 22, 80 and 443, and installs a daily backup timer. It generates the database password and writes it to `/opt/kelir/.env`.

Re-running it is safe.

### 6.2 DNS

Point an **A record** for `staging.kelir.gawshub.com` at the host, and make sure **port 80 is reachable from the internet** — Caddy needs it for the ACME challenge. Certificates cannot be issued before DNS resolves.

### 6.3 Secrets

Copy the deployment files to `/opt/kelir`, then complete the env file the provisioner started:

```bash
cd /opt/kelir
$EDITOR .env        # KELIR_DB_PASSWORD is already set; add the rest
```

Generate each value rather than inventing one:

```bash
openssl rand -base64 36
```

### 6.4 Deploy

```bash
./deploy.sh 0.1.0
```

The script refuses to proceed on empty or placeholder secrets, takes a backup, builds or pulls the images, starts the stack, and runs the smoke test from release process §4 step 7 — including checking that `/version` reports the version and environment expected, not merely that it answers.

Deploying another version is the same command; so is rolling back:

```bash
./deploy.sh 0.0.9
```

### 6.5 Images on the host

With no registry configured, `deploy.sh` builds on the host. A Rust release build on a small VM is slow and competes with the running stack for memory. Once images are published somewhere, set `KELIR_IMAGE_REGISTRY` and the same script pulls instead — which is what the release process means by deploying the same artifacts rather than rebuilding them.

## 7. Configuration Reference

### 7.1 Backend

Read by the application itself. `KELIR_JWT_SECRET` has no default; every other value does.

| Variable | Default | Notes |
|---|---|---|
| `KELIR_APP_NAME` | `Kelir` | Reported by `/version` |
| `KELIR_APP_ENV` | `development` | `development`, `test`, `staging`, `production`. Staging and production refuse placeholder secrets |
| `KELIR_BIND_ADDRESS` | `0.0.0.0:8080` | |
| `KELIR_DATABASE_URL` | `postgres://postgres:postgres@localhost:5432/kelir` | The URL scheme is **not** validated — a typo surfaces as a readiness failure, not a startup error |
| `KELIR_JWT_SECRET` | *(none — required)* | Startup fails if missing or blank |
| `KELIR_STORAGE_DRIVER` | `local` | Used from Phase 6 |
| `KELIR_SMTP_HOST` | `localhost` | Used from Phase 6 |
| `KELIR_FRONTEND_URL` | `http://localhost:5173` | The single origin allowed by CORS |
| `KELIR_MULTI_TENANT` | `false` | Multi-tenant mode (FR-IDM-009). Off, sign-in resolves the default tenant and the login request carries no tenant field; on, every sign-in must name an existing `ACTIVE` tenant. Accepts `true`/`false`, `1`/`0`, `yes`/`no`, `on`/`off`; anything else fails startup rather than being read as off |
| `KELIR_DEFAULT_TENANT_CODE` | `SYSTEM` | The tenant resolved when multi-tenant mode is off, and the tenant the first administrator is created in either way. Must match a `tenants.tenant_code`; startup fails if it does not. Compared case-insensitively |
| `KELIR_LOG` | `info,sqlx=warn,tower_http=info` | Standard `EnvFilter` syntax |
| `KELIR_BOOTSTRAP_ADMIN_USERNAME` | *(none)* | First administrator, created at startup only when no user exists |
| `KELIR_BOOTSTRAP_ADMIN_PASSWORD` | *(none)* | Required with the username; refused in staging and production if it is a placeholder |
| `KELIR_BOOTSTRAP_ADMIN_EMAIL` | `<username>@localhost` | Optional |

> **A fresh deployment needs the bootstrap variables.** The permission model and the `ROLE-ADMIN` role are seeded by migration, but no user holds that role, so without them the API starts and nobody can sign in. The startup log says so explicitly when they are unset. Change the password after the first sign-in — doing so ends every session for the account.

### 7.2 Deployment

Read by the compose files and the scripts.

| Variable | Used by | Purpose |
|---|---|---|
| `KELIR_VERSION` | staging compose | Image tag to run |
| `KELIR_DB_PASSWORD`, `KELIR_MINIO_USER`, `KELIR_MINIO_PASSWORD` | staging compose | Secrets, from `.env` |
| `KELIR_DB_HOST`, `KELIR_DB_PORT` | staging compose | Where PostgreSQL is, if not `host.docker.internal:5432` |
| `KELIR_SITE_ADDRESS` | Caddyfile | A hostname enables automatic TLS; a bare port such as `:80` serves plain HTTP |
| `KELIR_HTTP_PORT`, `KELIR_HTTPS_PORT` | staging compose | Host ports Caddy publishes |
| `KELIR_PUBLIC_URL` | `deploy.sh` | Where the smoke test looks |
| `KELIR_EXPECTED_ENV` | `deploy.sh` | Environment `/version` must report |
| `KELIR_IMAGE_REGISTRY` | `deploy.sh` | Pull instead of build |
| `KELIR_SOURCE_DIR` | `deploy.sh` | Build from this checkout instead of fetching the tag |
| `KELIR_FORCE_BUILD` | `deploy.sh` | Rebuild even when images exist at that tag |
| `KELIR_HOST_IP` | `deploy-local.sh` | Skip IP auto-detection |
| `KELIR_APP_DIR` | both scripts | Where `.env` and the compose file live (default `/opt/kelir`) |

## 8. Backup and Restore

The provisioner installs a systemd timer that dumps the database daily at 02:30 UTC into `/var/backups/kelir`, keeping 14 days. `deploy.sh` also takes one immediately before every deploy — a migration that fails halfway is exactly when yesterday's dump is not good enough.

```bash
sudo systemctl start kelir-backup       # run one now
systemctl list-timers kelir-backup      # when it next fires
```

Restore into a clean database:

```bash
sudo -u postgres dropdb kelir
sudo -u postgres createdb -O kelir kelir
sudo -u postgres pg_restore -d kelir /var/backups/kelir/kelir-<stamp>.dump
```

**This path has not been rehearsed.** [NFR-AVA-004](../requirements/srs.md) commits to RPO ≤ 24 h and RTO ≤ 4 h, and the drill that proves them is scheduled for Sprint 20. Until it runs, treat the numbers as intent.

## 9. Troubleshooting

**`permission denied` running a deploy script.** The executable bit may not have survived the checkout. `chmod +x deploy/staging/*.sh`.

**`password authentication failed` when the credentials are right.** Something else is listening on that PostgreSQL port. A natively installed PostgreSQL — common on developer machines, and Windows can run several versions at once — binds the same port Docker publishes on, and a connection may reach either. Check with `netstat -ano | grep :5432` (or `ss -ltnp` on Linux) and move the container to a free port with `KELIR_POSTGRES_PORT`.

**The backend container restarts in a loop.** It runs migrations at startup and exits if the database is unreachable; the restart policy retries. `docker compose logs backend` shows the reason.

**Caddy cannot get a certificate.** DNS must resolve to the host *before* the first start, and port 80 must be reachable — the ACME challenge uses it even though the site ends up on 443. An IP address can never be issued a certificate; use §5 for that.

**Browser console shows a CORS error.** Only possible in the development stack, where the Vite dev server and the API are different origins. Check `KELIR_FRONTEND_URL` matches the origin the browser is actually on. Deployed shapes serve one origin and cannot hit this.

**`/version` reports `unknown` for the commit.** The image was built without `--build-arg KELIR_BUILD_SHA=...`. Rebuild with it; the release checklist compares that value against the tag.

**A migration fails with a checksum mismatch.** A migration that had already been applied was edited afterwards. Migrations are immutable once merged ([coding standard §2.5](../standards/01.%20Coding%20Standard.md)) — fix forward with a new one. On a throwaway database, recreate it instead.
