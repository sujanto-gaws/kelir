# Kelir User Manual

**Status:** Living · **Last updated:** 2026-09-12

How to use a running Kelir: raise a document, decide a task, find a supplier, and — for an administrator — configure the types, forms and roles that shape all three. It assumes somebody else has installed it. If nobody has, [Quick Start](02.%20Quick%20Start.md) gets a stack running in one sitting.

**This describes the screens that exist.** Where a capability is real over the API and has no screen, the manual says so in place rather than describing a page you would go looking for; §12 collects them. Where the interface behaves in a way that looks like a defect and is not — a refusal, a missing button, a file that will not download — the manual says why, because that is the question a manual is actually asked.

The vocabulary here is the product's own. Where a word carries more meaning than a screen can hold, the definition is in [concepts/01. Concept.md](../concepts/01.%20Concept.md) and the rules are in the [SRS](../requirements/srs.md).

---

## 1. The Five Words

Everything in Kelir is built from these, and nothing on a screen means anything without them.

| Word | What it is |
|---|---|
| **Document** | A business event — a purchase request, an onboarding, a change to a supplier. It happens once, moves through a controlled lifecycle, and is then history. Every transaction in Kelir is one |
| **Document type** | The configured shape of a kind of document: which form it renders, how it is numbered, which workflow routes it, what it is allowed to change. An administrator creates these; everybody else creates documents *from* them |
| **Form** | The fields, validation and calculations a document is filled in against, stored as a definition rather than written as code. A published form revision is frozen, and a document pins the exact revision it was filled against |
| **Workflow** | The route a submitted document takes — who approves it, in what order, under what conditions. While a workflow is running, it owns the document's status |
| **Task** | One person's or one role's piece of a running workflow: a decision waiting to be made. Tasks arrive in **My Tasks** |

Two further words appear on screens and are easy to confuse with each other:

- A **party** is anyone or anything the business deals with — a person or an organisation — and a **supplier**, **customer** or **employee** is a party holding that role. One record, many roles, which is why a supplier who becomes a customer does not become a second record.
- A **record status** is the governance lifecycle of a master-data record, which keeps existing. A **document status** belongs to an event, which does not. The two never appear on the same row.

## 2. Signing In

Go to the address your administrator gave you and sign in with your username and password.

**If the form asks for a tenant code**, the deployment runs in multi-tenant mode and your account lives in exactly one tenant. Your administrator knows the code; existing accounts on a deployment that has just turned the mode on all live in its default tenant. If the field is absent, the deployment is single-tenant and a tenant code would be ignored rather than obeyed.

**If you have forgotten your password**, use *Forgot your password* on the sign-in page. A link is emailed to you. On a development stack the mail is not sent anywhere — it lands in Mailpit, and the person running the stack can retrieve it.

**Changing your own password has no screen yet.** The endpoint exists and nothing calls it. Until it does, the route to a new password is *Forgot your password*, or an administrator resetting it for you. An account created by an administrator, and the first administrator created at install, are both flagged as needing a password change, and nothing in the interface acts on the flag — so treat it as a reminder to you rather than as something the product will enforce.

**Signing out** revokes the session. Changing a password revokes every refresh token on the account, so no session can be extended; an access token already issued stays valid until it expires, which is at most fifteen minutes.

## 3. Finding Your Way Around

The rail down the left is the navigation. **You see only what you may open** — an entry whose permission you do not hold is not drawn. This is cosmetic tidiness and nothing more: the server re-checks every request and is the only thing that decides, so a link you reach by typing its address still refuses you.

Built-in destinations, in the order they appear:

| Entry | What it is for | You need |
|---|---|---|
| **Dashboard** | The landing page | a session |
| **My Tasks** | Decisions waiting for you | `workflow:task:read` |
| **Documents** | Everything you may read, and the way to raise a new one | `document:read` |
| **Notifications** | What has been sent to you | `notification:read` |
| **Master Data** | Parties, suppliers, customers, employees | `master-data:party:read` |
| **Users**, **Roles**, **Delegations**, **Tenants** | Administration (§11) | the matching `identity:` or `organization:` code |
| **Document Types**, **Forms**, **Lists**, **Navigation** | Configuration (§10) | the matching `document-type:` or `rad:` code |

**The dashboard is a placeholder.** It confirms the interface is talking to a working API and shows nothing else; the widgets a dashboard should have — tasks pending, recent documents, a status chart — are Phase 8 work. Start at **My Tasks** or **Documents** instead.

**Your deployment may have added to the rail.** An administrator can configure extra entries pointing at configured lists (§10.3). These appear alongside the built-in ones. If the configured entries fail to load, the built-in navigation is still drawn — the sidebar is how you leave a page, so it does not disappear because a configuration call failed.

**Every list keeps its state in the address bar.** The page you are on, the text you searched for and the filters you set are all in the URL, so a filtered view can be bookmarked, linked to a colleague, and survives a reload. Searching happens when you submit, not as you type.

## 4. Documents

### 4.1 Finding one

**Documents** lists what you may read, with search and filters. A document has two identifiers and they are not the same thing:

- The **reference** (`DOC-2026-000123`) is the internal handle. A document has one from the moment it is created.
- The **number** is the business number, assigned by the numbering rule **when the document is submitted**. A draft has none. If you are looking for a document by a number somebody quoted at you and finding nothing, the likeliest reason is that it has not been submitted.

### 4.2 Raising one

**Documents → New**. Choose a type, give the document a title, and it opens.

Only **active** types are offered. If the type you expect is missing, it is still a draft, or it has been deprecated to stop new documents being raised from it while the existing ones carry on. A type that has no form bound to it is shown and cannot be started from, and the screen says which — that state is ordinary, because a type is often configured before its form exists.

### 4.3 The workspace

A document opens on six tabs.

| Tab | What it holds |
|---|---|
| **Form** | The fields, and the buttons that move the document |
| **History** | This document's **status changes** — one row per transition, with who and why |
| **Workflow** | The running process: where it is, who has it, and what has been decided |
| **Attachments** | Files and links (§5) |
| **Comments** | The conversation (§6) |
| **Activity** | Everything that has happened to the document, from all four sources |

**History and Activity are one word apart and answer different questions.** History is the status trail and nothing else. Activity is the whole timeline — lifecycle, workflow, attachments and comments in one list, each entry labelled with where it came from. When you want *how did this get here*, read History; when you want *what has been done to this*, read Activity.

An Activity entry does not name its subject — no file name, no comment text, no second party to a delegation. Those live behind their own permissions, and the entry links to them rather than repeating them. So a row reads *a file was attached, by Sara, at 09:05*, and the file's name is on the Attachments tab, where the permission to see it is decided.

### 4.4 Filling it in, and submitting

**A document can be edited while it is a draft, and while it has been returned to you.** Anything else is read-only, and the fields are drawn disabled rather than hidden — you can read what was submitted.

**Save** keeps your work. **Submit** sends it. Submitting does three things at once: it validates the whole payload **on the server**, assigns the business number, and moves the document out of `Draft`.

**The validation that counts is the server's.** The form checks what it can as you type, and that is a convenience; the answer is the one the submit returns. A refusal lands where it belongs — a missing required field lands on the field, and a refusal about the type's configuration lands as a message naming what an administrator has to fix. Neither is flattened into *something went wrong*.

**A submit refused because the type has no numbering rule is not your problem to solve.** It means the type was configured without deciding how its documents are numbered. Send the message to whoever administers document types; §10.5 is what they need to do.

**A returned document is corrected and submitted again, and keeps the number it already has.** That is the whole difference between a return and a rejection: a rejection ends the document, a return asks you to fix it.

### 4.5 Statuses, and who moves them

| Status | Means |
|---|---|
| `Draft` | Being written. Editable. Not yet numbered |
| `Submitted` | Sent, not yet being decided |
| `In review` | Being looked at |
| `Pending approval` | **A workflow is deciding it** |
| `Approved` / `Rejected` | Decided |
| `Returned` | Sent back for correction. Editable again, number kept |
| `Completed` | Finished after approval |
| `Cancelled` | Stopped |
| `Archived` | Put away |

**When a workflow is running, the workspace's transition buttons are gone and that is correct.** A running process owns the document's status, and the way the document moves is through a task in **My Tasks** — not through a button here. A status set here would disagree with the process the moment it moved, so the product refuses it rather than allowing two things to decide one field.

**When no workflow is bound to the type**, the workspace offers the moves the server will accept from where the document is, and you move it by hand. This is the simpler configuration and a perfectly legitimate one; it is also what a newly configured deployment does before anyone has written a workflow definition.

## 5. Attachments and Links

The **Attachments** tab holds two different things, deliberately together: files stored by Kelir, and links to somewhere else. A person looking for the quotation does not care which it arrived as, so they are in one list — but they must not be mistaken for one another, so a link carries a **Link** badge, has no size and no scan status, and opens outward instead of downloading.

**A newly uploaded file cannot be downloaded immediately, and this is a security control rather than a delay.** Every upload is virus-scanned, and until the scan clears it the file is refused. Three refusals look similar and mean different things:

| State | Means | What to do |
|---|---|---|
| `PENDING` | Not scanned yet | Wait. The scanner looks every few seconds |
| `INFECTED` | The scanner found something | Nothing. The file will not be released |
| `FAILED` | The scan could not run | **Not a Kelir error to shrug at.** A scan that did not run has cleared nothing, so the file is refused exactly as an infected one is. Re-upload it; if it keeps failing, tell whoever runs the deployment |

There are limits an administrator sets: a maximum size (25 MB by default) and a list of accepted file types (PDF, PNG, JPEG, and Word and Excel documents by default). **The type is detected from the file's contents, not from its name**, so renaming a file to get past the list does not work.

Deleting an attachment removes it from the document; the stored bytes are a retention matter and are not destroyed by the delete.

## 6. Comments

The **Comments** tab is a conversation about the document. Write one, reply to one, edit your own, delete your own.

**A comment is not a decision reason.** The Workflow tab one panel across shows decisions *with the reasons they were given*, and those look exactly like comments with authors. They are not the same thing and they are kept in different tabs on purpose: a decision's reason is written with the approval, is part of the record of that approval, and can never be edited or deleted. A comment can be all three. The note under the comment box says so, for the same reason this paragraph does.

**A reply sits under what it answers, and threads are one level deep.** You reply to a comment; you do not reply to a reply. If a root comment is on another page of a long conversation, its reply is still shown rather than dropped.

**A deleted comment that has replies leaves a marker** — *this comment was deleted*, with its author and time and nothing else. The replies under it are somebody else's words and are not taken away with it.

**An edited comment says that it was edited**, beside its time.

## 7. Tasks

### 7.1 The inbox

**My Tasks** is what is waiting for you: tasks assigned to you, and tasks offered to a role you hold. Nothing is filtered in your browser — the rule is in the server's own query, because showing you a task the server would then refuse you reads as a broken product while being a leak.

**Yours and unclaimed are shown apart, because they are different situations.** A task assigned to you is work you have. An unclaimed one is work going spare, and somebody else may take it while you are reading.

Four scopes:

| Scope | Shows |
|---|---|
| **Waiting for me** | Open tasks |
| **Late** | Open tasks past their due date — a narrowing of the above, not a separate axis |
| **Decided by me** | What you have already decided |
| **Everything I have held** | Both |

### 7.2 Deciding one

Open a task. If it is unclaimed, **claim** it first — that is what stops two people deciding the same thing.

**The decisions on offer come from the workflow, not from a fixed list.** A definition decides what its tasks may do, so one task offers *Approve* and *Reject* and another adds *Return*. A button you do not see is one this task does not have, not one you are forbidden.

**Some decisions require a reason and will not proceed without one.** The reason is entered *with* the decision rather than after it — a screen that recorded the decision and then asked why would have recorded a decision with no reason attached the moment somebody closed it. What you write becomes part of the record of that approval, permanently, and is not a comment (§6).

**Returning sends the document back to its author to correct**, keeping its number. Rejecting ends it.

### 7.3 Handing a task over

**Delegate** hands one task to a named person. That is a single handover, decided by you, now.

For planned absence, use a **delegation window** instead (§11.3) — that routes work to somebody else for a period, rather than moving one task.

## 8. Notifications

**Notifications** is what has been sent to you: a record of what reached you, not a live to-do list.

The difference matters. When a task is offered to a role, every holder of that role is notified, and the moment one of them claims it the others are holding a notification about something no longer waiting for them. **Those rows stay** — they were true when they were written, and deleting them would take away the answer to *what was I told* from somebody who is reading it. **My Tasks is the live view**, and every task notification links to it.

Following a notification marks it read. There is also an explicit *mark read*, for the case where you can tell from the list that you do not need to open it.

**A notification may arrive by email as well**, if the deployment is configured for it. Email is sent once per channel and a failure is logged rather than retried — so the notification centre, not your inbox, is the reliable record.

## 9. Master Data

**Master Data** has four views over one set of records:

| View | Shows |
|---|---|
| **Parties** | Everyone and everything the business deals with, whatever role they hold |
| **Suppliers** | Parties holding the supplier role, with the supplier number that makes them one |
| **Customers** | The same, with customer numbers |
| **Employees** | The same, with employee numbers |

**One party, many roles.** A supplier who becomes a customer gains a role; they do not become a second record. This is why the Parties view exists beside the three role views.

**The three role views can be searched and filtered; the Parties view cannot**, and it offers no search box rather than offering one that would be ignored.

**You may see some tabs and not others.** The role views need the permission to read role assignments as well as the permission to read parties, because a row is a party with a supplier number on it and is made of both. If you hold one permission and not the other, you get the tabs you may open rather than a screen that refuses all four.

**In this release the master-data screens are read-only.** Creating and editing party records is real over the API and has no screen. There is a deliberate route to changing governed master data that does not need one, and it is the whole point of the design: **a change to a supplier is raised as a document**. An administrator configures a document type whose target is a party, somebody raises it, it goes through approval like anything else, and the record changes when the document is approved. A record awaiting that approval sits at `Pending approval` — the governance lifecycle in §1, not a document status.

**A business code is never reused.** A supplier number belongs to that supplier permanently, even if the record is deleted; the next supplier gets the next number. If you are looking for a gap in a numbering sequence, that is where it came from.

## 10. Configuration

These screens belong to whoever configures the deployment. Everything here shapes what §4 to §9 look like for everybody else.

### 10.1 Forms

**Forms** lists form definitions; opening one is the builder. A form is a definition — components, validation rules, conditional logic and calculations — not code, and it is edited here rather than deployed.

**A form has revisions, and publishing freezes one.** A published revision cannot be edited: a document pins the exact revision it was filled against and re-renders against that revision for ever, so editing a published one would change what an old document says it recorded. To change a published form, create a new revision.

**Only a published revision can be bound to a document type**, which is the most common reason a form does not appear in the type's chooser.

**Publishing re-validates the whole definition**, so a publish can be refused for something a save allowed. That is deliberate: a rule the engine could not run — a calculation that depends on itself, a condition referring to a field that is not there — is caught here rather than in front of the person filling the form in. A refusal names what is wrong.

### 10.2 Lists

**Lists** configures the list screens people use: which columns, which filters, which sort. A list is a definition too, and adding one needs a definition rather than a code change. A configured list is reachable at its own address and can be pointed to from the navigation (§10.3).

**Opening a configured list needs the permission of the rows behind it**, not the permission to build lists. Otherwise only a configuration administrator could open a screen built for everybody.

### 10.3 Navigation

**Navigation** configures the extra entries in the left-hand rail — typically pointing at the lists from §10.2. Built-in entries are not configured here and cannot be removed.

### 10.4 Document types

**Document Types** is where a kind of document is defined. A type carries:

| Setting | What it decides |
|---|---|
| **Code** and **name** | What it is called |
| **Status** | `Draft` while being set up, `Active` to let people raise documents from it, `Deprecated` to stop new ones while existing documents carry on |
| **Form** | Which published form its documents are filled against |
| **List** | Which configured list its documents appear on |
| **Workflow** | Which active workflow routes it. Leave it empty and documents are moved by hand (§4.5) |
| **Target** | Whether this type exists to change a master-data record (§9), and which kind |
| **Security level** | How the document is classified |

**The bindings are chosen from what can actually be bound** — published forms, active lists, active workflows — rather than typed, so a broken binding is refused before it is saved rather than discovered when somebody raises a document.

**Deleting a type is refused while documents exist from it.** `Deprecated` is the control for retiring one.

### 10.5 Numbering

Each type has its own **Numbering** rule, and a type with no rule is an ordinary state rather than an error — the numbering is usually decided after the type exists. **But a submit against a type with no rule is refused**, so the rule has to exist before anybody uses the type in anger.

A rule is a template, a scope and a padding:

- **Template** — `PO-{year}-{sequence}`. The placeholders are `{sequence}`, `{year}`, `{month}` and `{department}`. **`{sequence}` is required**: without it every document of the type would be given the same number, and the second one would be refused at submit having already done the work. An unknown placeholder is left in the output rather than blanked, so a mistake in a template is visible as a mistake.
- **Scope** — when the sequence restarts: never (`Global`), each calendar year, each calendar month, or per department per year.
- **Padding** — how many digits the sequence is padded to.
- **Gap policy** — whether a failed submission gives its number back (`Gapless`) or leaves a hole (`Allow gaps`). Choose `Gapless` where an auditor will ask about missing numbers.

### 10.6 Workflows

**There is no workflow builder screen.** Forms, lists, navigation and document types each have one; workflow definitions are written and published over the API, against the [JSON Workflow Schema](../schema/JSON%20Workflow%20Schema.md). Until a screen exists, a deployment that wants approval routing needs somebody who can call the API — and a deployment that does not want it binds no workflow and moves documents by hand (§4.5), which is a supported configuration rather than a workaround.

**A definition the engine could never run is refused when it is saved**, not when a document reaches the broken part of it. So a definition that saved and published is one the engine has already agreed it can execute.

Only an **active** definition can be bound to a document type, the same rule forms follow.

## 11. Administration

### 11.1 Users

**Users** creates and edits accounts and assigns roles to them. A username cannot be changed after the account is created; an email can. A duplicate username or email is refused by the server and shown against the field that caused it.

An administrator can reset another account's password. A person cannot yet change their own from within the product (§2).

### 11.2 Roles and permissions

**Roles** creates roles and chooses the permissions each grants. A permission is a code of the form `module:resource:action` — `document:create`, `master-data:party:read` — and the catalogue is grouped by module in the dialog, because a hundred ungrouped checkboxes is not a list anybody can read.

**Permissions are granted through roles, never to a person directly.** To give somebody an ability, give them a role that grants it.

**Hiding a navigation entry is not a security control.** The server checks every request against the permissions your session actually carries, and refuses regardless of what your browser drew. Equally, a screen may be open to you while a button on it is refused — reading a task and deciding it are different permissions, and the product shows you the task you were told about rather than hiding it because you may not decide it.

### 11.3 Delegations

A **delegation window** routes work to somebody else for a period — cover for leave, in practice.

**A window is opened and ended. It is never edited.** Editing one in place would change where work was being routed with nothing on the record saying it had changed; ending one and opening another leaves both facts visible.

**You open a window in your own name and nobody else's.** There is no field for whose authority is being handed over — a person who could name somebody else could point the finance director's approvals at themselves, and the row would look exactly like legitimate cover. Reading and *ending* windows are administrative, because the row somebody has to be able to find is the one whose owner went on leave without ending it.

**Ending a window stops work arriving; it does not reach back.** Tasks already handed over stay where they are — moving approvals out from under somebody mid-decision, on a schedule nobody triggered, is what both halves of that rule avoid. The same is true opening one: it routes what comes next, not what is already assigned.

**Two columns, because they are two facts.** A window ends either by being switched off or by its end date passing, and the list shows both — cover that was cancelled is not the same as cover that ran its course.

### 11.4 Tenants

Only on a deployment running in multi-tenant mode.

**Tenants are administered only from the deployment's default tenant.** Holding the permission is not enough, and a tenant's own administrator is never granted it — otherwise a tenant administrator could create tenants and grant themselves any permission in the catalogue. If you hold the permission and are refused, you are signed in to the wrong tenant.

**Do not create tenants on a single-tenant deployment.** Sign-in resolves the default tenant and ignores the code, so the new tenant's administrator is a real account that nobody can reach.
