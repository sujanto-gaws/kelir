# Kelir Coding Standard

**Status:** Draft · **Last updated:** 2026-08-05

This document defines the coding standard for all Kelir code: the Rust backend (`kelir-backend/`), the Vue 3 frontend (`kelir-frontend/`), database migrations, and deployment configuration. Naming rules are defined separately in [02. Naming Convention.md](02.%20Naming%20Convention.md).

The keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted as described in RFC 2119.

---

## 1. General Principles

1. **Consistency over preference.** Follow the existing style of the file or module you are editing. Deviations from this standard within a module are fixed module-wide, not file-by-file.
2. **Module boundaries are hard boundaries.** Kelir is a modular monolith. A module accesses another module only through its public service interface — never through its repository, tables, or private types.
3. **The database schema, API envelope, permission format, and event names are governed** by the architecture documents and the SRS. Code MUST NOT invent variants of these; propose changes to the documents first.
4. **Metadata over code.** Form, list, and workflow behavior belongs in RAD metadata and JFSS schemas wherever the metadata layer can express it. Custom code is the fallback, not the default.
5. **Every change is reviewable.** Small commits, focused pull requests, no drive-by refactoring mixed into feature work.

## 2. Rust Backend

### 2.1 Toolchain and Formatting

- Rust edition **2021** (upgrade is a project-wide decision).
- `rustfmt` with default configuration. Formatting is not debated in review; run `cargo fmt` before committing.
- `cargo clippy --all-targets -- -D warnings` MUST pass. `#[allow(...)]` requires a comment stating the reason.
- Dependencies are added deliberately: prefer the blueprint stack (Axum, Tokio, SQLx, Serde, Tracing, Argon2, Utoipa, `validator`). A new dependency needs a justification in the PR description.

### 2.2 Module Layout

Each business module lives in `src/modules/<module_name>/` and follows the four-layer architecture:

```text
src/modules/document/
├── mod.rs          # public interface of the module (re-exports)
├── handlers.rs     # HTTP layer: Axum handlers, request/response DTOs
├── service.rs      # application layer: use cases, transactions, permissions
├── domain.rs       # domain layer: entities, value objects, invariants
└── repository.rs   # infrastructure layer: SQLx queries
```

- Handlers MUST stay thin: parse/validate input, call one service function, map the result to the response envelope. No business logic, no SQL.
- Services own transactions and permission checks. A service function is the unit other modules are allowed to call.
- Repositories are private to their module. Cross-module data access goes through the owning module's service.
- Domain types do not depend on Axum, SQLx, or serde DTOs. Map at the boundaries.

### 2.3 Error Handling

- One central `AppError` type (in `src/error.rs`) implementing `IntoResponse`, mapping to the standard error envelope `{success: false, error: {code, message, details}}`.
- Module-level errors use `thiserror` and convert into `AppError` via `From`.
- `unwrap()`, `expect()`, and `panic!` MUST NOT appear in request-handling paths. They are acceptable only in startup code (with a clear message) and tests.
- Errors carry stable machine-readable codes (see the SRS error envelope); human-readable messages are never used for programmatic branching.
- Validation failures return the JFSS error contract (`path`, `rule`, `code`, `message`) as defined in JSON Form Schema S10.3.

### 2.4 Async and Concurrency

- All I/O is async (Tokio). Blocking work (password hashing, file processing) goes through `tokio::task::spawn_blocking`.
- No `std::sync::Mutex` held across `.await`; use `tokio::sync` primitives where shared state is unavoidable.
- Background work (outbox dispatch, notifications, virus scanning) runs in dedicated workers, never inline in a request handler.

### 2.5 Database Access (SQLx)

- Use `sqlx::query!`/`query_as!` compile-time-checked macros wherever the query is static. Dynamic query building is confined to repository helpers and MUST use bind parameters — string interpolation of values into SQL is forbidden without exception.
- Identifiers that must be dynamic (table/column names for RAD or validation rules like `unique`/`exists`) MUST be resolved through an allow-list, never taken from input.
- Transactions begin and end in the service layer. A repository function either takes an executor/transaction argument or is a single statement.
- Migrations are immutable once merged: fix-forward with a new migration, never edit an applied one. See the Naming Convention for migration file naming.
- Soft delete is `deleted_at IS NOT NULL`; queries exclude soft-deleted rows by default.

### 2.6 API Conventions

- All endpoints live under `/api/v1` except the root-level operational endpoints `/health`, `/health/ready`, `/health/live`, `/version` (and `/metrics` if enabled).
- Responses use the standard envelope: item responses `{success, data}`; list responses `{success, data: [...], meta: {page, pageSize, total}}`.
- Every endpoint declares Utoipa annotations; the OpenAPI document at `/api/docs/openapi.json` is generated, never hand-edited.
- Input validation happens at the boundary with the `validator` crate plus JFSS server-side rules for dynamic forms. Handlers never trust client-computed values: server-side recalculation of JFSS `calculate` fields (the Tamper-Proof Pattern) is mandatory.
- Permission checks use the `module:resource:action` format and happen in the service layer before any state change.

### 2.7 Logging and Observability

- Use `tracing` macros exclusively; `println!`/`dbg!` MUST NOT be committed.
- Every request carries a correlation ID (middleware-assigned); spans include it.
- Never log credentials, tokens, session IDs, attachment contents, or personal data. Integration payloads are logged masked, per the integration rules in architecture document 03.
- Log levels: `error` = action required, `warn` = degraded but handled, `info` = business-significant events, `debug`/`trace` = development detail.

### 2.8 Security

- Passwords: Argon2id only. Tokens and secrets come from configuration (`KELIR_*` env vars), never from source code.
- All queries parameterized (see 2.5). All uploads size-checked and virus-scanned asynchronously before download is allowed.
- Audit events for create/update/delete/status-transition/permission/configuration changes are written through the audit module (hash-chained, append-only) — modules MUST NOT write audit rows directly.

### 2.9 Testing

- Unit tests live in a `#[cfg(test)] mod tests` block in the same file; integration tests in `kelir-backend/tests/`.
- Test names describe behavior: `fn rejects_submission_when_amount_exceeds_limit()`.
- Repository and service tests run against a real PostgreSQL (Docker Compose); do not mock SQL.
- Every bug fix includes a regression test. Every new endpoint has at least one success-path and one failure-path test.

### 2.10 Documentation

- Public items (services, domain types, module `mod.rs`) carry `///` doc comments stating what and why, not how.
- Comments explain constraints and non-obvious decisions; they do not narrate the code.

## 3. Vue 3 Frontend

### 3.1 Language and Tooling

- TypeScript in `strict` mode. `any` is allowed only with an inline comment justifying it; prefer `unknown` + narrowing.
- ESLint + Prettier govern style; both MUST pass before commit. Formatting is not debated in review.
- Vue SFCs use `<script setup lang="ts">` with the Composition API. The Options API MUST NOT be introduced.

### 3.2 Project Structure

- Feature-first layout: code for a domain lives in `src/features/<feature>/` (components, composables, store, api calls, types). Shared building blocks live in `src/components/`, `src/composables/`, `src/lib/`.
- SFC block order: `<script setup>`, `<template>`, `<style>`. Styles are Tailwind-first; `<style>` blocks are the exception and MUST be `scoped`.
- Props and emits are fully typed (`defineProps<...>()` / `defineEmits<...>()`). Components with more than ~5 props should take an object or be split.

### 3.3 State and Data Flow

- Server state is fetched through the single API client in `src/api/`; components MUST NOT call Axios directly.
- Pinia stores hold cross-page state only; page-local state stays in the component. Store actions are the only place that mutates store state.
- All API types are declared in `src/types/` (or the feature's `types.ts`) and mirror the backend DTOs. No untyped `response.data` access.
- The API client unwraps the standard envelope and normalizes errors into a typed `ApiError` (carrying the backend `code` and JFSS validation `details`).

### 3.4 UI Standards

- Components come from shadcn-vue plus Tailwind CSS v4 utilities (CSS-first config via `@theme` in `src/styles/main.css`; no `tailwind.config.ts`).
- Every async view handles three states: loading, error, empty. No silent failures.
- Forms driven by JFSS render through the dynamic form renderer; hand-built forms are reserved for cases the metadata layer cannot express, and use VeeValidate + Zod schemas mirroring the server rules.
- User-facing strings go through the i18n layer once introduced; until then, keep them in the component, not in stores or API code.

### 3.5 Testing

- Vitest for unit/component tests, colocated as `<name>.spec.ts`.
- Test composables and store logic directly; test components for behavior (rendered output, emitted events), not implementation details.

## 4. SQL and Migrations

- PostgreSQL is the primary target; avoid PostgreSQL-only features where the optional MariaDB compatibility would be broken without a documented reason (JSONB and GIN indexes are accepted exceptions per the blueprint).
- Every table carries the base fields from concepts document 04: `id`, `tenant_id`, `created_by`, `created_at`, `updated_by`, `updated_at`, `deleted_at`.
- Foreign keys are declared, indexed, and named (see Naming Convention). Cascading deletes MUST NOT be used on business data; soft delete governs lifecycle.
- Each migration is one concern, has a descriptive name, and includes any index the new queries need. Data migrations are separated from schema migrations.

## 5. Git Conventions

- Commit messages follow [03. Commit Message Convention.md](03.%20Commit%20Message%20Convention.md) (Conventional Commits); releases follow [04. Release Process.md](04.%20Release%20Process.md).
- Branches: `feature/<short-slug>`, `fix/<short-slug>`, `docs/<short-slug>`.
- `main` is protected: changes land via reviewed pull requests; CI (fmt, clippy, tests, lint, build) must be green.
- Generated files (lockfiles excepted) and secrets are never committed; see `.gitignore`.

---

## 6. Code Review Checklist

Reviewers verify, at minimum:

1. Module boundaries respected (no cross-module repository/table access).
2. Envelope, error codes, permission checks, and audit events present and correct.
3. No `unwrap`/`expect`/`println!`/`dbg!` in production paths; no `any` without justification.
4. SQL parameterized; dynamic identifiers allow-listed.
5. JFSS: client-computed values recalculated server-side; operators used are registered in the Calculation/Validation Rule Registries.
6. Tests cover the change (success + failure path); names describe behavior.
7. Naming follows [02. Naming Convention.md](02.%20Naming%20Convention.md).
