# Kelir Naming Convention

**Status:** Adopted · **Last updated:** 2026-09-01

This document is the single authority for names in Kelir: code identifiers, database objects, API surface, permissions, events, identifiers, and files. Where an older document conflicts with this one, this document wins; update the older document.

---

## 1. Quick Reference

| Context | Convention | Example |
|---|---|---|
| Rust crate / repo folder | `kebab-case`, lowercase | `kelir-backend` |
| Rust module / file | `snake_case` | `task_inbox`, `repository.rs` |
| Rust type / trait / enum | `PascalCase` | `DocumentService`, `WorkflowState` |
| Rust function / variable | `snake_case` | `submit_document` |
| Rust constant / static | `SCREAMING_SNAKE_CASE` | `MAX_ATTACHMENT_BYTES` |
| Vue component file | `PascalCase.vue` | `DocumentDetail.vue` |
| Composable | `useXxx` camelCase | `useTaskInbox` |
| Pinia store | `useXxxStore` | `useAuthStore` |
| TS type / interface | `PascalCase`, no `I` prefix | `PartySummary` |
| Non-component frontend file | `kebab-case` or `camelCase` (follow folder) | `api/client.ts` |
| DB table | `snake_case`, plural | `documents`, `mdm_parties` |
| DB column | `snake_case`, singular | `created_at`, `party_id` |
| API URL path | `kebab-case`, plural resources | `/api/v1/master-data/parties` |
| JSON payload field | `camelCase` | `formId`, `virusScanStatus` |
| Permission | `module:resource:action` | `master-data:party:update` |
| Event | dotted `PascalCase` | `Document.Approved` |
| Env var | `KELIR_*` / `VITE_KELIR_*` | `KELIR_DATABASE_URL` |
| Migration file | `NNNN_snake_case.sql` | `0004_string_lengths.sql` |

## 2. Rust Backend

- Follow the Rust API Guidelines defaults: `snake_case` for functions, methods, variables, modules, and files; `PascalCase` for types, traits, and enum variants; `SCREAMING_SNAKE_CASE` for constants.
- Business modules under `src/modules/` use the module vocabulary of architecture document 02 in `snake_case`: `auth`, `identity`, `roles`, `organization`, `master_data`, `rad`, `document_type`, `document`, `workflow`, `task_inbox`, `attachment`, `comment`, `activity`, `audit`, `notification`, `reporting`, `search`, `integration`, `plugin`.
- Conceptual module names in documentation are unprefixed `PascalCase` + `Module` (`DocumentModule`, `RadModule`). The `Kelir…Module` prefixed style found in some older documents is deprecated — the prefix is redundant inside the project.
- Service types are `<Entity>Service`, repositories `<Entity>Repository`, request/response DTOs `<Action><Entity>Request` / `<Entity>Response` (e.g. `SubmitDocumentRequest`, `DocumentResponse`).
- Error enums are `<Module>Error`; variants describe the failure, not the HTTP status (`DocumentLocked`, not `Conflict409`).

---

## 3. Vue 3 Frontend

- Component files and component names: `PascalCase`, multi-word (per Vue style guide): `TaskInboxList.vue`, never `Inbox.vue`.
- Feature folders under `src/features/` are `kebab-case`: `master-data`, `documents`, `tasks`.
- Composables: `useXxx` (`useDocumentForm`); Pinia stores: `useXxxStore` defined in `<feature>/store.ts` or `src/stores/`.
- Props and emits: `camelCase` in script, `kebab-case` in templates (`:documentId` → `:document-id`). Emitted event names are `camelCase` verbs (`submit`, `rowSelected`).
- Route names are `kebab-case` (`document-detail`); route paths follow the API resource naming (§5).
- TS interfaces/types mirror backend DTO names (`DocumentResponse`, `PartySummary`); enums use `PascalCase` names with `SCREAMING_SNAKE_CASE` members only when mirroring backend enum wire values.

## 4. Database

### 4.1 Tables

- `snake_case`, **plural**: `documents`, `workflow_tasks`, `comments`.
- Domain prefixes group related tables: `mdm_` (master data), `rad_` (RAD metadata), `workflow_`, `plugin_`, `integration_`. Core platform tables (users, roles, documents, …) carry no prefix.
- Party model (per architecture document 05): `mdm_parties`, `mdm_persons`, `mdm_party_groups`, `mdm_role_types`, `mdm_party_roles`, `mdm_party_identifications`, `mdm_party_statuses`, `mdm_party_relationships`, `mdm_party_classifications`, `mdm_contact_mechs`, `mdm_party_contact_mechs`, plus role profiles `mdm_supplier_profiles`, `mdm_customer_profiles`, `mdm_employee_profiles`, `mdm_contact_profiles`.
- Join tables combine both names in the natural reading order: `user_roles`, `role_permissions`.

### 4.2 Columns

- `snake_case`, singular. Every table carries the base fields: `id`, `tenant_id`, `created_by`, `created_at`, `updated_by`, `updated_at`, `deleted_at`.
- Foreign keys: `<referenced_entity_singular>_id` (`document_id`, `party_id`). When the role differs from the entity, prefix with the role: `manager_party_id`, `created_by_document_id`.
- Timestamps end in `_at` (`submitted_at`); dates end in `_date` (`join_date`); booleans start with `is_`/`has_`/`allow_` (`is_enabled`, `allow_solicitation`).
- JSON columns end in `_json` (`form_data_json`, `config_json`).
- Enum-valued columns store `SCREAMING_SNAKE_CASE` values (`PENDING_APPROVAL`, `ACTIVE`).
- External references to Kelir entities use `kelir_entity_id` (architecture document 03).

### 4.3 Constraints, Indexes, Migrations

- Indexes: `idx_<table>_<columns>` (`idx_documents_tenant_id_status`); unique constraints: `uq_<table>_<columns>`; foreign keys: `fk_<table>_<column>`.
- Migrations: `NNNN_short_description.sql`, zero-padded, one concern each (`0004_string_lengths.sql`).
- `NNNN` is the next free number at the time the migration is written, not a number reserved for a phase. sqlx applies migrations in version order, so a migration that arrives earlier than planned takes the lower number and every later file shifts down; merged migrations are never renumbered ([git workflow](05.%20Git%20Workflow.md) §7). The current sequence lives in one place only — the mapping table at the top of the [Database Schema](../design/02.%20Database%20Schema.md).

## 5. API

- Base path `/api/v1`. Operational endpoints at root: `/health`, `/health/ready`, `/health/live`, `/version`, `/deployment`. These answer **outside** the response envelope, which is what makes root the right place for them — an endpoint under `/api/v1` carries `success`/`data` without exception. `/deployment` reports how the deployment is configured (today, whether it is multi-tenant) and is unauthenticated because the login form reads it before it has credentials.
- Resource segments: `kebab-case`, plural nouns (`/master-data/parties`, `/document-types`). Path parameters are `{id}` (or `{taskId}` when two IDs appear in one path).
- Actions that are not CRUD are verbs as sub-resources: `POST /documents/{id}/submit`, `/approve`, `/reject`, `/cancel`.
- Query parameters and **all JSON payload fields are `camelCase`** (`pageSize`, `virusScanStatus`, `formId`). Rust DTOs use `#[serde(rename_all = "camelCase")]`; the database stays `snake_case`. Older concept documents with `snake_case` JSON samples are superseded on this point.
- The response envelope fields are fixed: `success`, `data`, `meta` (list responses), and `error: {code, message, details}`. JFSS validation errors use `path`, `rule`, `code`, `message` per JSON Form Schema S10.3.
- **A refusal raised before the handler runs is still in the envelope.** A bad body, a bad query parameter or a bad path segment is rejected by an extractor, and the framework's own extractors reply in plain text — a 400 with an empty body, on every list endpoint in the product, until #122. Handlers therefore take `JsonBody`, `QueryParams` and `PathParam` from `crate::extract` rather than `axum::Json`, `axum::extract::Query` and `axum::extract::Path`. A query parameter that will not parse is a 422 naming the parameter **as the caller spelled it** (`pageSize`, not `page_size`); a path segment that will not parse stays a 400.

## 6. Permissions

- Format: `module:resource:action`, all `kebab-case`, per the SRS and architecture documents 01/02.
- The `resource` segment MAY be omitted when a module manages a single resource (`document:create`); it is required when a module manages several (`master-data:party:update`, `workflow:task:execute`).
- Actions are short verbs: `create`, `read`, `update`, `delete`, `approve`, `execute`, `manage` (full control). Plugin-runtime permissions use the `plugin:` module (`plugin:read-secrets`).

---

## 7. Events

- Dotted `PascalCase`: `<Entity>.<PastTenseAction>` — `Document.Created`, `Document.Approved`, `Attachment.Added`, `Supplier.Created`, `Workflow.TaskCompleted`, `Security.AccessDenied`.
- The entity is the business subject, not the table name. Master-data events use the role/domain name (`Supplier.Created`) even though storage is party-based.
- Notification *types* are a separate vocabulary and stay `SCREAMING_SNAKE_CASE` (`TASK_ASSIGNED`) — they are enum values (§4.2), not events.

## 8. Business Identifiers

| Prefix | Meaning | Format |
|---|---|---|
| `DOC-` | Document internal reference | `DOC-2026-000123` |
| `PR-`, `INV-`, `PO-` … | Business numbers per document type numbering rule | `PR-{year}-{sequence}` → `PR-2026-000123` |
| `WF-` | Workflow definition | `WF-PR-STANDARD` |
| `WFI-` | Workflow instance | `WFI-9001` |
| `TASK-` | Workflow task | `TASK-7001` |
| `TNT-` | Tenant | `TNT-001` |
| `DEPT-` | Department | `DEPT-PROC` |

- Business numbers come from the document type's numbering rule (RAD metadata); code never hardcodes formats.
- Internal IDs (`id` columns) are surrogate keys; business identifiers are separate columns. Never use a business number as a foreign key.

---

## 9. Environment Variables and Configuration

- Backend: `KELIR_` prefix, `SCREAMING_SNAKE_CASE` (`KELIR_DATABASE_URL`, `KELIR_JWT_SECRET`).
- Frontend (build-time, public): `VITE_KELIR_` prefix (`VITE_KELIR_API_BASE_URL`). Secrets MUST NOT use the `VITE_` prefix — Vite inlines them into the bundle.
- Docker Compose service names: lowercase single words (`backend`, `frontend`, `postgres`, `minio`, `mailpit`).

## 10. Files and Documents

- Documentation folders are numbered series: `NN. Title Case.md` (`05. Core - Master Data - Party.md`). New design docs continue the numbering of their folder. **Exception:** `docs/schema/` uses unnumbered specification filenames (`JSON Form Schema.md`).
- Architecture decision records live in `docs/architectures/adr/` and carry a **four-digit** series of their own: `NNNN. Title Case.md` (`0007. Outbox Before Direct Delivery.md`), titled with the decision rather than the topic. The number is the record's permanent identity, cited everywhere as `ADR-0007`; numbers are never reused and never renumbered after merge. `0000. ADR Template.md` is the template. Rules in [06. Architecture Decision Records.md](06.%20Architecture%20Decision%20Records.md).
- Every document carries the header line `**Status:** … · **Last updated:** YYYY-MM-DD` under its H1. **Exception:** `docs/schema/` specifications use the specification title block instead (`**Version:** … / **Status:** … / **Target Stack:** … / **Last updated:** …`), with the H1 carrying the standard's acronym in parentheses.

### 10.1 Status Vocabulary

`Status` answers one question — **how much can a reader rely on this?** — and takes one of these values. Nothing else is valid; a status needing a qualifier to be understood ("Draft, in effect") means the wrong value was chosen.

| Status | Means | The reader should |
|---|---|---|
| `Draft` | Being written or revised; may change without notice | Not build against it |
| `Adopted` | Agreed and in force; changes go through the document's own change control | Rely on it, and treat any conflict with reality as a bug |
| `Living` | Updated continuously by design; has no finished state | Trust it as current, and expect it to move |
| `Superseded` | Replaced by another document; kept for its intent and history | Read it for background only, and follow the pointer |
| `Retired` | No longer applies, and nothing replaces it | Ignore it |
| `Template` | A file to be copied, never edited in place | Copy it |
| `Final` | A point-in-time record — a status report, a retrospective | Read it as evidence of that moment, not of now |

`Final` never becomes `Superseded`: a later report does not invalidate an earlier one, it follows it.

Architecture decision records use this same vocabulary with one addition — `Rejected`: considered and turned down, kept because the reasoning is the value. An ADR is `Draft` while proposed, `Adopted` once the decision is in force, `Superseded` when a later ADR decides otherwise, and `Retired` when what it decided no longer exists ([06. Architecture Decision Records.md](06.%20Architecture%20Decision%20Records.md) §5).

Specifications in `docs/schema/` carry a version, so their status describes stability rather than progress:

| Status | Means |
|---|---|
| `Draft Standard` | The shape may still change; implement at your own risk |
| `Active Standard` | In force; backwards-compatible change only, signalled by the version |
| `Final Standard` | Frozen at this version; errata only — a successor takes a new major version |
| `Superseded Standard` | Replaced by a later specification |

Changing a document's status is itself a change: bump `Last updated` with it.
- JFSS schema artifacts embed their version in the filename (`jfss-meta-v2.0.1.json`).
- Plugin manifests are `plugin.json`; plugin IDs are `kebab-case` (`contract-management`).
