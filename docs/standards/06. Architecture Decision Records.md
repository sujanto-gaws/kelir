# Kelir Architecture Decision Records

**Status:** Adopted · **Last updated:** 2026-09-01

This document defines how architectural decisions are recorded in Kelir: what earns a record, where it lives, what it must contain, and how its status changes. The record itself is written from [architectures/adr/0000. ADR Template.md](../architectures/adr/0000.%20ADR%20Template.md); this document is the rule, that file is the form.

An architecture decision record (ADR) exists for one reason: six months later, somebody asks *why is it built this way*, and the answer must not be a person. Code says what was built. A design document says how it works now. Only an ADR says which alternatives were rejected, under which constraints, and what would have to change for the answer to change.

---

## 1. What an ADR Is

An ADR is a **point-in-time record of one architecturally significant choice**, written when the choice is made and never rewritten afterwards. It is immutable in substance: once adopted, an ADR is corrected only for errata (a broken link, a wrong section number), and reversed only by a later ADR that supersedes it.

A decision is **architecturally significant** when at least one of these is true:

| Test | Example |
|---|---|
| It is expensive to reverse | Choosing PostgreSQL-only over a database abstraction layer |
| It constrains code that has not been written yet | Every hook returns CONTINUE / MODIFY / REJECT and nothing else |
| It is cross-cutting | The response envelope, the permission string grammar, the outbox pattern |
| It trades a stated requirement against another | Synchronous webhook delivery for latency, against durability |
| It will look wrong to a newcomer without the context | A lightweight internal workflow engine instead of BPMN |

If none of them holds, the decision belongs in the code, the commit message, or the design document — not in an ADR. A folder of ADRs recording choices nobody would have questioned is a folder nobody reads.

## 2. What Is Not an ADR

These have their own homes, and moving them into `adr/` fragments the record:

| Decision | Where it belongs |
|---|---|
| Scope: what is built, when, in which sprint | Product Backlog §6 (`D-n`), the operative sprint plan |
| A name, a casing rule, a prefix | [02. Naming Convention.md](02.%20Naming%20Convention.md) — the single authority on names |
| How a shipped subsystem works | The SDD, the architecture documents, the schema specifications |
| A column, an index, a table | [Database Schema](../design/02.%20Database%20Schema.md), with deviations in its §14 |
| A JSON shape | The owning specification in `docs/schema/`, whose meta-schema is normative |
| A process or convention change | The relevant `docs/standards/` document; the retrospective records that it was decided |
| A bug fix, however clever | The commit message and the issue |

**`D-n` and ADR are not competitors.** A `D-n` decides *whether and when* something is in scope; an ADR decides *how* it is shaped once it is. A scope decision that also fixes an architecture (D-9 retiring staging, D-18 superseding D-7) gets a `D-n` row for the scope half and an ADR for the architecture half, each citing the other.

## 3. Location, Numbering, Identity

- ADRs live in **`docs/architectures/adr/`**, one file per decision.
- Files are `NNNN. Title Case.md` — a four-digit series of its own, not the two-digit series used elsewhere in `docs/` (naming convention §10).
- The number is the ADR's **permanent identity**, cited everywhere as `ADR-0007`. Numbers are allocated when the branch is opened, are never reused, and are never renumbered after merge. If two open PRs claim the same number, the one merging second renumbers — before merge, that is free.
- `0000. ADR Template.md` is the template and is never an ADR.
- The title states **the decision, not the topic**: `0007. Outbox Before Direct Delivery.md`, not `0007. Event Delivery.md`. A reader scanning filenames should learn what was decided without opening anything.
- The index is the `architectures/adr/` table in [docs/README.md](../README.md). Adding an ADR adds its row in the same change; there is no second index.

## 4. Required Structure

Every ADR carries these sections, in this order, with these numbers. The template is already in this shape — fill it, do not restructure it.

| § | Section | Must contain |
|---|---|---|
| — | Metadata block | Decision date, deciders, and the `Supersedes` / `Superseded by` / `Related` links |
| 1 | Context | The forces as they were: constraints, requirement IDs (`FR-*`/`NFR-*`), what was already true. No solution language |
| 2 | Decision | The choice, in one paragraph, imperative and unhedged: "Kelir uses …". A decision written as a preference is not a decision |
| 3 | Options Considered | Every option that was genuinely on the table, each with why it lost. The chosen one is included and marked |
| 4 | Consequences | What this costs as well as what it buys, plus the **impacted documents** table (§7) |
| 5 | Compliance | How a reviewer checks that code actually follows this — a test, a CI check, a review checklist line. "Reviewer judgement" is a valid answer only when nothing mechanical exists |
| 6 | Revisit When | The observable trigger that would reopen this decision. Every ADR has one; "never" is an answer only for decisions the product's identity rests on |
| 7 | References | Issues, PRs, spikes, external material |

An ADR with an empty §3 is not an ADR — it is a note. If no alternative was considered, the decision was not architecturally significant, or the alternatives were not looked for.

## 5. Status Lifecycle

ADRs use the standard status vocabulary (naming convention §10.1) plus `Rejected`:

```text
   Draft ──────▶ Adopted ──────▶ Superseded   (a later ADR replaces it)
     │              │
     │              └──────────▶ Retired      (what it decided no longer exists)
     │
     └───────────▶ Rejected                   (considered and turned down)
```

| Status | Means | Transition happens when |
|---|---|---|
| `Draft` | Proposed, under review | The file is written |
| `Adopted` | In force; code and documents follow it | The PR merges with the impacted documents updated (§7) |
| `Rejected` | Considered and turned down | The proposal is declined — the file is **kept**, because the reasoning is the whole value |
| `Superseded` | A later ADR decided otherwise | The superseding ADR is adopted |
| `Retired` | The subsystem or constraint is gone; nothing replaced it | The thing it decided about is removed |

A `Rejected` or `Superseded` ADR is never deleted and never edited beyond its supersession note. The record of a road not taken is what stops the project taking it twice.

## 6. Supersession

Reversing a decision means writing a new ADR, not editing the old one:

1. The new ADR names the old one in its metadata (`**Supersedes:** ADR-0007`) and its §1 states what changed in the forces — a reversal without a changed force is an admission the first analysis was wrong, which is worth writing down as exactly that.
2. The old ADR's status becomes `Superseded`, its `Last updated` is bumped, and its metadata gains `**Superseded by:** ADR-0021`. Nothing else in it is touched.
3. Supersession may be **partial**: the new ADR says which part it replaces, and the old one's note says which part still stands. An ADR that is half in force stays `Adopted` and carries the note inline.

## 7. Authority and Consequences

**An ADR records why; it never states what or how.** It sits below the operative documents in the authority chain (docs/README.md, authority rule 8): if an ADR and the SDD, the Database Schema, or a schema specification disagree, **the operative document wins** and the ADR is stale — repaired by a superseding ADR, never by quietly rewriting history.

This makes the impacted-documents table in §4 the load-bearing part of the record. **Adoption is not complete until those documents carry the change**, in the same PR:

| Document | Change | Status |
|---|---|---|
| `design/01. System Design Document.md` §7.3 | Delivery described as outbox-first | Done in this PR |

A merged ADR whose impacted documents were left for later has moved the decision out of the documents and into a file nobody consults — the exact failure ADRs exist to prevent. If an impacted change is genuinely too large for the same PR, the row says so and names the issue that carries it, and the ADR stays `Draft` until that issue closes.

## 8. Process

1. **Branch** `docs/adr-<slug>` off `main` (git workflow §2), allocating the next free number.
2. **Copy** `0000. ADR Template.md` to `NNNN. Title Case.md`. Never edit the template in place.
3. **Write** it — including the impacted-documents table — and make those document changes in the same branch.
4. **Index**: add the row to `docs/README.md`.
5. **Commit** as `docs(adr): …` — type `docs`, scope `adr` (commit message convention §2–§3); the subject states the decision, matching the title.
6. **Review** as for any PR (git workflow §4–§5). The review's job here is §3 and §4 of the record: whether the alternatives were real, and whether the costs are stated as plainly as the benefits. While the approval requirement is relaxed to zero on a single-maintainer repository (git workflow §5), that review is a deliberate pass by the author before merging, not a step that disappears — and it is the first thing a second reviewer takes back when one exists.
7. **Adopt**: on merge, the status is `Adopted` and the decision date is the merge date. A PR that is declined flips the status to `Rejected` and merges anyway, so the analysis survives.
8. **Gate**: documentation changes run through `doc-consistency` like any other (project ground rules).

## 9. Decisions Made Before This Standard

Kelir recorded architectural decisions for a year before this folder existed, in two places: [architectures/01](../architectures/01.%20Basic%20Framework%20Concept%20and%20Architecture.md) §29 and its inline `**Decision:**` paragraphs, and the `D-n` table in [Product Backlog](../../projects/planning/02.%20Product%20Backlog.md) §6.

**A one-time retrofit was directed by the product owner and completed on 2026-09-01**, filing [ADR-0001…ADR-0028](../architectures/adr/) from those documents. It is a **one-time pass, not a standing practice**: from here, a decision is recorded when it is taken, and a pre-2026-09-01 decision that was not filed earns an ADR only when it is revisited.

Four rules held the retrofit to something honest, and they bind anyone extending it:

1. **The source keeps authority.** A retrofitted ADR restates a decision; it does not become the operative statement. The `D-n` row and the architecture paragraph remain what they were, and where the two differ the source wins (authority rule 8).
2. **Every record says it was written after the fact.** Each carries *"Recorded retrospectively on 2026-09-01 from …"* in §1, naming the source. A reader must never mistake a reconstruction for a contemporaneous record.
3. **No invented alternatives.** §3 carries only options the documents actually record. Where the founding pass named no rejected option — the web framework, the query library — the ADR says so rather than reconstructing a plausible loser. A retrofit's failure mode is a record written from the outcome, and an invented alternative is exactly that.
4. **Not everything was filed.** Scope and planning decisions stayed `D-n` (§2): the MVP tag moving to `v0.6.0` (`D-1`), the RAD phase split (`D-2`), priority versus MVP scope (`D-3`), the confirmed NFR targets (`D-5`), the requirement amendments (`D-6`, `D-8`), staging (`D-9`), the carry-over dispositions (`D-13`, `D-17`), the phase re-baselines (`D-16`, `D-43`, `D-44`), the documentation-pointer rule (`D-34`) and the CI title lint (`D-38`). So did the process decisions — the browser harness (`D-14`) — a single screen's behaviour (`D-25`), and the open question `D-15`. §6 of the backlog carries the full map of which `D-n` became which ADR.

The one thing a retrofit cannot recover is the moment of choosing. These records are as good as the documents they were written from — which, in this project, is good — but a decision taken tomorrow and written tomorrow is worth more than any of them.

## 10. Author Checklist

- [ ] The decision passes at least one significance test (§1) and is not on the exclusion list (§2)
- [ ] Number is free; title states the decision, not the topic
- [ ] §3 lists every option that was really on the table, each with why it lost
- [ ] §4 states the costs, not only the benefits, and its impacted-documents table is complete
- [ ] Those documents are changed in this same branch, with their `Last updated` bumped
- [ ] §5 names a mechanical check where one can exist; §6 names a real trigger
- [ ] Row added to `docs/README.md`; superseded ADRs updated on both sides
- [ ] Status and `Last updated` are correct for what merging this actually means
