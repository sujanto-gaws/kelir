# Kelir Commit Message Convention

**Status:** Draft · **Last updated:** 2026-08-05

Kelir uses [Conventional Commits](https://www.conventionalcommits.org/) . Commit messages are machine-readable: they drive the changelog and the version bump in the [release process](04.%20Release%20Process.md).

---

## 1. Format

```text
<type>(<scope>): <subject>

<body>

<footer>
```

- **Header** (required): ≤ 72 characters, imperative mood ("add", not "added"/"adds"), lowercase after the colon, no trailing period.
- **Body** (optional): explains *why*, not *what* — the diff shows what. Wrap at 72 characters. Separated from the header by a blank line.
- **Footer** (optional): breaking-change notice and issue references.

---

## 2. Types

| Type | Meaning | Version effect |
|---|---|---|
| `feat` | New user-facing capability | minor |
| `fix` | Bug fix | patch |
| `docs` | Documentation only | none |
| `refactor` | Code change that is neither feature nor fix | none |
| `perf` | Performance improvement | patch |
| `test` | Adding or correcting tests | none |
| `build` | Build system, dependencies, Docker | none |
| `ci` | CI configuration | none |
| `chore` | Maintenance that touches no production code | none |
| `revert` | Reverts a previous commit | mirrors reverted commit |

A `!` after the type/scope marks a breaking change (see §4).

---

## 3. Scopes

The scope is the module or area touched, in `kebab-case`. Use the backend module vocabulary, frontend feature names, or doc areas:

- Backend modules: `auth`, `identity`, `roles`, `organization`, `master-data`, `rad`, `document-type`, `document`, `workflow`, `task-inbox`, `attachment`, `comment`, `activity`, `audit`, `notification`, `reporting`, `search`, `integration`, `plugin`
- Frontend: the feature folder (`documents`, `tasks`, `master-data`, `admin`, …) or `ui` for shared components
- Cross-cutting: `api`, `db`, `deploy`, `docs`, `jfss`, `standards`

Omit the scope only when the change genuinely spans the repository (`chore: bump toolchain`).

---

## 4. Breaking Changes

Mark with `!` and describe in the footer:

```text
feat(api)!: move supplier endpoints to party-based master data

The /master-data/suppliers collection is now a role-filtered view over
/master-data/parties. Clients that created suppliers directly must use
POST /master-data/parties with a SUPPLIER role.

BREAKING CHANGE: POST /master-data/suppliers removed.
```

Breaking changes to the API, database schema, JFSS contract, or plugin interface always require the `!` marker — reviewers reject unmarked ones.

---

## 5. Examples

Good:

```text
feat(document): add cancel action with CANCELLED workflow state
fix(attachment): block download until virus scan status is CLEAN
docs(standards): add naming convention for party tables
refactor(workflow): extract state-transition validation into domain layer
build(deploy): add minio service to docker compose
revert: feat(document): add cancel action with CANCELLED workflow state
```

Bad — and why:

```text
Fixed some bugs               # no type/scope, past tense, says nothing
feat: update code             # subject does not describe the change
fix(Document): Add Cancel.    # scope not kebab-case, capitalized subject, period
feat(document): add cancel action and fix attachment scan bug   # two changes in one commit — split it
```

---

## 6. Rules of Thumb

1. **One logical change per commit.** If the subject needs "and", split the commit.
2. **The subject must let a reader decide whether to open the diff.** "fix(workflow): handle X" beats "fix(workflow): bug fix".
3. **Reference issues in the footer** (`Closes #42`), never in the subject.
4. **Revert with `git revert`** so the `revert:` header and original SHA footer are generated.
5. Merge commits and release tags are exempt from this format; everything else is not — CI lints commit headers on pull requests.
