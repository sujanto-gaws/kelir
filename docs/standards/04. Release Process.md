# Kelir Release Process

**Status:** Adopted · **Last updated:** 2026-11-04

This document defines how Kelir is versioned, released, and rolled back. Commit messages feeding this process are defined in [03. Commit Message Convention.md](03.%20Commit%20Message%20Convention.md).

---

## 1. Versioning

- The **platform** (backend + frontend, released together) follows [Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`.
- `kelir-backend/Cargo.toml` and `kelir-frontend/package.json` always carry the same platform version.
- **Pre-1.0 rule:** while the platform is `0.x`, breaking changes bump the **minor** version and fixes bump the **patch** version. From `1.0.0` on, standard SemVer applies and breaking changes require a major bump.
- Independently versioned artifacts (not tied to the platform version):
  - **JFSS** specification and meta-schema (currently v2.0.1) and its rule registries — versioned in `docs/schema/`.
  - **Plugins** — each carries its own version in `plugin.json` and declares platform compatibility via `kelirVersion` (e.g. `>=1.0.0`).
  - **Documents** in `docs/` — versioned per document (see the SRS revision history).
- The version bump for a release is derived from the commits since the last tag: any `!`/`BREAKING CHANGE` → minor (pre-1.0) or major (post-1.0); else any `feat` → minor; else `fix`/`perf` → patch.

## 2. Branching Model

The day-to-day branch, PR, and merge workflow is defined in [05. Git Workflow.md](05.%20Git%20Workflow.md); in summary:

- `main` is the integration branch and is always releasable: protected, PR-only, CI green required.
- Work happens on `feature/<slug>`, `fix/<slug>`, `docs/<slug>` branches off `main`.
- Releases are cut from `main` and marked with an annotated tag `vX.Y.Z`.
- Hotfixes branch from the release tag (`hotfix/<slug>` from `vX.Y.Z`), release as `vX.Y.Z+1`, and are merged back to `main`.

## 3. Release Cadence

- Releases align with the roadmap phases in the System Design Document (§14): each phase ends with at least one tagged release.
- Patch releases ship as needed; there is no fixed calendar.

## 4. Release Steps

**The steps are numbered by what each one produces, and a release run does them in this order** (added 2026-11-04, [#653](https://github.com/sujanto-gaws/kelir/issues/653)):

```text
1. Steps 1-4: the freeze on main, then the migration review, the version bump and the
   changelog on the release branch.
2. Build the images from the release commit, the chore(release) commit, in a detached
   worktree at that commit (step 6).
3. Rehearse on those images: step 2's two databases, §6's rollback, step 7's smoke pass.
4. Merge the release PR. It carries the release record's Pre-flight rows (step 5).
5. Tag the release PR's squash-merge commit, locally (step 5).
6. Build again, from that commit (step 6). Repeat step 7's smoke pass on those images,
   and run the release gate with the tag present.
7. Push the tag.
```

**Why this order and not tag, then build.** Three facts fix it. [Release record 08](../../projects/releases/08.%20Release%20v0.8.0.md) is where they were first met:

- **The tag names a commit `main` holds.** A release PR is squash-merged ([05. Git Workflow.md](05.%20Git%20Workflow.md) §6), so the `chore(release)` commit on the release branch never reaches `main`, and tags exist only on `main` commits (§8 there). The tag goes on the squash-merge commit, which exists only after the merge.
- **What is tagged is rehearsed before it is tagged.** A rehearsal can find a defect. Found after the tag, it is a defect in a tagged release. So the rehearsals run first, on images from the release commit, and the release PR merges once they pass.
- **The gate is green with the tag present before the tag is pushed.** `releases_are_independently_verified.rs` rules 11 and 12 read the record at the tag's commit and turn red only once the tag exists ([#484](https://github.com/sujanto-gaws/kelir/issues/484)). The workflow that runs on a `v*` push detects a wrong tag and cannot stop one. So the tag is created locally, the gate runs with it, and the push comes last.

**The rehearsals stand for the tagged images only because no product path differs between the two commits.** The run checks that `git diff --stat <release commit> <merge commit> -- kelir-backend kelir-frontend deploy` is empty, and the release record says so. If it is not empty, the rehearsals run again on the second build. The second build is what makes `/version` and `/version.json` report the tagged commit, because each image bakes its SHA in (step 6). *(Steps 5 and 6 said to tag and then build from the tag until 2026-11-04. `v0.8.0` and `v0.9.0` were cut in the order above, and records 08 and 09 say so.)*

1. **Freeze and verify.** All intended PRs merged; CI green on `main` (fmt, clippy, backend tests, frontend lint + type-check + tests, builds).
2. **Migration review.** New migrations are numbered sequentially with no gaps, apply cleanly to (a) an empty database and (b) a copy of the previous release's schema, and respect the compatibility rule in §6.
3. **Determine the version** from the commit log (§1) and bump `Cargo.toml` + `package.json` in a single `chore(release): vX.Y.Z` commit.
4. **Update `CHANGELOG.md`** ([Keep a Changelog](https://keepachangelog.com/) format): generate the section from conventional commits, then curate — group by Added/Changed/Fixed/Removed, write for users, call out breaking changes and required migration/config actions at the top.

   **A released section is corrected in place and never rewritten, because its tag cannot change** (added 2026-11-04, [#699](https://github.com/sujanto-gaws/kelir/issues/699)). The tag message keeps the text it was cut with. A sentence in a released section that says more than the code is struck through with `~~ ~~` and restated beside it, with the date and the issue, and `[Unreleased]` names the correction under *Fixed*, so the next tag carries it. [#697](https://github.com/sujanto-gaws/kelir/issues/697)'s correction of `v0.4.0`'s reset entry was the first struck in place; an earlier correction of a `[0.4.0]` sentence, [#652](https://github.com/sujanto-gaws/kelir/pull/652)'s, is a note in `[0.9.0]`. It is the form [06. Architecture Decision Records.md](06.%20Architecture%20Decision%20Records.md) §6 uses for an adopted ADR. **A claim readers have split twice is struck and not narrowed** ([sprint plan](../../projects/planning/01.%20Sprint%20Plan.md) §2 (a)): what is restated beside it promises nothing a case can refute.
5. **Tag**: annotated tag `vX.Y.Z` on ~~the release commit~~ the release PR's squash-merge commit, created locally and pushed only once step 7's smoke pass on that commit's images and the gate with the tag present are green (the order above; corrected 2026-11-04, [#653](https://github.com/sujanto-gaws/kelir/issues/653)); the tag message is the changelog section for that version. The release record's Pre-flight rows, the Independent pass citation included, are committed before the tag, because `releases_are_independently_verified.rs` reads the record at the tagged commit ([#484](https://github.com/sujanto-gaws/kelir/issues/484)). **The citation is a link in the Pre-flight table's *Independent pass* row**: rules 1, 2 and 7 read only that row's links, so a path elsewhere in the record, in a link's title or in a code span does not count ([#568](https://github.com/sujanto-gaws/kelir/issues/568)); an angle-bracket destination and an HTML `href` are not links to it, and the row must open with `|` and start with *Independent pass*. Rule 12 reads the row at the tag the same way, and rules 6, 13 and 14 still read every citation in the record. **The cited record's `**Reader session:**` must appear in no construction commit's `Claude-Session:` line since the previous tag** (rules 13 and 14, [#549](https://github.com/sujanto-gaws/kelir/issues/549)), and the gate checks this before the tag as well as at it.
6. **Build artifacts** ~~from the tag~~ twice, each from a detached worktree at its commit: from the release commit, for the rehearsals, and from the commit step 5 tags, before the tag is pushed (the order above; corrected 2026-11-04, [#653](https://github.com/sujanto-gaws/kelir/issues/653)):
   - Backend container image `kelir-backend:X.Y.Z` (also tagged with the git SHA).
   - Frontend build `kelir-frontend:X.Y.Z` (static bundle image or artifact).
   - Images are immutable: never overwrite a published version tag; `latest` is a convenience alias only.

   ```bash
   VERSION=0.1.0
   SHA=$(git rev-parse --short HEAD)

   docker build -f deploy/docker/backend.Dockerfile      --build-arg KELIR_BUILD_SHA="$SHA"      -t kelir-backend:"$VERSION" -t kelir-backend:"$SHA" kelir-backend

   docker build -f deploy/docker/frontend.Dockerfile      --build-arg KELIR_BUILD_SHA="$SHA"      -t kelir-frontend:"$VERSION" -t kelir-frontend:"$SHA" kelir-frontend
   ```

   **Both images bake `KELIR_BUILD_SHA` in at build time**, and neither build argument is optional: it is what `/version` and `/version.json` report in step 7. **The frontend's was missing until [#362](https://github.com/sujanto-gaws/kelir/issues/362)**, and the cost was that `kelir-frontend:0.6.0`'s served bundle was byte-identical to `0.6.0-rc`'s — 45 files, same hash — so Docker gave the new image the rc's creation timestamp and **no frontend image could be told from another**. Unset, both fall back to `git rev-parse` and then to `unknown`, which never fails a build; step 7 is where a missing SHA is caught.

7. **Bring the stack up from the release images and smoke-test it.** Not from the working tree: the point of this step is that what you verify is what the images contain, built in step 6, with migrations run by the backend as it starts. Then: `/health`, `/health/ready`, `/health/live` all green; `/version` reports the expected version and SHA **for the backend**; **`/version.json` reports them for the frontend** ([#362](https://github.com/sujanto-gaws/kelir/issues/362)) — a static asset of the bundle, which Caddy serves ahead of the SPA fallback, so the two identities sit side by side and this step covers both artefacts rather than one; login, document submission, and one workflow approval succeed (the last three from Phase 2, 4 and 5 respectively — until then, verify what exists).

   **Sign-in no longer has to be checked by hand.** From Sprint 7 the browser harness in [`e2e/`](../../e2e/README.md) drives it against this same stack, ~~so point it at the address the deploy printed rather than repeating the flow in a browser yourself~~ so run it on the stack's host rather than repeating the flow in a browser yourself (restated 2026-11-04, [#670](https://github.com/sujanto-gaws/kelir/issues/670); the paragraph after the commands says why). The stack and the harness are brought up with [`e2e/README.md`](../../e2e/README.md)'s commands, *Running it*:

   ```bash
   cd deploy/staging
   KELIR_BOOTSTRAP_ADMIN_USERNAME=admin \
   KELIR_BOOTSTRAP_ADMIN_PASSWORD='a-real-bootstrap-password' \
   KELIR_COMPOSE_OVERLAY=docker-compose.e2e.yml \
   KELIR_E2E_UPSTREAM_TOKEN='a-throwaway-upstream-token' \

   npx playwright install --with-deps chromium firefox

   KELIR_E2E_USERNAME=admin \
   KELIR_E2E_PASSWORD='a-real-bootstrap-password' \
   KELIR_E2E_UPSTREAM_TOKEN='a-throwaway-upstream-token' \
     npm test
   ```

   *(Restated 2026-11-04, [#670](https://github.com/sujanto-gaws/kelir/issues/670). This step gave two commands of its own: the harness pointed at `http://<host-ip>:8080` with no `KELIR_E2E_USERNAME`, and, further down, `./deploy/staging/deploy-local.sh 0.1.0`, which set neither `KELIR_COMPOSE_OVERLAY` nor `KELIR_E2E_UPSTREAM_TOKEN`, so it did not layer the overlay the paragraph below describes.    **The harness runs on the stack's host.** The overlay publishes the stand-in's journal on that host's loopback only, `127.0.0.1:8089` (`KELIR_E2E_UPSTREAM_PORT`), so a harness on another machine cannot read it. A stack whose stand-in is on another port gives the harness `KELIR_E2E_UPSTREAM_URL` to match ([`e2e/README.md`](../../e2e/README.md), *The one system the stack can reach*). **A release run adds two variables to the `deploy-local.sh` command**, `KELIR_SOURCE_DIR` and `KELIR_FORCE_BUILD=1`, as the paragraph on the detached worktree below says.

   **One flow needs the stack brought up with an overlay, and the release run layers it** ([#593](https://github.com/sujanto-gaws/kelir/issues/593)). An integration test call that is answered needs a system to answer it, which a release stack does not have. So this step brings the stack up with `KELIR_COMPOSE_OVERLAY=docker-compose.e2e.yml` and a throwaway `KELIR_E2E_UPSTREAM_TOKEN`, and gives the harness the same token. The overlay adds a stand-in system, its one address in `KELIR_INTEGRATION_ALLOWED_CIDRS` and the system tenant's secret, and changes neither image; [`e2e/README.md`](../../e2e/README.md), *The one system the stack can reach*, has the whole of it. **The flow is skipped in one case only: the harness has no `KELIR_E2E_UPSTREAM_TOKEN` and is not running in CI.** The report then lists it as skipped, with the reason. With the token it always runs, and fails against a stack that lacks the overlay; in CI it fails without the token. A release run gives the token, so a skipped flow in a release run's report means the step was not run as written.

   Document submission and workflow approval stay manual until a flow covers each; the harness is the place they go when it does.

   `deploy-local.sh` ~~is the same compose file, the same images and the same smoke test as a hosted deploy would use — only the address differs~~ runs the same images and the same smoke test as a hosted deploy would use, and the same compose file with `docker-compose.e2e.yml` layered over it. **The overlay adds** the stand-in service on a network of its own, publishes the stand-in's journal on the host's loopback, and sets two variables on the backend: `KELIR_INTEGRATION_ALLOWED_CIDRS`, naming the stand-in's one address, and the system tenant's secret, `KELIR_INTEGRATION_SECRET_SYSTEM__E2E_UPSTREAM_TOKEN`. It changes neither image. Beyond the overlay only the address differs (restated 2026-11-04, [#670](https://github.com/sujanto-gaws/kelir/issues/670): with the overlay layered, the compose file is not a hosted deploy's), and that is deliberate: a deployment test that differs from the real deployment mostly proves the difference works. Two things it cannot cover are stated in the script itself: no TLS, because certificates are not issued for an IP address (so NFR-SEC-010 is not exercised here), and `KELIR_APP_ENV=development` unless `KELIR_EXPECTED_ENV=staging` is passed.

   **A release run builds from a detached worktree at the release commit** (added 2026-10-08): `deploy-local.sh` builds the working tree by default and reuses images already tagged with the version unless `KELIR_FORCE_BUILD=1`, so the run sets `KELIR_SOURCE_DIR` to that worktree and `KELIR_FORCE_BUILD=1`, and the images' `KELIR_BUILD_SHA` is then the release commit, because `deploy.sh` reads it from the worktree's `HEAD` and not from the environment. **The second build does the same from a detached worktree at the squash-merge commit** (added 2026-11-04, [#653](https://github.com/sujanto-gaws/kelir/issues/653); the order at the top of this section).

   **There is no staging host.** This step named one until 2026-08-21, and it was outstanding at every release the project has cut, because no infrastructure was available to host it (decision **D-9**). The compose stack is what exists, and it preserves the property the staging step was protecting — that the artefact verified is the artefact released, not a developer's working tree. [§4.1](#41-staging-environment-unscheduled) keeps the environment definition for the day a host appears.
8. **Deploy to production** using the same artifacts (never rebuilt). Migrations run before the new version receives traffic. **No production host exists under decision D-9**, so this step is not performed today; the release record says so rather than leaving the step implied. It becomes live once a host exists.
9. **Post-release verification.** `/version` correct, error rates and latency normal for 30 minutes, no failed outbox/notification workers — **against the production host of step 8, so likewise not performed under D-9**, and the release record says so; step 7's smoke pass is the verification that runs. Announce the release with the changelog section.

## 4.1 Staging Environment (unscheduled)

> **Nothing runs this.** `kelir-staging-01` has never existed and no infrastructure is available to provision it. Decision **D-9** (2026-08-21) removed staging from the release steps and the Definition of Done rather than leaving a gate nobody could pass; issue #12 is closed as not planned. What follows is kept because it is finished and verified — if a host appears, the work is a deploy, not a redesign. Read it as a design, not as a description of something running.

`kelir-staging-01` **would be** an Ubuntu Server 24.04 host serving <https://staging.kelir.gawshub.com>.

- **One origin.** Caddy serves the frontend bundle at `/` and reverse-proxies `/api/*`, `/health*` and `/version` to the backend container. The browser would therefore never make a cross-origin request, so CORS would not apply there — it exists for the local Vite dev server — and session cookies stay same-site.
- **PostgreSQL runs natively on the host**, not in a container. Its data directory is an ordinary host path, which makes the NFR-AVA-004 restore drill a real exercise rather than a volume copy, and it keeps the database alive across a stack redeploy. The application containers reach it through the Docker bridge gateway (`host.docker.internal`), a local host and so exempt from the backend's TLS requirement for the database ([#803](https://github.com/sujanto-gaws/kelir/issues/803), added 2026-10-29); `pg_hba.conf` admits only the Docker address pool with `scram-sha-256`, and the firewall never opens 5432.
- **Only Caddy publishes ports.** Object storage and the mail catcher are reachable on the internal Docker network alone; reach Mailpit over an SSH tunnel rather than by publishing it.
- **Backups run daily at 02:30 UTC** via a systemd timer (`kelir-backup.timer`), keeping 14 days of ~~`pg_dump` custom-format archives~~ encrypted pairs in `/var/backups/kelir`: `kelir-<stamp>.dump.age`, the database, and `kelir-<stamp>.objects.age`, every object in the bucket, each streamed through `age` to recipients whose identity the host does not hold. The unit runs as root. *(Corrected 2026-10-28, [#778](https://github.com/sujanto-gaws/kelir/issues/778), ADR-0049, **D-122**; the [Installation guide](../operations/01.%20Installation%20and%20Deployment.md) §8.)* `deploy.sh` also takes one immediately before every deploy, because a migration that fails halfway is exactly when yesterday's dump is not good enough.
- **TLS** is obtained and renewed automatically by Caddy, ~~satisfying NFR-SEC-010~~ which meets NFR-SEC-010 at the edge. *(Corrected 2026-10-28: under decision **D-119**, NFR-SEC-010 also needs the backend's connection to PostgreSQL over TLS, which ~~[#803](https://github.com/sujanto-gaws/kelir/issues/803) builds~~ holds since [#803](https://github.com/sujanto-gaws/kelir/issues/803) for any database host that is not local. Restated 2026-10-29.)*
- **Secrets** come from `/opt/kelir/.env` on the host, generated per environment. The backend refuses to start in staging on a placeholder secret, so an unedited copy of the example file fails immediately rather than running with forgeable tokens.
- **Deploys are by tag.** `KELIR_VERSION` selects the released image; nothing is built on the host.

Everything lives in [`deploy/staging/`](../../deploy/staging/):

| File | Purpose |
|---|---|
| `provision-ubuntu-24.sh` | One-time host setup: Docker, PostgreSQL, role and database, firewall, backup timer. Idempotent |
| `deploy.sh` | Per-release deploy: secret checks, image build or pull, pre-deploy backup, `compose up`, smoke test |
| `deploy-local.sh` | The same deploy against an IP address: it sets the address and hands over to `deploy.sh` (*Testing the deployment locally*, below) |
| `docker-compose.staging.yml` | The stack — Caddy, backend, MinIO, Mailpit |
| `docker-compose.e2e.yml` | An overlay for the browser flows, layered when `KELIR_COMPOSE_OVERLAY` names it: one stand-in external system ([#593](https://github.com/sujanto-gaws/kelir/issues/593), §4 step 7). No hosted deployment sets the variable |

First-time setup on a fresh host:

```bash
sudo ./provision-ubuntu-24.sh          # installs everything, generates the DB password
$EDITOR /opt/kelir/.env                # add KELIR_JWT_SECRET and the MinIO pair
./deploy.sh 0.1.0                      # build or pull, deploy, smoke-test
```

### Testing the deployment locally

`deploy-local.sh` runs the same images, compose file and smoke test against an IP address instead of a hostname, for trying a release candidate before it is tagged:

```bash
./deploy-local.sh 0.1.0            # auto-detects the host IP, port 8080
./deploy-local.sh 0.1.0 9090       # a different port
KELIR_HOST_IP=192.168.1.50 ./deploy-local.sh 0.1.0
```

Two differences are unavoidable, and both are why this mode is for testing only:

- **Plain HTTP.** No certificate can be issued for an IP address, so ~~NFR-SEC-010 is not satisfied~~ NFR-SEC-010 is not satisfied at the edge. The database hop, to `host.docker.internal`, is local, where **D-119** C requires no TLS *(restated 2026-10-29, [#803](https://github.com/sujanto-gaws/kelir/issues/803))*.
- **`KELIR_APP_ENV=development`.** Staging refuses placeholder secrets, which is right for an internet-facing host and needless friction on a laptop. Pass `KELIR_EXPECTED_ENV=staging` to exercise the stricter path deliberately.

It builds from the working tree rather than a tag, since the point is to test before tagging, and reuses images already present at that tag unless `KELIR_FORCE_BUILD=1`.

`deploy.sh` builds the images on the host while no registry is configured. Set `KELIR_IMAGE_REGISTRY` once images are published and the same script pulls them instead, which is what step 8 means by deploying the same artifacts rather than rebuilding them.

## 5. Hotfixes

1. Branch from the affected tag: `hotfix/<slug>` from `vX.Y.Z`.
2. Fix with the minimal change; add the regression test.
3. Release as `vX.Y.(Z+1)` following §4 steps 3–9 (the step 7 smoke pass is mandatory even for hotfixes; for a hotfix, step 5 tags the hotfix release commit, because the merge back to `main` follows in item 4, and [05. Git Workflow.md](05.%20Git%20Workflow.md) §8 allows a tag on a hotfix release commit; added 2026-11-04).
4. Merge the hotfix branch back to `main` (or cherry-pick if `main` has diverged).

## 6. Rollback and Migration Compatibility

- **Application rollback** is redeploying the previous version's images. The images are immutable, so the old binary always exists — but *existing* and *starting* are different things, and the two rules below are what make the second one true.
- **Migrations are forward-only** (never edited or reverted once applied). To make application rollback safe, every migration MUST be backward-compatible with the previous release (**N−1 rule**). The rule has two halves, and a release can satisfy one while breaking the other.
  - **The schema half.** The previous application version must run correctly against the new schema. Practically: add columns as nullable or with defaults; don't drop or rename columns/tables in the same release that stops using them — deprecate in release N, remove in N+1.
  - **The bookkeeping half.** The previous application version must also *start* against the new `_sqlx_migrations`. By default SQLx treats an applied migration it cannot resolve as fatal — `migration N was previously applied but is missing in the resolved migrations` — so a perfectly additive release is still unrollable unless the migrator is told to tolerate versions newer than itself. Kelir sets `Migrator::set_ignore_missing(true)` in `db::run_migrations` for exactly this reason (#76). Checksums are still verified, so an edited migration fails as loudly as before.
  - This half was learned the hard way: `v0.2.0` obeyed every word of the schema rule and could not be rolled back, because the rule as written named only columns. **A binary released before the migrator was configured cannot be rolled back to** without deleting the rows above its highest known migration from `_sqlx_migrations` first — which for Kelir means `v0.1.0`.
  - A migration that cannot be N−1-compatible requires an explicit maintenance-window plan in the release notes.
- **Rehearse the rollback, don't reason about it.** Both halves are cheap to test and neither is visible from reading a diff:
  1. Migrate an empty database with the **new** binary, so `_sqlx_migrations` holds what a real deployment would.
  2. Start the **previous release's** binary, built from its tag, against that database. It must reach `/health/ready`.
  3. If it is a compiled check you want as well: the previous release's source compiling against the migrated database proves every query it holds still type-checks, because SQLx verifies them at build time.

  Step 2 is the one that caught this at `v0.2.0`, and the one a reader is most likely to skip. Record the result in the release document under *Staging → Rollback rehearsed*, including a failure — a blank row reads as "passed" to everyone who comes later.
- **A rollback to a release before `v0.7.0` verifies one artefact of the two, and the deploy says which.** `/version.json` is [#362](https://github.com/sujanto-gaws/kelir/issues/362)'s asset and no frontend image before `v0.7.0` carries it, so Caddy answers that path with the single-page fallback instead. `deploy.sh` reports the frontend as **unverified** and exits 0 rather than calling the right image the wrong one — which is what it did until [#440](https://github.com/sujanto-gaws/kelir/issues/440), on `v0.7.0`'s only rollback target. **The assertion is narrowed, not suspended:** a bundle answering with a *different* version still fails the deploy at every version, and an absent answer fails it too from `v0.7.0` upward. The backend's identity is unaffected — `/version` has answered since Sprint 0 — so what step 7 above covers in full on a forward deploy, a rollback below `v0.7.0` covers by half, and the output names the half.
- If a release fails in production: roll back the application images first; investigate; fix forward with a hotfix. Database restore from backup is the last resort and follows the DR targets in the SRS (RPO ≤ 24h, RTO ≤ 4h).
