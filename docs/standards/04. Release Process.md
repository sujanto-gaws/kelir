# Kelir Release Process

**Status:** Adopted · **Last updated:** 2026-08-20

This document defines how Kelir is versioned, released, and rolled back. Commit messages feeding this process are defined in [03. Commit Message Convention.md](03.%20Commit%20Message%20Convention.md).

---

## 1. Versioning

- The **platform** (backend + frontend, released together) follows [Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`.
- `kelir-backend/Cargo.toml` and `kelir-frontend/package.json` always carry the same platform version.
- **Pre-1.0 rule:** while the platform is `0.x`, breaking changes bump the **minor** version and fixes bump the **patch** version. From `1.0.0` on, standard SemVer applies and breaking changes require a major bump.
- Independently versioned artifacts (not tied to the platform version):
  - **JFSS** specification and meta-schema (currently v2.0.1) and its rule registries — versioned in `docs/schema/`.
  - **Plugins** — each carries its own version in `plugin.json` and declares platform compatibility via `kelirVersion` (e.g. `>=1.0.0`).
  - **Documents** in `docs/` — versioned per document (see the SRS revision history).
- The version bump for a release is derived from the commits since the last tag: any `!`/`BREAKING CHANGE` → minor (pre-1.0) or major (post-1.0); else any `feat` → minor; else `fix`/`perf` → patch.

## 2. Branching Model

The day-to-day branch, PR, and merge workflow is defined in [05. Git Workflow.md](05.%20Git%20Workflow.md); in summary:

- `main` is the integration branch and is always releasable: protected, PR-only, CI green required.
- Work happens on `feature/<slug>`, `fix/<slug>`, `docs/<slug>` branches off `main`.
- Releases are cut from `main` and marked with an annotated tag `vX.Y.Z`.
- Hotfixes branch from the release tag (`hotfix/<slug>` from `vX.Y.Z`), release as `vX.Y.Z+1`, and are merged back to `main`.

## 3. Release Cadence

- Releases align with the roadmap phases in the System Design Document (§14): each phase ends with at least one tagged release.
- Patch releases ship as needed; there is no fixed calendar.

## 4. Release Steps

1. **Freeze and verify.** All intended PRs merged; CI green on `main` (fmt, clippy, backend tests, frontend lint + type-check + tests, builds).
2. **Migration review.** New migrations are numbered sequentially with no gaps, apply cleanly to (a) an empty database and (b) a copy of the previous release's schema, and respect the compatibility rule in §6.
3. **Determine the version** from the commit log (§1) and bump `Cargo.toml` + `package.json` in a single `chore(release): vX.Y.Z` commit.
4. **Update `CHANGELOG.md`** ([Keep a Changelog](https://keepachangelog.com/) format): generate the section from conventional commits, then curate — group by Added/Changed/Fixed/Removed, write for users, call out breaking changes and required migration/config actions at the top.
5. **Tag**: annotated tag `vX.Y.Z` on the release commit; the tag message is the changelog section for that version.
6. **Build artifacts** from the tag:
   - Backend container image `kelir-backend:X.Y.Z` (also tagged with the git SHA).
   - Frontend build `kelir-frontend:X.Y.Z` (static bundle image or artifact).
   - Images are immutable: never overwrite a published version tag; `latest` is a convenience alias only.

   ```bash
   VERSION=0.1.0
   SHA=$(git rev-parse --short HEAD)

   docker build -f deploy/docker/backend.Dockerfile      --build-arg KELIR_BUILD_SHA="$SHA"      -t kelir-backend:"$VERSION" -t kelir-backend:"$SHA" kelir-backend

   docker build -f deploy/docker/frontend.Dockerfile      -t kelir-frontend:"$VERSION" -t kelir-frontend:"$SHA" kelir-frontend
   ```

   The backend image bakes `KELIR_BUILD_SHA` in at build time — that is what `/version` reports in step 7, so the build argument is not optional.

7. **Bring the stack up from the release images and smoke-test it.** Not from the working tree: the point of this step is that what you verify is what the images contain, built in step 6, with migrations run by the backend as it starts. Then: `/health`, `/health/ready`, `/health/live` all green; `/version` reports the expected version and SHA; login, document submission, and one workflow approval succeed (the last three from Phase 2, 4 and 5 respectively — until then, verify what exists).

   **Sign-in no longer has to be checked by hand.** From Sprint 7 the browser harness in [`e2e/`](../../e2e/README.md) drives it against this same stack, so point it at the address the deploy printed rather than repeating the flow in a browser yourself:

   ```bash
   cd e2e && npm ci
   KELIR_E2E_BASE_URL=http://<host-ip>:8080 KELIR_E2E_PASSWORD='…' npm test
   ```

   Document submission and workflow approval stay manual until a flow covers each; the harness is the place they go when it does.

   ```bash
   ./deploy/staging/deploy-local.sh 0.1.0        # brings the stack up and runs the smoke test
   ```

   `deploy-local.sh` is the same compose file, the same images and the same smoke test as a hosted deploy would use — only the address differs, which is deliberate: a deployment test that differs from the real deployment mostly proves the difference works. Two things it cannot cover are stated in the script itself: no TLS, because certificates are not issued for an IP address (so NFR-SEC-010 is not exercised here), and `KELIR_APP_ENV=development` unless `KELIR_EXPECTED_ENV=staging` is passed.

   **There is no staging host.** This step named one until 2026-08-21, and it was outstanding at every release the project has cut, because no infrastructure was available to host it (decision **D-9**). The compose stack is what exists, and it preserves the property the staging step was protecting — that the artefact verified is the artefact released, not a developer's working tree. [§4.1](#41-staging-environment-unscheduled) keeps the environment definition for the day a host appears.
8. **Deploy to production** using the same artifacts (never rebuilt). Migrations run before the new version receives traffic.
9. **Post-release verification.** `/version` correct, error rates and latency normal for 30 minutes, no failed outbox/notification workers. Announce the release with the changelog section.

## 4.1 Staging Environment (unscheduled)

> **Nothing runs this.** `kelir-staging-01` has never existed and no infrastructure is available to provision it. Decision **D-9** (2026-08-21) removed staging from the release steps and the Definition of Done rather than leaving a gate nobody could pass; issue #12 is closed as not planned. What follows is kept because it is finished and verified — if a host appears, the work is a deploy, not a redesign. Read it as a design, not as a description of something running.

`kelir-staging-01` **would be** an Ubuntu Server 24.04 host serving <https://staging.kelir.gawshub.com>.

- **One origin.** Caddy serves the frontend bundle at `/` and reverse-proxies `/api/*`, `/health*` and `/version` to the backend container. The browser would therefore never make a cross-origin request, so CORS would not apply there — it exists for the local Vite dev server — and session cookies stay same-site.
- **PostgreSQL runs natively on the host**, not in a container. Its data directory is an ordinary host path, which makes the NFR-AVA-004 restore drill a real exercise rather than a volume copy, and it keeps the database alive across a stack redeploy. The application containers reach it through the Docker bridge gateway (`host.docker.internal`); `pg_hba.conf` admits only the Docker address pool with `scram-sha-256`, and the firewall never opens 5432.
- **Only Caddy publishes ports.** Object storage and the mail catcher are reachable on the internal Docker network alone; reach Mailpit over an SSH tunnel rather than by publishing it.
- **Backups run daily at 02:30 UTC** via a systemd timer (`kelir-backup.timer`), keeping 14 days of `pg_dump` custom-format archives in `/var/backups/kelir`. `deploy.sh` also takes one immediately before every deploy, because a migration that fails halfway is exactly when yesterday's dump is not good enough.
- **TLS** is obtained and renewed automatically by Caddy, satisfying NFR-SEC-010.
- **Secrets** come from `/opt/kelir/.env` on the host, generated per environment. The backend refuses to start in staging on a placeholder secret, so an unedited copy of the example file fails immediately rather than running with forgeable tokens.
- **Deploys are by tag.** `KELIR_VERSION` selects the released image; nothing is built on the host.

Everything lives in [`deploy/staging/`](../../deploy/staging/):

| File | Purpose |
|---|---|
| `provision-ubuntu-24.sh` | One-time host setup: Docker, PostgreSQL, role and database, firewall, backup timer. Idempotent |
| `deploy.sh` | Per-release deploy: secret checks, image build or pull, pre-deploy backup, `compose up`, smoke test |
| `docker-compose.staging.yml` | The stack — Caddy, backend, MinIO, Mailpit |
| `Caddyfile` | Single-origin routing and TLS |
| `.env.staging.example` | Secret template; the real `.env` is never committed |

First-time setup on a fresh host:

```bash
sudo ./provision-ubuntu-24.sh          # installs everything, generates the DB password
$EDITOR /opt/kelir/.env                # add KELIR_JWT_SECRET and the MinIO pair
./deploy.sh 0.1.0                      # build or pull, deploy, smoke-test
```

### Testing the deployment locally

`deploy-local.sh` runs the same images, compose file and smoke test against an IP address instead of a hostname, for trying a release candidate before it is tagged:

```bash
./deploy-local.sh 0.1.0            # auto-detects the host IP, port 8080
./deploy-local.sh 0.1.0 9090       # a different port
KELIR_HOST_IP=192.168.1.50 ./deploy-local.sh 0.1.0
```

Two differences are unavoidable, and both are why this mode is for testing only:

- **Plain HTTP.** No certificate can be issued for an IP address, so NFR-SEC-010 is not satisfied.
- **`KELIR_APP_ENV=development`.** Staging refuses placeholder secrets, which is right for an internet-facing host and needless friction on a laptop. Pass `KELIR_EXPECTED_ENV=staging` to exercise the stricter path deliberately.

It builds from the working tree rather than a tag, since the point is to test before tagging, and reuses images already present at that tag unless `KELIR_FORCE_BUILD=1`.

`deploy.sh` builds the images on the host while no registry is configured. Set `KELIR_IMAGE_REGISTRY` once images are published and the same script pulls them instead, which is what step 8 means by deploying the same artifacts rather than rebuilding them.

## 5. Hotfixes

1. Branch from the affected tag: `hotfix/<slug>` from `vX.Y.Z`.
2. Fix with the minimal change; add the regression test.
3. Release as `vX.Y.(Z+1)` following §4 steps 3–9 (the step 7 smoke pass is mandatory even for hotfixes).
4. Merge the hotfix branch back to `main` (or cherry-pick if `main` has diverged).

## 6. Rollback and Migration Compatibility

- **Application rollback** is redeploying the previous version's images. The images are immutable, so the old binary always exists — but *existing* and *starting* are different things, and the two rules below are what make the second one true.
- **Migrations are forward-only** (never edited or reverted once applied). To make application rollback safe, every migration MUST be backward-compatible with the previous release (**N−1 rule**). The rule has two halves, and a release can satisfy one while breaking the other.
  - **The schema half.** The previous application version must run correctly against the new schema. Practically: add columns as nullable or with defaults; don't drop or rename columns/tables in the same release that stops using them — deprecate in release N, remove in N+1.
  - **The bookkeeping half.** The previous application version must also *start* against the new `_sqlx_migrations`. By default SQLx treats an applied migration it cannot resolve as fatal — `migration N was previously applied but is missing in the resolved migrations` — so a perfectly additive release is still unrollable unless the migrator is told to tolerate versions newer than itself. Kelir sets `Migrator::set_ignore_missing(true)` in `db::run_migrations` for exactly this reason (#76). Checksums are still verified, so an edited migration fails as loudly as before.
  - This half was learned the hard way: `v0.2.0` obeyed every word of the schema rule and could not be rolled back, because the rule as written named only columns. **A binary released before the migrator was configured cannot be rolled back to** without deleting the rows above its highest known migration from `_sqlx_migrations` first — which for Kelir means `v0.1.0`.
  - A migration that cannot be N−1-compatible requires an explicit maintenance-window plan in the release notes.
- **Rehearse the rollback, don't reason about it.** Both halves are cheap to test and neither is visible from reading a diff:
  1. Migrate an empty database with the **new** binary, so `_sqlx_migrations` holds what a real deployment would.
  2. Start the **previous release's** binary, built from its tag, against that database. It must reach `/health/ready`.
  3. If it is a compiled check you want as well: the previous release's source compiling against the migrated database proves every query it holds still type-checks, because SQLx verifies them at build time.

  Step 2 is the one that caught this at `v0.2.0`, and the one a reader is most likely to skip. Record the result in the release document under *Staging → Rollback rehearsed*, including a failure — a blank row reads as "passed" to everyone who comes later.
- If a release fails in production: roll back the application images first; investigate; fix forward with a hotfix. Database restore from backup is the last resort and follows the DR targets in the SRS (RPO ≤ 24h, RTO ≤ 4h).

## 7. Release Checklist

| # | Check | Gate |
|---|---|---|
| 1 | CI green on `main` (fmt, clippy, tests, lint, builds) | blocking |
| 2 | Migrations sequential, tested on empty + previous schema; N−1 compatible in **both** halves — schema and migration bookkeeping — rehearsed per §6, not reasoned about | blocking |
| 3 | Version bumped in `Cargo.toml` and `package.json` (matching) | blocking |
| 4 | `CHANGELOG.md` updated and curated; breaking changes at top | blocking |
| 5 | Annotated tag `vX.Y.Z` created | blocking |
| 6 | Images built from tag and pushed with version + SHA tags | blocking |
| 7 | Staging deploy + smoke tests passed | blocking |
| 8 | Production deploy verified via `/version` + monitoring window | blocking |
| 9 | Release announced with changelog | non-blocking |
| 10 | Docs updated if API/config/schema changed | non-blocking |
