# Kelir Git Workflow

**Status:** Adopted · **Last updated:** 2026-09-09

This document defines the day-to-day git workflow: branches, pull requests, review, and merging. Commit messages are defined in [03. Commit Message Convention.md](03.%20Commit%20Message%20Convention.md); versioning, tags, and hotfix releases in [04. Release Process.md](04.%20Release%20Process.md).

---

## 1. Model at a Glance

Trunk-based development with short-lived branches:

```text
main ──●──────●──────●──────●──────●──▶  (protected, always releasable)
        \            ▲ \            ▲
         \           │  \           │
          feature/…──●   fix/…──────●     (squash-merged via PR)

release tags:        v0.2.0         v0.2.1
hotfix (from tag):   hotfix/… ──▶ v0.2.1 ──▶ merged back to main
```

- `main` is the only long-lived branch. It is protected: no direct pushes, PR + green CI + review required.
- Work branches are **short-lived** (target: days, not weeks) and are deleted after merge.
- History on `main` is **linear**: PRs are squash-merged; merge commits and long-running divergence are avoided.

## 2. Branches

| Branch | Purpose | Created from | Merges to |
|---|---|---|---|
| `main` | Integration; always releasable | — | — |
| `feature/<slug>` | New capability | `main` | `main` |
| `fix/<slug>` | Bug fix | `main` | `main` |
| `docs/<slug>` | Documentation only | `main` | `main` |
| `hotfix/<slug>` | Urgent fix to a released version | tag `vX.Y.Z` | tag `vX.Y.Z+1`, then `main` |

- Slugs are `kebab-case` and descriptive: `feature/party-master-data`, `fix/attachment-scan-status`.
- One branch = one PR = one logical change. If the scope grows, split the branch.
- There are no `develop`, `release/*`, or environment branches; environments are served by tags and artifacts (release process §4).

## 3. Working on a Branch

1. Start from a current `main`:

   ```bash
   git switch main && git pull --ff-only
   git switch -c feature/party-master-data
   ```

2. Commit early and often locally; every commit follows the commit convention. Work-in-progress commits are fine on the branch — the squash-merge produces the final history.
3. Keep the branch current by **rebasing onto main** (never merging main into the branch):

   ```bash
   git fetch origin
   git rebase origin/main
   ```

4. Force-push only your own branch, and only with `--force-with-lease`:

   ```bash
   git push --force-with-lease
   ```

5. Never rebase or force-push `main`, tags, or anyone else's branch.

## 4. Pull Requests

- Open the PR early (as **draft** while unfinished). The PR title MUST follow the commit convention — it becomes the squash commit's header, e.g. `feat(master-data): add party CRUD endpoints`.
- The description states: what changed, why, how it was tested, and any breaking change / migration / config action. Link the issue (`Closes #42`).
- **A pull request that closes more than one issue repeats the keyword, one issue per line.** GitHub honours `Closes #42, #43, #44` for `#42` only, silently — the remaining issues stay open with no warning anywhere. Write `Closes #42` / `Closes #43` / `Closes #44` on separate lines. #219 and #223 each closed one of seven and the rest were closed by hand afterwards; #216 is the form that works.
- **An issue folded into another by decision is closed by that other issue's pull request, and the `Closes` line is written when the decision is recorded.** The bullet above is about a pull request that forgot a keyword; this is about one that never had a reason to write it. A branch is named after the issue it implements, and `Closes` follows the branch — so an issue that was *absorbed* rather than implemented has no pull request of its own to be closed by. The work merges and the issue stays open, which reads to everyone afterwards as outstanding scope on a delivered requirement. It is the shape this project's parking decisions produce: an issue unscheduled with a return condition comes back attached to a sibling, not under its own number. #24 (FR-IDM-006) was unscheduled by **D-13** with a return condition and scheduled into #184 by **D-17**; #184 shipped the window, the routing and the surface, and #24 sat open until somebody thought to look. **Write the second `Closes` line into the absorbing issue at the moment the decision is recorded** — by the time the branch is cut, the absorbing issue is the only one anybody still has in mind.
- A PR is ready for review when:
  1. CI is green (fmt, clippy, backend tests, frontend lint + type-check + tests, builds, and the browser flow the `End-to-end (browser)` job drives against the release stack).
  2. It is rebased on current `main` with no conflicts.
  3. It is reviewable in one sitting (~≤ 400 changed lines as a guideline; split larger work).
- Migrations, API contract changes, JFSS/registry changes, and permission changes MUST be called out explicitly in the description.

## 5. Review

- At least **one approval** is required; two for changes to auth/security, migrations, or the plugin interface.

  > **Currently relaxed to zero.** GitHub does not let an author approve their own pull request, so on a single-maintainer repository a one-approval rule blocks every merge. Branch protection on `main` therefore requires a pull request and green CI but no approval. Restore the rule above — set required approvals to 1 — as soon as a second contributor can review. The two-approval cases are unchanged in intent and take effect at the same time.

- **The administrator is inside the gate** (**D-66**, decided 2026-09-08). The rule is that `main`'s required checks bind everybody, administrators included — the party who merges waits for the same checks as the party who does not.

  > **Applied 2026-09-09, and this bullet is a description of the repository at last.** `main` requires five checks — `Backend (Rust)`, `Frontend (Vue)`, `Commit messages`, `End-to-end (browser)` and `Pull-request title` — and bypassing them is off, so the party who merges waits for the same checks as the party who does not. **Both halves went on in one visit to the settings page**, which is what **D-66** required of them: contexts first would have tightened the rule for everybody except the party it was raised about.
  >
  > **One half is verified and the other is attested, and the difference is kept rather than blurred.** The context list reads without administration rights — `gh api repos/sujanto-gaws/kelir/branches/main --jq '.protection.required_status_checks.contexts'` returns the five, which is [#335](https://github.com/sujanto-gaws/kelir/issues/335) AC1's own command. **`enforce_admins` does not read**: the repository's token answers `403` on `repos/…/branches/main/protection`, so that half rests on the product owner having set it rather than on a check. **Stating which is which is the point** — a document asserting a state the system is not in is the defect this project keeps finding, and `activity:read`, `rad_actions` and row 8 of Sprint 14's table were each one. **The evidence that would settle it is the probe** [#335](https://github.com/sujanto-gaws/kelir/issues/335) AC3 asks for: a pull request with a deliberately failing browser spec, *seen* unable to merge. Until that has been run the issue stays open.

  > **The rejected alternative was the honest version of the status quo** — declare the checks advisory and stop maintaining a required list that never fires. It was rejected because a check worth six minutes of CI on every pull request is a check worth waiting for, and **a gate the merging party steps around is not a gate but a report**. (This read *thirteen minutes* until 2026-09-09: `End-to-end (browser)` measures 5–7 minutes over the thirty most recent green runs, and the pipeline's twenty-five are `Backend (Rust)`, already required. The argument is the same at either number, which is why the number is corrected rather than defended.) The question stood open for two sprints as an exit criterion, which is how long it took to notice that *"required"* had been describing nobody.
  >
  > **The setting and the context list are one change, not two.** Adding required contexts while `enforcement_level` stayed `non_admins` would have tightened the rule for everybody except the party it was raised about — the exact state D-66 exists to end. [#335](https://github.com/sujanto-gaws/kelir/issues/335) carries both halves and stays open until they are applied together.
- **A branch is not required to be up to date with `main` before it merges** (**D-75**, decided 2026-09-09). §4's readiness item 2 and §6's rebase bullet stay conventions the author holds rather than settings the gate holds: `required_status_checks.strict` is deliberately **off**.

  > **Decided rather than defaulted, which is D-66's lesson applied one setting over.** A setting nobody chose reads afterwards exactly like a setting somebody did — that is how `enforcement_level: non_admins` survived two sprints of being described as a gate — so this is a *no* with a reason and a return condition rather than an absence.
  >
  > **The reason is measured.** `Backend (Rust)` takes 23–26 minutes across the thirty most recent green runs and is the pipeline's long pole; `End-to-end (browser)` is 6. Under `strict`, every branch behind `main` rebases and pays that again before it can merge — against the eight merges of 2026-09-08, over three hours of serialized CI. What it buys is the composition defect between two branches each green against a different base, and with one party merging sequentially that is rare. **The trade reverses once branches are in flight in parallel**, which is why this is parked rather than closed.
  >
  > **Revisit on the same trigger as the approval rule above** — a second contributor. Both rules are relaxed for the same reason: a single-maintainer repository does not have the shape they assume.

- **The break-glass is `enforce_admins` off, then on again, and said out loud** (**D-75**). Once the checks bind everybody there is no bypass left, which is the point — and there is still such a thing as an emergency, which is why the way out is named in advance instead of improvised. Toggling the setting is the sanctioned route, and the toggle is recorded in the sprint's status report or the release record with what was red and why it could not wait.

  > **What is not sanctioned is a bypass nobody wrote down.** The failure this replaces is not that somebody merged past a red check; it is a repository where that had happened thirteen times in one sprint and no document said so.
- Reviewers apply the checklist in [01. Coding Standard.md](01.%20Coding%20Standard.md) §6.
- Review comments are resolved by the author with a code change or a reasoned reply — never dismissed silently.
- The author merges after approval; do not merge someone else's PR without their ack.

## 6. Merging

- **Squash-merge only.** The squash commit message is the PR title (+ curated body listing noteworthy points, including any `BREAKING CHANGE:` footer).
- The branch is deleted on merge.
- If `main` moved after approval, rebase, let CI re-run, and merge without re-review unless the rebase changed the diff. **This is a convention the author holds, not a check the gate holds** — `required_status_checks.strict` is off by decision (**D-75**, §5), so a branch behind `main` is mergeable and the rebase is yours to remember.
- Reverts on `main` use `git revert` (producing a `revert:` commit) via a normal PR — never history rewrites.

## 7. Conflicts

- Resolve conflicts on the branch during rebase, not in a merge commit.
- When a conflict involves a migration number, renumber your new migration to the next free number — never renumber an existing one (migrations are immutable once merged).
- If two PRs touch the same module contract, coordinate: merge the smaller/contract-defining PR first and rebase the other onto it.

## 8. Tags and Releases

- Tags exist only on `main` commits (or hotfix release commits) and are created by the release process, not ad hoc.
- Nothing in this workflow blocks a release: because `main` is always releasable, cutting a release is tagging the current tip after the checklist in [04. Release Process.md](04.%20Release%20Process.md) §7.

## 9. Repository Hygiene

- Sync with `git pull --ff-only` (set it as default: `git config pull.ff only`) — accidental merge commits from pulling are not allowed.
- Do not commit generated files, local settings, or secrets; `.gitignore` is the authority. If a secret is ever committed, rotate it immediately — removal from history is not sufficient.
- Line endings are governed by `.gitattributes`, not by each developer's `core.autocrlf`: LF in the repository and in the working tree, except `.bat`/`.cmd`/`.ps1`, which keep CRLF. The compose stack volume-mounts sources into Linux containers, where a CRLF script fails at runtime. Do not override this locally.
- Large binaries do not belong in the repo; attachments and test fixtures above ~1 MB need a justification or external storage.
