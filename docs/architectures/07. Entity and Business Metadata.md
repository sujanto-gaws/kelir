# Entity and Business Metadata

**Status:** Draft · **Last updated:** 2026-11-07

This document is the specification for the post-`v1.0.0` platform theme decision **D-124** approved on 2026-10-29: **tenant-defined entities, and the domain and business metadata that stand on them** ([Product Backlog](../../projects/planning/02.%20Product%20Backlog.md) §6.1). # 1. Goals and non-goals

**Goals**

1. An administrator defines a business entity (fields, keys, lines, relations) without a code change or a release, as forms and workflows are defined today (ADR-0006).
2. Forms, lists and lookups bind to entity fields, so one definition drives entry, display and search.
3. Line items have their own row, id and foreign keys. A receipt line can point at the order line it consumes (architectures/06 §3 item 7).
4. Business rules live in metadata: lifecycle states, computed fields and invariants, all in the one JSON Logic engine (ADR-0008).
5. Every record change is audited in the hash chain and published as a domain event through the outbox (ADR-0012, ADR-0041).
6. Definitions are files Kelir Studio can validate offline, through the `kelir-schema` crate (D-123 K1).

**Non-goals**

- **No runtime DDL.** Kelir never creates a table per tenant entity (see §3).
- **No change to JFSS 2.0.1.** It is frozen; bindings go in form `settings`, on ADR-0014's precedent.
- **No ledger, posting or valuation.** Those are the ERP layer's (D-73, ADR-0037). This theme provides the line identity and relations that layer would need.
- **No replacement of core master data.** Party, facility, product and service keep their dedicated tables and explicit endpoints (ADR-0007). They are described to the metamodel, not moved into it.
- **No general-purpose query language.** Queries run over declared, indexed fields only.

Forms, lists, lookups and document types bind to one definition. Every request passes the same tenant and permission check before it touches a row. A write then runs one evaluated path and commits the entity's rows, an audit entry and an event together, or nothing at all. A read is ordinary SQL over the tenant's own tables, built from the definition with every identifier quoted and every value bound; only definitions are cached (§9.3). Revisions form a single line, and each revision is one table shape.

# 3. Where records live

**Decided (D-125, 2026-11-07): option B. Every published `CUSTOM` entity is a physical PostgreSQL table, generated from its EDS document at publish, in a schema that belongs to the tenant.** Lines are child tables with foreign keys. Relations are foreign-key columns or link tables. Unique keys and indexed fields are real unique indexes and btree indexes. Nothing about a record is stored as JSON.

| Option | Line identity | Unique keys and FKs | Compile-time checked (ADR-0002) | Shared-schema tenancy (§1.5) | Ad hoc SQL | Outcome |
| --- | --- | --- | --- | --- | --- | --- |
| A. JSONB on one generic table | No | No | Yes | Yes | No | Rejected |
| B. Physical tables generated at publish | Yes | Yes, native | **No**: the entity module builds SQL at runtime | **No**: a schema per tenant for entity data | Yes | **Decided** |
| C. Hybrid of generic rows and typed index rows | Yes | Through side tables | Yes | Yes | No | Rejected, was recommended |

The product owner chose B for the query experience it gives: any field is filterable, any declared relation is joinable, and a tenant's data is readable by a human or a reporting tool with its own names. §3.4 says what that costs and which standing rules it reverses; §12's D-143 to D-146 are the answers B still owes.

## 3.1 One schema per tenant

- **Platform tables stay where they are**, in `public`, with `tenant_id` on every row, exactly as [Database Schema](../design/02.%20Database%20Schema.md) §1.5 says. Nothing about documents, workflow, audit, outbox or master data moves.
- **Entity data lives in `tenant_<tenant_code>`**, one schema per tenant, created when the tenant is provisioned (`organization::service`, FR-ORG-001) and dropped only when the tenant is hard-deleted, which nothing does today. `tenant_code` is `VARCHAR(64)`, lower-cased and already constrained to `^[a-z][a-z0-9_]*$`-safe characters at provisioning; the schema name is derived from it and nothing else.
- **Two tenants may have different `purchase_order` shapes**, because `tenant_a.purchase_order` and `tenant_b.purchase_order` are different tables. This is the reason the schema is per tenant and not a shared table with a `tenant_id` column: a shared table forces one shape on everyone.
- **Every statement names the schema explicitly.** `search_path` is never set and never relied on; a query that could resolve an unqualified name against the wrong schema is the cross-tenant leak §1.5 exists to prevent, moved one level up.
- **Every entity table still carries `tenant_id`**, constant for the schema, so composite foreign keys to `public` tables keep working: a `reference` field targeting `PARTY` is `FOREIGN KEY (supplier, tenant_id) REFERENCES public.mdm_parties (id, tenant_id)`, which is `0017`'s rule unchanged.

## 3.2 What publish generates

For the example definition in §4.3 (`service_contract`, revision 1, tenant `acme`):


| EDS construct | Generated object |
| --- | --- |
| Entity | `tenant_<code>.<entityKey>` with the platform columns above |
| Field | One column, typed by §4.2's table; `money` is two columns, `_amount` and `_currency` |
| `required` | `NOT NULL` |
| `maxLength`, `min`, `max`, `enum` options | `VARCHAR(n)`, `CHECK` constraints |
| `reference` to a core kind | `UUID` column plus a composite foreign key to the `public` table |
| `reference` to a `CUSTOM` entity | `UUID` column plus a foreign key to that entity's table in the same schema |
| `MANY` relation | Link table `<entityKey>__rel_<relationKey>` (`source_id`, `target_id`, unique on both) |
| Line set | Child table `<entityKey>__<lineSetKey>` with `record_id`, `line_no`, and `source_line_id` when it consumes |
| `uniqueKeys` | Partial unique index `WHERE deleted_at IS NULL` |
| `indexed` | Partial btree index |
| `computed` | An ordinary column, written by the server; never a generated column, because the expression is JSON Logic, not SQL |

**Identifiers come from keys and nothing else.** Every key in EDS already matches `^[a-z][a-z0-9_]*$` and is at most 60 characters (E1). The DDL and every later statement quote every identifier, so a key that is also a SQL reserved word (`order`, `user`) is harmless. A new S-rule, **E8**, bounds the composed names: `entityKey` plus `__` plus the longest `lineSetKey` or `rel_<relationKey>` is at most 63 characters, PostgreSQL's limit; a definition over it is refused at publish naming the pair.

**Column names are field keys, not slot names.** `t01` and the map that explained it are gone; a DBA reading `tenant_acme.service_contract` sees `supplier`. That is the whole reason the product owner chose B, and it is why the design does not abbreviate or hash anything a human would read.

## 3.3 How publish runs the DDL

1. **Validate the document** (E1–E8) and classify the change against the current revision (§7.2). A document that fails never reaches the database.
2. **Dry-run, if the classification needs one.** Additive and index-only changes skip this. For a breaking or destructive change, the generated DDL and the data migration run inside a transaction that is rolled back, and every row that would fail is reported. PostgreSQL DDL is transactional, so the dry run is the real run without the commit; on a large table it costs about what the real run costs, which the builder page says before offering it.
3. **Take an advisory lock** on `(tenant_id, entity_id)` so that two backend processes (NFR-SCA-001) cannot run DDL for one entity at once. A second publish waits or answers 409 `ENTITY_PUBLISH_IN_PROGRESS`.
4. **Run the DDL and bump the revision in one transaction**: `CREATE TABLE` or the `ALTER` statements, then `rad_entities.published_revision = n+1`. The projections `rad_fields` are regenerated in the same transaction. Either everything commits or the previous revision is still current and the schema is untouched.
5. **Indexes that cannot be built in the transaction** (`CREATE INDEX CONCURRENTLY` on a large existing table) are queued as a job after the commit; the field is `indexed` in metadata and the builder shows the index as *building* until the job completes. Filters on it work meanwhile, slowly.
6. **Every process re-reads the published revision on each request** (one indexed row) and refreshes its cached definition when the number moves. A statement is always built from the revision the row says, never from a cache that outlived it.

**Publish is the only path that runs DDL.** No request, no worker and no migration file touches a tenant schema otherwise. `kelir entity ddl --dry-run <tenant> <entityKey>` prints what publish would run, for the operator and for Studio's validate-only write (K5).

## 3.4 What this decision reverses, and what it keeps

| Standing rule | Status under B |
| --- | --- |
| [ADR-0002](adr/0002.%20SQLx%20with%20Compile-Time%20Verified%20Queries.md), every statement compile-time checked | **Superseded in part.** One module, `rad::entity::sql`, builds statements at runtime from the definition and runs them with `sqlx::query()`. Nothing outside that module may. The ADR that carves this out is owed before Step 1 (**D-145**) |
| Database Schema §1.5, one shared schema with `tenant_id` | **Amended.** Platform tables are unchanged; entity data is one schema per tenant. The amendment is the same ADR's second half, or its own (**D-125**'s answer names it) |
| Release process §6, migrations are the schema | **Extended.** The numbered migration sequence still defines every `public` table. Tenant schemas are defined by metadata and regenerated from it, and the three release rehearsals gain a tenant fixture (**D-143**) |
| [ADR-0003](adr/0003.%20PostgreSQL%20as%20the%20Only%20Database.md), one database | Kept. Schemas, not databases |
| [ADR-0028](adr/0028.%20A%20Definition%20Is%20Refused%20at%20Save%20Rather%20Than%20at%20Render.md), refused at save | Kept, with a wider meaning: publish refuses on validation, on the dry run, or on the DDL, and in every case the previous revision stands |
| Coding standard §2.5, one pooled connection per request | Kept; DDL runs on the publish request's own connection |
| Naming convention §4 | **Extended** with the generated-identifier rules of §3.2 |

**What the hybrid gave that B does not, stated plainly:** compile-time checking of the entity module's statements; a schema that is the same in every deployment; a definition change that can never be half-applied to a live table; and a migration that keeps old rows readable in the new shape without rewriting them. §7 and §9 say how each is handled now.

## 3.5 What stays where it is

- **Core master data** keeps `mdm_*`. Party, facility, product, service and document are seeded as `SYSTEM` entities with `table_name` set: described, bindable and searchable, but never generated.
- **Documents** keep `form_data_json`. A document type may bind its form to a custom entity; then its record and lines are written in the submit transaction (§6.4).
- **Audit, outbox, permissions, access rules** are platform tables in `public`, unchanged.

# 4. Entity Definition Schema (EDS)

**Proposed: a fourth schema family, EDS 1.0.0, beside JFSS, JWSS and DTDS.** An entity definition is one JSON document, stored whole in a new `rad_entities.definition_json` column. `rad_entities` and `rad_fields` become projections regenerated on publish, the pattern forms and workflows already follow. The meta-schema and validator ship in `kelir-schema` (K1), so Studio validates offline what the server enforces.

## 4.1 Root properties

| Property | Type | Required | Meaning |
| --- | --- | --- | --- |
| `entityKey` | string | Yes | Immutable key, `^[a-z][a-z0-9_]*$`, max 60 |
| `version` | string | Yes | EDS spec version, `"1.0.0"`; not the definition revision |
| `name`, `description` | string | name: Yes | Display text |
| `kind` | enum | Yes | `CUSTOM` (a generated table in the tenant's schema) or `SYSTEM` (core table, seeded, read-only) |
| `recordCode` | object | No | How the business key is made: a field, or a numbering rule in DTDS §3's template grammar |
| `fields` | array | Yes | Field objects, min 1 |
| `lineSets` | array | No | Named sets of lines, each with its own `fields` (§6) |
| `relations` | array | No | Typed links to records or core objects (§6) |
| `uniqueKeys` | array | No | Named field combinations that must be unique per tenant |
| `computed` | array | No | Fields whose value is a JSON Logic calculation (§8) |
| `invariants` | array | No | JSON Logic conditions every write must satisfy (§8) |
| `lifecycle` | object | No | States and transitions over the `record_status` spine (§8) |
| `governance` | object | No | `DIRECT`, or `GOVERNED` with the document type that approves changes |
| `events` | object | No | Which domain events to emit, and fields excluded from payloads |
| `display` | object | No | Title template and default list columns |

## 4.2 Field types

| `type` | Stored in `data_json` as | Indexable as | Notes |
| --- | --- | --- | --- |
| `string` | string | `value_text` | `maxLength` required, ≤ 2048; `pattern` in the linear-time subset (ADR-0038) |
| `text` | string | No | Unbounded prose |
| `integer` | number | `value_num` | `min`, `max` |
| `decimal` | string, exact | `value_num` | `precision`, `scale`; stored as a string so JSON never rounds it |
| `money` | `{amount, currency}` | `value_num` on amount | Paired amount and currency (architectures/06 §6 change 4) |
| `boolean` | boolean | `value_bool` | — |
| `date`, `datetime` | ISO string | `value_date`, `value_ts` | `datetime` is UTC |
| `enum` | string | `value_text` | `options` with codes and labels |
| `reference` | UUID string | `value_text` | `target`: an entity key or a core kind; checked on write |

Every field also takes `key`, `label`, `required`, `default`, `indexed`, `readOnly`, `sensitive` and `description`. A `sensitive` field is withheld from event payloads (EES §4.2) and from audit values for callers without the entity's read permission (D-12).

## 4.4 Validation at publish (S-rules)

A definition that breaks any rule never reaches `PUBLISHED` (ADR-0028: refused at save, not at render). Proposed rules:

- **E1.** Field, line-set, relation and unique-key keys are unique within their scope.
- **E2.** Every `reference` target names a published entity or a core kind.
- **E3.** Every `var` in `computed` and `invariants` names a declared field or line path.
- **E4.** Computed fields form no cycle and are `readOnly`.
- **E5.** Every operator is in the JFSS Calculation Rule Registry's allowed tier for its use: calculation tier for `computed`, §2.5 conditional tier for `invariants` (ADR-0035).
- **E6.** A `uniqueKeys` field is `required`, and its type is indexable.
- **E7.** A `GOVERNED` entity names a document type that exists.
- **E8.** `entityKey` plus `__` plus the longest `lineSetKey` or `rel_<relationKey>` is at most 63 characters, so every generated identifier fits PostgreSQL's limit.

# 5. Step 1 — Entities, fields and form binding

**Outcome:** an administrator publishes an entity, binds a form to it, and users create, edit and read its records. This makes FR-RAD-001 and FR-RAD-005 true.

## 5.1 Requirements (proposed new SRS section, FR-ENT)

| ID | Requirement | Priority |
| --- | --- | --- |
| FR-ENT-001 | The system shall store an entity definition as an EDS document with draft, published and deprecated revisions | Must |
| FR-ENT-002 | The system shall refuse at publish an entity definition that breaks an EDS S-rule, naming the rule and the path | Must |
| FR-ENT-003 | The system shall describe core master data and documents as `SYSTEM` entities that forms, lists and lookups can bind to | Should |
| FR-ENT-004 | The system shall create, read, update and soft-delete records of a published `CUSTOM` entity | Must |
| FR-ENT-005 | The system shall validate every record write against the definition: types, required fields, bounds, references and unique keys | Must |
| FR-ENT-006 | The system shall bind a form's components to entity fields through form settings, checked at form publish | Must |
| FR-ENT-007 | The system shall audit every definition and record change in the tenant hash chain | Must |

## 5.2 Routes

| Route | Permission | Purpose |
| --- | --- | --- |
| `GET /api/v1/rad/entities` and `/{id}` | `rad:entity:read` | Builder: any status |
| `GET /api/v1/rad/entities/by-key/{entityKey}` | the entity's record read permission | Renderer: published only |
| `POST /api/v1/rad/entities`, `PUT /{id}` | `rad:entity:create`, `rad:entity:update` | Write a draft; `?validateOnly=true` checks without saving (K5) |
| `POST /api/v1/rad/entities/{id}/publish` | `rad:entity:publish` | Draft to published; runs the DDL (§3.3); a published revision is immutable |
| `POST /api/v1/rad/entities/{id}/publish?dryRun=true` | `rad:entity:publish` | The DDL and migration in a rolled-back transaction; reports what would fail |
| `POST /api/v1/rad/entities/{id}/deprecate` | `rad:entity:deprecate` | No new records; existing records stay readable |
| `GET /api/v1/entities/{entityKey}/records` and `/{id}` | record read | List and detail |
| `POST /api/v1/entities/{entityKey}/records` | record create | Create |
| `PUT /api/v1/entities/{entityKey}/records/{id}` | record update | Update, with `If-Match: <row_version>`; a stale version answers 409 |
| `DELETE /api/v1/entities/{entityKey}/records/{id}` | record delete | Soft delete; refused with 409 while another record or document references it |

The `rad:entity:*` rows join the global catalogue. How a record permission is decided for a tenant-defined entity is **D-127** (§12).

## 5.3 Form binding

JFSS 2.0.1 is frozen, so the binding goes in the form's `settings`, as ADR-0014 did for lookups:

```json
"settings": {
  "entityBinding": {
    "entityKey": "service_contract",
    "fields": { "txtTitle": "title", "selSupplier": "supplier", "dtStart": "starts_on", "dtEnd": "ends_on" },
    "lineSets": { "gridItems": "items" }
  }
}
```

**Checked at form publish.** Each mapped component exists and has `role: "data"`. Its type is compatible with the field's (for example `textfield` to `string`, `number` to `integer` or `decimal`, `datagrid` to a line set). Every required entity field is mapped, unless it is computed or has a default. A form that fails is refused with the S10.3 envelope (ADR-0017).

## 5.4 The write path

1. Re-evaluate the submitted payload with the form's own pipeline (JFSS S8.1 and S10.2), so the server's values replace the client's. Map bound components to entity fields, and check types and bounds.
2. Evaluate computed fields, then invariants.
3. Check references, unique keys and line draw-down: a line that consumes part of an upstream line's quantity, such as a receipt line drawing down an order line, may not take more than is left (Step 2).
4. In one transaction, write the record row, its line rows and link rows, the audit entry and the outbox event. Unique keys and references are enforced by the generated constraints as the rows are written.

## 5.5 When a write is refused

**A write commits whole or not at all.** Steps 1 to 3 run before anything is written. Step 4 writes every row inside one transaction, and any failure rolls all of it back: no record, lines, link rows, audit row or event. A record code taken from a gapless numbering rule is allocated after validation, as the document submit does, so a refused write uses no number.

| Failure | Detected in | Answer | What the caller does |
| --- | --- | --- | --- |
| Missing, malformed or out-of-bounds field | Step 1 | 422, every failing field listed | Fix the fields shown |
| Invariant false | Step 2 | 422, the invariant's message and field paths | Fix the values |
| Expression cannot be evaluated (e.g. division by zero) | Step 2 | 422 naming the expression (ADR-0016, ADR-0018) | Fix the data or the definition |
| Dangling or cross-tenant reference | Step 3 | 422 naming the field | Choose another target |
| Unique key taken by a concurrent write | The generated unique index | 422 naming the key, mapped from the constraint name, never a 500 | Change the value |
| Consumption over the upstream quantity | Locked check in Step 3 | 422 naming the line | Reduce the quantity |
| Stale `If-Match` version | Update statement | 409 with the current version | Reload and reapply |
| Delete of a referenced or consumed record | Before delete | 409 naming what holds it | Remove the link first |
| No permission or wrong tenant | Guard, before any read | 403, or 404 where existence must not leak | — |

**Field errors are collected, not stopped at the first.** Steps 1 to 3 gather every failing field into one S10.3 envelope (ADR-0017), so a form can mark them all at once. Errors found by the database (unique keys, versions) arrive one at a time, because only the first one aborts the transaction.

**The browser runs the same expressions before sending**, through the WASM build of the same engine. That gives instant feedback, and the server's answer stays the one that counts.

## 5.6 Acceptance criteria

- [ ] A definition breaking any of E1–E7 is refused at publish with the rule's code and JSON path.
- [ ] Editing a published entity creates revision n+1 as a draft; revision n is unchanged.
- [ ] A record with a missing required field, an over-long string or a dangling reference is refused with 422 naming the field.
- [ ] Two concurrent creates with the same unique-key values: exactly one succeeds; the other gets 422, not 500.
- [ ] A stale `If-Match` update is refused with 409, and the record is unchanged.
- [ ] A record of tenant A cannot be read, referenced or updated from tenant B (a test with a second tenant).
- [ ] Every create, update and delete writes one audit row and one outbox row in the same transaction; a rolled-back write leaves neither.
- [ ] A form bound to a field it does not have, or with a type mismatch, is refused at form publish.

# 6. Step 2 — Relationships and line records

**Outcome:** a line has its own id and survives edits; one line can consume another; records link to records and to core objects with integrity the database enforces.

## 6.1 Relations

| Property | Meaning |
| --- | --- |
| `key`, `label`, `inverseLabel` | Names, both directions |
| `target` | An entity key, or a core kind: `PARTY`, `FACILITY`, `PRODUCT`, `SERVICE`, `DOCUMENT`, `USER` |
| `cardinality` | `ONE` or `MANY` |
| `required` | At least one link on every write |

**A `reference` field is a `ONE` relation.** It is a foreign-key column on the entity table, so a dangling target is refused by the database and a reverse lookup is an indexed read of that column. `MANY` relations are a generated link table, `<entityKey>__rel_<relationKey>`, with a foreign key at each end.

**Deleting a target is refused while it is linked**, never cascaded and never set to null. This follows `0042`'s reasoning for `rad_actions.list_id`: a cascade deletes data nobody asked to delete.

## 6.2 Line sets

**A line set is a repeating group of child rows owned by one record**: an order's items, or a contract's service lines. A line is not a record. It has no lifecycle, permissions, code or relations of its own beyond `source_line_id`. It is read, written, audited and deleted only through its parent, and the parent's permission covers it. What a line has that a JFSS `datagrid` row lacks is its own row and a stable id, so other lines can point at it.

- **Each line gets a UUID v7 id on creation** and keeps it across edits. An update sends existing lines with their `id` and new lines without one.
- **A line left out of an update is deleted**, unless another line consumes it; then the update is refused with 409, naming the consuming record.
- **Bounds:** `minLines`, and `maxLines` capped at a proposed 1,000 per set, so one write stays inside NFR-PERF budgets.
- **Line fields can be `indexed`.** They get a btree index on the line table, and the query grammar can filter a record by a line value through an `EXISTS` on that table (§9.4).

## 6.3 Consumption: one line drawing down another

A line set may declare that it consumes lines of another set:

```json
{ "key": "received", "consumes": { "entityKey": "purchase_order", "lineSet": "items", "quantityField": "quantity" }, "fields": [ ] }
```

The consuming line stores the upstream line in `source_line_id`, a foreign key to the upstream line table. On every write, the platform locks each upstream line (`FOR UPDATE`) and refuses the write if the total consumed would exceed the upstream quantity. This is the primitive behind three-way matching (architectures/06 §5.2). Ledgers and valuation stay with the ERP layer.

## 6.4 Document-backed entities

**Proposed: a document type can bind its form to a `CUSTOM` entity.** DTDS gains an optional `entityKey` in a minor version (1.1.0). While the document is a draft, its lines stay in `form_data_json`, as today; the generated tables hold nothing until submit. **At submit, inside the existing submit transaction**, the record and its lines are written from the server's re-evaluated payload. The record's `created_by_document_id` is set, and `document_relations` keeps the document-level chain. A resubmission after `RETURNED` updates the same record and keeps line ids.

Whether this happens at submit, or waits for the unbuilt `POST` stage, is D-130.

## 6.5 Routes added

| Route | Purpose |
| --- | --- |
| `GET /api/v1/entities/{entityKey}/records/{id}/lines/{lineSetKey}` | Lines of one set, paged |
| `GET` / `POST` / `DELETE …/records/{id}/relations/{relationKey}` | Read, add or remove `MANY` links |
| `GET …/records/{id}/referenced-by` | Reverse links: records and documents that point here |

## 6.6 Acceptance criteria

- [ ] Editing a record keeps every unchanged line's id.
- [ ] Two concurrent consuming writes against one upstream line cannot together exceed its quantity; one is refused with 422.
- [ ] Deleting a record or line that is linked or consumed is refused with 409, naming what holds it.
- [ ] A `MANY` relation to another tenant's record is refused.
- [ ] Submitting a document of a bound type writes its record and lines in the submit transaction; a refused submit writes neither.

# 7. Step 3 — Revisions and data migration

**Outcome:** an entity can change after it holds data, and every record ends up valid against the published revision, or the change is refused. This step is FR-RAD-012 (metadata versioning) for entities, so it brings that `Could` forward (D-131).

## 7.1 How revisions work

- **A published revision is immutable**; a change is revision n+1, a draft, as for forms (ADR-0027) and workflows (JWSS §9).
- **One revision is current** per entity. Writes validate against it.
- **A revision is a table shape.** Every row of `tenant_<code>.<entityKey>` is in the current revision's shape, because the DDL that made the revision current also changed the table. `entity_revision` on the row records the revision it was last written under, for audit; no row is ever read in an older shape.
- **Forms pin the entity revision they were published against.** A form pinned to a non-current revision can still render records whose mapped fields still exist, but cannot save until it is republished against the current revision.

**The revision graph is a single line: no branches, no merges.** An entity has at most one draft at a time, and that draft is always based on the current revision. Publishing a draft whose base is no longer current is refused; the builder rebases it first. Migrations therefore always run from revision n to n+1. A record several revisions behind is migrated through each step in order, never by a jump that skips one. Branching was rejected because a merge between two schema branches would need a migration that nobody wrote and nobody dry-ran.

## 7.2 Change classes

Publishing n+1 compares it to n and classifies every difference:

| Class | Examples | What publish requires |
| --- | --- | --- |
| Additive | New optional field; new line set; new relation; new enum option | `ALTER TABLE … ADD COLUMN` (nullable, no rewrite), `CREATE TABLE` for a line set or link table, a widened `CHECK`. Online, in the publish transaction |
| Widening | Larger `maxLength`; looser `min`/`max`; `required` removed | `ALTER COLUMN TYPE varchar(n)` (metadata-only in PostgreSQL), a replaced `CHECK`, `DROP NOT NULL`. Online |
| Index change | A field becomes `indexed`, or stops being | `CREATE INDEX CONCURRENTLY` as a job after publish, or `DROP INDEX`. Filters work meanwhile, slowly |
| Breaking | Rename; type change; new required field with no default; narrowing; enum option removed; new unique key | A declared migration, a dry run with zero failures, then the run **in a migration window** (§7.4) |
| Destructive | Field or line set removed | A migration that says what happens to the data, explicit confirmation, then `DROP COLUMN` or `DROP TABLE` in the window; the data is exported first (§7.3) |

## 7.3 Migrations

A breaking revision carries `migrations`, ordered operations from revision n:

```json
"migrations": [
  { "from": 3, "ops": [
    { "op": "rename", "field": "vendor", "to": "supplier" },
    { "op": "set", "field": "region", "logic": { "if": [ { "var": "is_export" }, "EXPORT", "DOMESTIC" ] } },
    { "op": "drop", "field": "legacy_note" }
  ] }
]
```

- **Operations:** `rename`, `set` (a value or JSON Logic over the old record), `convert` (type change with an explicit rule), `drop`, `splitLines` and `mergeLines`.
- **Dry run first.** It runs the DDL and the operations in a transaction and rolls back, reporting each row that would fail validation or a constraint against n+1. Publishing is refused while the dry run reports any failure.
- **The run is one transaction per entity**, holding the table's lock for its duration (§7.4). It writes one audit row per changed row. A new `public.ent_migration_runs` table records each run: started, finished, rows, failures, and the DDL it executed, so an operator can read what happened to a tenant's table and when.
- **During the run** the entity is unavailable: reads and writes answer 503 `ENTITY_MIGRATING` with the run's expected end. Every other entity, and every document, is unaffected.
- **No rollback by reverse script.** Before a destructive or breaking run, the dry-run report and a JSON export of the affected columns are kept for the retention period. A run that fails mid-way rolls back whole, because the DDL and the data changes are one transaction; undoing a run that succeeded is a new forward revision.

## 7.4 Publishing a breaking revision: the migration window

**Decided shape under B: a breaking or destructive revision runs as one transaction that holds the entity's table, and the entity is offline for that long.** There is no upcast on read and no dual-read period, because a table has one shape at a time.

| Phase | Writes | Reads | Other entities, documents |
| --- | --- | --- | --- |
| 1. Dry run (r4 still a draft) | Normal, against r3 | Normal | Normal |
| 2. Window opens: publish takes `LOCK TABLE … IN ACCESS EXCLUSIVE MODE` | Blocked; the API answers 503 `ENTITY_MIGRATING` rather than queueing on the lock | Blocked, the same answer | Normal |
| 3. DDL and data operations run, one transaction | — | — | Normal |
| 4. Commit; `published_revision = 4`; lock released | Normal, r4 shape | Normal, r4 shape | Normal |

- **The window's length is the dry run's length**, which the builder page reports before the operator confirms. A tenant with 10,000 contracts sees seconds; one with 10 million sees minutes, and schedules it.
- **A failure anywhere rolls back everything**, DDL included, and r3 is still current. There is no half-migrated table.
- **Forms pinned to r3** keep rendering fields that survived and cannot save until republished against r4 (§7.1).
- **A record several revisions behind** does not exist: every row was rewritten at each revision.
- **Progress** is in `ent_migration_runs` and on the entity's builder page. A window that overruns its estimate by a configured factor alerts `ROLE-ADMIN` holders; it is not cancelled, because cancelling is the rollback and loses the work.

*Under C this section described a batched background rewrite with upcast on read and no outage. That design is not available with real columns, and the product owner accepted the window with D-125.*

## 7.5 Acceptance criteria

- [ ] An additive revision publishes with no job, and old records read unchanged.
- [ ] A breaking revision without migrations is refused at publish, naming each breaking difference.
- [ ] A dry run that would leave one record invalid blocks publish and names that record.
- [ ] A run interrupted by a process restart rolls back whole; the previous revision is current and the table is unchanged.
- [ ] During a window, the entity answers 503 `ENTITY_MIGRATING` and every other entity and every document is unaffected.
- [ ] Every migrated record has an audit row carrying old and new values.

# 8. Step 4 — Business model

**Outcome:** an entity's rules (what is derived, what must hold, which states it moves through, what it announces) are metadata. They run in the engines Kelir already has, with no second evaluator and no private mechanism.

## 8.1 Computed fields

- **Expressions use the calculation tier** of the JFSS Calculation Rule Registry, evaluated by `datalogic-rs` on the server and its WASM build in the browser (ADR-0008).
- **The server's value always wins.** Computed fields are evaluated on every write, before invariants, and stored; a client-sent value is overwritten (JFSS S8.1's tamper-proof rule; ADR-0015's order).
- **Scope is one record and its lines.** Totals across lines are in (`reduce`, `sum`); values across records are not, because they would go stale. Those are queries (Step 5).
- **Division by zero is an evaluation error**, not zero or null (ADR-0018).

## 8.2 Invariants

- **Expressions use the §2.5 conditional tier** and must evaluate to `true` on every write.
- **A failed invariant is a 422** with the invariant's `message` and the field paths its `var`s name, in the S10.3 envelope (ADR-0017).
- **An invariant that cannot be evaluated refuses**, never passes (ADR-0016).
- **Invariants may be scoped to states:** `"inStates": ["ACTIVE"]`. Fields may declare `editableIn` states, so an active contract's price cannot change outside a governed change.

## 8.3 Lifecycle

**Proposed: a small state machine inside EDS, mapped onto the `record_status` spine**, rather than a JWSS workflow per entity:

```json
"lifecycle": {
  "initialState": "DRAFT",
  "states": [
    { "code": "DRAFT", "status": "DRAFT" },
    { "code": "ACTIVE", "status": "ACTIVE" },
    { "code": "ON_HOLD", "status": "SUSPENDED" },
    { "code": "EXPIRED", "status": "INACTIVE" }
  ],
  "transitions": [
    { "action": "ACTIVATE", "from": "DRAFT", "to": "ACTIVE", "condition": { "!!": { "var": "supplier" } } },
    { "action": "HOLD", "from": "ACTIVE", "to": "ON_HOLD", "roles": ["CONTRACT_MANAGER"] },
    { "action": "EXPIRE", "from": ["ACTIVE", "ON_HOLD"], "to": "EXPIRED" }
  ]
}
```

- **Every state maps to a `record_status` value**, as JWSS states map to `documents.status` (JWSS S9). Lists and governance read the spine and never need the entity's own vocabulary.
- **Approval is not re-implemented.** A transition that needs approval goes through the entity's governing document type and the existing workflow engine. The record parks at `PENDING_APPROVAL`, as ADR-0033 already does for master data.
- **Conditions use the JWSS §6.1 context**, with `record` in place of `document`: `record.state`, `record.recordCode`, the field values, and `actor`.
- **Transitions run the hook chain:** `before_record_transition` may veto; `after_record_transition` runs from the outbox. That is new Lifecycle Hook Contract stages, served by core handlers until a hook-registration API is scheduled (D-79).

Whether lifecycle lives in EDS or in a JWSS 1.1 that can drive records is D-129.

## 8.4 Domain events

| Event | Written when | Payload carries |
| --- | --- | --- |
| `Record.Created` | A record is created | `entityKey`, `entityRevision`, `recordId`, `recordCode`, `state` |
| `Record.Updated` | Fields or lines change | The same, plus `changedFields` (keys only) |
| `Record.Transitioned` | The lifecycle moves | The same, plus `action`, `fromState`, `toState` |
| `Record.Deleted` | Soft delete | `entityKey`, `recordId`, `recordCode` |

- **EES gains `RECORD` as an `aggregateType`** in a minor version (1.1.0); `sequence` is monotonic per record.
- **Payloads carry keys, not values, by default** (EES §4.2). An entity may opt specific non-`sensitive` fields into payloads with `events.includeValues`.
- **Every event is written in the same transaction as the change** and delivered by the existing outbox worker, so it can never announce a write that rolled back (ADR-0041).

## 8.5 Delivery and ordering

| Question | Answer | Basis |
| --- | --- | --- |
| Can an event announce a write that rolled back? | No. The event row is written in the write's own transaction | ADR-0041 |
| What if delivery fails after commit? | The write stands. The outbox row is retried: `FAILED`, then retries at 30 s × 2^(n−1) | ADR-0041, outbox §12.8 |
| What if it keeps failing? | The sixth failure makes it `DEAD_LETTER`. The envelope is kept, never discarded, and an administrator can replay it | ADR-0041 |
| What if the worker crashes mid-delivery? | The five-minute lease expires and the row is claimed again | ADR-0041 |
| Delivered how many times? | At least once. Consumers deduplicate on `eventId`, and handlers must be idempotent | EES §1.3, LHCS |
| Ordered per record? | Every event carries `sequence`, monotonic per record | EES §2 |
| Ordered across records, entities or tenants? | No, by design | EES §1.1 |

**The gap: delivery order within one record.** The worker claims rows by `created_at` with `SKIP LOCKED`, across several workers. A retrying `Record.Updated` can therefore be overtaken by a later `Record.Transitioned` for the same record. Today EES puts the burden on consumers: they must order by `sequence` themselves.

**Proposed for `Record.*` events: per-record head-of-line delivery.** The worker does not claim an event while an earlier event for the same record is still pending or failed. A dead-lettered event then holds back later events for that record only, and alerts `ROLE-ADMIN` holders, who replay or skip it. Other records keep flowing. This costs one extra indexed check per claim, and it is D-134.

## 8.6 Acceptance criteria

- [ ] A client-sent value for a computed field is overwritten, and the stored value matches a server-side evaluation.
- [ ] The same computed expression gives identical results in Rust and WASM across the parity corpus, including empty line sets.
- [ ] A write that breaks an invariant is refused with its message and field paths.
- [ ] A transition not declared from the current state is refused with 409; a transition whose condition is false is refused with 422.
- [ ] A governed transition parks the record at `PENDING_APPROVAL`; approval completes it, and refusal restores the previous state.
- [ ] Each committed write produces exactly one event; a rolled-back write produces none; a `sensitive` field's value never appears in a payload.

# 9. Step 5 — Querying over entities

**Outcome:** lists, lookups and the records API filter, sort and page records by declared fields, inside the performance targets, with no SQL assembled from data.

## 9.1 Lists over entities

`rad_lists.entity_id` already exists and nothing uses it. A list bound to an entity is resolved by the same `rad::domain::render` step as a document list (SDD §9.2.4):

- **Column keys** resolve to an entity field, a line-set aggregate (`items.count`), a `recordCode`, `state` or a base column. An unknown key is refused by name, never shown as an empty table.
- **Filter keys may be any declared field.** The builder flags a filter on a field that is not `indexed` before save, and §9.3's tier 2 reports the ones that cost.
- **Sorting** is `ORDER BY` a quoted column name from the definition, through `ident()` (§9.2); a key the definition does not hold is refused by name.

## 9.2 The read path

**Reads are ordinary SQL over the tenant's generated tables, built by `rad::entity::sql` from the definition.** There is no cache and no separate read model.

| Read | How it is resolved |
| --- | --- |
| Record detail | One row of `tenant_<code>.<entityKey>` by `id`; its lines by `record_id` from each line table, paged when a set is large |
| List or records API | 1. The guard resolves tenant and permission. 2. Each filter becomes a predicate on a real column, with the value bound. 3. Keyset paging on the sort column. 4. The declared columns are selected by name |
| Lookup options | The same statement, with the lookup's `filter` added and `label` and `value` projected |
| Reverse links | The foreign-key column, or the link table, by target id |

**Permission is a predicate in the statement, not a filter after it.** A list never fetches rows the caller cannot see and then drops them, so paging and counts are honest (SDD §8.4's visibility rule).

**How the statement is built, and why it is safe.** `rad::entity::sql` is the one module allowed to assemble SQL from data (§3.4). Its rules, which **D-144**'s mutation campaign must prove:

- Every identifier passes through one function, `ident()`, which accepts only a key that exists in the published definition and returns it double-quoted. A key that is not in the definition is a 422 naming it, never a string in the statement.
- Every value is a bound parameter. The builder has no code path that formats a value into SQL text.
- The schema name is derived from the caller's tenant inside the module and cannot be supplied by a request.
- The permission predicate (§10.2) is appended by the module from the caller's roles; a request cannot omit or alter it.
- The statement shapes are enumerable: detail, list, lookup, reverse-link, exists-in-lines, and the writes. Each has a golden test per shape, and the campaign mutates each rule above and expects a red test.

## 9.3 Read scaling plan

Scaling reads under B is the ordinary PostgreSQL story, because the data is ordinary tables.

| Tier | What | Ships | Trigger |
| --- | --- | --- | --- |
| 0 | **Definition cache.** Published revisions are immutable, so each worker caches them in memory by `(tenant_id, entity_id, revision)`; only the current-revision pointer is re-read, one indexed row per request | Step 1 | Always on |
| 1 | **Declared indexes.** `indexed` fields get a btree; unique keys get a unique index. An unindexed filter is allowed and counted (§9.4) | Step 1 | Always on |
| 2 | **Index advice.** The builder page shows, per entity, the filters the last 30 days ran without an index, from `pg_stat_statements`, so the author adds `indexed` where it matters | Step 5 | A list misses its P95 |
| 3 | **Asynchronous aggregates** kept by an outbox consumer, labelled *as of* | With the first aggregate endpoint | An aggregate is asked for |
| 4 | **A reporting role** granted `SELECT` on a tenant's schema, for analysts and BI tools, on a read replica when one exists | When asked | Analysts need live SQL |

*Under C this section had a bounded-projection tier and ruled out an external cache; neither is needed now. A tenant's schema is already the wide table with real names.*

## 9.4 The query grammar

`GET /api/v1/entities/{entityKey}/records` takes a small grammar that the builder turns into one statement:

| Parameter | Example | Rule |
| --- | --- | --- |
| `filter[<field>][<op>]` | `filter[ends_on][lt]=2026-12-31` | `op` in `eq`, `ne`, `lt`, `lte`, `gt`, `gte`, `in`, `prefix`, `isNull`; any declared field; value bound as a typed parameter |
| `filter[<lineSet>.<field>][<op>]` | `filter[items.quantity][gt]=50` | A line field: an `EXISTS` on the line table |
| `state` | `state=ACTIVE` | Lifecycle state or `record_status` |
| `related[<relation>]` | `related[supplier]=<uuid>` | Records linked to one target |
| `sort` | `sort=-ends_on` | Any declared field or platform column |
| `cursor`, `limit` | `limit=50` | Keyset paging; `limit` ≤ 100, as `ck_rad_lists_page_size` |

More than one filter is an AND. **A filter on a field that is not `indexed` is allowed**, logged with the entity and field, and surfaced by tier 2; it is not refused, which is the first visible difference from C. There is still no OR, no free-text across fields, and no join to another entity in one call: those are saved queries (§9.5) and global search (FR-SRH-004).

## 9.5 Lookups and reports

- **`rad_lookup_definitions` gets its first reader for `source_type = ENTITY`.** The permission is the entity's record read permission, never a lookup permission of its own (SDD §9.2.1, ADR-0011).
- **Dashboards stay purpose-built endpoints** (ADR-0039). Aggregation over entities is a later endpoint, not a general query language.
- **Saved queries** (a later item): a named, declared join over declared relations, compiled by the platform at save into one of the enumerable statement shapes, the way OFBiz's view-entities work. Not in Steps 1–5.

## 9.6 Lookup binding, exactly

A lookup over an entity is a `rad_lookup_definitions` row with `source_type = ENTITY`. Its `source_config_json` names exactly what to read:

```json
{
  "lookupKey": "active_service_contracts",
  "sourceType": "ENTITY",
  "sourceConfig": {
    "entityKey": "service_contract",
    "value": "id",
    "label": ["recordCode", "title"],
    "search": ["recordCode", "title"],
    "filter": { "state": "ACTIVE" },
    "sort": "-starts_on"
  }
}
```

- **A form uses it** by mapping a component id to the `lookupKey` in its settings, as ADR-0014 does for master-data lookups.
- **Checked when the lookup is saved:** the entity is published in the tenant; `value` is `id` or a unique-key field; every `search`, `filter`, `sort` and `label` field exists. A `search` field that is not `indexed` is accepted with a warning.
- **Resolved at request time** by `GET /api/v1/rad/lookups/{lookupKey}/options?q=…`. That runs the list statement above, with `q` as a prefix match over the `search` fields.
- **Permission is the entity's record read permission.** A lookup has no permission of its own (ADR-0011).
- **On save of a record that uses it**, the chosen value is checked again against the same lookup, so a stale or forged id is refused.

## 9.7 Performance targets (proposed)

| Measure | Target |
| --- | --- |
| List, one indexed filter, 100,000 records per entity per tenant, 50 concurrent users | P95 ≤ 1 s, NFR-PERF-001's list figure |
| Record detail with up to 1,000 lines | P95 ≤ 2 s |
| Create or update with 200 lines | P95 ≤ 1.5 s |

The 100,000-record volume is a proposal; NFR-PERF-001 is set at 10,000 documents.

## 9.8 Acceptance criteria

- [ ] A filter on a field the definition does not declare is refused with 422 naming the field; a filter on a declared, unindexed field is accepted and logged.
- [ ] A list column naming an unknown field is refused by name at render.
- [ ] Keyset paging returns every record exactly once while records are inserted between pages.
- [ ] A lookup over an entity returns nothing to a caller without the entity's read permission.
- [ ] The load test meets the targets above on the release stack.

# 10. Cross-cutting rules

| Concern | Rule |
| --- | --- |
| Tenancy | Entity data is one PostgreSQL schema per tenant (§3.1); every statement names the schema from the caller's tenant and never relies on `search_path`. Every generated table still carries `tenant_id`, so foreign keys to `public` tables are composite `(id, tenant_id)` and a cross-tenant link is refused by the database (`0017`). |
| Permissions | Definition admin uses the global `rad:entity:*` rows. Record access needs a decision (D-127): the proposal is generic `entity:record:read`, `create`, `update`, `delete` rows, **plus** per-entity role grants, row scope and field rules in the entity's `access` rules, held outside the revisioned definition; both are required (§10.3). |
| Audit | `audit::domain::ObjectType` gains `ENTITY_DEFINITION` and `ENTITY_RECORD`. It is a closed enum, so the compiler forces each into `readable_by`. A record's audit values are withheld from callers who lack its read permission (D-12). |
| Sensitive data | `sensitive` fields are withheld from events, and from audit values for callers without read access. |
| Strings and bounds | Every `string` field has `maxLength`; the service checks it before PostgreSQL does, so an over-long value is a 422, not a 500 (§1.3.1). |
| Patterns | Field `pattern`s use the linear-time subset only (ADR-0038). |
| Business codes | A record's `recordCode` is never released after deletion, as for party codes (ADR-0013). |
| One evaluator | Computed fields, invariants, lifecycle conditions and migration `set` logic all run on `rad::evaluator` (ADR-0008). |
| Connections | No request holds more than one pooled connection (coding standard §2.5); publish runs its DDL on the request's own connection, and concurrent index builds run on the worker. |
| Migrations | Each step's `public` schema migration is forward-only and N−1 compatible (release process §6). Tenant schemas are generated from metadata and never appear in a migration file; the three release rehearsals run against a fixture with two tenants and three published entities each (**D-143**). |
| Generated SQL | Only `rad::entity::sql` builds statements from data; every identifier goes through `ident()`, every value is bound, and the module's rules are held by a mutation campaign (§9.2, **D-144**). |
| Kelir Studio | The EDS meta-schema, the S-rule validator and the change classifier live in `kelir-schema`, so Studio checks a definition's shape offline (K1). Whether the DDL applies to a given database is only known by the server's dry run, which the validate-only write (K5) runs. |
| API stability | The records API and EDS come under the API stability policy K6 publishes. |

## 10.1 Tenancy at each level

**The tenant always comes from the caller's token, never from the request body or path.**

| Level | How it is enforced |
| --- | --- |
| Entity definition | `rad_entities.tenant_id`; `entityKey` is unique per tenant. `SYSTEM` entities are seeded into each tenant when it is provisioned, and the tenant's schema is created then |
| Form, list, lookup binding | Resolved by key within the binding's own tenant. Publish refuses a key that tenant does not have |
| Records, lines, relations | In `tenant_<code>`; foreign keys between them stay inside the schema, and foreign keys to `public` are composite `(id, tenant_id)` |
| Indexes and unique keys | Per table, so per tenant by construction |
| Queries | The schema name is the tenant; `tenant_id` is still a predicate on every `public` join |
| Audit and events | Hash chain per tenant; every envelope carries `tenantId` |

## 10.2 Authorization at each action

| Action | Requires |
| --- | --- |
| Draft, publish or deprecate a definition | `rad:entity:create`, `update`, `publish` or `deprecate` |
| Read a definition in the builder | `rad:entity:read` |
| Read records (detail, list, lookup, reverse links) | `entity:record:read` **and** a role in the entity's `access.read` |
| Create, update or delete a record | The matching `entity:record:*` **and** a role in `access.write` |
| Fire a lifecycle transition | Record update rights **and** a role the transition lists, if it lists any |
| See audit values of a record | `audit:read` **and** the record read rights (D-12) |
| Receive event values | None: payloads carry keys only, and never `sensitive` values |

`access.read` and `access.write` above mean the entity's access rules, defined below. Until D-127 is taken, this whole section is the proposal, not the rule.

## 10.3 Where roles come from

- **Roles are the tenant's existing roles** (`roles`, tenant-scoped since D-18), managed on the Roles screen. An entity never defines a role; its access rules name role codes, as JWSS assignment rules do.
- **Access rules live outside the revisioned definition**, in a new `ent_entity_access` table edited under a new `rad:entity:access` permission. Revisions describe the data's shape; access describes who may use it. If the two were coupled, granting a role would mean publishing a schema revision and republishing every bound form.
- **An access change takes effect at once**, needs no migration, and is audited as a change to the entity definition.

```json
{
  "entityKey": "service_contract",
  "grants": [
    { "role": "CONTRACT_MANAGER", "read": "ALL", "write": "ALL", "delete": true },
    { "role": "PROCUREMENT", "read": "ALL", "write": "OWN" },
    { "role": "REQUESTER", "read": "DEPARTMENT" }
  ],
  "fields": [
    { "field": "total", "read": ["CONTRACT_MANAGER", "PROCUREMENT"] },
    { "field": "supplier", "write": ["CONTRACT_MANAGER"] }
  ]
}
```

## 10.4 Row scope

Each grant scopes the rows a role reaches: `ALL`; `OWN`, meaning records the caller created; or `DEPARTMENT`, meaning records whose creator is in the caller's department. A caller holding several roles gets the widest scope among them. The scope is a predicate in the statement, like every other permission (§9.2).

## 10.5 Field-level access

| Rule | Effect on reads | Effect on writes |
| --- | --- | --- |
| No `read` role | The field is left out of detail, list columns, lookup labels and audit values. A filter or sort on it answers 403 | The caller cannot send it; it is kept as stored |
| `read` but no `write` role | Shown, and rendered read-only | A changed value answers 422 `FIELD_NOT_WRITABLE`; an unchanged or omitted value is accepted |
| No field rule | Entity-level grants apply | Entity-level grants apply |

- **The renderer receives the caller's field access with the form**, hides or disables accordingly, and the server enforces it regardless.
- **Computed fields can leak hidden inputs.** If a readable computed field depends on a hidden field, saving the access rules warns the author, naming both fields.
- **Events never carry values by default**, so field rules need no extra handling there.

## 10.6 Permissions and revisions

**Access is always checked against the current access rules, never against the revision a record is pinned to.** A role that can read the entity can read its r2, r3 and r4 records alike. They are all returned in the current shape (§7.4). A field rule naming a field the new revision drops is listed at publish and removed in the same change, so no rule ever points at nothing.

- **Money and FX:** `money` pairs amount and currency, but no rate table exists. Is conversion ever in scope here, or only for an ERP layer?
