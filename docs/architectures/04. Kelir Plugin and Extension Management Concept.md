# Kelir Plugin and Extension Management Concept

**Status:** Adopted · **Last updated:** 2026-08-12

For **Kelir**, additional features should be managed through a controlled **Plugin / Extension Management Architecture**.

The main idea is:

> The Kelir core remains stable, while additional business features, integrations, UI components, workflow behaviors, document types, reports, and connectors can be added through plugins or extensions.

This allows Kelir to become a flexible platform without modifying the core framework every time a new business requirement appears.

---

# 1. Core Concept

Kelir should distinguish between:

```text
Core Modules
Official Modules
Configurable Extensions
Code-Based Plugins
External Plugin Services
```

---

## 1.1 Core Modules

Core modules are always available and maintained by the framework team.

Examples:

```text
Authentication
Users
Roles
Documents
Workflow
Attachments
Comments
Audit
Master Data
RAD Engine
Integration Core
```

---

## 1.2 Configurable Extensions

Configurable extensions do not require custom code.

Examples:

```text
New document type
New form
New list
New workflow
New master data field
New report widget
New notification template
New menu item
```

This should be the first mechanism used in Kelir because it is safe and easy to maintain.

---

## 1.3 Code-Based Plugins

Code-based plugins add behavior using backend or frontend code.

Examples:

```text
ERP connector
E-signature connector
Custom approval rule
Custom workflow service task
Custom dashboard widget
Custom document tab
Custom report generator
Custom authentication provider
Custom storage driver
Custom notification channel
```

---

## 1.4 External Plugin Services

For isolated or third-party plugins, Kelir can support external services.

Example:

```text
Kelir Core
    ↓
Plugin API / Webhook / Message Queue
    ↓
External Plugin Service
```

This is safer for untrusted or independently deployed plugins.

---

### Module Name

```text

```

- Restrict plugin access to database, file, HTTP, secrets
- Audit permission usage

### Permission Examples

```text

plugin:write-documents
plugin:read-master-data

plugin:read-storage
plugin:write-storage
plugin:read-secrets

```

Plugin manifests request core permissions (e.g. `document:read`) for what the plugin does to platform data, while the `plugin:*` permissions above govern the plugin runtime itself.

Important rule:

> Plugins must run with limited permissions. They should not automatically have full access to Kelir core.


### Event Hooks

The hooks below are the ones most plugins use. The complete per-stage catalogue, the `before_*` / `after_*` execution contract, and the hook registry tables are defined in document 01 §12; plugin-registered handlers are merged into that same ordered chain.

```text
before_document_create
after_document_create
before_document_submit
after_document_submit
before_document_approve
after_document_approve
before_workflow_transition
after_workflow_transition
after_task_completed
after_attachment_uploaded
after_comment_created
after_master_data_updated
```

Login/session reactions are not lifecycle hooks (the catalogue is document-scoped); plugins react to logins by subscribing to the corresponding platform event (e.g. `Security.*` / user login events) via `plugin_events`.

Example:

```text

```

# 6. Plugin Manifest

Every plugin should have a manifest file.

Recommended file:

```text
plugin.json
```

Example:

```json
{
  "pluginId": "contract-management",
  "name": "Contract Management",
  "version": "1.0.0",
  "publisher": "Kelir Official",
  "category": "FEATURE",
  "description": "Adds contract lifecycle management capabilities.",
  "kelirVersion": ">=1.0.0",
  "entrypoints": {
    "backend": "backend/contract_management",
    "frontend": "frontend/contract-management.js"
  },
  "permissions": [
    "document:read",
    "document:write",
    "attachment:read",
    "attachment:write",
    "workflow:task:execute",
    "notification:send"
  ],
  "extensionPoints": [
    "document-tab",
    "dashboard-widget",
    "workflow-handler",
    "report"
  ],
  "settingsSchema": {
    "contract_retention_years": {
      "type": "number",
      "default": 7,
      "required": true
    },
    "enable_contract_renewal_reminder": {
      "type": "boolean",
      "default": true
    }
  },
  "dependencies": [
    {
      "pluginId": "document-core",
      "version": ">=1.0.0"
    },
    {
      "pluginId": "workflow-core",
      "version": ">=1.0.0"
    }
  ],
  "assets": {
    "icon": "assets/icon.svg",
    "logo": "assets/logo.svg"
  },
  "checksum": "sha256:...",
  "signature": "..."
}
```

In the v1 strategy the `backend` entrypoint is a reference to a compiled-in Rust crate (see §14 Phase 2 and §15 Option 1); from Phase 3 onward it may point to a `.wasm` artifact loaded at runtime instead.

The normative manifest format is the [Plugin Manifest Schema (PMS)](../schema/Plugin%20Manifest%20Schema.md) specification; the example above is illustrative and predates it (PMS adds the required `manifestVersion` field plus `hooks`, `events`, and `migrations` declarations, and extends `settingsSchema` with `enum`/`secret` types).

Entries in `dependencies` may reference other plugins or core capability modules such as `document-core` and `workflow-core`, which are addressable as built-in pseudo-plugins.

# 8. Plugin Lifecycle Flow

## 8.1 Installation Flow

```text
Admin uploads or selects plugin
        ↓
Kelir validates manifest
        ↓
Kelir checks compatibility
        ↓
Kelir checks signature/checksum
        ↓
Kelir checks required permissions
        ↓
Admin approves installation
        ↓
Plugin files are stored
        ↓
Plugin migrations are executed
        ↓
Plugin is registered
        ↓
Plugin is disabled by default
```

---

## 8.2 Enable Flow

```text
Admin enables plugin
        ↓
Kelir loads plugin backend extension
        ↓
Kelir loads plugin frontend assets
        ↓
Kelir registers extension points
        ↓
Kelir applies plugin settings
        ↓
Plugin becomes active
        ↓
Activity/audit log recorded
```

---

## 8.3 Upgrade Flow

```text
New plugin version available
        ↓
Kelir validates compatibility
        ↓
Backup plugin settings and migration state
        ↓
Admin approves upgrade
        ↓
New plugin package installed
        ↓
Plugin migrations executed
        ↓
Frontend assets replaced
        ↓
Plugin restarted/reloaded
        ↓
Upgrade result logged
```

---

## 8.4 Uninstall Flow

```text
Admin requests uninstall
        ↓
Kelir checks dependencies
        ↓
Kelir warns about data removal
        ↓
Plugin disabled
        ↓
Plugin routes removed
        ↓
Plugin UI removed
        ↓
Optional cleanup of plugin data
        ↓
Plugin package removed or archived
        ↓
Audit log recorded
```

# 13. Plugin Security Model

Kelir must enforce strict plugin security.

## Security Rules

### Rule 1

Plugins must declare permissions in manifest.

```json
"permissions": [
  "document:read",
  "notification:send"
]
```

---

### Rule 2

Plugins must not access core database tables directly unless permitted.

Use plugin-scoped tables or core APIs.

---

### Rule 3

Plugins must not read secrets unless explicitly granted.

Example:

```text
integration-secret:read
```

---

### Rule 4

Plugins must be versioned and signed.

```text
plugin version
checksum
publisher signature
```

---

### Rule 5

Plugins must be auditable.

Every plugin action should be logged.

---

### Rule 6

Plugins must fail safely.

If a plugin fails, Kelir core should continue running.

---

# 14. Recommended Technical Strategy

For Kelir, plugin support should be implemented in phases.

---

## Phase 1: Configuration-Based Extensions

No custom code.

Support:

```text
Document types
Forms
Lists
Workflows
Menus
Master data fields
Notification templates
Reports from configuration
```

This is safest and fastest.

---

## Phase 2: First-Party Compiled Plugins

Plugins are developed as Rust crates and Vue packages, then compiled with Kelir.

Advantages:

- Stable
- Type-safe
- Easier to debug
- Secure
- No dynamic loading risk

Disadvantages:

- Requires deployment to add plugin

Recommended for early Kelir versions.

---

## Phase 3: Managed Dynamic Plugins

Support controlled dynamic plugins.

Backend options:

```text
WASM plugins using Wasmtime
External plugin services via REST/gRPC
Sidecar plugin processes
```

Frontend options:

```text
Dynamic ESM import
Module federation
Remote components
Iframe sandbox
```

Recommended for third-party extension ecosystem.

---

## Phase 4: Plugin Marketplace

Support:

```text
Plugin catalog
Publisher profile
Version management
Rating and review
License management
Paid plugins, optional
Automatic updates
```

This is for future platform maturity.

---

# 15. Backend Plugin Technology Options

For Rust backend, there are several possible plugin mechanisms.

---

## Option 1: Compiled-In Modules

Plugin is a Rust crate included during build.

Pros:

- Stable
- Secure
- Fast
- Easy integration

Cons:

- Requires rebuild/redeploy

Recommended for version 1.

---

## Option 2: WASM Plugins

Use:

```text
Wasmtime
Wasmer
```

Pros:

- Sandbox
- Portable
- Safer than dynamic shared libraries

Cons:

- More complex
- Plugin API must be defined carefully
- Some Rust ecosystem limitations

Recommended for future third-party plugins.

---

## Option 3: Dynamic Shared Libraries

Use:

```text
libloading
.so / .dll / .dylib
```

Pros:

- Native performance
- Direct Rust integration possible

Cons:

- Risky
- Version compatibility difficult
- Can crash core process
- Security concerns

Not recommended unless plugins are fully trusted.

---

## Option 4: External Plugin Services

Plugin runs as separate service.

Kelir communicates using:

```text
REST
gRPC
Message queue
Webhook
```

Pros:

- Isolated
- Independent deployment
- Language flexible
- Safer for third-party plugins

Cons:

- More infrastructure
- Network latency
- Operational complexity

Recommended for large enterprise or third-party integration plugins.

---

# 16. Frontend Plugin Technology Options

## Option 1: Compiled-With App

Plugin components are included in frontend build.

Pros:

- Simple
- Fast
- Stable

Cons:

- Requires frontend rebuild

Recommended for version 1.

---

## Option 2: Dynamic ESM Import

Frontend loads plugin JavaScript module at runtime.

Pros:

- More flexible
- No full rebuild for some plugin updates

Cons:

- Versioning and caching must be handled
- Security must be controlled

---

## Option 3: Module Federation

Use Vite module federation or similar.

Pros:

- Good for micro-frontend style plugins
- Independent deployment possible

Cons:

- More complex
- Requires discipline

## Option 4: Iframe Sandbox

# 21. Recommended Kelir Plugin Strategy

For the first version of Kelir, the recommended approach is:

```text
Start with configuration-based extensions.
Then support compiled-in official plugins.
Later introduce WASM or external plugin services for third-party plugins.
```

Recommended roadmap:

```text
Phase 1:
  RAD configuration
  Document type builder
  Form builder
  Workflow builder
  Menu builder

Phase 2:
  Plugin registry
  Plugin manifest
  Plugin settings
  Plugin permissions
  Plugin audit

Phase 3:
  Compiled backend plugin modules
  Compiled frontend plugin components

Phase 4:
  WASM plugins or external plugin services
  Module federation frontend plugins
  Plugin marketplace
```

# 22. Final Concept

Kelir should manage plugins and extensions through a dedicated plugin platform.

The core system should remain stable:

```text
Kelir Core
```

Additional features should be added through:

```text
Configurable Extensions
Official Plugins
Third-Party Plugins
External Plugin Services
```

With this architecture, Kelir can grow into a flexible business application platform where new capabilities such as contract management, fleet management, ERP integration, e-signature, WhatsApp notification, custom reports, and industry-specific features can be added without changing the core framework.
