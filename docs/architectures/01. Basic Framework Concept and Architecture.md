# Basic Framework Concept and Architecture  
## Rapid Application Development Platform for Document-Based Business Applications

**Status:** Adopted · **Last updated:** 2026-08-13

This document defines the **basic concept and architecture** before starting code implementation.

The goal is to create a **full-stack rapid application development framework** for building document-based business applications where:

- Business documents are the main transactional objects.
- Workflow and document routing are handled by a workflow engine.
- Master data such as employee, customer, supplier, facility, product, and service are managed separately but can be updated through controlled document workflows.
- Backend uses **Rust**.
- Frontend uses **Vue + Vite + Axios + shadcn-vue + Tailwind CSS v4**.
- Database uses **PostgreSQL**, with optional compatibility for **MariaDB**.

---

# 1. Framework Objective

The framework should allow developers to rapidly build business applications such as:

- Purchase requisition
- Invoice approval
- Vendor registration
- Employee onboarding
- Contract approval
- Asset request
- Permit / license processing
- General document approval systems

The framework should support:

1. Dynamic form creation
2. Document type configuration
3. Workflow definition
4. Task inbox and approvals
5. Attachments
6. Comments
7. Activity logs
8. Audit trail
9. Master data management
10. User and role management
11. Dashboard and reporting

# 2. Framework Name

The framework is named **Kelir**. This name is used consistently across all documentation, the monorepo (`kelir/`), and the backend and frontend repositories (`kelir-backend/`, `kelir-frontend/`).

Concept:

> A metadata-driven, document-centric, workflow-enabled full-stack framework for building enterprise business applications rapidly.

# 3. Core Architecture Principles

## 3.1 Modular Monolith First

Start with a **modular monolith** instead of microservices.

Reason:

- Faster development
- Easier debugging
- Simpler deployment
- Easier transaction consistency
- Can evolve into services later if needed

Backend modules:

```text
Auth
Identity
Organization
Master Data
Document Management
Workflow Engine
Attachment
Comment
Activity / Audit
Notification
Reporting
System Configuration
```

---

## 3.2 Metadata-Driven Rapid Development

The framework should not hardcode every business form.

Instead, use metadata to define:

```text
Entity
Form
List
Document Type
Workflow
Permission
Attachment Requirement
```

Example:

```text
Document Type = Purchase Requisition
Form Schema = Purchase Requisition Form
Workflow = Standard Purchase Approval
Numbering = PR-{year}-{sequence}
Required Attachments = Quotation if amount > 10,000,000
```

This allows administrators or developers to create new business applications quickly.

---

## 3.3 Document + Workflow Separation

The system must separate:

```text
Document Data
Workflow Process
Master Data
Audit Data
```

High-level flow:

```text
User creates document
        ↓
Document saved
        ↓
Workflow engine starts process
        ↓
Tasks created
        ↓
Approvers act
        ↓
Document status changes
        ↓
Activity and audit recorded
        ↓
Final result posted to business module or master data
```

---

## 3.4 API-First Design

Backend exposes REST JSON APIs.

Frontend consumes APIs using Axios.

Use OpenAPI specification to generate frontend types if possible.

```text
Rust Backend → OpenAPI JSON → Frontend TypeScript Types
```

## 5.3 Database

Primary recommendation:

```text
PostgreSQL
```

Reasons:

- Better JSON support with JSONB
- Better full-text search
- Better indexing
- Row-level security support
- Better fit for document metadata and audit logs
- Strong integrity features

MariaDB can be supported, but for the first version, PostgreSQL is safer.

If MariaDB is required:

- Use SQLx MySQL dialect
- Avoid PostgreSQL-specific features
- Avoid heavy dependency on JSONB operators
- Use JSON column type carefully
- Test migrations in both databases if needed

# 12. Document Lifecycle

Every document in Kelir travels the same lifecycle regardless of its document type or workflow shape. The workflow definition decides *which* approval states exist and *who* acts; the lifecycle defines the *fixed spine* the platform guarantees: create, edit, validate, submit, route, decide, complete, archive.

Each lifecycle stage exposes **hooks** — named extension points where core modules, document type configuration, workflow definitions, and plugins can inject behavior without modifying framework code. This is what makes the framework extensible without forking: business-specific rules (budget checks, ERP posting, contract registration) attach to hooks instead of being hardcoded in the document module.

The lifecycle and the workflow engine are complementary, not alternatives. Transition-scoped rules are authored inside the workflow definition and resolve into the same hook chain (§12.4.2), but the lifecycle extends before a workflow instance exists (draft editing, validation, workflow selection) and after it has completed (archive, purge), so the hook chain — not the flow — is the hosting mechanism.

Related documents:

- Platform status enum and document module responsibilities: document 02 §3.12.
- Plugin hook subscription, priority, and sandboxing: document 04 §4.6.
- Normative JSON shapes (registration entry, invocation payload, result): the [Lifecycle Hook Contract](../schema/Lifecycle%20Hook%20Contract.md) specification.
- Workflow definition format embedding transition guards/actions: the [JSON Workflow Schema](../schema/JSON%20Workflow%20Schema.md) specification.
- Event naming (`Document.Submitted`) and hook naming rules: naming convention §7.

## 12.1 Lifecycle Stages

```text
        CREATE
          ↓
    ┌── DRAFT ────────────────┐
    │     ↓ EDIT / VALIDATE   │
    │     ↓                   │
    │  SUBMIT                 │ CANCEL
    │     ↓                   │
    │  SUBMITTED              │
    │     ↓ ROUTE             │
    │  IN_REVIEW              │
    │     ↓                   │
    │  PENDING_APPROVAL ──────┤
    │     ↓ DECIDE            │
    │  ┌──┴───────┬─────────┐ │
    │  ↓          ↓         ↓ │
    │ APPROVED  RETURNED  REJECTED
    │  ↓          │           │
    │ POST        └→ back to DRAFT (RESUBMIT)
    │  ↓
    │ COMPLETED
    │  ↓ ARCHIVE
    └→ ARCHIVED → (retention) → PURGED
```

Stage definitions:

| Stage | Meaning | Resulting status |
|---|---|---|
| Create | Document instance created from a document type; form data may be empty | `DRAFT` |
| Edit | Owner revises draft form data, metadata, attachments | `DRAFT` |
| Validate | Form schema, cross-field, and attachment rules evaluated | unchanged |
| Submit | Owner releases the document for processing; numbering assigned | `SUBMITTED` |
| Route | Workflow definition selected, process instance started, first task created | `IN_REVIEW` / `PENDING_APPROVAL` |
| Decide | Approver approves, rejects, or returns a task | `APPROVED` / `REJECTED` / `RETURNED` |
| Post | Approved result written to the business module or master data | `COMPLETED` |
| Archive | Document closed for editing and moved to archive storage | `ARCHIVED` |
| Cancel | Owner or admin abandons the document before completion | `CANCELLED` |
| Purge | Retention period expired; payload removed, audit record retained | — |

`documents.status` is the fixed platform enum defined in document 02 §3.12 (`DRAFT`, `SUBMITTED`, `IN_REVIEW`, `PENDING_APPROVAL`, `APPROVED`, `REJECTED`, `RETURNED`, `COMPLETED`, `ARCHIVED`, `CANCELLED`). Workflow states such as `MANAGER_APPROVAL` map onto these statuses; hooks are defined against **lifecycle stages**, not against workflow states, so a hook written once works for every document type.

## 12.2 Hook Model

Two hook kinds, with different guarantees:

| Kind | Runs | Transaction | Can veto | Can mutate payload | Failure impact |
|---|---|---|---|---|---|
| `before_*` | Synchronously, before the state change is written | Inside the caller's transaction | Yes | Yes | Aborts the action, transaction rolled back |
| `after_*` | Asynchronously, after commit, via the outbox worker (§20) | Own transaction | No | No | Logged and retried; business data unaffected |

Design rule:

> A `before_*` hook is part of the business rule. An `after_*` hook is a reaction. Never put a reaction in a `before_*` hook — a slow integration call must not be able to block or roll back a user's submission.

### Naming Rule

- Paired hooks use the **base verb**: `before_document_submit` / `after_document_submit`.
- After-only hooks use the **past tense**: `after_task_completed`, `after_attachment_uploaded`.

This matches the hook names already registered by the plugin hook module (document 04 §4.6).

### Hook Result

A `before_*` handler returns one of:

```text
CONTINUE          proceed unchanged
MODIFY            proceed with the returned payload
REJECT            abort with an error code and message
```

Rejection surfaces as the standard error response (§17):

```json
{
  "success": false,
  "error": {
    "code": "HOOK_REJECTED",
    "message": "Budget exceeded for cost center CC-4400",
    "details": [
      {
        "field": "amount",
        "message": "Remaining budget is 8,500,000"
      }
    ]
  }
}
```

### Hook Invocation Payload

```json
{
  "hookName": "before_document_submit",
  "stage": "SUBMIT",
  "tenantId": "TNT-001",
  "documentId": "DOC-2026-000123",
```

## 12.3 Hooks per Lifecycle Stage

The full catalogue. Every row is a stage; `before` hooks may veto, `after` hooks emit the listed event.

### Creation and Editing

| Stage | Before hook | After hook | Event | Typical use |
|---|---|---|---|---|
| Create | `before_document_create` | `after_document_create` | `Document.Created` | Default field values, copy from template, deny creation outside period |

### Submission and Routing

| Stage | Before hook | After hook | Event | Typical use |
|---|---|---|---|---|
| Submit | `before_document_submit` | `after_document_submit` | `Document.Submitted` | Mandatory attachment check, budget availability, freeze form data |

## 12.4 Hook Registration

Hooks are registered from four sources, resolved into one ordered chain per hook name:

```text
Core module handlers        built into Kelir, always first
Document type configuration declarative rules from RAD metadata
Workflow definition         transition guards and actions (§12.4.2)
Plugin handlers             registered through the plugin manifest (document 04)
```

There is **one execution mechanism and four authoring surfaces**. A rule that belongs to a specific approval step is written in the workflow definition next to that step; a rule that applies to a document type regardless of workflow is written in the document type configuration; a rule shipped by a plugin is declared in the manifest. All of them resolve into the same ordered chain, obey the same `CONTINUE` / `MODIFY` / `REJECT` contract, and are recorded in the same execution log.

### 12.4.1 Document Type Registration

```json
{
  "documentTypeKey": "purchase_requisition",
  "hooks": [
    {
      "hook": "before_document_submit",
      "handler": "core:require_attachment",
      "priority": 100,
      "config": {
        "category": "QUOTATION",
        "requiredIf": "amount > 10000000"
      }
    },
    {
      "hook": "before_document_approve",
      "handler": "core:check_approval_limit",
      "priority": 200
    },
    {
      "hook": "after_document_complete",
      "handler": "plugin:erp-connector:post_purchase_requisition",
      "priority": 500,
      "isEnabled": true
    }
  ]
}
```

### 12.4.2 Workflow Definition Registration

Stages that occur **while a process instance is running** can be authored directly in the workflow definition, as transition-level `guards` and `actions`, instead of registering a globally-scoped hook:

```json
{
  "from": "MANAGER_APPROVAL",
  "to": "FINANCE_APPROVAL",
  "action": "APPROVE",
  "by": "ROLE:MANAGER",
  "guards": [
    {
      "handler": "core:check_approval_limit",
      "priority": 300,
      "config": { "limitField": "amount" }
    }
  ],
  "actions": [
    {
      "handler": "plugin:erp-connector:reserve_budget",
      "priority": 320
    }
  ]
}
```

Resolution:

```text
guards   → merged into the before_workflow_transition chain at their declared priority,
           scoped to this transition only
actions  → merged into the after_workflow_transition chain at their declared priority,
           scoped to this transition only
```

The same handler may be registered from more than one source at different scopes. `core:check_approval_limit` registered on the document type (§12.4.1) guards every approval of that document type; registered on a transition it guards only that step. The handler code is identical — only the registration scope differs.

Scope rule:

> A workflow-declared handler runs **only** for the transition that declares it, in the workflow definition version the process instance was started with. Registry-declared hooks (core, document type, plugin) run for every transition of every document type they match.

This is why the workflow definition cannot be the *only* hosting mechanism. Guards and actions exist only where a transition exists, which is why the following stages are registry-only:

| Stage group | Why it cannot live in the flow |
|---|---|
| Create, update, validate, attachment, comment, version | Fire while the document is `DRAFT`; no process instance exists yet, and none of them are state changes a transition could model |
| Numbering, workflow selection | `before_workflow_select` decides *which* definition applies — a guard inside a definition cannot make that decision |
| Archive, purge | Fire after the process instance has completed, often years later under a retention timer |
| Cross-cutting and plugin rules | Must be registered once for all document types; a plugin cannot rewrite a tenant's workflow definitions on install |

### 12.4.3 Priority Bands

To keep the merged chain deterministic across sources, priorities are banded:

```text
0   – 99     core platform handlers
100 – 299    document type configuration
300 – 499    workflow definition guards / actions
500 +        plugin handlers
```

Lower runs first. Within a band, ties are resolved by registration order. The bands are a convention that keeps merged chains predictable, not a hard constraint — an entry registered outside its source's band is accepted with a warning.

### 12.4.4 Storage

Supporting tables (added to the core table groups in §9.1):

```text
document_lifecycle_hooks
document_hook_executions
```

```text
document_lifecycle_hooks
----------------------------------------
hook_id
tenant_id
document_type_id        nullable = applies to all document types
hook_name
handler_reference       core:… | plugin:<pluginId>:<handler>
priority
config_json
is_enabled
created_at
updated_at
```

```text
document_hook_executions
----------------------------------------
execution_id
tenant_id
source                  CORE | DOCUMENT_TYPE | WORKFLOW | PLUGIN
hook_id                 null when source = WORKFLOW
workflow_transition_ref null unless source = WORKFLOW
document_id
hook_name
handler_reference
result                  CONTINUE | MODIFY | REJECT | ERROR
duration_ms
error_message
executed_at
```

Where each source is stored:

| Source | Stored in | Resolved |
|---|---|---|
| Core | compiled into the backend | at startup |
| Document type | `document_lifecycle_hooks` | per document type |
| Workflow definition | `workflow_definitions.definition_json` (the `guards` / `actions` on each transition) | per transition, from the instance's definition version |
| Plugin | `plugin_hooks` (document 04 §9.7) | on plugin enable |

Workflow-declared handlers are deliberately **not** rows in `document_lifecycle_hooks` — they belong to the workflow definition and must version with it. The resolver reads all four sources and produces one ordered chain; every handler it runs, whatever the source, is recorded in `document_hook_executions`.

## 12.5 Hook Execution Rules

```text
Ordering            ascending priority within the bands of §12.4.3; ties by registration order
Scoping             workflow-declared guards/actions run only for their own transition;
                    registry-declared hooks run for every matching document type
Definition version  a running instance uses the workflow definition version it started with,
                    so editing a definition never changes guards mid-flight
Before hooks        synchronous, inside the caller's transaction
After hooks         published to the outbox in the same transaction, executed by the worker
Timeout             before hooks have a per-hook budget (default 2s) and a total budget (default 5s)
Timeout result      treated as REJECT for before hooks, as retryable failure for after hooks
Idempotency         after hooks must be idempotent; delivery is at-least-once
Isolation           a plugin hook panic or error must never abort a core transaction it did not veto
Circuit breaker     a handler failing N consecutive times is disabled and reported to admins
Permissions         handlers execute with the registering plugin's permissions (document 04 §4.5)
Status changes      hooks must not write documents.status directly; status changes go through the workflow engine
Recursion           hook-initiated actions carry a depth counter; exceeding the limit aborts the chain
Logging             every execution recorded in document_hook_executions and the activity log
```

Retry policy for `after_*` hooks follows the outbox worker retry schedule (§20).

## 12.6 Lifecycle Trace Example

Purchase requisition above the high-value threshold:

```text
POST /documents                       → before_document_create → after_document_create
PUT  /documents/{id}                  → before_document_update → after_document_update
POST /documents/{id}/attachments      → before_attachment_upload → after_attachment_uploaded
POST /documents/{id}/submit
        before_document_validate      → JFSS + cross-field rules
        before_document_submit        → quotation attachment required (amount > 10,000,000)
        before_document_number_assign → PR-2026-000123
        before_workflow_select        → purchase_requisition_high_value
        commit
        after_document_submit         → Document.Submitted
        after_workflow_start          → Workflow.Started
        after_task_assigned           → notify manager
POST /tasks/{id}/approve
        before_workflow_transition    → guard from the workflow definition (MANAGER_APPROVAL
                                        → FINANCE_APPROVAL): core:check_approval_limit
        before_document_approve       → registry hook, runs for every approval of this type
        commit
        after_workflow_transition     → action from the workflow definition:
                                        plugin:erp-connector:reserve_budget
        after_document_approve        → Document.Approved
        after_task_completed          → SLA recorded
        after_task_assigned           → notify finance approver
POST /tasks/{id}/approve
        before_document_approve
        before_document_post          → ERP connection check
        commit
        after_document_post           → ERP purchase requisition created
        after_document_complete       → PDF generated, requester notified
```

The second step shows both authoring surfaces in one chain: the transition-scoped guard declared in the workflow definition and the document-type-scoped hook from the registry, executed in priority order by the same mechanism.

`GET /lifecycle/hooks` returns the catalogue of available hook names with their stage, kind, and payload schema, so the admin UI and plugin developers can discover extension points without reading source code.


## 16.3 Master Data APIs

Generic pattern:


> **Suppliers, customers and employees do not follow this shape.** They are role views over the Party model, not entities of their own ([Database Schema](../design/02.%20Database%20Schema.md) §14 deviation #1), so only the `GET` collection exists: a supplier is created by `POST /master-data/parties` and an assignment of the SUPPLIER role. For stricter architecture, use explicit endpoints:

```text
GET    /suppliers
POST   /suppliers
GET    /suppliers/{id}
PUT    /suppliers/{id}

GET    /customers
GET    /employees
GET    /facilities
GET    /products
GET    /services
```

For RAD framework, generic endpoints are useful, but explicit typed endpoints are safer for long-term systems.

Recommended hybrid:

```text
Core master data uses explicit endpoints.
Configurable RAD entities can use generic endpoints.
```

**Decision:** the six core master data entities (suppliers, customers, employees, facilities, products, services) use explicit endpoints (matching document 02 §3.9); the generic pattern remains available for configurable RAD entities.

# 18. Authentication and Authorization Architecture

## 18.1 Authentication

Recommended:

```text
JWT access token + refresh token
```

Alternative:

```text
HTTP-only session cookie
```

For SPA, JWT with short-lived access token and rotating refresh token is common.

Access token payload:

```json
{
  "sub": "user.john",
  "tenant_id": "TNT-001",
  "roles": ["ROLE-PROC-STAFF"],
  "exp": 1760000000
}
```

---

## 18.2 Authorization

Use RBAC first.

```text
User → Role → Permission
```

Permission format:

```text
module:resource:action
```

The `resource` segment may be omitted when a module manages a single resource, giving the shorter form `module:action` (e.g. `document:create`).

Examples:

```text
document:create
document:read
document:update
document:submit
document:approve
attachment:upload
attachment:delete
master-data:supplier:create
master-data:supplier:update
workflow:definition:manage
audit:read
```

Later extend to ABAC:

```text
department scope
facility scope
document owner
security level
```

# 29. Key Architectural Decisions

## Decision 1

Use **Axum** as Rust web framework.

Reason:

- Modern
- Async
- Tower middleware ecosystem
- Good for REST APIs

---

## Decision 2

Use **SQLx** as database access layer.

Reason:

- Supports PostgreSQL and MySQL/MariaDB
- Async
- Strong query safety
- Good migration support

---

## Decision 3

Use **PostgreSQL** as primary database.

Reason:

- JSONB
- Better search
- Better indexing
- Better for audit and document metadata

MariaDB support can be added later with compatibility layer.

---

## Decision 4

Use **modular monolith** backend.

Reason:

- Faster to build
- Easier to maintain
- Can evolve into services later

---

## Decision 5

Use **lightweight internal workflow engine** first.

Reason:

- Simpler
- Fits RAD concept
- Avoids external Java dependency early

Later can integrate Camunda or Flowable if full BPMN is required.

---

## Decision 6

Use **metadata-driven forms and lists** for rapid application development.

Reason:

- New business applications can be created faster
- Admin can configure document types
- UI can render forms dynamically
- Workflow can be attached to document type

---

```text
  ├── shadcn-vue
  ├── Tailwind CSS v4
  ├── Dynamic form renderer
  ├── Dynamic list renderer
  ├── Document workspace
  └── Workflow task inbox
```

The main system flow:

```text
User logs in
        ↓
User selects document type
        ↓
User fills dynamic form
        ↓
User uploads attachments
        ↓
User submits document
        ↓
Workflow engine starts process
        ↓
Approvers receive tasks
        ↓
Approvers approve / reject / return
        ↓
Document status changes
        ↓
Activity and audit logs recorded
        ↓
Final document completed or archived
```

This architecture provides a solid foundation for building a **rapid, document-based, workflow-driven business application platform** using Rust and Vue.
