# ADR-0002 — SQLx with Compile-Time Verified Queries

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-04 (founding) · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** [ADR-0001](0001.%20Rust%20and%20Axum%20for%20the%20Backend.md), [ADR-0003](0003.%20PostgreSQL%20as%20the%20Only%20Database.md), [ADR-0016](0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md)

## 1. Context

**Recorded retrospectively on 2026-09-01** from [architectures/01](../01.%20Basic%20Framework%20Concept%20and%20Architecture.md) §29 Decision 2, with the constraint half from [Validation Rule Registry](../../schema/JFSS%20Validation%20Rule%20Registry.md) §2.5 as `D-11` made it concrete. The operative statements remain there (standard §9).

The backend is Rust ([ADR-0001](0001.%20Rust%20and%20Axum%20for%20the%20Backend.md)) and every module reaches the same database: identity, master data, documents, workflow, audit. The founding pass had to choose how Rust talks to it — and, later, what that choice obliges of a data-integrity validation rule whose table is named by tenant-authored metadata rather than by code.

## 2. Decision

**Kelir accesses the database through SQLx, writing SQL directly, with queries verified at compile time.** `sqlx::query!` and its siblings are the normal shape; migrations are SQLx migrations, applied in numbered order.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. SQLx with compile-time verified SQL** | Async, database-supported, query safety, migrations | **Chosen** |
| B. Queries assembled at run time from metadata | What a `unique` or `exists` rule naming its own table would need | Rejected — `sqlx::query!` cannot take a runtime table name, and the safety property is the reason to use SQLx at all |

### A. SQLx — chosen

Chosen for supporting PostgreSQL (and, at the time, MySQL/MariaDB), for being async, for query safety, and for migration support (architectures/01 §29). The founding record names no rejected library, and this retrofit does not invent one.

### B. Run-time query assembly

Rejected where it surfaced, in the Validation Rule Registry: `unique` and `exists` are `server`-scoped rules that name a table to check against. Taking that name from a form definition at run time would mean building SQL from tenant-authored metadata — which forfeits compile-time verification and opens an injection surface. The registry instead specifies an **allow-list** shape, and §2.5 states why in as many words: compile-time-verified queries are required, and `query!` cannot take a runtime table name.

## 4. Consequences

**Positive** — a query that does not match the schema fails the build rather than a request. The `.sqlx` offline cache makes that true in CI and in the release image build (`SQLX_OFFLINE=true`).

**Negative** — the schema must be reachable (or the cache current) to compile, so a schema change is a two-step change: migration, then `cargo sqlx prepare`. Dynamic queries are deliberately awkward, which is why lookups and validation rules are allow-listed rather than free-form. A request must hold at most one pooled connection at a time ([coding standard](../../standards/01.%20Coding%20Standard.md) §2.5) — the rule `D-35` was reopened by when a gap-tolerant numbering allocation opened a second transaction inside a submit's.

**Neutral** — migrations are files with numbers, and a merged migration is never edited; a correction is a new migration (`D-20`, `D-21`).

## 5. Compliance

CI compiles the backend against the committed `.sqlx` cache; a query that drifted from the schema breaks the build. The one-connection rule is checked at review and, for the numbering path, by `concurrent_submits_of_a_gap_tolerant_type_do_not_exhaust_the_pool`.

## 6. Revisit When

A surface genuinely requires run-time table selection that an allow-list cannot express — the point at which the injection question has to be answered rather than avoided — or SQLx stops supporting a database Kelir has to serve.
