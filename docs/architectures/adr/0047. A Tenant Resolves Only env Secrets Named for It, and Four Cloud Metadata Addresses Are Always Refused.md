**Neither change answers a force that moved. In both, the first analysis was wrong or incomplete**, and this record says so:

- **The allow-list on secret names weighed the deployment, not the tenant.** ADR-0043 §O resolved `env://NAME` when `NAME` began with `KELIR_INTEGRATION_SECRET_`. That kept Kelir's own settings out. But multi-tenant mode runs ([ADR-0010](0010.%20Multi-Tenant%20Mode%20Runs%20and%20Roles%20Are%20Tenant-Scoped.md)), so every tenant's secrets share one process environment, and §O did not weigh that. [Record 20](../../../projects/verifications/20.%20Sprint%2021%20Independent%20Pass.md)'s Finding 1 (P1, [#618](https://github.com/sujanto-gaws/kelir/issues/618)) shows the cost:
  - A tenant was created through `POST /organization/tenants`.
  - Its administrator granted their own `ROLE-ADMIN` `integration:credential:create`. Provisioning withholds that permission, but withholding it is not a boundary.
  - They named the system tenant's variable, and their collector received the system tenant's token.
- **A tenant code is not a variable name.** `tenants.tenant_code` is `[A-Za-z0-9_-]{2,64}`, stored in upper case. It may hold `-`, which no environment variable name may hold, so a code cannot be used in a name as it stands. It may also hold `_`, and `__`. A tenant's code cannot be changed after creation. A code identical to a deleted tenant's is still refused by the unique index, so a later tenant reaches a deleted tenant's namespace only through a different code that maps like it or overlaps it.
- **Nothing released used #547's names.** `v0.8.0` has no resolver, and `v0.9.0` was tagged at Sprint 22's close. A rename was free before the tag and breaking after it ([construction plan 18](../../../projects/planning/18.%20Sprint%2022%20Phase%209%20Close%20Construction%20Plan.md) §8).
- **ADR-0043 named one metadata address.** Its §1 names *"the cloud metadata address `169.254.169.254`"*, and §2 refused it as link-local. Record 20's Finding 5 (P4, [#622](https://github.com/sujanto-gaws/kelir/issues/622)) reached three more:
  - `100.100.100.200` (Alibaba Cloud ECS), in CGNAT, which ADR-0043's option F allows as public;
  - `192.0.0.192` (Oracle Cloud Infrastructure Compute Classic), in `192.0.0.0/24`, also public;
  - `fd00:ec2::254` (AWS's metadata service over IPv6), which is unique-local, so `fd00::/8`, the Installation guide's own example, opens it.

  The first two needed only a registered `baseUrl`. On those clouds, a test call's preview would be the metadata service's answer.

FR-INT-002 and NFR-SEC-004 bind as they did in ADR-0043: a resolved secret leaves the process only for the system it belongs to, and a test call must not reach what the deployment cannot see.

## 2. Decision

**Kelir resolves an `env://` reference only when its name is in the caller's tenant's own namespace, `KELIR_INTEGRATION_SECRET_<CODE>__<NAME>`, and in no other live tenant's, in every deployment. Tenant creation refuses a code whose namespace overlaps a live tenant's (§2.1). Kelir's egress guard always refuses four cloud metadata addresses: `169.254.169.254` as link-local, and three more as addresses of their own, checked before every range, every listed CIDR and every test seam.**

- **The namespace.**
  - `<CODE>` is the caller's `tenants.tenant_code` in upper case, with each `-` written as `_`.
  - `__` separates `<CODE>` from `<NAME>`, because a code may hold `_`.
  - `<NAME>` is one or more of `A–Z 0–9 _`.
  - The match is exact and case-sensitive. So `SYSTEM` reads `KELIR_INTEGRATION_SECRET_SYSTEM__ERP_TOKEN`, and `TNT-001` reads `KELIR_INTEGRATION_SECRET_TNT_001__ERP_TOKEN`.
- **The code comes from the database, by the caller's `tenant_id`, and never from the request, the token or the reference.** One read per call takes every live tenant's id and code, before the environment is read.
- **Three gates, in order, all before the environment is read**:
  1. The `KELIR_INTEGRATION_SECRET_` prefix, with something after it. This gate is ADR-0043's.
  2. The caller's own namespace.
  3. **No other live tenant's namespace also spells the name.** Codes `A-B` and `A_B` both map to `A_B`, and every `ACME__X` name is also spelled as an `ACME` name. Such a name belongs to nobody, so it is refused for every tenant it matches: **ambiguity fails closed**.
- **Any refusal is `SECRET_NAME_NOT_PERMITTED`**, and it names only the caller's own prefix. The variable is not read, so another tenant's variable answers the same bytes whether it is set or not. `SECRET_NOT_FOUND` answers a name that is in the caller's namespace but is unset or empty. Only a name inside the caller's own namespace can reach it.
- **Live means not deleted, whatever its status.** An `INACTIVE` or `SUSPENDED` tenant's code still blocks, and a soft-deleted tenant's does not. A caller whose own tenant is not live resolves nothing. That can happen only in a race, because [ADR-0045](0045.%20Every%20Authenticated%20Request%20Reads%20That%20Its%20Tenant%20and%20User%20Are%20Not%20Deleted,%20and%20a%20Token%20Has%20No%20Leeway.md) refuses a deleted tenant's token first.
- **A single-tenant deployment follows the same rule, with its one tenant's code** (#618's A1). #547's bare `KELIR_INTEGRATION_SECRET_<NAME>` names no tenant and resolves nowhere.
- **The operator's contract changes, and the change is a breaking rename.**
  - Every variable a test call reads is named for its tenant. Each `KELIR_INTEGRATION_SECRET_<NAME>` that #547 allowed becomes `KELIR_INTEGRATION_SECRET_<CODE>__<NAME>`, and its stored `env://` reference has to be edited to match.
  - **No migration rewrites a reference**: a reference is the operator's text, and Kelir cannot tell whose secret a bare name was meant to be.
  - **Saving is unchanged**: the registry accepts any `env://NAME` of the right shape, and the rule is applied only when a call would read the name.
- **The always-refused metadata addresses.**
  - `100.100.100.200`, `192.0.0.192` and `fd00:ec2::254` are refused as *a cloud metadata address*. The two IPv4 addresses are refused in their IPv4-mapped and IPv4-compatible spellings too.
  - They are checked before any range is consulted. So no entry in `KELIR_INTEGRATION_ALLOWED_CIDRS` opens one, not even the address's own `/32` or `/128` host route, and neither does the test seam `integration_allow_loopback`.
  - A refusal offers no setting, and it names the class, not the address.
  - `169.254.169.254` is still refused as link-local, under ADR-0043.
- **They are addresses, not ranges.** The addresses beside them keep their class. CGNAT and `192.0.0.0/24` stay public, and the rest of `fd00:ec2::/32` stays unique-local, which a listed range opens.

**What this record replaces in ADR-0043**:
- §2's headline as amended, and its `env://` bullet;
- the bullet *"Always refused, with them: three cloud metadata addresses"*;
- §O's amendment of 2026-10-01;
- the lines of §4 and §6 that rest on those.

**What ADR-0043 keeps**:
- the call runs in the request (A);
- `env://` resolves and `vault://` fails by name (C);
- the prefix is the first gate, and the allow-list is checked before the environment is read (§O's first paragraph);
- the resolved address is checked, the connection is pinned to it, and no redirect is followed (F);
- every address class other than the three, the IPv4-mapped and IPv4-compatible reading, and **D-103**'s five translated forms;
- the two credential types (J), the client (L), redaction (R) and masking (V).

**Left open:** where a `vault://` path's tenancy comes from. That is decided with the Vault client ([#605](https://github.com/sujanto-gaws/kelir/issues/605)).

### 2.1 A Tenant Code Whose Namespace Overlaps a Live Tenant's Is Refused at Creation

**Kelir refuses, at tenant creation, a code whose secret prefix overlaps a live tenant's** (**D-102** B, product owner, 2026-10-01; [#655](https://github.com/sujanto-gaws/kelir/issues/655)). A code's prefix is `KELIR_INTEGRATION_SECRET_<SEG>__`, `__` included, where `<SEG>` is the code in upper case with each `-` written as `_`. **Two prefixes overlap when they are equal, or when one starts with the other.**

- **This is gate 3's condition, and nothing else.** Two prefixes overlap exactly when some name is spelled in both namespaces:
  - A name spelled in both starts with both prefixes, so the longer prefix starts with the shorter.
  - Conversely, what lies between a shorter prefix and a longer one is only `A–Z 0–9 _`, so any name under the longer prefix is also under the shorter.

  So creation refuses exactly the pairs whose shared names §2's gate 3 refuses for both.
- **The whole prefix is compared**, so overlap covers more than codes that map alike or are joined by `__`.
  - Refused:
    - `A_B` beside `A-B`;
    - `ACME__X` beside `ACME`, in either order;
    - `ACME_` or `ACME-` beside `ACME`, since `…ACME___` starts with `…ACME__`;
    - `EF--G` beside `EF`;
    - `SYSTEM__X`, because the system tenant is live.
  - Not refused: `ACME_X`, `ACMEX`, `ACME2` or `XACME` beside `ACME`, because one underscore is not the separator. Nor is `LONG__Y` beside `LONG__X`.
- **No code is exempt.** Every code validation admits maps to a legal variable name, and the comparison never asks which variables are set.

**The refusal.** `POST /api/v1/organization/tenants` answers **422 `VALIDATION_ERROR`** with one detail: `path` `tenantCode`, `rule` `secretNamespace`, `code` `SECRET_NAMESPACE_IN_USE`.
- `SECRET_NAMESPACE_IN_USE` is the detail's code, not the top-level `error.code`.
- The detail names no other tenant's code. The caller can list tenants anyway, and the refusal has no need to say which tenant it is.
- **A code identical to an existing tenant's, live or deleted, is still 409 `CONFLICT`**, from the unique index. The comparison skips an identical live code, so the 409 keeps its meaning.

**Live means not deleted, whatever its status**, as in §2. A suspended or inactive tenant's code blocks, and a deleted tenant's does not.

**The check is serialised.** Every creation first takes one deployment-wide advisory lock (`pg_advisory_xact_lock`), then reads the live codes and inserts in the same transaction. Of two racing creations, the second either reads the first's committed code or waits for it. Deleting a tenant does not take the lock: a delete can only free a prefix, and never makes a passing check fail.

**Creation is the only route.** A tenant's code cannot be changed after creation, so no other API route needs the check. **Restoring a deleted tenant in SQL, by clearing `deleted_at`, bypasses it**: the restored tenant can overlap a live one created since, and the two then fail closed for the names they share.

**Gate 3 stays.** It still covers pairs that existed before the refusal, which are not repaired. `CHANGELOG.md`'s `[Unreleased]` upgrade note gives the SQL that lists every live pair whose prefixes overlap. A pair that maps alike can be separated only by deleting the tenant created by mistake.

**The stated limit, and the operator's duty** (**D-102** B; [#690](https://github.com/sujanto-gaws/kelir/issues/690)):

- **A deleted tenant's variables stay in the environment until the operator removes them, and a later tenant whose prefix overlaps the deleted one's reads them.**
  - A code that maps alike reads all of them: `A_B`, created after `A-B` is deleted, reads every variable `A-B` had.
  - A code that covers the deleted one's, or is covered by it, reads the names the two share. `ACME__X`, created after `ACME` is deleted, reads `ACME`'s `KELIR_INTEGRATION_SECRET_ACME__X__…` variables. `ACME`, created after `ACME__X` is deleted, reads every variable `ACME__X` had.
- **When a tenant is deleted, the operator must remove every variable under its `KELIR_INTEGRATION_SECRET_<CODE>__` prefix and restart the backend.** That duty covers every case above ([Installation and Deployment](../../operations/01.%20Installation%20and%20Deployment.md) §7.1). Nothing checks it, and renaming variables cannot separate two codes that map alike.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. A namespace per tenant, with A1** | `KELIR_INTEGRATION_SECRET_<CODE>__<NAME>`, ambiguity failing closed, the same rule with one tenant | **Chosen** (product owner, 2026-09-30, #618's option A with A1) |
| B. The #547 prefix alone | ADR-0043 §O as adopted on 2026-09-29 | Rejected — every tenant resolves every tenant's variable (record 20, P1) |
| C. Option A without A1 | A single-tenant deployment keeps #547's bare names | Not taken by the product owner; no reason recorded |
| D. Withhold the permission across tenants | A created tenant cannot attach a credential, so it cannot name a variable | Rejected — a tenant's administrator grants `integration:credential:create` to their own role (ADR-0043 §Q, as added 2026-10-01) |
| **E. Four metadata addresses, three of them exact and checked first** | `169.254.169.254` by its class; `100.100.100.200`, `192.0.0.192`, `fd00:ec2::254` by address, before any range or list | **Chosen** (#642, merged by the product owner on 2026-10-01 with the extension stated in its body) |
| F. The link-local address only | ADR-0043 §2 as adopted | Rejected — record 20's P4 reached the other three |
| G. Refuse the ranges they sit in | `fd00:ec2::/32`, and CGNAT or `192.0.0.0/24` with it | Not taken by #642 — it refuses addresses nobody documents as metadata, two of them in ranges ADR-0043's F allows |
| **H. Refuse an overlapping code at creation, against live tenants** | The whole prefix compared, gate 3's own condition, under one lock (§2.1) | **Chosen** (product owner, 2026-10-01, **D-102** B) |
| I. Refuse against live and deleted tenants | No later code reads a deleted tenant's variables | Rejected by the product owner — chosen first, then changed to B; no reason recorded |
| J. No refusal | Both consequences stated as limits | Rejected by the product owner |

### A. A namespace per tenant, with A1 — chosen

The variable's name says whose it is, and that is the only thing the process environment can say. The caller's code is read from the database by `tenant_id`, so nothing a caller sends chooses the namespace. Failing closed on ambiguity means no tenant reads a name another live tenant could also claim, and the cost falls on the two tenants that overlap rather than on a third party. With A1 there is one rule for every deployment, so a deployment that adds its second tenant has nothing to rename. **What it does not solve**:
- What an operator puts under a tenant's prefix is still theirs to get right.
- A pair whose prefixes overlap and that existed before §2.1's refusal loses the names it shares, and nothing repairs it.
- A deleted tenant's leftover variables are read by a later tenant whose prefix overlaps it (§2.1).

### B. The #547 prefix alone

It kept Kelir's own settings out, which is all ADR-0043 weighed. Across tenants it guards nothing: record 20's P1 was sent the system tenant's token by a tenant created through the API. It is the decision this record replaces.

### C. Option A without A1

A single-tenant deployment would have kept `KELIR_INTEGRATION_SECRET_<NAME>`, with no rename for the deployments most likely to be using the resolver. The product owner chose A1 and recorded no reason. **Read here, not decided**: a single-tenant deployment would have one rule and a multi-tenant one another, so adding a tenant would mean renaming every variable the first tenant had.

### D. Withhold the permission across tenants

Provisioning already withholds `integration:credential:create` from a created tenant's `ROLE-ADMIN`. That administrator also holds `identity:role:update` and can grant it to their own role, which is what P1 did. A guard the guarded party can lift is not a guard, so the check has to turn on the tenant and not on the permission.

### E. Four metadata addresses, three of them exact and checked first — chosen

Each address is its provider's own documented address, and refusing it by address leaves its range's class untouched. CGNAT stays the carrier network ADR-0043 allows, `192.0.0.0/24` stays public, and the rest of `fd00:ec2::/32` stays unique-local, opened by a listed range like any other. Because the three are checked before any range, no allow-list entry and no test seam can open them, in any spelling a URL host can take. **What it does not solve**: a provider's metadata address that is not on the list is judged by its range. So is anything else AWS puts in `fd00:ec2::/32` once a deployment lists `fd00::/8`.

### F. The link-local address only

`169.254.169.254` serves AWS, Azure, GCP and present-day Oracle, and the link-local class refuses it without naming it. On Alibaba Cloud, on Oracle Compute Classic, and over IPv6 on AWS, the metadata service sat outside that class and was reached.

### G. Refuse the ranges they sit in

Refusing `fd00:ec2::/32` whole would close whatever else AWS serves there. Refusing CGNAT or `192.0.0.0/24` whole would refuse carrier and special-purpose addresses that ADR-0043's F allows as public, and that no provider documents as metadata. #642 refused the addresses and recorded no further reason. ADR-0043 §6's trigger kept refusing the prefix as the remedy if something beside `fd00:ec2::254` answers; §6 below carries that trigger now.

### H. Refuse an overlapping code at creation, against live tenants — chosen

The tenant that would overlap is told at creation, and the existing tenant's secrets never go silent. **Comparing the whole prefix makes creation and resolution one rule**, so creation refuses no pair that resolution would let share a name, and no pair that resolution would not. One deployment-wide lock makes the read and the insert one step against other creations, which the unique index cannot do, because the codes differ. Tenant creation is a rare administrative act, so the lock costs nothing anybody will measure. A deleted tenant's code does not block an overlapping code, so overlapping prefixes stay usable. **What it does not solve**:
- a later overlapping tenant reads a deleted tenant's leftover variables (§2.1);
- pairs that already overlap are not repaired;
- a tenant restored in SQL is not checked.

### I. Refuse against live and deleted tenants

It closes the read of a deleted tenant's leftover variables. It was the recommendation, and the product owner chose it first and then changed to B in the next message. No reason was recorded. Its cost, read here: every code that overlaps a deleted tenant's could never be used.

### J. No refusal

Both consequences would have stayed stated limits. Two live tenants that overlap would keep failing closed for the names they share, and nothing would tell either administrator why.

## 4. Consequences

**Positive**

- One tenant cannot resolve another's secret by naming it, whoever holds which permission. A foreign variable answers the same whether it is set or not.
- The variable's name says whose it is, so an operator can see each tenant's secrets in the environment's listing.
- A test call cannot reach a metadata service on Alibaba Cloud, on Oracle Compute Classic or over IPv6 on AWS, whatever is listed, in any spelling a host can take.
- A code whose prefix overlaps a live tenant's is refused when it is entered, with a detail on the field, before it can silence either tenant's names.

**Negative**

- **A breaking rename.** Every `KELIR_INTEGRATION_SECRET_<NAME>` that a deployment run from `main` during Sprint 22 set fails until it is renamed, and its stored reference with it. No migration does it. After `v0.9.0`, any change to the scheme is breaking too.
- **Every tenant's secrets share one process environment.** The scheme is a naming rule the operator follows, and nothing stops a deployment from setting `KELIR_INTEGRATION_SECRET_SYSTEM__X` to its database password.
- **Live tenants whose prefixes overlap lose the names they share.** This applies to pairs created before §2.1's refusal, or brought back by restoring a tenant in SQL. Nothing repairs them; the upgrade note's query finds them.
- **A deleted tenant's variables are read by a later tenant whose prefix overlaps it**, until the operator removes them (§2.1). Nothing checks that they have.
- **Tenant creation is serialised deployment-wide.** Each creation also reads every live tenant's code.
- **Each call reads every live tenant's code.** That is one query per call, and its size grows with the number of tenants.
- **The metadata addresses are a named list.** A provider's address that is not on it is judged by its range. So is the rest of `fd00:ec2::/32` once `fd00::/8` is listed.
- **The subsystem's decision now lives in two records**, and a reader of ADR-0043 has to follow its pointers to this one.

**Neutral**

- One namespace per tenant, `<CODE>__`, under the reserved prefix `KELIR_INTEGRATION_SECRET_`.
- A new address class, *a cloud metadata address*, in the refusal's words.
- A new validation detail code, `SECRET_NAMESPACE_IN_USE`, on `tenantCode`, under the existing `VALIDATION_ERROR`.
- ADR-0043's text stays as it was amended on 2026-10-01, with dated pointers to this record.

  - `a_code_that_maps_like_a_deleted_tenants_is_accepted_and_a_suspended_one_still_blocks`.

- **`domain::secret`'s unit tests** hold the mapping, the separator, the exact upper-case match, the refusal of another tenant's name and of a name two live tenants reach, and A1's refusal of the bare prefix. **The overlap is held by three more**:
  - `codes_overlap_when_they_map_alike_or_one_covers_the_other`;
  - `codes_that_share_only_characters_do_not_overlap`;
  - `creation_refuses_exactly_the_pairs_whose_shared_names_gate_three_refuses`, which checks the comparison against `TenantNamespaces::admits` over every pair of 17 codes.
- **`organization::domain`'s unit tests** hold the 422 detail and the identical code left to the index: `a_code_sharing_a_live_tenants_secret_names_is_refused_on_the_code_field` and `a_code_sharing_no_name_passes_and_an_identical_one_is_left_to_the_index`.
- **`domain::egress`'s unit tests** hold the three addresses against every list (`a_cloud_metadata_address_is_refused_whatever_is_listed`), and their neighbours' classes (`the_addresses_beside_a_metadata_address_keep_their_class`).
- A reviewer checks what no test can:
  - **the code is never taken from the request, the token or the reference**;
  - no new resolver path reads the environment before the three gates;
  - any new route that writes `tenants.tenant_code`, or restores a tenant, takes `lock_tenant_codes` and calls `refuse_shared_secret_namespace`.

## 6. Revisit When

- **A tenant's code becomes changeable, or a route restores a deleted tenant.** Creation would then no longer be the only route §2.1's refusal needs.
- **A deployment meets a deleted tenant's variables read by a later tenant** (§2.1). That reopens option I, refusing against deleted tenants too.
- **A deployment cannot choose a secret's variable name**, because a platform injects it under its own. The namespace rests on the operator naming the variable.
- **A provider documents a metadata or credential address that is neither link-local nor on §2's list**, or **a deployment on AWS lists a unique-local range covering `fd00:ec2::/32` and something in it besides `fd00:ec2::254` answers** with what a test call should not show. The list is then extended, or the prefix refused whole (option G).
- **A secret backend with its own tenancy arrives** (the Vault client, [#605](https://github.com/sujanto-gaws/kelir/issues/605)). Whether a `vault://` path is scoped by the same namespace, by a prefix of its own, or by the backend's policy is then decided with it.
