# ADR-0017 — Field Refusals Answer 422 with the S10.3 Envelope

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-27 · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** `D-29`, [ADR-0016](0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md)

## 1. Context

**Recorded retrospectively on 2026-09-01** from `D-29` in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1; the operative statement is [SDD](../../design/01.%20System%20Design%20Document.md) §8.2.2 (standard §9).

JFSS S10.3 shows its error envelope with `"status": 400`, and S8.1.1 says `400 Bad Request` for an unknown custom operator. Every field-level refusal in this API answers **422**, through `AppError::Validation` — the only variant that carries `details`, whose `ValidationDetail` **is** S10.3's shape (`{path, rule, code, message}`), documented as such in `error.rs` since Phase 1. A submission that refuses has to answer with one number.

## 2. Decision

**422 with the S10.3 envelope, for every refusal a field can carry.** The envelope, the dot-notation `path` and the stable machine-readable `code` are preserved exactly; only the status number differs from the specification's illustrative example.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. 422 for every field-level refusal** | One status for one failure class | **Chosen** |
| B. 400 throughout, as S10.3's example shows | Most literal reading of the specification | Rejected — gives one failure class two status codes across the product and makes a client branch on which endpoint it called |
| C. 400 for the two structural cases, 422 for the rest | The most literal reading of both texts | Rejected — the same refused submission would answer differently depending on which of its fields was wrong |

### A. 422 — chosen

`validate_definition`'s refusal of a non-conformant JFSS document already answers 422, as does every other field-level refusal in the product. The `400` in S10.3 sits inside an **illustrative body** rather than in a MUST, and 422 is a 4xx, which is what the construction plan asked for. What S10.3 actually specifies — the envelope shape, the `path`, and the stable `code` a client branches on — is preserved: `RULE_NOT_REGISTERED` for the unknown-rule case S8.1.1 names, `EVALUATION_FAILED` for an expression that produced no value, `RULE_NOT_ENFORCED` for [ADR-0016](0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md)'s refusal.

### C. Split by case

The worst outcome for a caller, and the reason this decision exists at all.

## 4. Consequences

**Positive** — a client has one status and one body shape for "the payload is wrong at these fields", across definitions, submissions and documents. Branching happens on `code`, which is the field the specification made stable for that purpose.

**Negative, accepted** — a reader comparing a response to S10.3's example sees a different number beside an identical body. Recorded so it reads as a decision rather than an oversight.

**Neutral** — nothing about the envelope changed, so the client-side handling S10.3 describes works unmodified.

### 4.1 Impacted Documents

| Document | Change | Status |
|---|---|---|
| [SDD](../../design/01.%20System%20Design%20Document.md) §8.2.2 | Already carries the status and the codes | No change |
| [JFSS](../../schema/JSON%20Form%20Schema.md) S10.3 | Deliberately untouched — the divergence is from an illustrative body, not a MUST | No change |

## 5. Compliance

`tests/rad_form_submissions.rs` holds the status and the envelope. The OpenAPI document generated from the handlers states 422 for these paths, so a generated client sees the real contract.

## 6. Revisit When

JFSS turns the `400` into a normative requirement — at which point the choice is a specification conformance question rather than an API consistency one.
