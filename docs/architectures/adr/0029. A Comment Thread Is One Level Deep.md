# ADR-0029 — A Comment Thread Is One Level Deep

**Status:** Draft · **Last updated:** 2026-09-02

**Decision date:** — · **Deciders:** Sprint 13 item 4's author, at construction — **author-verified** ([sprint plan](../../../projects/planning/01.%20Sprint%20Plan.md) §2), so this record stays `Draft` until a second reader has it · **Supersedes:** — · **Superseded by:** — · **Related:** `D-50`, [ADR-0030](0030.%20A%20Deleted%20Comment%20Leaves%20a%20Tombstone.md), FR-CMT-002, issue [#253](https://github.com/sujanto-gaws/kelir/issues/253)

## 1. Context

**Written when the decision was taken**, which is what separates this record from ADR-0001…ADR-0028 (standard §9).

[SRS](../../requirements/srs.md) §4.11 FR-CMT-002 says *the system shall support threaded replies*, `Should`. It does not say how deep, and neither did anything else: `0032_comment.sql` created `comments.parent_comment_id` in Sprint 12, wrote nothing to it, and recorded in its own header that threading was Sprint 13's to fill. A nullable self-reference carries **any** depth, so the schema had already committed to nothing and would have accepted everything.

Two surfaces were waiting on the answer. `POST /api/v1/documents/{id}/comments` took a body and nothing else — [#249](https://github.com/sujanto-gaws/kelir/issues/249) left `parentCommentId` off deliberately, on the grounds that *a reply nothing renders as one is not a reply*. `CommentsTab.vue` ([#296](https://github.com/sujanto-gaws/kelir/issues/296)) then shipped the screen that would render one, and said in its own documentation that the reply control was waiting for this item.

[#253](https://github.com/sujanto-gaws/kelir/issues/253) AC1 is the requirement that the depth be **decided and stated** rather than left to fall out of the column being nullable. The constraint on what could hold it: `0026_form_section_not_its_own_parent.sql` had already established, about this exact shape, that a row-level `CHECK` sees one row — *my parent has no parent* is a property of a second row and no constraint can read it.

The audience matters to the choice. This conversation hangs on a document somebody is deciding whether to approve; it is read start to finish by a reviewer who has a decision to make, not browsed like a forum.

## 2. Decision

**Kelir threads comments exactly one level: a reply names a root comment, and a reply to a reply is refused.** `parentCommentId` on the create surface must name a comment of the same document whose own `parent_comment_id` is null; anything else is a 422 naming the field. The refusal lives in `comment::service::add_comment`, inside the transaction that writes the reply. This decides the depth of the conversation and nothing else — resolving a thread (FR-CMT-005) and mentions (FR-CMT-006) remain unbuilt and unconstrained by it.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. One level, refused in the service** | A reply answers a root; the second hop is a 422 | **Chosen** |
| B. Unbounded depth | Let the column mean what it can hold | Rejected — a recursive read and a collapsing screen bought for a `Should`, and threads that wander off the document |
| C. Bounded depth of *n* | Three or four levels, enforced by a walk | Rejected — the walk costs the same as B and the bound is a number nobody can defend |
| D. Decide it in the screen, leave the API open | No server work at all | Rejected — two clients would then disagree about what a conversation is |

### A. One level — chosen

**It is the depth the reader needs.** A reply exists so that an answer sits next to its question; a second level exists so that a conversation can branch, and a document under approval is not a place anybody wants a branching argument. One level costs a field on an existing surface and an indent on an existing screen, and it leaves the reading order total: root, its answers, next root.

**It also keeps every query a single hop.** `repository::list_for_document` orders by joining the parent once, and [ADR-0030](0030.%20A%20Deleted%20Comment%20Leaves%20a%20Tombstone.md)'s tombstone test is an `EXISTS` over direct children. Both statements are readable, and both stop being right the day the depth changes — visibly, in the file the change would be made in.

**What it does not solve:** a long thread is still a long thread. Nothing here collapses, paginates within a thread, or summarizes; a page boundary can still separate a reply from its root, and the screen draws such a reply at the top level rather than dropping it.

### B. Unbounded depth

It would have bought the shape the column already had and FR-CMT-002 read literally. The cost is a recursive read (`WITH RECURSIVE`, or a second query per level), a screen that must collapse and indent arbitrarily, and an ordering rule that no longer fits in one `ORDER BY`. That is a large surface for a `Should` — and the requirement asks for *threaded replies*, which one level is.

### C. Bounded depth of *n*

Enforcing "at most three" needs the same ancestor walk as B — `master_data/service/facility.rs::refuse_cycle`'s shape — because depth is a property of a path. Having paid for the walk, the bound is then a number with no argument behind it: three is not better than four, and the first person to hit it will ask why.

### D. Decide it in the screen

The API would accept any depth and `CommentsTab.vue` would draw two levels. The second client — a mobile app, an integration, a later screen — would draw something else, and both would be right, because nothing had decided. The refusal has to be where the row is written.

## 4. Consequences

**Positive** — the create surface gains one optional field and no new endpoint; a reply and a comment are the same write, which is what [concepts/02](../../concepts/02.%20Handling%20Attachments%20Comments%20and%20Activity%20Log.md) §12.3 sketched. The list statement stays one `SELECT` with one join, and the screen's nesting is one `v-for` inside another. The reply control appears on roots only, so a control whose only outcome is a 422 never exists.

**Negative, accepted** — a person who wants to answer a specific reply must answer its root, and the thread reads slightly flatter than what they meant. Deep discussion has nowhere to go; if it happens anyway, it will happen as a run of roots. This is a real loss of expressiveness in exchange for a conversation a reviewer can read in order.

**Neutral** — `comments.parent_comment_id` is unchanged and still holds any depth. Widening later needs no migration: it is one refusal in one function, a recursive read, and a screen.

## 5. Compliance

`a_reply_to_a_reply_is_refused_and_the_conversation_stays_one_level` in `kelir-backend/tests/document_comments.rs` asserts the refusal **and** that the refused reply was not stored; `a_reply_cannot_reach_across_documents` covers the other half of the parent check. `offers no reply control on a reply` in `CommentsTab.spec.ts` holds the screen to it.

A reviewer checking a new comment query asks one question: does it assume children have no children? Both statements that do — the tombstone `EXISTS` and the ordering join — say so in their own documentation.

## 6. Revisit When

FR-CMT-005 (resolve) or FR-CMT-006 (mentions) lands and needs a place to hang something this shape cannot hold; or a deployment reports people answering the wrong comment because the one they meant was itself a reply. Either is a cheap reopen: the column carries any depth already.
