## 1. Context

**Written when the decision was taken, before its build** (plan 22 §7, *Merge order*: row 2's build waits for row 2's ADR).

**[NFR-SEC-006](../../requirements/srs.md) reads *audit trail must be protected from unauthorized modification*, and FR-AUD-003 *the system shall prevent audit records from being modified*.** **D-139** (2026-10-31) met both with a trigger and recorded them as met against the application's connection, not against the table's owner. On 2026-11-10 the product owner named [#842](https://github.com/sujanto-gaws/kelir/issues/842), *the backend's role can drop the audit trigger*, a `v1.0.0` blocker, `priority:must`, and plan 22 places it as row 2.

**The acceptance bar is `requirements-analyst`'s trace-T criteria, posted on #842 on 2026-11-14** (plan 22 §5's second state note). This record restates none of them. Where a criterion and this record differ, the criterion is read first, and the two are reconciled before this record is adopted.

**What exists at `621cd56`:**

- **One role migrates and serves.** `main.rs` opens one pool from `KELIR_DATABASE_URL` (line 56), runs `db::run_migrations` on it (line 61), and serves through it. Record 25 §4.5 found #842 as filed: *that pool owns the table*.
- **The trigger.** `0052_audit_events_append_only.sql` refuses `UPDATE`, `DELETE` and `TRUNCATE` on `audit_events`, per statement and unconditionally. `audit_append_only` sends 14 kinds of write through the application's pool and all 14 are refused (record 25 §4.5). **Its own header lists what it does not stop**: anything the owner or a superuser can do (`DISABLE TRIGGER`, `DROP TRIGGER`, `DROP TABLE`, replacing the function, `ALTER TABLE … INHERIT`), access to the disk or a backup, a restore from an altered dump, and a forged appended row. **The owner is the application**, so a stolen application credential defeats the trigger ([Database Schema](../../design/02.%20Database%20Schema.md) §10.2).
- **The provisioner** (`deploy/staging/provision-ubuntu-24.sh` §4) creates one role, `kelir`, with the password in `.env` as `KELIR_DB_PASSWORD`. It creates the database owned by `kelir`, grants it `ALL ON SCHEMA public`, and admits `kelir` alone in `pg_hba.conf`. The release compose file builds `KELIR_DATABASE_URL` from that role. The local deployment (Installation guide §5) asks the operator for the same one role, `CREATE ROLE kelir … ; CREATE DATABASE kelir OWNER kelir;`. The development stack connects as `postgres`, the superuser.
- **The harness** migrates and serves each test database through one pool, and `fixtures::write_past_the_audit_trigger` disables the trigger through it. Its comment says that works only because the pool owns the table.
- **No runtime code runs DDL.** A search of `kelir-backend/src` finds no `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `LOCK TABLE` or `SET ROLE` in a statement. The application's statements are `SELECT`, `INSERT`, `UPDATE` and `DELETE`, and advisory locks.
- **The migrator** is sqlx 0.8.6's, with `set_ignore_missing(true)` so a previous binary tolerates newer rows (#76, Release Process §6). **Before it reads anything, `Migrator::run` takes an advisory lock and runs `CREATE TABLE IF NOT EXISTS _sqlx_migrations`** (`sqlx-postgres` 0.8.6, `migrate.rs`), then two `SELECT`s on that table. With nothing to apply it writes nothing.
- **Rollback is redeploying the previous images**, and `./deploy.sh <previous-version>` keeps the compose file and `.env` (Release Process §6, ADR-0049 §4). For `v1.0.0`, the previous binary is `v0.9.0`'s, which reads `KELIR_DATABASE_URL` and nothing else about the database, and migrates at startup.
- **Configuration is refused, not defaulted, where a default would be a decision nobody took.** `config.rs` gives the object-store credentials a value in `development` and `test` and refuses to start without them in `staging` and `production` (#317). `deploy.sh` refuses a `.env` that lacks a variable `.env.staging.example` declares.
- **PostgreSQL 16 and 17 are the supported servers** (**D-153**). Since PostgreSQL 15, `PUBLIC` holds no `CREATE` on schema `public`.

**Why this is an ADR** (standards/06 §1, plan 22 §8 decision 5): it changes how every deployment connects to its database, it is the first upgrade with required database steps, and it trades rollback to `v0.9.0` against NFR-SEC-006.

## 2. Decision

**Kelir's backend migrates as the role that owns the schema, through a URL and a pool of their own, and serves as a role that owns nothing, may not change `audit_events`, and runs no DDL. Outside `development` and `test` it refuses to start in any other shape.**

- **Two roles.**
  - **The owner**, `kelir`: the role a `v0.9.0` host already has. It owns the database, schema `public`'s objects, every table including `audit_events` and `_sqlx_migrations`, the trigger and its function. It logs in only to migrate.
  - **The serving role**, `kelir_app`: `LOGIN`, not a superuser, owner of nothing, member of no role, with no `CREATE` on the database or on schema `public`. It holds `CONNECT` on the database, `USAGE` on schema `public`, `SELECT, INSERT, UPDATE, DELETE` on every table, and `USAGE, SELECT` on every sequence, **except**:
    - on `audit_events`, `SELECT` and `INSERT` only;
    - on `_sqlx_migrations`, `SELECT` only.

    It holds `TRUNCATE`, `REFERENCES` and `TRIGGER` on nothing. Without ownership it cannot `ALTER`, `DISABLE`, `DROP` or replace the trigger, its function or its table, and without `CREATE` it cannot create an object for the owner to resolve.
- **Future tables are granted by default privileges.** Provisioning runs, as a superuser:

  ```sql
  ALTER DEFAULT PRIVILEGES FOR ROLE kelir IN SCHEMA public
      GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO kelir_app;
  ALTER DEFAULT PRIVILEGES FOR ROLE kelir IN SCHEMA public
      GRANT USAGE, SELECT ON SEQUENCES TO kelir_app;
  ```

  So a table a later migration creates is the serving role's to read and write without that migration naming any role.
- **Widening is provisioning's; narrowing is the backend's, on every start.** **A migration names no role**, because the role names are a deployment's. After migrating, while it still holds the owner's pool, the backend revokes `UPDATE, DELETE, TRUNCATE` on `audit_events` and `INSERT, UPDATE, DELETE, TRUNCATE` on `_sqlx_migrations` from the serving role, which it learns as `current_user` on the serving pool. The revokes are idempotent, so the narrowing holds against a table a migration recreates, and against a fresh host, where default privileges grant `_sqlx_migrations` in full when the first start creates it. **The pass is skipped when both pools are the same role**, the development shape: the owner would otherwise revoke from itself, and `write_past_the_audit_trigger` would stop working.
- **Configuration.**
  - **`KELIR_DATABASE_URL` is the serving role's URL.** The name keeps the meaning the previous binary gives it, so a rollback runs the previous binary as the restricted role, which fails loudly rather than serving as the owner.
  - **`KELIR_DATABASE_MIGRATION_URL` is new: the owner's URL.** `config.rs` reads it as `database_migration_url: Option<String>`. `KELIR_DATABASE_SSL_MODE` and `KELIR_DATABASE_SSL_ROOT_CERT` apply to both URLs through the one `db::connect_options` rule.
  - **`main.rs` opens a migration pool of its own** from that URL, at most 2 connections. It runs `db::run_migrations`, then the narrowing, on that pool, and **closes it before the server binds**. The administrator bootstrap, the three workers and every request use the serving pool.
  - **In the release compose file** the deployment variables become `KELIR_DB_PASSWORD`, the owner's, unchanged, and `KELIR_DB_APP_PASSWORD`, new, the serving role's, declared in `.env.staging.example`.
- **With only `KELIR_DATABASE_URL` set**:
  - **in `development` and `test`, the backend migrates and serves through that one URL**, as `v0.9.0` does;
  - **in `staging` and `production`, it refuses to start**, naming `KELIR_DATABASE_MIGRATION_URL`, as a missing `KELIR_JWT_SECRET` is refused.

  **The single-URL shape is not an upgrade path for a deployed host.** A `v0.9.0` host takes §4's steps before its first `v1.0.0` start. `deploy.sh` refuses its `.env` until `KELIR_DB_APP_PASSWORD` is there, and the compose file's `:?` refuses it to an operator driving compose by hand.
- **The serving role's posture is checked before serving.** In `staging` and `production`, after the narrowing and before binding, the backend reads, on the serving pool, that its `current_user`:
  - is not a superuser;
  - is not a member of the owner of `audit_events`;
  - holds none of `UPDATE`, `DELETE`, `TRUNCATE` on `audit_events`;
  - holds no `CREATE` on schema `public`.

  Any of these, and it refuses to start, naming what it found. So one URL naming the owner twice, a serving role granted too much, or a superuser in `KELIR_DATABASE_URL` cannot pass for this shape.
- **The rollback to `v0.9.0` is what row 2's rehearsal proves** (§4, *The N−1 question*).

**Scope.** It covers `audit_events` and `_sqlx_migrations`; the backend's configuration, pools and startup; the harness; the release compose file, `.env.staging.example`, the provisioner and `deploy.sh`; and CI's databases. **It leaves four things open**:
- other tables whose rows are history: `workflow_history`, `document_status_history` and the rest keep full DML, as the trigger leaves them;
- a forged appended row, since `INSERT` stays the serving role's;
- the superuser, the host, the disk and the backups, which no role separation reaches;
- the development compose stack, which keeps connecting as `postgres` with one URL.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. The existing owner migrates; a new serving role serves; both URLs in the backend** | `kelir` keeps ownership and becomes the migration role; `kelir_app` is created and granted; `KELIR_DATABASE_MIGRATION_URL` and a pool of its own | **Chosen** |
| B. A separate migrate step holds the owner's URL | The same roles, but a one-shot `migrate` command or compose service runs the migrations, and the serving container never holds the owner's URL | Rejected for `v1.0.0` — a second deploy-time process and order for a gain the threat it closes does not need yet; §6's first trigger |
| C. A `NOLOGIN` owner, a login migrator and a serving role | Ownership moves to a role nobody logs in as; a migrator role is its member | Rejected — `REASSIGN OWNED` in every upgrade, and a migrator that is the owner's member can do what the owner can |
| D. One role, with its own `UPDATE`, `DELETE` and `TRUNCATE` on `audit_events` revoked | No second role and no new URL | Rejected — an owner can grant itself back what was revoked, and keeps `ALTER` and `DROP` |
| E. `audit_events` alone moved to an audit owner | `ALTER TABLE audit_events OWNER TO kelir_audit`; the application keeps owning everything else | Rejected — the application still holds DDL over every other table, and every migration that touches `audit_events` needs the third role |
| F. Tamper evidence only | Rely on the hash chain (ADR-0012) and stop at detection | Rejected — **D-139**'s option 3: it narrows a `must` and FR-AUD-003's *prevent*, which is a scope call the product owner did not take |

### A. The existing owner migrates; a new serving role serves — chosen

**It moves the owner out of the request path with the fewest upgrade steps.** A `v0.9.0` host's `kelir` already owns every object, so nothing changes owner: the upgrade creates one role, grants it, sets default privileges and admits it in `pg_hba.conf`. The serving role is the one an attacker reaches through the application, by SQL injection, a leaked log line or a stolen URL, and **that role can no longer touch the trigger, its function or the table's definition**. The trigger then holds against everything except the owner and a superuser, and the owner is out of the serving connections.

**Keeping `KELIR_DATABASE_URL` as the serving role's URL is what makes the rollback fail closed.** The previous binary reads only that variable. Naming the owner's URL there and adding an application URL beside it would make a rollback silently serve as the owner again.

**The narrowing at startup is what makes the restriction a property of the product rather than of a script.** A provisioner can drift, and an operator can run `GRANT ALL ON ALL TABLES`. The backend revokes again on every start and then checks its own posture, so a deployment that widened the grants does not start, as a store with no key refuses the write in ADR-0049.

**What it does not solve.** **The serving container's environment holds the owner's URL**, because the same process migrates. Code execution inside the backend reads it from the environment, as it can read `KELIR_JWT_SECRET` and MinIO's pair. A, then, closes the routes that reach only the serving connection, and not a compromise of the process. B is what would close that too.

### B. A separate migrate step holds the owner's URL

The backend binary would gain a `migrate` command, run by a one-shot compose service before the backend starts, with `depends_on: condition: service_completed_successfully`. Only that service's environment would hold the owner's URL. **It buys the one thing A does not**: code execution in the serving process finds no owner credential. The costs:
- **A second process in every deploy.** `deploy.sh`, the release compose file, the local deployment, CI's browser job and the rollback each gain a step and an order. A migrate that fails leaves the backend not started, which is right and is a new failure the Installation guide must describe.
- **Plan 22 sized row 2 for A**: a migration URL and a pool of its own in `config.rs` and `main.rs`, at 1,300–2,200, stop 3,300. B adds the command, the service and its ordering in every stack.
- **The rollback question is unchanged.** `v0.9.0`'s image does not have the command, so the rollback still runs the previous binary's own startup migration, as the serving role.
- **The secrets sit together anyway.** `/opt/kelir/.env` holds both passwords (root, 600, NFR-SEC-007), so B moves the owner's password out of one container, not off the host.

**B is the right shape once migrations leave startup**, as `main.rs`'s comment already expects when replicas start together, or once a secret store can hand the owner's credential only to a migrate job. That is §6's first trigger.

### C. A `NOLOGIN` owner, a login migrator and a serving role

Ownership would move to `kelir_owner`, `NOLOGIN`; `kelir` would become a migrator, a member of `kelir_owner`; `kelir_app` would serve. **It buys an owner nobody can log in as.** But a member of the owner role can `SET ROLE` to it, or inherits its rights, so the migrator's credential is the owner's in all but name. Every `v0.9.0` host would run `REASSIGN OWNED BY kelir TO kelir_owner`, and a restore would need three roles. The gain over A is a name.

### D. One role, with its own privileges revoked

`REVOKE UPDATE, DELETE, TRUNCATE ON audit_events FROM kelir` would make the owner's own writes fail on privilege before the trigger. **It needs no new role, no new URL and no upgrade step.** It is no control: the owner may `GRANT` the privileges back to itself, and keeps `DISABLE TRIGGER`, `DROP TRIGGER` and `CREATE OR REPLACE FUNCTION`, which are ownership's and cannot be revoked. It would be a second trigger with the first one's limit.

### E. `audit_events` alone moved to an audit owner

`ALTER TABLE audit_events OWNER TO kelir_audit`, with the function too. **It is one statement per host, and the application keeps its URL.** The costs: the application still owns every other table, so it can still drop a foreign key, a constraint or a table; every later migration that touches `audit_events`, as `0004`, `0019`, `0022`, `0035` and `0052` did, must `SET ROLE` to an owner it is not; and the application, owner of the schema's other objects, keeps `CREATE` on schema `public`, so it can create objects the audit owner's statements resolve. It meets the letter of #842 and leaves the application with DDL.

### F. Tamper evidence only

The hash chain (ADR-0012) detects a rewritten row; it does not prevent one. **D-139** rejected this as its option 3 because it narrows a `must` and FR-AUD-003's *prevent*. Nothing has changed that force.

## 4. Consequences

**Positive**
- **The serving role cannot change a stored audit row by any route the trigger's header lists for the owner**: no `UPDATE`, `DELETE` or `TRUNCATE` by privilege, and no `DISABLE`, `DROP` or replacement of the trigger, its function or its table, by ownership. The trigger and the privileges each stop the three verbs, so either alone still holds.
- **A widened grant does not start.** The narrowing and the posture check run on every start in `staging` and `production`.
- **The upgrade changes no owner.** One role is created and granted; nothing is reassigned.
- **A later migration needs no grant of its own.** Default privileges grant its tables.
- **The development shape is unchanged**: one URL, one role, the harness's fixture as it is.

**Negative**
- **The backend's environment holds the owner's URL** (§3, A). Code execution in the serving process reaches the owner. The NFR-SEC-006 claim after this row is *against the serving connection*, not *against the process*.
- **It is the first upgrade with required database steps**, run as a superuser on the host, below. An operator who skips them is refused at deploy, not at first use.
- **Every deployment holds a second database password**, `KELIR_DB_APP_PASSWORD`, and `pg_hba.conf` admits a second role.
- **A restore needs both roles to exist first.** `pg_dump` carries the grants and the default privileges, and `pg_restore` re-issues them to `kelir_app`, which must exist in the target cluster. The provisioner creates both, so a restore onto a provisioned host works. A restore with `--no-privileges` leaves the serving role with no grants, so the backend fails at its first statement, which is the safe direction. Installation guide §8.3's `pg_restore --no-owner --role=kelir` keeps `kelir` as the owner, as this decision needs.
- **A table a migration creates with rows nobody may change gets full DML by default.** The narrowing names two tables; a third append-only table is added to it by the change that creates the table (§5).
- **The harness needs a role it can serve as.** Roles are per cluster, so the native `kelir_dev` setup (Installation guide §3) gains either `CREATEROLE` or a pre-created serving role. That is the build's to choose and §3's to state.
- **Two pools at startup.** The migration pool holds up to 2 connections and is closed before the server binds. Under §10 of the Installation guide, n backends started together take up to 2 × n more connections for the length of their migrations.

**Neutral**
- **One backend variable**, `KELIR_DATABASE_MIGRATION_URL`, so `configuration_reference.rs` requires its row in Installation guide §7.1. **One deployment variable**, `KELIR_DB_APP_PASSWORD`. `KELIR_DATABASE_URL`'s meaning narrows to *the serving role's URL*.
- **`write_past_the_audit_trigger` runs on the harness's owner pool**, and its comment now describes a fixture, not the product's limit.

### The N−1 question: what row 2's rehearsal must prove

**The question.** After the upgrade, the release compose file sets `KELIR_DATABASE_URL` to `kelir_app`, and `./deploy.sh 0.9.0` keeps that file. So the rollback starts `v0.9.0`'s binary as the serving role, and that binary migrates at startup. With nothing to apply, sqlx 0.8.6 takes an advisory lock, runs `CREATE TABLE IF NOT EXISTS _sqlx_migrations`, and reads the table twice. **The serving role has `SELECT` on `_sqlx_migrations` and no `CREATE` on schema `public`.** Whether PostgreSQL 16 and 17 refuse that `CREATE TABLE IF NOT EXISTS` for want of `CREATE` on the schema, when the table already exists, is what the rehearsal decides. This record does not reason it out (Release Process §6: *rehearse the rollback, don't reason about it*).

**What row 2's rehearsal must prove**, recorded in the row's pull request as Release Process §6 asks, failure included:
1. Migrate an empty database with the new binary through `KELIR_DATABASE_MIGRATION_URL`, and provision `kelir_app` as §2 says.
2. Start `v0.9.0`'s binary, built from its tag, with `KELIR_DATABASE_URL` naming `kelir_app`. **It reaches `/health/ready`.**
3. Through that binary's API, sign in, and do one write that audits. The row is in `audit_events`, and the rollback served as the restricted role.

**If step 2 fails**, the serving role is **not** given `CREATE` on schema `public`: that is DDL, and with it the serving role could create objects the owner's statements resolve, which is part of what this record removes. Instead:
- **the rollback to `v0.9.0` runs in `v0.9.0`'s posture**: the operator points `KELIR_DATABASE_URL` at the owner, `kelir` with `KELIR_DB_PASSWORD`, for as long as the rollback lasts, and NFR-SEC-006 is held only against the application's connection for that time, as it is on `v0.9.0` today;
- that is the maintenance plan Release Process §6 requires of a release that is not N−1-compatible, and **the `CHANGELOG.md` upgrade note and the release notes state it**, with the line to change;
- `v1.0.0`'s own rollback target, from `v1.0.1` on, knows both URLs, so **the question arises once**.

**If step 2 passes**, the rollback needs no step, and the upgrade note says so.

### The upgrade a `v0.9.0` host runs

These are the commands the `CHANGELOG.md` upgrade note and Installation guide §6.1, §7 and §8 carry; row 2 writes them there, not this record. Role names are §2's.

**On the staging-shape host** (Installation guide §6), the provisioner does the database half when re-run, as it did across #778:

```bash
cd /opt/kelir
printf 'KELIR_DB_APP_PASSWORD=%s\n' "$(openssl rand -base64 36 | tr -d '\n/+=' | head -c 40)" >> .env
sudo ./provision-ubuntu-24.sh          # creates kelir_app, grants it, sets default privileges, admits it in pg_hba.conf
cp <release>/deploy/staging/docker-compose.staging.yml <release>/deploy/staging/.env.staging.example .
./deploy.sh 1.0.0
```

**On any other host, the local deployment included** (Installation guide §5), as a superuser, after a backup:

```sql
CREATE ROLE kelir_app WITH LOGIN PASSWORD '...';     -- KELIR_DB_APP_PASSWORD
GRANT CONNECT ON DATABASE kelir TO kelir_app;
\c kelir
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
GRANT USAGE ON SCHEMA public TO kelir_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO kelir_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO kelir_app;
REVOKE UPDATE, DELETE, TRUNCATE ON audit_events FROM kelir_app;
REVOKE INSERT, UPDATE, DELETE, TRUNCATE ON _sqlx_migrations FROM kelir_app;
ALTER DEFAULT PRIVILEGES FOR ROLE kelir IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO kelir_app;
ALTER DEFAULT PRIVILEGES FOR ROLE kelir IN SCHEMA public
    GRANT USAGE, SELECT ON SEQUENCES TO kelir_app;
```

and, where `pg_hba.conf` names roles, a line for `kelir_app` beside `kelir`'s, then `SELECT pg_reload_conf();`. Then `KELIR_DB_APP_PASSWORD` in `.env`, the new compose file, and the deploy.

**What the upgrade does not need**: no ownership change, no migration, no data rewrite, and no downtime beyond the deploy's own restart. The two `REVOKE`s are the backend's on every start too; they are in the list so the host is right before the first start.

## 5. Compliance

**The probe decides #842's test, red with the grants widened** (plan 22 §7, *Gates per row*, row 2). As the serving role, against a database the owner migrated:
- **`UPDATE`, `DELETE` and `TRUNCATE` on `audit_events` are refused on privilege**, before the trigger. **Red**: with `UPDATE, DELETE, TRUNCATE` granted back, they reach the trigger, which still refuses them; the probe asserts which of the two refused.
- **`ALTER TABLE audit_events DISABLE TRIGGER`, `DROP TRIGGER`, `CREATE OR REPLACE FUNCTION audit_events_refuse_change()`, `ALTER TABLE audit_events INHERIT`, `ATTACH PARTITION`, `ENABLE REPLICA TRIGGER`, `DROP FUNCTION … CASCADE`, `DROP COLUMN`, `RENAME` and `CREATE TABLE` are refused.** These are every case [#833](https://github.com/sujanto-gaws/kelir/issues/833)'s campaign landed as the owner, several with the trigger still enabled, which #842's comments read into its *Done when*. **Red**: with the serving role made a member of `kelir`, the first succeeds.
- **Every table but the two is the serving role's to read and write.** A query over `information_schema.role_table_grants` finds no table where `kelir_app` lacks `SELECT`, `INSERT`, `UPDATE` or `DELETE`, other than `audit_events` and `_sqlx_migrations`. **Red**: with the default privileges removed and a table created, it finds that table.
- **The startup refuses.** In `staging`, with `KELIR_DATABASE_MIGRATION_URL` unset, the backend exits naming it. With `UPDATE` granted on `audit_events` and the narrowing mutated out (no setting turns it off), or with `KELIR_DATABASE_URL` naming the owner, it exits naming what it found. **Red**: with the check removed, each starts.
- **The narrowing is idempotent.** Two starts leave the same grants.

**The N−1 rehearsal is recorded in row 2's pull request**, as §4 says, with its result and, if it failed, the fallback written into the upgrade note.

**A reviewer of any migration checks two lines**: it names no role, and a table it creates whose rows nobody may change is added to the narrowing in the same change. `migration-author` carries both.

## 6. Revisit When

- **Migrations leave the backend's startup**: replicas started by an orchestrator, a release step that migrates, or a secret store ([#605](https://github.com/sujanto-gaws/kelir/issues/605)) that can hand the owner's credential to one job only. B then costs no more than A, and the owner's URL leaves the serving container.
- **A supported target cannot create a role**, such as a managed PostgreSQL that gives a deployment one login. The single-URL refusal in `staging` and `production` is reopened then, not before.
- **Another table is made append-only**: the narrowing's list is the pattern, and a third entry is the point to ask whether a group role named in migrations serves better than a list in the binary.
