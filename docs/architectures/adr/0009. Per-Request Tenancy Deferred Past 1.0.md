# ADR-0009 — Per-Request Tenancy Deferred Past 1.0

**Status:** Superseded · **Last updated:** 2026-09-01

**Decision date:** 2026-08-20 · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** [ADR-0010](0010.%20Multi-Tenant%20Mode%20Runs%20and%20Roles%20Are%20Tenant-Scoped.md) (2026-08-25) · **Related:** `D-7`, `D-13`, `D-17`

> **Superseded by [ADR-0010](0010.%20Multi-Tenant%20Mode%20Runs%20and%20Roles%20Are%20Tenant-Scoped.md).** Multi-tenant mode runs, the boot guard is gone, and roles are tenant-scoped. Nothing in this record still describes the system; it is kept because the deferral shaped Sprints 5–10 and because two later decisions (`D-13`, `D-17`) declined to schedule work by naming *the decision that supersedes this one* as their return condition.

## 1. Context

**Recorded retrospectively on 2026-09-01** from `D-7` in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1, which remains the operative history (standard §9).

FR-IDM-009 obliges tenant isolation *"if multi-tenant mode is enabled"*, and nothing resolved a tenant per request — so the condition had no state in which it was true. Identity queries were tenant-scoped (94 references, every one from the caller's own claims), but turning `KELIR_MULTI_TENANT` on made sign-in impossible from the UI (#67) and the bootstrap granted a role across the boundary (#65). Master data was the first module where a second tenant would show.

## 2. Decision

**One tenant per deployment; multi-tenant mode is not exercised before 1.0.** The structural half stands — `tenant_id` is in the BASE column set and every identity read is scoped by it — and the half with no consumer is deferred: per-request resolution, its transport, and how the frontend learns the deployment's mode.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Keep the structural half, defer resolution** | Boot guard refuses to start with the mode on | **Chosen** |
| B. Build per-request resolution in Sprint 5 | Finish the feature now | Rejected — roughly two items on a mode no deployment runs, pushing Phase 3 for it |
| C. Ship the login field | The mode's original UI half | Rejected then — became a boot guard instead: refuse to start rather than serve a sign-in page nobody can complete |

### A. Defer — chosen

The expensive-to-retrofit half is the column and the scoping, and both were already delivered. What was deferred had no consumer.

### B. Build it now

Rejected on cost against a mode nothing ran.

### C. The login field

Replaced by the boot guard. #65 stayed open, correctly labelled `Should`, non-urgent while the default tenant held.

## 4. Consequences

**Positive** — Phase 3 was not delayed, and no deployment ran a half-resolved tenancy model.

**Negative** — three faces of one seam were left open, and two later decisions had to decline scheduling work because of it: `D-13` sent FR-ORG-001 (#27) to the unscheduled list because a tenant surface would create tenants nobody could sign in to, and `D-17` left #27 and #65 there for the same reason. A deferral that other decisions must route around is a cost that keeps being paid.

**Neutral** — MVP scope was unchanged; SRS §9 names no tenant criterion.

## 5. Compliance

While in force, the boot guard was the check: the backend refused to start with `KELIR_MULTI_TENANT` on. It no longer exists.
