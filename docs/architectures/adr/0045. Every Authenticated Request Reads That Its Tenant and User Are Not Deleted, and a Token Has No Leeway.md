# ADR-0045 — Every Authenticated Request Reads That Its Tenant and User Are Not Deleted, and a Token Has No Leeway

**Status:** Adopted · **Last updated:** 2026-10-01

**Decision date:** 2026-10-01, adopted at the merge of [#656](https://github.com/sujanto-gaws/kelir/pull/656) · **Deciders:** Product owner (**D-105**, answered A, *"Refuse at once, before the freeze"*; the leeway, answered separately, *"Set it to zero with D-105's fix"*) · **Supersedes:** — · **Superseded by:** — · **Related:** [ADR-0010](0010.%20Multi-Tenant%20Mode%20Runs%20and%20Roles%20Are%20Tenant-Scoped.md), [ADR-0043](0043.%20A%20Test%20Call%20Runs%20in%20the%20Request,%20Resolves%20Only%20env%20Secrets,%20and%20Connects%20Only%20to%20a%20Checked%20Address.md), [ADR-0044](0044.%20A%20Value%20PostgreSQL%20Cannot%20Store%20Is%20Refused%20in%20One%20Shared%20Place,%20Never%20per%20Parameter.md), `D-104`, `D-105`, FR-API-008, FR-AUTH-003, NFR-SEC-002, NFR-SEC-003, NFR-SCA-001, NFR-PERF-001, issues [#650](https://github.com/sujanto-gaws/kelir/issues/650), [#648](https://github.com/sujanto-gaws/kelir/issues/648), [#649](https://github.com/sujanto-gaws/kelir/issues/649)

## 1. Context

**This is the first record of the token model.** It was built in Sprint 1 from [architectures/01](../01.%20Basic%20Framework%20Concept%20and%20Architecture.md) §18.1 and no record weighed it. What existed when the question arose:

- **An access token is a JWT that lives 15 minutes** (`ACCESS_TOKEN_TTL_MINUTES`, a constant) and carries `sub`, `tenant_id`, `username`, `roles` and `permissions` (FR-AUTH-003, NFR-SEC-002). The `tenant_id` claim is the partition key every query filters by ([ADR-0010](0010.%20Multi-Tenant%20Mode%20Runs%20and%20Roles%20Are%20Tenant-Scoped.md)). The refresh token is opaque, stored as a hash, rotated on every use, and lives 30 days.
- **Authenticating a request read no row.** `Authenticated::from_request_parts` verified the signature and the expiry and nothing else, so nothing that happened to a user or a tenant after a token was issued reached that token. The refresh token was the only half that could be revoked.
- **Verification accepted a token for 60 seconds past its expiry.** That is the `jsonwebtoken` library's default leeway. Nothing in the code set it, and nothing recorded what it was for. The tests that applied D-104 measured it: a token 59 seconds past `exp` answered 200, and one 90 seconds past answered 401.
- **Authentication is per route, not a layer.** A handler that takes `Authenticated` cannot be reached without a token, and `router.rs` states that as the design for FR-API-008 and NFR-SEC-003: the rule is visible in each handler's signature, and `/auth/login` and `/auth/refresh` stay reachable without an exception list.
- **The backend holds no state between requests** (NFR-SCA-001), and the pool is 10 connections per instance. A request holds at most one pooled connection at a time ([coding standard](../../standards/01.%20Coding%20Standard.md) §2.5).
- **No performance budget covers a single request.** NFR-PERF-001 is stated per view: a list within 1 second and a detail within 2 at P95, with 50 concurrent users and 10,000 documents.

**D-104 was answered A on 2026-10-01**: an access token outlives the suspension or deactivation of its tenant, and the deactivation of its user, until it expires, as a stated limit. The product owner chose to state the limit over checking the tenant's status on each request. D-104 says in its own row that it does not decide a deleted tenant or a deleted user.

**The tests that applied D-104 found what the deleted case does** ([#650](https://github.com/sujanto-gaws/kelir/issues/650)). With a token issued before its tenant was soft-deleted, `GET /auth/me`, `GET /identity/users`, `GET /identity/roles` and `GET /documents` answered 200 with the tenant's data, and `POST /identity/users` answered 201: a user was created inside a deleted tenant, where no administrator can see it. A deleted user's token worked on every route that did not read the user's own row. An integration test call answered such a token 500, because a deleted tenant has no secret namespace ([#648](https://github.com/sujanto-gaws/kelir/issues/648), [ADR-0043](0043.%20A%20Test%20Call%20Runs%20in%20the%20Request,%20Resolves%20Only%20env%20Secrets,%20and%20Connects%20Only%20to%20a%20Checked%20Address.md)).

**D-105 asked whether a deleted tenant's token is refused at once or works until it expires**, and was answered A on 2026-10-01, to be built before the `v0.9.0` freeze. Its row records that the question put to the product owner described the tenant, that option A as written carries a deleted user with it, and that the user half was read as included and not separately confirmed. The leeway was asked separately and answered zero.

## 2. Decision

**Kelir refuses an access token whose tenant or user is deleted, on every authenticated route, from the next request after the deletion; and accepts no token past its expiry.**

- **The check lives in the `Authenticated` extractor.** After the token is verified, `from_request_parts` calls `identity::service::token_subject`, which runs one statement (`identity::repository::token_subject`): the tenant by the claims' `tenant_id`, and the user by the claims' `sub` within that tenant. The statement always returns one row, and reads each of the two as live, deleted or missing. Every route that takes `Authenticated` gets it, 143 operations on 2026-10-01, and so does every route written later.
- **It reads `deleted_at` and never `status`.** "Deleted" means `deleted_at`. A `SUSPENDED` or `INACTIVE` tenant's token, and an `INACTIVE` or `LOCKED` user's, keep working until they expire, which is **D-104**'s answer and is not changed here.
- **Not both live is a 401 `UNAUTHORIZED` with no reason.** The request is accepted only when the tenant and the user are both live. A deleted row, a missing row, and a user that does not belong to the claimed tenant are all refused. The envelope is the one an expired token gets. Which of the two it was, and whether deleted or missing, goes to the operator's log at `warn` with the user and tenant ids, and never to the caller.
- **A database error is a 5xx.** The request is never accepted on a failed read, and never answered 401 for one.
- **The leeway is zero, set explicitly.** `verify_access_token` sets it from a named constant, so a token is accepted for its 15 minutes and no longer.
- **Everything else in the token stays a snapshot.** The statement returns no status, username, role or permission. Those are the claims' until the token expires.

**Out of scope, and not covered by this decision:**

- **Refresh, logout and sign-in** are not given the check. Each already reads its own rows. That a refresh relies on the revocation and does not itself check the tenant's status stays open as [#649](https://github.com/sujanto-gaws/kelir/issues/649).
- **A password change** still does not end an access token already issued.
- **A request already past the extractor** when the deletion commits runs to completion.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. One read in the `Authenticated` extractor, of `deleted_at` only** | Every authenticated request reads two rows by primary key before its handler runs | **Chosen** |
| B. The same stated limit as D-104 | A deleted tenant's token works until it expires, and the texts say so | Rejected — it leaves rows written into a tenant nobody can open (D-105's option B) |
| C. A cache of the answer, with a staleness bound | Each process remembers which tenants and users are live for a few seconds | Rejected — it reintroduces the window it is meant to close, and replicas disagree inside it |
| D. The predicate folded into each route's own query | Every query joins `tenants` and `users` on `deleted_at IS NULL` | Rejected — there is no one query per route, and nothing makes a new route carry it |
| E. A tower layer over the authenticated routes | The check runs before routing reaches a handler | Rejected — it abandons the per-route design, and refuses before the extractors that answer 4xx |
| F. The extractor reads `status` as well | A suspended tenant's token is refused at once too | Rejected — it is D-104's option B, which the product owner declined the same day |
| G. Keep the library's 60 seconds of leeway | The bound stays 16 minutes | Rejected — nobody chose it, and it made every stated bound a minute longer than the constant |

### A. One read in the `Authenticated` extractor, of `deleted_at` only — chosen

**The extractor is the one place every protected route already passes through.** `router.rs` makes a handler's signature the statement that a route is protected, so a check there binds 100% of them by construction, and the route written next month gets it without a line of its own. That is the shape [ADR-0044](0044.%20A%20Value%20PostgreSQL%20Cannot%20Store%20Is%20Refused%20in%20One%20Shared%20Place,%20Never%20per%20Parameter.md) took for `QueryParams`: one shared place, and a walk that holds it.

**The cost is one read per authenticated request**: one statement, on a connection returned to the pool before the handler takes its own. The request still never holds two connections. Both predicates are on primary keys. On the builder's `EXPLAIN`, with 201 tenants, `users` was read by `users_pkey` and `tenants` by a sequential scan of four pages: the planner did not use the index at that size, and nobody tested a tenant count at which it does. No latency was measured, and no budget exists to test it against: NFR-PERF-001 is view-level. That is stated as a cost in §4 and as a trigger in §6.

**Two scalar subqueries and not a join, so the log can say which.** An inner join answers no row for a deleted tenant, a deleted user, a missing one and a mismatched pair alike. The statement as built returns one row with a column for each, `NULL` where there is no row, and the refusal's log line carries `tenant = live|deleted|missing` and `user = live|deleted|missing`.

**`deleted_at` and not `status`, because the two were decided apart.** D-104 states a limit for a tenant or a user that still exists and can be made `ACTIVE` again. A deleted tenant cannot be opened by anybody, so what its token writes has no owner who can see it. Reading `status` here would reverse D-104 without anybody having decided to.

**401 with no reason**, because the caller's remedy is the same as for an expired token: refresh, and when the refresh is refused, sign in. A reason in the response would tell a caller holding a stolen token that the account was removed, not merely that the token aged.

**A 5xx on a database error, in both directions.** Accepting the request would make the check advisory at exactly the moment nobody is watching. Answering 401 would turn a database blip into a sign-out: a browser answers a 401 by refreshing, and ends the session when the refresh fails.

**What it does not solve:** a tenant deleted between the extractor's read and the handler's own statements. The request completes. The window is one request, not 15 minutes.

### B. The same stated limit as D-104

It costs nothing at run time and keeps authentication free of the database. It was D-105's other option. With it, the documents would state that for up to 16 minutes after a tenant is deleted, a signed-in user can still read its records and create users in it, and #648's 500 would become a named answer. The product owner declined it: a row written into a deleted tenant has no owner who can see it, and the delete confirmation had told the administrator the data becomes unreachable.

### C. A cache of the answer, with a staleness bound

A per-process map of live tenant and user ids, refreshed every few seconds, would take the read off almost every request. **Its staleness bound is a new window**: a deleted tenant's token works for as long as the entry lives. The cache is per process, so two replicas answer the same token differently until both entries expire, and an instance that does the deleting can invalidate only its own. Closing that needs a shared invalidation channel, which is more machinery than one statement on two primary keys. It also puts state in the backend that NFR-SCA-001 asks it not to hold.

### D. The predicate folded into each route's own query

No read would be added: each query would join `tenants` and `users` and return nothing for a deleted one. There is no such query to fold it into. A route runs several statements, some write and return nothing to join, and some read no tenant-scoped table at all. It is also the per-parameter shape ADR-0044 rejected: a rule each author applies is as complete as each author's memory, and nothing reddens when a new route omits it. Its window would be zero where applied and 15 minutes where forgotten.

### E. A tower layer over the authenticated routes

One layer would run the check once, before any handler. It needs a list of the routes it does not cover, or a router split by whether a route is protected, which is the exception list `router.rs` was written to avoid. It would also run before the other extractors, so a request with a malformed path or body from a deleted tenant's caller would change from 4xx to 401, and a request with no token at all would have to be passed through to be refused later. The extractor already knows the claims and already runs only where a route is protected.

### F. The extractor reads `status` as well

The same statement could return `status` at no further cost, and a suspended tenant's users would be signed out at once. D-104 was answered on the same day by the same decider, with this as its rejected option B. Nothing changed between the two answers. Taking it here would be a reversal by implementation.

### G. Keep the library's 60 seconds of leeway

Leeway exists to tolerate clock difference between the party that issues a token and the party that verifies it. Kelir issues and verifies in the same process, or in replicas of it. The default was inherited, not chosen, and it made the D-104 bound 16 minutes while the constant, the question and the answer all said 15. Setting it explicitly to a non-zero value was not proposed by anybody. **What zero costs is the tolerance**: see §4.

## 4. Consequences

**Positive**

- A deleted tenant's token, and a deleted user's, answer 401 on every authenticated route from the next request. Nothing more is written into a deleted tenant.
- An integration test call by a deleted tenant's caller answers 401 before it reaches the service, not 500, and writes no `integration_logs` row.
- The user list's Deactivate button, which is `DELETE /identity/users/{id}` and a soft delete, signs that user out at their next request.
- An access token is accepted for 15 minutes, which is what the constant, D-104's question and every operator-facing text now say.
- A route written later is covered without knowing this record exists.

**Negative**

- **Every authenticated request costs one database read before its handler runs**, and takes a pooled connection to do it. With 10 connections per instance, a request now queues for the pool twice where it queued once. Nothing measured the effect, and there is no budget to hold it to.
- **Authentication now fails when the database does.** A route that could have answered from the token alone answers 5xx while the database is unreachable, and no route written later can avoid that.
- **The access token is no longer verifiable without the database.** That gives up the property JWTs are usually chosen for. The backend still holds no state of its own (NFR-SCA-001).
- **Zero leeway leaves no tolerance for clock difference between instances.** An instance whose clock runs ahead of the issuer's refuses a token that much early, which costs the caller a refresh. One whose clock runs behind accepts it that much late. Replicas must keep their clocks in step, well under a second apart. The shipped compose files run one backend, where the issuer and the verifier share a clock.
- **A client that held a token for a deleted account gets 401 where it got data.** That is the intent, and it is a visible change for an API client.
- **Two cases that look alike on the screen now differ.** Deleting a user ends their token at once. Setting a user's status to `INACTIVE` leaves it up to 15 minutes. The texts written for D-104 had run the two together.
- **The race in §3 A remains**, and the integration service's own 500 for a caller whose tenant is not live survives in it.

**Neutral**

- `GET /auth/me` for a deleted user answers 401, which a test holds. #650 reported 404 there before the change; no test saw that 404 red.
- The refusal and its reason are an operator's log line. No audit row is written for a refused token, as none is for an expired one.
- Roles and permissions in a token are still a snapshot, and age for up to 15 minutes, not 16.

## 5. Compliance

**The decision is held by tests in `kelir-backend/`, the integration ones against a real database:**

- **`tests/deleted_caller_refusals.rs` is the walk.** It reads every operation that declares bearer security from `ApiDoc::openapi()`, 143 on 2026-10-01, and sends each one three times: with a live token, with a token whose tenant has since been deleted, and with one whose user has. That is 429 cells. The live cell must not answer 401, and the other two must. It names no route, so a route added later is walked. **A count guard stops it walking fewer**: it counts the handler arguments of type `Authenticated` in every `modules/**/handlers.rs` and requires the walked operations to number the same. **Nothing is written by a refused request**: every table's row count is read before the two refused passes and after them, and none may move.
- **`tests/auth_deleted_caller.rs` holds what a walk cannot**: the envelope byte for byte against an expired token's, a write refused with nothing written, an upload refused, a row deleted by SQL and not through the route, the pairing of `sub` with `tenant_id`, a token naming a row that does not exist, a lookup that fails answering 500, sign-out still answering 204, `GET /auth/me`, and the expiry edge.
- **`tests/organization_tenants.rs` and `tests/auth_session.rs`** hold the two rules side by side: a token whose tenant is `SUSPENDED` or `INACTIVE`, or whose user is `INACTIVE` or `LOCKED`, still works until it expires (D-104), and a deleted tenant's or user's access token and refresh token are both refused at once (D-105). A test that refused the first would mean D-104 was reversed.
- **`tests/integration_test_call.rs`**: a deleted tenant's caller is answered 401, and no `integration_logs` row is written.
- **Unit tests in `modules/auth/token.rs`** hold the leeway: `ACCESS_TOKEN_LEEWAY_SECONDS` is asserted to be zero at compile time, and a token whose `exp` is one second before now is refused. **That cell is the one that tells a leeway of zero from one.** A token aged by its lifetime plus one second cannot do so on every run, because it is past a one-second leeway only once a second has ticked since issue.

**Seen red, 2026-10-01** ([coding standard](../../standards/01.%20Coding%20Standard.md) §2.9). Against `main` at `6631cc9`, before the fix, 286 of the walk's 429 cells failed: every refusal cell, and no live cell. Twenty mutations were then run, each alone, and the header of `tests/deleted_caller_refusals.rs` records each with what it reddened. Two of its findings bear on how far the walk can be trusted:

- **A status predicate in place of `deleted_at` leaves the walk green**, and every test that deletes through the route with it, because both soft deletes also write `INACTIVE`. That mutation is caught only by the fixtures that set `deleted_at` by SQL and by D-104's tests.
- **The pairing of `sub` with `tenant_id` is caught by one test only**, with both tenants live. The walk is green without it, because its tokens are the application's own.

**What no test holds:**

- **The operator's log line.** No test reads it.
- **The integration service's 500 for a caller whose tenant is not live** (`integration/service/test_call.rs`). It is reachable only in the race of §3 A, and is held by review.
- **That a refusal comes before the body is read** is shown by the answer, not by probing the stream: an oversized body and a non-multipart body both answer 401.

**What a reviewer checks:**

- **A protected handler takes `Authenticated`.** A handler that verifies a token some other way is outside the check and outside the walk's guard, as it is outside FR-API-008's design.
- **`TokenSubject` carries nothing a handler uses.** A handler that starts reading status or roles from the check has moved a snapshot claim to a live read, which is a decision this record did not take.

## 6. Revisit When

- **Pool contention is measured**: acquire timeouts or queueing on the 10 connections attributable to the check. A cache (option C) or a larger pool is then weighed with a number.
- **NFR-PERF-001 is breached**, or a per-request budget is written that this read does not fit.
- **More than one backend is deployed.** The clock assumption becomes a requirement on the deployment, and a small explicit leeway is weighed against it.
- **A cache of the answer is proposed.** Its staleness bound is a window this record closed, and replicas would disagree inside it.
- **D-104 is reversed.** The extractor then reads `status` in the same statement, and this record is extended by a later one.
- **[#649](https://github.com/sujanto-gaws/kelir/issues/649) is answered** in a way that gives refresh a check of its own. The two checks should then be one rule in one place.
