## 2. Decision

**Kelir's form builder drags with `vue-draggable-plus`, pinned at exactly `0.6.1`, imported only by the builder's canvas components on its router-lazy route. Kelir's workflow graph is drawn with `@vue-flow/core` at exactly `1.48.2` and `@vue-flow/controls` at exactly `1.1.3`, laid out by `@dagrejs/dagre` at exactly `3.1.1`, all imported only by the graph component, which its page reaches with `defineAsyncComponent`. Neither library is ever on the first-load path, and `check:bundle` gains each as a subject with ADR-0040's three checks. Kelir code imports none of zod, `@vueuse/core`, `reka-ui`, `vue-sonner`, `@lucide/vue` or `json-logic-js`.** `@vueuse/core` arrives as `@vue-flow/core`'s own dependency and stays inside the graph's lazy chunk; the rule is that Kelir code does not import it. Background and minimap are not taken. **This change adds no dependency**: row 10 adds Vue Flow, controls and dagre, and row 11 adds `vue-draggable-plus`, each with its `check:bundle` subject. It decides nothing about a canvas **editor** or where a layout would live (**D-95** B and C), nor about moving the tree from `lucide-vue-next` to `@lucide/vue` (§6).

## 3. Options Considered

Three choices, each with its own options.

### 3.1 The drag-and-drop package

| Option | Summary | Verdict |
|---|---|---|
| A. `vuedraggable` 4.1.0 | The reference's choice: a Sortable wrapper, Vue 3 line on the `next` dist-tag | Rejected — `latest` installs the Vue 2 line, and it pins an older Sortable |
| **B. `vue-draggable-plus` 0.6.1** | A Sortable wrapper written for Vue 3: a component, a composable and a directive | **Chosen** |
| C. `sortablejs` 1.15.7 alone | The library both wrappers drive, with Kelir's own Vue binding | Rejected — Kelir would own the reconciliation of Sortable's DOM moves with Vue's state |
| D. HTML5 drag events, no library | `dragstart`/`drop` handlers on the canvas | Rejected — tablet touch and drop-position feedback written by hand |

#### A. `vuedraggable` 4.1.0

It would have bought the reference's canvas almost verbatim: kopiformbuildervue nests `<draggable>` lists through a recursive component, and row 11 could have ported that shape without translating it. **What ruled it out is how it is published.** The Vue 3 line is 4.1.0 on the `next` dist-tag. `latest` is 2.24.3, the Vue 2 line, so **`npm install vuedraggable` installs a package that does not work with Vue 3**, and nothing fails until the canvas renders. An exact pin in `package.json` holds against a range resolving wrong, but not against the next person who adds it by name. It also fixes `sortablejs` at 1.14.0, two minors behind 1.15.7, and npm last modified either line on 2023-08-20.

#### B. `vue-draggable-plus` 0.6.1 — chosen

**It is the same engine, Sortable, published for Vue 3 on `latest`**, so `npm install vue-draggable-plus` gets what the canvas needs. It was last modified on 2026-01-11, and it is the smallest of the three packages, at 215 KB unpacked. Its `<VueDraggable>` component takes a `v-model` list and a `group`, which is the shape a recursive canvas nests: panel, fieldset, columns and tabs, each a list that accepts from the palette and from its siblings. Sortable handles touch itself, which NFR-USE-001's tablets need.

**What it does not solve.** It is pre-1.0, so a minor release may break its API; the exact pin makes every upgrade a deliberate change. Its only declared dependency is `@types/sortablejs`, declared as a peer too, so a types package is installed for a runtime library; which Sortable build it runs is in its own `dist`, and row 11 confirms it. **Row 11 translates the reference's `<draggable item-key>` slot templates** to its `v-model` lists, which is porting work A would not have had. **And dragging is a pointer gesture**: no Sortable wrapper reorders from the keyboard, so the builder needs a way to add and move a component without dragging. That is row 11's criterion, not a property any of these options supplies.

#### C. `sortablejs` 1.15.7 alone

It would have bought one dependency with none of its own, maintained and current. **What ruled it out is the binding.** Sortable moves DOM nodes itself, and Vue renders the list from state, so every drop must be undone in the DOM and replayed as a change to the reactive array, across nested lists, with Vue's keys intact. That is the code both wrappers exist to hold, and owning it buys nothing a wrapper does not already give.

#### D. HTML5 drag events, no library

It would have added nothing, as ADR-0040's option A would have. **It loses on what a nesting canvas needs and the events do not give**: drop position between siblings, a placeholder while dragging, and touch on a tablet, all written and tested by hand for every container type. It is the most code of the four for the least reach.

### 3.2 The `@vue-flow/*` packages

| Option | Summary | Verdict |
|---|---|---|
| **A. Core and controls** | `@vue-flow/core` 1.48.2 and `@vue-flow/controls` 1.1.3 | **Chosen** |
| B. Core alone | Pan and zoom by pointer, wheel and pinch only | Rejected — zoom and fit have no button a keyboard can reach |
| C. Core, controls, background and minimap | Everything the reference uses | Rejected — a dotted grid and an overview add nothing to a read-only view |

**D-95 named Vue Flow**, so the question is which of its packages, not whether. **Core** draws nodes and edges, pans and zooms, and fits the graph to its container. Its read-only switches turn off dragging, connecting and selecting, so the view cannot be mistaken for an editor. **Controls** adds zoom-in, zoom-out and fit-view as buttons, at 34 KB unpacked with no dependency but core. That is what B lacks: without it, a reader who is not using a mouse wheel or a touchscreen cannot zoom into a definition with many states. **Background** is a decorative grid, and **minimap** is an overview for a canvas larger than the screen. A graph fitted to its container on every load has nothing off-screen to point at, and the minimap would add 323 KB unpacked and two d3 modules for it. **The view adds no information the list does not hold**, so the list stays its text alternative; how the graph presents itself to a screen reader is row 10's.

### 3.3 The auto-layout package

| Option | Summary | Verdict |
|---|---|---|
| **A. `@dagrejs/dagre` 3.1.1** | The maintained continuation of dagre: a layered layout, synchronous | **Chosen** |
| B. `elkjs` 0.12.0 | The Eclipse Layout Kernel, compiled to JavaScript | Rejected — the licence, at 8.05 MB unpacked, for layout quality a state list does not need |
| C. `dagre` 0.8.5 | The original package | Rejected — unmaintained since 2022, and it brings lodash |

#### A. `@dagrejs/dagre` 3.1.1 — chosen

**A JWSS definition is a directed graph with cycles**: a `RETURN` edge goes back to an earlier state. A layered layout puts states in ranks by their transitions and reverses a cycle's edges internally to rank it, which is the drawing a reader of an approval path expects. It is MIT, was last modified on 2026-08-08, and depends on one package of its own, `@dagrejs/graphlib`. It runs synchronously, so the graph is laid out in the same tick it is drawn, with no worker. **Its cost**: 1.41 MB unpacked, whose shipped share is unmeasured until row 10 builds it. Its edges are routed as polylines, and a dense definition will cross more than ELK's would.

#### B. `elkjs` 0.12.0

It would have bought the better layout: orthogonal edge routing, ports, and fewer crossings on a dense graph. **What ruled it out is weighed in three parts, and the licence is the first.** `elkjs` is `EPL-2.0 OR GPL-3.0-or-later`. Kelir would elect EPL-2.0, a weak copyleft. **A minified bundle served to every browser is distribution in object code**, so Kelir would owe each deployment EPL-2.0's terms for that code: its notices kept, and the source made available. Every runtime dependency Kelir ships today is MIT, Apache-2.0 or ISC (§1), and Kelir declares no licence of its own and no policy against which a copyleft term could be judged. **Taking the first copyleft dependency is a decision for the product owner with a policy in hand**, not a side effect of a graph view. Second, its size: 8.05 MB unpacked, the Java kernel compiled to JavaScript, against dagre's 1.41 MB. Third, the lockfile already carries `elkjs` 0.10.2 through `@unovis/ts`, tree-shaken out. Taking 0.12.0 directly would put a second version beside it and make the shaken-out one shipped code. **None of this says elkjs is wrong for Kelir**; it says a read-only view of a state list does not need what it costs. §6 says what would reopen it.

#### C. `dagre` 0.8.5

**[Plan 19](../../../projects/planning/19.%20Sprint%2023%20Builder%20Pair%20Construction%20Plan.md) row 3 names `dagre`, and on npm that is this package, 0.8.5. This record takes `@dagrejs/dagre` instead.** `dagre` was last modified on 2022-06-14 and is unmaintained, and it depends on the whole of `lodash` and the old `graphlib`. `@dagrejs/dagre` is the same layout, maintained under the same organisation. **Nor is `@unovis/dagre-layout` taken**, the 0.8.8 prerelease fork already in the lockfile. It is Unovis's internal dependency, versioned for Unovis, and taking it directly would tie Kelir's layout to a chart library's release cycle.

### 3.4 What is not taken from the references

Each was in a reference, and none is a dependency of Kelir code. Two of them deserve more than a line, because the letter of the rule would not hold.

| Package | Why not |
|---|---|
| **zod**, and a Zod mirror of either meta-schema | A second validator beside the server's (**D-86** point 5, **D-95** point 4). The builders show the server's verdict at the state, transition or path it names (#426 AC3, S10.3). Hand-built forms already have no Zod (coding standard §3.4) |
| **`@vueuse/core`** | **It arrives anyway**, as `@vue-flow/core`'s dependency (^10.5.0). So the rule is that **Kelir code does not import it**, and it ships only inside the graph's lazy chunk, where `check:bundle` holds it (§5). It would resolve if imported, as `elkjs` already does through Unovis, which is why a lint rule is needed and a missing package is not enough |
| **`reka-ui`** | **shadcn-vue's primitives in the tree carry none today** (§1), so *beyond what shadcn-vue already brings* is nothing. Whether a generated shadcn-vue primitive that needs it is worth it is the question ADR-0040 §6 already leaves to the change that wants one |
| **`@lucide/vue`** | **It is not a different icon set**: the lockfile marks Kelir's `lucide-vue-next` deprecated in its favour (§1). Taking it beside `lucide-vue-next` would ship two copies of one icon set. The builders use `lucide-vue-next` like every other screen, and moving the whole tree to `@lucide/vue` is one change of its own (§6) |
| **`vue-sonner`** | A toast puts a refusal where the user is not looking. Kelir shows it where it happened (§1) |
| **`json-logic-js`** | **D-10**'s `datalogic-wasm` evaluates on the client ([ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md)), and row 4's shared builder evaluates with it (**D-110**) |

## 4. Consequences

**Positive** — Row 11 builds the nesting canvas on a maintained Vue 3 wrapper that installs correctly by name, and row 10 draws the graph with the library **D-95** named and a layout that ships under MIT. **No first-load cost**: a session that never opens a builder fetches none of it, and `check:bundle` holds that the way it holds the evaluator and Unovis. Of the six packages the references would have added, Kelir takes none directly; the one that arrives anyway, `@vueuse/core`, is confined to a lazy chunk. Vue Flow's four d3 modules, `d3-drag`, `d3-interpolate`, `d3-selection` and `d3-zoom`, are already in the lockfile through Unovis, so they are not new to the tree.

**Negative** — **Four new direct dependencies** (`vue-draggable-plus`, `@vue-flow/core`, `@vue-flow/controls`, `@dagrejs/dagre`) and their transitive trees, `@vueuse/core` with its own among them, for two admin screens. **Every size above is unmeasured**: what ships is known only when rows 10 and 11 build, and ADR-0040's table is the form their measurements take. `vue-draggable-plus` is pre-1.0, and row 11 translates the reference's canvas templates rather than copying them. **dagre draws a dense definition less cleanly than ELK would**, accepted for the licence and the size. **Dragging is pointer-only**, so the canvas owes a non-drag path for every add and move. `check:bundle` grows from two subjects to four, and Vue Flow's stylesheets are a payload its third check cannot see today (§5). Four more exact pins, each upgrade a deliberate change.

**Neutral** — The graph component and the canvas components live in their features' folders, beside the pages that use them, as `DocumentStatusChart.vue` does, not in `components/ui`. `eslint.config.js` gains its first `no-restricted-imports` rule.

## 5. Compliance

**`npm run check:bundle`, in CI's frontend job after the build, is what a violation fails.** It gains two subjects, each with ADR-0040's three checks: no chunk off the first-load path carries the library; a first-load chunk carries it; a first-load chunk carries its payload.

| Subject | Packages | Added by |
|---|---|---|
| The form builder's drag-and-drop library | `vue-draggable-plus`, and `sortablejs` if the build resolves it as a package of its own | Row 11, [#688](https://github.com/sujanto-gaws/kelir/issues/688) |
| The workflow graph | `@vue-flow/core`, `@vue-flow/controls`, `@dagrejs/dagre`, `@dagrejs/graphlib`, **`@vueuse/core`** | Row 10, [#687](https://github.com/sujanto-gaws/kelir/issues/687) |

**`@vueuse/core` is in the graph's subject on purpose**: that is what holds it inside the lazy chunk. A change that puts it on first load, for any reason, is this record being reversed and fails as one. **Each subject is seen to fail before its row merges**: a static import reintroduced on a first-load module goes red, and green again when removed, as ADR-0040 §5 recorded for Unovis.

**One gap the rows close.** Vue Flow needs its stylesheets, and the third check reads a first-load chunk's `assets`, not its `css`, so a stylesheet imported from `main.ts` would pass. **Row 10 makes the check see a first-load chunk's stylesheets**, or its pull request states why it cannot and imports the stylesheets only from the graph component.

**The rule on imports is `no-restricted-imports` in `eslint.config.js`**, naming zod, `@vueuse/core`, `reka-ui`, `vue-sonner`, `@lucide/vue`, `json-logic-js`, `vuedraggable`, `elkjs` and `dagre`, each with a message citing this record. **Whichever of rows 10 and 11 merges first adds it**, and it is seen red on one such import. `npm run lint` is one of the frontend's six checks.

**No check enforces the exact pins**, so it is a reviewer's line, as for Unovis: **a `^` or `~` on any of the four packages is this record being relaxed.** An upgrade re-runs the six checks and re-measures the chunks against the rows' recorded sizes.

## 6. Revisit When

- **A canvas editor is wanted** (**D-95** B or C). Its own ADR decides where a layout lives, and whether dragging on the graph is Vue Flow's or a second library's.
- **dagre's layout of a definition a deployment actually ships is unreadable**, judged by the edge crossings a reviewer cannot follow. elkjs is then reconsidered, with its licence put to the product owner.
- **Kelir adopts a licence, or a dependency-licence policy.** The weighing in §3.3 B changes with it, in either direction.
- **`vue-draggable-plus` reaches 1.0 with a breaking change, or publishes nothing for twelve months while a defect the canvas hits is open.**
- **The tree moves from `lucide-vue-next` to `@lucide/vue`**, as a change of its own. It replaces one package with the other everywhere, so it is not the second icon package §3.4 refuses; this record's line on it changes with that move.
- **A shadcn-vue primitive the tree wants needs `reka-ui` or `@vueuse/core`**, the trigger ADR-0040 §6 already names for its chart scaffolding.
