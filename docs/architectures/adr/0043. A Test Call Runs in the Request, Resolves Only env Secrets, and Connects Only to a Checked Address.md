# ADR-0043 — A Test Call Runs in the Request, Resolves Only `env` Secrets, and Connects Only to a Checked Address

**Status:** Adopted · **Last updated:** 2026-09-29

**Decision date:** 2026-09-29 · **Deciders:** Product owner (the five answers on #547: 2026-09-29) · **Supersedes:** — · **Superseded by:** — · **Related:** [ADR-0041](0041.%20Every%20Workflow%20Transition%20Writes%20an%20Outbox%20Event,%20and%20After-Hooks%20Are%20Its%20First%20Consumer.md), `D-96`, `D-94`, FR-INT-002, FR-INT-001, FR-INT-006, NFR-SEC-004, NFR-SEC-007, issues [#547](https://github.com/sujanto-gaws/kelir/issues/547), [#520](https://github.com/sujanto-gaws/kelir/issues/520), [#536](https://github.com/sujanto-gaws/kelir/issues/536), [#548](https://github.com/sujanto-gaws/kelir/issues/548)

## 1. Context

**The registry stores where a secret lives, and nothing reads it** ([#520](https://github.com/sujanto-gaws/kelir/issues/520), FR-INT-001, [SDD](../../design/01.%20System%20Design%20Document.md) §9.3). `integration_credentials.secret_reference` accepts `env://NAME` or `vault://path[#field]`, checked for shape only (§9.3.3). **Any environment-variable name has the right shape**, the deployment's own `KELIR_JWT_SECRET`, `KELIR_DATABASE_URL` and `KELIR_STORAGE_SECRET_KEY` included, and the backend process holds all of them. An endpoint's `path` is relative to its system's `baseUrl`, and a `baseUrl` is an absolute `http`/`https` URL with no user info and no query (§9.3.4). `external_systems.timeout_seconds` is 1 to 300 and read by nothing. `integration_logs` exists in `0046_integration.sql` and has no writer ([Database Schema](../../design/02.%20Database%20Schema.md) §12.5). The crate has no HTTP client of its own. `reqwest` 0.12 is already in `Cargo.lock` through `object_store`, and every TLS user in the crate is rustls (`sqlx`, `lettre`).

**FR-INT-002 (`Should`) is construction plan 17 row 16**, the first row below the line, and its criteria require an ADR recording where a secret is resolved, what egress is allowed, and the time bound (plan 17 §8). **Its first consumer is an administrator's test call** to one registered endpoint, answered in the request: `POST /api/v1/integration/external-systems/{id}/endpoints/{endpointId}/test-call`, under a new `integration:endpoint:call`.

**Three forces bind the shape:**

- **A resolved secret leaves the process only to the system it belongs to.** NFR-SEC-004 masks sensitive data in logs, and architectures/03 rule 3 logs every integration call masked. #547 extends that to every response, log line, `integration_logs` row and `audit_events` row. **What a call can resolve is the other half**: a caller who can write a credential reference and a `baseUrl` can otherwise send any variable the process holds to a host they control.
- **A test call is a server-side request whose destination an administrator types.** `baseUrl` is validated for shape at save, and nothing checks where its host name resolves. An unchecked call can reach the deployment's loopback, the cloud metadata address `169.254.169.254`, or a private network the server can see and the administrator cannot.
- **The outbox has one consumer, and ADR-0041 §6 reopens on a second.** An after-handler would be a new handler kind on that consumer, and it would pull in [#536](https://github.com/sujanto-gaws/kelir/issues/536), an after-hook's time budget measured and not enforced.

**Of the eight credential types the column accepts**, two have a wire shape that needs nothing beyond the secret: `BEARER_TOKEN` and `BASIC_AUTH`. `API_KEY` needs a header or parameter name, and no column holds one. The rest need a token exchange, a signature, or a certificate.

## 2. Decision

**Kelir makes an administrator's test call synchronously inside the request, resolves an `env://` reference under `KELIR_INTEGRATION_SECRET_` in process for the call's duration only, and connects only to an address it has checked, within the system's timeout.**

- **In the request, and nowhere else.** The handler resolves, calls and logs before it answers. **No `core:` handler, no outbox event, no hook chain.** ADR-0041 §6's trigger is not tripped, and #536 does not join row 16.
- **The destination is the endpoint's `path` appended to its system's `baseUrl`** (SDD §9.3.4), with the endpoint's `method` and an empty body. It is appended rather than resolved, so a `baseUrl` with a path keeps it, and it must stay on the base's scheme, host and port. **The route takes no request body**: nothing the caller sends names a URL, a host or a header.
- **The credential is the system's one credential that is active, not deleted and valid today** (UTC, both bounds inclusive). **None and several are both refused, by name**: a test that picked one of two would prove whichever it picked. **The credential's own type is attached**; the system's `authType` is not consulted.
- **`env://NAME` resolves only when `NAME` starts with `KELIR_INTEGRATION_SECRET_`**, by reading it from the backend process's environment at call time. **Any other name fails the call at resolve time with `SECRET_NAME_NOT_PERMITTED`**, and the failure is written to `integration_logs`. The variable is not read. **Saving is unchanged**: any name of the right shape is still accepted, and an operator names a secret with the prefix for it to resolve. **`vault://` does not resolve**: the call fails with `SECRET_BACKEND_NOT_CONFIGURED`, and the failure is written to `integration_logs`. The registry keeps accepting `vault://` at save. **The successor is named: a HashiCorp Vault KV v2 client, placed by construction plan 18.**
- **The resolved secret lives in the call's stack frame.** It is not stored, cached, returned, traced or audited. No response, log line, `integration_logs` row or `audit_events` row carries it. The request is logged with its `Authorization` header's value replaced by `[REDACTED]`.
- **Two credential types are attached.** `BEARER_TOKEN` is sent as `Authorization: Bearer <secret>`. `BASIC_AUTH` reads its secret as `user:password` and sends it as `Authorization: Basic <base64>`. **Every other type is refused with a named 422 that lists it as not built, before its secret is read.** `API_KEY` waits for a header-name column. **No DDL** beyond the permission row.
- **Egress is checked on the resolved address, and the connection is pinned to it.** The host is resolved once, and **every address it returns must pass**: a name that answers one public and one private address is refused. The connection goes only to an address that passed, so a second DNS answer cannot move it (no DNS rebinding). **Redirects are not followed**: a `3xx` is the call's answer. HTTPS still verifies the certificate against the host name.
  - **Always refused:** loopback, link-local (`169.254.169.254` included), unspecified and multicast addresses, in IPv4 and IPv6. An IPv4-mapped IPv6 address is judged as the IPv4 address it carries. Two readings go past these words, both towards refusing: all of `0.0.0.0/8` is unspecified, since an address in it reaches the local host on Linux, and `255.255.255.255` is refused with multicast.
  - **Refused unless listed:** the RFC 1918 ranges and IPv6 unique-local (`fc00::/7`). A deployment opens one with `KELIR_INTEGRATION_ALLOWED_CIDRS`. The list cannot open an always-refused range, and an entry that does not parse stops startup rather than leaving half a list.
  - **Allowed:** everything else, **CGNAT (`100.64.0.0/10`), NAT64 (`64:ff9b::/96`) and 6to4 (`2002::/16`) included**. None of the three is unwrapped to the address it carries (§6).
- **Time is bounded by `external_systems.timeout_seconds`**, as one deadline over host resolution, the request and the body read, with the client's own timeout at the same value as a second layer.
- **Every call writes exactly one `integration_logs` row** from the moment its endpoint is found, success or failure, with masked payloads. A caller refused for permission, or naming a system or endpoint outside their tenant, has made no call and writes none. It is the table's first writer. **A test call writes no audit event**: it changes no configuration, and its record is the log row.
- **The client is `reqwest` 0.12** with `default-features = false` and `rustls-tls-native-roots`, and `redirect::Policy::none()`. `base64` and `zeroize` join it as direct dependencies, for the `BASIC_AUTH` header and for wiping the resolved secret.

The route's answers, its error codes and the log row's shape are the SDD's (§9.3.6) and the Database Schema's (§12.5), not this record's.

**Left open:** the Vault client (plan 18), `API_KEY` and the other five credential types, calls made by anything other than an administrator's test, retry (FR-INT-007), and a screen for the log (FR-INT-006, [#548](https://github.com/sujanto-gaws/kelir/issues/548)).

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Synchronous, in the request** | Resolve, call and log before answering | **Chosen** |
| B. An after-handler on the outbox | A `core:` handler delivers the call after a commit | Rejected — the administrator's answer would arrive after the response; trips ADR-0041 §6 and pulls in #536 |
| **C. `env://` real, `vault://` a named failure** | One backend resolves; the other fails the call, logged | **Chosen** (product owner, 2026-09-29) |
| D. A real Vault KV v2 client now | Both schemes resolve | Rejected — its size, and a Vault container in CI |
| E. Refuse `vault://` at save | Only resolvable references are stored | Rejected — breaks #520's rules and the references already stored |
| **F. Check the resolved address, pin the connection, no redirects** | Private ranges refused unless listed | **Chosen** (product owner, 2026-09-29) |
| G. Check the host name at save | Validate `baseUrl`'s host when it is registered | Rejected — a DNS answer changes after the save |
| H. Private ranges allowed by default | Refuse only loopback, link-local, unspecified, multicast | Rejected by the product owner — a registry entry reaches the internal network |
| I. Public addresses only | No deployment setting | Rejected by the product owner — an on-premises ERP is a private address |
| **J. `BEARER_TOKEN` and `BASIC_AUTH`** | The two types that need nothing but the secret | **Chosen** (product owner, 2026-09-29) |
| K. `API_KEY` with an assumed header | `X-API-Key: <secret>` | Rejected — a guessed header name is a call that fails for a reason the log cannot show |
| **L. `reqwest`, rustls, no default features, no redirects** | The client already in `Cargo.lock` | **Chosen** |
| M. `hyper-util` directly | The layer under `reqwest` | Rejected — the TLS, pooling and timeout wiring `reqwest` already owns |
| N. `reqwest` with default features | `native-tls` | Rejected — a second TLS stack in one binary |
| **O. `env://` resolves only under `KELIR_INTEGRATION_SECRET_`** | An allow-list by prefix, checked at resolve time | **Chosen** (product owner, 2026-09-29) |
| P. A denylist of Kelir's own names | Refuse `KELIR_JWT_SECRET` and its siblings | Rejected by the product owner — it always misses one |
| Q. Accept the risk | Any name resolves; the permission split is the guard | Rejected by the product owner — three permissions stand between a caller and every secret the process holds |

### A. Synchronous, in the request — chosen

A test call answers *does this endpoint work*, and the person asking is waiting. The handler holds no transaction while it calls, so a slow system holds a request worker for at most `timeout_seconds`, not a database connection. What it does not solve: a call made on a document's behalf, which is not a test and will need its own decision on where it runs.

### B. An after-handler on the outbox

It would reuse ADR-0041's retry and breaker, which a test call does not want: a retried test is a second request the administrator did not make. The answer would reach the administrator only by polling. It would add a handler kind to the outbox's one consumer, which is ADR-0041 §6's trigger, and its duration would fall under #536, which measures an after-hook's time and does not enforce it.

### C. `env://` real, `vault://` a named failure — chosen

An environment variable is read with the standard library and needs no network, no token and no container. A `vault://` reference that fails with `SECRET_BACKEND_NOT_CONFIGURED`, logged, tells the administrator exactly why, and the reference stays valid for the day the client exists. What it does not solve: a deployment whose secrets are in Vault cannot test a call until plan 18.

### D. A real Vault KV v2 client now

Every stored reference would resolve. It costs a client with authentication, token renewal and error mapping, and a Vault container in CI to test it against, on a row already below the line for its size (plan 17 §3.2).

### E. Refuse `vault://` at save

It would make every stored reference resolvable, by breaking #520's rule that both shapes are accepted, and it would leave references already stored unreadable by the rule that stored them. It trades a clear failure at call time for a surprising refusal at save.

### F. Check the resolved address, pin the connection, no redirects — chosen

The address is what the connection reaches, so it is what is checked. Resolving once and connecting to the checked address closes DNS rebinding, where a host answers a public address to the check and a private one to the connection. A redirect is a second destination the check never saw, so it is not followed. Private ranges are closed by default and opened by the deployment, which knows its network, rather than by a registry entry, which any `:update` holder can write.

### G. Check the host name at save

It is cheap and it runs once. A host name's DNS answer belongs to whoever controls the zone, and it can change the second after the save, so a save-time check proves nothing at call time.

### H. Private ranges allowed by default

It makes an on-premises system work with no configuration. It also makes every internal service the server can reach a registry entry away from a `:update` holder. The product owner chose the default that is closed.

### I. Public addresses only

It is the simplest rule, and it refuses the ERP on the same network as Kelir, which is the integration most deployments are built for.

### J. `BEARER_TOKEN` and `BASIC_AUTH` — chosen

Both are one header computed from the secret, and both are fully described by the columns that exist. A test call against a system with any other type is refused with a 422 that says the type is not built, rather than sent unauthenticated.

### K. `API_KEY` with an assumed header

`X-API-Key` is common and not universal. A system that expects `apikey`, `Ocp-Apim-Subscription-Key` or a query parameter would answer 401, and nothing in the registry would say why. It waits for a column that names the header.

### L. `reqwest`, rustls — chosen

`reqwest` 0.12 is already built into the binary by `object_store`, so it adds a direct dependency and little build time. `default-features = false` keeps `native-tls` out, as `lettre`'s entry does. `redirect::Policy::none()` makes F's rule a property of the client. Its resolver override is what pins the connection to the checked address.

### M. `hyper-util` directly

It gives full control of the connection. It costs owning the TLS connector, the pool and the timeouts that `reqwest` already wires, for no property F needs.

### N. `reqwest` with default features

It pulls `native-tls`: two TLS stacks, two certificate stores, two sets of failures, which `Cargo.toml`'s `lettre` entry already refuses.

### O. `env://` resolves only under `KELIR_INTEGRATION_SECRET_` — chosen

An allow-list by prefix names what may be resolved, so a setting Kelir adds tomorrow is outside it without anybody remembering to exclude it. The check runs at resolve time, before the variable is read, so a refused name costs a logged failure and discloses nothing. **Saving is unchanged**, so #520's shape rule and the references it stored stand: a reference with any other name is stored and fails when called, as `vault://` does. What it does not solve: what an operator puts under the prefix is theirs to get right.

### P. A denylist of Kelir's own names

It would refuse `KELIR_JWT_SECRET`, `KELIR_DATABASE_URL` and the storage keys, and leave every other name resolvable. It has to be kept in step with `config.rs` by hand, and it cannot see what else a deployment puts in the process's environment: a cloud credential, a proxy password, another service's key. The product owner rejected it because it always misses one.

### Q. Accept the risk

The permission split would be the guard: a caller needs `integration:credential:create`, `integration:external-system:update` and `integration:endpoint:call` to send a variable to a host they control. The system tenant's `ROLE-ADMIN` holds all three, and what they would reach is the signing key every session is checked against. The product owner rejected it.

## 4. Consequences

**Positive**

- An administrator can prove an endpoint and its credential work before anything depends on them, and the answer names what failed: the secret backend, the address, the time or the system.
- The first writer of `integration_logs` exists, so FR-INT-006 (#548) has rows to show.
- A resolved secret has one place it exists, the call, and a test asserts it reaches none of the four places #547 names.
- The server cannot be pointed at its own loopback, the metadata address or, by default, its private network.

**Negative**

- **A deployment whose secrets are in Vault cannot test a call** until plan 18's client. The failure is named and logged, not silent.
- **Six of the eight credential types are refused**, `API_KEY` among them, which is the most common.
- **A test call is a real call.** A `POST` endpoint receives a real request, with whatever effect it has on the system.
- **A slow system holds a request worker** for up to 300 seconds, the column's maximum.
- **An `env://` reference stored under any other name fails every call** with `SECRET_NAME_NOT_PERMITTED`, and saving still accepts it. A reference registered before this decision, such as `env://ERP_API_KEY`, has to be renamed, and its variable with it.
- **The prefix is a naming rule the operator must follow.** It says nothing about what a prefixed variable holds: a deployment that sets `KELIR_INTEGRATION_SECRET_X` to its database password has published it to the call.
- **A private system needs a deployment setting**, so an on-premises integration fails until the deployer lists its range.

**Neutral**

- A new permission, `integration:endpoint:call`, and a new deployment variable, `KELIR_INTEGRATION_ALLOWED_CIDRS`.
- `reqwest`, `base64` and `zeroize` become direct dependencies.
- Sixteen new error codes, every one of them new to the API: fourteen 422s, `UPSTREAM_UNREACHABLE` (502) and `UPSTREAM_TIMEOUT` (504). `SECRET_BACKEND_NOT_CONFIGURED` and `SECRET_NAME_NOT_PERMITTED` are the two this decision names; the full list is [SDD](../../design/01.%20System%20Design%20Document.md) §9.3.6.
- A reserved variable prefix, `KELIR_INTEGRATION_SECRET_`, which no setting of Kelir's own may take.

## 5. Compliance

- **`kelir-backend/tests/integration_test_call.rs`** holds the decision, through the API against a mock system on `127.0.0.1`, reached only through the code-only test seam `AppConfig::integration_allow_loopback`. The tests that prove the guard run without the seam. Each guard is seen red under a reintroduced defect ([coding standard](../../standards/01.%20Coding%20Standard.md) §2.9): **the file's module header carries the mutation table**, each mutation with the tests it reddened, seen red 2026-09-29. The tests assert that:
  - a sentinel secret behind `env://KELIR_INTEGRATION_SECRET_…` reaches the called system, and appears in no response, no captured log line, no `integration_logs` row and no `audit_events` row, in any form it was sent in, including a `BASIC_AUTH` password on its own;
  - a reference to an unprefixed variable that is set, `env://KELIR_JWT_SECRET` among them, fails with `SECRET_NAME_NOT_PERMITTED`, writes one `integration_logs` row, and sends nothing to the called system;
  - a `vault://` reference fails with `SECRET_BACKEND_NOT_CONFIGURED` and writes one `integration_logs` row;
  - loopback in five spellings (`::ffff:127.0.0.1` and `2130706433` among them), `169.254.169.254`, link-local IPv6, unspecified, multicast and unlisted RFC 1918 and unique-local addresses are refused, nothing reaches the mock, and a listed range passes the guard;
  - a `3xx` is returned as the answer and its `Location` is not requested;
  - a system slower than its `timeout_seconds` fails at the bound;
  - no credential and two credentials valid today are both refused, by name;
  - every call, succeeding or failing, writes exactly one `integration_logs` row, and a refused caller or a missing target writes none;
  - `API_KEY` and the other unbuilt types are refused with the named 422 before the secret is read;
  - the route is refused without `integration:endpoint:call`.
- The address classes are held address by address by `domain::egress`'s unit tests. CGNAT, NAT64 and 6to4 are public by omission and no test names them. `config.rs`'s unit tests hold that a malformed `KELIR_INTEGRATION_ALLOWED_CIDRS` refuses startup and that no variable turns the test seam on.
- `configuration_reference.rs` holds `KELIR_INTEGRATION_ALLOWED_CIDRS`'s row in the Installation guide §7.1.
- A reviewer checks two things no test can: **every outbound request is built by the one client that pins and refuses redirects**, and **no type that holds a resolved secret derives `Debug`, `Serialize` or `ToSchema`**.

## 6. Revisit When

- **Plan 18's Vault client lands**: `vault://` then resolves, and C's named failure is removed.
- **A call is made on a document's or a workflow's behalf**, not by an administrator's test. Where it runs, and whether it retries, is then a new decision against ADR-0041.
- **A deployment reports a system reachable only through an address class not listed here**, or **an address judged public reaches something private**: CGNAT `100.64.0.0/10`, NAT64 `64:ff9b::/96` and 6to4 `2002::/16` are allowed as public today, and a NAT64 or 6to4 address carrying a refused IPv4 address is not unwrapped.
- **A deployment cannot choose a secret's variable name**, because a platform injects it under its own, or **a setting Kelir itself reads is proposed under `KELIR_INTEGRATION_SECRET_`**. Either breaks what option O rests on: that the prefix holds integration secrets and nothing else.
