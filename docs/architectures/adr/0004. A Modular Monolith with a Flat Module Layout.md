# ADR-0004 — A Modular Monolith with a Flat Module Layout

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-04 (founding) · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** [ADR-0001](0001.%20Rust%20and%20Axum%20for%20the%20Backend.md), [ADR-0007](0007.%20Explicit%20Endpoints%20for%20Core%20Master%20Data.md)

## 1. Context

**Recorded retrospectively on 2026-09-01** from [architectures/01](../01.%20Basic%20Framework%20Concept%20and%20Architecture.md) §29 Decision 4 and its inline `**Decision:**` on the module layout, and from [SDD](../../design/01.%20System%20Design%20Document.md) §4.3, which states the flat layout as the decided v1 shape. Those remain the operative statements (standard §9).

Two questions were taken together: how the backend is deployed, and how its source is laid out. Kelir spans a dozen module boundaries — identity, master data, RAD, documents, workflow, attachments, comments, activity, audit, notification, integration, plugin — and the module list ([architectures/02](../02.%20Kelir%20Framework.md)) was fixed before the first line of it was written.

## 2. Decision

**Kelir is a modular monolith: one deployable backend, with modules as a flat `modules/` source layout inside it.** Module boundaries are real — a module owns its domain, repository, service and handlers — but they are not process or crate boundaries.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Modular monolith, flat `modules/`** | One binary, one crate, modules as directories | **Chosen** |
| B. Rust workspace crates | `crates/api`, `app`, `domain`, `infrastructure`, `workflow`, `rad`, `integration`, `plugin`, `security` | Rejected for v1 — remains a considered later refactor |
| C. Services from the start | Split along the module boundaries as processes | Rejected — slower to build, harder to maintain; the monolith can evolve into services later |

### A. Flat modules — chosen

Faster to build, easier to maintain, and able to evolve into services later (architectures/01 §29). The flat layout matches [architectures/02](../02.%20Kelir%20Framework.md)'s module breakdown one-to-one, so the source tree and the canonical module list are the same list.

### B. Workspace crates

Explicitly kept alive rather than dismissed: architectures/01 records the flat structure as chosen *"and the workspace-crates layout remains a considered alternative for a later refactor"*, and SDD §4.3 says the same. It buys enforced boundaries — a crate cannot reach into another's internals — at the cost of compile-time complexity and a build split before the boundaries had settled.

### C. Services

Rejected on build speed and maintenance for a framework at v0.

## 4. Consequences

**Positive** — one binary to deploy, one migration sequence, one transaction scope. A cross-module invariant can be held in a single transaction: a submit allocates a number, writes the document, starts the workflow instance and writes the audit row together.

**Negative** — module boundaries are conventions the review has to hold, not compiler-enforced walls; nothing but discipline stops a handler reaching past a service into another module's repository. Scaling is whole-binary. The coding standard's module layout rules are load-bearing because of this.

**Neutral** — the plugin platform (architectures/04) is designed against in-process hooks rather than remote calls, which is a shape this decision makes natural.

## 5. Compliance

Review against the coding standard's module layout section; the source tree is checkable against [architectures/02](../02.%20Kelir%20Framework.md)'s module list by inspection. There is no mechanical boundary check — that is what option B would have bought.

## 6. Revisit When

Compile times or team size make the crate split pay for itself, or one module's scaling profile diverges sharply from the rest. The refactor is a documented option, so revisiting means taking B, not re-deciding A.
