# ADR-0032 — A Soft-Deleted Attachment Keeps Its Object

**Status:** Draft · **Last updated:** 2026-09-02

**Decision date:** — · **Deciders:** Sprint 13 item 5's author, at construction — **author-verified** ([sprint plan](../../../projects/planning/01.%20Sprint%20Plan.md) §2), so this record stays `Draft` until a second reader has it · **Supersedes:** — · **Superseded by:** — · **Related:** `D-52`, [ADR-0030](0030.%20A%20Deleted%20Comment%20Leaves%20a%20Tombstone.md), [ADR-0031](0031.%20An%20External%20Reference%20Is%20Not%20an%20Attachment%20Row.md), FR-ATT-009, issue [#254](https://github.com/sujanto-gaws/kelir/issues/254)

## 1. Context

**Written when the decision was taken** (standard §9).

[SRS](../../requirements/srs.md) §4.10 FR-ATT-009 says *the system shall support attachment deletion with soft delete*, `Should`. [#254](https://github.com/sujanto-gaws/kelir/issues/254) AC2 sharpens it into a question the requirement leaves open, and states why it has to be answered: **"soft" and "the bytes are gone" cannot both be true.**

The two halves of an attachment live in different places. The row is in PostgreSQL with `deleted_at` on it, like every other table in this schema; the bytes are an object in storage, written **before** the row and outside any transaction — `service::upload` documents that ordering and why. So a delete has two targets and no way to move both atomically.

[ADR-0030](0030.%20A%20Deleted%20Comment%20Leaves%20a%20Tombstone.md), one item earlier, answered the neighbouring question for comments and named this one as its follow-up: what a delete leaves behind, asked about a different object. A comment's answer turned on replies hanging from it. **Nothing hangs from an attachment** — no reply, no child row a reader would be left holding.

What does point at it is the timeline: `Attachment.Added` and any `Attachment.Downloaded` carry `attachment_id`, and `activity_events` is append-only.

## 2. Decision

**Kelir deletes an attachment softly and keeps the stored object.** `deleted_at` is set; the row keeps its `storage_reference`, `original_file_name`, `file_size` and `checksum`; nothing is removed from storage. The row leaves every list and the download refuses it — through `deleted_at IS NULL` in `list_for_document`, `count_for_document` and `find_stored_file`, so the gate is on the path that serves the bytes and not only on the one that names them. **When bytes actually leave a deployment is a retention question**, and `attachments.retention_policy_id` is the column that will answer it; nothing writes it in this release.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Soft row, object kept** | The row goes, the bytes stay for retention to decide | **Chosen** |
| B. Soft row, object deleted | *Deleted* means deleted | Rejected — unrecoverable, and it makes the row's checksum a claim about something that no longer exists |
| C. Hard delete of both | No dangling anything | Rejected — the requirement says soft, and the timeline's link would point at nothing |
| D. Tombstone in the list, as a comment leaves | Consistent with ADR-0030 | Rejected — nothing hangs from an attachment, so the tombstone holds no shape |

### A. Soft row, object kept — chosen

**It is the only option that is recoverable**, and a delete button beside somebody's upload is exactly where recoverability is worth paying for. Everything an undo would need is still on the row, and everything a *sweep* would need is too: `storage_reference` is derived from ids, so an object whose row is deleted is findable by the same listing that finds an orphan from a failed upload.

**It keeps the audit trail honest.** `Attachment.Added` recorded the checksum; the delete records it again on the way out. Both are claims about bytes that still exist, which is what makes them checkable.

**What it does not solve, stated:** the bytes stay indefinitely, because nothing in this product yet decides when they should not. §4 names that as the cost, and it is a cost this decision *creates* rather than inherits.

### B. Soft row, object deleted

The reading a person most likely has of the word *delete* — and it makes the row a description of something gone. The undo becomes impossible at the moment it is most wanted, and a checksum recorded against absent bytes is a fact nobody can ever check. It also races: an object deleted while the scan worker holds it in flight fails a scan for a reason nothing distinguishes from storage being down.

### C. Hard delete of both

The requirement says soft, which is enough. Beyond that: `activity_events` is append-only and its `attachment_id` is a foreign key, so a hard delete either violates it or takes the timeline entries with it — and *what happened to this document* is precisely what a deletion should not erase.

### D. A tombstone, as ADR-0030 chose for comments

Consistency for its own sake. A comment's tombstone exists because **replies hang from it**: remove the row and the answers are orphans. An attachment has no dependents, so a tombstone would be a row saying only *a file was here* — the timeline already says that, with the actor and the time, and says it in the place a person goes to ask.

**The two decisions differ because the objects differ, which is the point of asking the question twice.**

## 4. Consequences

**Positive** — the delete is recoverable, the audit trail keeps meaning, and the download gate needs no new code: `find_stored_file` already carried `deleted_at IS NULL`, so AC3 is held by a predicate rather than by a service remembering. The screen can say what the delete does, and does.

**Negative, accepted** — **storage grows and nothing shrinks it.** Every deleted attachment's bytes stay until something writes a retention policy, and that something does not exist. This is the decision's real cost, it is named here rather than discovered by an operator, and `retention_policy_id` is where it lands.

**Negative** — *deleted* means something narrower here than the word implies. A person deleting a file for privacy reasons is not achieving what they think. The screen's confirmation says *the stored copy is kept*, which is the honest version, and a deployment with a real erasure obligation needs the retention work before it can claim one.

**Neutral** — a deleted attachment's row is still reachable by id in the database, and its timeline entries still resolve. `Attachment.Deleted` is a new event type carrying nothing but the link, as its neighbours do.

## 5. Compliance

`a_deleted_attachment_leaves_the_list_and_keeps_its_object` asserts the row leaves the list **and** keeps its `storage_reference` and name; `a_deleted_attachment_cannot_be_downloaded` drives a cleared, downloadable file and asserts the download answers 404 after the delete — AC3's *enforced on the download path*. The authorship gate was seen red on 2026-09-02 by forcing `refuse_unless_uploader` to `Ok`.

A reviewer adding a delete anywhere in this product now has a worked answer to *what does this leave behind*, and two of them: this one and [ADR-0030](0030.%20A%20Deleted%20Comment%20Leaves%20a%20Tombstone.md).

## 6. Revisit When

A retention policy is implemented, or a deployment takes on an erasure obligation it cannot meet with a soft delete — at which point what changes is not this decision but the sweep it defers; or storage cost from deleted attachments becomes measurable, which is the same trigger arriving as a number.
