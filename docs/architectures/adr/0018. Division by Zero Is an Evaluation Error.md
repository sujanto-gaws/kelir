# ADR-0018 — Division by Zero Is an Evaluation Error

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-26 · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** `D-24`, [ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md), [ADR-0017](0017.%20Field%20Refusals%20Answer%20422%20with%20the%20S10.3%20Envelope.md)

## 1. Context

**Recorded retrospectively on 2026-09-01** from `D-24` in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1; the operative statement is [Calculation Rule Registry](../../schema/JFSS%20Calculation%20Rule%20Registry.md) §3.1 and §7.3 (standard §9).

The registry required division by zero to evaluate to `0`. Measured against the adopted engine ([ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md)), `10.5 / 0` returns `null` and normalizes to `0` as asked, while `10 / 0`, `0 / 0` and `10 % 0` **throw** — the integer path ignores the `division_by_zero` setting entirely. Both sides measure identically, so this was registry-versus-engine rather than a parity divergence. It could not stay measured-but-undecided: #163 had to render something and #164 had to return something.

## 2. Decision

**Every division by zero is an evaluation error.** `DivisionByZeroHandling::ThrowError` on both sides in place of `ReturnNull`, so the four cases behave identically instead of splitting on whether the numerator happens to be fractional. A field whose calculation errors renders **blank** and does not block typing; the refusal happens at submit, with the S10.3 envelope naming the field ([ADR-0017](0017.%20Field%20Refusals%20Answer%20422%20with%20the%20S10.3%20Envelope.md)).

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. `ThrowError` on both sides; registry bumped to 1.6.0** | Uniform behaviour, reachable by configuration | **Chosen** |
| B. Keep `ReturnNull` and define what the throw means | Smaller diff, no standards change | Rejected — ships the asymmetry: one expression renders `0` when the numerator is fractional and refuses when it is an integer |
| C. Deliver the `0` §3.1 asks for | Honour the standard as written | Rejected — not reachable by configuration; would take catching `EvaluationError` and discriminating on the engine's message text |

### A. Throw — chosen

The engine offers `ReturnSaturated`, `ThrowError`, `ReturnNull` and `ReturnInfinity`, and the integer path throws under all of them, so a uniform `0` is not available. Reaching it would mean parsing the engine's error message — text that is not API and that a version bump would change silently, which is what the pinned tests on both sides exist to make loud. It would also swallow the `min`-with-an-absent-operand refusal both sides ship deliberately. And **an average over zero scores is not `0`**: persisting `0` for it is the class of silent wrong answer the operator-parity spike was written about.

## 4. Consequences

**Positive** — one behaviour for all four expressions, on both sides, without message-text parsing.

**Negative, accepted** — the registry is an `Active Standard`, so this is a **version bump to 1.6.0** rather than errata: §3.1's division entry and §7.3 change what they require of an implementation. JFSS itself is untouched; S8.1 and S10.2 say nothing about division.

**Neutral** — the parity corpus gained `mod-by-zero`, the fourth of the four expressions this decision names and the one the corpus could not have seen move, because it carried `10 % 3` and no modulo by zero at all. The gap between the registry stating the requirement and the code meeting it lasted one day.

## 5. Compliance

The parity corpus holds all four expressions on both sides, and the two pinned division tests were inverted with the change; a regression fails CI.

## 6. Revisit When

The engine gains a configuration that returns a uniform value for the integer path — the only way option C becomes available without message parsing — or the registry's users ask for a per-form policy.
