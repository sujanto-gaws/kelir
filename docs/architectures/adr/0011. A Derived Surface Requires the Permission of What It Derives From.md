# ADR-0011 — A Derived Surface Requires the Permission of What It Derives From

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-24 (first taken as `D-12`; applied and refined through 2026-09-01) · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** `D-12`, `D-32`, `D-45`, `D-47`, `D-49`

## 1. Context

**Recorded retrospectively on 2026-09-01** from five decisions in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1 — `D-12`, `D-32`, `D-45`, `D-47` and `D-49` — which hold the individual reasoning and remain operative (standard §9). This ADR records the rule they share, because the same question has now been asked five times about five tables and answered the same way.

Kelir has surfaces that are *about* other surfaces: a record's change history, a document's activity timeline, the audit trail, a notification. Each is populated by writers elsewhere in the product, and each was at some point readable through a permission of its own.

The first instance made the failure concrete (`D-12`, #136). `master-data:audit:read` opened a party's change history on its own — but a record's `oldValue` and `newValue` **are** the record's own field values: `Party.Created` carries the code, type and status; `Party.Updated` carries `statusId`, `externalId` and `description`. A caller holding only that permission was refused `GET /parties/{id}` and answered `GET /parties/{id}/audit` with the same values.

The same shape recurred pointing outward (`D-45`, #292): a document's activity timeline carried an attachment's **original file name**, a comment's length, and the second party to a delegated decision — so a caller with `activity:read` and `document:read`, holding neither `attachment:read` nor `comment:read`, learned the name of every file on the document. *2026-redundancy-list.pdf* needs no contents to do damage.

## 2. Decision

**A surface derived from other records discloses only what the reader may already read: the derived record carries the event and the link, and the subject's own content stays behind the subject's own permission.** Where content must be gated, it is **withheld and said to be withheld**, never silently dropped. And the converse holds: a permission that guards nothing the first one does not is one permission too many.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Carry the link, not the subject; gate values by the subject's permission** | `D-45`, `D-49`; and `D-12` requiring the record's own read alongside the audit permission | **Chosen** |
| B. Filter the entries by what the caller may read | Redact per reader | Rejected — has to be remembered by every future writer, hides the event rather than the detail, and splits a page from its count |
| C. Keep the governance permission sufficient, and document the asymmetry | Defensible on its own terms | Rejected — one function applying two rules for the same reason; a tenant granting `audit:read` to a compliance reviewer does not read it as granting content |
| D. Require the object's read to see the row at all | `D-12`'s literal shape, generalized | Rejected for the audit **search** — a reviewer would need all nineteen object types, and each grantee would get a different trail |

### A. Link, not subject — chosen

`D-45` took the detail out of the timeline: `Attachment.Added`, `Attachment.Downloaded`, `Comment.Added` and `Workflow.TaskDelegated` carry `{}` and their link column, and `ActivityEvent` serves `workflowInstanceId`, `taskId`, `attachmentId` and `commentId` so *link by id* is something a caller can actually do. Nothing is lost, only relocated: the file's name is in `attachments` behind `attachment:read`, the comment behind `comment:read`.

`D-49` split the audit trail the same way for its search: *somebody updated party X at 09:05* is the trail, and `{"statusId": "SUSPENDED"}` is the object. The metadata serves anyone who may search; a row's values serve only a caller holding the read permission of the object the row names.

### B. Filtering per reader

Rejected in `D-45` for three reasons in order of weight. **(1) It has to be remembered** — every module adding an event type must extend the filter, and forgetting is silent, which is what #292 *was*. An entry with no field for a subject detail cannot forget. **(2) It hides the event, not the detail** — *a file was attached, by Sara, at 09:05* is the document's own history. **(3) It splits the page from its count** — a per-reader predicate has to appear in both statements or the two disagree, and a reader who counts learns what was filtered anyway.

### D. Requiring the object read everywhere

Right for one record (`D-12`), wrong for a search across nineteen object types (`D-49`). Hence `valuesWithheld` on the row: the difference between *nothing was recorded* and *you may not see it* is stated rather than inferred from a null. **Withheld, never hidden** — a search that dropped rows would teach an auditor the trail is shorter than it is.

## 4. Consequences

**Positive** — a derived surface cannot become a way around the permission on its subject, and it cannot become one later by accident, because the field a leak would travel in does not exist.

**Negative** — a reader of a timeline or a trail has to follow a link and hold a second permission to see detail; every caller of a master-data history needs one permission more than before (`D-12`). A deployment that *wants* the file name on the timeline for readers who hold `attachment:read` has no way to ask for it — that is the rejected shape, and it is a feature request against FR-ACT-005's screen rather than a gap.

**Neutral, and the converse of the rule** — `D-47` removed `activity:read` once `D-45` had taken the detail out: with nothing left for it to guard, it could only refuse the wrong person, namely whoever raised the document. Two permissions are one too many *only* when they answer the same question about the same rows; `master-data:audit:read` survives `D-49` on exactly that test, because it opens a different surface. Removing a permission is subject to the [release process](../../standards/04.%20Release%20Process.md) §6 N−1 rule — *deprecate in release N, remove in N+1* — so the row and its grants outlive the check by one release (#301); dropping the row beside the check would 403 every timeline read on the binary still serving a rolling deploy.

**Not settled** — `D-49`'s values are gated by object *type*, not instance: a caller holding `document:read` sees recorded values for documents they could not open. Narrowing that means a per-row existence check against nineteen modules.

## 5. Compliance

Held in code by `activity::domain::disclosable` and `audit::domain::readable_by` — allow-lists by event and object type that serve `{}` or withhold for a type they do not know, so a new type joins the safe side by default. A unit test names every object type this codebase writes, so a new one cannot join the unplaceable set silently. Six integration tests in `document_activity.rs` and `workflow_delegation.rs` and eleven in `audit_search.rs` were seen red against a reintroduced defect.

## 6. Revisit When

A reader of these tables appears that is **not** the subject's own workspace — a cross-document feed, a compliance export — which asks the question about a different subject rather than reopening this one; or per-instance gating of audit values becomes necessary.
