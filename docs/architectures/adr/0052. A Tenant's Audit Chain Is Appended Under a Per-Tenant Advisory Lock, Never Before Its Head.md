# ADR-0052 — A Tenant's Audit Chain Is Appended Under a Per-Tenant Advisory Lock, Never Before Its Head

**Status:** Adopted · **Last updated:** 2026-11-25

**Decision date:** 2026-11-25, adopted at the merge of [construction plan 22](../../../projects/planning/22.%20Sprint%2026%20Hardening%20Close%20Construction%20Plan.md) row 37's pull request, which builds [#995](https://github.com/sujanto-gaws/kelir/issues/995) with §4.1's operative documents · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** **D-157**, [ADR-0012](0012.%20The%20Audit%20Hash%20Chain%20Covers%20the%20Payload.md), [ADR-0051](0051.%20The%20Backend%20Migrates%20as%20the%20Schema's%20Owner%20and%20Serves%20as%20a%20Role%20That%20Owns%20Nothing.md), FR-AUD-003, NFR-AUD-001, NFR-AUD-002, NFR-SEC-006, [#995](https://github.com/sujanto-gaws/kelir/issues/995)

## 1. Context

**This record was written ahead of its build**, as **D-157** A requires ([construction plan 22](../../../projects/planning/22.%20Sprint%2026%20Hardening%20Close%20Construction%20Plan.md) §8, row 37). It is the shape half of D-157, and D-157 is its scope half (standard §2).

**What existed, before row 37's build.** Every audited action in Kelir goes through one function, `audit::record` (`kelir-backend/src/modules/audit/mod.rs`; coding standard §2.8). A pattern search on 2026-11-25 finds about 87 call sites, the wrappers `governance.rs` and `task.rs` call through included. It takes a `&PgPool` and runs two statements, each on whatever connection the pool hands it:

1. a `SELECT current_hash … ORDER BY created_at DESC, id DESC LIMIT 1` for the tenant, the chain's head, or the genesis hash if there is none;
2. an `INSERT` of the new row, whose `previous_hash` is that head and whose `current_hash` is `chain_hash` over it ([Database Schema](../../design/02.%20Database%20Schema.md) §10.2, *What the hash covers*; ADR-0012).

`created_at` is taken in the application, from `Utc::now()`, so that the hash is a function of the entry alone.

**What is wrong** ([#995](https://github.com/sujanto-gaws/kelir/issues/995), found by `test-engineer` on row 23, 2026-11-16). Nothing spans the read and the insert, so two writers for one tenant can read the same head and both chain to it. Every row is still written whole, and `trg_audit_events_append_only` still refuses any change to one. What forks is the chain. The shared verifier `chain_breaks` (`tests/common/audit_chain.rs`) walks a tenant's rows by `created_at, id` and reports a fork as a break at the later sibling, in the same words it uses for tampering. `migrations/0003_audit.sql` has no unique constraint on `(tenant_id, previous_hash)`, so the database cannot refuse a fork either.

**A second way to break the walk, with no concurrency** (`requirements-analyst`'s impact note on D-157, read and not tested). The head is the latest row by `created_at`, and `created_at` is the writing process's clock. If backend 2's clock runs behind backend 1's, backend 2 can write a row that chains correctly to the head but sorts before it. The walk then breaks on a chain nobody forked.

**The constraints.**

- **Who writes.** API handlers on every backend, the attachment scan worker once per backend (`attachment/worker.rs`), and the post-commit writes rows 34–36 added. With one tenant, which is the common deployment, all of them write one chain, so concurrent writes are normal use. Row 6's second backend ([#989](https://github.com/sujanto-gaws/kelir/issues/989)) makes the race easier to hit; it was already reachable on one backend.
- **The serving role.** `kelir_app` has only `SELECT` and `INSERT` on `audit_events` (ADR-0051). It cannot `UPDATE` the table, so it cannot take `SELECT … FOR UPDATE` on a row there, and the trigger refuses every rewrite whatever the role.
- **Audit writes come after the commit.** The audited change commits first, then `record` or `record_or_warn` writes its row, and a failure to write never fails the change (`record`'s own documentation). **No call site awaits `record` with a transaction open**: a read of the call sites on 2026-11-25 found each after its caller's commit or outside any transaction, and none in a function handed a transaction.
- **Every insert into `audit_events` takes `FOR KEY SHARE` on its `tenants` row**, through the `tenant_id` foreign key.
- **What the tree already uses.** Three transaction-scoped advisory locks in the two-argument form `pg_advisory_xact_lock(class, hashtext(key))`: tenant codes, the department hierarchy and the facility hierarchy, each with its own `*_LOCK_CLASS` constant, the ASCII of a four-letter tag. Bootstrap uses a fourth, a one-argument `pg_try_advisory_xact_lock` with no class.
- **The requirements.** FR-AUD-003 asks for an append-only trail that cannot be changed. NFR-AUD-001 and 002 ask that every change is auditable and that its row names its actor, time, action and object. NFR-SEC-006's detection claim rests on the chain: it is the only way to see an owner-level rewrite, and a chain that forks on its own makes that signal noisy. D-157 A reads a fork as a breach of the trail D-156 protects.

## 2. Decision

**Kelir appends to a tenant's audit chain inside one short transaction of `audit::record`'s own.** That transaction first takes `pg_advisory_xact_lock(AUDIT_CHAIN_LOCK_CLASS, hashtext(tenant_id::text))`, where `AUDIT_CHAIN_LOCK_CLASS` is the ASCII of `ADCH`. Holding the lock, it reads the head's `current_hash` and `created_at`, and takes the new row's `created_at` as the later of `Utc::now()` truncated to microseconds and the head's `created_at` plus one microsecond. It then hashes the row, inserts it and commits, which releases the lock.

`record`'s signature, its callers, the hash format and the stored columns are unchanged. No migration is needed, and no stored row is rewritten.

**`record` is never awaited while its caller holds a transaction open.** §1's read found it true of every call site, and it is now a rule. A caller whose open transaction holds a lock on its `tenants` row, waiting on a `record` that waits on the advisory lock, would wait in a cycle PostgreSQL cannot see. One edge of that cycle is in the application.

**This decides how the chain is appended. It leaves three things open:**

- forks already stored by a deployment that ran an earlier version, which a verifier still reports and nothing re-chains;
- trail order against commit order, which #995 also notes, since audits stay after commit;
- an operator-facing verifier, which still does not exist (Database Schema §10.2).

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. A per-tenant advisory lock, and a time never before the head's** | Lock, read the head, clamp the time, insert and commit, in one transaction of `record`'s own | **Chosen** |
| B. Lock the head row `FOR UPDATE` | Lock the row the new one chains to | Rejected — the serving role cannot take it, and an empty chain has no row to lock |
| C. Lock the tenant's `tenants` row | Use the tenant row as the chain's mutex | Rejected — it conflicts with the key share every insert in the tenant takes |
| D. A unique `(tenant_id, previous_hash)` and a retry | The database refuses a fork, and `record` retries | Rejected for `v1.0.0` — its index cannot be built on a chain that already forked |
| E. `SERIALIZABLE` and a retry | PostgreSQL aborts one of two conflicting appends | Rejected — it detects and retries where A waits, and nothing else in the tree runs at that level |
| F. A mutex in the process | Serialise appends inside one backend | Rejected — it does not hold across two backends, which row 6 runs |
| G. Chain by link, not by time | Keep the race, and make the verifier follow `previous_hash` | Rejected — a fork is still a fork |

### A. A per-tenant advisory lock, and a time never before the head's — chosen

The lock is held from just before the read until the commit just after the insert. Two writers for one tenant therefore append one after the other, and the second reads the first's row as its head. Writers for different tenants take different keys and never wait on each other. If two tenants' UUIDs hash to the same `hashtext`, the only cost is that those two wait on each other more than they need to; no wrong result is possible.

The lock needs no privilege `kelir_app` lacks, no migration and no new table. It is the idiom the tenant-code and hierarchy locks already use, with a class of its own.

The clamp fixes the clock-skew case. The verifier walks rows by `created_at, id`, and a row's time is now strictly later than its head's. So walk order is chain order whatever each backend's clock says, and the plus-one microsecond keeps a tie from falling back to the `id` order of two UUIDv7s from two hosts.

The cost of the clamp: under skew, a row's recorded time can be later than the moment it was written, by at most the skew between the backends. A row is never earlier than one before it, which is the property a reader of the trail relies on.

**What it does not solve.** Forks stored before it, and the reordering between commit and audit that #995's *Also seen* describes.

### B. Lock the head row `FOR UPDATE`

This would lock exactly the row being contended, with no new constant. But `SELECT … FOR UPDATE` needs `UPDATE` privilege on the table, and ADR-0051 gives `kelir_app` only `SELECT` and `INSERT` on `audit_events` on purpose. Granting `UPDATE` back to lock a row would weaken the posture ADR-0051 built for NFR-SEC-006, even with the trigger still refusing rewrites. There is also nothing to lock when a tenant's chain is empty, so two first writes would still race at the genesis hash.

### C. Lock the tenant's `tenants` row

The row exists before any audit row, so there is no empty-chain case, and no new lock class is needed. But `FOR UPDATE` on that row conflicts with the `FOR KEY SHARE` every insert into a table referencing `tenants` takes. Every audit append would wait on every open write transaction in the tenant, and every such transaction would wait on audits. `FOR NO KEY UPDATE` avoids that conflict, but it ties the chain's lock to tenant edits and deletes, which take the row for their own reasons. So the audit lock would join a lock order it has no business in.

### D. A unique `(tenant_id, previous_hash)` and a retry

This is the strongest guarantee: the database itself refuses a second child of one row, whatever writes it, including a writer that bypasses `record`. It costs a migration and a retry loop in `record` on `23505`.

**What rules it out for `v1.0.0` is the stored data.** A deployment that ran an earlier version under concurrent writes may already hold a fork, and then `CREATE UNIQUE INDEX` fails and the upgrade stops at that migration. Making it safe means deciding what a stored fork becomes, by re-chaining or by exempting rows, and §2 leaves that question open. It is §6's first trigger.

### E. `SERIALIZABLE` and a retry

Two appends that read the same head and each insert a row the other's read would have seen form a read-write dependency cycle. PostgreSQL's serializable isolation aborts one of them with `40001`, and `record` would retry it. This needs no lock class. It is still a retry loop, though: under contention on a one-tenant deployment, the cost is aborted work and retries where A costs a short wait. Its correctness rests on predicate locking over the index scan, which is harder to show in a test than a lock a test can hold. Nothing else in the tree runs at that level, so it would be the one place a reader had to reason about it.

### F. A mutex in the process

A `tokio::sync::Mutex` per tenant would need no database round trip. It serialises only one process, though, and `v1.0.0` runs two backends (row 6, [#989](https://github.com/sujanto-gaws/kelir/issues/989)) with a scan worker in each. It would also do nothing for the clock-skew case.

### G. Chain by link, not by time

The verifier could walk `previous_hash` links from the genesis hash instead of sorting by `created_at`. That makes clock skew harmless with no change to `record`. But a fork is still a node with two children, which a link walk reports as plainly as a time walk does. G fixes the walk, not the chain. It may still be the better verifier when one ships, and that is left open.

## 4. Consequences

**Positive.**

- Concurrent audited writes in one tenant no longer fork its chain, so `chain_breaks` reports only a real break, and NFR-SEC-006's detection claim holds without the caveat D-157 C would have written.
- Clock skew between backends no longer breaks the walk.
- No caller changes, no migration, no grant, and no stored row is touched.

**Negative.**

- **One tenant's audit writes now run one at a time**, across every backend and the scan worker. On a one-tenant deployment that is every audit write in the deployment. Each holds the lock for one indexed read, one insert and a commit. The throughput cost is not yet measured; row 19's load test on the release images is where it first shows.
- **The commit happens with the lock held**, so a slow commit makes every waiting writer in the tenant wait too.
- **A request now waits for other requests' audits.** Because audits are written after the commit, that wait adds latency to the response, not to the audited change.
- **A rule a compiler cannot check.** Never awaiting `record` with a transaction open (§2) is held by reading each call site, not by a type.
- **A waiting writer holds a pooled connection.** `record` checks its connection out before it takes the lock, so a burst of audited writes for one tenant can fill the pool with waiters, and requests that write no audit row queue behind them or reach the pool's acquire timeout.
- **A row's time can be later than when it was written**, by up to the clock skew between backends, because of the clamp.
- **Stored forks stay.** A deployment upgrading from `v0.9.0` keeps any fork it already has, and its verification keeps reporting it as a break.
- **A fourth advisory lock class.** Classes are chosen by convention only, so nothing yet stops two modules picking the same one.

**Neutral.** `record` now holds one pooled connection for its whole transaction, where before it checked one out for each statement. A new constant, `AUDIT_CHAIN_LOCK_CLASS`, sits next to the other lock classes.

## 5. Compliance

- **The staged race** (#995's reproduction, turned around). `tests/common/gate.rs`'s `ReadGate` stops the first writer after it holds the lock. The test shows that a second writer for the same tenant waits on the lock, that a writer for another tenant does not, and that once both are released `chain_breaks` reports nothing. Seen red against the unlocked `record` first. The gate stops only a plain `SELECT` that its predicate matches, so the test needs an existing head row, and it works inside `record`'s transaction because taking an advisory lock assigns no transaction id.
- **The clamp.** A head row is written as the owner with a `created_at` in the future. The next `record` writes a row strictly after it, and the chain verifies.
- **A burst.** N concurrent `record` calls for one tenant, from two pools standing in for two backends, leave a chain with no break. This is not deterministic on its own; the staged race is what proves the lock, and the burst is what would notice a path that skips it.
- **The rule on transactions.** No mechanical check exists. Row 37's build reads every call site and its review checks it. A reviewer of any later call site checks that nothing awaits `record` before the caller's transaction commits or rolls back.

## 6. Revisit When

- **A decision is taken on forks already stored**, by re-chaining or by exempting rows. Then D's unique constraint becomes buildable and should join the lock as the database's own refusal.
- **A load test on the release images, row 19's or a later one, shows waits on `AUDIT_CHAIN_LOCK_CLASS`, or pool acquire waits behind them, as a visible share of a request's p95.** Then the lock is the bottleneck, and the chain's shape (for example, more than one chain per tenant) is the question.
