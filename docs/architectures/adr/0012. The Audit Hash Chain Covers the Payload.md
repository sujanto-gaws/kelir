# ADR-0012 — The Audit Hash Chain Covers the Payload

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-26 · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** `D-20`, [ADR-0011](0011.%20A%20Derived%20Surface%20Requires%20the%20Permission%20of%20What%20It%20Derives%20From.md)

## 1. Context

**Recorded retrospectively on 2026-09-01** from `D-20` in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1; the operative statement is [Database Schema](../../design/02.%20Database%20Schema.md) §10.2 (standard §9).

FR-AUD-003 requires an append-only, hash-chained audit trail. As built, `chain_hash` covered ten inputs and **neither audit payload column was among them**, nor `created_at` — so what a record *says it changed* could be rewritten without disturbing any hash, and the chain still verified (#145).

Adding fields invalidates every chain computed without them, and no row carried a format version. The question was whether to change the format now or design a version stamp for later.

## 2. Decision

**Change the format now, and change it once: the hash covers the payload columns and `created_at`, with all fields length-prefixed.** No version stamp.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Change the format now, length-prefixed** | One break, taken while it is free | **Chosen** |
| B. Stamp a format version on every row, leave old rows outside payload coverage | The compatible-looking option | Rejected — buys nothing while no verifier exists, costs a branch in every future verifier |
| C. Defer to Phase 6, with verification | Do it when it is needed | Rejected — turns a free change into a re-chaining migration plus a decision about what a pre-version row means |

### A. Now, and once — chosen

Nothing verifies a chain today: FR-AUD-003's verification is Phase 6, no release has ever checked one, and the `previous_hash`/`current_hash` values in existing databases have never been read by anything. So today it is a code change with **no data consequence**. Because the break is only free once, the field framing was fixed in the same change: fields are **length-prefixed**, so a boundary between two of them cannot be moved.

### B and C

Both trade a free change for a permanent one. The version stamp in particular is a branch in code that does not exist yet, guarding rows nothing has read.

## 4. Consequences

**Positive** — the chain covers what an auditor cares about: what changed, not only that something did. Length prefixing closes the boundary-shifting class of attack before any verifier is written.

**Negative** — chains computed by earlier code do not verify under the new format. That cost is zero today and would not have been after Phase 6, which is the whole argument.

**Neutral** — the correction landed as `0019_audit_hash_covers_the_payload.sql`, because **a merged migration is never edited**; it rewrites the column comments that `0003_audit.sql` had set. `0022` later made the hash tell an absent value from an empty one — a defect in what was hashed, not in whether it was.

## 5. Compliance

`tests/audit_hash_chain.rs` holds the chain. The doc comment on `modules::audit::record` states the field order and the length prefixing; a verifier written later reads that as its specification.

## 6. Revisit When

The verifier lands (FR-AUD-003, Phase 6) and needs a format change — which is the moment a version stamp stops being speculative, because from then on a change costs a re-chaining migration.
