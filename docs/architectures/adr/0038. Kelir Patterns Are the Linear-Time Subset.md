# ADR-0038 — Kelir Patterns Are the Linear-Time Subset

**Status:** Adopted · **Last updated:** 2026-09-09

**Decision date:** 2026-09-09 · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** [ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md), [ADR-0016](0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md), [ADR-0028](0028.%20A%20Definition%20Is%20Refused%20at%20Save%20Rather%20Than%20at%20Render.md), [ADR-0035](0035.%20Rules%20Are%20Resolved%20Before%20a%20Form%20Is%20Published.md), `D-15`, FR-RAD-006, issues [#391](https://github.com/sujanto-gaws/kelir/issues/391) and [#393](https://github.com/sujanto-gaws/kelir/issues/393)

## 1. Context

**The [Validation Rule Registry](../../schema/JFSS%20Validation%20Rule%20Registry.md)'s `regex` rule promises a dialect Kelir cannot deliver.** Its params schema says *"ECMA 262 regex"*, the rule is scoped `both`, and the Rust `regex` crate is not an ECMA-262 engine. The [operator-parity spike](../../../projects/spikes/01.%20JFSS%20Operator%20Parity.md) §2.7 measured the gap on 2026-08-21, and it has two halves that fail in opposite ways:

- **Lookahead and backreferences fail loudly.** The crate rejects them at compile time by design, so a password-complexity pattern — the commonest custom `regex` rule there is — cannot be built at all.
- **Character classes fail silently.** ECMA-262's `\d` is ASCII; this crate's is Unicode `Nd`. The same rule rejects Arabic-Indic digits in the browser and accepts them on the server, with no error raised on either side. For a `both`-scoped rule that is two runtimes reaching opposite verdicts on one input, which is exactly what the registry's own §1 Semantic Parity requirement exists to forbid.

**The loud half was worse than it looked.** `rad::domain::validation::matches_pattern` maps a compile error to `false`, on [ADR-0016](0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md)'s reasoning — a rule that could not be applied has not been satisfied. That is right at submit and it meant an uncompilable pattern **stored happily and then rejected every value**, with nothing naming the pattern: a field nobody could fill, in a form that had already been published.

The registry has carried interim guidance since 1.2.0 — *prefer a plainly ASCII, non-lookahead pattern, and pin digit classes explicitly* — and named two candidate resolutions, both open for four sprints. `D-15` carried them from the spike through Sprints 14, 15 and 16.

## 2. Decision

**A Kelir pattern is what the `regex` crate compiles, with character classes written out, and a definition carrying anything else is refused where it is written.**

Concretely: `PATTERN_NOT_COMPILABLE` for a pattern this backend cannot build, `PATTERN_CLASS_NOT_PINNED` for a bare `\d`, `\w` or `\s`, both through the [JFSS](../../schema/JSON%20Form%20Schema.md) S10.3 envelope, at the seam [ADR-0035](0035.%20Rules%20Are%20Resolved%20Before%20a%20Form%20Is%20Published.md) already refuses an unregistered rule name at, and both covering §5's `validation.pattern` keyword as well as the `regex` rule — one evaluator decides both.

**The linear-time guarantee is the thing being kept.** It is not a side effect of the library choice; it is the property that makes a tenant-authored pattern safe to run on the server at all.

## 3. Options Considered

### A. Constrain the dialect and refuse at the write — chosen

The registry's first candidate. Keeps `regex`'s linear-time matching, ends the field nobody can fill, and closes the silent half — which **no engine choice closes**, because it is a semantic divergence rather than a capability gap.

It narrows what an author may write, and the narrowing is real: see §4.

### B. Adopt `fancy-regex` on the backend

The registry's second candidate. It restores lookahead and backreferences by adopting **backtracking**, and that is the objection: a pattern in Kelir is written by a tenant's configuration author and stored, so a catastrophically backtracking pattern becomes a denial of service reachable from a form definition. The exposure is not hypothetical for this shape of product — the input is attacker-influenced by design, because configuring forms is the product.

**Rejected on the NFR rather than on the capability.** It would also have left the `\d` divergence needing an explicit pin either way, so it buys expressiveness and pays for it in availability without closing the half that fails silently.

### C. Leave the guidance as guidance

The status quo for four sprints. Rejected because guidance that the server does not enforce is a rule the next author does not know about, and because the loud half was a live defect rather than a style preference.

### D. Refuse only the uncompilable half

Tempting — it is the live defect and the smaller change. Rejected because the silent half is the one Semantic Parity is about, and because the save is the only place it can be caught: both engines compile `\d` happily and disagree afterwards.

### E. Change the registry to promise the Rust dialect instead

Honest about what runs, and rejected because the frontend really is an ECMA-262 engine. Renaming the promise would move the divergence rather than close it, and would leave the browser free to accept a pattern the server refuses.

## 4. Consequences

**Kelir patterns carry no lookahead and no backreferences.** So **server-side password complexity is several rules rather than one** — a `minLength` and one pinned pattern per requirement, instead of a single expression with lookaheads. That is the cost, and it is paid by the author of a form rather than by the person filling it in.

**`passwordStrength` does not cover the gap.** Its own Rust note says the backend ignores it and relies on `validation.minLength` and `validation.pattern` — the keyword this decision constrains — so the registry states the limit where an author meets it rather than leaving the rule to imply a server-side guarantee it never had.

**A definition stored before this check keeps whatever it was stored with**, exactly as [ADR-0035](0035.%20Rules%20Are%20Resolved%20Before%20a%20Form%20Is%20Published.md) found for rule names: the refusal runs at the write and again at the publish, so a draft is caught when it next moves, and a *published* revision is immutable and is not reopened.

**The evaluator's behaviour is unchanged.** An uncompilable pattern still fails closed at submit ([ADR-0016](0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md)); what changes is that one can no longer be stored, so the evaluator's arm becomes unreachable through the API rather than wrong.

## 5. Compliance

`rad::domain::engine::check_patterns` raises both codes; `rad::domain::validation::refuse_pattern` is where the dialect is defined, beside the `compile_pattern` the evaluator itself uses — so the check and the evaluation cannot disagree about what compiles.

Five unit tests in `rad::domain::engine` and one integration test in `rad_forms.rs` cover the refusal at the endpoint, each with a second subject: a pattern this backend compiles, beside the one it does not, so *refused because uncompilable* can be told from *refused at all*.

**Seen to fail** (coding standard §2.9), 2026-09-09: removing the `check_patterns` call reddens all five; `refuse_pattern` skipping its compile check reddens the four about compiling and leaves the class one green; `unpinned_class` never matching reddens only the class one.

## 6. Revisit When

**A linear-time engine gains lookahead.** The objection to `fancy-regex` is backtracking, not lookahead — an engine offering the second without the first would reopen option B on its merits.

**A deployment needs a pattern this subset cannot express, and says which.** The narrowing in §4 is stated so that it can be argued with; the case that would move this decision is a real rule that cannot be written as several, not the inconvenience of writing several.

**The frontend stops being an ECMA-262 engine.** Option E is rejected because the browser really is one. If the renderer's evaluator changed, the divergence would change shape and this record would need re-reading rather than re-applying.
