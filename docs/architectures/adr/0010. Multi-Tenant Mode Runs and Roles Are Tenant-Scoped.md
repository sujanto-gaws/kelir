# ADR-0010 — Multi-Tenant Mode Runs and Roles Are Tenant-Scoped

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-25 · **Deciders:** Product owner · **Supersedes:** [ADR-0009](0009.%20Per-Request%20Tenancy%20Deferred%20Past%201.0.md) · **Superseded by:** — · **Related:** `D-18`, `D-13`, `D-17`

## 1. Context

**Recorded retrospectively on 2026-09-01** from `D-18` in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1, which holds the full reasoning and remains operative (standard §9).

[ADR-0009](0009.%20Per-Request%20Tenancy%20Deferred%20Past%201.0.md) deferred per-request tenancy and left three faces of one seam open: FR-ORG-001 (#27) had no surface, because a surface would create tenants nobody can sign in to; #65 asked whether roles are tenant-scoped or global and could not be answered without the tenancy model; and `KELIR_MULTI_TENANT` refused to start a deployment at all. `D-13` and `D-17` each declined to schedule that work, both naming the same return condition: *the decision that supersedes D-7*. This is that decision, taken at the product owner's direction rather than at a sprint boundary.

## 2. Decision

**Multi-tenant mode runs, and the three faces close together. The transport is the sign-in body field, roles are tenant-scoped, and creating a tenant creates its first administrator in the same transaction.** Tenant administration is performed only from the deployment's default tenant.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Sign-in body field + `GET /deployment` + tenant-scoped roles + atomic create** | Uses a contract that already shipped | **Chosen** |
| B. Subdomain or header transport | The conventional tenancy transports | Rejected — a subdomain needs wildcard DNS and TLS; a header carries the same trust as a body field while being invisible to every generated client |
| C. Roles global (#65 option 1) | One catalogue of roles for the deployment | Rejected — contradicts `roles.tenant_id`; a tenant administrator's new role would be visible to every tenant |
| D. Roles scoped with shared system roles (#65 option 3) | A middle path | Rejected — needs a rule for a tenant editing a shared row, and buys nothing once provisioning exists |
| E. Drop `KELIR_MULTI_TENANT`, always resolve per request | Simpler configuration | Rejected — would let a caller on a single-tenant deployment name somebody else's tenant |
| F. Two-call create (tenant, then user) | Ordinary REST shape | Rejected — puts "rows nobody can sign in to" back within reach of any client that makes the first call and not the second |

### A. The chosen shape

`SignInRequest.tenantCode` shipped in Sprint 4 and is in the published contract, so the transport already existed. **What was missing was the client's half** — #67's original question — and `GET /deployment` answers it, unauthenticated, because the login form needs the answer before it has credentials. A build-time `VITE_` flag was rejected: the frontend image bakes only a *relative* API base, so one build serves every deployment, and a build-time tenancy flag would end that. The login form also reveals its tenant field on a `tenantCode` validation detail, so a deployment that cannot be probed costs one attempt rather than locking anyone out.

**Roles are tenant-scoped** (#65 answered): every tenant has its own `ROLE-ADMIN` — `uq_roles_tenant_id_role_code` is per tenant, so these are different rows — the permission catalogue stays global, and `roles_of_user`, `permissions_for_user` and `role_codes_for_user` gained the `tenant_id` filter their siblings already had. `0017_tenant_administration.sql` makes the old shape unwritable rather than merely unwritten.

**The boundary that makes tenant-scoped roles safe** is that tenant administration happens only from the default tenant. Withholding `organization:tenant:*` from a provisioned tenant's role is defence in depth, not the boundary — that tenant's administrator holds `identity:role:update` and could grant themselves any code in a global catalogue.

### E. Always resolving per request

The flag-off path ignoring a supplied tenant code is a **security property, not a legacy**.

## 4. Consequences

**Positive** — one decision closes #27, #65 and #67; a created tenant is one somebody can sign in to, by the endpoint's shape rather than by a client's diligence.

**Negative** — tenant administration is now a privileged surface confined to the default tenant, which is a boundary every future administrative feature has to respect. The `KELIR_MULTI_TENANT` flag stays, so two paths exist through sign-in.

**Neutral** — this is the return condition `D-13` and `D-17` were waiting on, so both are discharged.

## 5. Compliance

`0017_tenant_administration.sql` makes the pre-decision shape unwritable at the schema level; the tenant-scoped read helpers carry the `tenant_id` filter, and the identity integration tests hold the boundary.

## 6. Revisit When

A deployment needs cross-tenant administration from somewhere other than the default tenant, or a tenant transport other than the sign-in field becomes necessary (a genuinely white-labelled subdomain, say) — at which point the wildcard DNS and TLS cost is being paid for a different reason.
