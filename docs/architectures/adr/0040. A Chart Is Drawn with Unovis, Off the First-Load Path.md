# ADR-0040 — A chart is drawn with Unovis, off the first-load path

**Status:** Adopted · **Last updated:** 2026-09-14

**Decision date:** 2026-09-14 · **Deciders:** product owner, at Sprint 18 item 5 · **Supersedes:** — · **Superseded by:** — · **Related:** [ADR-0039](0039.%20A%20Dashboard%20Widget%20Is%20a%20Purpose-Built%20Endpoint.md), [ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md), **D-10**, **D-82**, FR-RPT-004, FR-RPT-006, [#447](https://github.com/sujanto-gaws/kelir/issues/447)

## 1. Context

**FR-RPT-004 — *the system shall show document status summary*, [SRS](../../requirements/srs.md) §4.14, `Should` — is the first surface in the tree that needs a chart, and the tree has no charting library.** `kelir-frontend/package.json` carries the JSON Logic evaluator, Axios, Pinia, Vue Router, Lucide and shadcn-vue's class helpers, and nothing that draws.

What the widget has to show is small and fixed:

| Fact | Where it comes from |
|---|---|
| One series of ten counts, one per `DocumentStatus`, in lifecycle order | The summary contract, extended rather than bypassed ([ADR-0039](0039.%20A%20Dashboard%20Widget%20Is%20a%20Purpose-Built%20Endpoint.md)) |
| The documents **the caller raised**, not every document they can see | #447 |
| Behind `reporting:dashboard:read`, unchanged | ADR-0039's one permission |

Four constraints bound the choice:

- **The dashboard is the home route.** `/` is where every session lands, so anything the page imports statically is fetched by every sign-in. The router lazy-loads the page, but `AppLayout.vue` and `DashboardPage.vue` are on the first-load path in every sense that matters to a user.
- **There is a precedent, with a condition attached.** **D-10** ([ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md)) took a heavy dependency on the terms that it stays off the first-load path, and `scripts/check-bundle-split.mjs` runs in CI to hold it there. That script walked the chunk graph from the entry alone.
- **The UI kit is shadcn-vue** (`kelir-frontend/components.json`), whose charting layer is Unovis. Its chart scaffolding depends on `@vueuse/core` and `reka-ui`, and the tree carries neither.
- **The frontend is type-checked with `vue-tsc --noEmit` under `strict` in CI, declaration files included.** `tsconfig.json`'s `ESNext.Disposable` entry exists because the evaluator's own declarations once failed that check.

Component specs run in jsdom (`vite.config.ts`), which lays out nothing and draws nothing, so a chart is invisible to them however it is drawn.

## 2. Decision

**Kelir draws charts with Unovis — `@unovis/vue` and `@unovis/ts`, pinned together at exactly `1.7.0` — used directly rather than through shadcn-vue's chart scaffolding, and reached only through a component the page loads with `defineAsyncComponent`, so the library is never on the first-load path. `vue-tsc` runs with `skipLibCheck: true`, because no Unovis release tried ships declarations that compile.** This covers FR-RPT-004's chart and whatever chart surface follows it. The component lives in `features/dashboard` while there is one chart; a second chart surface is when it moves to `components/ui`. The chart is `aria-hidden` and the counts it draws are also on the page as text, so a failed chunk leaves every number on screen. **It decides nothing about FR-RPT-006's shape**, which is Sprint 19's and is §6's first trigger.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| A. No library | Horizontal bars as Tailwind widths in a labelled list | Rejected — **the recommendation put to the product owner**, and not the decision |
| **B. Unovis** | `@unovis/vue` + `@unovis/ts`: SVG, drawn with d3, and shadcn-vue's charting layer | **Chosen** |
| C. Chart.js + vue-chartjs | A canvas chart behind a Vue wrapper | Rejected — not the UI kit's charting layer, and a canvas is opaque to everything but the eye |

### A. No library

**This was the recommendation, and it lost to a decision rather than to an argument about its weaknesses.** The coordinating session put it first because it adds nothing: no dependency, no chunk, nothing new for `check-bundle-split.mjs` to guard and no declaration files to compile. Ten counts in one series are within reach of a `<ul>` with a width per row, and the bars would have been the text, so there would have been no second rendering for a screen reader and nothing a spec could not read.

What it does not provide is everything a chart library is for: scales, axes, ticks and a shape other than a bar. Each later chart would be built by hand, and FR-RPT-006 is the next candidate. **The product owner's stated reason for B is that it fits the existing UI kit's charting layer, and A has no charting layer to fit.** This record does not add a reason the product owner did not give.

### B. Unovis — chosen

Chosen by the product owner as **the charting layer of the UI kit Kelir already uses**. The costs were stated at the time and measured when it was built:

| | Before (`main`) | After |
|---|---|---|
| Chart chunk | none | 162.65 kB raw / 54.99 kB gzip, loaded only when the card renders |
| Entry chunk | 168.69 kB / 63.77 kB | 168.89 kB / 63.84 kB |
| First load for `/` | 1106.80 kB raw / 233.16 kB gzip, 9 chunks | 1109.84 kB / 234.14 kB, 10 chunks |
| Lockfile entries | 384 | 557 — **+173**, none dev or optional |

The chunk carries `@unovis/ts`, `@unovis/vue`, twelve `d3-*` packages, `@emotion/*`, `stylis`, `internmap`, `@juggle/resize-observer` and `throttle-debounce`. Leaflet, maplibre, three and elkjs are in the lockfile and tree-shaken out of the build. **Of the +1.0 kB gzip on first load, 0.65 kB raw is a shared chunk holding the status labels**, which both the page and the chart import.

**It is used without shadcn-vue's scaffolding**, because that scaffolding would have added `@vueuse/core` and `reka-ui` for one chart. So what B keeps from *fits the UI kit* is the library, not the wrapper: `DocumentStatusChart.vue` composes `VisXYContainer`, `VisGroupedBar` and `VisAxis` itself and points Unovis's CSS variables at the theme's tokens.

**What it does not solve is accessibility or testability.** Unovis sizes its SVG with a `ResizeObserver` and draws nothing in jsdom, so the chart is `aria-hidden`, the ten counts are rendered as text in server order, and the specs read the text. That is the same text alternative C would have needed, paid here too.

### C. Chart.js + vue-chartjs

It would have bought a widely used library with a small Vue wrapper. **What ruled it out is that it is not the UI kit's charting layer**, which was the deciding force. It is also a canvas, so what it draws is not in the DOM at all and has to be restated as text. §3 B records that B needed the text alternative as well, so **that cost did not end up distinguishing the two** as much as it appeared to when the options were put. No bundle measurement was taken for C, and this record does not estimate one.

### B's type-check cost — decided separately

**Every Unovis release tried fails `vue-tsc` inside its own declaration files, with 0 errors in `src/`.** The product owner decided this after B was chosen, as a separate choice with its own options.

| Version | Errors | Fault |
|---|---|---|
| 1.7.0, latest, published 2026-09-10 | 168 | `__VLS_*` helpers left in the shipped `.d.ts` |
| 1.6.7 | 150 | The same fault, so it is not a 1.7.0 regression |
| 1.5.2 | 24 | `@unovis/vue`'s types import `@unovis/ts/dist/components/*/style` paths that are not shipped |

All three also carry a few `@unovis/ts` and `elkjs` errors. **Older releases were not smaller either** — 565 and 567 lockfile entries, pulling in a maplibre-gl 2.x tree — so pinning back would have bought nothing on size.

| Option | Verdict |
|---|---|
| **(i) `skipLibCheck: true`** | **Chosen** |
| (ii) A tsconfig `paths` redirect to hand-written declarations for the three components and two enums used | Rejected — it can drift from the pinned version, and every new chart surface must extend it |
| (iii) Drop Unovis for option A | Rejected — it reverses the library decision to repair a type-check |

**The cost of (i), stated plainly: TypeScript no longer checks any declaration file** — the evaluator's, every other package's, and any `.d.ts` in `src/`. Our `.ts` and `.vue` sources are still checked in full under `strict`. What is lost is the check that a declaration file is internally consistent, not the check that our code uses it correctly.

## 4. Consequences

**Positive** — The dashboard has a chart with axes and a scale, drawn by the library shadcn-vue's charts draw with, so adopting that scaffolding later is a change of wrapper rather than of library. **The chart costs a session that never scrolls to it 1.0 kB gzipped**; the 54.99 kB chunk is fetched only when the card renders. Extending the bundle guard also strengthened D-10's half of it: a walk from the entry alone was blind to a static import in any router-lazy page on `/`, for the evaluator as much as for Unovis, and it now starts from the home route's chunks too.

**Negative** — **173 new lockfile entries**, and a chunk carrying twelve d3 packages, for one series of ten bars; A would have added none. **No declaration file is type-checked**, and a `.d.ts` written in `src/` is now trusted rather than verified — [coding standard](../../standards/01.%20Coding%20Standard.md) §3.1 says so. The bundle guard gained moving parts: a Vite plugin that writes `dist/.vite/chunk-packages.json`, because the manifest does not name Unovis, and a `HOME_ROUTE` list in the script that has to move when the home route does. Both Unovis packages are pinned exactly, so every upgrade is a deliberate change that re-measures the chunk and re-runs the type-check. The card states its numbers twice, once drawn and once as text.

**Neutral** — `DocumentStatusChart.vue` lives in `features/dashboard`, beside the only page that uses it, not in `components/ui`, which holds shadcn-vue's generated primitives. `tsconfig.json`'s `skipLibCheck` comment names this record. `DashboardPage.chart-failure.spec.ts` is a spec shape the dashboard did not have: a lazily loaded component whose chunk fails.

## 5. Compliance

**`npm run check:bundle`, run in CI's frontend job after the build, is what a violation fails.** For `@unovis/ts` and `@unovis/vue` it fails when:

1. no chunk off the first-load path carries the library — a static import has folded it into a first-load chunk;
2. any first-load chunk carries it; or
3. any first-load chunk carries its assets.

*First load* is the entry plus `AppLayout.vue` and `DashboardPage.vue`, followed through static imports only. **Seen to fail, 2026-09-14:** with a static `@unovis/vue` import reintroduced in `DashboardPage.vue`, the check went red with *"the Unovis chart library has no chunk of its own…"*. It went green again when the import was removed. The same mutation had passed against the earlier walk from the entry alone, which is why the walk changed.

**What it does not guard** is a static Unovis import on a page other than `/`. That page is still router-lazy and off first load, so this decision permits it.

**`DashboardPage.chart-failure.spec.ts`** covers the other half of the decision: when the chart's chunk fails to load, the card says so and the counts stay on screen.

**No check enforces the exact pin**, so it is a reviewer's line: **a `^` or `~` on either `@unovis/*` package, or the two packages at different versions, is this record being relaxed.** An upgrade re-runs `type-check` and `check:bundle` and re-measures the chunk against §3 B's table. **Removing `skipLibCheck` without a Unovis release that compiles fails `npm run type-check`**, which is the check working as intended.

## 6. Revisit When

- **A Unovis release ships declarations that compile.** `skipLibCheck` comes out in that upgrade; the `tsconfig.json` comment names this record so the upgrade finds it. This reverses §3's type-check decision, not the library decision.
- **FR-RPT-006, the approval time report in Sprint 19, needs a chart shape Unovis cannot serve, or one option A's approach serves well.** It is the second chart Kelir will draw and the first test of whether a library was needed; if it is served by widths in a list, B's weight is paying for one chart.
- **The chart chunk's gzip size grows materially on an upgrade**, measured against §3 B's 54.99 kB, **or a chart lands on a first-load route** in a way `check:bundle` does not cover.
- *A note, not a reversal:* **a second chart surface** is when `DocumentStatusChart.vue`'s pattern is promoted to `components/ui`, and whether shadcn-vue's scaffolding is then worth `@vueuse/core` and `reka-ui` is a question for that change.
