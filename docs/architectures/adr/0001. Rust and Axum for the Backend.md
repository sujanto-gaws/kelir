# ADR-0001 — Rust and Axum for the Backend

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-04 (founding) · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** [ADR-0002](0002.%20SQLx%20with%20Compile-Time%20Verified%20Queries.md), [ADR-0003](0003.%20PostgreSQL%20as%20the%20Only%20Database.md), [ADR-0004](0004.%20A%20Modular%20Monolith%20with%20a%20Flat%20Module%20Layout.md), `D-11`

## 1. Context

**Recorded retrospectively on 2026-09-01** from [architectures/01](../01.%20Basic%20Framework%20Concept%20and%20Architecture.md) §29 Decision 1 and from `D-11` in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1, which is where this decision was actually taken and where the operative statement remains (standard §9).

Kelir is a document-centric framework whose backend carries a workflow engine, a rule evaluator that must agree with a browser, and an audit trail that is expected to be tamper-evident. The founding pass chose the language and the web framework before any module existed.

A second force arrived later and is part of this record because it settled the same question: the JSON standards family had been written for **two** backend languages. The JFSS target stack read "Golang / Rust", both matrices in the Calculation Rule Registry carried a Go column, and the Validation Rule Registry carried `Go/Rust` implementation notes throughout. No Go service existed, none was planned, and nothing in the repository compiled Go. The [operator-parity spike](../../../projects/spikes/01.%20JFSS%20Operator%20Parity.md) §2.8 named the mechanism behind a worse problem: three columns of support ticks, none of them checked by any build — which is how the Rust column came to name a crate that does not exist.

## 2. Decision

**Kelir's backend is Rust, and its HTTP surface is Axum.** One backend language, stated as one in the code and in every specification that describes it: the standards family describes a Rust implementation and nothing else.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Rust + Axum, one backend language** | Async, Tower middleware, strong type guarantees | **Chosen** |
| B. A Go backend, or a Go service beside Rust | What the JFSS family's Go column implied | Rejected — no Go exists, and an unverifiable claim in an Active Standard is worse than an absent one |
| C. Keep the Go column "in case" | Documentation-only hedge | Rejected — the registry naming a nonexistent crate is the proof of what an unchecked claim costs |

### A. Rust + Axum — chosen

Axum was chosen for being modern and async, for the Tower middleware ecosystem, and for suiting REST APIs (architectures/01 §29). The founding record does not name a rejected web framework, and this retrofit does not invent one — see §7 of the standard on why a reconstructed alternative would be fiction.

### B. A second backend language

`D-11` (2026-08-21) closed it. Every Go reference was converted or removed across three documents: the Calculation Rule Registry dropped the Go column from both matrices and deleted the Go `sum` and `map` sections (v1.4.0), the Validation Rule Registry converted every `Go/Rust` note to concrete Rust (v1.3.0), and JFSS took it as errata E-1 rather than a version bump, being a Final Standard.

### C. Keeping the hedge

Rejected on the ground that a support tick nobody can fail is not information. **Polyglot Parity is not weakened by this**: it was never a claim about the number of languages — one JavaScript runtime and one Rust runtime still meet at a boundary where a schema can mean two different things, and every mechanism guarding that boundary is unchanged ([ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md)).

## 4. Consequences

**Positive** — one toolchain, one dependency set, one place a rule is implemented on the server side. Every claim a specification makes about the backend is now checkable by a build.

**Negative** — Rust's compile times and its smaller hiring pool are accepted. A `both`-scoped rule needing a library the Rust ecosystem lacks becomes a real constraint rather than an inconvenience: `regex` had to be added as a dependency for exactly this reason (`D-28`), and the `regex` rule still cannot be honoured as specified by any Rust backend (`D-15`, open).

**Neutral** — the Validation Rule Registry gained a **Semantic Parity** requirement in §1.1: for a `scope: "both"` rule the two implementations must agree on the edge cases.

## 5. Compliance

The build is the check: nothing in the repository compiles Go, and CI runs `cargo fmt`, `clippy` and the backend test suite. A specification claiming backend support is verifiable only if a build can fail on it — the rule `D-11` drew from the nonexistent-crate incident.

## 6. Revisit When

A requirement arrives that Rust cannot serve within the parity constraint — a `both`-scoped rule needing a library with no Rust equivalent and no Semantic Parity story — or the plugin platform's sandboxing (architectures/04) needs a runtime the backend cannot host in-process.
