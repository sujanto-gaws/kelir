# ADR-0035 — Rules Are Resolved Before a Form Is Published

**Status:** Draft · **Last updated:** 2026-09-04

**Decision date:** — · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** [ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md), [ADR-0015](0015.%20Calculations%20Run%20Before%20Conditional%20Stripping.md), [ADR-0016](0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md), [ADR-0019](0019.%20A%20Workflow%20Definition%20Is%20Narrowed%20at%20Save%20Time.md), [ADR-0027](0027.%20A%20Document%20Pins%20the%20Form%20Revision%20It%20Was%20Filled%20Against.md), [ADR-0028](0028.%20A%20Definition%20Is%20Refused%20at%20Save%20Rather%20Than%20at%20Render.md), `D-2`, FR-RAD-006, issue [#338](https://github.com/sujanto-gaws/kelir/issues/338)

## 1. Context

**Kelir has evaluated JFSS rules since Sprint 7 and has never had an engine around the evaluator.** `rad::evaluator` takes one JSON Logic expression and a payload and answers what the expression computes ([ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md)); `rad::service::evaluation` re-runs every `calculate` on every write, which is [JFSS](../../schema/JSON%20Form%20Schema.md) S8.1's Tamper-Proof Pattern. FR-RAD-006 asks for the layer neither of those is: which rules run, in what order, and what a failure means. `D-2` reserved it for Phase 7 and three construction plans restated the boundary rather than crossing it.

Three things were true when Sprint 14 opened, and each lands on a different person:

- **The order was the author's.** `calculate` expressions ran in the order the definition declared them, repeated until the payload stopped moving. That converges for any acyclic definition, and JFSS §9.2 asks for topological order instead.
- **A cyclic definition was refused at *submit*, and named no field.** The repeated pass had a bound; exceeding it produced `CALCULATION_DID_NOT_SETTLE` against `definition` as a whole. JFSS S12.2 makes such a schema **invalid** — *"implementations MUST build the graph from every `{"var": ...}` reference in both properties and MUST reject a cyclic schema; authoring tools SHOULD surface the cycle before it is saved"* — so the specification's own answer is a refusal at authoring time, naming the loop.
- **A `rules[].rule` name outside the [Validation Rule Registry](../../schema/JFSS%20Validation%20Rule%20Registry.md) was refused at submit.** Correctly ([ADR-0016](0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md)), but against the person filling the form in, who cannot edit a definition — and by then the form had been published and used. The operator half of the same question was already answered at save ([ADR-0028](0028.%20A%20Definition%20Is%20Refused%20at%20Save%20Rather%20Than%20at%20Render.md)), so one document's rules were being resolved against two registries at two different moments.

**Publishing is a one-way door.** A published revision is immutable because documents pin the exact `rad_forms.id` they were created against ([ADR-0027](0027.%20A%20Document%20Pins%20the%20Form%20Revision%20It%20Was%20Filled%20Against.md)), so a definition that goes live wrong cannot be corrected in place — only superseded by a further revision, which the documents already written against the bad one will never see. Definition checks so far have run on the **write** (`create_form`, `update_form`) and never on the publish, which means a draft stored before a check existed keeps whatever it was stored with. Sprint 14's checks are exactly that case: every draft in every deployment predates them.

## 2. Decision

**Kelir resolves a form's rules when the form is written and again when it is published, over one dependency graph spanning both `calculate` and `conditional`.** `rad::domain::engine` builds a catalogue of every `data` component in a scope, resolves its `rules[].rule` names against the Validation Rule Registry and its expression operators against the Calculation Rule Registry, and topologically orders the scope from every `{"var": ...}` reference in **both** rule properties, per JFSS S12.2. An unresolvable name and a cycle are `ValidationDetail`s naming the rule or every field on the loop, raised by `validate_definition` — so they refuse the write — and `publish_form` re-runs `validate_definition` against the **stored** definition before flipping the status, so nothing goes through the one-way door unchecked. The submit path asks the same graph for the same order and maps the same cycle onto an S10.3 error, which is the only route left for a form published before this gate existed. **One asymmetry is deliberate and is part of the decision:** a reference from a component's `calculate` to its own key is a cycle, and a reference from its `conditional.logic` to its own key is not — S8.1 computes a field from the record, and S10.2 decides visibility against the complete payload snapshot ([ADR-0015](0015.%20Calculations%20Run%20Before%20Conditional%20Stripping.md)), so only the first is self-referential.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Resolve at write and re-check at publish, one graph over both properties** | The specification's own moment, with the one-way door guarded | **Chosen** |
| B. Resolve at write only | One gate, no duplicate work | Rejected — every draft that exists today predates the checks, and publish is where they go live |
| C. Keep the verdict at submit | No new gate at all; the code already refused | Rejected — refuses the wrong person at a moment when nothing can be fixed |
| D. Graph `calculate` only | Simpler, and matches what the evaluation order actually needs | Rejected — S12.2 says both, and a loop through a `conditional` makes the stored shape depend on evaluation order |
| E. Refuse a `conditional` self-reference too | Uniform: one rule for both properties | Rejected — `{"!!": {"var": "notes"}}` is an ordinary conditional, and refusing it would refuse working definitions |

### A. Write **and** publish, over one graph — chosen

**A definition is written once and rendered thousands of times** — [ADR-0028](0028.%20A%20Definition%20Is%20Refused%20at%20Save%20Rather%20Than%20at%20Render.md)'s argument, and this is the same discipline one moment later. Refusing at the write costs one round trip to the person who can fix it. The second gate at publish is not a duplicate of the first: it checks a *different artefact* — the definition as stored, which may have been written by an older build — at the moment that artefact becomes immutable. [ADR-0019](0019.%20A%20Workflow%20Definition%20Is%20Narrowed%20at%20Save%20Time.md) already made the same pairing for workflow definitions, which are "enforced when the definition is written and again at publish"; this brings forms into line with workflows rather than inventing a shape.

One graph rather than two walks is what makes *both registries* a single answer. The catalogue has to visit every `data` component to build the graph at all, so resolving the rule names on the same visit costs nothing and removes a second traversal that carried its own idea of JFSS §4.3.1's three container shapes — the duplication the specification warns about, and the way a rule comes to mean one thing per traversal.

**What it does not solve:** a form published before this gate existed. Those are reached only by the submit path, which now names the fields on the loop instead of reporting that a bound was exceeded.

### B. Resolve at the write only

Cheaper by one `validate_definition` call per publish, and defensible on the day the checks ship — every subsequent draft is written through the gate. It fails on the drafts that already exist. Nothing re-validates a stored definition, so a cyclic form authored last month publishes cleanly, documents pin it, and it can never be corrected in place. **The gate has to be at the door that only opens one way.**

### C. Keep the verdict at submit

This is what the code did, and for `RULE_NOT_REGISTERED` it did it correctly under [ADR-0016](0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md) — a rule that fails open is a rule that is not there, reported as a rule that passed. The objection is not the refusal but its audience: the person filling in the form cannot edit a definition, cannot see the loop, and gets a form that cannot be submitted at all with no route to anyone who can fix it. The submit-side refusal is kept as the second line rather than removed, because a definition published under an older build still has to fail safely.

### D. Graph `calculate` only

The evaluation order genuinely only needs the `calculate` edges: `conditional` is resolved once, after the calculations, against a snapshot ([ADR-0015](0015.%20Calculations%20Run%20Before%20Conditional%20Stripping.md)), so no conditional can feed a calculation. S12.2 nonetheless says both properties, and the reason is visible in the shape it catches: `grand_total` calculating from `approval_reason` while `approval_reason`'s `conditional` reads `grand_total` is a definition whose *stored* shape — which keys survive S10.2's stripping — depends on which expression ran first. That is not a wrong number; it is two different documents from one payload.

**The cost is stated rather than hidden:** the conditional edges also constrain the evaluation *order*, which they need not, so a definition whose only loop runs through a conditional is refused although its calculations could have been ordered. S12.2 calls that definition invalid, so the refusal is the specification's and not this graph's.

### E. Refuse a `conditional` self-reference

The uniform rule, and it refuses `{"conditional": {"action": "show", "logic": {"!!": {"var": "notes"}}}}` — show this field when it has a value — which is an ordinary and useful conditional. S10.2 evaluates visibility against the complete payload with S8.1's overwrite already applied, so a component reading its own value there is reading a settled number, not its own output. The asymmetry is a property of the two specifications, not a special case in the graph.

## 4. Consequences

**Positive** — a cyclic definition and an unregistered rule name are refused where they can be fixed, naming the rule or every field on the loop; calculations run in one pass in dependency order instead of up to `n + 1` passes over the whole scope; the two registries are resolved on one walk of the tree, so they cannot disagree about which components exist; and a stored definition is checked at the moment it becomes immutable.

**Negative** — `publish_form` now does the meta-schema, engine and lookup work on every publish, which is one extra full walk of the definition on a rare endpoint. A definition already published and cyclic cannot be corrected in place, and this ADR does not reach it — it is refused at submit, which is a form nobody can fill in until a new revision is published. The `{"var": ""}` case is treated as a reference to every key in the scope, which makes a `calculate` reading the whole record a self-cycle; that is a judgement about an exotic expression rather than a rule the specification states. And the conditional edges over-constrain the order, per §3 D.

**Neutral** — a new module, `rad::domain::engine`, and two new S10.3 codes: `CALCULATION_CYCLE` at both moments, and `RULE_NOT_REGISTERED` now appearing at publish as well as at submit. `CALCULATION_DID_NOT_SETTLE` is gone, having described a bound that no longer exists. The frontend already builds this graph for its own recomputation (JFSS §9.1) and is unchanged by this.

## 5. Compliance

`rad::domain::engine`'s unit tests hold the graph: a chain declared backwards orders forwards, an iterator body is not read as an outer-scope reference, a row template is its own scope, and each of the four cycle shapes is refused with its fields named. `rad_forms.rs` holds the endpoint: `RULE_NOT_REGISTERED` and `CALCULATION_CYCLE` refuse a create with 422, and `publishing_a_definition_the_engine_refuses_is_refused` writes a cyclic definition through the repository — behind the API that would now refuse it — and asserts the publish is refused and the revision stays `DRAFT`. `rad_form_submissions.rs` holds the second line: an evaluation failure is a 422 naming the field, never a 500.

A reviewer checks one thing this cannot: that a new definition-level check is added to `validate_definition` rather than to a caller, since that function is what `publish_form` re-runs. A check added at the create endpoint alone would pass every test above and still let a stored draft through the door.

## 6. Revisit When

The document type and menu builder UI ships (FR-RAD-004/008, [#341](https://github.com/sujanto-gaws/kelir/issues/341)) and has to *surface* a cycle rather than report it — S12.2's `SHOULD`, which no API refusal satisfies. Or a definition grows large enough that the extra walk at publish is measurable, at which point the question is whether the write-time verdict can be recorded on the row and trusted by the publish.
