# ADR-0015 — Calculations Run Before Conditional Stripping

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-27 · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** `D-27`, [ADR-0006](0006.%20Metadata-Driven%20Forms%20and%20Lists.md), [ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md)

## 1. Context

**Recorded retrospectively on 2026-09-01** from `D-27` in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1; the operative statement is [SDD](../../design/01.%20System%20Design%20Document.md) §8.2.2 (standard §9).

A submitted form is re-evaluated by the server: calculated fields are recomputed and overwritten (JFSS S8.1), and components hidden by a `conditional` are stripped (S10.2). The [Sprint 8 construction plan](../../../projects/planning/03.%20Sprint%208%20Form%20Renderer%20Construction%20Plan.md) §6.3 numbered stripping as step 3 and the calculation overwrite as step 4; [JFSS](../../schema/JSON%20Form%20Schema.md) §9.2 lists *Calculation Overwrite* **before** *Conditional Stripping*. A submission has to pick one order.

## 2. Decision

**The calculations run first, as JFSS §9.2 has them.** The plan's numbering is the one that gives.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Calculate, then strip** | JFSS §9.2's order | **Chosen** |
| B. Strip, then calculate | The construction plan's numbering | Rejected — a `conditional` over a computed field would then be decided from the client's number |
| C. Two passes: calculate, strip, calculate again | Tidier reading of "absent" | Rejected — converges to a different answer from the browser's, trading a real parity property for a tidier one |

### A. Calculate first — chosen

The plan names JFSS as the specification authority for these items, so the conflict is not a close call — **but the order is a security property rather than a preference.** A `conditional` keyed on a computed field is decided from whichever number is in the payload when it runs. Strip first and that number is the *client's*: an attacker claiming a grand total of five million opens an approval branch the rules would have kept shut, and the value smuggled in beside it is persisted. Calculate first and the branch is decided from the server's own figure — S8.1 applied one layer further than S8.1 states it. `a_conditional_over_a_computed_field_reads_the_servers_number` is that case, and it fails against the other order.

### C. Two passes

Rejected because the browser has no stripping step at all, so one pass agrees with it by construction on any form where a hidden field feeds a total. That agreement is what S10.1.1's argument is about.

## 4. Consequences

**Positive** — a routing condition over a computed value cannot be steered from the client.

**Negative, and correct rather than a compromise** — a `calculate` that reads a field a conditional later hides is evaluated against that field's live value rather than against its absence. The browser does exactly the same, so the two sides agree.

**Settled with it, from the same paragraph** — a hidden component is *"treated as absent for validation"* (JFSS §9.2), so a `matchesField` targeting one compares against absent on the server and against the live value in the browser. That divergence is the specification's own instruction and is named in `service/evaluation.rs` where it happens.

## 5. Compliance

`a_conditional_over_a_computed_field_reads_the_servers_number` in the RAD submission tests is red under the reversed order. `modules/rad/service/evaluation.rs` carries the reasoning at the point the order is fixed.

## 6. Revisit When

JFSS §9.2 changes its pipeline, or a form shape appears where the browser gains a stripping step — the assumption that makes one pass agree with the client.
