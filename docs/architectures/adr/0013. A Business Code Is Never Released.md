# ADR-0013 — A Business Code Is Never Released

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-26 · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** `D-19`, [ADR-0007](0007.%20Explicit%20Endpoints%20for%20Core%20Master%20Data.md), [ADR-0022](0022.%20Numbering%20Counters%20Live%20in%20Per-Scope%20Buckets.md)

## 1. Context

**Recorded retrospectively on 2026-09-01** from `D-19` in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1; the operative statement is [Database Schema](../../design/02.%20Database%20Schema.md) §1.3.1 and §4.1 (standard §9).

`uq_mdm_parties_tenant_id_party_code` was partial on `deleted_at`, so deleting a party **released its code**. Every stored reference keeps a UUID and renders whatever code that row now carries — so a customer's `billingPartyId` went on reading `PARTY-BILL` after a different legal entity took the freed code, and a consumer resolving it landed on the wrong party (#107).

## 2. Decision

**A party's business code is never released.** `0018_party_code_is_not_released.sql` makes the index total: a deleted party keeps its code, and creating a party with that code is a `409` — which says "including by a deleted party" in as many words, because the caller cannot see that party in any list and a bare "already in use" would read as a bug in the API.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Total unique index — the code is never freed** | Removes the failure class | **Chosen** |
| B. Render a soft-deleted referent as `null` | Reports the dangling reference honestly | Rejected — leaves the code free to be re-taken, so live references still change meaning |
| C. Document the behaviour as intended | No code change | Rejected — makes every consumer responsible for knowing a code is valid only as of the moment it was read |

### A. Total index — chosen

Chosen because it removes the failure class rather than reporting it, and because **a business identifier that names one thing this year and another thing next year is not an identifier**.

### B and C

Both leave the reuse window open. C in particular pushes an invariant out to every caller, which is where invariants go to be forgotten.

## 4. Consequences

**Positive** — a code resolves to one legal entity for the life of the deployment; a reference read today means the same thing when it is followed tomorrow.

**Negative** — a tenant cannot reuse the code of a party they deleted, including one deleted by mistake, and the refusal names a row they cannot see. `deleting_a_party_releases_the_business_numbers_it_held` had a fixture reusing a deleted party's code and had to be corrected.

**Not settled by this** — the *profile numbers* half (#103). Codes and numbers now behave differently on delete, deliberately for now: a supplier number is a slot in a sequence a deleted supplier has no claim on. #103 is where that is settled.

## 5. Compliance

The total unique index is the enforcement — the database refuses, so no code path can forget. The `409` and its wording are held by the master-data integration tests.

## 6. Revisit When

#103 settles the numbers half and makes the two behave alike, or a tenant requirement to reuse codes after a retention period arrives — which is a purge decision, not a uniqueness one.
