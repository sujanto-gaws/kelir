# ADR-0028 — A Definition Is Refused at Save Rather Than at Render

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-26 · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** `D-22`, [ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md), [ADR-0016](0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md), [ADR-0019](0019.%20A%20Workflow%20Definition%20Is%20Narrowed%20at%20Save%20Time.md)

## 1. Context

**Recorded retrospectively on 2026-09-01** from `D-22` in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1; the operative statement is [Calculation Rule Registry](../../schema/JFSS%20Calculation%20Rule%20Registry.md) §3.2 and `modules/rad/domain/jfss.rs` (standard §9).

`{"sum": [a, b]}` evaluates to `0` on both engines, silently. Nothing on the path refused it: the meta-schema's `jsonLogic` accepts any single-key object and defers arity by design, `sum` is in the `calculate` allow-list, the client renders `0`, and JFSS S8.1's server-side re-evaluation recomputes `0` and stores it (#201).

**Parity is what makes it invisible.** The Tamper-Proof Pattern catches a client that disagrees with the server; here they agree. The mistake is a natural one — `+` sits beside `sum` in the registry, in the same allow-list, with the same bracket syntax, and it *does* take a list of operands. The registry specifies `{ "sum": [array] }` and the empty-array answer and is silent on every other shape, so this was a specification gap first and an implementation behaviour second.

## 2. Decision

**A malformed definition is refused when it is saved, and the engines are not touched.** `validate_definition` rejects a `sum` whose argument **list** is any length but one, with `SUM_TAKES_ONE_ARRAY`. A non-array argument is left alone.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Refuse at save** | One round trip to the person who can fix it | **Chosen** |
| B. Raise an evaluation error in the operator | Louder, and catches definitions stored before the rule existed | Rejected — changes the documented non-array answer and must land on both engines in step: a parity-affecting change made to catch an authoring mistake |
| C. Document `0` as intended | Cheapest | Rejected — leaves the registry's flagship operator failing silently on its most natural misuse |

### A. Save time — chosen

**A definition is written once and rendered thousands of times.** Refusing at save costs one round trip to the person who can fix it; refusing at render costs a form that half-works for everyone else. It is the same discipline `jfss.rs` applies elsewhere and that [ADR-0019](0019.%20A%20Workflow%20Definition%20Is%20Narrowed%20at%20Save%20Time.md) applies to workflow definitions.

**The non-array case was measured rather than assumed**: JSON Logic's shorthand — `{"sum": {"var": "line_totals"}}` — is one argument and evaluates correctly on both engines, so the obvious rule ("the argument list must have one element") would have refused definitions that work.

### B. An engine-level error

Rejected as parity-affecting, which is the one class of change [ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md) was adopted to make rare.

## 4. Consequences

**Positive** — the silent `0` is unreachable for new definitions, and the refusal names what is wrong at the moment somebody can fix it.

**Negative** — definitions stored before the rule existed are not caught by it; only option B would have reached them. The refusal lives in the implementation rather than in the meta-schema, so a different JFSS implementation would not inherit it.

**Neutral** — the corpus gap was closed with it: both implementations' comments name three edge cases they must agree on — a non-array argument, an empty array, and non-numeric members — and `parity/cases.json` carried only the empty array. All three are in it now, plus the shorthand and the multi-argument shape, so the runtime answers are pinned even though the refusal happens earlier.

### 4.1 Impacted Documents

| Document | Change | Status |
|---|---|---|
| [Calculation Rule Registry](../../schema/JFSS%20Calculation%20Rule%20Registry.md) §3.2 | Already states the shapes | No change |
| `parity/cases.json`, `expectations.json` | Already carry the five cases | No change |

## 5. Compliance

`validate_definition` refuses with `SUM_TAKES_ONE_ARRAY`, held by `rad_forms.rs`; the five arity cases are in the parity corpus, so the runtime behaviour behind the refusal is pinned on both sides.

## 6. Revisit When

A second operator shows the same silent-answer shape — at which point the question is whether the refusal belongs in the meta-schema, where every implementation would inherit it, rather than in `validate_definition`.
