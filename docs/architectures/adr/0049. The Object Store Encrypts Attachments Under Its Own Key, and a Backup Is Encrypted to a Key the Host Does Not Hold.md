## 1. Context

**Written when the decision was taken, before its build** (plan 21 §7 step 4: row 2's ADR precedes row 2's build).

**[NFR-SEC-009](../../requirements/srs.md) reads *attachments and backups must be encrypted at rest*.** It is a `must`, baselined as written by **D-5** on 2026-08-11. Plan 21 places it in Sprint 25 as row 2, [#778](https://github.com/sujanto-gaws/kelir/issues/778), and its §8 decision 5 settles that the scope is not open and the shape is.

**This record reads the requirement as follows.** `requirements-analyst` traces NFR-SEC-009 separately (plan 21 §4, T). ~~The two readings are reconciled before this record merges.~~ **The two readings were reconciled on 2026-10-27**, in the criteria posted on [#778](https://github.com/sujanto-gaws/kelir/issues/778#issuecomment-6446837189). They agree on attachments and backups. The trace adds that the key is never on the volume it protects, which this record meets, and leaves the live database's data directory out, as this record does.
- **Attachments** are the bytes of every object in the attachment bucket, as the object store holds them on disk. That includes a soft-deleted attachment's object, which [ADR-0032](0032.%20A%20Soft-Deleted%20Attachment%20Keeps%20Its%20Object.md) keeps, an `INFECTED` or `FAILED` one, and any copy of the store's data. It does not include the `attachments` row (name, type, size, checksum), which is in PostgreSQL.
- **Backups** are every archive a shipped definition writes, wherever it is later copied. Today that is the daily timer's dump and `deploy.sh`'s pre-deploy dump, which run the same unit. *(2026-10-28: **D-122** adds the object store's archive to both runs, §2.)*
- **At rest** means that whoever holds the stored bytes, and not the key, reads nothing. Bytes in transit are NFR-SEC-010's. Bytes in a process's memory, and clamd's transient scan file, are not at rest.
- **The live database is not named.** PostgreSQL's data directory holds every document's content in plaintext, and the requirement names attachments and backups, not the database. This record does not extend it.

**What existed at `be3a9a0`:**

- **The attachment path.** `ObjectStorage::put` (`kelir-backend/src/modules/attachment/storage.rs`) is the only writer of an object. *(2026-11-01, [#834](https://github.com/sujanto-gaws/kelir/issues/834), **D-140**: true at `be3a9a0`, and no longer. `put` writes a file of one part or less, and `ObjectStorage::begin_upload` and `PartUpload` write a longer one as a multipart upload. Both ask for SSE-S3, because the request is set on the store, §2's **As built**. Every read still goes through `ObjectStorage::get`, which now hands back a stream.)* It is an `object_store` 0.12 S3 client that sends nothing about encryption. Two paths read an object back through `ObjectStorage::get`: the download (`service.rs`) and the scan worker (`worker.rs`, [ADR-0026](0026.%20ClamAV%20in%20the%20Stack,%20Scanning%20Asynchronously.md)). The backend reaches MinIO at `http://minio:9000`, plain HTTP inside the compose network.
- **The object store.** Both compose files and both of CI's jobs run `ghcr.io/sujanto-gaws/minio:RELEASE.2025-09-07T16-13-09Z`, with `mc` at `RELEASE.2025-08-13T08-35-41Z`. Both are pinned (**D-62**) and are Kelir's own copies (**D-92**): amd64 only, rebuilt from a filesystem, and any bump is a rebuild and a push by the maintainer. `minio-init` creates the bucket and ends with `mc ls` as its postcondition. **No compose file configures a key**, so every object sits in plaintext in the `minio-data` volume, or in the development container's `/data`.
- **What that release offers.** Server-side encryption with SSE-S3 or SSE-KMS, under one of two key sources: a single static key given as `MINIO_KMS_SECRET_KEY`, or KES, a separate key service with its own image, its own key store and mutual TLS to MinIO. **MinIO's documentation advises the static key for testing rather than production**, because it is one key with no rotation. MinIO refuses SSE-C, where the client supplies the key, over plain HTTP.
- **The backups.** `provision-ubuntu-24.sh` §6 writes `/usr/local/bin/kelir-backup` from a heredoc, and a systemd service and timer that run it at 02:30 UTC as `postgres`. It runs `pg_dump --format=custom` into `/var/backups/kelir` (mode 700), each dump mode 600, kept 14 days. `deploy.sh` starts the same unit before every deploy and stops if it fails. **The timer takes the database only.** Nothing backs up the object store, and the [Installation guide](../../operations/01.%20Installation%20and%20Deployment.md) §8 does not mention attachments. A custom-format dump compresses table data, so a plaintext dump does not show its rows to a search of its bytes.
- **The shapes that run.** Staging is a design and not a host (**D-9**). What runs is the local deployment, Installation guide §5: the release compose file, on a machine with no backup timer. CI's browser job brings that same stack up.
- **The secrets.** One `.env` in `/opt/kelir` (root, 600) holds the database password, the JWT secret and MinIO's root pair (NFR-SEC-007). **The stack has no key service**: a `vault://` reference resolves nowhere until [#605](https://github.com/sujanto-gaws/kelir/issues/605), placed after `v1.0.0` by **D-98** C.
- **The upgrade.** `deploy.sh` refuses a `.env` that lacks a variable `.env.staging.example` declares, so a new variable is enforced on the first deploy that needs it. A `v0.9.0` deployment holds plaintext objects and, where the timer was installed, plaintext dumps. The release process's N−1 rule binds the upgrade.

**Why this is an ADR** (standards/06 §1): once objects are stored under a key, the choice is expensive to reverse, and every option trades operability against a requirement. **Plan 21 sized the object store encrypting what it holds** (§3.2 row 2, 700–1,600). It asked that the store encrypting, the application encrypting and an operator's encrypted volume all be weighed. It also said that preferring the third would be a scope call, the next `D-n`.

**Added 2026-10-28, for D-122.** The product owner answered **D-122** on 2026-10-28: **Kelir's backups take the object store too** ([Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1). [#778](https://github.com/sujanto-gaws/kelir/issues/778)'s *Done when* is widened [in this comment](https://github.com/sujanto-gaws/kelir/issues/778#issuecomment-6462911831): the bucket is copied beside each dump, on the same timer and retention, encrypted to the same recipients; `deploy.sh`'s pre-deploy backup takes it; the probe reads a backed-up object raw; and a restored document's attachment downloads and matches, within NFR-AVA-004's 4-hour RTO. The forces on how:
- **MinIO decrypts an SSE-S3 object on every read through the S3 API.** A copy taken that way is plaintext unless it is encrypted again.
- **The store is reachable only on the stack's network.** Only Caddy publishes a port (the staging compose file's note 2), and `mc` exists only as the pinned image `minio-init` runs.
- **The timer's user can reach neither.** It runs as `postgres`, which is not in the `docker` group and cannot read `.env` (root, 600), where MinIO's root pair is (NFR-SEC-007).
- **The upload stores the object before it commits the row** (`service.rs`, [#244](https://github.com/sujanto-gaws/kelir/issues/244)'s object-first order), **and nothing deletes an object**: `ObjectStorage` has `put` and `get` only, and ADR-0032 keeps a soft-deleted attachment's object. *(2026-11-01, #834: it has `begin_upload` too, and `PartUpload` aborts an upload it did not complete. An abort removes parts that were never an object, so it stays true that nothing deletes one, and §2's **The database goes first** holds.)*
- **An object's key names its file**: `tenants/<tenant>/documents/<document>/attachments/<id>/<file name>` (`domain.rs`, `storage_reference`).

## 2. Decision

**Kelir has the object store encrypt every attachment under a key the store holds, and encrypts every backup archive to a public key whose private half the host does not hold.**

- **Attachments: MinIO's SSE-S3, under a static key.** MinIO is given `MINIO_KMS_SECRET_KEY` in both compose files. **In the release stack it comes from `KELIR_MINIO_KMS_SECRET_KEY` in `.env`**, which is required, generated by the operator and refused as a placeholder. The development stack and CI use a fixed development key published in the repository. **`minio-init` sets the bucket's default encryption to SSE-S3**, and its postcondition checks the setting as it checks the bucket.
- **The backend asks for SSE-S3 on every write**, unconditionally, with no setting that turns it off. A store with no key refuses that write, so an upload fails rather than landing in plaintext. No key service and no new image.
- **Objects an upgrade finds are re-encrypted, not left.** Before it exits, and so before the backend starts, `minio-init` rewrites through the S3 API every object the store does not report as encrypted, soft-deleted ones included. The pass is idempotent: after one complete run it finds nothing to do.
- **Backups: `age`, to one or more X25519 recipients.**
  - The backup command pipes `pg_dump` through `age` and writes only `kelir-<stamp>.dump.age`. A plaintext dump never touches the disk, not even briefly.
  - The recipients are configured on the host as `KELIR_BACKUP_AGE_RECIPIENTS`. The operator generates the identity on a machine other than the host, and brings it to a host only to restore.
  - **Without a recipient the backup fails and writes nothing.** `deploy.sh`'s pre-deploy backup then stops the deploy, as it does for any failed backup.
  - **Restore decrypts with the identity**, then runs the documented `pg_restore`.
- **The upgrade leaves no plaintext dump behind.** The provisioner, re-run on upgrade, encrypts each plaintext dump it finds to the recipients and removes it. `deploy.sh` refuses to deploy over an installed backup unit that does not encrypt, or, since **D-122**, that does not take the store.
- ~~**An object-store backup, when one is taken, is a copy of MinIO's data as stored.** That copy is already ciphertext under the store's key, and restoring it needs that key.~~ An export through the S3 API is plaintext, so it is encrypted to the backup recipients before it touches a disk. *(Corrected 2026-10-28: **D-122** takes the store into every backup, and §3's store-half options choose an export through the S3 API, not a copy of the data as stored. The rule in the last sentence stands.)*
- **Backups take the object store too (D-122, 2026-10-28).** Each run takes the database, then the store, under one stamp.
  - **The store half is read through the S3 API by the pinned `mc`, and streamed into `age`.** A one-off container of the compose file's `mc` image, on the stack's network, lists the bucket and reads every object with `mc cat`, in one stream. The host pipes that stream through `age` to the same `KELIR_BACKUP_AGE_RECIPIENTS`, into `kelir-<stamp>.objects.age`.
  - **Inside the encryption, a manifest leads**: each object's key and size, in order. The objects' bytes follow in that order.
  - **No plaintext object touches the disk, and the archive names no file.** A key carries its file's name, and the key is inside the ciphertext.
  - **The copy is checked before it is kept.** The bytes streamed must equal the manifest's sum, or the half fails.
  - **The database goes first.** An object is stored before its row commits, and nothing deletes one, so every attachment the dump names is in the copy taken after it. An object stored between the two is an orphan in the backup, which the object-first order already allows.
  - **The 14-day retention takes both halves.**
  - **Either half failing fails the run, and a failed half leaves no file.** `deploy.sh`'s pre-deploy backup is the same unit, so it takes the store too, and a failed store half stops the deploy.
  - **Restore decrypts with the identity and writes each object back through the S3 API**, into any MinIO under its own key. **It does not need the store key.** The provisioner installs the restore as a command beside the backup, because the archive is not a tar. A restore takes a stamp that has both halves.
- **The backup unit runs as root.** It must read MinIO's root pair from `.env` (root, 600, NFR-SEC-007), and reach MinIO, which is only on the stack's network, through Docker.
  - **`postgres` cannot do either.** Adding it to the `docker` group would make it root-equivalent and still not let it read `.env`. Widening `.env` to a group breaks NFR-SEC-007's one root-only file.
  - **The database half still runs as `postgres`**, through `runuser`, so `pg_dump` keeps its peer authentication. Root's shell, not `postgres`, writes the encrypted file.
  - **The credentials reach `mc` in the container's environment**, never on its command line.
  - **The backup directory becomes root's**, mode 700, each archive mode 600.
- **Key custody: two keys, two duties.**
  - **The store key** is in `.env` on the host, because MinIO reads it at every start. The operator keeps a copy off the host, apart from any copy of MinIO's data. ~~**Losing it loses every attachment**, with no recovery.~~ **Losing it loses every attachment in the store.** The latest store archive brings them back into a store under a new key, less what was stored after it *(corrected 2026-10-28, **D-122**)*.
  - **The backup identity** is kept off the host and nowhere else. **Losing it loses every archive encrypted only to it**, both halves. The live database is untouched, and the next backup can be taken to a new recipient at once.
- **Rotation.**
  - **The backup recipient rotates without tooling**: add the new recipient, and drop the old one once the 14-day retention has passed.
  - **The store key is not rotated by this decision.** MinIO's static key is one key with no versions, so rotation means rewriting every object under a new key. It is deferred to §6's trigger. Since **D-122**, the store archive is what that rewrite can start from: restoring it into a store under a new key is a rotation, with the stack down for its length. That is not built either.

**Scope.** It covers both compose files, CI's two object stores, `minio-init`, the backend's write, the backup command, the provisioner and `deploy.sh`, and, since **D-122**, the backup's store half and the restore command. ~~**It leaves three things open**:~~ **It leaves two things open** *(corrected 2026-10-28)*:
- ~~whether Kelir's backups take the object store at all, which is NFR-AVA-004's question;~~ **decided 2026-10-28 by D-122** ([Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1): they do, by the store half above;
- the database's own data directory;
- an external key service.

**As built (2026-10-28, [#778](https://github.com/sujanto-gaws/kelir/issues/778)).** The build follows this section, and settles the details it left to the build:
- **The backend's request is set through `object_store`'s configuration key, named as a string.** `object_store` 0.12 does not re-export its encryption key type, so `ObjectStorage` parses `"aws_server_side_encryption"` as an `AmazonS3ConfigKey` and sets it to `AES256`. That sends `x-amz-server-side-encryption: AES256` on every single-request write and on the start of a multipart one. An upload part carries no header, as S3 specifies for SSE-S3. A unit test reads both requests off a socket.
- **A store with no key answers that write `501 Not Implemented`**, and the upload fails with nothing stored (seen against a keyless MinIO).
- **The pinned MinIO encrypts its own `config.json` and IAM data under the key too.** §4's open negative is answered: losing the key loses the store's users and settings as well, and the Installation guide §8.2 says so.
- **`minio-init`'s script is one literal block run by `bash -c`, the same in both compose files.**
  - It finds what to rewrite with `mc ls --recursive --json`, then reads each object's state with `mc stat --recursive --json`. The listing comes first because `mc stat --recursive` fails on an empty bucket.
  - It re-encrypts an object by copying it onto itself with `mc cp --enc-s3`. **A rewrite changes the object's modification time, and may change its ETag**; nothing in Kelir reads either.
  - Its postcondition lists again and finds nothing unencrypted. A second start finds nothing to rewrite.
- **The store archive's manifest is text.** Two header lines, `kelir-objects 1` and `<count> <total bytes>`, then one `<size> <key>` line per object. A key holding a line break fails the run. One `mc` container reads every object in turn with `mc cat`, and the bytes are counted through a FIFO on their way into `age`.
- **Every container the backup starts runs with `--log-driver none`.** The store half's plaintext leaves `mc` on its container's stdout, and Docker's default `json-file` driver, Ubuntu's default and so the staging host's, writes a container's stdout to a file under `/var/lib/docker/containers` before `--rm` removes it. Without the flag a plaintext copy of every object would touch the host's disk during the run, which §2 forbids. The listing's container gets it too, because the listing names every file. The probe asserts the flag on every `docker run` it traces.
- **A restore cut short removes the object it was writing.** `mc pipe` stores whatever bytes reach it, so an archive that ends inside an object would leave its first bytes under the object's real key, and the download serves an object without checking it against its row's checksum. The restore removes that key before it fails. Objects written whole before the failure stay, and a rerun over the same target replaces them.
- **`mc` reads the credentials in `MC_HOST_kelir` as written, not percent-decoded.** A percent-encoded pair was refused with `SignatureDoesNotMatch`. So the backup refuses a MinIO user holding `:` or `@`, or a password holding `@`. A generated value holds neither.
- **The backup command carries a format stamp**, the line `# kelir-backup-format: 2`. `deploy.sh` reads it to tell a unit that takes the store from `v0.9.0`'s heredoc.
- **With no backup unit installed, `deploy.sh` warns on stderr and deploys.** That is the local deployment, CI's browser job included, which has no timer. A unit that is installed and lacks the stamp is refused, before any image is pulled or built.
- **`deploy.sh` refuses the published development key by its value**, as well as an empty key or one that is not `<name>:<base64 of 32 bytes>`.
- **The upgrade's conversion is `kelir-backup --encrypt-old-dumps`**, which the provisioner runs. Each `.dump.age` keeps its plaintext's modification time, so retention counts from the day the dump was taken.
- **The restore command is `kelir-restore-objects`**, installed beside `kelir-backup`.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. The store encrypts under a static key; archives are encrypted to an `age` recipient** | SSE-S3 with `MINIO_KMS_SECRET_KEY`, requested by the backend and set as the bucket default; `pg_dump` piped through `age`, and since **D-122** the store's objects too (*The store's half of a backup*, below) | **Chosen** |
| A2. The store encrypts under keys from KES | SSE-KMS, with MinIO asking a KES service for each object's key | Rejected — a new image from the publisher whose registries closed twice, and mutual TLS to run. The only key store the stack could give it is a file on the same host, so no custody is gained |
| B. The application encrypts before it stores | AES-256-GCM per object in the backend, under a data key wrapped by a master key from the environment | Rejected — key handling in every reader of an object, a key column, and 1,500–3,000 lines. The master key sits in the same `.env` as the store's credentials |
| C. An operator's encrypted volume | LUKS or a cloud disk's encryption, under the database, the volumes and the backup directory | Rejected — a `must` met by an operator's duty, which is a scope call. No probe from inside a running host can see it |
| D. Archives encrypted with a passphrase on the host | `gpg --symmetric` or `openssl enc`, with the passphrase where the timer can read it | Rejected — the passphrase sits beside the archives it protects |
| E. Archives encrypted to an OpenPGP public key | `gpg --encrypt` to a key imported into the `postgres` user's keyring | Rejected — the same custody as A, with a keyring and a trust decision to carry |

### A. The store encrypts under a static key; archives are encrypted to an `age` recipient — chosen

**It meets the requirement with what the stack already runs.**
- **No new image**, so nothing new is pinned (**D-62**) and nothing new is mirrored and rebuilt by hand (**D-92**).
- **Every reader is unchanged.** The download and the scan worker read through `ObjectStorage::get`, and MinIO decrypts for them. ClamAV still scans the bytes that were uploaded.
- **The backend gains one setting**, on the one writer. *(2026-11-01, #834: two writers now, and still one setting, on the store.)*

**Asking for SSE-S3 on every write is what makes it fail closed.** A bucket default is a property of the deployment that nothing in the product checks. Recreate the bucket, or point the backend at a store with no key, and writes land in plaintext without a sound. With the request, a store that cannot encrypt refuses the write, and the upload fails where somebody sees it. That is the scanner's direction: ADR-0026 blocks a download until a file is `CLEAN`, and an unreachable scanner leaves a file undownloadable rather than unscanned (SDD §13.1).

**`age` gives the backup half the property the store half cannot have: the host writes archives it cannot read.** The timer needs only the recipient, which is public. So anyone holding the host, or a copy of its backup directory, holds archives they cannot open, the host's own past archives included. `age` is one Ubuntu 24.04 package and takes the recipient as a string. Its header line, `age-encryption.org/v1`, is something a probe can check.

**What it does not solve.** The store key must be readable on the host for MinIO to start, so it sits on the same disk as the data it protects. **This shape protects every copy of the store's data that leaves the host, and not the host's own disk.** That is the cost upstream's advice names. Kelir accepts it because §1's stack has one node and no key service, and what KES would add (more than one key, rotation, a key audit) is custody only when its keys live somewhere other than this host.

### A2. The store encrypts under keys from KES

**KES is MinIO's answer to the static key's limits**: many keys, rotation, and a key store that can be Vault or a cloud KMS. The costs are concrete:
- **A fourth infrastructure image**, `minio/kes`, from the publisher whose images left Docker Hub on 2026-09-12 and quay on 2026-09-24. Under **D-92** it would be one more mirror rebuilt and pushed by the maintainer with a classic token, amd64 only. Under **D-62** it would be one more pin.
- **Mutual TLS between MinIO and KES**, with certificates to issue, mount and renew, and an identity for MinIO. The stack issues no certificate for an internal service: Caddy's are for the site it serves.
- **A key store, and the stack has only one to give it.** Vault is after `v1.0.0` (#605, **D-98** C), and no deployment has a cloud KMS. **KES's filesystem key store keeps its keys on the same host**, so the custody is option A's, reached through two more containers.

It is the right shape once an external key store exists, which is §6's first trigger.

### B. The application encrypts before it stores

The backend would seal each object with AES-256-GCM under a fresh data key, and store that data key wrapped by a master key from the environment. **It would buy two things**: it works on any S3 store, and a compromise of the store alone (its root credentials, say) yields ciphertext. The costs:
- **Every reader decrypts.** The download and the scan worker both gain the key and a failure mode, and so will any later reader, such as a thumbnail or an export.
- **A wrapped key per object**: a column on `attachments` with a migration (`migration-author`), or a header inside each object. Either way, the application must re-encrypt every existing object itself.
- **The master key would sit in the same `.env` as MinIO's root pair.** On this stack, "the store compromised alone" means the same host, so the protection gained over A is narrow.
- **Plan 21 §3.2 sizes it at 1,500–3,000 lines**, against ~~900–2,000 (700–1,600 at adoption)~~ 1,200–2,750 with **D-122**'s store half (re-sized 2026-10-28, *The size* below; 900–2,000 before it, 700–1,600 at adoption). It does nothing for the backups, which still need D's or E's or A's answer, and its figure does not include the store half either.

**SSE-C, the store encrypting under a key the backend supplies with each request**, is B's custody with A's mechanism. MinIO refuses it over plain HTTP, and the backend reaches MinIO over plain HTTP inside the compose network. Adopting it would mean TLS on that hop as well.

### C. An operator's encrypted volume

LUKS under the host's disks, or a cloud disk's own encryption. **It needs no Kelir code, and it covers more than A**: the database's data directory, the scan worker's transient files, and the free blocks a deleted plaintext dump leaves. The costs:
- **Kelir would ship nothing that does it and could check nothing about it.** A running host reads its volume in plaintext, so the probe #778 asks for, a raw read that finds ciphertext, cannot be written from inside the host.
- **It protects a powered-off disk only.** An archive copied off the host leaves in plaintext.
- **A `must` requirement would be met by an operator's duty.** Plan 21 §4 row 2 and §8 decision 5 make that a scope call, the next `D-n`.

It is not chosen, so no `D-n` is raised. The Installation guide may still recommend an encrypted disk as defence in depth for what A leaves on the host. NFR-SEC-009 does not rest on it.

### D. Archives encrypted with a passphrase on the host

`gpg --symmetric` or `openssl enc`, keyed by a passphrase. **The timer runs unattended as `postgres`, so the passphrase must be readable there**, and anyone holding the host holds the archives and their key together. That is the property `age`'s recipient exists to avoid. `openssl enc` also authenticates nothing, so a damaged archive decrypts into garbage instead of failing.

### E. Archives encrypted to an OpenPGP public key

`gpg --encrypt` to the operator's public key. **It has A's custody**, and `gpg` is already on the host. It loses on operability alone:
- the key must be imported into the `postgres` user's keyring, with a trust decision (`--trust-model always`, or a signature);
- an expired subkey stops the timer;
- a failure reads as a keyring's.

`age` takes the recipient as a string and has no keyring. **E is the close second**, and §6's triggers do not reopen it.

### The store's half of a backup (added 2026-10-28, D-122)

**D-122 settles that a backup takes the store. How it reads the store is this record's.** Each option uses only what the stack already ships: the pinned `mc` (**D-62**, **D-92**), `tar`, and `age`.

| Option | Summary | Verdict |
|---|---|---|
| F. Mirror, then archive | `mc mirror` the bucket into a staging directory, then `tar` piped through `age` | Rejected — every object lands in plaintext on the backup disk for the run, and its blocks outlive the directory |
| **G. Stream every object into one archive** | One `mc cat` of every listed object, behind a manifest of keys and sizes, piped through `age` | **Chosen** |
| H. Copy MinIO's volume | `tar` of the `minio-data` volume's files, piped through `age` | Rejected — a restore needs the store key, a running drive's files are not a consistent copy, and they are one release's on-disk format |

**F is the simplest restore**: decrypt, untar, `mc mirror` back, with standard formats only. **It writes the plaintext §2 forbids.** MinIO decrypts on read, so the staging directory holds every attachment in plaintext until it is removed, and removing it does not scrub its blocks (§4's negative for the old dumps). It also needs free space for the bucket twice.

**G keeps F's custody without F's plaintext.** The bytes leave `mc` into `age` and reach the disk only as ciphertext. A restore needs the identity and any MinIO, under any key. The costs:
- **The archive is Kelir's own framing**, a manifest and the bytes it describes, not a tar. So the restore is a command Kelir ships, and the Installation guide states the format for an operator who has lost it.
- **One damaged chunk loses every object after it in that archive.** `age` authenticates in 64 KiB chunks and stops at the first bad one. The previous day's pair is the fallback.
- **It needs root**, for Docker and for `.env` (§2).

**One `age` file per object** was the variant weighed and dropped. Damage would stay in one object, but every object would cost a container call on backup and on restore, and the restore's calls count against the 4-hour RTO.

**H is the fastest copy and needs no credentials**, and under this record its files are already ciphertext. The costs decide it:
- **A restore needs `MINIO_KMS_SECRET_KEY` as well as the identity.** The store and its backups would hang on one key, so losing it would lose the attachments and every backup of them together. Under G, the store archive is what recovers that loss.
- **MinIO's files are not an interface.** An object written while `tar` reads them is copied torn, unless MinIO is stopped for the copy, and the pre-deploy backup runs in the working day.
- **The files are the pinned release's on-disk format.** A restore across a MinIO bump, **D-92**'s rebuild, is unproven.

**The size.** Plan 21 §3.2 sizes row 2 at 900–2,000 by its columns, for the database half only (re-sized 2026-10-27). **The store half adds 300–750**, by the same columns:
- configuration and scripts, 100–250: the store half, its check, the unit's user, and the restore command;
- probe and tests, 150–350: the store archive's raw read, its red run, and the restored download;
- other texts, 50–150: the Installation guide §8's two halves, and this revision.

**Row 2 is 1,200–2,750** under the storage-side shape (2026-10-28), against 900–2,000 before **D-122**.

## 4. Consequences

**Positive**
- **Every attachment write is encrypted, and a store that cannot encrypt refuses the write.** The probe in §5 reads the store's files raw.
- **An archive is unreadable to anyone without the identity**, the host's own root included, and so is every copy of it.
- **No new image and no new crate.** One distribution package, `age`.
- **Every reader of an object is unchanged**: the download and the scan worker.
- **The upgrade depends on nothing the operator must remember.** `deploy.sh` refuses an old `.env` and an old backup unit, and `minio-init` re-encrypts what it finds.
- **A backup now holds the attachments** (**D-122**). A restore brings back the documents and their files together, by one documented path.
- **A restore needs the identity, and not the store key**, for either half. A lost store key is recovered from the latest store archive.

**Negative**
- **The store key sits on the host beside the data.** A copy of the host's disk, or the running host, yields every attachment in plaintext. NFR-SEC-009 is met for every copy of the store's data that leaves the host, and not for the host's own disk.
- **Two keys must be kept, and losing either loses data.** ~~Losing the store key loses every attachment.~~ Losing the store key loses the attachments stored since the last store archive, and the stack is down until the restore *(corrected 2026-10-28, **D-122**)*. Losing the backup identity loses every archive encrypted only to it, which is why a second recipient, held apart from the first, is advisable.
- **The store key cannot be rotated in place.** Rotation is a rewrite of every object, and it is not built.
- **A restore needs the identity on the restoring machine** for its length. NFR-AVA-004's 4-hour RTO now includes fetching it, and Sprint 26's drill times that. Since **D-122** it also includes writing every object back through the S3 API, which the build measures. *(Measured 2026-10-28, on the laptop the Installation guide §8.3 names: 518 objects, 1.08 GB, written back in 99 s; the database half in 8 s and the stack's start in 7 s.)*
- **The backup grows with the attachments, and so does its run.** The store archive is about the bucket's size: most attachments are already compressed formats, and `age` does not compress. Each run copies the whole bucket, so **the 14-day retention keeps fourteen full copies on the host**, and the backup disk needs about fourteen times the bucket beside the dumps.
- **Every deploy waits on a copy of the whole bucket**, because the pre-deploy backup is the same unit.
- **The backup unit runs as root**, where it ran as `postgres`. It reads `.env` and drives Docker, so a fault in the backup command is a fault with root's reach.
- **The store archive is not a tar.** Restoring it needs Kelir's restore command, or the format the Installation guide states.
- **A damaged store archive loses every object after the damage.** The previous day's pair is the fallback, at up to a day's uploads more lost.
- **A `v0.9.0` deployment has no attachment backup at all.** An attachment stored before the upgrade has its first copy in the first backup after it. The upgrade's own pre-deploy backup takes the store only once the provisioner has been re-run, which `deploy.sh`'s refusal of an old unit enforces.
- **Every MinIO the backend writes to needs a key**, the developer's and CI's backend job's included, or uploads fail. The development key is published and protects nothing. It exists so the development and CI stacks take the release's path.
- **Restoring `v0.9.0`'s compose file leaves MinIO without its key**, and every object unreadable. `./deploy.sh <previous-version>` is not that: it changes the images and keeps the compose file and `.env`.
- **The first start after the upgrade re-encrypts every object before the backend starts.** That start is slower, once, and every later start reads each object's metadata. The build measures both. *(Measured 2026-10-28: 515 objects, about 1 GiB, re-encrypted in 52 s; the next start rewrote nothing, in 4 s.)*
- **Removing a plaintext dump does not scrub its blocks.** After the upgrade, the old dumps' contents may survive in free space until they are overwritten. Option C's disk encryption is what covers that.
- **If the pinned MinIO also encrypts its own configuration under the key**, losing the key loses the store's users and settings as well. The build confirms which, and the Installation guide says so. *(Confirmed 2026-10-28: it does, §2's **As built**.)*
- **The database's data directory stays in plaintext**, by §1's reading.

**Neutral**
- ~~**Two deployment variables**: `KELIR_MINIO_KMS_SECRET_KEY`, and `KELIR_BACKUP_AGE_RECIPIENTS`.~~ **Two variables in `.env`**, `KELIR_MINIO_KMS_SECRET_KEY` and `KELIR_BACKUP_AGE_RECIPIENTS`, **and optional settings on the two commands** (the Installation guide §7.2), such as the network, the MinIO address and the `mc` image, which let them run against any stack. The backend reads no new variable, so `configuration_reference.rs` gains no row. ~~The store half adds none:~~ The store half adds no secret: it reads MinIO's root pair, which `.env` already holds. *(Corrected 2026-10-28: the build added the commands' settings.)*
- ~~**An archive is named `kelir-<stamp>.dump.age`.**~~ **A backup is a pair under one stamp**: `kelir-<stamp>.dump.age` and `kelir-<stamp>.objects.age` *(corrected 2026-10-28, **D-122**)*.

## 5. Compliance

**The probe decides #778's test, and each half is seen red with encryption off.**

- **Attachments.** The probe stores objects through the backend's write, not through `mc`, so it tests the request the product sends.
  - It writes two objects, each carrying a marker string: one small enough for MinIO to keep inline in its metadata file, and one large enough to be stored as a part file.
  - It also writes one object before the key is set, as a `v0.9.0` store holds it, and starts `minio-init` over it.
  - It then reads every file under MinIO's data directory for the bucket raw, from outside MinIO. **It finds no marker**, and the store reports each object as SSE-S3.
  - **Red**: with the key, the bucket default and the backend's request all removed, the same read finds the marker.
- **Backups.** The probe runs the backup command the timer runs, against a database holding a known row. The provisioner installs that command as a file, rather than writing it from a heredoc, so a test can run it.
  - **The archive's first line is `age-encryption.org/v1`, and `pg_restore --list` refuses the raw archive.**
  - Decrypted with the identity, the archive is restored into a scratch database by the documented path, and the known row is read back.
  - **Red**: with encryption removed, `pg_restore --list` reads the raw archive.
  - **The probe does not search the archive for the row.** A custom-format dump compresses table data, so a plaintext dump can hide a row from a search and pass with encryption off.
- **The store half** *(added 2026-10-28, **D-122**)*. The same run takes the store, after the probe has stored an object carrying a marker through the backend's write.
  - **The store archive's first line is `age-encryption.org/v1`, and a raw read of it finds no marker.** The store half compresses nothing, so here a search is the test, as it is not for the dump.
  - **Red**: with the archive's encryption removed, the same read finds the marker.
  - Decrypted with the identity, both halves are restored into a scratch stack by the documented path. **The restored document's attachment downloads, and its bytes match the row's checksum.** The probe records the restore's time against NFR-AVA-004's 4 hours.
- **It fails closed.**
  - A backend write to a MinIO with no key is refused.
  - The backup command with no recipient exits non-zero and leaves no file.
  - A store half that cannot reach MinIO, or whose bytes do not match its manifest, exits non-zero and leaves no store archive.
  - `deploy.sh` refuses an installed backup unit that does not take the store.
  - `deploy.sh` refuses a `.env` without `KELIR_MINIO_KMS_SECRET_KEY`, or with a placeholder in it.

**A reviewer of any new writer of objects, or of any new archive or export, checks it against §2**: a write asks for SSE-S3, and an archive or export is encrypted to the recipients before it touches a disk.

## 6. Revisit When

- **An external key store reaches the stack**: Vault through #605, or a cloud KMS in a production topology (SDD §13.2, *Secret management*). KES then gains custody (A2), and the store key can leave the host.
- **The store key is exposed**, or someone who held it leaves while a copy of the store's data exists. Rotation, the rewrite of every object, is built then.
- **The pinned MinIO is bumped** (**D-92**'s rebuild): the probe is run again, because static-key support is upstream's to remove.
- **The store outgrows a full copy a day** *(added 2026-10-28, **D-122**)*: fourteen store archives no longer fit the backup disk, or the store half's restore no longer fits NFR-AVA-004's 4 hours. An incremental copy, or MinIO's replication to a second store, is weighed then.
