# ADR-0016 — An Unenforceable Rule Refuses Rather Than Passes

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-26 (browser, `D-26`); 2026-08-27 (server, `D-28`); bounded 2026-08-27 (`D-33`) · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** `D-26`, `D-28`, `D-33`, [ADR-0017](0017.%20Field%20Refusals%20Answer%20422%20with%20the%20S10.3%20Envelope.md)

## 1. Context

**Recorded retrospectively on 2026-09-01** from `D-26`, `D-28` and `D-33` in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1, which hold the reasoning and remain operative (standard §9).

The [Validation Rule Registry](../../schema/JFSS%20Validation%20Rule%20Registry.md) defines rules a form definition may name. Some of them this build cannot decide. In the browser, §3.2's `passwordStrength` needs a scoring library the frontend does not carry and an allow-listed endpoint that is not served. On the server, §3.3 defines `unique`, `exists` and `authorized`, and a definition may carry any of them today because `validate_definition` checks the meta-schema, the operator set and the lookup allow-list at save — and a rule *name* is none of the three.

The failure to avoid is stated in the construction plan and repeated in both decisions: ***a rule that fails open is a rule that is not there, reported as a rule that passed.*** The reference implementation's `backendValidator.ts` returning `true` for an unknown rule is the shape being refused.

## 2. Decision

**A rule this build cannot enforce never passes silently.** On the server the submission is **refused**, naming the rule (`RULE_NOT_ENFORCED`). In the browser — which has the server below it — the rule is **declared on the form** as one that is not checked as you type, with the registry's reason. A draft write is the one bounded exception, and it is bounded by what a draft is.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Refuse (server) / declare (browser)** | Never silent, and loud where nothing is below | **Chosen** |
| B. Skip the rule | The reference implementation's shape | Rejected — a rule that fails open reported as one that passed |
| C. Raise on it as on an unknown name | Refuse to render the form | Rejected in the browser — a name nobody defines is a defect in the definition; a rule this runtime cannot run is a gap in the runtime, and taking a working form off the screen over a strength meter is the wrong trade |
| D. Add the missing dependency (`zxcvbn`) | Make the browser able to decide | Rejected — adding a dependency is a decision rather than an import, and a hand-rolled scorer would give `minScore: 3` a different meaning on each side |
| E. Refuse the *definition* at save | Where every other definition-level refusal lives | Rejected for now — a rule name is not checked at save today, so adding it would change #156's contract and refuse definitions already stored |
| F. Implement the three server rules | Close the gap properly | Rejected — `unique` and `exists` query the table a form writes to, and a form does not write to a table yet; `authorized` is FR-DTYPE-008, unbuilt |

### A. The chosen shape

`VALIDATION_RULES` in `features/rad/renderer/validation.ts` gives every catalogue entry **either a decision function or a stated reason, never neither and never both**, and a spec asserts that. `server`-scoped rules are filtered out of the notice — those are not a gap, they are registry §3.3 working as written. On the server, `RULE_NOT_ENFORCED` refuses the submission against the field that carries it, so a definition using one cannot be submitted until the rule is built. `RULE_NOT_REGISTERED` is kept distinct and still refuses: a rule nobody defines is a defect in the definition (JFSS S8.1.1).

### The bounded exception (`D-33`)

A document is validated on **every** write, and `required` is the rule an unfinished draft breaks. The line is drawn where the sentence is: **a value that is present and wrong is refused; a value that is missing is not wrong, it is unfinished.** A `Strictness` parameter on the one evaluator forgives three failure classes on a draft and only on a draft, matched on the `(code, rule)` pair the walk emits rather than on message text — `VALIDATION_FAILED`/`required`, `RULE_NOT_ENFORCED` (which is this decision's own reasoning: on a draft there *is* something below, namely the submit) and `EVALUATION_FAILED`. `RULE_NOT_REGISTERED` still refuses. **Rejected: a second, laxer pipeline for drafts** — two answers to what the Tamper-Proof Pattern does is the failure the pattern is about; the submit calls the same function with `Strictness::Submit`.

## 4. Consequences

**Positive** — no configuration of definition and build produces a silent pass. A gap is visible to the person filling the form, not only to whoever reads the code.

**Negative, accepted** — `unique`, `exists` and `authorized` are unusable until they are built, and an author reaching for one meets a refusal rather than a silence. A form using `passwordStrength` shows a notice explaining that the check happens at submit. A draft can hold a payload the submit will refuse — but only by being unfinished.

**Neutral** — the server's half needed a dependency: the five `both`-scoped rules of registry §3.1 include `regex`, which no Rust standard library decides, so `kelir-backend` takes the `regex` crate. The two engines read a pattern differently, which stays `D-15`'s open question and is not widened here.

## 5. Compliance

A spec asserts the "function or reason, never neither and never both" invariant over `VALIDATION_RULES`, so a new catalogue entry cannot join silently. On the server the refusal is held by the RAD submission tests, and the draft exception by the document tests; the forgiveness list is matched on `(code, rule)` pairs rather than message text, so a rewording cannot widen it.

## 6. Revisit When

The three server rules become implementable — documents write to a table, FR-DTYPE-008 lands — at which point option E (refusing the definition at save) becomes the right home for what is left, and #156's contract change can be planned rather than improvised.
