# ADR-0014 — Kelir Extends JFSS Through `settings`

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-26 · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** `D-23`, [ADR-0006](0006.%20Metadata-Driven%20Forms%20and%20Lists.md)

## 1. Context

**Recorded retrospectively on 2026-09-01** from `D-23` in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1; the operative statements are [SDD](../../design/01.%20System%20Design%20Document.md) §8.2.1 and [Database Schema](../../design/02.%20Database%20Schema.md) §5.12–§5.13 (standard §9).

#161 needed a form definition to declare a lookup field naming a master-data source, and JFSS had nowhere to put one. The meta-schema closes a component with `unevaluatedProperties: false`, so `dataSource` on the field is not a conformant v2.0.1 document — and JFSS is a **`Final Standard`**: frozen at v2.0.1, errata only, a successor takes a new major version ([naming convention](../../standards/02.%20Naming%20Convention.md) §10.1). A v2.1.0 adding an optional property was not available either.

## 2. Decision

**The binding lives in the form's `settings`, mapping a component `id` to a source key, and JFSS is not touched.** A Kelir form carrying a lookup is a conformant JFSS **v2.0.1** document, and every existing definition stays valid.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. `settings.lookups`, bound on component `id`** | Uses the one object the specification leaves open | **Chosen** |
| B. JFSS v3.0.0 with a `dataSource` property on the component | What the standard's own philosophy wants | Rejected — a phase-scale decision, not a sprint item |
| C. Edit `jfss-meta-v2.0.1.json` in place | Add the property to the published artifact | Rejected — the same class of mistake as editing a merged migration |
| D. A `settings.kelir` namespace | Namespace the extension | Rejected — `settings` is already the implementation's namespace; a `kelir` level namespaces Kelir against itself |

### A. `settings` — chosen

`settings` is the one object the specification declares `additionalProperties: true` and describes as global form configuration, which makes it **the extension point a frozen standard leaves an implementation**. Bound on `id` rather than `key` because §4.1 makes `id` unique per component *instance*, while a `key` inside a datagrid row template lives in the row's scope and two components may legitimately share one.

### B. A new major version

The right design and the wrong scale: a new major version of a Final Standard means a new meta-schema, a migration story for every stored definition, and a conformance clause saying what a v2 document means to a v3 validator. Taking that inside a sprint would have been deciding the standard's future to save a level of nesting.

### C. Editing the artifact

The file is the published artefact its `$id` names; a definition validated by two different v2.0.1 schemas is exactly the drift the byte-comparison test in `rad_jfss_meta_schema.rs` exists to prevent.

## 4. Consequences

**Positive** — lookups shipped without breaking a frozen standard or invalidating a stored definition, and the rule generalizes: a future Kelir extension takes its own key beside `lookups`.

**Negative, recorded rather than hidden** — the binding does not sit on the component it binds, which departs from JFSS's own component-driven philosophy, and a reader of a definition has to look in two places.

**Left open** — if a second Kelir extension needs `settings`, the shape of that object becomes a contract worth writing down, and the place for it is Kelir's own documentation rather than JFSS.

### 4.1 Impacted Documents

| Document | Change | Status |
|---|---|---|
| [SDD](../../design/01.%20System%20Design%20Document.md) §8.2.1, [Database Schema](../../design/02.%20Database%20Schema.md) §5.12, §5.13 | Already updated when the decision was taken | No change |
| [JFSS](../../schema/JSON%20Form%20Schema.md) | Deliberately untouched | No change |

## 5. Compliance

`rad_jfss_meta_schema.rs` compares the extracted meta-schema byte-for-byte with the specification's fenced block, so option C cannot happen by accident. `validate_definition` accepts a lookup-carrying form as conformant v2.0.1, and `rad_lookups.rs` holds the binding.

## 6. Revisit When

A second extension needs `settings` — at which point the object's shape is written down here — or a JFSS successor version becomes a project in its own right, which is when option B is on the table properly.
