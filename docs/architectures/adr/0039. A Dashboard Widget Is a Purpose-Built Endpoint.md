# ADR-0039 — A dashboard widget is a purpose-built endpoint, not a RAD list definition

**Status:** Adopted · **Last updated:** 2026-09-12

**Decision date:** 2026-09-12 · **Deciders:** product owner, at Phase 8 planning · **Supersedes:** — · **Superseded by:** — · **Related:** **D-78**, **D-77**, [ADR-0037](0037.%20ERP%20Posting%20Runs%20Inside%20the%20Document%20Transaction.md), FR-RPT-001 … FR-RPT-005, [#431](https://github.com/sujanto-gaws/kelir/issues/431)

## 1. Context

Phase 8 opens on the dashboard, and **Kelir has two ways to put rows on a screen.**

[Architectures/06](../06.%20Building%20an%20ERP%20on%20Kelir.md) §7 states them as paths that **do not converge**:

| Path | Rows are | Built by |
|---|---|---|
| RAD list | the documents of every type that names the list | configuration, no code |
| Written report | whatever the statement selects | an endpoint and a page, per report |

[SDD](../../design/01.%20System%20Design%20Document.md) §8.2.4 is explicit about the first: **the rows of a list are documents**, and its own example column keys are `document_number` and `form_data.amount`. `ListRenderer` and `rad:list:*` exist, are shipped, and were exercised through Sprints 14 and 15.

**What forces the question now is the shape of Phase 8's five widgets**, which is a fact about the requirements rather than a preference:

| Requirement | The rows are | A RAD list would serve it |
|---|---|---|
| FR-RPT-001 — dashboard summary | counts, not rows at all | **no** |
| FR-RPT-002 — pending tasks | `workflow_tasks` | **no** |
| FR-RPT-003 — recent documents | `documents` | **yes** |
| FR-RPT-004 — document status summary | an aggregate over statuses | **no** |
| FR-RPT-005 — overdue tasks | `workflow_tasks` | **no** |

**One of five fits the configured path, and it fits it genuinely.** FR-RPT-003 is a page of documents; a list definition would render it today with no code at all, which is what `ListRenderer` was built for.

Three constraints bound the choice:

- **`modules::reporting` is one line** — `// reporting module scaffold.` — and `DashboardPage.vue` is 81 lines whose only data call is `/version`. Nothing is built, so nothing is being migrated; this is a choice about the first thing written rather than a reversal.
- **[Architectures/06](../06.%20Building%20an%20ERP%20on%20Kelir.md) §10 already carries the failure mode in its risk register**, third row: *a list definition format stretched until it breaks, discovered months in*. The mitigation it names is **§7's two paths, stated before the first report is written** — and this is that moment.
- **The visibility rules for the two row types are not the same rule.** A document is visible on tenant plus `document:read` and no third condition (`document/repository/list.rs`); a task is visible when the caller is its assignee, or it is unassigned and they hold its candidate role in its candidate department (`workflow/repository/inbox.rs`). Two paths over two rules is two places for either rule to be re-derived.

The question was raised at Phase 8 planning on 2026-09-12, **before the first widget was written**, and **D-77** — which gave the phase a second sprint — is what made room to answer it rather than discover it.

## 2. Decision

**Kelir serves every dashboard widget from a purpose-built endpoint in `modules::reporting`, and ships no FR-RPT row as a RAD list definition.** The dashboard is one screen with one contract: a single summary endpoint that the widgets extend, one permission in front of it, and one place where *what may this viewer see* is answered. This covers FR-RPT-001 through FR-RPT-005 — every widget in Phase 8 — and it covers the dashboard only. **It decides nothing about RAD lists on their own screens**, where a list definition remains the way a deployment builds a page of documents without code, and it decides nothing about the ledger reports [architectures/06](../06.%20Building%20an%20ERP%20on%20Kelir.md) §7 anticipates, which are the same written-report path arriving for a different reason.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. One purpose-built contract for the whole dashboard** | Every widget is served by `modules::reporting`; no FR-RPT row is a list definition | **Chosen** |
| B. Per-widget choice | FR-RPT-003 ships as a RAD list definition because its rows genuinely are documents; the other four are endpoints | Rejected — four widgets fetched four ways is four surfaces to secure and two answers to *what may this viewer see* |
| C. Everything through `ListRenderer` | Extend the list definition format until it can express tasks and aggregates | Rejected — this is [architectures/06](../06.%20Building%20an%20ERP%20on%20Kelir.md) §10's third risk, written out |

### A. One purpose-built contract — chosen

It wins on the count in §1 and on the visibility rules underneath it. **Four of five widgets need a written statement anyway**, so the choice is not *configuration versus code* but *one path or two*, and the fifth is the one that would be different.

What it buys is that the dashboard has **one contract that the later widgets extend rather than bypass**. FR-RPT-002 and FR-RPT-003 inherit FR-RPT-001's endpoint, its permission and its card; Sprint 18's two inherit the same. A second dashboard endpoint added later is the defect this shape exists to prevent, and it is the one worth naming because it arrives quietly — as *just this one widget, which is different*.

**What it does not solve:** a deployment that wants to change what is on its dashboard must now ask for code, where a list definition could have been configured. That is a real loss and §4 states it rather than hiding it. It is bounded by the fact that Kelir's dashboard is a product surface rather than a tenant's report: the configurable surface is RAD lists, and it still exists.

### B. Per-widget choice

**This was the serious alternative and it was not dismissed on principle.** It would have bought FR-RPT-003 for nearly nothing — a list definition, no endpoint, no page, no permission — and the row that would have paid for it is the cheapest `Must` in the phase precisely because its rows *are* documents.

What ruled it out is what the dashboard becomes when its widgets disagree about how they are fetched:

- **Four surfaces to secure rather than one.** The list path answers *what may this viewer see* with `rad:list:read` plus the document rule; the reporting path answers it with the reporting permission plus the row's own scoping. A dashboard carrying both has two answers to that question on one screen, and the next widget's author has to know which one applies.
- **Two shapes to page.** A rendered list carries the list envelope and the definition's columns; a widget endpoint carries the widget's payload. A card that is one shape on Tuesday and the other on Wednesday is a frontend that special-cases per widget.
- **The saving is one-off and the cost recurs.** FR-RPT-003 is built once; every widget after it inherits the question of which path it is on.

It is worth recording that **this option remains correct for its own job**. A deployment building *my open requisitions* as a page of its own should use a list definition, and nothing here discourages that.

### C. Everything through `ListRenderer`

The tempting unification: one renderer, one definition format, no second architecture. It would have bought a single path and a configurable dashboard.

It is ruled out by [SDD](../../design/01.%20System%20Design%20Document.md) §8.2.4 rather than by taste — **the rows of a list are documents**, and `workflow_tasks` rows are not documents and an aggregate over statuses is not a row at all. Reaching them means widening the definition format until it can express a join, a predicate over a role grant, and a `GROUP BY`. [Architectures/06](../06.%20Building%20an%20ERP%20on%20Kelir.md) §10's third risk is exactly this attempt, and the failure it names is **discovered months in** — after the format has been stretched, after definitions in the field depend on the stretch, and after the stretch is the thing that has to be unpicked.

## 4. Consequences

**Positive** — The dashboard has one contract, one permission and one scoping story, and FR-RPT-002 through 005 extend it instead of each choosing. `ListRenderer` is left as the thing it was designed to be — a page of documents built by configuration — rather than becoming a general query surface under pressure from five widgets, four of which it cannot serve. The choice is made while `modules::reporting` is one line, which is the only moment it costs nothing.

**Negative** — **The dashboard is not configurable by a deployment**, and FR-RPT-003 in particular is built with code that a list definition would have produced for free. Every future widget costs an endpoint, a handler, a statement and a page, and there is no configuration path that shortens it. **A tenant that wants a sixth card must file a requirement, not write a definition.** That is the price, it is paid per widget, and it is the reason option B was argued rather than waved away.

**Neutral** — `modules::reporting` becomes a module with the ordinary shape — domain, repository, service, handlers — rather than a place where list definitions are seeded. The reporting permission joins the catalogue as a surface permission rather than a data one. *Widget* becomes vocabulary in the code and the documents, meaning *one card on the dashboard, served by the summary contract*.

## 5. Compliance

**`reporting_dashboard.rs` is what a violation fails**, and it checks the half that can be checked mechanically: the dashboard's data reaches the browser through `modules::reporting`'s summary endpoint, behind `reporting:dashboard:read`, with the viewer's scoping applied in the statement.

**What no test can check is the negative** — *no FR-RPT row ships as a list definition* is a statement about code that does not exist, and a test asserting the absence of a seeded list definition would pass for a project that had simply not got there yet. So the reviewer's line is stated instead, and it is narrow enough to apply: **a pull request closing an FR-RPT issue that adds a row to `rad_lists` or a `list_id` to a document type is this decision being reversed**, and it needs a superseding record rather than a review comment.

The first half is worth more than it looks: the failure this record guards against is not somebody arguing for list definitions, it is **a second dashboard endpoint appearing beside the first** because one widget was different. The summary contract being the only route the page calls is what makes that visible in a diff.

## 6. Revisit When

- **A deployment asks to change its own dashboard**, rather than asking for a widget Kelir does not have. §4's stated cost is that this is impossible; the first real request for it is the force that was absent in §1, and it reopens option B for the widgets whose rows are documents.
- **A widget is asked for whose rows are documents and whose columns a tenant wants to choose** — FR-RPT-003 with per-tenant columns, say. That is a list definition wearing a card, and it is the case where the boundary this record draws is in the wrong place.
