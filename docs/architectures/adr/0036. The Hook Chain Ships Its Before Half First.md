# ADR-0036 — The Hook Chain Ships Its Before Half First

**Status:** Draft · **Last updated:** 2026-09-05

**Decision date:** — · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** [ADR-0008](0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md), [ADR-0016](0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md), [ADR-0034](0034.%20One%20Delivery%20Attempt,%20Recorded%20Rather%20Than%20Retried.md), [ADR-0035](0035.%20Rules%20Are%20Resolved%20Before%20a%20Form%20Is%20Published.md), `D-69`, FR-WF-005, issue [#339](https://github.com/sujanto-gaws/kelir/issues/339)

## 1. Context

**The document lifecycle hook chain has been specified since the founding architecture and built by nothing.** [Architectures/01](../01.%20Basic%20Framework%20Concept%20and%20Architecture.md) §12 defines a catalogue of forty hook names across twenty lifecycle stages, four registration sources merged into one ordered chain, and execution rules covering ordering, timeouts, isolation and logging. The [Lifecycle Hook Contract](../../schema/Lifecycle%20Hook%20Contract.md) makes three of its shapes a plugin ABI. `document_lifecycle_hooks` and `document_hook_executions` have been in the schema since `0015_document.sql`. **None of it had a reader**, and `workflow::service::engine`'s own module doc said so in the words *there is no chain*.

Sprint 14 reached it from an unexpected direction. FR-WF-005 (`SERVICE_TASK`) is *a step the product performs rather than a person*, and [#339](https://github.com/sujanto-gaws/kelir/issues/339) found it in the worst of the three possible states: the value was in JWSS's `taskType` enum, a definition declaring it validated and published, and the engine then **generated a human task that sat in somebody's inbox waiting for a person who was not coming**. Worse than refusing it, because it failed silently and late.

Closing that needs somewhere for the step to live. Three facts bounded the answer:

- **JWSS's `taskSpec` cannot say what a service task does.** No `service`, `action` or `config` property; `assignment` is required even on a task with no assignee. The only executable thing a transition can declare is its `guards` and `actions`, which JWSS §7 already routes into the hook chain.
- **`AUTO` transitions do not fire.** The action is in the vocabulary, the meta-schema models it fully — it forbids `allowedBy` and forces `requiresComment: false` — and nothing drives one. The engine's module doc named FR-WF-005 as the `Should` that would.
- **There is no outbox.** §12.5 specifies an after-hook as *published to the outbox in the same transaction, executed by the worker*. Kelir delivers notifications through a worker over `notifications` — a queue for one subject, chosen in [ADR-0034](0034.%20One%20Delivery%20Attempt,%20Recorded%20Rather%20Than%20Retried.md) — and `notification::service` records that a general outbox is Phase 8.

## 2. Decision

**Kelir builds the before half of the lifecycle hook chain, drives it from a service task's `AUTO` transition, and leaves after-hooks unbuilt until there is an outbox to deliver them through.** `modules::hook` implements LHCS §2's handler grammar, §3's registration entry with §3.1's priority bands, §4's invocation payload in full — every field present, inapplicable ones `null` — §5.1's `CONTINUE`/`MODIFY`/`REJECT`, §6's `HOOK_REJECTED` envelope and §7's execution log. A closed `core:` registry resolves handler references **at publish**, so an unknown handler is refused to the author rather than discovered by the first document to reach the transition. One hook name fires: `before_workflow_transition`, from a state whose task is a `SERVICE_TASK`, taking that state's `AUTO` edge inside the transaction that reached it. **An `AUTO` edge with no service task on its state still does not fire**, and a chain of automatic steps is bounded rather than cycle-checked. JWSS `actions` remain stored, validated and never invoked, and every `plugin:` reference is refused while no plugin runtime exists.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Build the before half; a service task drives it** | The contract's synchronous half, over the one stage that needed it | **Chosen** |
| B. A service task advances and runs nothing | No hook chain at all; the "step" is the advance | Rejected — closes the defect and leaves *the engine performs the step* with no step, in the sprint whose own reason for scheduling this was that the rule engines make one meaningful |
| C. Extend JWSS with a `taskSpec.service` action | A service task sets a variable from an expression | Rejected — invents a second execution surface beside the `guards` JWSS §7 already routes into the hook chain, and the chain is the one architectures/01 calls the hosting mechanism |
| D. Build after-hooks too, synchronously | The whole contract at once | Rejected — §12.5 forbids exactly this: an after-hook runs post-commit, and running one in the caller's transaction makes a fire-and-forget handler able to roll back the thing it was told about |
| E. Build after-hooks over a second private queue | Deliver them now, outbox later | Rejected — two queues to reconcile when the outbox lands, and the first one would set the retry and circuit-breaker semantics §12.5 assigns to the outbox worker |
| F. Make every `AUTO` transition self-firing | No task type needed; the edge drives itself | Rejected — see below |

### A. The before half, driven by a service task — chosen

**It is the half that fits the transaction Kelir already has.** A before-hook is *synchronous, inside the caller's transaction* (§12.5), and a workflow transition is already one transaction holding a locked instance. Nothing had to be invented for it: the chain runs where `fire` already runs, a `REJECT` rolls back what a `REJECT` should roll back, and the execution log is written by the same transaction — so a refused chain leaves no trace, which is right, because nothing happened to the document.

**And it is the half a service task needs.** A guard can `REJECT` (the automatic step is refused and the approval that reached it is undone) or `MODIFY` (the step changes the form payload). Those are the two things *a step the product performs* can usefully be, and both are in LHCS §5.1 already.

**What it does not solve:** the other thirty-nine hook names in the catalogue. `before_document_submit`, `before_document_approve` and the rest are valid registrations that fire nothing. That is a smaller claim than §12.3 makes and a larger one than the day before, and `modules::hook`'s module doc is where a reader finds the boundary rather than inferring it.

### F. Every `AUTO` transition self-firing

The tempting simplification, and it changes what a definition means. `AUTO` says *how* an edge is taken — without a caller — and it is already used to model an edge the engine may take rather than one it must. A state with an `AUTO` exit and no service task is a definition parking a process somewhere; making every such edge self-firing would turn a parked state into one the engine runs straight through, silently, in every definition already published.

**So the task type is the driver and the action is the mechanism.** They answer different questions, and a workflow author sets both.

### B. Advance and run nothing

Defensible, and it was the recommendation until the product owner chose otherwise. It closes the defect — no phantom task, the instance advances — and leaves AC1's *the engine performs the step* satisfied only in the sense that advancing is a step. The cost is that FR-WF-005 would have shipped as a state machine feature in the sprint whose stated reason for scheduling it was that the rule engines make *set a field from a rule* meaningful.

### D and E. After-hooks now

**§12.5 is unusually specific about why not.** An after-hook is idempotent, at-least-once, retried on a schedule and cut off by a circuit breaker; all four of those are the outbox worker's properties, not a handler's. Building the invocation without them would produce something that looks like an after-hook, is called in the same places, and has none of the guarantees the contract promises handlers written against it — which is the shape [#339](https://github.com/sujanto-gaws/kelir/issues/339) itself is about, one layer up.

## 4. Consequences

**Positive** — the chain exists, with the ABI its specification defines rather than a subset shaped by one caller; a handler reference is resolved where the author is (LHCS §2, and the same discipline [ADR-0035](0035.%20Rules%20Are%20Resolved%20Before%20a%20Form%20Is%20Published.md) applied to form rules a day earlier); every execution is logged as §7 requires; and `SERVICE_TASK` stops being a vocabulary entry that produces a task nobody will do.

**Negative** — the contract is half-implemented, and half of a published ABI is a thing readers must be told about rather than discover: a definition author's `actions` are validated and never run. `MODIFY` is implemented in the chain and **refused** at the workflow call site, because applying a modified payload needs the re-validation §5.1 requires and that belongs beside the submit path's `secure_payload`; a guard returning `MODIFY` therefore fails rather than taking effect, which is honest and is not what a handler author will expect. `guards` fire only on an automatic transition — a decided one does not yet invoke them. Three core handlers is a small registry, and the catalogue's own example (`core:require_attachment`) is not among them because it would need database access this signature deliberately does not carry.

**Neutral** — a new top-level module (`modules::hook`), a `revision` on `Graph` so the execution log can record `<workflowKey>@<revision>:<from>-><to>`, and a bound (`MAX_AUTOMATIC_STEPS`) rather than a publish-time cycle check over the `AUTO` subgraph.

## 5. Compliance

`modules::hook`'s unit tests hold the contract: §2's grammar against eight malformed references, §3.1's bands and their floors, §4's *every field present even when null*, §3.2's kind constraint, and the merge's stable tie-break. `tests/workflow_system_tasks.rs` holds the engine: a `SERVICE_TASK` writes no `workflow_tasks` row, the instance advances two states on one decision, a rejecting guard leaves the document where a person can act, a service state with no `AUTO` exit stays put rather than failing, a loop of them is refused, and a guard's execution is in `document_hook_executions` — with the paired assertion that a *rejected* chain leaves none.

A reviewer checks one thing no test can: that a new hook stage is added by calling `run_before_chain` rather than by growing a second invocation path. The chain's guarantees — the log, the budget, the payload's full shape — are properties of that function, and a second caller assembling its own payload would have none of them.

## 6. Revisit When

The outbox lands (Phase 8), at which point after-hooks become buildable and this decision's main negative expires. Or a plugin runtime lands, at which point §12.5's isolation rule — *a plugin hook panic must never abort a core transaction it did not veto* — stops being vacuous and needs an answer this ADR does not give.
