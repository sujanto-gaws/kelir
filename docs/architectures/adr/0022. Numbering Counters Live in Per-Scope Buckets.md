# ADR-0022 — Numbering Counters Live in Per-Scope Buckets

**Status:** Adopted · **Last updated:** 2026-09-01

**Decision date:** 2026-08-26 (`D-21`); refined 2026-08-28 (`D-35`) · **Deciders:** Product owner · **Supersedes:** — · **Superseded by:** — · **Related:** `D-21`, `D-35`, [ADR-0002](0002.%20SQLx%20with%20Compile-Time%20Verified%20Queries.md), [ADR-0003](0003.%20PostgreSQL%20as%20the%20Only%20Database.md)

## 1. Context

**Recorded retrospectively on 2026-09-01** from `D-21` and `D-35` in [Product Backlog](../../../projects/planning/02.%20Product%20Backlog.md) §6.1; the operative statement is [Database Schema](../../design/02.%20Database%20Schema.md) §6.3 and §6.3.1 (standard §9).

`document_type_numbering_rules` held **one** `sequence_key`/`next_sequence` pair, and the Database Schema stated that as the design — *"One bucket per rule."* A `DEPARTMENT_YEAR` rule needs one bucket **per department**, live at the same time. The allocator restarted the counter whenever the computed key differed from the stored key and was not judged earlier, and two departments are never earlier than one another — so allocating for A, then B, then A, then B issued `000001` four times (#200). Release-blocking for `v0.4.0`, and unfixable without a migration.

A second defect on the same path (`D-35`, #118's shape): a gap-tolerant rule's `allocate_committed` opens a transaction of its own — that is what `AllowGaps` *means* — so calling it from inside the submit's transaction held two pooled connections per submit, which [coding standard](../../standards/01.%20Coding%20Standard.md) §2.5 forbids. Twenty-four concurrent submits answered `500` after the acquire timeout.

## 2. Decision

**The counter moves to one row per scope value — `document_type_sequence_buckets`, keyed `(document_type_id, sequence_key)` — and `DEPARTMENT_YEAR` stays.** Allocation is one `INSERT … ON CONFLICT DO UPDATE … RETURNING`. **A gap-tolerant rule allocates on the pool, before the submit's transaction opens**; a gapless rule allocates inside it, which is what makes it gapless.

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. Per-scope bucket rows, keyed on the document type** | One row per live scope value | **Chosen** |
| B. Drop `DEPARTMENT_YEAR` | One line in the migration | Rejected — deletes a capability from a published v1.0.0 standard to work around an implementation defect |
| C. Deprecate the two counter columns in place | The release process §6 N−1 rule | Rejected — no released binary has ever seen this table, so there is no release N to deprecate them in |
| D. Re-evaluate on the pool, then write under a lock | Keeps the no-burn behaviour and satisfies §2.5 | Rejected (`D-35`) — adds a 409 a concurrent edit can raise on a submit that was going to succeed |
| E. Make every rule gapless | One policy, no ordering question | Rejected — deletes a capability #158 built and serialises every submit of a busy type |

### A. Buckets — chosen

**Keyed on the document type rather than on the rule**, because a rule row is replaced on every edit and a sequence that reset when somebody corrected a template would re-issue numbers just as surely. That makes *"replacing a rule does not un-issue the numbers the old one produced"* true by construction instead of by the `highest_issued` check that used to carry it. One upsert means there is no read to race, and two scope values do not contend at all.

`D-35` then placed the allocation where §2.5 says to resolve what a request points at: the document's status, type and department are read on the pool, the policy is read on the pool, and a gap-tolerant rule allocates there, committed, with nothing else held.

## 4. Consequences

**Positive** — concurrent departments allocate independently and correctly; a submit holds one connection.

**Negative, accepted** — a gap-tolerant rule **now loses the number a refused submission took**. That is the trade #158 named — *a number allocated to a submission that then fails is gone* — so it restores the stated policy rather than weakening it; the previous behaviour kept the number, which was an accident of ordering that the code had written down as a property and had bought with a rule violation. A gap-tolerant sequence has holes where submissions were refused, which is what a deployment chooses that policy knowing.

**Not settled** — the back-dating refusal. Reaching into a passed bucket used to *restart* it; buckets persist now, so it would resume correctly. It is still refused, on the different ground that a closed period should not gain new numbers — a policy rather than a safety property, and the product owner's to revisit.

**The rule the second finding argues for, and it is the larger half** — *a fix for a rule violation is checked against the rule, not against the test that exposed it*: both halves of that defect were twelve lines apart in one function.

## 5. Compliance

`two_departments_run_separate_sequences` in `document_numbering.rs` makes three moves rather than two, so the broken property cannot pass again; `concurrent_submits_of_a_gap_tolerant_type_do_not_exhaust_the_pool` is red under the allocation moved back inside the transaction. Migration `0020_numbering_buckets.sql` carries the schema change.

## 6. Revisit When

Back-dating into a closed period is asked for, or a numbering scope arrives that is not expressible as a `sequence_key` — the assumption the bucket table's primary key rests on.
