## 1. Context

**A password change, a self-service reset and an administrator's set-password each revoke every refresh token of the user** ([SDD](../../design/01.%20System%20Design%20Document.md) §11.1, D-107). The revoke is one statement, `UPDATE refresh_tokens … WHERE user_id = $1 AND revoked_at IS NULL` (`revoke_all_for_user`). Under READ COMMITTED it sees the tokens committed when it starts, and no later one. What existed when the question arose:

- **The password writes.** `change_own_password` and `set_password` wrote the hash on the pool, then revoked on the pool, as two statements in no transaction. `reset_password` wrote the hash in a transaction, committed, and revoked after the commit.
- **The paths that store a token.** A sign-in verifies the password against the hash it read, on a blocking thread, which takes as long as Argon2 does. It then inserts its refresh token on the pool. A refresh rotates in one transaction since #751: it revokes the presented token, `rotated`, and inserts the new one. Neither took any lock on the user.
- **Two windows, each found by a probe.**
  - **#756**, from #754's gate: a revoke that starts while a rotation sits between its `UPDATE` and its commit waits on the old token's row, skips it once the rotation commits, and never sees the new token, inserted after its snapshot.
  - **#788**, record 24's finding 1: a sign-in that verified the old password during a password write stores its token after the revoke has run.
  - Either way a refresh token outlives the password write for its 30 days. Serially, neither order gives that result.
- **The other user-wide revokes have a second check.** A deactivation, a deletion, a tenant's suspension and a replay sweep are re-read by every refresh: the user's status (`can_sign_in`), and the tenant's (`admits_session`, #649). A token stored past one of them is refused at its first refresh. **A password has no such second check**: nothing a refresh reads moves with it.
- **Record 23 §5 states the lock rules the product keeps.** §5.1: every stamping foreign key takes the acting user's row `FOR KEY SHARE`, and nothing takes a `users` row in a mode that conflicts with it. That stays true only while no path locks a user `FOR UPDATE`, deletes one outright, or changes its id.
- **Plan 21 row 6** names #756's remedy as a lock between a rotation and every user-wide revoke, and asks for this record. #788's *Done when* asks that the sign-in path follow the same rule.

## 2. Decision

**Kelir takes the user's row before any refresh token row, and a password write revokes in its own transaction.**
- **A password write** (`change_own_password`, `reset_password`, `set_password`) runs its `UPDATE users` and `revoke_all_for_user` in one transaction, the `UPDATE` first, and commits after the revoke.
- **A path that stores a refresh token** (a sign-in, and a refresh's rotation) takes the user's row `FOR SHARE` in its transaction before it writes any token (`identity::repository::lock_password_hash_for_session`).
- **A sign-in compares the hash it verified with the hash it reads under that lock.** If they differ, it refuses: 401 `UNAUTHORIZED`, with a `Security.SignInFailed` row whose reason is *the password changed during the sign-in*. It is not counted towards a lockout.
- **`FOR SHARE`, not `FOR KEY SHARE`.** Only `FOR SHARE` conflicts with the `FOR NO KEY UPDATE` a password write's `UPDATE` takes.

**Scope.** It covers the three password writes and the two paths that store a token. It leaves the other user-wide revokes as they are, unlocked, because a refresh re-checks what they change. It does not touch access tokens, which a password write does not end (D-104, ADR-0045).

## 3. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| **A. The user's row before the token's** | Password writes hold the user's row through their revoke; token writers take it `FOR SHARE` first; a sign-in re-checks its hash | **Chosen** |
| B. A credential epoch checked at refresh | A counter on the user, bumped by every password write and copied onto each token; a refresh refuses a token whose epoch is behind | Rejected — a migration, a second check on every refresh, and a token that stays stored and live until it is presented |
| C. Revoke after the commit, as it was | One revoke statement, outside the password write's transaction | Rejected — it is #756 and #788 |
| D. `SERIALIZABLE` for the auth paths | Let the database find the conflicting interleavings | Rejected — retries on every sign-in and refresh path, and it does not see a hash a sign-in verified outside the transaction |

### A. The user's row before the token's — chosen

**The two sides meet on one row, so they cannot interleave.**
- **A token writer that takes the row first** commits its token before the password write's `UPDATE` is granted. The write's revoke is a later statement, with a later snapshot, so it sees that token.
- **A password write that takes the row first** holds it until its revoke has committed.
  - A rotation that reaches the lock then finds its own token revoked, so its `UPDATE … WHERE revoked_at IS NULL` changes nothing, and #710's branch refuses it as `password changed`.
  - A sign-in that reaches the lock reads the new hash, and refuses.

**The re-check is what closes #788**, not the lock alone. A sign-in that verified the old hash and reaches the lock after the write committed holds nothing the write waited on. Without the comparison it would store a token the revoke never saw.

**It takes no new mode on `users` that record 23 §5.1 rules out.** `FOR SHARE` and `FOR NO KEY UPDATE` conflict with each other, and neither conflicts with `FOR KEY SHARE`. So a stamping foreign key still waits on nothing. Nothing here takes a user `FOR UPDATE`.

**It closes no cycle.**
- A token writer holds only the user's row when it locks or writes a token. Its token `INSERT` takes `FOR KEY SHARE` on the same user through the foreign key.
- A password write holds the user's row, then the user's token rows.
- A rotation that holds the user `FOR SHARE` and then waits on its token's row waits on a revoke that holds no user lock: a replay sweep, a deactivation's revoke. None of those waits on a user.

**What it does not solve.** An access token issued before a password write stays valid until it expires, at most 15 minutes (D-104). A sign-in or a rotation now waits for a password write in flight, which is one statement and a revoke.

### B. A credential epoch checked at refresh

A `credential_epoch` on `users`, bumped by every password write, and copied onto every refresh token by the sign-in that verified it and by each rotation. A refresh refuses a token whose epoch is behind the user's. **It would have closed both windows without a lock**, and made the revoke a sweep rather than the guarantee.
- **It costs a migration on two tables**, and a second read of the user on every refresh.
- **A token a sign-in stored past the write stays stored and live.** It is refused only when it is presented, which is no worse for a thief but leaves the table saying something false. Every report of live sessions would have to join the epoch.
- **The sign-in must still carry the epoch it verified from its read to its insert.** That is option A's comparison with a column added.

The lock needs no schema change and keeps `revoked_at` the single answer to "is this session live".

### C. Revoke after the commit, as it was

The reset path revoked after its commit on purpose: *"a revoke that rolled back with a failed password change would cut sessions short for nothing."* **Inside the transaction, a revoke rolls back with the change**, so the sessions are kept exactly when the change is. Outside it, the revoke runs once the row is released, and a token stored between the two escapes it. That is #756.

### D. `SERIALIZABLE` for the auth paths

Serializable isolation would detect a rotation and a revoke that read each other's rows, and fail one. **It needs a retry loop on every sign-in, refresh and password write**, and an error class the auth module does not have today. **It does not reach #788 by itself**: the sign-in's verify reads the hash outside any transaction, on a blocking thread, so the conflict is between a read the database never saw and a write.

## 4. Consequences

**Positive**
- A refresh token never outlives a password write, whichever order a sign-in, a rotation and the write run in.
- The guarantee lives in the database's lock table, and the five tests in `tests/auth_session.rs` stage both windows deterministically.
- The reset path's revoke now rolls back with a failed reset, instead of running after a commit that might never be followed by it.

**Negative**
- **A sign-in and a refresh now open a transaction and take a row lock** that they did not before. Concurrent sign-ins of one user share the lock and do not wait on each other. They wait only on a password write, or on an `UPDATE` of the user's row (`record_successful_login`, `record_failed_login`, an administrator's edit), each one statement.
- **A sign-in overtaken by a password write answers 401** with the password that was right when it was checked. The user signs in again with the new one, which is what a sign-in a moment later would have required.
- **A password write's revoke now holds the user's row for one more statement.** A user with many live tokens holds it longer.

**Neutral**
- A new audit reason on `Security.SignInFailed`, *the password changed during the sign-in*.
- `issue_session` is gone. A sign-in mints before its transaction and stores inside it, as a refresh already did.

## 5. Compliance

- **`tests/auth_session.rs`, the *ADR-0048* section**, fails if a password write revokes outside its transaction, if a token writer skips the lock, or if a sign-in skips the comparison:
  - `a_password_change_during_a_rotation_ends_its_new_token` and its set-password twin hold a rotation at its token's insert, with a `BEFORE INSERT` trigger on an advisory lock;
  - `a_password_change_during_a_sign_in_ends_its_token` and its set-password twin hold a sign-in the same way;
  - `a_sign_in_that_verified_a_password_written_since_is_refused` holds the password write's transaction open while the sign-in waits.
  - All five failed against the code before this record, with the probes' own results: a live token refreshed 200, and a sign-in answered 200.
- **A reviewer of any new path that stores a refresh token, or writes `users.password_hash`, checks it against §2.** That means `lock_password_hash_for_session` before the token, or the `UPDATE` and the revoke in one transaction.

## 6. Revisit When

- **A second credential is added** (a passkey, a one-time code, an external identity provider): the hash comparison no longer says whether the credential the sign-in proved is the current one.
- **Sign-in or refresh latency under load shows waits on `users` rows** in the NFR-PERF-001 measurement (#777), or the product adds a user-row write on every request.
