# Building an ERP on Kelir

**Status:** Draft · **Last updated:** 2026-09-12

This document describes the architecture of an **ERP built on top of Kelir** — what the platform already provides, what it has no concept of, and the layering that connects the two without forking the framework.

It is written ahead of any scope decision. Nothing in it is scheduled, no `FR-*` covers it, and the [SRS](../requirements/srs.md) does not mention an ERP. It exists so that the shape is decided before the first line is written rather than discovered halfway through, and so the platform changes it forces (§7) are recognised as platform work rather than smuggled in as application work.

Related documents:

- The lifecycle stages and hook model this architecture hangs on: document [01](01.%20Basic%20Framework%20Concept%20and%20Architecture.md) §12.
- The document, RAD and workflow designs it builds over: [SDD](../design/01.%20System%20Design%20Document.md) §8.
- The integration layer, which is where the *external* half of an ERP's obligations live: document [03](03.%20Kelir%20Modules%20for%20Interfacing%20with%20External%20Systems.md).
- The posting placement decision: [ADR-0037](adr/0037.%20ERP%20Posting%20Runs%20Inside%20the%20Document%20Transaction.md).

# 1. The Framing This Reverses

**Every ERP reference in the current documentation set treats ERP as an external system Kelir talks to.** Document [03](03.%20Kelir%20Modules%20for%20Interfacing%20with%20External%20Systems.md) §6.1 is titled *Purchase Requisition to ERP*; `external_systems.system_type` carries `'ERP'` as a value; document 01 §12.3 lists *"Write to ERP"* as the example of what an `after_document_post` hook does; and document [04](04.%20Kelir%20Plugin%20and%20Extension%20Management%20Concept.md) §12.2 names an *ERP Integration Plugin*. In all of them the ledger is somebody else's.

This document assumes the opposite: **the ledger is ours**. That single inversion changes what the hook chain is for, what a document's completion means, and what the integration layer is still needed for — which is why it is written down rather than left as a shared assumption.

The integration layer does not become redundant. It stops carrying the general ledger and starts carrying what an ERP genuinely must exchange: bank files, e-invoicing, tax portals, e-signature, HRIS and CRM. Those are §9's territory and are unaffected by everything below.

# 3. What Kelir Has No Concept Of

The other half of an ERP is not documents. It is **accumulators**: values that carry a running balance, must answer *what is it now*, and must answer *what was it at period end* years later.

Kelir stores a document's data as `form_data_json`, a JSONB payload pinned to a form revision ([ADR-0027](adr/0027.%20A%20Document%20Pins%20the%20Form%20Revision%20It%20Was%20Filled%20Against.md)). **There is no table in the schema where a quantity or an amount accumulates.** Specifically absent:

1. **A general ledger** — accounts, journals, entry lines, and balances by account × period × cost centre.
2. **A stock ledger** — on-hand by item × warehouse × lot, with a valuation method behind it.
3. **Open-item subledgers** — AR and AP with partial settlement, matching, and aging.
4. **Fiscal period control** — a period that can be *closed*, after which nothing may post into it.
5. **Posting** — the moment a document becomes financially real and irreversible. The `POST` lifecycle stage is specified in document 01 §12.1 and §12.3 and **is implemented by nothing**; `DocumentStatus` terminates at `COMPLETED`.
6. **Reversal** — an ERP never edits a posted document; it posts a contra entry.
7. **Line items with identity** — a JFSS datagrid row lives *inside* a JSON payload. A purchase-order line that a receipt consumes 30 of and an invoice matches 25 of needs its own row, its own remaining quantity, and its own foreign keys.
8. **Currency, FX rates and tax** — nothing. `currency_uom` on a product is a label, not a monetary type.
9. **Budget commitment** — reserving budget when an order is approved and releasing it when the invoice posts.

> Kelir is a state machine over documents. An ERP is a state machine over documents **plus the ledgers those documents move**. The second part is the whole of the work.

# 4. The Layered Architecture

The modular monolith stands ([ADR-0004](adr/0004.%20A%20Modular%20Monolith%20with%20a%20Flat%20Module%20Layout.md)). Kelir is not forked; it gains tiers.

```text
+------------------------------------------------------------------+
|  TIER 1 — Kelir Platform (unchanged, upstream-mergeable)          |
|                                                                   |
|  auth · identity · roles · organization · master_data · rad       |
|  document_type · document · workflow · task_inbox · hook          |
|  attachment · comment · activity · audit · notification           |
|  integration · plugin                                             |
|                                                                   |
|  Knows: documents, forms, workflows, parties, tasks.              |
|  Knows nothing about: debits, stock, fiscal periods.              |
+------------------------------------------------------------------+
            |                                     ^
            | invokes before_document_post        | reads master data
            v                                     | through its service
+------------------------------------------------------------------+
|  TIER 2 — Posting Seam  (modules/posting)                         |
|                                                                   |
|  The only module that knows both vocabularies.                    |
|    posting rules      document type -> ledger effects             |
|    line projection    form_data_json -> doc_lines rows            |
|    posting runs       idempotency, reversal, attribution          |
|    core: handlers     registered on the lifecycle hook chain      |
+------------------------------------------------------------------+
                                 |
                                 v
+------------------------------------------------------------------+
|  TIER 3 — ERP Domain Modules (new; own tables, own permissions)    |
|                                                                   |
|  ledger     gl_accounts, gl_journals, gl_entries, gl_balances      |
|  inventory  inv_stock, inv_moves, inv_lots                         |
|  subledger  ap_open_items, ar_open_items, settlements              |
|  period     fiscal_years, fiscal_periods                           |
|  costing    cost methods, standard costs, variances                |
|  tax        tax codes, rates, jurisdiction rules                   |
|  currency   currencies, fx_rates                                   |
|  budget     budget lines, commitments, releases                    |
|                                                                   |
|  These modules never import `document`. They take value objects.  |
+------------------------------------------------------------------+
```

## 4.1 The Dependency Rule

**Tier 3 must not know that documents exist.** It is one line and it is the load-bearing constraint of the whole architecture.

If `ledger` ever queries `documents`, posting from anything other than a document becomes impossible — and an ERP posts from four other places on its first day: a period-end accrual job, an FX revaluation run, an opening-balance import, and the migration from whatever system it replaces. None of those has a document behind it, and none of them should have to invent one.

A ledger module therefore takes a value object — a balanced set of entry lines with an account, an amount, a period, a cost centre and an attribution — and refuses anything else. Who assembled it is the seam's problem.

The converse holds and is cheaper to keep: Tier 1 must not know that ledgers exist. It already does not, and the only edits §7 makes to it are gaps in the platform's own specification rather than ERP special cases.

## 4.2 Naming and Permissions

Tier 3 modules follow the [naming convention](../standards/02.%20Naming%20Convention.md) as ordinary modules — unprefixed conceptual names, `snake_case` directories under `modules/`. Their tables take the module's own prefix (`gl_`, `inv_`, `ap_`, `ar_`), and their permissions take an `erp:` namespace so that a deployment can grant the whole application without granting the ledger, and a Tier 1 permission is never widened to cover a Tier 3 surface.

Migrations continue the single repository sequence, taking the next free number in the order they are applied ([naming convention](../standards/02.%20Naming%20Convention.md) §4.3).

# 5. The Posting Seam

## 5.1 Posting Runs Inside the Document's Transaction

Document 01 §12.2 gives two hook kinds with different guarantees:

| Kind | Transaction | Can veto | On failure |
|---|---|---|---|
| `before_*` | inside the caller's transaction | yes | aborts, rolls back |
| `after_*` | outbox, after commit, asynchronous | no | logged and retried |

and one design rule: *never put a reaction in a `before_*` hook — a slow integration call must not block or roll back a user's submission.*

**That rule is about external calls.** Posting to the general ledger is not external; it is a set of inserts into the same database, on the connection the transaction already holds. Posting therefore runs in `before_document_post`, and the reasoning is [ADR-0037](adr/0037.%20ERP%20Posting%20Runs%20Inside%20the%20Document%20Transaction.md)'s:

- **"Approved but not yet posted" is a state somebody sees and does not trust.** If the ledger write is asynchronous there is a window in which the document reads `COMPLETED` and the trial balance disagrees. That window is a support ticket every time it is observed, and it cannot be closed by making the worker faster.
- **The veto is the point.** Period closed, account blocked, insufficient stock, budget exceeded — each is a refusal that must prevent the completion rather than follow it. An `after_*` hook cannot refuse anything; it can only record that the money already moved. This is [ADR-0016](adr/0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md) applied to a ledger.
- **Atomicity is otherwise unobtainable.** `documents.status = COMPLETED` and the journal entry are either both written or neither, and one transaction is the only mechanism that delivers it.

What goes to `after_document_post`, through the outbox, is the genuinely external consequence: the e-invoice submission, the supplier notification, the bank payment file, the tax-portal filing. Those are slow, they fail for reasons the user cannot fix, and they are exactly what §12.5's retry schedule and circuit breaker exist for.

```text
Workflow reaches its final state and the document is approved
        |
        |  one transaction
        v
before_document_post  ->  posting::post(tx, document)
                           |- is the period open?              REJECT if not
                           |- resolve the posting rule for this document type
                           |- project lines: form_data_json -> doc_lines
                           |- ledger::post_journal(tx, entries)   balanced or refuse
                           |- inventory::apply_moves(tx, moves)   may refuse
                           '- subledger::open_items(tx, items)
        |
        v
documents.status = COMPLETED, posting_run_id written
        |
        v  commit, then
after_document_post -> outbox -> e-invoice, supplier mail, bank file
```

## 5.2 Line Projection

JFSS is a **Final Standard**, frozen at v2.0.1 with errata only; a successor takes a new major version ([naming convention](../standards/02.%20Naming%20Convention.md) §10.1, [ADR-0014](adr/0014.%20Kelir%20Extends%20JFSS%20Through%20Settings.md)). Relational line items cannot be bolted onto it and should not be attempted.

**Project at post time instead.** When a document posts, the seam walks its datagrid rows and writes real rows the ERP layer owns:

```text
doc_lines
    id, tenant_id, document_id, line_no
    item_id, uom, quantity, unit_price, currency_code, amount
    tax_code, account_id, cost_center_id
    source_line_id        the upstream line this one consumes
    qty_consumed          maintained by downstream postings
    form_key              provenance back into form_data_json
```

Three things this buys, each of which is otherwise paid for repeatedly:

1. **The ERP layer never reads `form_data_json` at query time.** No JSONB path extraction inside a trial balance, an aging report or a stock card.
2. **Three-way matching becomes a foreign key** rather than a JSON comparison. A receipt line points at the order line it consumes, and `qty_consumed` is maintained under the same lock as the posting that moves it.
3. **The draft stays flexible.** Until the moment of posting a line is ordinary JFSS, rendered by the form renderer and computed by the calculation engine for free. Authoring speed for the draft, referential integrity for the posted record — available precisely because Kelir already separates *a document being filled in* from *a document that is final*.

`document_relations` records the chain at **document** level and answers *which order did this receipt come from*. `doc_lines.source_line_id` records it at **line** level and answers *how much of that order line is left*. Both are needed; neither substitutes for the other.

## 5.3 Posting Runs, Idempotency and Reversal

```text
posting_runs
    id, tenant_id, document_id, posted_at, posted_by
    reversal_of_run_id
    idempotency_key       unique per (tenant, document, key)
```

Every ledger row, stock movement and open item carries its `posting_run_id`. The consequences are the ones an auditor asks about:

- **A retry cannot double-post.** The unique index refuses the second attempt rather than relying on the caller to have been careful.
- **A reversal is a new run** with `reversal_of_run_id` set and the signs flipped. Nothing is deleted, nothing is updated. This is what makes the hash-chained audit trail ([ADR-0012](adr/0012.%20The%20Audit%20Hash%20Chain%20Covers%20the%20Payload.md)) meaningful for financial data rather than decorative.
- **"Unpost and re-post" is expressible** as a reversal followed by a posting, with both runs visible and attributable, rather than as a mutation that leaves no trace of what was there before.

## 5.4 Posting Rules: What Is Configuration and What Is Code

The temptation is to make everything configurable — an account-determination engine in its own right. The split that holds:

**Configurable**, as tables with a small allow-listed expression vocabulary: account determination (item category × transaction type → account), tax code → account, cost-centre derivation, document type → journal type. Where an expression is needed, it is evaluated by `rad::evaluator` — the engine that already exists on both sides ([ADR-0008](adr/0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md)) — rather than by a second one invented for the ledger.

**Code**, as one registered function per document-type family: the *shape* of the posting. A goods receipt posts differently from an invoice in a way no configuration table expresses without becoming a programming language. The registry is a closed enum, on the precedent [SDD](../design/01.%20System%20Design%20Document.md) §8.2.1 sets for `LookupSource`: *sources are code, not configuration*, because taking an identifier out of a data row and into control flow makes a misconfigured row a privilege bypass.

**A posting rule the registry does not know refuses the post** ([ADR-0016](adr/0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md)). It must never fall through to *post nothing and mark the document complete* — that is a document claiming to be posted having moved no money, which is the failure mode the whole rule exists to name.

# 6. Changes an ERP Forces on the Platform

Each of these is a gap in Kelir's own specification rather than an ERP requirement. They are listed here because an ERP is the first consumer that makes them urgent, and because they should be planned as platform work.

| # | Change | Why | Where |
|---|---|---|---|
| 1 | **Implement the `POST` lifecycle stage** — `before_document_post` / `after_document_post`, `documents.posted_at`, the `APPROVED` → `COMPLETED` transition through posting | Specified in document 01 §12.1 and §12.3, built by nothing. Every other item depends on it | `modules::hook`, `modules::document` |
| 2 | **Refuse every write to a posted document** — edit, status override, deletion of posting evidence | The status legality table already exists in `document::domain::status`; this extends it. Without it, somebody edits a posted invoice and the ledger is silently wrong | `document::domain::status` |
| 3 | **A general outbox, and the after half of the hook chain** | [ADR-0036](adr/0036.%20The%20Hook%20Chain%20Ships%20Its%20Before%20Half%20First.md) shipped the before half only; JWSS `actions` are stored and never invoked, and there is no general outbox table — notification and attachment workers poll their own. Roadmap Phase 9 | `modules::hook`, new outbox |
| 4 | **Money as a type** | JFSS `number` carries no currency. A convention (paired amount and currency keys) plus FX resolved at the seam against a rate pinned to the posting date | Convention + `modules::posting` |
| 5 | **A fiscal-period numbering scope** | `sequence_scope` offers `GLOBAL`, `YEAR`, `MONTH`, `DEPARTMENT_YEAR`. A fiscal year that is not the calendar year needs its own scope. The gapless policy already exists and is what a tax invoice requires | `document_type_numbering_rules` |
| 6 | **Incrementally maintained balances** | See §7 | `modules::ledger` |
| 7 | **An item master worth the name** | `mdm_products` has a single `uom` column. UoM conversion, item category, cost method, valuation account and tax defaults are all absent. Warehouse maps cleanly onto `mdm_facilities` and needs nothing | `modules::master_data` |

Two things do **not** need building, and both are worth knowing before somebody designs them again. `document_types.target_entity_type` with its `GovernedEntity` resolution already implements *a document creates or governs a master record*; and `mdm_products.created_by_document_id` / `last_updated_by_document_id` are already the provenance columns for it. Vendor onboarding through an approved document is a designed and partly built path, not a new one.

# 7. Reporting Is a Second Architecture

**A RAD list is over documents.** [SDD](../design/01.%20System%20Design%20Document.md) §8.2.4 is explicit: the rows of a list are the documents of every type that names it, and its own example column keys are `document_number` and `form_data.amount`.

A trial balance is over `gl_entries`. An inventory valuation is over `inv_stock` joined to cost. An AP aging is over `ap_open_items` bucketed by date. **None of these is a list of documents**, and rendering them through `ListRenderer` will fail — late, after a definition format has been stretched to accommodate them.

So there are two reporting paths and they do not converge:

| Path | Rows are | Built by | Examples |
|---|---|---|---|
| RAD list | documents | configuration, no code | requisitions awaiting approval, my claims, overdue tasks |
| Ledger report | ledger rows | endpoints and pages written for each | trial balance, GL detail, aging, stock card, valuation, budget vs actual |

**`gl_balances` is maintained incrementally inside the posting transaction, never aggregated on read.** This is the difference between a trial balance that answers in milliseconds and one that times out in the third year, and retrofitting it means backfilling and then reconciling what the backfill got wrong. It belongs in the first ledger migration.

## 7.1 Kelir's own dashboard takes the second path

**This section named two paths and left the platform's own dashboard unassigned**, which mattered as soon as Phase 8 opened: [ADR-0039](adr/0039.%20A%20Dashboard%20Widget%20Is%20a%20Purpose-Built%20Endpoint.md) (**D-78**, 2026-09-12) assigns it. **Every FR-RPT widget is a purpose-built endpoint in `modules::reporting`, and no FR-RPT row ships as a RAD list definition.**

The argument is the one §10's third risk anticipates, arriving a phase earlier than the ledger: **four of Phase 8's five widgets have rows a RAD list cannot carry** — FR-RPT-002 and FR-RPT-005 are over `workflow_tasks`, FR-RPT-004 is an aggregate over statuses, FR-RPT-001 is counts rather than rows — and the fifth, FR-RPT-003, genuinely is a page of documents and would render as a list definition today. **That fifth is why the decision had to be taken rather than assumed**, and per-widget choice is its rejected alternative: a dashboard that fetches its cards two ways has two answers to *what may this viewer see* on one screen.

**So the second path arrives before the ledger does**, and the first thing written on it is a dashboard rather than a trial balance. Nothing above changes — a RAD list is still the right tool for a page of documents built by configuration, which is what FR-RPT-003 gives up and what §10's risk row is about protecting.

# 8. Packaging

| Option | Verdict |
|---|---|
| **A. New modules in `kelir-backend/src/modules/`** | **Chosen for Tiers 2 and 3.** Posting shares a database transaction with the document's status change, and nothing else can |
| B. Compiled-in plugin (document [04](04.%20Kelir%20Plugin%20and%20Extension%20Management%20Concept.md) §14 Phase 2) | Right for connectors, report generators and notification channels. Not for the ledger |
| C. External plugin service over HTTP or a queue | **Structurally impossible for posting.** A separate process cannot enlist in Kelir's transaction; posting from outside means two-phase commit, or eventual consistency in a general ledger — which is a reconciliation job that never ends |

The constraint in row C is the one to write down before somebody proposes a service boundary there: *the same-transaction requirement rules out the external-plugin pattern for posting*, and it rules it out on a property of the ledger rather than on a preference about deployment.

Tier 1 stays upstream-mergeable. Tier 3 takes its own module directories, its own migration numbers, its own `erp:` permission namespace; the only edits to Tier 1 are §6's seven, each defensible as a platform gap on its own.

# 9. Build Sequence

Each phase ends somewhere defensible — the work can stop after any of them and leave a product somebody can use.

| Phase | Scope | Why here |
|---|---|---|
| **E1. Foundations** | Fiscal calendar with period open and close; chart of accounts as governed master data; currencies and FX rates; the item master of §6 item 7 | Nothing posts until a period exists. Putting the chart of accounts through Kelir's own governance means an account change is an approved document from the first day rather than a retrofit |
| **E2. The seam** | The `POST` stage; `posting_runs`; `doc_lines` projection; the posting-rule registry; the **manual journal voucher** as the first posting document type | A journal voucher is the simplest posting there is — no lines to match, no stock to move. It proves the seam end to end across the smallest surface |
| **E3. General ledger** | `gl_entries`, incrementally maintained `gl_balances`, reversal, trial balance, GL detail | The first phase an accountant can use |
| **E4. Purchase to pay** | PR → PO → GRN → AP invoice → payment; three-way matching over `doc_lines.source_line_id`; `ap_open_items`, settlement, aging | The document-and-approval half is nearly free. The work is matching and the subledger |
| **E5. Inventory** | `inv_moves`, `inv_stock`, one valuation method (moving average), stock card, transfers, adjustments | Deliberately after P2P: the receipt in E4 posts stock as a simple movement, and this puts the ledger behind it |
| **E6. Order to cash** | SO → delivery → AR invoice → receipt; `ar_open_items`; aging | Mirrors E4 and reuses the seam unchanged |
| **E7. Period close** | Close checklist, accruals, FX revaluation, closing entries, year-end rollover | Meaningful only once E3–E6 produce entries worth closing |
| **E8. Budget and commitment** | Budget lines, commitment at order posting, release at invoice posting, budget vs actual | The canonical `before_document_post` veto, and the clearest demonstration of why the veto had to be in the transaction |

**Tax is not a phase.** Indonesian tax alone — PPN, PPh 21/23/4(2), e-Faktur — is large enough to be its own track, and it cuts across E4 and E6 rather than following them. It starts in parallel with E4.

# 10. Risks

| Risk | What it looks like | Mitigation |
|---|---|---|
| The documents become the ledger | A balance computed by scanning `form_data_json` across documents | §4.1's dependency rule; `gl_balances` from the first ledger migration |
| Posting is made asynchronous | A permanent window where the document and the ledger disagree, and a reconciliation job that never goes away | [ADR-0037](adr/0037.%20ERP%20Posting%20Runs%20Inside%20the%20Document%20Transaction.md) |
| Financial reports are attempted through `ListRenderer` | A list definition format stretched until it breaks, discovered months in | §7's two paths, stated before the first report is written |
| A posted document is edited | Kelir documents edit and version naturally in `DRAFT`; nothing yet refuses a posted one | §6 item 2, in the status legality table where every other transition rule lives |
| JFSS v3 is waited for | Relational line items that never arrive, because JFSS is a Final Standard | §5.2's projection at post time |
| A posting rule fails open | A document marked complete having moved nothing | §5.4, applying [ADR-0016](adr/0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md) |

# 11. What This Document Does Not Decide

Stated so that silence is not read as a position:

- **Whether Kelir grows an ERP at all.** That is scope, and scope is a `D-n` in [Product Backlog](../../projects/planning/02.%20Product%20Backlog.md) §6 ([standards/06](../standards/06.%20Architecture%20Decision%20Records.md) §2). Nothing here is scheduled.
- **Whether the ERP ships in this repository or another.** §8 settles that posting must share a process with the platform; it does not settle whether that process is built from this repository's tree or from one that vendors it.
- **The valuation method beyond the first.** E5 names moving average as the one to build first and takes no position on FIFO or standard costing.
- **The chart-of-accounts structure** — segments, hierarchies, statutory mappings. It is E1's own design work.
- **Anything about a specific jurisdiction's tax.** §9's closing paragraph says only that it is its own track.
