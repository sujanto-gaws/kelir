## 3.2 Frontend Stack

| Layer | Technology |
|---|---|
| Framework | Vue 3 |
| Build Tool | Vite |
| Language | TypeScript |
| State | Pinia |
| Router | Vue Router |
| HTTP Client | Axios |

| Icons | Lucide Vue Next |

## 3.3 Database Strategy

Primary database: **PostgreSQL** — JSONB support, GIN indexing, full-text search, strong integrity, row-level security potential, better fit for metadata and audit logs.

Optional: **MariaDB**. MariaDB support requires the SQLx MySQL dialect, avoiding PostgreSQL-specific JSONB features, tested migration compatibility, and generated columns if indexing JSON fields.

# 7. Workflow Engine Design

## 7.1 Workflow Model

Lightweight internal state-transition engine (external BPMN engines remain a later integration option):

```text
Workflow Definition
    ↓
States
    ↓
Transitions
    ↓
Actions
    ↓
Process Instance
    ↓
Tasks
    ↓
History
```

## 7.2 Workflow States Example

```text
DRAFT
SUBMITTED
MANAGER_APPROVAL
FINANCE_APPROVAL
DIRECTOR_APPROVAL
COMPLETED
REJECTED
RETURNED
CANCELLED
ARCHIVED
```

Workflow-defined states map onto the fixed platform-level `documents.status` enum; the mapping is part of the workflow definition (see [architectures/02](../architectures/02.%20Kelir%20Framework.md) §3.12).

## 7.3 Workflow Actions

```text
SUBMIT
APPROVE
REJECT
RETURN
RESUBMIT
DELEGATE
ESCALATE
CANCEL
COMPLETE
```

## 7.4 Workflow Processing Flow

```text
Document submitted
        ↓
Workflow engine selects workflow definition
        ↓
Process instance created
        ↓
First transition evaluated
        ↓
Task created if human action required
        ↓
Task assigned to user/role/group
        ↓
User completes task
        ↓
Transition evaluated
        ↓
Document status updated
        ↓
Next task created or process completed
        ↓
History and audit recorded
```

## 8.1 RAD Concept

```text

    ↓

    ↓

    ↓

```

```text
Entity
Field
Form
Form Section
Form Field
List
List Column
List Filter
Menu
Action
Lookup

```

Form definitions conform to the **JSON Form Schema Standard (JFSS v2.0.1)** in [docs/schema/](../schema/JSON%20Form%20Schema.md); calculations and validation rules are restricted to the operators and rules registered in the JFSS Calculation and Validation Rule Registries.

## 8.3 RAD Rendering Flow

```text
Frontend requests metadata
        ↓
Backend returns form/list/document type metadata
        ↓
Frontend FormRenderer renders form
        ↓
Frontend ListRenderer renders table
        ↓
User submits data
        ↓
Backend validates using schema (and recalculates JFSS calculated fields — Tamper-Proof Pattern)
        ↓
Document or master data saved
```

# 11. Security Design

## 11.1 Authentication

```text
Username/email + password
Argon2 password hashing
JWT access token or secure session
Refresh token or session renewal
Logout and token invalidation
Rate limiting on authentication endpoints (NFR-SEC-008)
```

## 11.2 Authorization

```text
RBAC first
Permission format: module:resource:action
Backend enforcement
Frontend visibility control
```

Permission naming rule: permissions follow `module:resource:action`; the `resource` segment may be omitted when a module manages a single resource (e.g. `document:create`), and is required when a module manages multiple resources (e.g. `master-data:party:update`).

Example permissions:

```text
document:create
document:read
document:update
document:submit
document:approve
attachment:upload
attachment:delete
master-data:party:update
audit:read
integration:manage
plugin:manage
```

## 11.3 Audit and Logging

```text
Activity log for user-friendly timeline
Audit log for formal compliance record (hash-chained, append-only)
Integration log for external calls (masked payloads)
Plugin audit log for extension actions
Security log for authentication and authorization failures
```

## 12.3 Standard Response

Item response:

```json
{
  "success": true,
  "data": {}
}
```

List response:

```json
{
  "success": true,
  "data": [],
  "meta": { "page": 1, "pageSize": 20, "total": 0 }
}
```

Standard error:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Validation failed",
    "details": []
  }
}
```

JFSS validation failures populate `details` with `{path, rule, code, message}` entries per JSON Form Schema S10.3. JSON payload fields are `camelCase` (naming convention §5).

```text

├── frontend
├── backend
├── postgres
├── mailpit

└── clamav        (added in Phase 6, when attachment scanning needs it)
```

The scanner is ClamAV, decided 2026-08-11 as [Product Backlog](../../projects/planning/02.%20Product%20Backlog.md) decision **D-4**. # 14. Development Roadmap

Delivery is phased; each phase ends with a tagged release, and the sprint-level breakdown lives in the [sprint plan](../../projects/planning/01.%20Sprint%20Plan.md).

Two placements in the table below are deliberate and were decided on 2026-08-11 (recorded as D-1 and D-2 in the [Product Backlog](../../projects/planning/02.%20Product%20Backlog.md) §6.1): the **MVP marker sits at Phase 6, not Phase 5**, because SRS §9 requires attachments, comments, the activity log and audit of approvals; and **RAD is split**, with its metadata tables and form renderer in Phase 4 — `document_types.form_id` references `rad_forms` ([Database Schema](02.%20Database%20Schema.md) §6.2), so `0008_rad.sql` must apply before `0009_document.sql`.

| Phase | Scope | Deliverable |
|---|---|---|
| 1. Foundation | Skeleton, Docker Compose, DB connection, health endpoints, config, logging, layout, login page | Running Kelir skeleton |
| 2. Authentication and User Management | Users, roles, permissions, login/logout, JWT/session, route guards, user/role CRUD | Authenticated application |
| 3. Master Data | Party model (persons, party groups), party roles and profiles (supplier, customer, employee), facility, product, service, lists, search, audit | Master data management module |
| 4. Document Core | RAD metadata tables and form/list definition storage, lookup fields, read-only JFSS form renderer; document types, numbering, creation, editing, submission, list, detail, metadata, versions | Working document management module |
| 5. Workflow Engine | Workflow definitions, process instances, tasks, approve/reject/return, task inbox, history, document status synchronization | Approval workflow end-to-end |
| 6. Attachments, Comments, Activity | Upload/download, attachment list, threaded comments, activity timeline, basic audit trail | Collaborative document workspace (**MVP**, SRS §9) |
| 7. RAD Engine | Rule engines, dynamic list renderer, conditional visibility, document type builder, menu builder | Configurable RAD capability |
| 8. Reporting and Dashboard | Dashboard summary, pending tasks, recent documents, status chart, overdue tasks, approval reports | Management dashboard |
| 9. Integration and Plugin Foundation | Integration core, external system registry, integration logs, outbox events, plugin registry/settings/manager UI | Extensible platform foundation |

# 16. Risks and Mitigation

| Risk | Mitigation |
|---|---|
| Workflow engine becomes too complex | Start with lightweight state-transition engine before BPMN |
| Multi-database compatibility complexity | Use PostgreSQL first, MariaDB later with compatibility layer |
| Dynamic plugins introduce security risk | Start with configuration-based and compiled-in plugins |
| RAD metadata becomes unstable | Version metadata and validate schema strictly (JFSS meta-schema is normative) |
| Frontend dynamic rendering complexity | Build reusable FormRenderer and ListRenderer incrementally |
| Audit log grows large | Partition/archive audit tables and define retention policy |
| File storage grows | Use object storage and metadata tracking |
| Integration failures | Use outbox, retry, dead-letter, and integration logs |
| Permission complexity | Start with RBAC before ABAC |
