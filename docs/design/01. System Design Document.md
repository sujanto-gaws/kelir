## 3.3 Database Strategy

Primary database: **PostgreSQL** — JSONB support, GIN indexing, full-text search, strong integrity, row-level security potential, better fit for metadata and audit logs.

Optional: **MariaDB**. MariaDB support requires the SQLx MySQL dialect, avoiding PostgreSQL-specific JSONB features, tested migration compatibility, and generated columns if indexing JSON fields.

**`features/rad/` is shaped by the definition it renders, not by a screen** (FR-RAD-010, #162). `renderer/` holds the dispatch and the component registry, `fields/`, `layout/`, `display/` and `actions/` hold one component per JFSS role, and `__fixtures__/` holds the definitions both the unit tests and the browser harness read.

**The registry is Kelir's component vocabulary, and the only copy of it.** JFSS §4.4 makes `type` *"an open vocabulary defined by each implementation's component registry"* and the meta-schema enumerates none, so nothing upstream decides which component types exist — `features/rad/renderer/registry.ts` does, for the client, exactly as `modules/rad/domain/jfss.rs` does for the lookup sources on the server. A type that is neither supported nor declared missing there renders as a named placeholder rather than as nothing, because a form silently missing a field is indistinguishable from a form that never had one.

## 5.4 Session Lifecycle

The session lives in one Pinia store (`stores/auth.ts`) and is read by two things that must not import it directly: the API client, which needs the bearer token and a way to refresh it, and the router, which needs to know when the session ends. Both seams are small modules the store registers with — `api/session.ts` in one direction, `stores/session-events.ts` in the other — because a direct import either way is a cycle, and the router installs its guards before any store exists.

A session ends in one of three ways, and they are not the same event:

| How it ends | What the store does | What the caller sees |
|---|---|---|
| The caller signs out | Clears locally, calls `/auth/logout` | The caller is already navigating |
| The server refuses the credentials — a refresh 401s, a token is revoked, an account is deactivated | Clears **and announces** | Redirected to the login page, told the session ended |
| Another tab signs out | Clears **and announces** | The same |

**The second row happens when the server next refuses, not when the account or its tenant changes.** Which request that is depends on the change (corrected 2026-10-01, §11.1). **A status change keeps the token until it expires**: an account made `INACTIVE`, or one whose tenant is suspended or deactivated, has its access token accepted for at most 15 minutes from issue, and the session ends at the refresh that follows (decision **D-104**). **A deletion ends it at the next request**: a deleted account's token, or a deleted tenant's, is answered 401, the refresh that follows is refused, and the session ends there (decision **D-105**). The user list's Deactivate button is a deletion.

**Announcing is what makes the second and third cases survivable.** The route guard runs on navigation; a session lost while the caller sits on a page moves nothing, so before [#68](https://github.com/sujanto-gaws/kelir/issues/68) nothing redirected them. They stayed on a page whose data was stale and whose every action would fail — an administrator editing a role submitted the form, got a 401, and had no explanation. `registerGuards` listens for the announcement and leaves the page.

Two things are deliberately *not* announced. A deliberate sign-out is not, because its caller is already navigating and a second redirect would race the first. And a failure that is not the server refusing the credentials — a 5xx, a timeout, an unreachable host — is not a lost session at all: the tokens are still good, and treating a two-second connectivity drop as a sign-out is the outcome the distinction exists to prevent. Only 401 and 403 end a session; every other status leaves it standing for the server to refuse on the next call.

The login page then has two things to say and picks the better one. Tokens still present means the session was never lost, only unconfirmed, and it offers a retry ([#66](https://github.com/sujanto-gaws/kelir/issues/66)). Tokens gone plus the router's `sessionEnded` marker means the session genuinely ended, and it says so — without the marker, arriving after a lost session and arriving from a deep link are indistinguishable, since both carry `redirect` and neither carries a session.

### 8.2.1 Lookup Fields (FR-RAD-007)

A **lookup** is the one component whose options come from the database rather than from the definition. Every other component is a function of the definition it is declared in; this one is a function of master data, which makes it the component that has to answer a question none of the others do: *a lookup must not become a way to read master data the caller could not read directly.*

**How a definition declares one.** A `data` component of `type: "lookup"`, plus an entry in the form's `settings.lookups` mapping that component's `id` to a master-data source:

```json
{
  "formId": "purchase-requisition",
  "version": "2.0.1",
  "settings": { "lookups": { "supplier_field": "supplier" } },
  "components": [
    { "id": "supplier_field", "role": "data", "type": "lookup",
      "key": "supplier_id", "label": "Supplier",
      "validation": { "type": "string" } }
  ]
}
```

**Why the binding sits in `settings` rather than on the component.** JFSS is a `Final Standard` — frozen at v2.0.1, errata only, and a successor takes a new major version ([naming convention](../standards/02.%20Naming%20Convention.md) §10.1). Its meta-schema closes a component with `unevaluatedProperties: false`, so a `dataSource` property on the field would make the document non-conformant, and `settings` is the one object the specification declares `additionalProperties: true` and describes as global form configuration. The cost is stated rather than hidden: the binding is not local to the field it binds, which departs from JFSS's own component-driven philosophy. Making it local means JFSS v3.0.0, which is a phase-scale decision rather than a sprint item.

The binding is on the component's `id` rather than its `key` because JFSS §4.1 makes `id` unique per component *instance*, while a `key` inside a datagrid row template lives in the row's scope and two components in one document may legitimately share one.

**Both directions are refused at save**, not at render (`rad::domain::jfss`): a binding naming no component, a component of `type: "lookup"` nothing binds, a source outside the allow-list, an ambiguous `id`, and a bound component that also carries a static `options` array. A definition is written once and rendered thousands of times, and at render the failure is a chooser that opens empty — indistinguishable from master data holding nothing.

**Sources are code, not configuration.** `supplier`, `customer`, `employee` and `facility`, as an allow-list in `rad::domain::lookup::LookupSource`. A source decides which query runs *and* which permission the caller must hold, and taking either from `rad_lookup_definitions` would put an identifier into SQL from data and make a misconfigured row a permission bypass ([Database Schema](02.%20Database%20Schema.md) §5.12).

**The permission is the underlying entity's, and is required by not being checked twice.** `GET /api/v1/rad/lookups/{source}/options` calls the master-data module's service, which refuses before anything is read, so a lookup opens exactly what `GET /master-data/suppliers` and `GET /master-data/facilities` open and the two cannot drift apart. A caller without it gets **403 rather than an empty page**: an empty list is a false statement about the data that the person filling in the form cannot tell from a tenant with no suppliers yet, while refusing discloses only that a source exists — which the definition they just read already told them. The list is paged and searched server-side, and the filters that decide which records may be offered at all (an enabled party, a role it currently holds, a facility that is not archived) are the server's rather than the caller's.

### 8.2.2 Submitting a Form, and the Re-evaluation Behind It (FR-RAD-010, FR-RAD-006)

**The client's arithmetic is not trusted.** [JSON Form Schema](../schema/JSON%20Form%20Schema.md) S8.1 requires the backend to re-evaluate every `calculate` expression and **overwrite** the submitted value before persistence, and S10.2 requires the same for every `conditional` — re-deciding visibility against the complete payload and discarding the values of the components that resolve to hidden. Together they are the **Tamper-Proof Pattern**, and it is the security-critical control of Phase 4: *a submitted total the server accepted because the browser said so is not a rounding bug, it is an invoice for the wrong amount.*

`POST /api/v1/rad/forms/{id}/submissions` is where it happens. It takes a payload carrying **every** data `key` the definition declares, visible or not (S10.1), and stores a row in `rad_form_submissions` ([Database Schema](02.%20Database%20Schema.md) §5.14) whose `payload_json` is the server's own answer.

**The code is split in two, and the split is a Sprint 9 dependency rather than a preference.** `rad::service::evaluation` is pure — a definition and a payload in, a secure payload or an S10.3 error envelope out, with no database handle, no permission check and no `AppState`. `rad::service::submission` is what adds the permission, the tenant scope, the published check and the write. Sprint 9's [#168](https://github.com/sujanto-gaws/kelir/issues/168) calls the first from inside the transaction that takes a document's number, and that is only possible if it drags no submission row along with it.

**The order of operations**, which is JFSS §9.2's:

1. **Project the payload onto the definition.** Every declared `key` is present — a missing one resolves to `Value::Null`, which is S12.4 as errata **E-1** restates it for `serde_json` — and every *un*declared key is dropped rather than stored.
2. **Overwrite `sequenceKey`** with the row's 1-based position. §10.2 puts sequencing beside calculation under *"Backend overwrites to prevent tampering"*: a line-item table that reads 1, 3, 4 after a deletion is what the property exists to prevent, and a client does not get to decide it.
3. **Re-evaluate every `calculate`** by the **declared** `calculateMode` (S4.2.3, S8.1.1) — `derived` overwrites unconditionally, `generated` resolves only where the stored value is null. **In the order §9.2 asks for**, taken from the dependency graph §8.2.3 builds, so a chain declared backwards settles in one pass rather than in as many passes as it is long. A scope with no such order is cyclic, which S12.2 makes invalid; it is refused with every field on the loop named rather than half-persisted, and §8.2.3 is why that refusal is the second line rather than the first.
4. **Re-evaluate every `conditional`** against that payload and discard the values of the components that resolve to hidden. A hidden `key` being *present* is expected and never by itself a rejection (S10.1.1).
5. **Run `validation` and the `rules`** scoped `server` or `both`. A rule name outside the Validation Rule Registry is a refusal and never a skipped arm (S8.1.1) — *a rule that fails open is a rule that is not there, reported as a rule that passed.*

**Steps 3 and 4 are in that order and it matters.** A `conditional` keyed on a computed field would otherwise be decided from the number the *client* sent, so tampering with a total would move which fields get persisted. Recorded as decision **D-27**.

**A failure is a refusal, never a partial write.** The response is a 4xx carrying the S10.3 envelope, whose `path` is a dot-notation path — `line_items.2.quantity` addresses a row, which is why the field is named `path` and not `key`. This is where a division by zero lands (**D-24**): blank on the screen while the form is being filled in, a named refusal when it is submitted.

**And the browser is told what was stored.** The response carries the payload read back from the row, and the page compares it against what it sent: where the two differ it says which fields moved and to what. Both sides run one engine compiled for two runtimes (**D-10**) and `parity/forms.json` holds them to the same answers over whole submissions, so that banner should never appear — which is exactly why it is on the screen rather than in a log. *A form that changes your number without saying so is its own defect.*

### 8.2.3 The Rule Engine Behind It (FR-RAD-006)

**An evaluator answers *what does this expression compute*; an engine answers which expressions run, in what order, and what a failure means.** `rad::evaluator` has been the first half since Sprint 7 (**D-10**, [ADR-0008](../architectures/adr/0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md)). `rad::domain::engine` is the second, built in Sprint 14 under **D-67** and recorded as [ADR-0035](../architectures/adr/0035.%20Rules%20Are%20Resolved%20Before%20a%20Form%20Is%20Published.md).

**The catalogue resolves a definition's rules against both registries, on one walk.** Every `data` component in a scope is visited once: its `rules[].rule` names are resolved against the [Validation Rule Registry](../schema/JFSS%20Validation%20Rule%20Registry.md) and its `calculate` and `conditional.logic` operators against the [Calculation Rule Registry](../schema/JFSS%20Calculation%20Rule%20Registry.md) and the `conditional` floor. One walk rather than two because a second traversal carries its own idea of JFSS §4.3.1's three container shapes, and two traversals that must agree are two places to forget one.

**The graph is built from every `{"var": ...}` reference in *both* rule properties**, which is S12.2's requirement rather than a choice. A repeater's row template is its own graph: a `key` inside one addresses a property of the row (§4.3.1), so `line_total` reading `quantity` means the same row's quantity and a top-level field of that name is a different field. An iterator's body — the second argument of `map`, `filter`, `reduce`, `all`, `some`, `none` — is read against an item and not against the enclosing scope, so it contributes no edge there; treating it as one would invent a dependency and, with it, a cycle the definition does not have.

**One asymmetry between the two properties is deliberate.** A `calculate` referencing its own key is a cycle, because S8.1 computes the field from the record. A `conditional.logic` referencing its own key is not, because S10.2 decides visibility against the complete payload with the calculations already applied (§8.2.2, **D-27**) — `{"!!": {"var": "notes"}}` is an ordinary conditional and refusing it would refuse working definitions.

**The verdicts land at two moments, and the second one is the door that only opens once.** `validate_definition` refuses the *write*, so an unregistered rule name (`RULE_NOT_REGISTERED`) or a cycle (`CALCULATION_CYCLE`, naming every field on the loop) never reaches storage. `publish_form` re-runs the same function against the **stored** definition before flipping the status, because a draft written by an older build keeps whatever it was stored with and a published revision is immutable — documents pin it (§8.4, [ADR-0027](../architectures/adr/0027.%20A%20Document%20Pins%20the%20Form%20Revision%20It%20Was%20Filled%20Against.md)), so a definition that goes live wrong can never be corrected in place. Workflow definitions have been checked at both moments since Sprint 10 (§8.5); this brings forms into line with them.

**The submit path is the second line, not the first.** It asks the same graph for the same order, and a cycle there means a form published before this gate existed: it answers 422 with the S10.3 envelope naming the fields, never a 500. A rule name outside the registry still refuses a submission (**D-28**, [ADR-0016](../architectures/adr/0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md)) — *a rule that fails open is a rule that is not there, reported as a rule that passed* — but the person it now refuses is the author, at the moment they can fix it.

**What S12.2 asks for and this does not yet do** is *surface* the cycle in an authoring tool. The API names it; the builder UI that would draw it is FR-RAD-004/008, [#341](https://github.com/sujanto-gaws/kelir/issues/341).

### 8.2.4 Rendering a Configured List (FR-RAD-003, FR-RAD-010)

**The list definition storage API shipped in Sprint 7 and nothing read it until Sprint 14** ([#340](https://github.com/sujanto-gaws/kelir/issues/340)). Four endpoints, a `rad::service::list`, a definition format — and no frontend. FR-RAD-010 was recorded as delivered on the strength of the *form* renderer; the list half of the same requirement is this section.

**What a rendered list is over is documents.** [Database Schema](02.%20Database%20Schema.md) §6.2 gives `document_types.list_id`, and §5.7's own example column keys are `document_number` and `form_data.amount`. So the rows of a list are the documents of **every type that names it** — a predicate in the same statement as every other filter, never a lookup above it, for the reason §8.4's visibility rule gives.

**Two reads, because the builder and the renderer ask different questions.**

| | `GET /rad/lists/{id}` | `GET /rad/lists/by-key/{listKey}` |
|---|---|---|
| For | the builder, editing a definition | a renderer, drawing a screen |
| Permission | `rad:list:read` | `document:read` |
| Status | any | `ACTIVE` only |
| Answers | what is stored | what can be drawn |

**The renderer's permission is the one its rows require, and no new row was added.** This is §5.13's lookup precedent applied a second time: `GET /rad/lookups/{source}/options` requires what the master-data endpoint it projects requires, because a permission of its own would let a deployment grant the projection without the thing projected. A rendered list is a view of documents. Gating it on `rad:list:read` would mean only a configuration administrator could open a screen built for everybody, and a third permission would guard nothing `document:read` does not ([ADR-0011](../architectures/adr/0011.%20A%20Derived%20Surface%20Requires%20the%20Permission%20of%20What%20It%20Derives%20From.md)'s converse).

**A definition is resolved against what can be drawn, and every failure is named.** `rad::domain::render` resolves each `columnKey` to a document field or a `form_data.` path, each `filterKey` to a parameter the documents query has, and `default_sort_json` to a column that can be ordered on. Anything it cannot resolve is a `ValidationDetail` naming the key — **not an empty table**, which is the whole point: a table with no rows reads as *this tenant has no documents*, and is the same silence [#326](https://github.com/sujanto-gaws/kelir/issues/326) took in the attachments panel. A `DRAFT` list, and a list no document type binds, are refused the same way.

**Refused at render rather than at save, which is the opposite of a form** (§8.2.3). A form definition is checked when it is written because JFSS is what a form *means*. A list definition's column keys mean something only once you know what the list is over, and `rad_lists` is generic — refusing `form_data.amount` at the storage API would put the document module's vocabulary inside a table written for lists over anything. The cost is stated: a broken list definition is stored happily and fails when somebody opens it. What makes that acceptable is that it fails loudly, naming the key, and that the builder ([#341](https://github.com/sujanto-gaws/kelir/issues/341)) calls the same function to show an author the problem before they save.

**Sorting is an allow-list, not an identifier.** `DocumentSortKey` is a closed enum of nine columns; its token reaches the statement as a **bound parameter** and every column the query could order by is written out in the statement's own text. Coding standard §2.5 keeps the statement checkable and §6.4 requires a dynamic identifier to be allow-listed; both hold with no assembled string. `entityId` and `id` are deliberately absent — they are v7 UUIDs, so a sort on one would look chronological while ordering a foreign key.

**`form_data.*` columns are extracted server-side.** The rows query fetches `form_data_json` only when a declared column reads it, and the response carries the *declared cells* rather than the payload — a page of twenty documents with twenty form payloads on it is the reason `DocumentSummary` exists (NFR-PERF-002).

**The page size is the definition's and a request cannot widen it**, refused by name rather than ignored. A client that could set it would be overruling the configuration it had just read.

### 8.2.5 Configured Actions (§5.10)

`rad_actions` has been in the schema since `0014_rad.sql` and had no reader until [#340](https://github.com/sujanto-gaws/kelir/issues/340). `GET /api/v1/rad/actions?context=LIST` is it.

**An action is scoped by `context` and, since [#348](https://github.com/sujanto-gaws/kelir/issues/348), optionally by list.** `0042_rad_action_scoped_to_a_list.sql` gives §5.10 the `list_id` that §5.7 and §5.8 always had, because a column and a filter belong to a list and an action did not. **The null is the old behaviour**: an action naming no list is offered on every list of its context, so nothing changes until a deployment scopes something. `GET /api/v1/rad/actions?context=LIST&listId=…` returns the tenant-wide rows plus that list's own — it narrows and never excludes — while asking **without** a list returns the tenant-wide rows alone, which is deliberate: a caller that has not said which list it is drawing must not be handed buttons configured for one. **Lists alone are closed**; a `DETAIL`, `DOCUMENT` or `TASK` action still has the same gap against a document type or a task definition, and a `CHECK` keeps the column from being reused for them until that decision is taken.

**The permission is the action's own, and there is no second one.** `required_permission` is a column, so *may this caller invoke this action* already has a per-row answer, and that is where it is asked. An action the caller could not invoke is **not returned** rather than returned and disabled: a disabled button states that the thing exists and is not for you, which is what the row's permission was set to withhold, and a renderer that had to filter would be a second copy of the rule. A row whose `required_permission` is null is the deployment saying *everyone may*.

### 8.2.6 The Builder Screens, and the Configured Navigation (FR-RAD-004, FR-RAD-008, FR-RAD-013, FR-DTYPE-001..004, FR-WF-018)

Everything above is metadata somebody has to author. Until [#341](https://github.com/sujanto-gaws/kelir/issues/341) the only way to author it was the API, which is what **D-64** accepted at the MVP tag and scheduled a screen for. `/admin/document-types` and `/admin/menus` are those screens.

**A document type is configured through one dialog, and its numbering through another.** A type has one numbering rule or none, and the endpoint behind it is a `PUT` on a sub-resource rather than a `POST` that would conflict the second time — so folding it in would make creating a type require deciding how its documents are numbered, which is a decision often taken later. A type with **no** rule reads 404, and the dialog treats that as *not configured yet* rather than as a failure; it says so, because a type without one cannot have its documents submitted.

**The form, the list and the workflow are chosen, not typed.** All three choosers are filtered to what may actually be bound — `PUBLISHED` form revisions, `ACTIVE` lists, `ACTIVE` workflow definitions — because a draft revision bound to a type would be pinned by the first document raised from it, and a revision is immutable once pinned. The three reads want three different permissions and are settled independently: a caller without `rad:list:read` gets a list chooser that says its choices could not be loaded, and the form chooser still works.

**The governed record is offered as two named choices and a blank.** `document_types.target_entity_type` is free text with no `CHECK`, and `GovernedEntity::from_db` refuses a value it does not implement rather than guessing one — so a type carrying an unrecognised value governs **nothing**, silently. The chooser offers only `PARTY` and `FACILITY`, and reads an unrecognised stored value back as *no governance* rather than showing it selected: displaying it would claim a governance that does not happen, and saving the dialog unchanged would write it back.

**`retentionPolicyId` is the one column the screen does not offer.** Nothing in this build creates a retention policy, reads one, or acts on one — the column has waited since `0015` for the surface that will — so the field would be a UUID box for a record that cannot exist, inviting an administrator to invent an id and believe a retention was configured.

**The list screen offers only the actions its viewer can perform**, each gated on its own permission rather than on a single "admin" one, which is how `admin/users`, `admin/roles` and the other four already behave. Gating the button is not the enforcement; the route behind it enforces its own.

#### The navigation is built-in destinations *plus* configured ones

`rad_menus` has been in the schema since `0014_rad.sql` and, like `rad_actions` before §8.2.5, had no reader and no writer. `GET|POST /api/v1/rad/menus` and `GET|PUT|DELETE /api/v1/rad/menus/{id}` are that surface, and `/admin/menus` is its screen.

**The built-in destinations stay in code and the configured ones are merged in.** The alternative — seeding the built-ins as `CORE` rows and rendering the table alone — was rejected because a tenant whose table is empty or mis-edited is then an application nobody can navigate, including back to the screen that would fix it. So `mergeNavigation` takes the built-in list, the tenant's `CONFIG` rows and the viewer's permissions, and interleaves them by `sort_order`; the built-ins are numbered in tens so a tenant can sit between two without renumbering anything. `source` is written by the server as `CONFIG` and is never taken from the request: `CORE` is the code's word and `PLUGIN` is Phase 9's.

**A subtree travels with its root.** A child's own `sort_order` orders it among its siblings and never moves it out from under its parent, because a tree drawn by sorting every node flat is not the tree that was authored. A child whose parent the viewer cannot see — or whose parent is not on the page at all — **rises to the top level** rather than disappearing with it; it is the tenant's own entry, and losing it silently is the failure the delete path avoids for the same reason.

**Deleting an entry re-parents its children to their grandparent**, in one transaction. The alternative is a cascade that removes navigation nobody asked to remove, or an orphan the renderer has to guess about.

**A parent that would close a loop is refused, and the walk is bounded.** `menu_ancestors` is the recursive CTE of [#141](https://github.com/sujanto-gaws/kelir/issues/141)/[#191](https://github.com/sujanto-gaws/kelir/issues/191) applied to `rad_menus`: it climbs from the proposed parent to the root under a depth bound, and a re-parent whose ancestry contains the entry itself is `MENU_WOULD_CYCLE`. **A walk that hits the bound refuses rather than assuming**, as `MENU_TREE_TOO_DEEP` — a truncated walk has not proved the absence of a cycle, and treating "I stopped looking" as "there is none" is how a ring of three gets written past a self-reference check the database can see but a `CHECK` constraint cannot. The renderer carries its own terminating walk for the same reason: a client that trusted the refusal completely would have no answer when the refusal was wrong.

**A configured entry's `required_permission` hides the link and nothing more.** The screen behind it enforces its own, and the dialog says so where somebody would otherwise assume the opposite. An entry naming no permission is offered to everybody.

#### The workflow editor is a list of states, and the server's verdict is drawn where it points (FR-WF-018)

`workflow_definitions` has had a full write API since Sprint 10 ([#174](https://github.com/sujanto-gaws/kelir/issues/174)), and until [#426](https://github.com/sujanto-gaws/kelir/issues/426) nothing in the interface wrote one. `/admin/workflows` and `/admin/workflows/{id}` are its screens, in `features/workflow-builder/`, against the routes that already existed. `api/workflow.ts` gained get, create, update, publish and new revision, and no backend route was added.

```text
/admin/workflows           WorkflowListPage     every revision a row; open, new workflow, new revision
/admin/workflows/new       WorkflowEditorPage   a workflow not yet saved, under workflow:definition:create
/admin/workflows/{id}      WorkflowEditorPage   one revision: edit, save, publish, new revision
```

**The editor is a state list with a transition table under each state** (**D-95** A). A read-only graph of the same definition is [#687](https://github.com/sujanto-gaws/kelir/issues/687)'s, laid out on every load with nothing stored. **It edits the JWSS document itself, not a model of its own**, so what it has no field for goes back as it came: guards, actions, a task's escalation, variables and settings. **Escalation and parallel approval get no field** (FR-WF-010 and FR-WF-016 are unscheduled), and a stored escalation is said to be inert.

**The draft follows kopiflowvue's store conventions**, as D-95 borrowed them, in a page-local composable (`useWorkflowDraft`) rather than a store. Every edit builds a new definition and replaces only the arrays and objects on its path, so a snapshot is the definition itself and undo is a pointer move. History is two plain arrays, and only their lengths are reactive. An `isRestoring` guard applies a write that lands while an undo settles without recording it. Each state and transition has a key that is not in the JWSS and that survives edits, moves and removals, so a row is never remounted under the user. **Identity is what the logic builder needs**: a condition nobody touched is the same object after an edit elsewhere, so a builder holding an unfilled operand is not reloaded. The vocabularies — actions, assignee types, task types, state kinds — are one typed registry each (`jwssRegistry.ts`), a `Record` over the union, so a value added to the type without a row fails the build.

**There is no second validator in the browser** (ADR-0019). A save is checked by the server against the meta-schema, the conditional operator tier and JWSS §8, and a publish again with the tenant's roles (**D-111**). Every detail comes back addressed by its position in the body, and the editor only decides where to draw it. A detail under `definition.states.<i>` or `definition.transitions.<i>` is drawn on that row: under the input it names, or listed at the row's top when the row has no input for it, so S12's refusal of `requiresComment` on an `AUTO` edge lands on that edge's checkbox. **S6 and S7 report at the whole list** and name the state in the message, so a detail at `definition.states` or `definition.transitions` whose first backticked token is a declared state code is drawn on that state. Details that land on one path are joined rather than first-wins, because one state can be both unreachable and a dead end. The rest goes through `useFormErrors`, and `FormUnplacedErrors` lists what nothing on the screen draws (coding standard §3.4).

**A condition is offered the context the engine builds, not JWSS §6.1's sketch.** `EvaluationContext` gives JSON Logic `document` as `{status, documentTypeId, documentNumber}`, `actor` as `{userId}`, the form payload as `formData`, and the instance's `variables`. §6.1 also names `document.amount`, `document.documentTypeKey`, `actor.roles` and `actor.departmentId`, which the engine does not fill in, so a condition on one reads `null` and takes the fallback without saying so. **The editor offers the four built paths and each declared variable**, and lets a `formData.<key>` path be typed, because a workflow is bound to a document type rather than a form and the editor cannot list the fields. The builder marks a typed path as outside the offered set.

**A published revision opens read-only and says why**: running approvals execute the revision they started on. *New revision* is the way forward. **Deprecating a revision joins it after [#573](https://github.com/sujanto-gaws/kelir/issues/573)'s route** (**D-101** B, `workflow:definition:deprecate` by **D-108**). The places it goes are marked in both pages, and `api/workflow.ts` gains its call with the route. Until then the screen has no button for it, rather than one that cannot work. **Publish saves unsaved edits first**, because what is published is what is stored.

#### The visual logic builder edits what it can show and keeps the rest (FR-RAD-013, FR-WF-018)

**One builder edits both of Kelir's expression surfaces**: a form's `calculate` and `conditional.logic`, and a workflow transition's `condition` (**D-110**, [#686](https://github.com/sujanto-gaws/kelir/issues/686)). It is `src/components/logic-builder/`: `JsonLogicBuilder.vue` holds the expression, `JsonLogicNode.vue` draws one node and every node below it, `JsonLogicRawBox.vue` is the raw-JSON box, and `logicTree.ts` is the seam between the JSON and the tree. It offers comparisons, `and`, `or`, `!`, arithmetic and `var`, and nothing else.

**What it can show is decided per node.** A node is representable when it is a single-key object, its operator is offered in the current tier, its arity and shape are the ones the seam pins, and its children are representable or opaque. **Anything else is an opaque leaf**: it holds the original value by reference and is drawn as a raw-JSON block marked *Advanced*, inside the tree, with the rest of the expression still visual. **Only an unrepresentable root opens the whole expression in the raw-JSON box**, also marked *Advanced*: a bare literal, an array, `null`, `{}`, a multi-key object, or an operator the tier does not offer. **Anything but a literal nested deeper than `MAX_VISUAL_DEPTH` (64) is one opaque leaf too**, held by reference, so the round trip stays exact and a pathological expression cannot overflow the stack: a cold mount, a page whose first render is the deep expression, overflowed from about 248 levels in vitest, and a browser's stack is not Node's. An operator the builder does not offer is held, never judged. `min`, `max`, `map`, `if`, `in` and the rest are approved by the [Calculation Rule Registry](../schema/JFSS%20Calculation%20Rule%20Registry.md) (`if`, `?:` and `in` in the conditional tier only, §2.5; §2.3 forbids them in `calculate`) and simply not offered. A forbidden or unknown operator is held the same way. **The verdict on all of them is the server's save-time check, and there is no second validator in the browser.**

**Nothing is silently rewritten.** An opaque leaf is emitted as the value it holds, and an untouched node as the value it was parsed from, both by reference. An edit rebuilds only the edited node and its ancestors, so its siblings and any opaque subtree come back unchanged. `!` keeps the bare or wrapped form it was written in, `"5"` stays a string, and `===` and `==` are never merged. The raw-JSON box behaves as `FormComponentEditor`'s box does today: text that is not yet JSON leaves the held value alone, and a value that parses is emitted as parsed, never re-indented or re-sorted. An opaque block edited into text that now parses stays a raw block until the expression reloads; a change of `tier` reloads the builder from its value and drops unfilled operands. **The builder emits only on an edit.** Mounting, focusing, blurring and expanding emit nothing. The host's next value after an emission is taken as its echo when it is equal as JSON and the user has changed nothing since, so a host that clones on write does not reload the tree, and any other value the host sets is loaded, a redo of the last emission or a reset to it included. An operand not yet filled in is shown invalid and emits nothing, and the builder reports its validity to the host. **"Unchanged" means `JSON.stringify` equality with key order included.** A duplicate key, `1.0` against `1`, and an integer past 2^53 are lost at `JSON.parse`, before the builder sees the value, exactly as they are in today's box.

**The tier and the variables are inputs.** `tier` is `calculate` or `conditional`, registry §2.1 against §2.5. In `calculate` the comparisons, `and`, `or` and `!` are not offered, and an existing one is an opaque leaf. `variables` is `{path, label, type?}[]`, plus a flag that lets a path be typed. The form builder passes its field keys, and the workflow editor passes the condition context the engine builds, which is narrower than [JWSS](../schema/JSON%20Workflow%20Schema.md) §6.1's (above), so the builder hard-codes no variable. A path outside the offered set is kept verbatim, with a visible warning.

**It evaluates nothing.** Evaluation is **D-10**'s `datalogic-wasm`, reached only through `lib/jsonlogic.ts`'s `loadEvaluator`. The builder does not import it, and `json-logic-js` is not a dependency (**D-86**). ## 8.4 The Document Lifecycle (FR-DOC-001..007)

A **document** is what a document type produces. It is created from the type, pins the exact form revision the type binds at that moment, holds the data somebody fills in, takes a number when it is submitted, and then moves through statuses until it is finished.

```text
Created from a type          DRAFT      form_id pinned, document_ref allocated
        ↓
Edited                       DRAFT      re-evaluated on every write (§8.2.2)
        ↓
Submitted                    SUBMITTED  number + status + payload, one transaction
        ↓                               …and the workflow, if its type binds one (§8.5)
Decided                      IN_REVIEW → APPROVED | REJECTED | RETURNED
        ↓                               by a person, or by an approval (§8.5.2)
Finished                     COMPLETED  or CANCELLED at any point before it
```

**Three status notions exist in this system, and only one of them is authoritative for any given question.**

- **`record_status`** is the governance lifecycle of a *master-data record* — a supplier is drafted, approved, made active, suspended (FR-MDM-007). It is a property of a record about a thing that keeps existing.
- **`workflow_instances.current_state`** is where a *process* is, and it is the single source of truth for that (§8.5). It is a state of one definition, so it means whatever that workflow says it means.
- **`documents.status`** is where an *event* is in a life that happens once and ends — and for a document with a live process it is a **projection** of the instance's state rather than a parallel record.

`ARCHIVED` is in the column and reachable from nothing until FR-DOC-010; the legality table says so rather than leaving a reader to grep for the string. **`PENDING_APPROVAL` became reachable in Phase 5** and is reachable only through a workflow — no manual transition enters it, which is what makes it a state that always means "something is deciding this".

### 8.4.1 The Submit Transaction (FR-DOC-003, FR-DOC-004)

The order matters and is not the obvious one:

```text
1. document:submit                     before anything is read
2. lock the instance, if there is one,  then read the document FOR UPDATE;
                                       not a draft → refused (#663)
3. re-evaluate the payload             the full pipeline; required now applies
4. allocate the number                 per the rule's own gap policy
5. write number + status + payload     conditional on it still being a draft
6. append the status-history row
7. start the workflow, if one is bound in the same transaction (§8.5)
8. commit, then audit as a SUBMIT
```

**Step 3 before step 4 is the whole of it.** Numbering first burns a number on every refused submission, and on a gapless rule it is worse than that: the counter is held from the allocation to the commit, so a slow re-evaluation serialises every concurrent submit of that type behind a document that is about to be refused. The order also buys more than the gap policy promised — a submission refused by the re-evaluation burns no number on *either* policy, because it never reaches the allocator.

**Everything from step 2 to step 7 runs on one connection.** A submit that took a second connection while holding a transaction on the first deadlocks a pool below the concurrency the pool can serve. That is exactly what a Sprint 7 defect did here, and it survived because nothing called the allocator's dispatcher under load.

### 8.4.2 What a Document Hands Back About Its Linked Entity (FR-DOC-011)

Reading a document returns `entityType` and `entityId` and nothing about the record they name. Resolving them is a sub-resource that requires the entity's **own** read permission — enforced by calling the master-data service rather than by checking a string, so a document cannot open what the master-data surface does not. It is the same answer §8.2.1 gives for lookup fields, and for the same reason.

Retiring the linked record leaves the document readable and its link unchanged; the resolution answers 404 about the *entity*. Cascading or nulling the link would rewrite a historical record because a supplier was retired years later.

## 8.5 The Workflow Engine (FR-WF-001..004, 006, 007, 013, 014)

A **workflow definition** is a finite state machine written in [JWSS](../schema/JSON%20Workflow%20Schema.md): states, the transitions between them, who may act on each, and — crucially — what each state *means for the document underneath it*. Publishing one freezes it and writes the projections a running instance is constrained by.

```text
Definition authored          DRAFT      validated on save: shape, operators, S1–S10
        ↓
Published                    ACTIVE     its roles checked live; immutable; states and
                                        transitions projected
        ↓
Bound to a document type                checked: exists, and is ACTIVE
        ↓
A document of that type is submitted
        ↓
Instance started             RUNNING    pins the revision; variables computed
        ↓
State entered                           its task is generated, in the same transaction
        ↓
Task decided                 APPROVE | REJECT
        ↓
Instance moved                          the next state's task, or the end
        ↓
Final state                  COMPLETED  outcome recorded; the document's status follows
```

**A definition that cannot terminate is refused at save, not discovered at run time.** JWSS §8's structural rules — reachability, dead ends, duplicate triples, a transition out of a final state, an ambiguous fallback — are enforced when the definition is written and again at publish. A workflow that can deadlock is a workflow that will, and the failure would land on whoever was waiting for an approval that could not move.

**Kelir resolves four of JWSS's six assignee types and refuses the other two at save**, naming what would have to exist first: `MANAGER_OF_OWNER` needs a user-to-manager relation this schema does not have (FR-ORG-002 is unbuilt), and `EXPRESSION` needs a directory context §6.1's condition context does not carry. JWSS §5.3 records the narrowing.

**The roles a definition names are checked live at publish, not at save** (**D-111**, [#572](https://github.com/sujanto-gaws/kelir/issues/572)). Every `ROLE` and `DEPARTMENT_ROLE` in a task's `assignment` (an object) or a transition's `allowedBy` (an object, or the JWSS §5.2 shorthand `"ROLE:X"`, which only `allowedBy` takes) must be a live role in the tenant, or the publish is refused with `ROLE_NOT_LIVE` at each path that names it. Liveness is a fact about the tenant rather than the document, so save does not ask it ([ADR-0019](../architectures/adr/0019.%20A%20Workflow%20Definition%20Is%20Narrowed%20at%20Save%20Time.md)). The publish holds those roles `FOR KEY SHARE` until it commits, which a role delete's `FOR UPDATE` conflicts with, so a publish and a delete of one role do not both succeed. The publish locks the definition's row first and reads the definition inside its transaction, so an edit to the draft cannot land between the checks and the publish: it waits, and is then refused because the revision is no longer a draft. JWSS §5.3 states the rule.

~~**`guards` and `actions` are stored and not executed** as of `v0.5.0`: there is no hook chain to merge them into (architectures/01 §12.4.2).~~ **`guards` and `actions` were stored and not executed as of `v0.5.0`**, when there was no hook chain to merge them into (architectures/01 §12.4.2). **Both run now**: `guards` on an automatic transition since Sprint 14, `actions` after every committed transition since Sprint 20 — §8.5.4 says where each is invoked and where not (corrected 2026-09-24, [#519](https://github.com/sujanto-gaws/kelir/issues/519)). They were accepted rather than refused so definitions authored then did not have to be rewritten, and the engine said so in one place — a stored handler must not read as evidence that it runs.

**Sequential approval only.** An instance is in one state, a JWSS state declares at most one `task`, so an instance has at most one open task — held by a partial unique index rather than by convention. FR-WF-016 (parallel approval) is deferred by SRS §4.8 itself, and when it is scheduled that index is what it has to argue with.

### 8.5.1 One Place a Process Moves

Starting an instance, firing a transition, generating the next state's task and projecting the document's status are **one code path**, called from the submit and from a decision. An engine is the shape a system most easily grows two of, and two engines would be two answers to "what happens when this is approved".

Every function on that path takes a transaction and none takes the pool: a submit already holds a numbering counter, and a second pooled connection taken inside a transaction deadlocks at the concurrency the pool can serve (§8.4.1's last paragraph, and **D-35**). ~~The lock ordering is **instance first, then task**, on every path~~ (struck 2026-10-08, [#663](https://github.com/sujanto-gaws/kelir/issues/663): the claim of a complete order was split twice, by #619 and #663, so it is struck rather than narrowed, by sprint plan §2 (a)). Two paths that take the same two rows in opposite orders deadlock at exactly the concurrency the feature exists for. **A decision, a claim, a hand-off and a reassign lock the instance, then the task. A submit locks the instance, then the document.** The task and history rows reference the document, so their foreign keys take it after the instance, and a resubmit that held the document while it waited for the instance deadlocked with a task path (#663). The submit reads the instance id before its transaction, and answers 409 if the document, once locked, points at a different instance. **This says what the paths lock. It does not promise that these are all the locks they take** ([ADR-0042](../architectures/adr/0042.%20An%20Administrator%20Reassigns%20an%20Open%20Task%20and%20Nothing%20Cancels%20One.md) §2).

### 8.5.2 The Document–Workflow Seam (FR-DOC-012, FR-WF-013)

> A workflow transition sets the document's status. **Setting the document's status does not move the workflow.**

The map from state to status is `mapsToDocumentStatus` **in the definition**, never in code: a new workflow says what its own states mean for a document, and adding one needs no backend change. The projection is written in the transition's own transaction, so a document whose status disagrees with the process deciding it is not a state the system can reach.

Enforcing the one-way rule costs the manual transition route something, and the cost is paid deliberately: `PUT /documents/{id}/status` **refuses a document that has a live instance**, naming the instance. Letting it through would produce the disagreement this seam exists to prevent, silently, on the screen a person is most likely to trust. A manual override would be a separate, audited action; nothing has asked for one, and the refusal is what makes the need visible if anything does.

A document links to **at most one live instance**, held by a partial unique index as well as by the service — so the refusal is true under concurrency and not only in the ordinary case.

### 8.5.3 The Task Inbox (FR-TASK-001, 002, 003)

> A caller sees a task when it is in their tenant **and** either they are its assignee, **or** it has no assignee and it is offered to a role they currently hold.

Enforced as a predicate in the query, not in a handler: a rule in a handler is one the next caller of the repository can step around. The roles are read from `user_roles` rather than from the access token's claim — a token is a snapshot from sign-in, and an inbox built from a stale claim offers somebody tasks the API will then refuse them, which reads as a broken product while being a leak.

**A task assigned to somebody and a task offered to a role are different situations**, and the payload says which rather than leaving a client to derive it from a null assignee. A role task is claimed by a compare-and-swap: two people claiming at once produce one winner and one 409.

### 8.5.4 System Tasks and the Hook Chain (FR-WF-005)

**`SERVICE_TASK` was in JWSS's `taskType` enum and nowhere else in the product** ([#339](https://github.com/sujanto-gaws/kelir/issues/339)). `graph.rs` stored the value as a string, defaulted it to `APPROVAL_TASK` and nothing branched on it — so a definition could declare a service task, validate, publish, and then generate a **human task that sat in somebody's inbox waiting for a person who was not coming**. The worst of the three possible states: worse than refusing it, because it failed silently and late.

**A service task writes no task row and takes its state's `AUTO` edge**, in the transaction that reached the state. One approval therefore moves a document through the service state and out the other side, and the approver never sees the middle one. The automatic step is its own `workflow_history` row, attributed to the decision that caused it.

**`AUTO` fires from a service task and from nothing else.** The action says *how* an edge is taken — without a caller — and the task type says whether anything takes it. Making every `AUTO` edge self-firing would turn a definition's parked state into one the engine runs straight through, in every definition already published.

**A chain of automatic steps is bounded rather than cycle-checked.** Two service states pointing at each other are both live and both exited, so S6's dead-end rule does not catch them; sixteen steps is far past any real chain and far short of a request that appears to hang. Exceeding it refuses the whole advance, which leaves the document where the decision found it.

**A failing service task does not strand the instance**, and the two failures differ:

| What happened | What the engine does |
|---|---|
| A guard returned `REJECT` | The transaction rolls back. The approval is undone, the task is open again, and the response is LHCS §6's `HOOK_REJECTED` naming the handler's own code |
| The state has no `AUTO` exit, or every condition was false | The instance stays, with its status projected. Refusing here would roll back somebody's approval because a *later* state was misconfigured |

**Four of the six task types are refused at publish, naming themselves.** `USER_TASK`, `REVIEW_TASK` and `DATA_ENTRY_TASK` would create the same row an approval does, and accepting them would mean four enum members behaving identically while claiming to be different things — the defect this section closes for the fifth. `SIGNATURE_TASK` is worse: nothing captures a signature, so accepting it would record an approval **as a signature that never happened**. It is [ADR-0016](../architectures/adr/0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md)'s rule — *a rule that fails open is a rule that is not there, reported as a rule that passed* — applied to a vocabulary rather than to a validator.

#### The chain itself

`modules::hook` implements the [Lifecycle Hook Contract](../schema/Lifecycle%20Hook%20Contract.md): §2's handler grammar, §3's registration entry and §3.1's priority bands, §4's payload in full — *every field present, inapplicable ones `null`* — §5.1's `CONTINUE` / `MODIFY` / `REJECT`, §6's envelope and §7's execution log in `document_hook_executions`. Registrations merge across sources into one chain ordered by priority, ties by registration order.

**A handler reference resolves at publish** (§2). A `core:` name outside the registry, a `plugin:` reference while no plugin runtime exists, a reference outside the grammar, and an `after_*` name inside `guards` (§3.2's kind constraint) are each a named refusal to the person writing the definition. Three core handlers ship — `continue_always`, `set_form_field`, `reject_when` — chosen as the smallest set that exercises all three of §5.1's results; every one of them is pure, and `core:require_attachment` is deliberately absent because it would need the database access this signature does not carry.

**What ~~is~~ was built first is the before half, and the reason ~~is~~ was not a schedule** ([ADR-0036](../architectures/adr/0036.%20The%20Hook%20Chain%20Ships%20Its%20Before%20Half%20First.md)). Architectures/01 §12.5 delivers an after-hook *through the outbox*, with idempotency, at-least-once delivery, a retry schedule and a circuit breaker — all four the worker's properties rather than a handler's. Kelir ~~has~~ had no outbox until ~~Phase 8~~ **Phase 9** (**D-79**, moved a sprint by **D-81**; corrected 2026-09-16, [#449](https://github.com/sujanto-gaws/kelir/issues/449)), ~~so JWSS `actions` stay stored, validated and never invoked, exactly as they were~~. **The outbox arrived in Sprint 20, and JWSS `actions` now run through it** — the after half below ([ADR-0041](../architectures/adr/0041.%20Every%20Workflow%20Transition%20Writes%20an%20Outbox%20Event,%20and%20After-Hooks%20Are%20Its%20First%20Consumer.md); corrected 2026-09-24, [#519](https://github.com/sujanto-gaws/kelir/issues/519)). `guards` now run, on an automatic transition and on no other; a decided transition does not yet invoke them, and the chain is the same one when it does.

**`MODIFY` is implemented in the chain and refused at the workflow call site.** §5.1 requires the engine to re-validate a modified payload against the form's own schema, which is the submit path's `secure_payload` — writing `form_data_json` from a guard without it would be the Tamper-Proof Pattern's failure with a hook in place of the browser. A guard returning `MODIFY` therefore fails with a message saying so, rather than taking effect unchecked.

#### The after half, through the outbox

**Every committed workflow transition writes one `Workflow.Transitioned` event to `outbox_events`, in the transition's own transaction** ([ADR-0041](../architectures/adr/0041.%20Every%20Workflow%20Transition%20Writes%20an%20Outbox%20Event,%20and%20After-Hooks%20Are%20Its%20First%20Consumer.md)). Decided (`engine::fire`) and automatic (`engine::advance_automatically`) alike, and whether or not any handler is registered to hear it: what the engine knows at commit is that a transition happened, not which handlers care. A second consumer — FR-INT-005's webhooks, a search indexer — reads the same rows without the engine writing again. A transition that rolls back leaves no event, because the transaction that would have written it is the one that rolled back.

| Envelope field ([EES](../schema/Event%20Envelope%20Schema.md) §2) | Value |
|---|---|
| `eventType` | `Workflow.Transitioned` |
| `aggregateType` / `aggregateId` | `WORKFLOW_INSTANCE` / the instance |
| `sequence` | The transition's position in the instance's `workflow_history` |
| `payload` | The `Workflow.*` profile plus `fromState` and `toState`, with the profile's `action` set. **No form data** (EES §4.2, §3.1) |

**`modules::outbox` is the writer, the worker, and a dispatch table from `eventType` to consumer.** An event is written through `outbox::write` inside the business transaction, never by one consumer calling another. The worker is `notification::worker`'s shape — a loop over its own table, with a `pass` a test can drive — and `after_workflow_transition` is the first consumer in its table.

```text
Transition commits           workflow_history row + outbox_events row      PENDING
        ↓
Worker claims the row        five-minute lease, held in next_attempt_at    PROCESSING
        ↓
Chain resolved               the transition's own actions, from the revision the instance runs
                             + the registry's after_workflow_transition entries, as they stand now
        ↓
Chain invoked                LHCS §4's payload, built from the document as it is at delivery
        ↓
Every handler succeeded      an empty chain too, with nothing run         PROCESSED
Any failure or timeout       next_attempt_at on the schedule below        FAILED
Sixth failed attempt         the envelope is kept                         DEAD_LETTER
```

**The chain is resolved at delivery, not at commit.** The definition revision is pinned on the instance (architectures/01 §12.5, *Definition version*), so the `actions` that run are the ones in force when the transition fired. Registry entries are read as they stand when the event is delivered: an entry added between commit and delivery runs, and one removed does not. **A handler sees the document as it is at delivery**, not as it was at commit — the envelope carries no form data, and a snapshot would be a second copy of it.

**A delivery succeeds when every handler it runs succeeds.** Any failure or timeout makes the whole delivery retryable, and a retry runs the whole chain again: LHCS §5.2 makes an after-hook idempotent, and a handler that is not has its effect applied again. Each handler has a 2-second budget and the chain 5 seconds: the before-hook defaults architectures/01 §12.5 sets, applied to after-hooks, because it gives after-hooks none. **A budget is measured, not enforced.** As in the before chain, a handler is timed and not cancelled, and a handler or chain that overran is logged `ERROR` and the delivery is retried. Every `core:` handler is pure and synchronous, so there is nothing to cancel. The first handler that waits on something outside the process is where cancellation has to be built.

| Failed attempt | The row becomes | Next attempt after |
|---|---|---|
| 1 | `FAILED` | 30 s |
| 2 | `FAILED` | 1 min |
| 3 | `FAILED` | 2 min |
| 4 | `FAILED` | 4 min |
| 5 | `FAILED` | 8 min |
| 6 | `DEAD_LETTER` | — |

That is 30 s × 2^(n−1) after the *n*th failure. **A `PROCESSING` row whose lease has expired is claimed again**, which is how a crashed worker's work is redelivered rather than lost. A `DEAD_LETTER` row keeps its envelope, so the event is never discarded; **dead letters have no screen**, and are read by SQL until FR-INT-006 or a later row gives them one. The schedule governs in-process dispatch only — FR-INT-007's per-integration `external_systems.retry_policy_json` governs calls to one external system, and is not this.

**Every handler run is a `document_hook_executions` row.** Success is logged `CONTINUE`, and failure or timeout `ERROR` with its `error_message` (LHCS §5.2, §7). An after-hook's result is not a veto: the transition has committed.

**A delivery that runs a handler holds its document's key share until it commits, and a submission waits for it** ([#556](https://github.com/sujanto-gaws/kelir/issues/556)). The worker writes each `document_hook_executions` row in the delivery's own transaction, and that table's `document_id` references `documents`, so the first insert takes `FOR KEY SHARE` on the document row and holds it until the delivery commits. A delivery that writes no row, an empty chain or one whose every handler the breaker holds, takes no lock on the document. `document::repository::lock_document` takes `FOR UPDATE`, which conflicts with it. So submission and resubmission (`submit_document`), and the edit and the delete routed through `lock_document` (`update_document`, `delete_document`), wait for a delivery of that document's event that is in flight. **The wait is not bounded by the 2-second and 5-second budgets**, which are measured, not enforced ([#536](https://github.com/sujanto-gaws/kelir/issues/536)). **A decision does not wait**: its status write is an `UPDATE` of non-key columns, which takes `FOR NO KEY UPDATE`, and that does not conflict with a key share. **No cycle forms**, because the worker waits on nothing a transition holds. [Record 19](../../projects/verifications/19.%20Sprint%2020%20Independent%20Pass.md) P1 held a delivery for 20 s under a forced sleep: the resubmission answered 200 after 18.1 s, with 0 deadlocks. **`publish_transition` writes the outbox row after `history::record`, in the transition's transaction.** In `engine::fire` it runs before `enter`, and in `advance_automatically` it runs last. Its insert takes only the `tenants` key share every insert here takes, and the sequence is a plain `count(*)`, so the placement changes no conflict. This settles the placement [record 18](../../projects/verifications/18.%20Sprint%2019%20Post-Tag%20Reading.md) §4 left open.

**The circuit breaker is derived from that log**, not from `plugin_error_logs` and not from a table of its own:

| Condition | What the worker does |
|---|---|
| A handler's last five executions for (tenant, `hook_name`, `handler_reference`) are all `ERROR` | The breaker opens. Holders of `ROLE-ADMIN` in the tenant are notified **once**, by the execution that opened it, through `notification::service::notify` — an in-app notification, not an outbox event |
| The breaker is open | The handler is not run. Its event counts as a retryable failure, so it is **delayed, not dropped** |
| Ten minutes have passed since the handler's last `ERROR` | One trial execution is allowed. A success closes the breaker |
| The trial fails | It records an `ERROR`, so the last five are still all `ERROR`: the breaker stays open, and the ten minutes restart from that `ERROR`. No second notification |

**Handlers declare their kind.** A `MODIFY` or `REJECT` after commit looks like a write or a veto and is neither — [ADR-0016](../architectures/adr/0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md)'s failure — so the kind is refused where the author is:

| Handler | Kind |
|---|---|
| `core:continue_always` | Before and after |
| `core:set_form_field` | Before only |
| `core:reject_when` | Before only |

`actions` naming a before-only handler is refused at publish with `HANDLER_KIND_MISMATCH`. A definition published before that rule, reaching a before-only handler at delivery, gets an `ERROR` for it on every transition it covers. **That failure is permanent**: it does not make the delivery retryable, and the rest of the chain runs.

**Two things stay off the outbox, and three are not built on it yet.** Notifications stay on their own table, delivered by `notification::worker` under [ADR-0034](../architectures/adr/0034.%20One%20Delivery%20Attempt,%20Recorded%20Rather%20Than%20Retried.md), and ERP posting runs inside the document transaction ([ADR-0037](../architectures/adr/0037.%20ERP%20Posting%20Runs%20Inside%20the%20Document%20Transaction.md) §6). Every event family other than `Workflow.Transitioned`, webhook delivery and plugin dispatch are not built as of Sprint 20: the table is the general outbox, and it has one writer and one consumer.

## 9.3 The External System Registry (FR-INT-001)

### 9.3.1 Routes

All routes are under `/api/v1/integration` and use §12.3's envelope. ~~**Fifteen operations**~~ ~~**Sixteen operations**~~ **Eighteen operations** are served: the sixteenth is the test call (§9.3.6), and the last two read the integration log (§9.3.8):

```text
GET    /external-systems                       (paged; search on code or name, filter by status and systemType)
POST   /external-systems                       (registered ACTIVE; 409 on a systemCode taken in the tenant)
GET    /external-systems/{id}
PUT    /external-systems/{id}                  (systemCode is not editable; status only ACTIVE ↔ MAINTENANCE)
POST   /external-systems/{id}/deactivate       (to INACTIVE; idempotent)
POST   /external-systems/{id}/activate         (to ACTIVE, from INACTIVE or MAINTENANCE; idempotent)
GET    /external-systems/{id}/endpoints        (INACTIVE included, ordered by endpointCode)
POST   /external-systems/{id}/endpoints        (409 on an endpointCode taken in this system)
GET    /external-systems/{id}/endpoints/{endpointId}
PUT    /external-systems/{id}/endpoints/{endpointId}   (retire with status INACTIVE, bring back with ACTIVE)
POST   /external-systems/{id}/endpoints/{endpointId}/test-call   (calls the endpoint now; §9.3.6)
GET    /external-systems/{id}/credentials      (inactive included, oldest first)
POST   /external-systems/{id}/credentials
GET    /external-systems/{id}/credentials/{credentialId}
PUT    /external-systems/{id}/credentials/{credentialId}
DELETE /external-systems/{id}/credentials/{credentialId}   (soft delete; 204)
GET    /logs                                   (paged, newest first; filter by externalSystemId, endpointId, status, from/to; §9.3.8)
GET    /logs/{id}                              (one row, its masked payloads as stored)
```

**There is no `DELETE` on a system or an endpoint**, and both answer 405. A delete would have to decide what happens to the `master_data_source_references` rows whose key names the system, and that decision has not been taken. A system is deactivated and stays listed. An endpoint is retired through its own edit. **Deactivating a system does not change its endpoints or credential references.** They cannot be used through an inactive system anyway, and switching each one off would leave activation with the extra job of remembering which ones had been active before.

**The permission is checked before existence**, so a caller without it gets 403 even for an id that does not exist. The id's existence is not revealed to somebody who may not read it.

### 9.3.2 Permissions

Eight permissions, not eleven (#520, the product owner's answers; [Database Schema](02.%20Database%20Schema.md) §12.10), **a ninth for the test call** (#547) **and a tenth for the integration log** (#548) — ten in all:

| Permission | Opens |
|---|---|
| `integration:external-system:read` | Listing and reading systems, **and their endpoints** |
| `integration:external-system:create` | Registering a system |
| `integration:external-system:update` | Editing a system, including `ACTIVE` ↔ `MAINTENANCE`; creating and editing its endpoints |
| `integration:external-system:deactivate` | `POST …/deactivate` **and** `POST …/activate` |
| `integration:credential:read` | Listing and reading credential references |
| `integration:credential:create` / `:update` / `:delete` | Adding, editing and removing one |
| `integration:endpoint:call` | `POST …/endpoints/{endpointId}/test-call`: calling an endpoint with its system's credential (§9.3.6) |
| `integration:log:read` | `GET /logs` and `GET /logs/{id}`: reading every call's row, with its masked payloads (§9.3.8) |

**Turning a system off and turning it back on are one permission** (decided 2026-09-25). `:deactivate` means *change whether the system is active*. It is separate from `:update` because correcting a base URL and stopping every integration that runs through a system are different questions, which is also why `workflow:definition:publish` is separate from `:update`. **A `PUT` therefore cannot move `status` into or out of `INACTIVE`.** The request is refused with 422 `NOT_ALLOWED` on `status` if it asks for `INACTIVE`, or if it sends any `status` while the stored status is `INACTIVE`. A `PUT` that leaves out `status` still edits an inactive system. `ACTIVE` ↔ `MAINTENANCE` stays an edit, because it says the system is being worked on, not whether it is in service.

**Endpoints use the system's permissions**, for reading and editing. An endpoint is part of a system's configuration, so it has no permissions of its own. **Calling one is the exception**: a call sends a resolved secret to a third party and can change data there, which neither reading nor editing configuration does.

**Credentials have separate permissions.** A credential route needs only its own `integration:credential:*` permission, not `integration:external-system:read`. A system or endpoint response never contains a credential. The detail page fetches credential references separately and **does not render the section** for a caller without `integration:credential:read`. A person who can see a system cannot necessarily see where its secrets live.

### 9.3.3 A Credential Is a Reference ~~, Never a Secret~~

`secretReference` says where a secret lives. ~~No route resolves it. The runtime that resolves a reference to make a call belongs to FR-INT-002, and it will resolve in process.~~ **One route resolves it: the test call** (§9.3.6, [ADR-0043](../architectures/adr/0043.%20A%20Test%20Call%20Runs%20in%20the%20Request,%20Resolves%20Only%20env%20Secrets,%20and%20Connects%20Only%20to%20a%20Checked%20Address.md)). It resolves **in process, for the call's duration only**. No type, response, OpenAPI schema, log line, `integration_logs` row or `audit_events` row has a field for a resolved secret. **`env://NAME` resolves** from the backend process's environment, **and only when `NAME` ~~starts with `KELIR_INTEGRATION_SECRET_`~~ is in the calling tenant's namespace, `KELIR_INTEGRATION_SECRET_<CODE>__<NAME>`** (**D-96**, decided 2026-09-30 on [#618](https://github.com/sujanto-gaws/kelir/issues/618), amended 2026-10-01; §9.3.6's *Secret* row). Any other name fails the call with `SECRET_NAME_NOT_PERMITTED` before the variable is read, so `env://KELIR_JWT_SECRET` resolves nothing, and neither does another tenant's variable. **`vault://` does not resolve**: the call fails with `SECRET_BACKEND_NOT_CONFIGURED`, until a HashiCorp Vault KV v2 client, ~~placed by construction plan 18~~ [#605](https://github.com/sujanto-gaws/kelir/issues/605), placed after `v1.0.0` by **D-98**'s answer C (corrected 2026-10-08). **Saving is unchanged**: both shapes, and any variable name, are still accepted at save, and the rules above apply when the reference is called. An operator names a secret with ~~the prefix~~ its tenant's prefix ([Installation](../operations/01.%20Installation%20and%20Deployment.md) §7.1).

**Only two shapes are accepted**, and anything else is 422 `NOT_A_SECRET_REFERENCE`:

| Scheme | Shape |
|---|---|
| `env://NAME` | `NAME` is an environment-variable name: an upper-case letter or `_`, then upper-case letters, digits and `_` |
| `vault://path[#field]` | One or more `/`-separated segments of letters, digits, `_`, `-` and `.`. No segment is empty, `.` or `..`. The optional `#field` uses the same alphabet |

Every reference is also at most 255 characters and is stored trimmed.

**Whether a string is a secret cannot be decided from the string**, so this is a shape check and says what it cannot catch. It refuses a bare token, most base64, a PEM block, a `user:password` pair, a URL to anywhere else, and any value without one of the two schemes. **It does not refuse a secret typed as a path segment**: `vault://sk_live_abc123` has the right shape. The guarantee is narrower: every stored value parses as a reference a resolver can follow. **Nothing checks at save that the variable or vault path exists.** ~~because nothing resolves a reference yet~~ A missing variable is found by the first test call that needs it, and fails that call.

### 9.3.5 Audit

These are configuration changes, so they go to the hash-chained audit trail (§11.3). The activity timeline is not used, because it belongs to documents. An activate or deactivate that changes nothing writes no event, since an event saying the system moved would be false. **Each event is written after its change commits, through `audit::record_or_warn`.** If that write fails, the failure is logged at error level and the change still stands, so the trail can have a gap it records nowhere else.

| Object type | Events |
|---|---|
| `EXTERNAL_SYSTEM` | `ExternalSystem.Registered`, `.Updated`, `.Deactivated`, `.Activated` |
| `INTEGRATION_ENDPOINT` | `IntegrationEndpoint.Created`, `.Updated` |
| `INTEGRATION_CREDENTIAL` | `IntegrationCredential.Created`, `.Updated`, `.Deleted` |

`GET /audit` shows a row's values only with the read permission of the object the row names (**D-49**). For systems and endpoints, that is `integration:external-system:read`. **For credentials it is `integration:credential:read`**, because a credential event's values include `secretReference`.

### 9.3.6 The Test Call (FR-INT-002)

**An administrator calls one endpoint now, and gets the answer in the response** ([#547](https://github.com/sujanto-gaws/kelir/issues/547), plan 17 row 16). `POST /api/v1/integration/external-systems/{id}/endpoints/{endpointId}/test-call`, under `integration:endpoint:call`. Why it is shaped this way is [ADR-0043](../architectures/adr/0043.%20A%20Test%20Call%20Runs%20in%20the%20Request,%20Resolves%20Only%20env%20Secrets,%20and%20Connects%20Only%20to%20a%20Checked%20Address.md).

```text
Find the target          permission first (403 FORBIDDEN), then the system and the endpoint
                         in the caller's tenant (404 NOT_FOUND). Neither writes a log row
        ↓                ── the call begins here; every path below writes one row ──
Check it may be called   system ACTIVE, endpoint ACTIVE, baseUrl present;
                         the endpoint's path appended to baseUrl
        ↓
Choose the credential    exactly one active, undeleted credential valid today (UTC);
                         its type must be BEARER_TOKEN or BASIC_AUTH
        ↓
Read the tenant codes    the caller's tenant_code by tenant_id, and every other live
                         tenant's, in one query
        ↓
Resolve the secret       env://KELIR_INTEGRATION_SECRET_<CODE>__* from the process
                         environment, the caller's <CODE> only and no name another
                         tenant's code also covers; any other env:// name fails;
                         vault:// fails
        ↓                ── one deadline of timeoutSeconds from here to the body read ──
Check the address        resolve the host once; every address it returns must pass
        ↓
Call                     the endpoint's method, no body, pinned to the checked addresses,
                         no redirects; at most 64 KiB of the reply is read
        ↓
Log                      one integration_logs row, masked, success or failure
        ↓
Answer                   200 with what came back, or the failure's code, naming the log id
```

**It runs inside the request.** No `core:` handler, no outbox event, no hook chain: the outbox keeps one consumer (§8.5.4), and an after-hook's time budget ([#536](https://github.com/sujanto-gaws/kelir/issues/536)) does not apply. No transaction is held across the call: the log row is one statement written after the call ends, so a slow system holds a request worker and never a database connection.

| Rule | As built |
|---|---|
| Request | **The route takes no request body**, and one sent is ignored. **No URL, host or header comes from the caller** |
| Destination | The endpoint's `path` **appended to** its system's `baseUrl`, not resolved against it: `https://erp.example.com/api/v2` and `/orders` make `https://erp.example.com/api/v2/orders`. The result must keep the base's scheme, host and port, be `http` or `https` and carry no user information, or the call fails with `TARGET_URL_INVALID` (a row stored before §9.3.4's rules may not) |
| What is sent | **The endpoint's `method` with an empty body.** Two headers: `Authorization`, and `X-Correlation-Id` carrying the log row's `correlation_id` so the called system's own log can be matched with it (architectures/03 rule 4). No proxy is used |
| Callable | The system must be `ACTIVE` (a `MAINTENANCE` system is refused too) and so must the endpoint; the system must have a `baseUrl` |
| Credential | **Exactly one credential qualifies**: `isActive`, not deleted, and valid today, where today is the UTC date and both `validFrom` and `validTo` are inclusive (an absent bound is open). | Audit | **None.** A test call changes no configuration; its record is the log row |

~~**No response, log line, `integration_logs` row or `audit_events` row carries the resolved secret.**~~ **Kelir writes the resolved secret nowhere**: not in the request record, a log line or an `audit_events` row. An echo of it in the called system's reply is redacted in the spellings listed above, and a spelling outside the list is stored in the log row and returned in `bodyPreview` exactly as the system sent it (struck 2026-10-01, [#621](https://github.com/sujanto-gaws/kelir/issues/621)).

**A test call is a real call.** A `POST` endpoint receives a real request and does whatever it does with it.

**The client is `reqwest` 0.12** with `default-features = false` and `rustls-tls-native-roots` only, built per call with redirects disabled, no proxy and no idle pool, so the binary keeps one TLS stack and the operating system's certificate store. `base64` encodes the `BASIC_AUTH` header and `zeroize` wipes the resolved secret when the call ends.

**The test seams.** `AppConfig::integration_allow_loopback` lets the guard pass a loopback address so the integration tests can call a mock server on `127.0.0.1`. `AppConfig::integration_dns_overrides` answers chosen host names with chosen addresses ahead of the system resolver, so a test can make one name resolve to a public and a private address, or to one that does not connect before one that does; the answer is judged by the guard as any other. **Both are code-only**: `AppConfig::from_env` always sets the first `false` and the second empty, and no environment variable changes that.

#### The answer

A system that answered, whatever its status:

### 9.3.8 The Integration Log (FR-INT-006)

**An administrator reads the calls Kelir made** (2026-09-29, [#548](https://github.com/sujanto-gaws/kelir/issues/548), Sprint 21 row 17). Two routes read `integration_logs` ([Database Schema](02.%20Database%20Schema.md) §12.5) under `integration:log:read`, a permission of its own: a log reader need not manage systems, and a system manager does not see every call's payload by default. The permission is checked before existence, so a caller without it gets 403 from both routes, for any id.

```text
GET /api/v1/integration/logs         paged list of IntegrationLogSummary, newest first
GET /api/v1/integration/logs/{id}    one IntegrationLog: the summary, documentId, requestPayload, responsePayload
```

**The list** is ordered by `startedAt` descending, then `id` descending, so a page boundary inside a run of equal start times neither repeats nor skips a row. It uses §12.3's list envelope and the `page`/`pageSize` of every other list. Its filters combine:

| Filter | Selects |
|---|---|
| `externalSystemId` | The calls to one system |
| `endpointId` | The calls to one endpoint: rows whose `entity_type` is `IntegrationEndpoint` and whose `entity_id` is this id |
| `status` | One of the column's five values, `SUCCESS`, `FAILED`, `PENDING`, `RETRYING`, `DEAD_LETTER`; a test call writes only the first two |
| `from`, `to` | `startedAt` **from inclusive, to exclusive**, so consecutive ranges share no row. `to` before `from` is 422 `RANGE_INVERTED`; `to` equal to `from` is an empty range, not an error. A bound before 4714 BC is 422 `OUT_OF_RANGE` (§12.3) |

An id naming another tenant's system or endpoint, or none, matches no row; it is not checked against the registry. **`idx_integration_logs_tenant_system_started` serves every filter within the tenant**: with `externalSystemId` (and `from`/`to`) the list is a range scan of the index in `startedAt` order; without it the index serves the `tenant_id` prefix, `from`/`to` narrow that scan, and `status` and `endpointId` filter the rows it yields. None reads beyond the tenant's own rows, and no index was added. **Measured against a custom plan**: the optional filters are `$n IS NULL OR …` predicates in one prepared statement, and a generic plan, which PostgreSQL may choose after five executions, uses only the `tenant_id` prefix and applies every filter to the tenant's rows. That is still a scan of one tenant, never of the table.

**A list item** carries `id`, `externalSystemId`, `externalSystemCode` and `externalSystemName` (joined, `null` when the row names no system; a system deactivated since is still named), `direction`, `integrationType`, `method`, `endpoint` (the URL), `entityType`, `entityId`, `status`, `statusCode`, `errorMessage`, `correlationId`, `startedAt`, `completedAt` and `durationMs`. **The detail** adds `documentId`, `requestPayload` and `responsePayload`. Another tenant's id is 404.

**Nothing is resolved or unmasked.** The payloads were masked before they were stored, to §9.3.6's list, so an echo outside it is returned as stored, and both routes return them exactly as stored. The OpenAPI document has no field for an unmasked payload.

**A test call's refusal names its row**: its message ends `(integration log <id>)` (§9.3.6), and that id is the detail's `{id}`.

**In the browser**, `IntegrationLogPage` is at `/admin/integration-logs`, opened by `integration:log:read`, and a row's detail is a dialog at `?log=<id>`. A test call's log id links there for a holder of `integration:log:read`. In the detail, the system links to its page only with `integration:external-system:read`, and the document only with `document:read`.

`integration:log:read` is seeded by `0050_integration_log_read_permission.sql` and granted to the system tenant's `ROLE-ADMIN`. It is not a withheld family, so a tenant provisioned after that migration is granted it ([Database Schema](02.%20Database%20Schema.md) §12.10).

# 11. Security Design

## 11.1 Authentication

```text
Username/email + password
Argon2 password hashing
JWT access token or secure session
Refresh token or session renewal
Logout and token invalidation
Rate limiting on authentication endpoints (NFR-SEC-008)
Self-service password reset over an emailed single-use token (FR-AUTH-006)
```

**An access token is verified by its signature and its expiry, and then the
request reads that its tenant and its user are not deleted** (rewritten
2026-10-01, decisions **D-104** and **D-105**,
[ADR-0045](../architectures/adr/0045.%20Every%20Authenticated%20Request%20Reads%20That%20Its%20Tenant%20and%20User%20Are%20Not%20Deleted,%20and%20a%20Token%20Has%20No%20Leeway.md)).
~~It is verified by its signature and its expiry, and by nothing else, and
authenticating a request reads no row~~: that was true until
[#650](https://github.com/sujanto-gaws/kelir/issues/650) was closed. The token
is a JWT whose `exp` is 15 minutes after issue (`ACCESS_TOKEN_TTL_MINUTES` in
`modules/auth/token.rs`, a constant and not configuration). The refresh token
is opaque, stored as a hash, rotated on every use, and lives 30 days.

**A token is accepted for its 15 minutes and no longer.** `verify_access_token`
sets the leeway on `exp` explicitly, from a named constant, to zero. ~~It
allowed a further 60 seconds, the `jsonwebtoken` library's default, which
nothing in the code set~~, so until this change an issued token worked for up
to 16 minutes. With no leeway there is no tolerance for a clock difference
between the instance that issues a token and one that verifies it: a verifier
whose clock runs ahead refuses the token that much early, and one whose clock
runs behind accepts it that much late. A deployment that runs more than one
backend keeps their clocks in step, well under a second apart
([Installation and Deployment](../operations/01.%20Installation%20and%20Deployment.md)
§7). The shipped compose files run one.

**The read is in the `Authenticated` extractor** (`middleware/auth.rs`), after
the token is verified, on every route that takes it: 143 operations on
2026-10-01. It calls `identity::service::token_subject`, one statement of two
scalar subqueries: the tenant by the claims' `tenant_id`, and the user by the
claims' `sub` within that tenant. The statement always returns one row, and
each of the two reads as live, deleted or missing.

| The tenant and the user | The request |
|---|---|
| Both live | Proceeds to its handler |
| Not both live: either is deleted, either has no row, or the user is not the claimed tenant's | 401 `UNAUTHORIZED`, the envelope an expired token gets, with no reason. The operator's log says which, at `warn`: `tenant` and `user`, each `live`, `deleted` or `missing`, with both ids |
| The statement fails | A 5xx. The request is never accepted on a failed read, and never answered 401 for one: a 401 makes the client refresh, and end the session when that fails |

**It reads `deleted_at` and never `status`.** The status, the username, the
roles and the permissions a token carries are a snapshot from its issue, and
stay one until the token expires. The connection is returned to the pool before
the handler takes its own, so a request still holds one at a time
([coding standard](../standards/01.%20Coding%20Standard.md) §2.5).

**An access token outlives the suspension or deactivation of its tenant, and a
change of its user's status to `INACTIVE` or `LOCKED`, until it expires: at most 15
minutes from issue** (decision **D-104**, answered 2026-10-01; ~~16 minutes~~
until the leeway was removed). This is a stated limit, and the rule is the same
for a tenant and a user:

| Change | Sign-in | Refresh | Access token already issued |
|---|---|---|---|
| A tenant leaves `ACTIVE` (`SUSPENDED` and `INACTIVE` alike) | Refused | Refused: the tenant's refresh tokens are revoked, and a refresh reads its tenant's status itself, so it is refused, 401, and revokes that user's refresh tokens even where no revoke ran (added 2026-10-09, [#649](https://github.com/sujanto-gaws/kelir/issues/649)) | Works until it expires |
| A user is made `INACTIVE` or `LOCKED` | Refused | Refused: `update_user` revokes the user's refresh tokens for any status that cannot sign in | Works until it expires: no request checks the user's status. A read and a write were both tested, for each status (`LOCKED` added 2026-10-02, with `locked_until` set as well) |

**A deleted tenant's token, and a deleted user's, are refused at once**
(decision **D-105**, answered A on 2026-10-01; ~~D-104 does not decide a
deleted tenant or a deleted user~~). "Deleted" means `deleted_at`, never
`status`:

| Change | Sign-in | Refresh | Access token already issued |
|---|---|---|---|
| A tenant is deleted | Refused: the code resolves to nothing | Refused: the tenant's refresh tokens are revoked, and a refresh reads that its tenant is not deleted, as for a tenant that left `ACTIVE` (added 2026-10-09, #649) | Refused, 401, on every authenticated route from the next request |
| A user is deleted | Refused | Refused: the user's refresh tokens are revoked | Refused, 401, on every authenticated route from the next request. `GET /auth/me` answers 401, not 404 |

**The user list's Deactivate button is the second row, not D-104's.** It calls
`DELETE /identity/users/{id}`, a soft delete, so it ends that user's token at
their next request. Setting a user's status to `INACTIVE` in the edit dialog is
D-104's case and leaves up to 15 minutes.

Until this change, a token issued before its tenant was deleted read the
tenant's data on `GET /auth/me`, `GET /identity/users`, `GET /identity/roles`
and `GET /documents`, and `POST /identity/users` created a user inside the
soft-deleted tenant ([#650](https://github.com/sujanto-gaws/kelir/issues/650)).
The integration test call answered such a token 500
([#648](https://github.com/sujanto-gaws/kelir/issues/648)); it is now refused
before the service (§9.3.6).

**What the check does not reach:**

- **Refresh, logout and sign-in** are not given it. ~~A refresh does not check
  the tenant's status either: it is refused because the tokens were revoked
  ([#649](https://github.com/sujanto-gaws/kelir/issues/649), open).~~ A
  refresh reads its own rows instead: the user's status, and since #649
  (2026-10-09) its tenant's, by id, in one lookup per refresh. A tenant that
  is not `ACTIVE`, or is deleted, refuses the refresh and revokes that user's
  refresh tokens, so renewal does not depend on the revocation that follows a
  status change, which runs as a second statement. It reads the rule sign-in
  reads, `TenantStatus::admits_sign_in`, and not this check's, which reads
  `deleted_at` only.
- **A password change** revokes the refresh tokens and does not end an access
  token already issued.
- **A request already past the extractor** when a deletion commits runs to
  completion.

Both rules are held by tests in `tests/organization_tenants.rs` and
`tests/auth_session.rs`: a token whose tenant was suspended or deactivated, or
whose user was made `INACTIVE` or `LOCKED`, still reads and writes until it
expires; a deleted tenant's or user's access token and refresh token are both
refused at once; and an expired token is refused with nothing to renew it.
`tests/deleted_caller_refusals.rs` walks every operation in the OpenAPI
document that declares bearer security, sends each a live token, a deleted
tenant's and a deleted user's, and requires that no table's row count moves
across the refused passes. `tests/auth_deleted_caller.rs` holds the cases a
walk cannot: the envelope, the pairing of `sub` with `tenant_id`, a missing
row, a failed lookup and the expiry edge. The leeway is a named constant
asserted to be zero at compile time, and the unit test that sets `exp` to one
second before now is what tells zero from one. No test reads the log line.
[Database Schema](02.%20Database%20Schema.md) §2.1 and the
[User Manual](../operations/03.%20User%20Manual.md) §11.1 and §11.4 state the
same limits from this rule.

**The reset flow answers identically whatever it is given.** An unknown
identifier, a suspended account, a resend still inside its cooldown and a mail
server that is down all produce the same 202, because any difference between
them tells an unauthenticated caller whether an account exists. The throttle is
therefore per account and applied silently rather than reported, and the
endpoint is not metered by the rate limiter that answers 429 — a 429 would be
the difference the rest of the design removes. Redeeming a token *is* metered:
a wrong token is a 4xx, so attempts are countable there without leaking
anything.

**Identical is not indistinguishable, and the difference is timing** ([#202](https://github.com/sujanto-gaws/kelir/issues/202),
decision **D-31**). The status and the body are the same for every input; the
*work* is not, and until 2026-08-27 the response waited for a complete SMTP
transaction, so a known account answered in a p50 of 90ms against an unknown
identifier's 9.8ms — an enumeration oracle on the one endpoint deliberately
left off the rate limiter. The send is now handed to the runtime and the
measurement is 26.4ms against 10.5ms: **narrowed, not closed.** What is
guaranteed is that no caller's measurement includes a mail server, which is
the part that grows without bound when a relay is slow. Closing the residual
means padding the fast path to a fixed budget — a different control, with a
denial-of-service surface of its own, and D-31 declines it here.

See [Database Schema](02.%20Database%20Schema.md) §3.9 for how the token itself
is stored.

## 12.3 Standard Response

Item response:

```json
{
  "success": true,
  "data": {}
}
```

List response:

```json
{
  "success": true,
  "data": [],
  "meta": { "page": 1, "pageSize": 20, "total": 0 }
}
```

Every list takes `page` (1-based; absent or below 1 is 1) and `pageSize` (clamped to 1–100). **A list a chooser picks from also takes `search` and, where the resource has one, `status`** ([#525](https://github.com/sujanto-gaws/kelir/issues/525)): document types, forms, lists, workflow definitions, users and roles, as the external systems (§9.3) and documents already did. A chooser that fetched one page of 100 and filtered it could not reach a row that sorted past the hundredth, so the filtering is the server's. The rules are the same on every list:

- `search` is a case-insensitive substring of the resource's key and name — for a user, the username, the email and the display name. `%`, `_` and `\` in it match themselves (`utils::search::like_contains`, which these six, the external systems and the master-data lists share; the documents list and the task inbox still escape with private copies of the same rule), and a blank search is no search.
- ~~A `search` containing NUL (U+0000, `%00`) is a 422 on `search` (`INVALID_CHARACTER`; `q` on the task inbox)~~ **A NUL (U+0000, `%00`) in any query parameter is a 422 `VALIDATION_ERROR` naming that parameter as sent, with `rule` `pattern` and `code` `INVALID_CHARACTER`** ([#601](https://github.com/sujanto-gaws/kelir/issues/601), [ADR-0044](../architectures/adr/0044.%20A%20Value%20PostgreSQL%20Cannot%20Store%20Is%20Refused%20in%20One%20Shared%20Place,%20Never%20per%20Parameter.md)), rather than a search with the NUL stripped: PostgreSQL `text` cannot hold 0x00, so the value could only ever fail the statement, and no row can contain one. `crate::extract::QueryParams` refuses it before the query is deserialized, so it applies to every route that reads a query string, to a parameter the route ignores, and to a uuid or an enum, which answers `INVALID_CHARACTER` rather than its parse failure. A NUL in a key is not refused. Every list that searches — these six, the external systems, the documents list, the master-data role views, the lookups and the task inbox — still reads its term through `utils::search::parse_search`, which is the trim and the blank rule, and whose own NUL refusal is now a second line of defence.
- **A date bound PostgreSQL's `timestamptz` cannot hold** — before `-4713-11-24T00:00:00Z` (4714 BC) — is a 422 naming each such bound, with `rule` `range` and `code` `OUT_OF_RANGE`, from `utils::storable::refuse_out_of_range`, which every service taking a date range calls before its query (today `GET /audit` and `GET /integration/logs`, §9.3.8). When both bounds are out of range, both are named.
- `status` is an exact match. A value outside the resource's vocabulary is a 422 naming `status`, because it deserializes into the enum; a role has no status, and there the parameter is ignored like any unknown one.
- `meta.total` counts the rows matching both, because the count and the page are the same predicate.
- The order is the list's own, by key, whatever is searched.

**The search is an unindexed `ILIKE`, on purpose.** A substring match cannot use a b-tree index, and no trigram index is added for it — the searches that came before (documents, [Database Schema](02.%20Database%20Schema.md) §6.16; external systems; the master-data role views) have none either. These are configuration tables, sized in hundreds of rows per tenant rather than millions, and scanned within one tenant; a `pg_trgm` index chosen before the query has been measured against a real tenant would be chosen on a guess. The `status` filter on forms can use the existing `idx_rad_forms_tenant_id_form_key_status`.

Standard error:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Validation failed",
    "details": []
  }
}
```

JFSS validation failures populate `details` with `{path, rule, code, message}` entries per JSON Form Schema S10.3. JSON payload fields are `camelCase` (naming convention §5).

**Every refusal under `/api/v1` uses this shape, including the ones raised before a handler runs.** A malformed body, a body carrying an unknown field, a query parameter that will not parse, and a path segment that will not parse are all rejected by an extractor rather than by module code, and an extractor that rejects with its own reply answers outside the envelope — which is the one shape a client written against `error.code` cannot read. `kelir-backend/src/extract.rs` therefore supplies `JsonBody`, `QueryParams` and `PathParam` in place of `axum::Json`, `axum::extract::Query` and `axum::extract::Path`; the three are drop-in and their `utoipa` annotations are unchanged. Handlers use no other extractor for request data. Statuses are unchanged by the wrapping: a bad query parameter is a 422 naming the parameter, a bad path segment stays a 400.

# 13. Deployment Design

## 13.1 Development Deployment

```text
Docker Compose
├── frontend
├── backend
├── postgres
├── mailpit
├── minio
├── minio-init    (one shot: creates the bucket, then exits — #244)
└── clamav        (added in Phase 6, when attachment scanning needs it)
```

**`minio-init` exists because the application does not create its own bucket.**
The backend is given credentials that put and get objects in a bucket somebody
else provisioned; a process that can create buckets can create the one an
attacker names. CI's backend job does the same thing with a one-shot `mc` step,
and [`deploy/env/.env.example`](../../deploy/env/.env.example) says so where an
operator will read it. Storage was in this stack from Sprint 0 and used by
nothing until [#244](https://github.com/sujanto-gaws/kelir/issues/244).

The scanner is ClamAV, decided 2026-08-11 as [Product Backlog](../../projects/planning/02.%20Product%20Backlog.md) decision **D-4**. **Sized 2026-08-31**, which D-4 did not do: 25 MiB scans over INSTREAM in **169 ms** at ~156 MiB/s, `clamd` holds **955 MB resident** — almost all of it the signature set — and starts in ~20 s because the image ships its database. **Concurrency buys nothing**: aggregate throughput is flat from one parallel scan to sixteen, so one instance and a worker concurrency of 2–4 is the whole sizing. The 1 GB is the number this stack has to find, and it is per instance rather than per load. Method and numbers on [#246](https://github.com/sujanto-gaws/kelir/issues/246).

**Two things the scanner's own defaults make easy to get wrong.** `clamdscan` against a shared filesystem falls back to a path scan and answers `OK` where the wire answers `INSTREAM size limit exceeded. ERROR`, so the worker and its tests must speak INSTREAM. And `clamd.conf.sample` documents `StreamMaxLength 25M` — exactly `KELIR_STORAGE_MAX_UPLOAD_BYTES` — so **`StreamMaxLength` must be set strictly above the upload limit**, or every maximum-size upload is recorded `FAILED` and becomes permanently undownloadable. Scanning is asynchronous and never inline in a request handler ([coding standard](../standards/01.%20Coding%20Standard.md) §2.4): upload sets `virus_scan_status = 'PENDING'`, a worker scans and updates it via the outbox, and download is blocked until `'CLEAN'` ([Database Schema](02.%20Database%20Schema.md) §8.2 — §8.1 is the category table, and the pointer named it until #244 built both).

# 16. Risks and Mitigation

| Risk | Mitigation |
|---|---|
| Workflow engine becomes too complex | Start with lightweight state-transition engine before BPMN |
| Multi-database compatibility complexity | Use PostgreSQL first, MariaDB later with compatibility layer |
| Dynamic plugins introduce security risk | Start with configuration-based and compiled-in plugins |
| RAD metadata becomes unstable | Version metadata and validate schema strictly (JFSS meta-schema is normative) |
| Frontend dynamic rendering complexity | Build reusable FormRenderer and ListRenderer incrementally |
| Audit log grows large | Partition/archive audit tables and define retention policy |
| File storage grows | Use object storage and metadata tracking |
| Integration failures | Use outbox, retry, dead-letter, and integration logs |
| Permission complexity | Start with RBAC before ABAC |
