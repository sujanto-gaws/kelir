**`features/rad/` is shaped by the definition it renders, not by a screen** (FR-RAD-010, #162). `renderer/` holds the dispatch and the component registry, `fields/`, `layout/`, `display/` and `actions/` hold one component per JFSS role, and `__fixtures__/` holds the definitions both the unit tests and the browser harness read.

**The registry is Kelir's component vocabulary, and the only copy of it.** JFSS §4.4 makes `type` *"an open vocabulary defined by each implementation's component registry"* and the meta-schema enumerates none, so nothing upstream decides which component types exist — `features/rad/renderer/registry.ts` does, for the client, exactly as `modules/rad/domain/jfss.rs` does for the lookup sources on the server. A type that is neither supported nor declared missing there renders as a named placeholder rather than as nothing, because a form silently missing a field is indistinguishable from a form that never had one.

## 5.4 Session Lifecycle

The session lives in one Pinia store (`stores/auth.ts`) and is read by two things that must not import it directly: the API client, which needs the bearer token and a way to refresh it, and the router, which needs to know when the session ends. Both seams are small modules the store registers with — `api/session.ts` in one direction, `stores/session-events.ts` in the other — because a direct import either way is a cycle, and the router installs its guards before any store exists.

A session ends in one of three ways, and they are not the same event:

| How it ends | What the store does | What the caller sees |
|---|---|---|
| The caller signs out | Clears locally, calls `/auth/logout` | The caller is already navigating |
| The server refuses the credentials — a refresh 401s, a token is revoked, an account is deactivated | Clears **and announces** | Redirected to the login page, told the session ended |
| Another tab signs out | Clears **and announces** | The same |

**Announcing is what makes the second and third cases survivable.** The route guard runs on navigation; a session lost while the caller sits on a page moves nothing, so before [#68](https://github.com/sujanto-gaws/kelir/issues/68) nothing redirected them. They stayed on a page whose data was stale and whose every action would fail — an administrator editing a role submitted the form, got a 401, and had no explanation. `registerGuards` listens for the announcement and leaves the page.

Two things are deliberately *not* announced. A deliberate sign-out is not, because its caller is already navigating and a second redirect would race the first. And a failure that is not the server refusing the credentials — a 5xx, a timeout, an unreachable host — is not a lost session at all: the tokens are still good, and treating a two-second connectivity drop as a sign-out is the outcome the distinction exists to prevent. Only 401 and 403 end a session; every other status leaves it standing for the server to refuse on the next call.

The login page then has two things to say and picks the better one. Tokens still present means the session was never lost, only unconfirmed, and it offers a retry ([#66](https://github.com/sujanto-gaws/kelir/issues/66)). Tokens gone plus the router's `sessionEnded` marker means the session genuinely ended, and it says so — without the marker, arriving after a lost session and arriving from a deep link are indistinguishable, since both carry `redirect` and neither carries a session.

Form definitions conform to the **JSON Form Schema Standard (JFSS v2.0.1)** in [docs/schema/](../schema/JSON%20Form%20Schema.md); calculations and validation rules are restricted to the operators and rules registered in the JFSS Calculation and Validation Rule Registries.

### 8.2.1 Lookup Fields (FR-RAD-007)

A **lookup** is the one component whose options come from the database rather than from the definition. Every other component is a function of the definition it is declared in; this one is a function of master data, which makes it the component that has to answer a question none of the others do: *a lookup must not become a way to read master data the caller could not read directly.*

**How a definition declares one.** A `data` component of `type: "lookup"`, plus an entry in the form's `settings.lookups` mapping that component's `id` to a master-data source:

```json
{
  "formId": "purchase-requisition",
  "version": "2.0.1",
  "settings": { "lookups": { "supplier_field": "supplier" } },
  "components": [
    { "id": "supplier_field", "role": "data", "type": "lookup",
      "key": "supplier_id", "label": "Supplier",
      "validation": { "type": "string" } }
  ]
}
```

**Why the binding sits in `settings` rather than on the component.** JFSS is a `Final Standard` — frozen at v2.0.1, errata only, and a successor takes a new major version ([naming convention](../standards/02.%20Naming%20Convention.md) §10.1). Its meta-schema closes a component with `unevaluatedProperties: false`, so a `dataSource` property on the field would make the document non-conformant, and `settings` is the one object the specification declares `additionalProperties: true` and describes as global form configuration. The cost is stated rather than hidden: the binding is not local to the field it binds, which departs from JFSS's own component-driven philosophy. Making it local means JFSS v3.0.0, which is a phase-scale decision rather than a sprint item.

The binding is on the component's `id` rather than its `key` because JFSS §4.1 makes `id` unique per component *instance*, while a `key` inside a datagrid row template lives in the row's scope and two components in one document may legitimately share one.

**Both directions are refused at save**, not at render (`rad::domain::jfss`): a binding naming no component, a component of `type: "lookup"` nothing binds, a source outside the allow-list, an ambiguous `id`, and a bound component that also carries a static `options` array. A definition is written once and rendered thousands of times, and at render the failure is a chooser that opens empty — indistinguishable from master data holding nothing.

**Sources are code, not configuration.** `supplier`, `customer`, `employee` and `facility`, as an allow-list in `rad::domain::lookup::LookupSource`. A source decides which query runs *and* which permission the caller must hold, and taking either from `rad_lookup_definitions` would put an identifier into SQL from data and make a misconfigured row a permission bypass ([Database Schema](02.%20Database%20Schema.md) §5.12).

**The permission is the underlying entity's, and is required by not being checked twice.** `GET /api/v1/rad/lookups/{source}/options` calls the master-data module's service, which refuses before anything is read, so a lookup opens exactly what `GET /master-data/suppliers` and `GET /master-data/facilities` open and the two cannot drift apart. A caller without it gets **403 rather than an empty page**: an empty list is a false statement about the data that the person filling in the form cannot tell from a tenant with no suppliers yet, while refusing discloses only that a source exists — which the definition they just read already told them. The list is paged and searched server-side, and the filters that decide which records may be offered at all (an enabled party, a role it currently holds, a facility that is not archived) are the server's rather than the caller's.

### 8.2.2 Submitting a Form, and the Re-evaluation Behind It (FR-RAD-010, FR-RAD-006)

**The client's arithmetic is not trusted.** [JSON Form Schema](../schema/JSON%20Form%20Schema.md) S8.1 requires the backend to re-evaluate every `calculate` expression and **overwrite** the submitted value before persistence, and S10.2 requires the same for every `conditional` — re-deciding visibility against the complete payload and discarding the values of the components that resolve to hidden. Together they are the **Tamper-Proof Pattern**, and it is the security-critical control of Phase 4: *a submitted total the server accepted because the browser said so is not a rounding bug, it is an invoice for the wrong amount.*

`POST /api/v1/rad/forms/{id}/submissions` is where it happens. It takes a payload carrying **every** data `key` the definition declares, visible or not (S10.1), and stores a row in `rad_form_submissions` ([Database Schema](02.%20Database%20Schema.md) §5.14) whose `payload_json` is the server's own answer.

**The code is split in two, and the split is a Sprint 9 dependency rather than a preference.** `rad::service::evaluation` is pure — a definition and a payload in, a secure payload or an S10.3 error envelope out, with no database handle, no permission check and no `AppState`. `rad::service::submission` is what adds the permission, the tenant scope, the published check and the write. Sprint 9's [#168](https://github.com/sujanto-gaws/kelir/issues/168) calls the first from inside the transaction that takes a document's number, and that is only possible if it drags no submission row along with it.

**The order of operations**, which is JFSS §9.2's:

1. **Project the payload onto the definition.** Every declared `key` is present — a missing one resolves to `Value::Null`, which is S12.4 as errata **E-1** restates it for `serde_json` — and every *un*declared key is dropped rather than stored.
2. **Overwrite `sequenceKey`** with the row's 1-based position. §10.2 puts sequencing beside calculation under *"Backend overwrites to prevent tampering"*: a line-item table that reads 1, 3, 4 after a deletion is what the property exists to prevent, and a client does not get to decide it.
3. **Re-evaluate every `calculate`** by the **declared** `calculateMode` (S4.2.3, S8.1.1) — `derived` overwrites unconditionally, `generated` resolves only where the stored value is null. **In the order §9.2 asks for**, taken from the dependency graph §8.2.3 builds, so a chain declared backwards settles in one pass rather than in as many passes as it is long. A scope with no such order is cyclic, which S12.2 makes invalid; it is refused with every field on the loop named rather than half-persisted, and §8.2.3 is why that refusal is the second line rather than the first.
4. **Re-evaluate every `conditional`** against that payload and discard the values of the components that resolve to hidden. A hidden `key` being *present* is expected and never by itself a rejection (S10.1.1).
5. **Run `validation` and the `rules`** scoped `server` or `both`. A rule name outside the Validation Rule Registry is a refusal and never a skipped arm (S8.1.1) — *a rule that fails open is a rule that is not there, reported as a rule that passed.*

**Steps 3 and 4 are in that order and it matters.** A `conditional` keyed on a computed field would otherwise be decided from the number the *client* sent, so tampering with a total would move which fields get persisted. Recorded as decision **D-27**.

**A failure is a refusal, never a partial write.** The response is a 4xx carrying the S10.3 envelope, whose `path` is a dot-notation path — `line_items.2.quantity` addresses a row, which is why the field is named `path` and not `key`. This is where a division by zero lands (**D-24**): blank on the screen while the form is being filled in, a named refusal when it is submitted.

**And the browser is told what was stored.** The response carries the payload read back from the row, and the page compares it against what it sent: where the two differ it says which fields moved and to what. Both sides run one engine compiled for two runtimes (**D-10**) and `parity/forms.json` holds them to the same answers over whole submissions, so that banner should never appear — which is exactly why it is on the screen rather than in a log. *A form that changes your number without saying so is its own defect.*

### 8.2.3 The Rule Engine Behind It (FR-RAD-006)

**An evaluator answers *what does this expression compute*; an engine answers which expressions run, in what order, and what a failure means.** `rad::evaluator` has been the first half since Sprint 7 (**D-10**, [ADR-0008](../architectures/adr/0008.%20One%20JSON%20Logic%20Engine%20on%20Both%20Sides.md)). `rad::domain::engine` is the second, built in Sprint 14 under **D-67** and recorded as [ADR-0035](../architectures/adr/0035.%20Rules%20Are%20Resolved%20Before%20a%20Form%20Is%20Published.md).

**The catalogue resolves a definition's rules against both registries, on one walk.** Every `data` component in a scope is visited once: its `rules[].rule` names are resolved against the [Validation Rule Registry](../schema/JFSS%20Validation%20Rule%20Registry.md) and its `calculate` and `conditional.logic` operators against the [Calculation Rule Registry](../schema/JFSS%20Calculation%20Rule%20Registry.md) and the `conditional` floor. One walk rather than two because a second traversal carries its own idea of JFSS §4.3.1's three container shapes, and two traversals that must agree are two places to forget one.

**The graph is built from every `{"var": ...}` reference in *both* rule properties**, which is S12.2's requirement rather than a choice. A repeater's row template is its own graph: a `key` inside one addresses a property of the row (§4.3.1), so `line_total` reading `quantity` means the same row's quantity and a top-level field of that name is a different field. An iterator's body — the second argument of `map`, `filter`, `reduce`, `all`, `some`, `none` — is read against an item and not against the enclosing scope, so it contributes no edge there; treating it as one would invent a dependency and, with it, a cycle the definition does not have.

**One asymmetry between the two properties is deliberate.** A `calculate` referencing its own key is a cycle, because S8.1 computes the field from the record. A `conditional.logic` referencing its own key is not, because S10.2 decides visibility against the complete payload with the calculations already applied (§8.2.2, **D-27**) — `{"!!": {"var": "notes"}}` is an ordinary conditional and refusing it would refuse working definitions.

**The verdicts land at two moments, and the second one is the door that only opens once.** `validate_definition` refuses the *write*, so an unregistered rule name (`RULE_NOT_REGISTERED`) or a cycle (`CALCULATION_CYCLE`, naming every field on the loop) never reaches storage. `publish_form` re-runs the same function against the **stored** definition before flipping the status, because a draft written by an older build keeps whatever it was stored with and a published revision is immutable — documents pin it (§8.4, [ADR-0027](../architectures/adr/0027.%20A%20Document%20Pins%20the%20Form%20Revision%20It%20Was%20Filled%20Against.md)), so a definition that goes live wrong can never be corrected in place. Workflow definitions have been checked at both moments since Sprint 10 (§8.5); this brings forms into line with them.

**The submit path is the second line, not the first.** It asks the same graph for the same order, and a cycle there means a form published before this gate existed: it answers 422 with the S10.3 envelope naming the fields, never a 500. A rule name outside the registry still refuses a submission (**D-28**, [ADR-0016](../architectures/adr/0016.%20An%20Unenforceable%20Rule%20Refuses%20Rather%20Than%20Passes.md)) — *a rule that fails open is a rule that is not there, reported as a rule that passed* — but the person it now refuses is the author, at the moment they can fix it.

**What S12.2 asks for and this does not yet do** is *surface* the cycle in an authoring tool. The API names it; the builder UI that would draw it is FR-RAD-004/008, [#341](https://github.com/sujanto-gaws/kelir/issues/341).

## 8.4 The Document Lifecycle (FR-DOC-001..007)

A **document** is what a document type produces. It is created from the type, pins the exact form revision the type binds at that moment, holds the data somebody fills in, takes a number when it is submitted, and then moves through statuses until it is finished.

```text
Created from a type          DRAFT      form_id pinned, document_ref allocated
        ↓
Edited                       DRAFT      re-evaluated on every write (§8.2.2)
        ↓
Submitted                    SUBMITTED  number + status + payload, one transaction
        ↓                               …and the workflow, if its type binds one (§8.5)
Decided                      IN_REVIEW → APPROVED | REJECTED | RETURNED
        ↓                               by a person, or by an approval (§8.5.2)
Finished                     COMPLETED  or CANCELLED at any point before it
```

**Three status notions exist in this system, and only one of them is authoritative for any given question.**

- **`record_status`** is the governance lifecycle of a *master-data record* — a supplier is drafted, approved, made active, suspended (FR-MDM-007). It is a property of a record about a thing that keeps existing.
- **`workflow_instances.current_state`** is where a *process* is, and it is the single source of truth for that (§8.5). It is a state of one definition, so it means whatever that workflow says it means.
- **`documents.status`** is where an *event* is in a life that happens once and ends — and for a document with a live process it is a **projection** of the instance's state rather than a parallel record.

`ARCHIVED` is in the column and reachable from nothing until FR-DOC-010; the legality table says so rather than leaving a reader to grep for the string. **`PENDING_APPROVAL` became reachable in Phase 5** and is reachable only through a workflow — no manual transition enters it, which is what makes it a state that always means "something is deciding this".

### 8.4.1 The Submit Transaction (FR-DOC-003, FR-DOC-004)

The order matters and is not the obvious one:

```text
1. document:submit                     before anything is read
2. read the document FOR UPDATE        not a draft → refused
3. re-evaluate the payload             the full pipeline; required now applies
4. allocate the number                 per the rule's own gap policy
5. write number + status + payload     conditional on it still being a draft
6. append the status-history row
7. start the workflow, if one is bound in the same transaction (§8.5)
8. commit, then audit as a SUBMIT
```

**Step 3 before step 4 is the whole of it.** Numbering first burns a number on every refused submission, and on a gapless rule it is worse than that: the counter is held from the allocation to the commit, so a slow re-evaluation serialises every concurrent submit of that type behind a document that is about to be refused. The order also buys more than the gap policy promised — a submission refused by the re-evaluation burns no number on *either* policy, because it never reaches the allocator.

**Everything from step 2 to step 7 runs on one connection.** A submit that took a second connection while holding a transaction on the first deadlocks a pool below the concurrency the pool can serve. That is exactly what a Sprint 7 defect did here, and it survived because nothing called the allocator's dispatcher under load.

### 8.4.2 What a Document Hands Back About Its Linked Entity (FR-DOC-011)

Reading a document returns `entityType` and `entityId` and nothing about the record they name. Resolving them is a sub-resource that requires the entity's **own** read permission — enforced by calling the master-data service rather than by checking a string, so a document cannot open what the master-data surface does not. It is the same answer §8.2.1 gives for lookup fields, and for the same reason.

Retiring the linked record leaves the document readable and its link unchanged; the resolution answers 404 about the *entity*. Cascading or nulling the link would rewrite a historical record because a supplier was retired years later.

## 8.5 The Workflow Engine (FR-WF-001..004, 006, 007, 013, 014)

A **workflow definition** is a finite state machine written in [JWSS](../schema/JSON%20Workflow%20Schema.md): states, the transitions between them, who may act on each, and — crucially — what each state *means for the document underneath it*. Publishing one freezes it and writes the projections a running instance is constrained by.

```text
Definition authored          DRAFT      validated on save: shape, operators, S1–S10
        ↓
Published                    ACTIVE     immutable; states and transitions projected
        ↓
Bound to a document type                checked: exists, and is ACTIVE
        ↓
A document of that type is submitted
        ↓
Instance started             RUNNING    pins the revision; variables computed
        ↓
State entered                           its task is generated, in the same transaction
        ↓
Task decided                 APPROVE | REJECT
        ↓
Instance moved                          the next state's task, or the end
        ↓
Final state                  COMPLETED  outcome recorded; the document's status follows
```

**A definition that cannot terminate is refused at save, not discovered at run time.** JWSS §8's structural rules — reachability, dead ends, duplicate triples, a transition out of a final state, an ambiguous fallback — are enforced when the definition is written and again at publish. A workflow that can deadlock is a workflow that will, and the failure would land on whoever was waiting for an approval that could not move.

**Kelir resolves four of JWSS's six assignee types and refuses the other two at save**, naming what would have to exist first: `MANAGER_OF_OWNER` needs a user-to-manager relation this schema does not have (FR-ORG-002 is unbuilt), and `EXPRESSION` needs a directory context §6.1's condition context does not carry. JWSS §5.3 records the narrowing.

**`guards` and `actions` are stored and not executed** as of `v0.5.0`: there is no hook chain to merge them into (architectures/01 §12.4.2). They are accepted rather than refused so definitions authored now do not have to be rewritten, and the engine says so in one place — a stored handler must not read as evidence that it runs.

**Sequential approval only.** An instance is in one state, a JWSS state declares at most one `task`, so an instance has at most one open task — held by a partial unique index rather than by convention. FR-WF-016 (parallel approval) is deferred by SRS §4.8 itself, and when it is scheduled that index is what it has to argue with.

### 8.5.1 One Place a Process Moves

Starting an instance, firing a transition, generating the next state's task and projecting the document's status are **one code path**, called from the submit and from a decision. An engine is the shape a system most easily grows two of, and two engines would be two answers to "what happens when this is approved".

Every function on that path takes a transaction and none takes the pool: a submit already holds a numbering counter, and a second pooled connection taken inside a transaction deadlocks at the concurrency the pool can serve (§8.4.1's last paragraph, and **D-35**). The lock ordering is **instance first, then task**, on every path — two paths taking them in opposite orders is a deadlock at exactly the concurrency the feature exists for.

### 8.5.2 The Document–Workflow Seam (FR-DOC-012, FR-WF-013)

> A workflow transition sets the document's status. **Setting the document's status does not move the workflow.**

The map from state to status is `mapsToDocumentStatus` **in the definition**, never in code: a new workflow says what its own states mean for a document, and adding one needs no backend change. The projection is written in the transition's own transaction, so a document whose status disagrees with the process deciding it is not a state the system can reach.

Enforcing the one-way rule costs the manual transition route something, and the cost is paid deliberately: `PUT /documents/{id}/status` **refuses a document that has a live instance**, naming the instance. Letting it through would produce the disagreement this seam exists to prevent, silently, on the screen a person is most likely to trust. A manual override would be a separate, audited action; nothing has asked for one, and the refusal is what makes the need visible if anything does.

A document links to **at most one live instance**, held by a partial unique index as well as by the service — so the refusal is true under concurrency and not only in the ordinary case.

### 8.5.3 The Task Inbox (FR-TASK-001, 002, 003)

> A caller sees a task when it is in their tenant **and** either they are its assignee, **or** it has no assignee and it is offered to a role they currently hold.

Enforced as a predicate in the query, not in a handler: a rule in a handler is one the next caller of the repository can step around. The roles are read from `user_roles` rather than from the access token's claim — a token is a snapshot from sign-in, and an inbox built from a stale claim offers somebody tasks the API will then refuse them, which reads as a broken product while being a leak.

**A task assigned to somebody and a task offered to a role are different situations**, and the payload says which rather than leaving a client to derive it from a null assignee. A role task is claimed by a compare-and-swap: two people claiming at once produce one winner and one 409.

# 11. Security Design

## 11.1 Authentication

```text
Username/email + password
Argon2 password hashing
JWT access token or secure session
Refresh token or session renewal
Logout and token invalidation
Rate limiting on authentication endpoints (NFR-SEC-008)
Self-service password reset over an emailed single-use token (FR-AUTH-006)
```

**The reset flow answers identically whatever it is given.** An unknown
identifier, a suspended account, a resend still inside its cooldown and a mail
server that is down all produce the same 202, because any difference between
them tells an unauthenticated caller whether an account exists. The throttle is
therefore per account and applied silently rather than reported, and the
endpoint is not metered by the rate limiter that answers 429 — a 429 would be
the difference the rest of the design removes. Redeeming a token *is* metered:
a wrong token is a 4xx, so attempts are countable there without leaking
anything.

**Identical is not indistinguishable, and the difference is timing** ([#202](https://github.com/sujanto-gaws/kelir/issues/202),
decision **D-31**). The status and the body are the same for every input; the
*work* is not, and until 2026-08-27 the response waited for a complete SMTP
transaction, so a known account answered in a p50 of 90ms against an unknown
identifier's 9.8ms — an enumeration oracle on the one endpoint deliberately
left off the rate limiter. The send is now handed to the runtime and the
measurement is 26.4ms against 10.5ms: **narrowed, not closed.** What is
guaranteed is that no caller's measurement includes a mail server, which is
the part that grows without bound when a relay is slow. Closing the residual
means padding the fast path to a fixed budget — a different control, with a
denial-of-service surface of its own, and D-31 declines it here.

See [Database Schema](02.%20Database%20Schema.md) §3.9 for how the token itself
is stored.

## 11.2 Authorization

```

Permission naming rule: permissions follow `module:resource:action`; the `resource` segment may be omitted when a module manages a single resource (e.g. `document:create`), and is required when a module manages multiple resources (e.g. `master-data:party:update`).

```

JFSS validation failures populate `details` with `{path, rule, code, message}` entries per JSON Form Schema S10.3. JSON payload fields are `camelCase` (naming convention §5).

**Every refusal under `/api/v1` uses this shape, including the ones raised before a handler runs.** A malformed body, a body carrying an unknown field, a query parameter that will not parse, and a path segment that will not parse are all rejected by an extractor rather than by module code, and an extractor that rejects with its own reply answers outside the envelope — which is the one shape a client written against `error.code` cannot read. `kelir-backend/src/extract.rs` therefore supplies `JsonBody`, `QueryParams` and `PathParam` in place of `axum::Json`, `axum::extract::Query` and `axum::extract::Path`; the three are drop-in and their `utoipa` annotations are unchanged. Handlers use no other extractor for request data. Statuses are unchanged by the wrapping: a bad query parameter is a 422 naming the parameter, a bad path segment stays a 400.

# 13. Deployment Design

## 13.1 Development Deployment

```text
Docker Compose
├── frontend
├── backend
├── postgres
├── mailpit
├── minio
├── minio-init    (one shot: creates the bucket, then exits — #244)
└── clamav        (added in Phase 6, when attachment scanning needs it)
```

**`minio-init` exists because the application does not create its own bucket.**
The backend is given credentials that put and get objects in a bucket somebody
else provisioned; a process that can create buckets can create the one an
attacker names. CI's backend job does the same thing with a one-shot `mc` step,
and [`deploy/env/.env.example`](../../deploy/env/.env.example) says so where an
operator will read it. Storage was in this stack from Sprint 0 and used by
nothing until [#244](https://github.com/sujanto-gaws/kelir/issues/244).

The scanner is ClamAV, decided 2026-08-11 as [Product Backlog](../../projects/planning/02.%20Product%20Backlog.md) decision **D-4**. **Sized 2026-08-31**, which D-4 did not do: 25 MiB scans over INSTREAM in **169 ms** at ~156 MiB/s, `clamd` holds **955 MB resident** — almost all of it the signature set — and starts in ~20 s because the image ships its database. **Concurrency buys nothing**: aggregate throughput is flat from one parallel scan to sixteen, so one instance and a worker concurrency of 2–4 is the whole sizing. The 1 GB is the number this stack has to find, and it is per instance rather than per load. Method and numbers on [#246](https://github.com/sujanto-gaws/kelir/issues/246).

**Two things the scanner's own defaults make easy to get wrong.** `clamdscan` against a shared filesystem falls back to a path scan and answers `OK` where the wire answers `INSTREAM size limit exceeded. ERROR`, so the worker and its tests must speak INSTREAM. And `clamd.conf.sample` documents `StreamMaxLength 25M` — exactly `KELIR_STORAGE_MAX_UPLOAD_BYTES` — so **`StreamMaxLength` must be set strictly above the upload limit**, or every maximum-size upload is recorded `FAILED` and becomes permanently undownloadable. Scanning is asynchronous and never inline in a request handler ([coding standard](../standards/01.%20Coding%20Standard.md) §2.4): upload sets `virus_scan_status = 'PENDING'`, a worker scans and updates it via the outbox, and download is blocked until `'CLEAN'` ([Database Schema](02.%20Database%20Schema.md) §8.2 — §8.1 is the category table, and the pointer named it until #244 built both).

# 16. Risks and Mitigation

| Risk | Mitigation |
|---|---|
| Workflow engine becomes too complex | Start with lightweight state-transition engine before BPMN |
| Multi-database compatibility complexity | Use PostgreSQL first, MariaDB later with compatibility layer |
| Dynamic plugins introduce security risk | Start with configuration-based and compiled-in plugins |
| RAD metadata becomes unstable | Version metadata and validate schema strictly (JFSS meta-schema is normative) |
| Frontend dynamic rendering complexity | Build reusable FormRenderer and ListRenderer incrementally |
| Audit log grows large | Partition/archive audit tables and define retention policy |
| File storage grows | Use object storage and metadata tracking |
| Integration failures | Use outbox, retry, dead-letter, and integration logs |
| Permission complexity | Start with RBAC before ABAC |
