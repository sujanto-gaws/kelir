# Kelir Database Schema

**Status:** Draft · **Last updated:** 2026-09-01

This document is the column-level database schema for the whole Kelir platform. It expands the table groups listed in the [System Design Document](01.%20System%20Design%20Document.md) §6 into concrete DDL, organized by migration file. Naming follows the [naming convention](../standards/02.%20Naming%20Convention.md) §4; where an older document sketches different columns for the same table, this document wins.

DDL is written for **PostgreSQL** (the primary target). MariaDB portability notes are in §1.6.

# 1. Schema Conventions

## 1.1 Identifiers

- Surrogate primary keys are **UUID** (v7, time-ordered), generated by the application. Business identifiers (`DOC-2026-000123`, `PR-2026-000123`) are separate columns and are never used as foreign keys (naming convention §8).
- Every foreign key is `<referenced_entity_singular>_id`; role-prefixed when the role differs from the entity (`owner_user_id`, `manager_party_id`).

## 1.2 Base Columns

Every table carries these columns unless its section states otherwise. In the DDL below they are abbreviated as `-- BASE`:

```sql
id              UUID        PRIMARY KEY,
tenant_id       UUID        NOT NULL REFERENCES tenants (id),
created_by      UUID        REFERENCES users (id),
created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
updated_by      UUID        REFERENCES users (id),
updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
deleted_at      TIMESTAMPTZ
```

Exceptions:

- `tenants` has no `tenant_id`.
- Append-only tables (`audit_events`, `activity_events`, `document_hook_executions`, all `*_logs`) drop `updated_by` / `updated_at` / `deleted_at` — rows are never updated or soft-deleted.
- `created_by` is nullable because system-generated rows (workers, migrations, seed data) have no acting user.

Soft delete: `deleted_at IS NULL` means live. Unique constraints that must survive soft delete are partial indexes (`WHERE deleted_at IS NULL`).

## 1.3 Types

| Concern | Type |
|---|---|
| Timestamps | `TIMESTAMPTZ` (UTC), columns end `_at` |
| Dates | `DATE`, columns end `_date` |
| Booleans | `BOOLEAN NOT NULL DEFAULT`, columns start `is_` / `has_` / `allow_` |
| Enum values | `VARCHAR(40)` + `CHECK`, values `SCREAMING_SNAKE_CASE`; no native `ENUM` types (MariaDB portability, cheap value additions) |
| JSON | `JSONB`, columns end `_json` |
| Money / amounts | `NUMERIC(18,2)` |
| Bounded strings | `VARCHAR(n)` from the standard set below |
| Unbounded prose | `TEXT` — descriptions, reasons, comment bodies, messages |

### 1.3.1 String Lengths

Bounded columns take a length from this set. It is deliberately short: picking from five values keeps a schema consistent, where per-column judgement produces `VARCHAR(45)` beside `VARCHAR(50)` for the same concept.

| Length | For | Examples |
|---|---|---|
| `VARCHAR(40)` | Enum values and short status codes | `status`, `action`, `scope`, `source` |
| `VARCHAR(64)` | Business and system codes, usernames | `tenant_code`, `role_code`, `permission_code`, `username`, `document_number` |
| `VARCHAR(200)` | Human-readable names and titles | `name`, `display_name`, `subject` |
| `VARCHAR(320)` | Email addresses — the RFC 5321 maximum | `email` |
| `VARCHAR(255)` | Opaque tokens, hashes and external references | `password_hash`, `token_hash`, `current_hash`, `external_id` |
| `VARCHAR(2048)` | URLs and paths | `storage_path`, `callback_url` |
| `TEXT` | Anything genuinely unbounded | `description`, `reason`, `body`, `message` |

**Why a length at all.** In PostgreSQL `VARCHAR(n)` and `TEXT` are the same type — same storage, same performance, the length is simply a constraint. The bound is not for the database's benefit; it is so the limit is visible in the DDL rather than living in an unwritten rule.

Two concrete reasons it matters here:

- **Indexed columns fail unpredictably without one.** A btree entry cannot exceed roughly 8 KB, and index entries are compressed but never TOASTed — so an oversized value is accepted or rejected depending on how compressible it happens to be. Measured on `users.username`: a 10,000-character repetitive value inserted fine, while a 9,600-character random one failed with `index row requires 9632 bytes, maximum size is 8191`. That is a 500 at insert time rather than a validation message, and it passes testing with repetitive fixtures.
- **MariaDB cannot index `TEXT` without a prefix length.** Every unique index on a code column would become `username(191)`, which stops enforcing real uniqueness — two values sharing a long prefix would collide. `VARCHAR(n)` indexes normally there (§1.6).

**Every request field that fills a bounded column carries the same bound in the domain layer.** A field that does not reaches PostgreSQL, which answers `value too long for type character varying(n)` — a `sqlx` error, an `INTERNAL_ERROR`, and a 500 where the contract promises a 422 naming the field. That is #109, found on `contactMechanisms[].purposeTypeId` against `mdm_party_contact_mechs.purpose_type`.

The bound is therefore part of the contract, not a defensive check, and the constants mirror this table one-for-one:

| Column width | Constant (`modules::master_data::domain`) |
|---|---|
| `VARCHAR(40)` | `MAX_VOCABULARY_LENGTH` |
| `VARCHAR(64)` | `MAX_CODE_LENGTH` (`MAX_FACILITY_CODE_LENGTH` for facility codes) |
| `VARCHAR(200)` | `MAX_NAME_LENGTH` |
| `VARCHAR(255)` | `MAX_EXTERNAL_ID_LENGTH` |

`mdm_parties.party_code` is the one column bounded tighter than its type: `MAX_PARTY_CODE_LENGTH` is 60 against a `VARCHAR(64)`, and `ck_mdm_parties_party_code_len` holds that in the database so a path that skipped validation still cannot store a value the aggregate would reject.

Three kinds of field are deliberately outside the rule, and a reader auditing it should expect to find them unbounded: fields written to `TEXT` columns, which have no width to exceed; fields typed as an enum in Rust against a `CHECK` in the DDL, where an unrecognised value never deserializes; and business codes that are **resolved to a surrogate key** before anything is written, where an over-long value matches no row and is already a 422. The sweep's full boundary is recorded against the two tests that assert it — `every_string_field_that_reaches_a_varchar_column_is_bounded` in `domain/party_validation.rs` and `every_profile_field_that_reaches_a_varchar_column_is_bounded` in `domain/role.rs`.

## 1.4 Constraints and Indexes

- Indexes `idx_<table>_<columns>`, unique constraints `uq_<table>_<columns>`, foreign keys `fk_<table>_<column>` (naming convention §4.3).
- Every table gets `idx_<table>_tenant_id` implicitly via its leading composite indexes; only additional indexes are listed per table.
- All `REFERENCES` default to `ON DELETE RESTRICT`. Cascade is opt-in and stated explicitly where used (pure child rows such as form sections).

## 1.5 Multi-Tenancy

Single database, shared schema, `tenant_id` discriminator on every row. All application queries filter by `tenant_id`; PostgreSQL row-level security is a later hardening option (SDD §3.3). Global rows (platform-level seed data such as core role types) use the reserved system tenant.

**Which rows are global, settled 2026-08-25 by decision D-18.** The `permissions` catalogue is global — a permission is an identifier the code checks, so it is seeded in the system tenant and read across every tenant. **Roles are not.** `uq_roles_tenant_id_role_code` is per tenant, so each tenant has its own `ROLE-ADMIN` and they are different rows; the system tenant's copy is the one `0002_identity.sql` seeds, and a tenant created through FR-ORG-001 is provisioned with its own. That had been ambiguous for five sprints — every identity read filtered `tenant_id` while `roles_of_user` joined without it — and [#65](https://github.com/sujanto-gaws/kelir/issues/65) is where the ambiguity was written down. `0017_tenant_administration.sql` makes the answer structural rather than conventional: a `user_roles` or `role_permissions` row naming another tenant's role is refused by a foreign key.

**A tenant is not a row inside a tenant.** `tenants` has no `tenant_id` (§1.2), so nothing about `tenant_id` scoping can say who may administer one. What does is a rule in `organization::service`: tenant administration is performed only from the deployment's *default* tenant (`KELIR_DEFAULT_TENANT_CODE`), and a tenant provisioned through the API is not granted the `organization:tenant:*` family.

## 1.6 MariaDB Portability

If the optional MariaDB target is enabled: `UUID` → `CHAR(36)`, `TIMESTAMPTZ` → `DATETIME(6)` (UTC by convention), `JSONB` → `JSON`, `TEXT CHECK` enums unchanged, GIN/partial indexes replaced by generated columns + plain indexes. Migrations are maintained PostgreSQL-first; the MariaDB variants are generated and tested separately (architecture document 01 §9.2).

# 2. Core — `0001_core.sql`

## 2.1 tenants

```sql
CREATE TABLE tenants (
    id              UUID        PRIMARY KEY,
    tenant_code     VARCHAR(64)        NOT NULL,           -- TNT-001
    name            VARCHAR(200)        NOT NULL,
    status          VARCHAR(40)        NOT NULL DEFAULT 'ACTIVE'
                    CHECK (status IN ('ACTIVE', 'SUSPENDED', 'INACTIVE')),
    settings_json   JSONB       NOT NULL DEFAULT '{}',
    created_by      UUID,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_by      UUID,
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at      TIMESTAMPTZ,
    CONSTRAINT uq_tenants_tenant_code UNIQUE (tenant_code)
);
```

**Administered through the API since 2026-08-25** (FR-ORG-001, [#27](https://github.com/sujanto-gaws/kelir/issues/27), decision **D-18**), which supersedes **D-7**'s "no surface". Four properties of that surface are schema-visible:

- **`tenant_code` is not updatable.** It is the handle a caller signs in with in multi-tenant mode, and no session carries it — the JWT carries `tenant_id` — so changing it would strand a tenant's users with nothing failing loudly enough to notice.
- **`status` means what it says.** `resolve_for_sign_in` refuses a tenant that is not `ACTIVE`, and moving one out of `ACTIVE` also revokes its `refresh_tokens`, so sessions end rather than merely failing to renew.
- **Deletion is soft.** A soft-deleted tenant resolves to nothing at sign-in, which is what makes its data unreachable; hard-deleting it would take the audit trail with it.
- **`settings_json` is not part of that surface.** It is per-tenant configuration (FR-CFG) with its own eventual owner; publishing it on the tenant record would make FR-ORG-001 the thing that edits it.

## 2.2 system_settings

Platform-level and per-tenant configuration that is not RAD metadata (feature toggles, defaults, limits).

```sql
CREATE TABLE system_settings (
    -- BASE
    setting_key     TEXT        NOT NULL,
    setting_value   JSONB       NOT NULL,
    is_secret       BOOLEAN     NOT NULL DEFAULT false,
    description     TEXT
);
CREATE UNIQUE INDEX uq_system_settings_tenant_id_setting_key
    ON system_settings (tenant_id, setting_key) WHERE deleted_at IS NULL;
```

Secret values are stored as references into the secret store, never plaintext (same rule as `integration_credentials`, §12.5).

# 3. Identity and Organization — `0002_identity.sql`

## 3.1 departments

```sql
CREATE TABLE departments (
    -- BASE
    department_code     VARCHAR(64)    NOT NULL,           -- DEPT-PROC
    name                VARCHAR(200)    NOT NULL,
    parent_department_id UUID   REFERENCES departments (id),
    manager_party_id    UUID,                       -- FK to mdm_parties added in 0008
    status              VARCHAR(40)    NOT NULL DEFAULT 'ACTIVE'
                        CHECK (status IN ('ACTIVE', 'INACTIVE'))
);
CREATE UNIQUE INDEX uq_departments_tenant_id_department_code
    ON departments (tenant_id, department_code) WHERE deleted_at IS NULL;
CREATE INDEX idx_departments_tenant_id_parent_department_id
    ON departments (tenant_id, parent_department_id);
```

> **A surface exists for this table as of 2026-08-25 (#28), and until then none did.** `departments` shipped with `0002_identity.sql` in Phase 2, and `master_data` has validated an employee profile's `department_id` against it since Sprint 5 — a consumer depending on rows nothing could create. FR-ORG-002's endpoints live under `/api/v1/organization/departments`; FR-IDM-008 keeps only the edge `users.department_id`, which the identity surface writes (decision **D-8**).
>
> **`parent_department_id` is guarded in the service, not by a constraint.** A `CHECK` can express *not itself*; only a depth-bounded ancestor walk, inside the writing transaction and under a tenant-wide advisory lock, can express *not one of its own descendants*. That is the shape `mdm_facilities` needed three issues to get right (#133, #134, #137), and the department surface is written against all three.
>
> **No new permissions were seeded.** `0002_identity.sql` already carried `organization:department:read` and `organization:department:manage`, and nothing had ever checked them; the surface uses those rather than adding a `create`/`update`/`delete` trio that would leave the two originals orphaned.

## 3.2 users

```sql

    password_hash       VARCHAR(255)    NOT NULL,           -- Argon2id PHC string

    department_id       UUID    REFERENCES departments (id),

                        CHECK (status IN ('ACTIVE', 'INACTIVE', 'LOCKED', 'PENDING_ACTIVATION')),
    last_login_at       TIMESTAMPTZ,
    failed_login_count  INTEGER NOT NULL DEFAULT 0,
    locked_until        TIMESTAMPTZ,                -- added by 0007; failed-login lockout expiry
    must_change_password BOOLEAN NOT NULL DEFAULT false
);
CREATE UNIQUE INDEX uq_users_tenant_id_username
    ON users (tenant_id, username) WHERE deleted_at IS NULL;
CREATE UNIQUE INDEX uq_users_tenant_id_email
    ON users (tenant_id, email) WHERE deleted_at IS NULL;
```

`locked_until` and `status` are both locks and are deliberately separate. `status = 'LOCKED'` is an administrator's decision and holds until an administrator reverses it; `locked_until` is the automatic failed-login lockout of NFR-SEC-008, which expires on its own — `NULL`, or a time already past, means no lockout. Nothing sweeps the column: every check compares it against `now()`, so a lockout ends because time passed rather than because a job ran. Setting the status to `ACTIVE` clears it, which is the administrative unlock path; a successful sign-in and a password change clear it too.

## 3.8 delegations

Task/approval delegation windows (identity module).

> **Written and read since [#184](https://github.com/sujanto-gaws/kelir/issues/184)**, which is what **D-13** unscheduled [#24](https://github.com/sujanto-gaws/kelir/issues/24) over and what **D-17** scheduled its consumer into Sprint 11 for. Sprint 10 built the assignment resolver those windows apply *after* (JWSS §5.1) and left the seam named in `workflow::service::assignment`, deliberately without a no-op function; Sprint 11 put `redirect` in it. The writer is `identity::delegation_service`; the reader is `identity::delegation_repository::active_delegate_of`, called from that resolver.
>
> **`scope` has three values and the API accepts two.** `ALL` and `DOCUMENT_TYPE` are honoured. **`ROLE` is refused at creation**, in its own words: a window redirects a task that resolves to *a person*, and a task offered to a role has no assignee to redirect — it is unclaimed, and every other holder of the role is still being offered it. A `ROLE`-scoped row could therefore never match anything the resolver looks at, so accepting one would store a window that silently routes nothing. The value stays in the `CHECK` with `STARTED`'s standing on `workflow_instances` (§7.4): it was specified, and the product does not produce it.
>
> **`is_active` is how a window is ended, and `deleted_at` is not.** A window that covered somebody's leave is part of how a month of approvals were routed, so `DELETE /api/v1/identity/delegations/{id}` sets `is_active = false` and the row stays in the list that explains them. What ending it has to do is stop it routing, which `active_delegate_of` reads in the same predicate as the dates — and a window whose `ends_at` has simply passed stops the same way, on the next transition rather than on a sweep (#184 AC6).
>
> **The routing predicate joins `users`**, so a window pointing at an account that has been deleted or deactivated matches nothing and work falls back to the delegator. Sending an approval to an account nobody can sign in to is worse than not delegating it, and it would be invisible: the task would look assigned.

```sql
CREATE TABLE delegations (
    -- BASE
    delegator_user_id   UUID    NOT NULL REFERENCES users (id),
    delegate_user_id    UUID    NOT NULL REFERENCES users (id),
    scope               VARCHAR(40)    NOT NULL DEFAULT 'ALL'
                        CHECK (scope IN ('ALL', 'DOCUMENT_TYPE', 'ROLE')),
    document_type_id    UUID,                       -- FK added by the document migration,
                                                -- required when scope = DOCUMENT_TYPE
    role_id             UUID    REFERENCES roles (id),  -- required when scope = ROLE
    starts_at           TIMESTAMPTZ NOT NULL,
    ends_at             TIMESTAMPTZ NOT NULL,
    reason              TEXT,
    is_active           BOOLEAN NOT NULL DEFAULT true,
    CONSTRAINT ck_delegations_window CHECK (ends_at > starts_at),
    CONSTRAINT ck_delegations_not_self CHECK (delegate_user_id <> delegator_user_id)
);
CREATE INDEX idx_delegations_tenant_id_delegator_user_id
    ON delegations (tenant_id, delegator_user_id, starts_at, ends_at);
```

## 3.9 password_reset_tokens

Self-service password reset (FR-AUTH-006). Deliberately not part of `0002_identity.sql` — the table arrived with `0006` in Sprint 4, which is also where §14 deviation #14 records it. Shaped like `refresh_tokens` (§3.3): a digest of the opaque token is stored, never the token itself, and the row records its own consumption rather than being deleted so a redeemed or expired token cannot be replayed.

> **Sprint 4 shipped this table and not the flow that uses it; Sprint 7 shipped the flow.** An earlier version of this section said Sprint 4 "added the reset *token* flow", and `0006`'s own header comment still says so. Neither was true when written: until [#17](https://github.com/sujanto-gaws/kelir/issues/17) landed there was no reference in `kelir-backend/src`, no prepared query in `.sqlx/`, no route and no test — only the storage. The migration comment cannot be corrected, because a merged migration is immutable and `sqlx` checksums the whole file including its comments (coding standard §2.5, §4.3). **This paragraph is the correction, and it is the only place the sequence is recorded correctly.** The flow itself — request, issue, deliver, redeem, and the rate limiting a public reset endpoint needs — arrived in Sprint 7, scheduled there by decision **D-13**.

```sql
CREATE TABLE password_reset_tokens (
    id              UUID        PRIMARY KEY,
    tenant_id       UUID        NOT NULL REFERENCES tenants (id),
    created_by      UUID,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_by      UUID,
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at      TIMESTAMPTZ,
    user_id         UUID        NOT NULL REFERENCES users (id),
    token_hash      VARCHAR(255) NOT NULL,          -- SHA-256 of the opaque reset token
    expires_at      TIMESTAMPTZ NOT NULL,
    consumed_at     TIMESTAMPTZ                     -- set once redeemed; NULL means still usable
);
CREATE UNIQUE INDEX uq_password_reset_tokens_token_hash ON password_reset_tokens (token_hash);
CREATE INDEX idx_password_reset_tokens_user_id_expires_at ON password_reset_tokens (user_id, expires_at);
```

**How the flow uses the columns.** `token_hash` is a SHA-256 digest produced by the same helper as `refresh_tokens`; the token itself exists only in the emailed link. Lookup is by digest alone, with no `tenant_id` predicate — somebody following a link out of a mailbox has no tenant context to supply, so the digest is what identifies the row and the row is what names the tenant. `expires_at` is 30 minutes out, and is checked twice: once when the digest is looked up and again in the `UPDATE` that consumes it. Either check alone would hold; both are there because the consuming statement must be safe on its own terms, since it is the one that runs under concurrency. `consumed_at` is that statement's predicate — two requests carrying the same token both reach it and exactly one affects a row, which is what makes a token single-use without a read-then-write race. The same column is the invalidation mechanism: redeeming one token stamps `consumed_at` on every other live token for that user, so a mailbox holding three "forgot password" links has none left after one is used. Nothing is deleted, so a replayed link is refused by a row that exists rather than by a row that is missing. `created_at` carries the per-account resend throttle (60 seconds), which reads issue time rather than consumption because the abuse being throttled is *sending* — a token the victim never clicked is the case that matters. Revoking the account's sessions on a successful reset happens in `refresh_tokens` (§3.3), not here.

---

> **Migration numbering has moved on from this table, twice.** `audit_events` was needed in Phase 2 for FR-AUTH-008 ("record login activity in audit log"), and sqlx applies migrations in version order, so a later phase cannot insert a lower-numbered file. It shipped as `0003_audit.sql`, which is why master data starts at `0004` rather than `0003` here (the earlier `0004_rad.sql` in this same section printed the un-shifted number — a documentation bug, now fixed: it is `0008`). Sprint 4 then inserted three more out-of-plan migrations ahead of master data — `0004_string_lengths.sql` (bounded-column lengths on `0001`–`0003`), `0005_delegation_tenant_permissions.sql`, and `0006_password_reset_tokens.sql` (new identity-module surfaces) — so every migration from master data onward is renumbered again in the table above. `0007_account_lockout.sql` then made it a third shift, adding `users.locked_until` so the lockout of NFR-SEC-008 could expire (#55). The remainder of §10 — `activity_events` and the snapshots — still lands in Phase 6, in its own migration.

# 4. Master Data — `0008_master_data.sql`

The Party model normalizes the `PartyAggregate` JSON Schema of [architectures/05](../architectures/05.%20Core%20-%20Master%20Data%20-%20Party.md). The aggregate remains the API payload shape; these tables are its storage. Free-string type ids in the aggregate (`roleTypeId`, `contactMechTypeId`, `partyIdentificationTypeId`, …) become seeded code columns here, extendable per tenant. `additionalAttributes` maps to `attributes_json` wherever the aggregate carries it.

Master data records governed by document workflows carry the lifecycle columns of [concepts/03](../concepts/03.%20Handling%20Master%20Data.md) §5, abbreviated below as `-- LIFECYCLE`:

```sql
record_status               VARCHAR(40) NOT NULL DEFAULT 'DRAFT'
                            CHECK (record_status IN ('DRAFT', 'PENDING_APPROVAL', 'ACTIVE',
                                                     'SUSPENDED', 'INACTIVE', 'ARCHIVED')),
created_by_document_id      UUID,       -- FK to documents added by the document
last_updated_by_document_id UUID        -- migration; 0008 says 0010 (§4)
```

Direct (non-workflow) edits by authorized users leave the document references null.

**Where the stored party and the aggregate differ.** The aggregate is `additionalProperties: false` and has no surrogate key, so `/master-data/parties` adds `id` to the party it returns — every route addresses a party by `{id}` ([naming convention](../standards/02.%20Naming%20Convention.md) §5), and a client that had only seen `partyId` could not build a URL. Nothing else is added: `record_status` and the two document references are storage until Phase 5 gives them a consumer. Two aggregate members have no storage here at all — see §14 deviation #16.

## 4.1 mdm_parties

```sql
CREATE TABLE mdm_parties (
    -- BASE
    party_code      VARCHAR(64)        NOT NULL,           -- aggregate partyId, 1..60 chars
    party_type      VARCHAR(40) NOT NULL
                    CHECK (party_type IN ('PERSON', 'PARTY_GROUP')),
    status          VARCHAR(40)        NOT NULL DEFAULT 'PARTY_ENABLED'
                    CHECK (status IN ('PARTY_ENABLED', 'PARTY_DISABLED')),
    external_id     VARCHAR(255),
    description     TEXT,
    attributes_json JSONB       NOT NULL DEFAULT '{}',
    -- LIFECYCLE
    CONSTRAINT ck_mdm_parties_party_code_len CHECK (char_length(party_code) BETWEEN 1 AND 60)
);
CREATE UNIQUE INDEX uq_mdm_parties_tenant_id_party_code
    ON mdm_parties (tenant_id, party_code);          -- total, not partial: see below
CREATE INDEX idx_mdm_parties_tenant_id_party_type ON mdm_parties (tenant_id, party_type);
```

**A `partyId` is never released, decided 2026-08-26 on [#107](https://github.com/sujanto-gaws/kelir/issues/107).** The index above was partial on `deleted_at IS NULL` until `0018_party_code_is_not_released.sql`, so deleting a party freed its code for another party to take. Every read path stores a *UUID* and renders it as whatever code that UUID's row currently carries, so the pair re-targeted stored references without touching them: a customer whose `billingPartyId` read `PARTY-BILL` went on reading `PARTY-BILL` after a different legal entity took the freed code, and a consumer resolving that code landed on the wrong party. `relationshipsFrom`/`relationshipsTo` (§4.8), `managerPartyId` (§4.14) and `assistantPartyId` (§4.15) have the same shape.

Three answers were available and the first was taken:

1. **Do not release the code** — one migration, and it removes the failure class rather than reporting it. A business identifier names one thing for as long as the deployment remembers that thing at all. The cost is that a mistyped code stays unusable until somebody hard-deletes the row.
2. Render a soft-deleted referent as `null` — honest about a dangling reference, but the code is still free to be re-taken, so live references still change meaning.
3. Accept it and document it — leaves every consumer of a party code responsible for knowing a code is valid only as of the moment it was read.

Two consequences a reader should expect. `POST /master-data/parties` answers `409` for a code a deleted party holds, and says so in as many words — a caller cannot see the deleted party in any list, so a bare "already in use" would read as a bug in the API. And this interacts with [#103](https://github.com/sujanto-gaws/kelir/issues/103), which releases the *profile* numbers on delete: codes and numbers should behave the same way, and #103 is where that half is decided.

`starts_at` was not carrying the stopped-then-restarted supplier, which is the reason it looked load-bearing. `soft_delete_party_role` sets `deleted_at` alongside `ends_at`, so an ended period is invisible to a partial index on `deleted_at IS NULL` and the same role can be assigned again later. **The key is not scoped to the tenant, deliberately.** `party_id` already names one tenant's party, so a tenant column would widen the key to no purpose and would leave room for one tenant's role row beside another's on the same party. That state is unreachable through the API and is now unconstructible.

The lock [#105](https://github.com/sujanto-gaws/kelir/issues/105) added to `assign_role` stays. The index catches what a future writer forgets; the lock keeps the outcome a correct 200/201 rather than the 500 a unique violation surfaces as.

## 4.16 mdm_facilities

Not party-based. Hierarchical: Building → Floor → Room (concepts/03 §4.1).

```sql
CREATE TABLE mdm_facilities (
    -- BASE
    facility_code       VARCHAR(64)    NOT NULL,
    name                VARCHAR(200)    NOT NULL,
    facility_type       VARCHAR(64),                       -- BUILDING | FLOOR | ROOM | WAREHOUSE | SITE
    parent_facility_id  UUID    REFERENCES mdm_facilities (id),
    owner_party_id      UUID    REFERENCES mdm_parties (id),
    address_json        JSONB   NOT NULL DEFAULT '{}',
    attributes_json     JSONB   NOT NULL DEFAULT '{}'
    -- LIFECYCLE
);
CREATE UNIQUE INDEX uq_mdm_facilities_tenant_id_facility_code
    ON mdm_facilities (tenant_id, facility_code) WHERE deleted_at IS NULL;
CREATE INDEX idx_mdm_facilities_tenant_id_parent ON mdm_facilities (tenant_id, parent_facility_id);
```

Three things this DDL cannot say, settled by #98 (2026-08-23) and enforced in `modules::master_data`:

- **`facility_type` has no `CHECK`**, so the vocabulary in the comment is enforced in code or not at all. It is a closed enum on the request type: an unknown value is a 422, and the column stays open so that adding a type is a code change rather than a migration. Reads are lenient — a value already stored that the enum does not know comes back as `null` rather than hiding the row.
- **`parent_facility_id` is a self-reference, and a self-reference is not a tree.** PostgreSQL can say *points at a facility* and cannot say *and not at one of its own descendants*, so the service walks up from the proposed parent before writing and refuses a move that would close a loop. The walk is depth-bounded, because a cycle that reached the table some other way would otherwise make it run forever.

    **The walk and the write it guards are one transaction, serialised per tenant by an advisory lock** (#133). Read on the pool and written afterwards, they were check-then-act: two callers each walked a path the other was about to change, both were told the move was legal, and the pair closed a loop neither could see alone. Row locks do not fix it — two re-parentings can close a loop while touching four different facilities, so each caller's own row and its proposed parent are disjoint sets. Re-parenting is a rare administrative act, so taking it one at a time per tenant is the version whose correctness needs no proof.

    **A delete refuses while anything still sits under the facility, and the count and the delete are one transaction** (#137). Counted on the pool and deleted afterwards, the refusal only held against children that already existed: a create resolving this facility as its parent a moment before the delete landed left a live row under a retired one. The same per-tenant lock covers all three writers — a re-parenting, a delete, and a create or re-parent naming a parent, which re-reads that parent under the lock before pointing at it.

    **A walk that hits the depth bound is a refusal, not a pass** (#134). Past the bound the walk returns a prefix of the path, and the facility being moved not appearing in a prefix is not evidence that it is not an ancestor — which made the bound able to create the corruption it existed to survive. A move the check cannot verify is answered `422` with `TOO_DEEP` naming `parentFacilityId`. Nothing limits how deep a hierarchy may be *built*, so this is reachable by ordinary use rather than only by a corrupt table; the resolution errs towards refusing a legal move over allowing an illegal one.
- **`address_json` reuses the `postalAddress` shape** the party contact mechanisms already define (§4.11), rather than inventing a second one. It is stored inline rather than as a contact mechanism because a facility *has* an address, where a party may have several for several purposes.

A delete does **not** cascade to the children: retiring a building would otherwise retire its floors and their rooms in one call. The service refuses while anything still points at the row.

## 4.17 `record_status` — the governance lifecycle

`mdm_parties`, `mdm_facilities`, `mdm_products` and `mdm_services` all carry `record_status`, `created_by_document_id` and `last_updated_by_document_id`. The first became a controlled transition with #99 (2026-08-23); the two document references stay unwritten until FR-MDM-010 gives them a document to name.

**`record_status` is not `mdm_parties.status`.** `status` is `PARTY_ENABLED` / `PARTY_DISABLED`, the party's own enabled flag, moved by an ordinary update and audited as `STATUS_CHANGE`. `record_status` is how far the *record* has got through governance, moved only by `POST /{entity}/{id}/transition` and audited as `RECORD_STATUS_CHANGE`. Two columns, two meanings, two audit actions — an auditor asking who took a supplier out of service must not have to read the payload to tell which one happened.

The `CHECK` lists six values; the legal moves between them are narrower and live in `domain::record_status`:

```text
DRAFT      -> ACTIVE, INACTIVE
ACTIVE     -> SUSPENDED, INACTIVE
SUSPENDED  -> ACTIVE, INACTIVE
INACTIVE   -> ACTIVE, ARCHIVED
ARCHIVED   -> (terminal)
PENDING_APPROVAL -> ACTIVE, DRAFT
```

Two of those are decisions rather than transcription:

- **Nothing reaches `PENDING_APPROVAL`.** It is the workflow's state (FR-MDM-010, Phase 5+), and nothing today can approve anything, so a record put there would await an approver that does not exist. `DRAFT -> ACTIVE` is the path until the workflow lands.
- **`ARCHIVED` is terminal.** A route back to `DRAFT` would make the archive a filter rather than a decision; a record that must live again is re-created.

The write is conditional on the row still holding the status the transition was checked against, so two concurrent transitions cannot both move a record away from the same state. `mdm_products` and `mdm_services` have no transition route because they have no endpoints until Sprint 7 — the code is shared, so adding them is one enum variant each.

# 5. RAD Metadata — `0014_rad.sql`

Form definitions are **JFSS v2.0.1 documents stored whole** in `definition_json` — the component tree is the authority, per the [JSON Form Schema](../schema/JSON%20Form%20Schema.md). The `rad_form_sections` / `rad_form_fields` tables are projections extracted from the JFSS document on save, so the form builder and reporting can query fields relationally without parsing JSON. JFSS itself has no revision concept (`version` is the spec version), so revisioning lives here in `revision` / `status`.

> **Built 2026-08-25 as `0014_rad.sql` (#155), and this section is corrected to what was built.** Two kinds of change, both recorded as §14 deviation #17. **Bounded string columns take a length from §1.3.1** rather than `TEXT` — this section wrote `form_key TEXT` beside `status VARCHAR(40)`, and eleven of the affected columns sit inside unique indexes, which is the failure `0004_string_lengths.sql` exists to fix. **Four constraints and three indexes were added** that this section did not carry: they are marked `-- added by 0014` below, and each exists because the value it bounds is written by configuration rather than through a form that would have validated it.

```sql
CREATE TABLE rad_lookup_definitions (
    -- BASE

    label           VARCHAR(200) NOT NULL,
```

**This table is still storage without a reader, and [#161](https://github.com/sujanto-gaws/kelir/issues/161) deliberately did not give it one.** FR-RAD-007's lookup fields ship over a **code allow-list** — `rad::domain::lookup::LookupSource`, four constants — rather than over rows here, and the reason is the permission rather than the query. A lookup source decides two things: which query runs, and which permission the caller must hold for it. Taking the first from `source_config_json` puts an identifier into SQL from data, which §2.5 of the [coding standard](../standards/01.%20Coding%20Standard.md) requires an allow-list for; taking the second from the same row makes a misconfigured row a permission bypass that reads as a typo. `RoleView` is the same shape for the same reason, and #97's two-permission rule is what a row would have to reproduce.

So the table waits for configurable lookups — its `ENUM` and `STATIC` source types need no permission of their own, and `ENTITY` and `API` need an answer to "which permission does this row require" that the row cannot give. Nothing about it changes here, and no permission is seeded for it, which keeps §5.13's rule intact.

## 5.13 Permission catalogue rows

`0014_rad.sql` seeds nine permissions and grants them to `ROLE-ADMIN`, for the storage APIs of [#156](https://github.com/sujanto-gaws/kelir/issues/156) and for nothing else — entities, fields, menus, actions and lookups have no endpoint yet, and a permission row that no route checks reads as a control that exists (the rule `0010_facility_permissions.sql` states).

**The lookup surface added by [#161](https://github.com/sujanto-gaws/kelir/issues/161) adds no row, and that is the design rather than an omission.** `GET /api/v1/rad/lookups/{source}/options` requires exactly what the master-data endpoint it projects requires — `master-data:party:read` with `master-data:party-role:read` for the supplier, customer and employee sources, `master-data:facility:read` for facilities — and requires them by calling that module's service rather than by checking a string of its own. A `rad:lookup:read` beside them would create the gap it was meant to close: a deployment could grant the lookup without granting the list, which is a way to enumerate suppliers to somebody who may not read suppliers. It is also the per-endpoint permission shape decision **D-6** rejected for the catalogue.

| Permission | Grants |
|---|---|
| `rad:form:create` | Create a form definition |
| `rad:form:read` | View form definitions |
| `rad:form:update` | Edit a draft form revision |
| `rad:form:publish` | Publish a revision, fixing it for every document that pins it |
| `rad:form:submit` | Fill in a published form and record the submission (added by `0021`) |
| `rad:form:delete` | Retire a form definition |
| `rad:list:create` / `read` / `update` / `delete` | The same four on list definitions |

**The tenth row is `rad:form:submit`, added by `0021_rad_form_submissions.sql` ([#164](https://github.com/sujanto-gaws/kelir/issues/164)), and it is separate from `read` for the reason `publish` is separate from `update`.** Opening a requisition to read it and raising one are different questions, and a deployment that wants them to be the same person grants both. It is not `rad:submission:create`: the `resource` segment names what the permission is *about* ([naming convention](../standards/02.%20Naming%20Convention.md) §6), and this is about a form — the submission row is the record it leaves, not the thing being authorized.

`publish` is separate from `update` on forms and has no counterpart on lists. Publishing is not an update with a different value — it fixes a revision forever, and documents pin the exact `rad_forms.id` they were created against, so a published revision is what an old document re-renders with years later. Who may draft a form and who may make a draft binding are different questions; a deployment that wants them to be the same person grants both. A list has no such moment: its status moves between `ACTIVE` and `DEPRECATED` and back, and nothing pins it.


## 5.14 rad_form_submissions

Added by `0021_rad_form_submissions.sql` ([#164](https://github.com/sujanto-gaws/kelir/issues/164)).

```sql
CREATE TABLE rad_form_submissions (
    -- BASE
    form_id         UUID        NOT NULL REFERENCES rad_forms (id),
    form_revision   INTEGER     NOT NULL,       -- the revision form_id pins, denormalized
    payload_json    JSONB       NOT NULL,       -- the server's re-evaluated payload
    submitted_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_rad_form_submissions_form
        FOREIGN KEY (form_id, tenant_id)
        REFERENCES rad_forms (id, tenant_id),
    CONSTRAINT ck_rad_form_submissions_revision_positive CHECK (form_revision >= 1)
);
CREATE INDEX idx_rad_form_submissions_tenant_id_form_id
    ON rad_form_submissions (tenant_id, form_id, submitted_at DESC)
    WHERE deleted_at IS NULL;
-- The composite target the foreign key above needs, created in the same file.
ALTER TABLE rad_forms
    ADD CONSTRAINT uq_rad_forms_id_tenant_id UNIQUE (id, tenant_id);
```

**`payload_json` holds the server's answer and never the client's.** [JSON Form Schema](../schema/JSON%20Form%20Schema.md) S8.1 requires the backend to re-evaluate every `calculate` expression and *overwrite* the submitted value before persistence, and S10.2 requires the same for every `conditional`, discarding the values of components that resolve to hidden. What is written here came out of `rad::service::evaluation`, so a row is by construction not a record of what a browser computed — which is the whole of the Tamper-Proof Pattern and the reason there is no second column holding what was posted. Two answers side by side would be two things to reach for, and one of them is the untrusted one.

**This is not the document store, and nothing should grow it into one.** No status, no number, no workflow instance, no relations: those are §6's tables and Sprint 9 builds on them (FR-DOC-001..007, decision **D-16**). A form that submits is not yet a document that exists, and this table is that sentence in DDL. Sprint 9's [#168](https://github.com/sujanto-gaws/kelir/issues/168) calls the same re-evaluation from inside the transaction that takes a document's number, which is why the evaluation service takes no database handle at all.

**`form_revision` is denormalized on purpose.** `form_id` already pins the exact revision — a published revision is immutable and a new revision is a new row (§5.3) — so the number is a join away. It is stored anyway because a submission is evidence: reading "revision 3 of `purchase-requisition`" off the row is what makes a stored payload interpretable years later without trusting that nothing ever hard-deleted a form.

**`submitted_at` is not `created_at` wearing another name.** `created_at` is when the row was written; `submitted_at` is when the person pressed the button, which is the business fact Sprint 9's numbering and status transitions will be ordered by. They are equal today because both happen in one request, and they stop being equal the first time a submission is queued, retried or imported.

`deleted_at` is present because §1.2 gives it to every table and is never set by any route: a submission records something that happened, and retiring one would be editing history rather than the record it describes. Reads filter it all the same, so the day a retention policy sets one the reads are already right.

## 6.2 document_types

Tables §6.2–§6.5 and the type-scoped rows of §6.11 are the normalized storage of the [Document Type Definition Schema (DTDS)](../schema/Document%20Type%20Definition%20Schema.md) aggregate, which the builder and import/export APIs exchange.

```sql
CREATE TABLE document_types (
    -- BASE
    type_code       VARCHAR(64)        NOT NULL,           -- 'PURCHASE_REQUISITION', 'SUPPLIER_UPDATE'
    name            VARCHAR(200)        NOT NULL,
    description     TEXT,
    category        TEXT,                           -- 'PROCUREMENT', 'HR', 'MASTER_DATA'
    form_id         UUID        REFERENCES rad_forms (id),      -- published JFSS form
    list_id         UUID        REFERENCES rad_lists (id),
    default_security_level TEXT NOT NULL DEFAULT 'INTERNAL'
                    CHECK (default_security_level IN ('PUBLIC', 'INTERNAL', 'CONFIDENTIAL', 'RESTRICTED')),
    retention_policy_id UUID    REFERENCES retention_policies (id),
    target_entity_type  TEXT,                       -- set for master-data change document types
    status          VARCHAR(40)        NOT NULL DEFAULT 'ACTIVE'
                    CHECK (status IN ('DRAFT', 'ACTIVE', 'DEPRECATED'))
);
CREATE UNIQUE INDEX uq_document_types_tenant_id_type_code
    ON document_types (tenant_id, type_code) WHERE deleted_at IS NULL;
```

**`form_id` names the *current* binding, and a document does not read it.** A document pins its own `form_id` at creation (§6.6), so re-pointing a type at a newer published revision leaves every existing document rendering against the revision it was filled in with. That is what makes revising a form usable at all: a type that could never be re-pointed would be stuck on revision 1 the moment one document existed.

> **Re-pointing is refused while any document of the type pinned nothing** (decision **D-30**, [#165](https://github.com/sujanto-gaws/kelir/issues/165)). §6.6's `form_id` is nullable, and a document that pinned no revision has only its type's *current* binding to render against — so moving that binding re-renders it against a definition nobody filled in. The refusal is what turns the paragraph above from a description into a guarantee, and it is enforced by the foreign key rather than by a convention: inserting into `documents` takes a `FOR KEY SHARE` on the `document_types` row, which the rebinding's `FOR UPDATE` conflicts with, so the two serialize whatever the document surface later does.
>
> **A `NOT NULL` on §6.6's `form_id` was the alternative and is not taken.** It would forbid a document of a type that binds no form, which this table permits, and it would settle a column the document surface ([#167](https://github.com/sujanto-gaws/kelir/issues/167)) has not yet written to — a constraint reaching forward into an unbuilt surface rather than a rule about this one.

## 6.3 document_type_numbering_rules

```sql

    -- BASE
    document_type_id UUID       NOT NULL REFERENCES document_types (id) ON DELETE CASCADE,
    rule_template   TEXT        NOT NULL,           -- 'PR-{year}-{sequence}'
    sequence_scope  TEXT        NOT NULL DEFAULT 'YEAR'
                    CHECK (sequence_scope IN ('GLOBAL', 'YEAR', 'MONTH', 'DEPARTMENT_YEAR')),
    sequence_padding INTEGER    NOT NULL DEFAULT 6,
    is_active       BOOLEAN     NOT NULL DEFAULT true,
    -- added by 0016_numbering_gap_policy.sql
    allow_gaps      BOOLEAN     NOT NULL DEFAULT false,
    -- next_sequence and sequence_key were here until 0020_numbering_buckets.sql
    -- moved them to §6.3.1. See the note below.
    -- added by 0015: 0 renders no number and a large padding renders one no
    -- column holds
    CONSTRAINT ck_document_type_numbering_rules_padding CHECK (sequence_padding BETWEEN 1 AND 20)
);
CREATE UNIQUE INDEX uq_document_type_numbering_rules_active
    ON document_type_numbering_rules (document_type_id) WHERE is_active AND deleted_at IS NULL;
```

Number assignment increments `next_sequence` under `SELECT ... FOR UPDATE` inside the submit transaction, between the `before_document_number_assign` and `after_document_number_assign` hooks.

> **Built 2026-08-25 (#158).** The row lock is what this section always specified and is now the thing that holds: the read, the decision and the write are one transaction, and the lock is taken on the row the read consulted (coding standard §2.5). The advisory-lock alternative this section also offered is not used — the rule row *is* the contended resource, so locking it is both precise and cheaper than a lock two unrelated types would share.
>
> **`allow_gaps` is what makes the transaction's ownership meaningful**, and it is the one thing the original DDL left implicit. A gapless rule allocates inside the submitting transaction, so a rollback rolls the number back and concurrent submissions of that type serialise until commit — which several jurisdictions require of invoices and fiscal documents. A gap-tolerant rule allocates in a transaction of its own that commits immediately, so the row is held for microseconds and a failed submission leaves a gap. **The default is gapless**: a deployment that wants throughput can say so, and one that needed an unbroken sequence and never thought about it gets the safe answer rather than a compliance problem found at an audit.
>
> **One bucket per rule was wrong, and `0020_numbering_buckets.sql` corrects it (decision D-21, [#200](https://github.com/sujanto-gaws/kelir/issues/200)).** This paragraph used to say the counter lived in `sequence_key`/`next_sequence` on the rule row, one bucket at a time, and gave the reason: a document back-dated into a bucket the sequence had left was refused rather than restarting it, because restarting would re-issue numbers documents already hold.
>
> The reasoning was right and the storage could not carry it. `DEPARTMENT_YEAR` has buckets that are live **simultaneously** rather than in succession — one per department — and one row holds one. The allocator restarted the counter whenever the computed key differed from the stored key and was not judged *earlier*, and two departments are never earlier than one another, so every allocation that changed department reset the only bucket there was. Measured on the Sprint 7 surface: allocating for department A, then B, then A, then B issued `000001` four times.
>
> **The counters are now in [§6.3.1](#631-document_type_sequence_buckets), one row per scope value**, keyed on the document type rather than on the rule — a rule row is replaced on every edit, and a sequence that reset when somebody corrected a template would re-issue numbers just as surely.
>
> **The back-dating refusal survives, and its justification changed.** Reaching into a passed bucket no longer restarts anything; it would resume that bucket correctly. It is still refused, now because a closed period should not gain new numbers — a policy rather than a safety property, and one the product owner may revisit. Recorded as such in **D-21** rather than left to read as though nothing had moved.

```sql
    document_type_id UUID        NOT NULL REFERENCES document_types (id) ON DELETE CASCADE,
```

> **The unique index is total, not partial on `deleted_at`**, and that is deliberate twice over. It is also the honest shape: soft-deleting a counter would hand out numbers documents already hold, so nothing sets `deleted_at` on this table. The column is present because every table in §6 carries the base columns, and the migration says so rather than leaving a reader to infer it.

>
> **The composite foreign key** onto `document_types (id, tenant_id)` is `0017_tenant_administration.sql`'s pattern applied here: a bucket filed under the wrong tenant is unwritable rather than merely unwritten. `document_types` gains `UNIQUE (id, tenant_id)` in the same migration to be that target.

> **Which statuses a `documents` row is writable in, and it is two answers rather than one** ([#183](https://github.com/sujanto-gaws/kelir/issues/183)). Both are carried in the `WHERE` of the statements themselves (`update_document`, `soft_delete`) as well as by the service, which is what makes them properties of the write rather than of whoever remembered to check first.
>
> **A resubmission takes no number.** `mark_submitted` writes `COALESCE($3, document_number)` and the submit allocates nothing when the document is `RETURNED`, so the sequence is untouched by a correction round — on a gap-tolerant rule an allocate-then-discard would leave a permanent hole per round. **D-42** records the shape.

## 6.14 Permission catalogue rows

`0015_document.sql` seeds four permissions and grants them to `ROLE-ADMIN`, for the document-type surface of [#157](https://github.com/sujanto-gaws/kelir/issues/157) and for nothing else — documents, versions, metadata, relations and the hook tables have no endpoint until Sprint 9, and a permission row that no route checks reads as a control that exists.

| Permission | Grants |
|---|---|
| `document-type:create` | Create a document type |
| `document-type:read` | View document types |
| `document-type:update` | Edit a document type, including the form and workflow it binds |
| `document-type:delete` | Retire a document type |

The resource segment is omitted because `document-type` manages one resource ([naming convention](../standards/02.%20Naming%20Convention.md) §6): the numbering rule and the workflow bindings are parts of a type, not resources beside it.

**`0023_document.sql` seeds the six the document surface itself checks** ([#167](https://github.com/sujanto-gaws/kelir/issues/167)–[#172](https://github.com/sujanto-gaws/kelir/issues/172)), which is the paragraph above being honoured rather than overruled: the routes now exist.

| Permission | Grants |
|---|---|
| `document:create` | Create a document from a document type |
| `document:read` | View documents |
| `document:update` | Edit a draft document and its metadata |
| `document:delete` | Discard a draft document |
| `document:submit` | Submit a draft, which assigns its number |
| `document:transition` | Move a document to another status |

**`submit` and `transition` are separate from `update`, and neither is a convenience.** Submitting takes a number the document keeps forever and starts a life a workflow will later drive, so a deployment that lets a clerk correct a requisition's line items has not thereby decided the clerk may commit it. Transitioning is #99's AC1 restated one module over: a transition has a from-state, a legal set, its own audit action and its own consequences, and putting it behind the update permission would put approval behind typing. Nothing is seeded for versions, metadata, relations or the lifecycle hooks — metadata is part of a document rather than a resource beside it, and the other three still have no endpoint.

## 6.15 document_ref_sequences

Added by `0023_document.sql` ([#167](https://github.com/sujanto-gaws/kelir/issues/167)).

```sql
CREATE TABLE document_ref_sequences (
    id              UUID        PRIMARY KEY,
    tenant_id       UUID        NOT NULL REFERENCES tenants (id),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    reference_key   VARCHAR(64) NOT NULL,       -- the bucket: '2026'
    next_sequence   BIGINT      NOT NULL DEFAULT 1,
    CONSTRAINT ck_document_ref_sequences_sequence CHECK (next_sequence >= 1)
);
CREATE UNIQUE INDEX uq_document_ref_sequences_tenant_id_reference_key
    ON document_ref_sequences (tenant_id, reference_key);
```

**What it is for, and what it is not.** §6.6 documents `documents.document_ref` as `DOC-2026-000123` — tenant-wide, year-scoped, sequential — and nothing produced it. It is **not** `document_number`: the number is the business identifier a type's rule renders and a submit assigns, and the ref is the internal handle a draft has for the whole of its life *before* it has a number. A draft with no handle is what a user is looking at until they submit.

**The shape is `document_type_sequence_buckets`', deliberately.** One row per bucket, insert-or-advance in a single statement, `RETURNING next_sequence - 1` so the caller never re-reads to learn what it got, and no read to race — §6.3.1's reasoning transfers unchanged, and writing a second allocator that was subtly different is what [#200](https://github.com/sujanto-gaws/kelir/issues/200) was. What differs is the **scope**: a document number's bucket belongs to the document *type*, and a reference's belongs to the tenant, because §6.6 makes the ref unique per tenant rather than per type.

**It has no `created_by`, no `updated_by` and no `deleted_at`**, for the reason §6.3.1 gives about a bucket: a counter is not a record somebody owns, and a soft-deleted counter would be a sequence that silently restarted.

The allocation happens **inside** the creating transaction, so a failed create rolls the counter back with it and the refs have no gaps. The trade is that creations within one tenant-year serialise from the allocation to the commit; a creation transaction is short, and the [Sprint 9 construction plan](../../projects/planning/04.%20Sprint%209%20Document%20Construction%20Plan.md) §3 records this as the one question it leaves owed, so a measurement can move it.

## 6.16 The index over the entity link

# 7. Workflow — created by `0025_workflow.sql`

Written 2026-08-28 ([#174](https://github.com/sujanto-gaws/kelir/issues/174)). It also adds the two foreign keys `0015_document.sql` deferred (§7.4) and the eight permission rows the workflow surface checks (§7.12).

**The column widths below follow §1.3.1 rather than the `TEXT` this section originally specified.** §7 was written before `0004_string_lengths.sql`, and §1.3.1 is the general rule — an indexed `TEXT` column fails unpredictably at around 8 KB and MariaDB cannot index one without a prefix. `0015_document.sql` resolved the same disagreement the same way for `documents.document_ref`, so this follows the established answer rather than inventing a second one, and the DDL here is what was built.

## 7.1 workflow_definitions

The definition JSON is the authority (states, transitions, guards, actions, assignment rules) and conforms to the [JSON Workflow Schema (JWSS)](../schema/JSON%20Workflow%20Schema.md). `workflow_states` and `workflow_transitions` are projections regenerated on publish, for the designer UI and for the foreign key of §7.4. Running instances pin `workflow_definition_id`, so published definitions are immutable — editing creates the next `version`.

> **`version` and `jwss_version` are different numbers and the names keep them apart.** `version` is the *definition revision* — what an instance pins and what "revision 3 of this workflow" means. `jwss_version` is the *specification* version the document declares. The two were conflated once on forms, which is why they are named apart here.

```sql
CREATE TABLE workflow_definitions (
    -- BASE
    workflow_key    VARCHAR(64) NOT NULL,           -- 'purchase_requisition_standard'
    name            VARCHAR(200) NOT NULL,
    description     TEXT,
    version         INTEGER     NOT NULL DEFAULT 1, -- definition revision
    jwss_version    VARCHAR(40) NOT NULL,           -- JWSS spec version of definition_json, e.g. '1.0.0'
    definition_json JSONB       NOT NULL,           -- JWSS document: states, transitions incl. guards/actions
    initial_state   VARCHAR(64) NOT NULL,
    status          VARCHAR(40) NOT NULL DEFAULT 'DRAFT'
                    CHECK (status IN ('DRAFT', 'ACTIVE', 'DEPRECATED')),
    published_at    TIMESTAMPTZ,
    published_by    UUID        REFERENCES users (id)
);
CREATE UNIQUE INDEX uq_workflow_definitions_tenant_id_workflow_key_version
    ON workflow_definitions (tenant_id, workflow_key, version) WHERE deleted_at IS NULL;
```

> **`workflow_definition_id` is the version pin, and there is no `definition_version` column beside it.** [#175](https://github.com/sujanto-gaws/kelir/issues/175) AC1 asks that an instance record the revision it started against and keep running it; this reference names a revision *row*, and a published revision row never changes. A number stored beside it would be a second copy of a fact the reference already carries, which is AC3's failure in the other direction. The API answers the question by joining.
>
> **`fk_workflow_instances_current_state` forces an ordering that is correct anyway**: `workflow_states` is written on publish, so only a published definition can start an instance. That is not a second rule to remember, it is this one.
>
> **`STARTED` is in the `CHECK` and nothing writes it.** The engine inserts an instance as `RUNNING` — the transaction that creates it also enters the initial state, so a status every row would leave inside one statement is a status a reader would spend time on for nothing. The value is here because it was specified; the product does not produce it.

## 7.6 workflow_tasks

```sql
CREATE TABLE workflow_tasks (
    -- BASE
    task_ref        VARCHAR(64) NOT NULL,           -- TASK-2026-000123 (§7.10)
    workflow_instance_id UUID   NOT NULL REFERENCES workflow_instances (id) ON DELETE CASCADE,
    document_id     UUID        NOT NULL REFERENCES documents (id),

                                         'SIGNATURE_TASK', 'DATA_ENTRY_TASK')),
    status          VARCHAR(40) NOT NULL DEFAULT 'CREATED'
                    CHECK (status IN ('CREATED', 'ASSIGNED', 'IN_PROGRESS', 'COMPLETED',
                                      'DELEGATED', 'ESCALATED', 'CANCELLED')),
    assignee_user_id     UUID   REFERENCES users (id),
    candidate_role_id    UUID   REFERENCES roles (id),
    candidate_department_id UUID REFERENCES departments (id),
    delegated_from_user_id UUID REFERENCES users (id),
    priority        VARCHAR(40) NOT NULL DEFAULT 'NORMAL'
                    CHECK (priority IN ('LOW', 'NORMAL', 'HIGH', 'URGENT')),
    due_at          TIMESTAMPTZ,
    action          VARCHAR(40) CHECK (action IN ('APPROVE', 'REJECT', 'RETURN', 'SUBMIT',
                                                  'CONFIRM', 'SIGN', 'COMPLETE')),
    comment         TEXT,
    completed_by    UUID        REFERENCES users (id),
    completed_at    TIMESTAMPTZ
);
CREATE UNIQUE INDEX uq_workflow_tasks_tenant_id_task_ref
    ON workflow_tasks (tenant_id, task_ref) WHERE deleted_at IS NULL;
CREATE INDEX idx_workflow_tasks_assignee_status ON workflow_tasks (tenant_id, assignee_user_id, status);
CREATE INDEX idx_workflow_tasks_candidate_role_status ON workflow_tasks (tenant_id, candidate_role_id, status);
CREATE INDEX idx_workflow_tasks_due_at ON workflow_tasks (tenant_id, status, due_at);  -- escalation scan

-- Sequential approval only: an instance has at most one open task.
CREATE UNIQUE INDEX uq_workflow_tasks_open_per_instance
    ON workflow_tasks (workflow_instance_id)
    WHERE status IN ('CREATED', 'ASSIGNED', 'IN_PROGRESS') AND deleted_at IS NULL;
```

> **`delegated_from_user_id` names whose authority the assignee is exercising** ([#184](https://github.com/sujanto-gaws/kelir/issues/184)), and it is set two ways: by a delegation window (§3.8) redirecting the task when it is created, and by `POST /api/v1/workflow/tasks/{id}/delegation` when its holder hands it on. On a second hand-off it is **not** overwritten — `COALESCE` keeps the original — because what it answers is *whose approval is being given*, which is what the `allowedBy` check and the history row both read it for. The chain of who passed it to whom is in `workflow_task_history`, one row per hand-off.
>
> **`due_at` is stamped at generation, from the database's clock, and never recomputed** (FR-WF-011, [#185](https://github.com/sujanto-gaws/kelir/issues/185)). A JWSS task declares `dueInHours` — relative, because a definition outlives every instance that runs it and an absolute date in one is wrong for every instance after the first — and `insert_task` writes `now() + make_interval(...)` in the statement that creates the row. Two properties fall out of that and both are the requirement's: a deadline does not move because somebody published a new revision afterwards, and the stamp shares a clock with every later *is this overdue* comparison. An application fleet whose members' clocks drift would otherwise date two tasks generated a second apart hours apart, and no screen could tell.
>
> **Overdue is not a column and is not stored.** It is `due_at IS NOT NULL AND due_at < now() AND status IN ('CREATED','ASSIGNED','IN_PROGRESS')`, computed by the inbox's own statements and sent to the client as a boolean. The `IS NOT NULL` is written out rather than left to three-valued logic because the usual shorthand for it — a null coalesced to the epoch — reports every undated task as years late. The status clause is what keeps *late* meaning *needs doing*: a task finished after its date passed is done, not late, and colouring it would bury the ones that are.
>
> **A delegated task stays `ASSIGNED`; nothing writes `DELEGATED`.** That value is in the `CHECK` above and outside both `uq_workflow_tasks_open_per_instance` and the inbox's open filter, so writing it would leave a running process with no open task, stop the index guarding that instance against a second one, and hide the work from the person who had just been given it. A status answering *who holds this* rather than *where has this got to* is the two-meanings-one-column failure this schema has refused before, and `delegated_from_user_id` beside `assignee_user_id` is the answer to the first question. `DELEGATED` keeps `STARTED`'s standing (§7.4). The same goes for `action`: a hand-off decides nothing, so it writes neither `action` nor an `approval_decisions` row, and `DELEGATE` is absent from that column's `CHECK` for that reason rather than by omission.
>
> **A task is assigned to a user *or* offered to a role, never both** ([#176](https://github.com/sujanto-gaws/kelir/issues/176) AC2). A role task has no assignee until somebody claims it, and that is the difference [#179](https://github.com/sujanto-gaws/kelir/issues/179) AC1 has to show a person: an unclaimed queue item and work that is already mine are different situations. Writing both would erase the difference at creation and no screen could recover it. The invariant is held by the service — `workflow::service::assignment` has only two constructors — rather than by a `CHECK`, because a `CHECK` here would also have to be relaxed for Sprint 11's delegation.
>
> **`uq_workflow_tasks_open_per_instance` is "sequential approval only" written as a constraint rather than an intention.** An instance is in one state and a JWSS state declares at most one `task`, so the property falls out of the model; the index is what makes it checkable. When FR-WF-016 (parallel approval) is scheduled, this index is the thing it has to argue with — which is the point: the current design's assumption is visible and dated rather than discovered later as a property of code that turned out to allow something.
>
> **`comment` carries the reason the approver gave**, written by the same statement that completes the task ([#182](https://github.com/sujanto-gaws/kelir/issues/182), FR-TASK-006). It is one of three columns one decision fills — this one, `approval_decisions.comment` (§7.8) and `workflow_history.comment` (§7.11) — written from one value in one transaction, so a task recorded as decided cannot have its reason still in flight. **Whether a reason is required is the definition's to say, per transition** ([JWSS](../schema/JSON%20Workflow%20Schema.md) §4.1's `requiresComment`), not a rule in this schema: an approval explains itself and a refusal does not, and which is which belongs to whoever wrote the workflow. The value is trimmed and bounded at 4 000 characters by `workflow::domain::task::normalize_comment` — the column is `TEXT`, so nothing here bounds it.

> **`action` holds the transition vocabulary (§7.3), not the three verbs a decision issues.** It carried only `APPROVE`, `REJECT` and `RETURN` while those were the only things that happened to a task; [#184](https://github.com/sujanto-gaws/kelir/issues/184) added `DELEGATE`, which is a fourth thing that happens to a task and is not a decision about the document — so the request type for a decision does not gain the verb, and this column reads §7.3 rather than a subset of it.
>
> **`comment` gained its first writer with the hand-off, and only the hand-off.** A decision's reason already has three homes — §7.6, §7.8 and §7.11 — and this is not a fourth. What a hand-off has is a reason with nowhere else to go: nothing about the document was decided, so none of those three rows is written at all, and the note somebody left with "off from tomorrow" belongs to the task's own account of itself.

### 7.8.1 Three records of one approval, and which answers what

A decision writes two rows and a **third** record already exists elsewhere. They are not one fact three times, and `modules/workflow/mod.rs` states the distinction in the same words, because this project has twice found out what happens when two records of one event have no stated relationship:

| `workflow_task_history` (§7.7) | *What happened to this task* — including moves no person made | The task surface |

## 7.10 workflow_ref_sequences

Added by `0025_workflow.sql`. `workflow_instances.instance_ref` and `workflow_tasks.task_ref` are `NOT NULL` and unique per tenant, and nothing produced either.

**One table serves both, keyed by the prefix and the year** (`WFI-2026`, `TASK-2026`) rather than two tables differing only in what they count — two instances of a proven allocator is two places for the next fix to land in one of, which is what §6.3 used to be and what [#200](https://github.com/sujanto-gaws/kelir/issues/200) was. The prefix is part of the key, so an instance and a task never contend and neither can hand out the other's number.

The shape is `document_ref_sequences`' (§6.15), which is `0020_numbering_buckets.sql`': one row per bucket, insert-or-advance in a single statement, `RETURNING next_sequence - 1`, **no read to race**.

```sql
CREATE TABLE workflow_ref_sequences (
    id              UUID        PRIMARY KEY,
    tenant_id       UUID        NOT NULL REFERENCES tenants (id),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    reference_key   VARCHAR(64) NOT NULL,           -- 'WFI-2026' | 'TASK-2026'
    next_sequence   BIGINT      NOT NULL DEFAULT 1,
    CONSTRAINT ck_workflow_ref_sequences_sequence CHECK (next_sequence >= 1)
);
CREATE UNIQUE INDEX uq_workflow_ref_sequences_tenant_id_reference_key
    ON workflow_ref_sequences (tenant_id, reference_key);
```

It allocates **inside the transaction that creates the row it names**, so a rolled-back transition leaves neither a hole nor a reference on a task that was never created. The trade — two transitions in one tenant-year serialise from the allocation to the commit — is `document_ref_sequences`', accepted for its reason: a transition transaction is short, and if it ever bites, gaps in an internal handle cost nothing.

## 7.11 workflow_history

Append-only. How a document got here (FR-WF-012), created by `0027_workflow_history.sql` for [#181](https://github.com/sujanto-gaws/kelir/issues/181).

```sql
CREATE TABLE workflow_history (
    id              UUID        PRIMARY KEY,
    tenant_id       UUID        NOT NULL REFERENCES tenants (id),
    workflow_instance_id UUID   NOT NULL REFERENCES workflow_instances (id) ON DELETE CASCADE,
    document_id     UUID        NOT NULL REFERENCES documents (id),
    from_state      VARCHAR(64),                    -- null on the instance's first row
    to_state        VARCHAR(64) NOT NULL,
    action          VARCHAR(40),                    -- null when no action moved it
    task_id         UUID        REFERENCES workflow_tasks (id),
    comment         TEXT,                           -- the reason given with the decision (FR-TASK-006)
    actor_user_id   UUID        REFERENCES users (id),   -- null for engine actions
    on_behalf_of_user_id UUID   REFERENCES users (id),   -- whose authority (0028, #184)
    routing_json    JSONB,                          -- why this branch (0029, #186)
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_workflow_history_document_id ON workflow_history (document_id, created_at);
CREATE INDEX idx_workflow_history_instance_id ON workflow_history (workflow_instance_id, created_at);
```

> **This is not §7.7, and it is not §10.2.** Three tables record something about a workflow event and they answer different questions, which [#181](https://github.com/sujanto-gaws/kelir/issues/181) AC5 asks to be stated rather than inferred:
>
> | | Question | Reader | Permission |
> |---|---|---|---|
> | `workflow_history` (§7.11) | how did this document get here | the approver, in the workspace | `workflow:instance:read` |
> | `workflow_task_history` (§7.7) | what happened to this one task | whoever is looking at the task | `workflow:task:read` |
> | `audit_events` (§10.2) | was this tampered with | somebody investigating | `master-data:audit:read` |
>
> **Neither history is derived from the audit trail, and it is not derived from them.** The engine writes §7.11 in the transition's own transaction; `modules::audit` writes §10.2 from its own call site. Deriving the user-facing account from the audit trail would make a screen depend on rows that exist to be unchangeable — and an audit row a feature depends on is an audit row nobody can correct.
>
> **§7.7 could not hold this**, on two counts. Its `task_id` is `NOT NULL` and a transition needs no task — the submit enters the first state, and FR-WF-005's system tasks and JWSS `AUTO` transitions will move a process with none. And its `old_status`/`new_status` hold *task* statuses, a different vocabulary from a workflow state; one column pair holding both is the failure deviation #11 and §6.3 each record.
>
> **No `deleted_at`, `updated_at` or `updated_by`, deliberately** — §1.2's base columns are not all here, exactly as §7.7 and §6.9 omit them. [#181](https://github.com/sujanto-gaws/kelir/issues/181) AC6 asks that a record is never edited or deleted; the absence of the columns is what makes that true by construction rather than by nobody having written the route yet.
>
> **`routing_json` answers *why this branch and not the other one*** (FR-WF-015, [#186](https://github.com/sujanto-gaws/kelir/issues/186) AC5), added by `0029_workflow_routing.sql`. It holds every transition condition the engine actually evaluated to choose this edge, in the order S7 puts them, each with the boolean it produced:
>
> ```json
> [{"to": "DIRECTOR_APPROVAL", "condition": {"…": "…"}, "outcome": false},
>  {"to": "FINANCE_APPROVAL",  "condition": {"…": "…"}, "outcome": true}]
> ```
>
> **The working, not the conclusion.** The chosen edge's own condition is a tautology on a history row — it held, or it was the fallback that needed nothing — so recording only that would answer half the question and look like all of it. The `false` entries are the half that says why *not* the other branch. Edges after the winner were never evaluated and are absent rather than recorded as `false`, because the engine stops at the first condition that holds and saying otherwise would record something that did not happen.
>
> **`JSONB` and not a table.** A trail is read with the row it belongs to, never queried across rows and never joined — the three things that would argue for one. A `workflow_history_conditions` table would be a second row to keep in step with the first inside the transition's own transaction, for a payload bounded by the definition's size.
>
> `NULL` where nothing was evaluated, which is most rows: the instance's first state, and every action leaving exactly one unconditioned edge. An empty array would record a deliberation that did not happen.
>
> **`on_behalf_of_user_id` is the second party to a delegated decision** ([#184](https://github.com/sujanto-gaws/kelir/issues/184) AC4), added by `0028_delegation.sql`. It comes off `workflow_tasks.delegated_from_user_id` — which the server wrote, never a request — so acting on somebody's behalf is a fact about the task rather than a claim a caller can make.
>
> **The pair is here and not in §7.8**, which is a distinction the three-way table above is the wrong shape to carry. `approval_decisions.approver_user_id` is the *signature*: a delegated approval is signed by the delegate, and Phase 8's signature binding needs one name. This table answers *how did this document get here*, which is the question accountability is asked in — and a history showing only the delegate loses exactly what delegation was supposed to preserve. `NULL` on every row nobody was standing in for, which is almost all of them; the actor is not copied in to avoid the null, because that would make *acting for oneself* and *acting for somebody who happens to be oneself* the same row.
>
> **A hand-off writes no row here at all.** Handing a task to somebody else does not move the process, so there is no transition to record; it goes in §7.7, which is the account of what happens to a task, and that is what happened to it. **This paragraph used to give the constraint as the reason** — *`ck_workflow_history_moved` refuses the `from_state = to_state` row one would produce* — and [#259](https://github.com/sujanto-gaws/kelir/issues/259) removed the constraint, which is why the reason is restated rather than quietly reworded. The behaviour never depended on it: the engine writes here from `fire` and a hand-off does not call `fire`.
>
> **`from_state` may equal `to_state`, and `0030_workflow_self_transition.sql` is what made that true** ([#259](https://github.com/sujanto-gaws/kelir/issues/259), finding 1 of the [Sprint 11 independent pass](../../projects/verifications/09.%20Sprint%2011%20Independent%20Pass.md)). `0027` created the table with `CONSTRAINT ck_workflow_history_moved CHECK (from_state IS DISTINCT FROM to_state)` — the only choice in that migration with no paragraph arguing for it. A self-transition is legal JWSS (§4.2): `REVIEW --RETURN--> REVIEW` is *send it round again*, it satisfies S3, S4, S6 and S7, and a definition using one published and then produced a 500 on the decision that fired it. The constraint read this table as a log of state changes, which is §7.3's vocabulary and not this one — the name `moved` is the assumption showing. What the table records is a **decision**, and a reviewer who acted and left the document where it was is the row a reader most needs: without it the history has a gap exactly where a person acted, and nothing on the screen says the gap is there.
>
> **`comment` is the reason recorded with the decision that moved the process** ([#182](https://github.com/sujanto-gaws/kelir/issues/182), FR-TASK-006), and **this is the copy a person reads**. §7.6 and §7.8 hold the same value for the task surface and for reporting; this one is what the document workspace renders beside the transition it explains, which is why #182 AC2 names the history rather than either of the others — a reason shown nowhere would not have been worth capturing. `NULL` on a transition nobody gave one for, and on every row no decision drove.

## 7.12 Permission catalogue rows

`0025_workflow.sql` seeds eight and grants them to `ROLE-ADMIN`.

**The resource segment is required here**, because this module manages several resources ([naming convention](../standards/02.%20Naming%20Convention.md) §6) — which is the case that convention names, with `workflow:task:execute` as its own worked example.

| Permission | Grants |
|---|---|
| `workflow:definition:create` | Create a workflow definition, or the next revision of one |
| `workflow:definition:read` | View workflow definitions |
| `workflow:definition:update` | Edit a draft revision |
| `workflow:definition:publish` | Publish a revision, fixing it for every instance that starts against it |
| `workflow:definition:delete` | Retire a workflow definition |
| `workflow:instance:read` | View a running process and its variables |
| `workflow:task:read` | View tasks — the inbox, and one task's detail |
| `workflow:task:execute` | Claim a task, and record a decision on it |

**`publish` is separate from `update` for the reason it is separate on forms** (§5.13): publishing is not an update with a different value, it fixes a revision that running instances will execute for as long as they run. Who may draft an approval chain and who may make one binding are different questions.

**`workflow:task:execute` covers claiming as well as deciding**, and a separate `workflow:task:claim` was rejected: a permission that lets somebody take a task off the queue and then not act on it is a permission to stall an approval, which is a worse power than the one it was trying to split off. *Which* task a caller may act on is not a permission question at all — it is answered against the row.

**The task inbox seeds nothing.** `GET /api/v1/tasks` requires `workflow:task:read`, the same permission the workflow module's own task read requires, because it reads the same rows. A `task:read` beside it would let a deployment grant the inbox without granting the task, which is the gap §5.13 refused to create for `rad:lookup:read`.

Nothing is seeded for escalations (§7.9), for `workflow_variables` or for the history and decision records: a variable is part of an instance and a decision record is the trace a decision leaves, so none of them is a resource beside the three above.

# 10. Activity and Audit — `0033_activity.sql` and `0003_audit.sql`

**Two migrations, four sprints apart, and this header used to imply one.** `audit_events` and `audit_snapshots` shipped in `0003_audit.sql` in Sprint 3; `activity_events` is `0033_activity.sql`, built 2026-08-31 ([#247](https://github.com/sujanto-gaws/kelir/issues/247), Sprint 12 item 4). **D-44** found the mapping table planning both as one file and corrected it.

**Neither record is derived from the other**, and the difference is visible in two function signatures rather than only in prose:

| Record | Answers | Behind | Written |
|---|---|---|---|
| `activity_events` | *what happened to this document* | the document's own read | in the action's **own transaction** — an action that rolled back leaves no event |

**The read is the document's own, and nothing else** ([#250](https://github.com/sujanto-gaws/kelir/issues/250) AC2, decision **D-47**). The `behind` column of §10's table has said so since it was written and the code asked for `activity:read` as well; since 2026-09-01 it does not. A caller who may read a document may read what happened to it, because those are the same question. `activity:read` still exists, is still seeded, and is checked by nothing — [#301](https://github.com/sujanto-gaws/kelir/issues/301) removes it, one release later than the check, which is [release process](../standards/04.%20Release%20Process.md) §7's N−1 rule (*deprecate in release N, remove in N+1*).

**`details_json` says what happened to the *document*, and nothing about the subject** ([#292](https://github.com/sujanto-gaws/kelir/issues/292), decision **D-45**). A timeline entry is read by everyone holding `activity:read` and the document's own read — and by nobody else, which is the whole of the permission on this table. So an attachment's original name and size, a comment's length and the second party to a delegated decision are **not** written here: they belong to `attachments`, `comments` and `workflow_history`, each behind its own permission, and `workflow_instance_id`, `task_id`, `attachment_id` and `comment_id` are how an entry reaches them.

The rule this enforces is the one at the top of §10: an `activity_events` row answers *what happened to this document*, and a row that repeated another record's answer would be a fourth surface serving three other modules' data without asking their permissions. What each event type may carry is named in `activity::domain::disclosable`, which is also what the read passes rows written before D-45 through — this table is append-only, so the boundary is the only place that can answer for them.

## 10.2 audit_events

Formal compliance record: old/new values, hash-chained per tenant (SDD §11.3; SRS FR-AUD-002/003).

```sql
    digital_signature_ref TEXT,
    previous_hash   VARCHAR(255)        NOT NULL,           -- 'sha256:...' of the previous row in the tenant chain
    current_hash    VARCHAR(255)        NOT NULL,           -- see 'What the hash covers' below

);

CREATE INDEX idx_audit_events_document_id ON audit_events (document_id, created_at);
```

### What the hash covers

`current_hash` is a SHA-256 over **every column the writer fills**, in this order: `previous_hash`, `id`, `tenant_id`, `created_at`, `event_type`, `action`, `object_type`, `object_id`, `actor_user_id`, `ip_address`, `reason`, `old_value_json`, `new_value_json`. The format is defined by `modules::audit::chain_hash` and nowhere else; anything verifying a chain calls it rather than reimplementing it.

**The encoding, stated as the two things it guarantees.** A present field is hashed as eight bytes of big-endian length followed by its bytes; an absent one as a length of `u64::MAX` and no bytes.

- **A field boundary cannot be moved.** Without the prefixes an `event_type` of `Party.Cre` with an `action` of `atedX` hashes identically to `Party.Created` with `X`.
- **Absent is not empty.** A `NULL` `ip_address` and an `''` one are different rows, and are different hashes; the same holds for `reason`, for `actor_user_id`, and for a payload that is absent against one that is JSON `null`. No present field can be `u64::MAX` bytes long, so the sentinel cannot collide with a real value — and the guarantee is the sentinel's, not the prefix's.

The columns **outside** the hash are the ones nothing writes yet — `document_id`, `workflow_instance_id`, `entity_type`, `entity_id`, `actor_role_id`, `digital_signature_ref`. They are `NULL` on every row written so far. They join the hash when something starts filling them, which is a format change and a re-chaining decision.

> **The absent-is-not-empty half was wrong until 2026-08-27**, here and on the column comment `0019` had just corrected. Both said the length prefix kept an absent field distinct from a present-but-empty one; `modules::audit::optional` hashed `None` as zero bytes and `Some("")` as zero bytes, so the two `Option<&str>` columns collided — four entries differing only in whether `ip_address` and `reason` were `NULL` or `''` produced one digest. Either column could be rewritten either way without breaking the chain. The claim was only ever true of the *payload* columns, and for a different reason: `None` writes SQL `NULL` while `Some(Value::Null)` canonicalises to the four bytes `null`, a present field of length four. Fixed on [#203](https://github.com/sujanto-gaws/kelir/issues/203) with the sentinel above, and the column comment corrected through `0022_audit_hash_tells_absent_from_empty.sql`.
>
> **This description was wrong until 2026-08-26**, here, on the column in `0003_audit.sql`, and in the doc comment on `record` — all three said "hash over row content", and the implementation hashed the row's *metadata*. `old_value_json`, `new_value_json` and `created_at` were not in it, so each could be rewritten without disturbing that row's hash or any hash after it, and the chain still verified. A control that protects who and when but not *what* protects the half nobody would bother to forge: only the payload says from what, to what. Fixed on [#145](https://github.com/sujanto-gaws/kelir/issues/145), while it was still free — FR-AUD-003 is Phase 6 and nothing had ever verified a chain, so no stored hash had been relied on. After verification ships the same change costs a re-chaining migration plus a decision about what a row predating the format means. The correction reached `0003_audit.sql`'s column comment through `0019_audit_hash_covers_the_payload.sql`, because a merged migration is never edited (release process §6).

**Payload columns are hashed in `jsonb`'s own text form.** Verification recomputes the hash from the stored row, and what comes back out of a `JSONB` column is not what went in — PostgreSQL sorts object keys by length then bytewise, discards whitespace, drops duplicate keys, and normalises numbers through `numeric`. `modules::audit::canonical_json` renders a payload the way PostgreSQL will, and `record` stores that text rather than the value the application held, so the bytes in the column are the bytes that were hashed. Two rules carry that: object keys are ordered here rather than left to whichever `serde_json` features the dependency graph unified, and numbers are written in plain decimal because `numeric` prints no exponent.

```sql
CREATE UNIQUE INDEX uq_plugin_migrations_plugin_id_migration_name
    ON plugin_migrations (plugin_id, migration_name);
```

Plugin-owned tables are namespaced `plg_<plugin_code>_*` to keep them out of the core namespace.

## 13.8 plugin_hooks / plugin_events

Plugin-registered lifecycle hook handlers and extension point registrations. Rows are (re)created from the manifest on enable and removed on disable. The lifecycle hook resolver merges `plugin_hooks` with `document_lifecycle_hooks` (§6.11) into one chain.

```sql
CREATE TABLE plugin_hooks (
    -- BASE
    plugin_id       UUID        NOT NULL REFERENCES plugins (id) ON DELETE CASCADE,
    hook_name       TEXT        NOT NULL,           -- lifecycle hook ('before_document_submit')
                                                    -- or extension point ('register_document_tab')
    handler_reference TEXT      NOT NULL,           -- 'plugin:<pluginCode>:<handler>'
    priority        INTEGER     NOT NULL DEFAULT 500,   -- plugin band per architectures/01 §12.4.3
    is_enabled      BOOLEAN     NOT NULL DEFAULT true
);
CREATE INDEX idx_plugin_hooks_hook_name ON plugin_hooks (tenant_id, hook_name, priority)
    WHERE deleted_at IS NULL;

CREATE TABLE plugin_events (
    -- BASE
    plugin_id       UUID        NOT NULL REFERENCES plugins (id) ON DELETE CASCADE,
    event_name      TEXT        NOT NULL,           -- subscribed platform event: 'Document.Approved'
    handler_reference TEXT      NOT NULL,
    config_json     JSONB       NOT NULL DEFAULT '{}',
    is_enabled      BOOLEAN     NOT NULL DEFAULT true
);
CREATE INDEX idx_plugin_events_event_name ON plugin_events (tenant_id, event_name)
    WHERE deleted_at IS NULL;
```
