# Sprints 0–1 Retrospective — 2026-08-12

**Status:** Final · **Last updated:** 2026-08-12

**Sprint outcome:** both goals met · **Velocity note:** Sprint 0's five activities and Sprint 1's six issues all closed. Velocity is not yet meaningful — the two sprints ran back to back in a single continuous push with no calendar boundary between them, so no elapsed-time signal exists to estimate from. The plan's re-baseline point after Sprint 2 stands.

> **Why one retrospective for two sprints.** The convention is one per sprint. Sprint 0 and Sprint 1 ran without a boundary between them, and the lessons interleave — the Sprint 0 tooling decisions are what produced the Sprint 1 findings. Splitting them would have duplicated every root cause. Sprint 2 gets its own.

## What Worked

- **Running the gates before writing the pipeline.** The plan's own ordering — toolchains, then CI — was right, and checking it paid immediately: the skeleton failed both `cargo fmt --check` and `clippy -D warnings` on the first run. Writing the workflow first would have shipped a red pipeline on day one.
- **Verifying against real infrastructure, not just unit tests.** Every significant finding in both sprints came from actually running things: the port collisions, the lock-file churn, the migration checksum trap, the native PostgreSQL conflict. None was visible from reading the code, and 32 passing unit tests said nothing about any of them.
- **Deferring dependencies until they have a consumer.** `sqlx` was left out of Sprint 0 deliberately and added in Sprint 1 with the pool that uses it. The same judgment kept shadcn-vue out until the first component needs it.
- **Recording decisions with their reasoning at the point of divergence.** D-1…D-5 and the approval exception in git workflow §5 mean the repository and the standards never silently disagree; a reader can see what was decided and why.

## What Didn't

- **The Sprint 0 exit criterion was unmeetable as written.** "Green CI on a trivial PR merged by the workflow" depends on a permission the working token did not have. Engineering work was complete while the criterion stayed unmet.
- **Two permission conclusions were reported wrong before being corrected.** `gh pr create` and `gh issue create` failing with 403 was read as "the token cannot create PRs or issues"; in fact those commands use GraphQL, which this fine-grained PAT cannot reach, while the REST endpoints work. A later note blamed a failed API merge on `workflows: write`, which a subsequent PR disproved.
- **The scaffold shipped conventions that contradicted the documented ones.** `error.rs` emitted a bare `{code, message}` where SDD §12.3 specifies the full envelope, and `main.rs` declared modules it never used. Both had been committed and pushed long before Sprint 1 read them.
- **Placeholder files created a trap that only executing them revealed.** Eleven empty migrations were recorded as applied with checksums, which would have made SQLx refuse to run once real DDL replaced any of them — a failure that would have landed in Sprint 3, far from its cause.
- **Compose dirtied the working tree on every run** — `npm install` rewriting `package-lock.json` — for three runs before it was noticed.

## Root Causes

- **Scaffolding was written to look right rather than to run.** Placeholder migrations, one-line module stubs, and an error type that did not match the design all pass review by eye and fail on execution. Nothing in the process required the scaffold to *do* anything, so nothing caught it until Sprint 1 ran it.
- **Acceptance criteria were written against a tool's behaviour instead of an outcome.** "A PR merged by the workflow" names a mechanism; what the sprint actually wanted was evidence that the contributor path works end to end. When the mechanism was unavailable, the criterion blocked despite the outcome being achievable.
- **Error messages were treated as diagnoses.** A 403 from `gh` was accepted as a statement about token permissions rather than a symptom with several possible causes. Probing the REST endpoints directly — which took one command — would have shown the real boundary immediately.
- **Sharing a mounted working tree between host and container was never examined.** Both build into the same `node_modules` and `target/` for different platforms; the churn was the visible symptom of a design nobody had questioned.
