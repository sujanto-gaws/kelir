**Status:** Final · **Last updated:** 2026-08-26

## What Worked

**Sequencing the verification capability ahead of the thing it verifies, for the third time.** #153 ran before the sprint's own construction, as #96 did in Sprint 6 and #112 did before #98. It is now the only reason `create-a-tenant.spec.ts` exists — an unplanned item that arrived mid-sprint shipped with a browser flow, which no frontend item in this project had ever done. The rule paid off on work nobody knew about when the rule was applied.

**A lesson crossed a module boundary, which is what Sprint 6 said it had failed to do.** Record 03 closed on the observation that #99 got check-then-act right and #98 — same agent, same sprint, same table family — got it wrong twice. Department management is the counter-example: a tenant-wide advisory lock in the caller's transaction (#133), an ancestor walk that reports truncation rather than answering from a prefix (#134), and both references re-read inside the transaction (#118/#137), in a module that shares no code with facilities. `lock_department_hierarchy` carries the four-department counter-example that rules out the narrower lock. It is the first hierarchy in this project to be right on the first attempt, and what carried the lesson was coding standard §2.5 — a written rule, which is exactly the remedy record 03 proposed.

**#138 was fixed at the class rather than at the instance.** `every_annotated_route_reaches_the_document` reads the source in both directions instead of naming routes, so all thirty-three handlers Sprint 7 added reached the document with nobody remembering. This is the Sprint 6 action about self-discovering tests, delivered and then immediately load-bearing for a sprint that added more routes than any before it.

**D-16's arithmetic was done at the boundary rather than discovered in the sprint.** Phase 4 was re-scoped to three sprints at Sprint 7 *planning*, before the sprint that would have overrun. The Sprint 7 close needed no re-baseline of its own, which is the first time that has been true at a phase boundary.

**Tenant provisioning was built from the catalogue rather than from a list.** `permission_ids_excluding_prefix` means the nine `rad:*` and four `document-type:*` permissions reached tenants provisioned after the migrations that seeded them, and Sprint 8's will too. The same shape as the OpenAPI fix — discover the subjects, do not enumerate them — arrived independently in a different module in the same sprint.

## What Didn't

**The pass ran at the end, and so nothing it found was fixed.** Sprint 6 filed twenty issues across three passes spread through the sprint and closed fourteen inside it. Sprint 7 filed seven at the close and closed none. The sprint plan's capacity note is written as *"construction: six items; verification allowance: ten closing issues"* — a budget for closing what verification finds. The budget was never drawn on, because there was nothing to close until the sprint was over.

**The predicate-coverage action failed, measurably.** Sprint 6's fourth action asked pull requests to state which predicates they added and how each is exercised, with the done-when *"No Sprint 7 verification pass reports an unexercised predicate in code that sprint added."* Nine pull requests went by and not one carried such a statement. [Record 04](../verifications/04.%20Sprint%207%20Surface%20Verification.md) reports **twenty of thirty-two**, four of them the only guard on their behaviour ([#206](https://github.com/sujanto-gaws/kelir/issues/206)). The red ratio fell from 65% to 37%.

**A retired decision left debris that nothing swept for.** **D-18**'s record is unusually thorough — it lists eleven documents and three issues it was applied to — and it does not mention the one `#[ignore]` that cited **D-7** by name, in a cross-tenant isolation test whose own comment states the condition D-18 had just met ([#204](https://github.com/sujanto-gaws/kelir/issues/204)). The decision's blast radius was traced through documents and issues and not through code, and the code cites decisions by identifier, which is greppable.

**The migration restatements are still there, and maintaining them cost this sprint a commit.** The Sprint 6 action to delete them from `projects/` is **not done for the fourth consecutive sprint**, and the evidence is sharper than a count: `9bc5647` — "shift the sprint plan's migration restatement to `0020`" — is a commit whose entire content is keeping a restatement in step with the table that is supposed to be authoritative. [Record 04](../verifications/04.%20Sprint%207%20Surface%20Verification.md) then found six pointers of the same class inside `docs/design/02. Database Schema.md` itself ([#205](https://github.com/sujanto-gaws/kelir/issues/205)), in two sections whose headers say they were corrected to what was built.

**A design pair was specified in one document and never compared.** [#200](https://github.com/sujanto-gaws/kelir/issues/200) is not a coding mistake: `is_earlier_bucket` is correct about sequences, the lock is correct, and the test asserts what its author believed. Database Schema §6.3 states "one bucket per rule" in bold and, one paragraph away, a `CHECK` constraint admitting a scope that needs many. Two halves of one design, written together, never read against each other.

**Two tests asserted the true half of a broken property.** `two_departments_run_separate_sequences` allocates A then B and stops one move short of the move that would have failed; the quarantined body in [#204](https://github.com/sujanto-gaws/kelir/issues/204) passes `&[]` for the caller's roles, so un-ignoring it as written would have produced a green test asserting the permission gate while reading as a test of tenant isolation. Both are one line away from being real.

**The working token still cannot merge a pull request.** Sixth occurrence, and reported here only, per the Sprints 2–4 action to consolidate it.

## Root Causes

**Verification is scheduled as a phase, and budgeted as a flow.** The plan's capacity model — construction items plus an allowance for what verification closes — assumes findings arrive while there is sprint left to spend on them. Nothing in the plan says *when* the pass runs, and the only pass this sprint ran after the last pull request merged. Sprint 6 got this right by accident: its first item *was* a verification pass, so the sprint learned early what it was dealing with.

**Two of this sprint's process failures are the same failure — a rule with no artefact that carries it.** The predicate-coverage action asks a pull request to say something, and nothing checks that it did. The migration-restatement action asks a document to stop saying something, and nothing checks that it stopped. Both have now failed for as long as they have existed. Contrast the two that worked: §2.5's locking rule is in the coding standard and was applied by an agent who had not read the retrospective, and `every_annotated_route_reaches_the_document` is a test. **The actions that held were encoded in a standard or in a test; the actions that failed were encoded in a retrospective.**

**Defence in depth is written deliberately and verified never, because verifying it means disabling the first layer.** Sixteen of the twenty unexercised predicates are second lines behind first lines that work. Each was written on purpose — `update_draft`'s statement predicate has a paragraph explaining why it is in the statement and not only in the service — and none has been exercised, because no harness in the project can turn off a service-level guard to see whether the statement-level one catches it. The project's most careful code is its least verified code.

**A decision's reach is recorded as documents, and its debris is code.** Every decision in Product Backlog §6.2 ends with "Applied to …", listing documents, issues and occasionally functions. Nothing lists what cited the decision being superseded. The one artefact that would have caught #204 is a grep for `D-7`.
