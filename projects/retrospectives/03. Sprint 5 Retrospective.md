# Sprint 5 Retrospective — 2026-08-21

**Status:** Final · **Last updated:** 2026-08-21

**Sprint outcome:** goal met · **Velocity note:** seven planned, seven closed, against a measured construction rate of six to seven. The gap the plan left unfilled on purpose — capacity budgeted for verification rather than an eighth item — was consumed by verification, and the sprint still filed zero issues against itself. That number is the subject of most of this record.

## What Worked

- **Planning the sprint around verification capacity rather than construction capacity.** Sprint 4 planned ten, built five, and spent the remainder filing twelve issues against what it had built. Sprint 5 planned seven, with four of them the exit block, and left the gap to the construction rate unfilled. Everything closed.
- **Sequencing the exit block first.** Items 1–4 are properties every new route inherits — deserializer behaviour, session contracts, the boot guard, automated flows. Fixing them after the master-data module would have doubled the surface each fix had to be re-verified against. By the time items 6 and 7 added eight routes, those routes inherited fixed behaviour rather than needing their own copies of it.
- **The mutation rule, applied before it was written down.** Twenty mutations across items 6 and 7, four on item 4, seven on item 2, all cited against named tests. It found things: a tenant-scope test that could not fail, and — on item 4 — a mutation that had to be *discarded* because it edited a line the test never reaches, which is a distinction worth having a vocabulary for.
- **Refusing a decision rather than patching around it.** Item 3's session contract was overstated, not broken. The wording was narrowed to what the code does and a test now pins the residual fifteen-minute window, rather than the behaviour being changed to match a sentence nobody had costed. The same instinct closed **D-9**: staging was replaced with a check that can actually be run, rather than waived a fifth time.
- **Spikes producing findings instead of code.** #31 returned a written recommendation and a corpus, and raised **D-10** rather than merging an engine. The finding was worse than the risk register had assumed, which is the outcome a spike exists to produce.

## What Didn't

- **Items 6 and 7 were authored and verified by the same agent.** The [Sprints 2–4 retrospective](02.%20Sprints%202-4%20Retrospective.md) made "evidence checked by someone other than the item's author" an action, with the Sprint 5 report as its done-when. The report cites twenty mutation runs; not one of them was designed by someone who had not written the code. **Zero issues filed against itself is therefore not a quality measurement.** It is consistent with clean work and equally consistent with nobody having looked.
- **The one green mutation shows what that costs.** `a_party_in_another_tenant_has_no_roles_to_reach` looked like a tenant-scope test and was not one: all three routes refuse at the party lookup and never reach the role type, so the scoping on `find_role_type_id` was covered by nothing. The author found it only because the mutation pass is mechanical. A reviewer reading the test would have seen it faster, and a reviewer is what was missing.
- **A stacked pull request gets no CI, and this was known before it was repeated.** The workflow triggers on `pull_request: branches: [main]`. Both items 6 and 7 were split into a groundwork PR and a feature PR, and in both cases the second sat green-untested until the first merged and it was retargeted. The second time, it also carried a real defect: the migration went into the groundwork PR and the test its rows break went into the feature PR, so the groundwork PR's CI failed on a test that had already been fixed one commit away.
- **Two file splits landed inside a feature branch.** `domain.rs` at 1362 lines and `repository.rs` at 1083 were split because the incoming code would have made them the largest files in the repository by a wide margin. Each was a clean move in its own commit, but coding standard §1.5 says no drive-by refactoring mixed into feature work, and "the file was about to get too big" is a reason discovered while writing the feature, not before it.
- **The retrospective action to stop restating migration numbers in `projects/` is not done**, and this sprint added to the restatement rather than removing it: the sprint plan's numbering note gained a third clause when `0009` shifted the sequence again.

## Root Causes

- **Independent verification has no trigger.** It happened in Sprint 4 because that sprint's work was under suspicion, and it did not happen here because this sprint's work was not. Nothing in the Definition of Done requires it, nothing schedules it, and the status report's evidence column can be filled without it — as this one's was. An action that depends on somebody deciding to invoke it will keep firing only when somebody is already worried.
- **Filed-issue count was adopted as a proxy for quality without stating what it measures.** The Sprint 5 plan set it as the measurement to take at the close. It measures *how much verification found*, which is the product of how much there was to find and how hard anyone looked, and the sprint that reports it is the sprint that controls both factors.
- **The CI trigger encodes an assumption the branch strategy broke.** `branches: [main]` is correct for a repository where every PR targets `main`. Stacking is a reasonable answer to a 3,600-line diff, and the two conventions were never reconciled — so the reviewability fix silently bought a testing gap.
- **File size is not a planning input.** Nothing estimates how much code an item adds to which file, so "this file is now too large" is always discovered mid-implementation, when the only options are a mixed commit or a separate PR that blocks the work.
