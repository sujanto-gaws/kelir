## The rollback rehearsal

**§6's procedure, all three steps, run on 2026-08-30.** The `v0.4.0` backend knows migrations `0001`–`0023`. It was started against a database the `v0.5.0` migrator had just taken to `0030`.

| Check | Result |
|---|---|
| `v0.5.0` migrates an empty database | **30 of 30 applied**, highest version 30 |
| `v0.4.0` **source compiles** against that schema, SQLx online | **Yes** — `cargo build --release` with `SQLX_OFFLINE=false` against the migrated database. **This is §6 step 3, and it is the schema half proven by the compiler**: SQLx verifies every query at build time, so `v0.4.0` compiling means every statement it holds still type-checks against `v0.5.0`'s schema |
| `v0.4.0` binary starts against a `0030` schema | **Yes.** `database migrations applied` — `set_ignore_missing` (the [#76](https://github.com/sujanto-gaws/kelir/issues/76) fix) tolerates the seven versions it has never heard of. This is the bookkeeping half |
| `/health`, `/health/ready`, `/health/live` | **200, 200, 200** |
| `/version` on the rolled-back binary | `{"version":"0.4.0","commit":"7401094",…}` — the tag's own commit |
| It writes, not just starts | **Yes.** It created the bootstrap administrator on that schema |
| `GET /api/v1/workflow/definitions` | **404** — the workflow surface is correctly absent from `v0.4.0`, which is what a rollback means |
| `GET /api/v1/documents` | **401** — `v0.4.0`'s own surface is present and asking for a token |
| `0024`'s index on the migrated schema | `uq_mdm_party_roles_party_id_role_type_id ON (party_id, role_type_id) WHERE deleted_at IS NULL` — present and partial, as `0024` intends |

**Why it passed.** Six of the seven new migrations are additive — new tables `v0.4.0` never saw, and two nullable columns on one of them — so there is nothing for the older binary to be wrong about. `0030` **drops** a `CHECK`, which only widens what the table accepts. The seventh, `0024_one_live_role_per_party.sql`, is the one this step exists for, and it is treated separately below.

### What was not rehearsed, and it is the part that matters most

**`0024`'s N−1 safety still rests on a claim, and this rehearsal did not test it.**

The claim, from the changelog: *`v0.4.0`'s only writer into `mdm_party_roles` holds the party row under `FOR UPDATE` and updates in place, so it cannot reach the violation the tightened index now refuses.* [#242](https://github.com/sujanto-gaws/kelir/issues/242) says plainly that this claim *"is exactly what the rehearsal tests"*.

What this rehearsal established is weaker, and the difference is worth being exact about:

- **Proven:** the index exists on the migrated schema; the `v0.4.0` binary starts, migrates and writes against that schema; and every SQL statement `v0.4.0` holds — `assign_role`'s included — still type-checks against it.
- **Not proven:** that `assign_role`, *executed* on the rolled-back binary, cannot produce two live rows for one party and role type. Driving it takes a party, a role type, a `fromDate` and a role profile through the API, and the attempt was abandoned after several wrong payload shapes rather than run to a result.

**Recorded as a gap rather than left blank**, because a blank row reads as "passed" to everyone who comes later — §6's own warning, and the reason `v0.2.0` shipped unrollable.

**It does not block the tag.** The failure mode it guards against is a *pre-existing* duplicate: the migration refuses to apply at all where two live rows already exist, naming every offending pair, and no released binary can have written one. What is untested is the narrower question of whether a rolled-back `v0.4.0` could create one afterwards. **The cheapest way to close it is not more curl**: run `v0.4.0`'s own `master_data_party_roles` suite — 39 tests, `assign_role` exercised exhaustively — against a `v0.5.0`-migrated database. That needs the harness to accept a pre-migrated database rather than provisioning its own, which it does not today.
