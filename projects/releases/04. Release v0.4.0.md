> **The rehearsal ran at the sprint close, not at its entry.** Sprint 9's entry criteria and the [Sprint 8 retrospective](../retrospectives/06.%20Sprint%208%20Retrospective.md) both asked for it before construction started. It is recorded here as a deviation rather than left to be noticed, and the [Sprint 9 retrospective](../retrospectives/07.%20Sprint%209%20Retrospective.md) root-causes it: an entry criterion whose output nothing downstream consumes is advisory, and sequencing is what makes it binding.

### The rollback rehearsal

The `v0.3.0` backend image knows migrations `0001`–`0013`. It was started against the database `v0.4.0` had just migrated to `0023`.

| Check | Result |
|---|---|
| `kelir-backend:0.3.0` starts against a `0023` schema | **Yes.** `set_ignore_missing` (the #76 fix) tolerates the ten versions it has never heard of |
| `/health/ready` | `{"status":"ok","database":"up"}` |
| `/version` | `{"version":"0.3.0","commit":"1c08902"}` — the older image, confirming the swap actually happened |
| Sign-in on the rolled-back binary | **200**, with an access token. Readiness alone would not have shown that the schema is still *usable*, only that it is reachable |
| `GET /api/v1/documents` on the rolled-back binary | **404** — the document surface is correctly absent from `v0.3.0`, which is what a rollback means |
| `_sqlx_migrations` after the rollback | **23 of 23 successful, unchanged.** A rollback does not un-apply; it tolerates |
| Roll forward to `0.4.0` | `/version` reports `0.4.0` again; `/api/v1/documents` answers **401** rather than 404, so the route is back |

**Why it passed without being fixed first**, unlike `v0.2.0`'s: `0023` alters no existing column. Every migration between `0014` and `0023` creates tables `v0.3.0` never saw, so there is nothing for the older binary to be wrong about. The one that *moved* data — `0020`, taking `next_sequence` off the rule row — moved it within a table group that arrived in `0015`, after `v0.3.0`'s last migration.

### What performing it found

- **The harness needs `KELIR_E2E_USERNAME` when the bootstrap administrator is not called `admin`.** Six flows failed with `sign-in failed for "admin": 401` before that was passed. Not a product defect and not a harness defect — a documentation gap in [`e2e/README.md`](../../e2e/README.md), which shows `KELIR_E2E_PASSWORD` and not the username beside it. Worth a line the next time that file is touched.
- **`deploy/staging/.env` needs `KELIR_BOOTSTRAP_ADMIN_USERNAME` and `KELIR_BOOTSTRAP_ADMIN_EMAIL`**, and `deploy.sh`'s required-variable check does not list them — it checks four and the backend needs six, so the failure surfaces as a container restarting rather than as the script saying which value is missing. The `v0.3.0` rehearsal did not meet this because its `.env` predated the bootstrap variables. **Filed as a finding of this rehearsal**, below.
- **The staging stack expects an external PostgreSQL** and the compose file has no database service, which the `v0.3.0` record did not have to state because that rehearsal ran where one already existed. Named here so the next rehearsal starts one first.

### The release-blocking finding, proven fixed in the shipped artefact

Record 06's **F2** is the reason `v0.4.0` could not be tagged on `main` until PR #220 merged. It was measured again here, against the released image rather than a working tree — twenty-four concurrent submits of a rule whose gap policy is `ALLOW_GAPS`, which is the exact shape that answered `500` after the acquire timeout before the fix:

| Check | Result |
|---|---|
| 24 concurrent submits | **24 × `200`.** None timed out, none deadlocked |
| Distinct numbers | **24 of 24** |
| Documents submitted without a number | **0** |

A green browser flow would not have shown this: the harness submits one document at a time, and the defect only exists at a concurrency the connection pool cannot absorb.

### How the tag came to be cut, and what held it up

**`v0.4.0` sat unreleasable for the length of a working session, and the reason was not the code.**

The construction merged as [PR #219](https://github.com/sujanto-gaws/kelir/pull/219) while the closing verification pass was still running. That pass then found **F2** — a submit holding two pooled connections and self-deadlocking — which is release-blocking, so the fix, the release commit and the sprint's closing documents went onto [PR #220](https://github.com/sujanto-gaws/kelir/pull/220). **`main` therefore carried the document surface without the fix for its own release-blocking defect**, and a tag cut in that window would have shipped it.

Neither pull request could be merged from the working session. `gh pr ready 219` and `gh pr merge 220 --squash` both answer `Resource not accessible by personal access token`; both were merged by hand. **That is the eighth occurrence of the pull-request permission item**, carried in every retrospective since Sprints 2–4, and this release is the first time it has delayed a tag rather than merely a merge.

**The order it was finally done in**, which is the order release process §4 prescribes and is worth recording because the middle step is the one a reader skips:

1. PR #219 merged, then PR #220 merged — `7401094` on `main`.
2. **CI verified green on `7401094` before the tag was cut**, not after. "Backend (Rust)", "Frontend (Vue)" and "End-to-end (browser)" all `success`; "Commit messages" `skipped`, because that job runs only on pull requests and had passed on both.
3. `git tag -a v0.4.0 7401094`, message = the `[0.4.0]` changelog section verbatim, `--cleanup=verbatim` so its markdown survives intact.
4. **Both images rebuilt from a checkout of the tag**, replacing the rehearsal artefacts, so `KELIR_BUILD_SHA` is the tagged commit.
5. Smoke pass and the browser harness re-run against those images, on a fresh database — above.

**Step 4 is not a formality.** The rehearsal images were built from the release branch before it was squash-merged, and that commit does not exist in the history any more. `/version` reporting `7401094` is what makes the smoke check a statement about the released artefact rather than about something that resembled it.

## Aftermath

**Two findings against the deployment path itself**, neither release-blocking and both filed here rather than lost:

1. **`deploy.sh`'s required-variable check is incomplete.** It asserts `KELIR_DB_PASSWORD`, `KELIR_JWT_SECRET`, `KELIR_MINIO_USER` and `KELIR_MINIO_PASSWORD`; the backend also requires `KELIR_BOOTSTRAP_ADMIN_USERNAME`, `KELIR_BOOTSTRAP_ADMIN_EMAIL` and `KELIR_BOOTSTRAP_ADMIN_PASSWORD`. A missing one surfaces as a container restart loop with the reason buried in `docker compose logs`, when the script's own design is to fail fast and say which value is absent. **The script has a list and the backend has a longer one, and nothing keeps them in step.**
2. **`e2e/README.md` shows `KELIR_E2E_PASSWORD` without `KELIR_E2E_USERNAME`**, so a stack whose bootstrap administrator is not called `admin` fails six flows on a 401 that reads like a product defect.

**What Phase 5 inherits from this release:** a document that exists and a lifecycle whose legality table already names the states a workflow will own. The seam is `documents.status` — a projection with nothing yet to project from, which is #178's.
