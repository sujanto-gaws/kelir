### The rollback rehearsal

By the procedure in [release process](../../docs/standards/04.%20Release%20Process.md) §6, which asks for the rehearsal rather than the reasoning:

1. An empty database migrated by the **`v0.3.0`** binary — thirteen rows in `_sqlx_migrations`, 32 tables.
2. The **`v0.2.0`** image (`aab2eda`, built at that release and never rebuilt) started against that database.

It started, logged `database migrations applied`, and answered `/health/ready` with `{"status":"ok","database":"up"}`. `/version` reported `0.2.0`, confirming the older binary was the one running rather than a stale container.

**Both halves of the N−1 rule hold, and the second is the one that matters here.** Six migrations — `0008` master data through `0013` master-data audit permission scope — were in `_sqlx_migrations` with no resolved definition in the `v0.2.0` binary. By default SQLx treats that as fatal. `Migrator::set_ignore_missing(true)`, added by #76 after this exact check failed at `v0.2.0`, is what let it start.

**This is the first release whose rollback worked without being fixed first.** `v0.1.0` deferred the rehearsal; `v0.2.0` ran it, failed, and fixed forward. The fix is now demonstrated rather than assumed — which is the whole reason §6 says to rehearse it.

**The last row is worth stating separately, because it is the fix this release closed latest.** An update that set only `description` produced exactly:

```json
"oldValue": {"description": null},
"newValue": {"description": "Set during the v0.3.0 release rehearsal"}
```

One field named on each side, and nothing else. Before #135 the same request would have reported `statusId` and `externalId` as cleared. That fix was verified by its tests on 2026-08-24; this verifies it in the artefact that would ship.

Two rejections were exercised incidentally and behaved: an unknown `partyTypeId` answered 422 naming the field and listing the valid variants, and a misspelled `supplierProfile` answered 422 with `UNKNOWN_FIELD` — the `deny_unknown_fields` contract #83 introduced.

### What performing it found

**Nothing.** No defect, in either the artefact or the deployment.

That is worth recording rather than leaving as a blank, because it is the first time: `v0.2.0`'s first deployment found two defects that no test could have caught, and its first rollback rehearsal found a third. The difference is not luck — all three were fixed forward, and this run is what confirms the fixes reach a release rather than a test.

The one thing this run does **not** cover is unchanged from `v0.2.0` and stated in the script itself: no TLS, because no certificate can be issued for an IP address, so NFR-SEC-010 is not exercised by the compose check. **D-9** accepted that when it replaced the staging step.

### The bounded read over PRs #141–#144: declined, 2026-08-24

**The product owner decided to tag without it.** Recorded here rather than omitted, which is what the [Sprint 6 retrospective](../retrospectives/04.%20Sprint%206%20Retrospective.md)'s first action asks for — its done-when is that this record carries *either* a verification note over those pull requests *or* the decision not to take one.

The question it answers: PRs #141–#144 close every finding of the closing verification pass ([record 03](../verifications/03.%20Sprint%206%20Surface%20Verification.md)) and carry only their own authors' verification, which sprint plan §2 reads as `In progress`. #116 is this project's precedent for why that is not a formality — it closed a real race and opened a worse one (#118) that CI never saw.

**What the release carries as a result.** The four pull requests are merged, CI-green, and exercised by the tests they added, and PR #141's locking change and PR #144's permission change were both additionally exercised end to end through the release stack during the rehearsal above — a role assignment withholding its profile, a lifecycle transition reporting both ends, and an update whose audit record names only the field that moved. That is not the same as an independent adversarial read, and this release does not claim it is. **What is untested is the failure mode #118 was: a defect that appears only at a concurrency the fix's own tests cannot reach.** #141 is a locking change, which is the class of change where that risk is highest.

The decision is defensible and is recorded so that it is a decision: nothing external depends on this date, and the alternative — a fourth verification pass before a tag on a release with no production environment — was judged not worth the delay. If a concurrency defect surfaces in Phase 4 against the facility hierarchy or the record-status transition, this paragraph is where to start.
