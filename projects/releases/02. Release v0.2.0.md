### The rollback rehearsal, and what it found

Done properly for the first time: an empty database migrated by the `v0.2.0` binary — seven rows in `_sqlx_migrations` — then booted with the `v0.1.0` binary built from the tag.

It refused to start:

```text
ERROR kelir_backend: kelir backend failed to start
  error=migration 2 was previously applied but is missing in the resolved migrations
```

**The schema is N−1 compatible; the bookkeeping is not.** Every change this release makes is additive — new tables, and `users.locked_until` as a nullable column — and the `v0.1.0` source *compiles* against the `v0.2.0` schema, which means every SQLx query it holds still type-checks against the migrated database. What blocks the rollback is `sqlx::Migrator`, which treats applied migrations it cannot resolve as fatal.

[Release process](../../docs/standards/04.%20Release%20Process.md) §6 states the N−1 rule in terms of columns — "add columns as nullable or with defaults; don't drop or rename" — and this release obeys every word of it. The rule did not anticipate the migrator, so a release can satisfy the rule as written and still be unrollable. That is a gap in the standard as much as in the code.

**Recovery, if `v0.2.0` has to be rolled back:** delete the rows above the old version's highest migration from `_sqlx_migrations`, then start the old image. The tables and columns those migrations created stay — they are unused by `v0.1.0`, and dropping them would lose data on the way forward again.

**Fixed, in this release.** `Migrator::set_ignore_missing(true)` on the startup migrator, so a rolled-back binary tolerates a database migrated by a newer release (#76). Two integration tests hold both halves of the trade: a database carrying a migration from a newer release still starts, and an *edited* migration is still refused by checksum — tolerating unknown versions is not a licence to change one that has already run.

**It cannot rescue this release's own rollback.** `v0.1.0` is tagged without the flag, so `v0.2.0 → v0.1.0` still needs the manual step above. What the fix buys is `v0.3.0 → v0.2.0`, and every rollback after it — which is why it landed here rather than in the next phase.
