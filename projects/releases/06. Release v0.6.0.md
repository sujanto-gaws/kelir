## The rollback rehearsal

**[Release process](../../docs/standards/04.%20Release%20Process.md) §6, run on 2026-09-03.** The `v0.5.0` backend knows migrations `0001`–`0030`. It was started against a database the v0.6.0 migrator had just taken to `0039`.

| Check | Result |
|---|---|
| v0.6.0 migrates an empty database | **39 of 39 applied**, highest version 39 |
| `v0.5.0` binary starts against a `0039` schema | **Yes**, `/health/ready` **200 in 1 second**. `set_ignore_missing` (the [#76](https://github.com/sujanto-gaws/kelir/issues/76) fix) tolerates the nine versions it has never heard of. This is the bookkeeping half |
| `/health`, `/health/ready`, `/health/live` | **200, 200, 200** |
| `/version` on the rolled-back binary | `{"version":"0.5.0","commit":"c91433a",…}` — the tag's own commit |
| `_sqlx_migrations` after the N−1 run | Still **39 rows, all `success`**. No checksum complaint: v0.6.0 edited nothing `v0.5.0` had already applied |
| It writes, not just starts | **Yes.** Given `KELIR_BOOTSTRAP_ADMIN_*`, it created the bootstrap administrator on the `0039` schema |
| `GET /api/v1/documents` | **401** — `v0.5.0`'s own surface is present and asking for a token |
| `GET /api/v1/audit` | **404** — audit search is `0035`'s surface and correctly absent from `v0.5.0` |
| `GET /api/v1/documents/{id}/attachments` | **404** — as is the attachment surface |
| `GET /api/v1/documents/{id}/comments` | **404** — and the comment surface. That is what a rollback means |
| Startup log | Clean. One WARN, that no bootstrap administrator exists on an empty database, before the variables above were supplied |

**Why it passed, and the one migration this step existed for.** Eight of the nine are invisible to `v0.5.0`: `0032`, `0033`, `0034`, `0037` and `0038` create tables it has never heard of; `0036` alters `comments`, which `0032` created; and `0035` and `0039` carry **no DDL at all** — permission rows, notification channels and templates.

**`0031_attachment` is the only one touching a table `v0.5.0` knows**, and it adds `fk_document_type_attachment_rules_category_id` to `document_type_attachment_rules`, which `0015_document` created in Sprint 9. Close plan §5 argued the exposure was smaller than it looks. **That argument is now checked rather than repeated:**

| The claim | What was measured |
|---|---|
| `v0.5.0`'s source references `document_type_attachment_rules` nowhere | `git grep document_type_attachment_rules v0.5.0 -- kelir-backend/src` returns **nothing** |
| So no release has ever written a row into it | The migrated table holds **0 rows** |
| So the constraint can reject nothing | It exists on the schema (`contype = 'f'`) and the `v0.5.0` binary starts, migrates and **writes** against that schema |

**A constraint can only reject rows that exist.** There are none, and no released binary contains the code that would make one.

### What was not rehearsed

**§6's optional third step — the compiled check — was not run.** The step reads *"if it is a compiled check you want as well: the previous release's source compiling against the migrated database proves every query it holds still type-checks."* [Record 05](05.%20Release%20v0.5.0.md) ran it for `v0.4.0` and called it the schema half proven by the compiler.

It is **not run here**, and this row says so rather than being left blank — §6's own warning, and the reason `v0.2.0` shipped unrollable. What stands in its place is weaker and worth being exact about:

- **Proven:** the `v0.5.0` binary starts, migrates, writes and serves its own surface against a `0039` schema; the Phase 6 surfaces are absent from it; and the one migration touching a table it knows constrains a table its source never names and no release has written to.
- **Not proven by a compiler:** that every SQL statement `v0.5.0` holds still type-checks against the `0039` schema. The evidence above is behavioural rather than exhaustive.

**It does not block the tag**, on the same reasoning the table above sets out: the only schema change reaching `v0.5.0`'s world is a foreign key on an empty table its source does not mention. **The cheapest way to close it** is `cargo build --release` with `SQLX_OFFLINE=false` at tag `v0.5.0` against a `0039` database — the procedure [record 05](05.%20Release%20v0.5.0.md) used, which needs a full Rust build this session did not run.

## The decision this record cannot take

> **Sprint plan §2 has no owner and no date, and the [Sprint 13 retrospective](../retrospectives/11.%20Sprint%2013%20Retrospective.md)'s first action falls due at this tag.** It is the fifth sprint the question has been open.

**The pass ran, and the rule still did not fire.** [Record 13](../verifications/13.%20Sprint%2013%20Independent%20Pass.md) exists because the product owner directed a pass after the sprint had closed — not because §2 named anybody, and not on a date §2 set. A control that needs an instruction each time it fires is a practice, not a control.

The action's own terms: **if neither branch is taken by the tag, the second is taken by default** — §2 says what a self-pass is worth, `author-verified` becomes the expected label, and this record says what the tag rests on. **Open as of 2026-09-04.** Close plan §8's rule is that taking the default silently is the sixth restatement of the question, so it is recorded here as a choice still to be made rather than as one already made by omission.
