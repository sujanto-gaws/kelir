**Why it passed, and the one migration this step existed for.** Eight of the nine are invisible to `v0.5.0`: `0032`, `0033`, `0034`, `0037` and `0038` create tables it has never heard of; `0036` alters `comments`, which `0032` created; and `0035` and `0039` carry **no DDL at all** — permission rows, notification channels and templates.

**`0031_attachment` is the only one touching a table `v0.5.0` knows**, and it adds `fk_document_type_attachment_rules_category_id` to `document_type_attachment_rules`, which `0015_document` created in Sprint 9. Close plan §5 argued the exposure was smaller than it looks. **That argument is now checked rather than repeated:**

| The claim | What was measured |
|---|---|
| `v0.5.0`'s source references `document_type_attachment_rules` nowhere | `git grep document_type_attachment_rules v0.5.0 -- kelir-backend/src` returns **nothing** |
| So no release has ever written a row into it | The migrated table holds **0 rows** |
| So the constraint can reject nothing | It exists on the schema (`contype = 'f'`) and the `v0.5.0` binary starts, migrates and **writes** against that schema |

**A constraint can only reject rows that exist.** There are none, and no released binary contains the code that would make one.

### What was not rehearsed

**§6's optional third step — the compiled check — was not run.** The step reads *"if it is a compiled check you want as well: the previous release's source compiling against the migrated database proves every query it holds still type-checks."* [Record 05](05.%20Release%20v0.5.0.md) ran it for `v0.4.0` and called it the schema half proven by the compiler.

It is **not run here**, and this row says so rather than being left blank — §6's own warning, and the reason `v0.2.0` shipped unrollable. What stands in its place is weaker and worth being exact about:

- **Proven:** the `v0.5.0` binary starts, migrates, writes and serves its own surface against a `0039` schema; the Phase 6 surfaces are absent from it; and the one migration touching a table it knows constrains a table its source never names and no release has written to.
- **Not proven by a compiler:** that every SQL statement `v0.5.0` holds still type-checks against the `0039` schema. The evidence above is behavioural rather than exhaustive.

**It does not block the tag**, on the same reasoning the table above sets out: the only schema change reaching `v0.5.0`'s world is a foreign key on an empty table its source does not mention. **The cheapest way to close it** is `cargo build --release` with `SQLX_OFFLINE=false` at tag `v0.5.0` against a `0039` database — the procedure [record 05](05.%20Release%20v0.5.0.md) used, which needs a full Rust build this session did not run.

### Two ways this deployment differed from a real one, stated rather than buried

- **Port 8090 rather than 8080**, because an unrelated container on this host holds 8080. Only the address differs, which is `deploy-local.sh`'s own stated design.

> **Sprint plan §2 was settled on 2026-09-04, before the tag, and this is the record naming what the tag rests on.**

**The first branch was taken, not the default.** The [Sprint 13 retrospective](../retrospectives/11.%20Sprint%2013%20Retrospective.md)'s first action offered two: an owner and a date in §2, or the `author-verified` label. §2 now carries the first — **the project manager dispatches the independent pass at mid-sprint refinement, and the reader is any session appearing in no construction commit trailer in the sprint's range.**

## Aftermath

- **Issues found post-release:** none. Two defects in the *release machinery* were found while running it, and both are filed below rather than fixed here — the tag was already proven by then, and changing the deploy path after verifying it would falsify the verification.
- **Follow-ups filed:**
  - **`deploy-local.sh` exited 0 on a run where Caddy never started.** The first attempt failed with `Bind for 0.0.0.0:8080 failed: port is already allocated`; the backend, MinIO, ClamAV and Mailpit all came up and **the stack had no ingress at all**, yet the script reported success. This is the [Sprint 13 retrospective](../retrospectives/11.%20Sprint%2013%20Retrospective.md)'s fifth action one layer up: a one-shot container's postcondition is now observed, and the deploy script's own compose failure is not. A deployment that cannot be reached should not exit 0.
  - **A frontend image has no version identity.** `kelir-frontend:0.6.0`'s served bundle is **byte-identical** to `0.6.0-rc`'s — 45 files, same hash — because the version bump never reaches the built assets. Docker therefore gave the new image the rc's creation timestamp. The backend has `/version` reporting both version and SHA; the frontend has no equivalent, so **you cannot tell which release a frontend image is from by inspecting it**. For a process whose stated point is that what ships is what was verified, that holds for one artefact of the two.
  - **`Pull-request title` is not among `main`'s required checks.** The check moved out of the `Commit messages` job in [#330](https://github.com/sujanto-gaws/kelir/pull/330) (**D-65**), and branch protection required it *through* that job. Until the new context is added, a title violation no longer blocks a merge — **D-38**'s original problem, by another route.
  - [#322](https://github.com/sujanto-gaws/kelir/issues/322), [#323](https://github.com/sujanto-gaws/kelir/issues/323), [#324](https://github.com/sujanto-gaws/kelir/issues/324) — Sprint 14's allowance; [record 13](../verifications/13.%20Sprint%2013%20Independent%20Pass.md) §7 says why none blocks the tag.
  - [#301](https://github.com/sujanto-gaws/kelir/issues/301) — dropping `activity:read`, which the §6 N−1 rule puts **after** this tag.
  - [#274](https://github.com/sujanto-gaws/kelir/issues/274) — unscheduled and still unreproduced; its first criterion is now satisfiable because the harness captures the log.
  - **Logout and the roles screen have no browser coverage** — [record 14](../verifications/14.%20MVP%20Verification.md) §6 finding 2, carried to Sprint 14.
