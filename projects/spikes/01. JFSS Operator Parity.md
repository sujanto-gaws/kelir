# JFSS Operator Parity — Spike Finding

**Status:** Final · **Last updated:** 2026-08-21

**Issue:** [#31](https://github.com/sujanto-gaws/kelir/issues/31) · **Sprint 5, item 5** · Time-boxed spike: the output is a finding and a recommendation, **not a merged engine**.

**Why now:** decision **D-2** moved the JFSS renderer and the RAD storage layer into Phase 4 (Sprints 7–8). This is Phase 4's entry criterion and has to resolve **before Sprint 7 planning**, or an unverified library assumption sits on the Phase 4 critical path.

**Evidence:** [`spikes/jfss-operator-parity/`](../../spikes/jfss-operator-parity/) — 51 expressions, four evaluators, re-runnable with `./run.sh`. Every number below comes from that harness; nothing here is asserted from documentation.

---

## Summary

**The registry's Rust column is not merely unverified — it names a crate that does not exist, and the crate it turns out to mean is unusable for this purpose.** `json-logic-rs` is a GitHub repository, not a package; it publishes to crates.io as `jsonlogic-rs`. That crate does not reject unknown operators — it returns them — so the registry's own §6.1 invoice pattern silently persists a grand total of **0 instead of 42**, with no error anywhere in the Tamper-Proof Pattern. It also has no custom-operator API, so `sum`, which §3.2 requires in all three environments, cannot be registered at all.

**A working candidate exists, and it does better than parity-by-test.** `datalogic-rs` 5.2.0 ships an official WebAssembly build of the same core, and the two agree on **51/51 cases including the error cases** — parity by construction rather than by CI. Against `json-logic-js` it agrees on 44/51 raw and 46/51 after the mandated normalization wrapper; all five residual divergences are cases where `json-logic-js` produces `NaN` or `Infinity`, not cases where Rust computes something wrong.

**Three registry defects surfaced along the way, and all three are the registry's own text rather than any library's behaviour.** The §7.3 wrapper every environment is told to replicate does not implement the §3.1 rule it is cited for; the "result is 0" rule is ambiguous in a way that makes the two readings disagree on `+` while agreeing on the `*` the registry uses as its worked example; and `conditional.logic` — which needs exactly the operators §2.3 forbids — is governed by no registry at all.

**No operator in the approved set is unimplementable in Rust.** The gaps are in the normalization rules and in the registry's text, not in operator coverage. Sprint 7 can plan the renderer on that basis, subject to the evaluator decision raised as **D-10**.

## 1. What was measured

`cases.json` holds 51 expressions, each derived from a claim the [Calculation Rule Registry](../../docs/schema/JFSS%20Calculation%20Rule%20Registry.md) or [JFSS](../../docs/schema/JSON%20Form%20Schema.md) makes:

|---|---:|---|

| Extended and unknown | 4 | Registry §3.2 `sum`, §6.1 invoice pattern, JFSS S8.1.1 unknown-operator rejection |
| Conditional | 14 | JFSS §7.1 — the operators §2.3 forbids in `calculate` and conditionals require |

Run through four evaluators, with `sum` registered as a custom operator wherever the library allows it, because §3.2 requires exactly that:

| `datalogic-rs` | 5.2.0 | stock, and configured to the registry's mandated normalizations |

All 11 base cases, all 11 array cases and all 14 conditional cases agree across every evaluator. **Every divergence in the whole corpus is either an unknown-operator case or a null/zero arithmetic case.**

## 2. Findings

### 2.1 The crate the registry names does not exist

`json-logic-rs` is not on crates.io. The registry cites it in every row of its Rust column and in §4.3. The repository `bestowinc/json-logic-rs` publishes as **`jsonlogic-rs`**, which is what was tested.

This is worth stating plainly because of what it implies: the ✅ marks in the Rust column were never checked against anything. A developer following §1.1's instruction to "ensure the operator is supported by the Rust JSON Logic library" would have found this in the first five minutes.

### 2.2 `jsonlogic-rs` does not reject unknown operators — it returns them

JFSS **S8.1.1** is unambiguous: *"If the backend encounters an unknown custom operator, it MUST reject the payload with `400 Bad Request`."*

```text
{"mapp":[[1,2],{"var":""}]}  ->  Ok(Object {"mapp": ...})
{"sum":[[1,2]]}              ->  Ok(Object {"sum": ...})
```

`Ok`, not `Err`. An unregistered operator — a typo, a `sum` the crate cannot register, a `generateInvoiceId` — is treated as a literal object and handed back.

Driving the registry's own §6.1 invoice pattern through the Tamper-Proof Pattern with a tampered payload:

```text
recalculated  = {"sum":[{"map":[{"var":"items"}, ...]}]}
was an error  = false  (there is nothing to reject on)
after wrapper = 0
persisted     = {"grand_total":0.0}
true total    = 42
```

The pattern inverts. The backend overwrites a correct value with a wrong one, and the §7.3 wrapper is what launders the un-evaluated expression into a plausible `0`. Nothing logs, nothing returns 400, and the stored figure is wrong in the direction of "free".

`jsonlogic-rs` also has **no custom-operator registration API** — its operator table is a compile-time static map. §4.3's Rust sample is already marked illustrative pseudocode; the finding is stronger than that caveat, because there is no real API for it to be an illustration *of*. The crate does offer a JSON-level `def`/`param` function mechanism, which `json-logic-js` does not have, so using it would break parity rather than restore it.

> **Decision: remove `jsonlogic-rs` from the registry. It is not a candidate.**

### 2.3 The §7.3 wrapper does not do what §3.1 says it does

Registry §3.1: *"If the denominator is `0`, the result is `0`… Every environment must apply a normalization wrapper."* §7.3 gives that wrapper as `Number(result) || 0`.

```text
10 / 0   -> Infinity    Number(x)||0 = Infinity    JSON.stringify = null
null * 5 -> NaN         Number(x)||0 = 0           JSON.stringify = 0
-1 / 0   -> -Infinity   Number(x)||0 = -Infinity   JSON.stringify = null
```

It normalizes `NaN`, which is falsy. It does **not** normalize `Infinity`, which is truthy. Division by zero is therefore not normalized on the frontend today: the field renders `Infinity`, and `JSON.stringify` turns it into `null` on submission — so the backend receives `null` for a field the frontend displayed as a number, and the two "agree" only because neither is right.

> **Decision: correct the wrapper to a finiteness test — `Number.isFinite(n) ? n : 0` — in the registry, and require the same predicate in every environment.**

### 2.4 "Result is 0" is ambiguous, and the two readings disagree

Does a null operand become `0`, or does the whole expression become `0`? The registry never says, and the difference is visible:

| Expression | `json-logic-js` | `datalogic-rs` (tuned) | After the wrapper |
|---|---|---|---|
| `{"*": [null, 5]}` | `NaN` | `0` | 0 vs **0** — agree |
| `{"+": [null, 5]}` | `NaN` | `5` | 0 vs **5** — differ |
| `{"-": [100, null]}` | `100` | `100` | agree |

`json-logic-js` takes the whole-expression reading for `+` and `*` and the operand reading for `-`; it is not self-consistent. The registry's only worked example uses `*`, where both readings give `0`, which is why this has never surfaced.

The operand reading is the one a partially typed form means — a blank quantity is zero of something, not an invalid document — and it is the only reading that composes, because `{"+": [null, 5]}` returning `0` discards a value the user did enter.

> **Decision: the registry must state the operand reading normatively, with `+`, `-`, `*`, `/` worked examples rather than one `*`.**

### 2.5 `min`/`max` with a missing operand is a trap in the rule itself

The §6.2 discount cap, `{"min": [computed, 100]}`, returns **0** under `json-logic-js` when the first operand is missing — `Math.min(null, 100)` is `0`. That satisfies the letter of "result is 0" and is a wrong business answer: the cap becomes zero, not the discount. `datalogic-rs` errors instead, which is at least loud.

This is not a language-parity defect — it is the mandated rule producing a wrong number. It belongs with the renderer's dependency-graph work (JFSS S12.2, already required for cycle detection): a calculation whose inputs are absent should not be evaluated at all.

> **Decision: substitute — do not evaluate a calculation with absent inputs. Record against the Sprint 7 renderer item, not against the evaluator choice.**

### 2.6 `conditional.logic` is governed by no registry

JFSS §7.1 admits *"a valid JSON Logic expression evaluating to a boolean"* for `conditional.logic`. The Calculation Rule Registry governs only `calculate`, and §2.3 **forbids** `==`, `!=`, `>`, `<`, `and`, `or`, `!`, `if`, `in` and `cat` there — which is precisely the set conditionals need.

So the operator surface the backend must implement is strictly larger than the matrix, and nothing bounds it. All 14 conditional cases agree across every evaluator today, so this is a documentation gap rather than a live defect — but §1.1's "binding architectural commitment" and §8.1's "if it is not in this registry it is FORBIDDEN" do not currently reach the half of JFSS the backend also has to re-evaluate (S10.2 requires conditionals re-evaluated server-side before persistence).

> **Decision: the registry needs a conditional tier, or a companion registry. Sprint 7 scope, ahead of the renderer.**

### 2.7 The `regex` validation rule cannot be honoured as specified

The [Validation Rule Registry](../../docs/schema/JFSS%20Validation%20Rule%20Registry.md) `regex` rule has `scope: "both"` and a params schema of *"ECMA 262 regex"*. Both sides evaluate it; they disagree.

| Pattern | ECMA-262 | Rust `regex` 1.x |
|---|---|---|
| `^[A-Z]{3}-\d{4}$` | matches | matches |
| `(?i)^abc$` | matches | matches |
| `^(?=.*[A-Z])(?=.*\d).{8,}$` — password complexity | matches | **refuses to compile** |
| `^(\w+)-\1$` — backreference | matches | **refuses to compile** |
| `^\d+$` against `٣٤٥` | **false** | **true** |
| `^a$` against `"a\n"` | false | false |

The first failure is loud and common — lookahead is how nearly every password-complexity pattern is written, and the Rust `regex` crate rejects lookahead and backreferences by design.

The second is worse because it is **silent**: ECMA-262 `\d` is ASCII-only, Rust's `\d` is Unicode `Nd`. A `^\d+$` rule rejects Arabic-Indic digits in the browser and accepts them on the server, with no error on either side. For a rule scoped `both`, that is the frontend and the backend reaching opposite verdicts on the same input.

> **Decision: constrain the params schema to a cross-compatible subset and validate it when the schema is saved, or adopt a backtracking engine (`fancy-regex`) on the backend and accept that `\d` still needs an explicit ASCII pin. Neither is free; the current text promises something no Rust backend delivers.**

### 2.8 The Go column has no backend behind it

Every row of the matrix carries a Go column, and §4.1 and §4.2 carry Go implementations. Kelir's backend is Rust; the SDD and architecture 01 name no Go service, and none is planned.

Maintaining a parity claim for a language nobody compiles is how the Rust column came to be wrong — three columns of ticks, none of them checked, and no build that would have failed.

> **Decision: product-owner question, raised as part of D-10. Either drop the Go column or state what it is for.**

## 3. The candidate, and what adopting it costs

`datalogic-rs` 5.2.0 (Apache-2.0) is actively maintained — 5.0.1 to 5.2.0 in the six weeks to 2026-08-19 — and covers every operator the registry approves except `sum`, which needs a custom operator exactly as §3.2 says. It rejects unknown operators with an `InvalidOperator` error, satisfying S8.1.1. Its `EvaluationConfig` expresses the registry's mandated normalizations as configuration — NaN handling, division by zero, truthiness, null-to-zero coercion — rather than as a wrapper each environment hand-writes and gets subtly different.

**What makes it more than "a working Rust library":** `@goplasmatic/datalogic-wasm` is the same core compiled to WebAssembly, published to npm within a minute of the crate, with the same `customOperators` and `config` surface. Running the corpus through both gave **51/51 identical results, error cases included**, with `sum` written independently in Rust and in JavaScript. That converts the Polyglot Parity Problem from something CI chases into something the build guarantees.

It also answers §3.3 cleanly. A `calculateMode: "generated"` operator registered on the server engine and not on the client engine is refused by the client outright:

```text
client refused it: Invalid operator: generateInvoiceId (in operator: generateInvoiceId)
```

That is S3.3 rule 2 — *"They are server-side only. The client MUST NOT evaluate them"* — enforced by the engine rather than by convention.

**The costs, stated plainly:**

- **Bundle size.** 2.83 MB of WebAssembly, **588 KB gzipped**, against 14.8 KB / 4.1 KB for `json-logic-js`. That is a real first-load regression. It is lazy-loadable — only form pages need an evaluator — and NFR-PERF-001 baselines view latency rather than bundle weight, so nothing is formally breached. It should still be a deliberate choice, not a side effect of this recommendation.
- **Version churn.** Major versions move fast. The `CustomOperator` trait is documented as stable for the 5.x series; the crate and the npm package must be pinned to the **same exact version**, and any bump treated as a parity-affecting change that re-runs this corpus.
- **A larger surface than the registry governs.** `datalogic-rs` normalizes `var` to a canonical `val`, and carries `datetime`, `ext-string`, `ext-array`, `ext-math` and `flagd` operator families behind feature flags. The registry's "not in this registry, therefore FORBIDDEN" rule is what keeps that from leaking into schemas, and it has to keep being enforced when a schema is saved.
- **Licence.** Apache-2.0, against MIT for `json-logic-js`.

**The fallback, if the bundle cost is refused:** keep `json-logic-js` on the client and take `datalogic-rs` on the server, correct the normalization spec per §2.3 and §2.4 above, implement it identically on both sides, and promote this corpus into the CI parity gate §2.1 already assumes. It is strictly weaker — it makes parity a property tests chase rather than a property that holds — and the five known divergences stay, each needing a wrapper to paper over it.

## 4. What Sprint 7 can rely on

- Every operator in registry §2.1 is natively supported by `datalogic-rs`, and the five that §2.1 flags for CI verification (`map`, `filter`, `reduce`, `all`, `some`) — plus `none` — agree with `json-logic-js` on all 11 array cases, empty arrays and missing arrays included.
- `sum` is a custom operator in every environment, as §3.2 says, and is about ten lines on each side.
- The conditional operator set works today across all four evaluators; it needs documenting, not building.
- **No approved operator is unimplementable in Rust.** Renderer planning does not need to route around a missing operator.
- What renderer planning *does* need to carry: the corrected normalization spec (§2.3, §2.4), the absent-input rule (§2.5), a conditional tier for the registry (§2.6), and the `regex` params constraint (§2.7).

## 5. What this spike did not check

- **Browser execution.** The WASM package ships `bundler/`, `web/` and `nodejs/` targets; only `nodejs/` was run. A Vite integration check is the first Sprint 7 task, and the bundle-size figures above are the uncompressed and gzipped artefacts, not a measured page load.
- **Performance** under a datagrid of realistic row count. No conclusion is offered on evaluation cost.
- **The `datetime`, `ext-*` and `flagd` operator families** — outside the registry's approved set.
- **The Go implementations** in §4.1 and §4.2 — see §2.8.
- **The `unique`, `exists` and `authorized` server-scope validation rules**, which are database queries rather than expression evaluation and carry no parity risk.
- **Whether the frontend's cycle-detection work (JFSS S12.2) is affected by the engine choice.** It reads `{"var": …}` references out of the schema rather than evaluating anything, so it should not be — untested.
