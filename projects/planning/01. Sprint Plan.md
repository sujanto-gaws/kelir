# Kelir Sprint Plan

**Status:** Living · **Last updated:** 2026-08-26

This plan maps the Development Roadmap (System Design Document §14, Phases 1–9) onto a sprint cadence. It is **scope-sequenced, not date-committed**: sprint contents are the commitment, calendar dates shift with measured velocity. Re-baseline after Sprint 2 and at every phase boundary.

Related documents: requirements and FR IDs in [srs.md](../../docs/requirements/srs.md); system design in the [SDD](../../docs/design/01.%20System%20Design%20Document.md); engineering rules in [docs/standards/](../../docs/standards/); release mechanics in [04. Release Process.md](../../docs/standards/04.%20Release%20Process.md). The FR-level scope inventory behind this sequence is the [Product Backlog](02.%20Product%20Backlog.md) — it maps every requirement to an epic and a sprint, and records the open scope decisions this plan depends on.

## 2. Cadence and Definition of Done

- Ceremonies: planning (first day), demo + review (last day), retro (last day, 30 min). Backlog refinement mid-sprint.
- A backlog item is **Done** when: code merged to `main` per the [git workflow](../../docs/standards/05.%20Git%20Workflow.md); tests per [coding standard](../../docs/standards/01.%20Coding%20Standard.md) §2.9/§3.5 pass in CI, and any security-control or contract test among them has been seen to fail against a reintroduced defect (§2.9); API changes reflected in OpenAPI; audit/permission checks in place; demoable from the Docker Compose stack built from release images.
- **The environment clause names Docker Compose because that is the environment this project has** (decision **D-9**, 2026-08-21). It read "demoable from a staging deploy" and was waived four sprints running, twice with an expiry that was extended rather than met — `kelir-staging-01` was never provisioned and no infrastructure is available to host it. The replacement keeps the property the clause was protecting: what is demonstrated is built the way a release is built, from release images, not run out of a working tree. It is also meetable, which the previous wording was not, so a waiver stops being the normal case. Staging is unscheduled rather than abandoned — [`deploy/staging/`](../../deploy/staging/) keeps its definition and says plainly that nothing runs it.
- **An item whose author is also its only verifier is `In progress`, not Done** ([Sprint 5 retrospective](../retrospectives/03.%20Sprint%205%20Retrospective.md), 2026-08-21). Sprint 5 met the previous wording — every Done row cited evidence — while for two of its seven items the evidence was twenty mutation runs designed by the agent that had written the code. Mutation runs are strong evidence of what the tests catch and no evidence of what nobody thought to test. The independent pass fired in Sprint 4 only because that sprint's work was under suspicion; naming it here is what stops it from depending on somebody already being worried.
- **A finding's fix carries the same rule as an item: fixed and verified by one author is `author-verified`, and the next independent pass reads it** ([Sprint 8 retrospective](../retrospectives/06.%20Sprint%208%20Retrospective.md), third action). §2 has always said this about a backlog item and said nothing about the four-line change that closes a security finding — so Sprint 8 closed an audit hash format, a mail path, a tenant-scope assertion and four repository predicates on their author's evidence alone. Each named its mutation and each was seen red, which is what [coding standard](../../docs/standards/01.%20Coding%20Standard.md) §2.9 requires and is not the same as a second reader. The status report labels such a row, and the next verification record reads what the labels point at.
- **A mutation campaign over the sprint's own new predicates runs once per sprint, and its red/green ratio is a number in the status report** ([#206](https://github.com/sujanto-gaws/kelir/issues/206), from the [Sprint 7 retrospective](../retrospectives/05.%20Sprint%207%20Retrospective.md)'s third action). It runs with the independent pass — the mid-sprint one where a finding can still be closed — and reports one line: *N mutations over predicates this sprint added, M red*. It replaces the rule that asked each pull request to state its own predicates, which existed for two sprints, produced no artefact either time, and was retired for it. The measurement is the artefact: record 03 was 65% red over the Sprint 6 surface and record 04 was 37% over Sprint 7's, and a ratio that falls says the sprint is writing guards that nothing holds while the guards are still cheap to hold. The rule the campaign enforces is [coding standard](../../docs/standards/01.%20Coding%20Standard.md) §2.5 and §2.9.
- Every sprint ends demoable; every **phase** ends with a tagged release (§4).

## 6. Sprint Outline — Later Phases (Sprints 12–21)

Detail these at the preceding phase boundary; current outline:

Planned migrations are named by what they create rather than by number, for the reason §4 of the [Product Backlog](02.%20Product%20Backlog.md) gives: a number written before the migration is guessed, and this plan guessed wrong through six shifts before it stopped guessing. **The enumeration of those shifts that used to stand here is deleted** ([Sprint 7 retrospective](../retrospectives/05.%20Sprint%207%20Retrospective.md), fifth action, carried since Sprints 2–4): it was a copy of the [Database Schema](../../docs/design/02.%20Database%20Schema.md) mapping table, it went stale every time an unplanned migration landed, and maintaining it cost a commit in Sprint 7 and was wrong again by the end of Sprint 8. **The rule that replaces it**: a document in `projects/` may name a migration that *exists*, and may never state what number an **unwritten** migration will take. That number is the mapping table's alone — sqlx applies migrations in version order, so a later phase cannot reclaim a lower number, and the number a migration gets is the next one free when it is written rather than one reserved for its phase ([naming convention](../../docs/standards/02.%20Naming%20Convention.md) §4.3). The two most recent shifts came from outside this plan entirely — FR-ORG-001 returning from Product Backlog §7 under **D-18**, and a defect whose answer was a constraint rather than code — which is the case the rule handles best and the one a reserved-number scheme could not handle at all: nothing schedules a defect, so nothing could have reserved it a number.

- **Sprints 7–9 (Phase 4, Document Core) — all three are now detailed in §5; the third sprint is decision D-16.** The RAD metadata migration, then the document migration — the RAD metadata tables must exist first, because `document_types.form_id` references `rad_forms` ([Database Schema](../../docs/design/02.%20Database%20Schema.md) §6.2) and migrations apply in version order. Phase 4 carries the front half of RAD (decision **D-2**): metadata tables, form/list definition storage APIs, lookup fields, and a read-only JFSS renderer (FR-RAD-001, 002, 003, 005, 007, 008, 010) — MVP criteria 4 and 5 need a form to render, not just tables.
