# Kelir Sprint Plan

**Status:** Living · **Last updated:** 2026-08-20

This plan maps the Development Roadmap (System Design Document §14, Phases 1–9) onto a sprint cadence. It is **scope-sequenced, not date-committed**: sprint contents are the commitment, calendar dates shift with measured velocity. Re-baseline after Sprint 2 and at every phase boundary.

Related documents: requirements and FR IDs in [srs.md](../../docs/requirements/srs.md); system design in the [SDD](../../docs/design/01.%20System%20Design%20Document.md); engineering rules in [docs/standards/](../../docs/standards/); release mechanics in [04. Release Process.md](../../docs/standards/04.%20Release%20Process.md). The FR-level scope inventory behind this sequence is the [Product Backlog](02.%20Product%20Backlog.md) — it maps every requirement to an epic and a sprint, and records the open scope decisions this plan depends on.

## 2. Cadence and Definition of Done

- Ceremonies: planning (first day), demo + review (last day), retro (last day, 30 min). Backlog refinement mid-sprint.
- A backlog item is **Done** when: code merged to `main` per the [git workflow](../../docs/standards/05.%20Git%20Workflow.md); tests per [coding standard](../../docs/standards/01.%20Coding%20Standard.md) §2.9/§3.5 pass in CI; API changes reflected in OpenAPI; audit/permission checks in place; demoable from a staging deploy.
- **The staging clause is under a waiver that now expires at the `v0.3.0` tag** — confirmed by the project owner on 2026-08-20, after the `v0.2.0` expiry was extended rather than met. Until then an item closes on merged, green CI and a local demo. This is the second and last extension: at `v0.3.0` the clause is either met by a staging deploy or struck from the line above, and it is not waived a third time. Standing action with a named owner in the [Sprints 2–4 retrospective](../retrospectives/02.%20Sprints%202-4%20Retrospective.md); the work is #12.
- Every sprint ends demoable; every **phase** ends with a tagged release (§4).

### Sprints 5–6 — Phase 3: Master Data (Party Model)

**Goal:** party-based master data management (FR-MDM-001..011; architecture doc 05).

#### Sprint 5 — planned 2026-08-20

**Goal:** Phase 2's exit debt is discharged, and the party model exists with parties and their roles created, read and audited through the API.

**Sequencing.** The exit block comes first, before any master-data work. The reason is sequencing rather than priority: Phase 3 adds the first module of routes on top of the identity module, and each of the four items below is a property of the platform that every new route inherits. Fixing them after master data doubles the surface each fix has to be re-verified against.

**Capacity.** Seven items, against a measured construction rate of six to seven ([Sprints 2–4 retrospective](../retrospectives/02.%20Sprints%202-4%20Retrospective.md)). The difference is budgeted for verification, not for an eighth item — Sprint 4 planned ten, built five, and spent the remainder filing twelve issues against what it had built. Findings are scope.

|---|---|---|---|---|

Posting `role_ids` for `roleIds` returns 201 with a role-less user today; a silently dropped field is a nuisance on a four-field request and a data-loss defect on a party with twenty. The fix is a sweep of every request struct, not only identity |
| 2 | Automate the eight Sprint 3 flows recorded as hand-verified | #59 | FR-AUTH-001..004 | One of the eight is automated today. The sprint that recorded the other seven as verified is the same sprint whose rate limiting later failed verification |

The documented contract — "every session for the account ends" — is not honoured: refresh tokens are revoked, access tokens live up to fifteen minutes longer. | 4 | Multi-tenant mode fails at boot, not at the login form | #67 | FR-IDM-009, decision **D-7** | D-7 keeps a deployment single-tenant, which turns #67 from a login-form feature into a guard: refuse to start with `KELIR_MULTI_TENANT=true` and say why, rather than serving a sign-in page nobody can complete |
| 5 | JFSS operator-parity spike — `json-logic` support in Rust | #31 | Phase 4 entry criterion | Must resolve before Sprint 7 planning, not during Phase 7: decision **D-2** moved the renderer into Phase 4. A spike, so its output is a written finding and a recommendation, not a merged engine |

**Explicitly not in Sprint 5**, so that the omissions are decisions rather than oversights:

- **Role-filtered endpoints** (`/master-data/suppliers`, `/customers`, `/employees`, FR-MDM-002/008) move to Sprint 6, where the list UI that consumes them lands. They are a projection over items 6 and 7 and are cheap once those are done; they are the first thing to pull forward if Sprint 5 runs ahead.
- **The four Phase 2 carry-overs** (#17, #24, #27, #28) move to Sprint 6. All `Should`, all first-cut, none gating the `v0.2.0` tag or Phase 3.
- **#65** (the bootstrap grants a role across a tenant boundary) stays open and non-urgent under **D-7**: it is only reachable with a non-`SYSTEM` default tenant, which no deployment has.
- **#68** (session loss outside a navigation leaves a dead page) stays open, `Should`.
- **Staging (#12)** is not sprint scope and never was — it needs a host and DNS, which is the project owner's action, four sprints old.

**Verification rules this sprint operates under**, all three from the retrospective's action list:

1. A test asserting a security control is not accepted until the defect it claims to catch has been reintroduced and the test seen to fail ([coding standard](../../docs/standards/01.%20Coding%20Standard.md) §2.9). Items 1–4 are all security-control or contract tests.
2. Every "Done" row in the Sprint 5 status report cites evidence checked by someone other than the item's author. An issue state or a merge is not evidence.
3. The status report does not go `Final` without its retrospective in the same change.

**Entry criteria — tracker work before the sprint starts.** Milestone `Phase 3 — Master Data (v0.3.0)` created 2026-08-20; it is empty until items 6 and 7 are filed against it. Outstanding: issues for items 6 and 7; closing #25 into #28 per **D-8**; re-labelling the four carry-overs and the deferred items from `sprint:5` to `sprint:6`.

**Exit:** the Phase 2 exit debt is closed, so `v0.2.0` is blocked only by staging; a party can be created with a SUPPLIER role and a supplier profile, read back through the API, and its creation is in the audit log. Phase 4's entry criterion is answered by #31's finding.

## 6. Sprint Outline — Later Phases (Sprints 7–20)

Detail these at the preceding phase boundary; current outline:

Migration numbers below have shifted twice, by four on 2026-08-13 and by one more on 2026-08-20: Sprint 4 consumed versions `0005` and `0006` (`0005_delegation_tenant_permissions.sql`, `0006_password_reset_tokens.sql`), and the lockout expiry of NFR-SEC-008 then took `0007` (`0007_account_lockout.sql`). sqlx applies migrations in version order, so a later phase cannot reclaim a lower number, and the number a migration gets is the next one free when it is written rather than one reserved for its phase ([naming convention](../../docs/standards/02.%20Naming%20Convention.md) §4.3). The [Database Schema](../../docs/design/02.%20Database%20Schema.md) mapping table is authoritative; this plan and the [Product Backlog](02.%20Product%20Backlog.md) restate it, which is the arrangement the [Sprints 2–4 retrospective](../retrospectives/02.%20Sprints%202-4%20Retrospective.md) committed to ending — until it does, expect a shift here every time an unplanned migration lands. Sprint 3 hit the same class of defect from the other direction — a renumbering recorded in one document and not written back to the others.

- **Sprints 7–8 (Phase 4, Document Core):** `0009_rad.sql` then `0010_document.sql` — the RAD metadata tables must exist first, because `document_types.form_id` references `rad_forms` ([Database Schema](../../docs/design/02.%20Database%20Schema.md) §6.2) and migrations apply in version order. Phase 4 carries the front half of RAD (decision **D-2**): metadata tables, form/list definition storage APIs, lookup fields, and a read-only JFSS renderer (FR-RAD-001, 002, 003, 005, 007, 008, 010) — MVP criteria 4 and 5 need a form to render, not just tables. Then document types & numbering rules (FR-DTYPE), document CRUD/submission/versions/metadata (FR-DOC), document list & detail UI. The widest phase in the plan; if it overruns, the RAD half is the part that stays and the `Should` document items (FR-DOC-008/009/010) are cut first. Exit: `v0.4.0`.
- **Sprints 9–10 (Phase 5, Workflow):** workflow definitions & state machine (FR-WF), task inbox (FR-TASK), approve/reject/return, document-status synchronization, workflow history; wire FR-MDM-010 (master-data change requests through workflow). Exit: `v0.5.0` — end-to-end approvals demoable; MVP criteria 8, 9, 10 met.
- **Sprints 11–12 (Phase 6, Collaboration):** attachments with async virus-scan gating (FR-ATT), threaded comments (FR-CMT), activity timeline + hash-chained audit (FR-ACT/AUD), notifications baseline (FR-NTF). Closes MVP criteria 6, 11, 12, 13. Exit: **MVP** verified against SRS §9 in full, `v0.6.0`.
- **Sprints 13–15 (Phase 7, RAD):** the back half of RAD — calculation/validation rule engines per the registries (client + server, Tamper-Proof Pattern), dynamic list renderer, conditional field visibility, document type & menu builder UIs (FR-RAD-004, 006, 011). The JFSS v2.0.1 form renderer and definition storage already shipped in Phase 4. Exit: `v0.7.0`.
- **Sprint 16 (Phase 8, Reporting):** dashboard (pending tasks, recent documents, status chart), approval reports (FR-RPT). Exit: `v0.8.0`.
- **Sprints 17–18 (Phase 9, Integration & Plugins):** integration core + external system registry + integration logs (FR-INT), outbox dispatcher, plugin registry/settings/manager UI (FR-PLG, config-based plugins per architecture doc 04 Phase 1). Exit: `v0.9.0`.
- **Sprints 19–20 (Hardening):** NFR verification (performance targets NFR-PERF, availability drills, security pass incl. encryption at rest), load testing, documentation completion, `v1.0.0`.
