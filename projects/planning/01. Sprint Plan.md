# Kelir Sprint Plan

**Status:** Draft · **Last updated:** 2026-08-11

This plan maps the Development Roadmap (System Design Document §14, Phases 1–9) onto a sprint cadence. It is **scope-sequenced, not date-committed**: sprint contents are the commitment, calendar dates shift with measured velocity. Re-baseline after Sprint 2 and at every phase boundary.

Related documents: requirements and FR IDs in [srs.md](../../docs/requirements/srs.md); system design in the [SDD](../../docs/design/01.%20System%20Design%20Document.md); engineering rules in [docs/standards/](../../docs/standards/); release mechanics in [04. Release Process.md](../../docs/standards/04.%20Release%20Process.md). The FR-level scope inventory behind this sequence is the [Product Backlog](02.%20Product%20Backlog.md) — it maps every requirement to an epic and a sprint, and records the open scope decisions this plan depends on.

## 2. Cadence and Definition of Done

- Ceremonies: planning (first day), demo + review (last day), retro (last day, 30 min). Backlog refinement mid-sprint.
- A backlog item is **Done** when: code merged to `main` per the [git workflow](../../docs/standards/05.%20Git%20Workflow.md); tests per [coding standard](../../docs/standards/01.%20Coding%20Standard.md) §2.9/§3.5 pass in CI; API changes reflected in OpenAPI; audit/permission checks in place; demoable from a staging deploy.
- Every sprint ends demoable; every **phase** ends with a tagged release (§4).

| Milestone | Version |

The MVP tag sits at `v0.6.0`, not `v0.5.0`: five of the fifteen SRS §9 acceptance criteria (attachments, comments, activity log, audit of approvals) are Phase 6 work, so Phase 5 delivers end-to-end approvals but does not satisfy §9. Decided 2026-08-11 as [Product Backlog](02.%20Product%20Backlog.md) decision **D-1**; SDD §14 carries the corrected label. `v0.5.0` remains a real release — it is an approval-workflow milestone, not the MVP.

### Sprints 1–2 — Phase 1: Foundation

**Goal:** running Kelir skeleton (SDD §14 Phase 1 deliverable).

- **Sprint 1 — done 2026-08-12** (issues #2–#7). Axum router; config loading (`KELIR_*`); tracing setup; SQLx pool + migration runner; `0001_core.sql` applied; `/health`, `/health/ready`, `/health/live`, `/version`; response envelope + `AppError` (coding standard §2.3/§2.6); pagination; generated OpenAPI. - **Sprint 2 — done 2026-08-12 except staging** (issues #8–#11 closed, #12 open). Frontend: app shell layout, router, Pinia, API client with envelope unwrapping; login page (UI only until Phase 2 wires it); Tailwind v4 + shadcn-vue baseline. **Phase 1 exits once staging is provisioned.** The environment is defined and verified in the repository (`deploy/staging/`, release images, single-origin Caddy); what remains for #12 is the host `kelir-staging-01`, DNS for `staging.kelir.gawshub.com`, and one deploy. Sprint 3 can start without it.

### Sprints 3–4 — Phase 2: Authentication and User Management

**Goal:** authenticated application (FR-AUTH-001..006, FR-IDM-001..008, FR-ORG-001..004).

- Sprint 3 (backend-heavy): `0002_identity.sql`; Argon2 password handling; login/logout/me; JWT or session decision implemented; permission middleware (`module:resource:action`); user & role CRUD APIs.
- Sprint 4: frontend auth flow + route guards; user/role/permission admin screens; delegation basics (FR-IDM-007); audit events for identity changes; rate limiting on auth endpoints (NFR-SEC-008).
- Deferred per SRS: SSO/OIDC (FR-AUTH-007, later phase).

**Exit:** `v0.2.0`; a user logs in, an admin manages users/roles, permissions enforced server-side.

### Sprints 5–6 — Phase 3: Master Data (Party Model)

**Goal:** party-based master data management (FR-MDM-001..011; architecture doc 05).

- Sprint 5: `0003_master_data.sql` implementing the normalized Party tables (`mdm_parties` … `mdm_contact_profiles`, per SRS §7 and the [Database Schema](../../docs/design/02.%20Database%20Schema.md) §4); party CRUD service + endpoints (`/master-data/parties`); role-filtered views (`/suppliers`, `/customers`, `/employees`); identifications & contact mechanisms.
- Sprint 6: role profiles (supplier/customer/employee); facility, product, service entities; master data list UI with search/filter/pagination (FR-MDM-008); lifecycle statuses (FR-MDM-007); audit logging (FR-MDM-009); `master_data_source_references` (FR-MDM-011).
- Deferred to Phase 5+: master-data changes via document workflow (FR-MDM-010) — needs the workflow engine.
- Phase 4 entry prep: JFSS operator-parity spike (`json-logic` library support, Calc Registry §2 note) — tracked as **issue #31**. The renderer moved into Phase 4 with decision **D-2**, so this must resolve before Sprint 7 planning, not during Phase 7.

**Exit:** `v0.3.0`; demo: create a party, assign SUPPLIER role + profile, find it via `/master-data/suppliers` and the UI. Phase 4 entry criteria met: JFSS spike resolved.

## 6. Sprint Outline — Later Phases (Sprints 7–20)

Detail these at the preceding phase boundary; current outline:

- **Sprints 7–8 (Phase 4, Document Core):** `0004_rad.sql` then `0005_document.sql` — the RAD metadata tables must exist first, because `document_types.form_id` references `rad_forms` ([Database Schema](../../docs/design/02.%20Database%20Schema.md) §6.2) and migrations apply in version order. Phase 4 carries the front half of RAD (decision **D-2**): metadata tables, form/list definition storage APIs, lookup fields, and a read-only JFSS renderer (FR-RAD-001, 002, 003, 005, 007, 008, 010) — MVP criteria 4 and 5 need a form to render, not just tables. Then document types & numbering rules (FR-DTYPE), document CRUD/submission/versions/metadata (FR-DOC), document list & detail UI. The widest phase in the plan; if it overruns, the RAD half is the part that stays and the `Should` document items (FR-DOC-008/009/010) are cut first. Exit: `v0.4.0`.
- **Sprints 9–10 (Phase 5, Workflow):** workflow definitions & state machine (FR-WF), task inbox (FR-TASK), approve/reject/return, document-status synchronization, workflow history; wire FR-MDM-010 (master-data change requests through workflow). Exit: `v0.5.0` — end-to-end approvals demoable; MVP criteria 8, 9, 10 met.
- **Sprints 11–12 (Phase 6, Collaboration):** attachments with async virus-scan gating (FR-ATT), threaded comments (FR-CMT), activity timeline + hash-chained audit (FR-ACT/AUD), notifications baseline (FR-NTF). Closes MVP criteria 6, 11, 12, 13. Exit: **MVP** verified against SRS §9 in full, `v0.6.0`.
- **Sprints 13–15 (Phase 7, RAD):** the back half of RAD — calculation/validation rule engines per the registries (client + server, Tamper-Proof Pattern), dynamic list renderer, conditional field visibility, document type & menu builder UIs (FR-RAD-004, 006, 011). The JFSS v2.0.1 form renderer and definition storage already shipped in Phase 4. Exit: `v0.7.0`.
- **Sprint 16 (Phase 8, Reporting):** dashboard (pending tasks, recent documents, status chart), approval reports (FR-RPT). Exit: `v0.8.0`.
- **Sprints 17–18 (Phase 9, Integration & Plugins):** integration core + external system registry + integration logs (FR-INT), outbox dispatcher, plugin registry/settings/manager UI (FR-PLG, config-based plugins per architecture doc 04 Phase 1). Exit: `v0.9.0`.
- **Sprints 19–20 (Hardening):** NFR verification (performance targets NFR-PERF, availability drills, security pass incl. encryption at rest), load testing, documentation completion, `v1.0.0`.

## 7. Cross-Sprint Dependencies and Risks

| Risk / dependency | Impact | Mitigation |
|---|---|---|
| Phase 4 now carries two modules (RAD front half + Document Core) after decision **D-2** | Sprints 7–8 overrun; Phase 5 start slips | Sequence RAD storage first (it blocks the document migration); cut `Should` document items (FR-DOC-008/009/010) before cutting RAD; re-baseline at the Phase 3 boundary with measured velocity |
| Party model is newly adopted; concepts docs 03/04 not yet updated | Rework in Sprints 5–6 | Reconcile concept docs before Sprint 5 planning |
| JFSS registries require Go/Rust operator parity verification | Phase 4 slip — the renderer moved forward with **D-2**, so this is now a Sprint 7 dependency, not a Sprint 13 one | Spike during Sprints 5–6: verify `json-logic` library support (Calc Registry §2 note) before Sprint 7 planning |
| Phase 4 and Phase 5 are both on the MVP critical path | MVP (`v0.6.0`) slip | Keep Phase 5 scope to sequential approvals; parallel approval stays deferred (FR-WF-016); Phase 6 attachment/comment/activity work is MVP-gating and cannot be traded for `Should` items |
| ClamAV signature updates and scan latency at 25 MB (**D-4** decided the scanner; sizing is untested) | Slow or failed uploads in Phase 6 | Scan asynchronously — upload returns immediately with `virus_scan_status = PENDING`, download is gated on `CLEAN`; measure scan time during Sprint 11 and size the worker before the `v0.6.0` tag |
| Single shared staging environment | Demo conflicts | Tag-based deploys only; compose profiles for local demos |
| Velocity unknown until Sprint 2 | Whole plan shifts | Re-baseline at Sprint 2 and each phase boundary; cut Should-priority scope first |

## 8. Change Control

- Scope changes enter through backlog refinement, priced against the sprint map; Must-priority FRs displace Should-priority FRs, never the reverse.
- This document is updated at each phase boundary (sprint numbers, velocity notes, next-phase detail) — it is a living plan, versioned by its **Last updated** line and git history.
