# Sprint 9 Document Construction Plan

**Status:** Adopted · **Last updated:** 2026-08-27

This plan decomposes Sprint 9's six items — [#167](https://github.com/sujanto-gaws/kelir/issues/167) create and edit, [#168](https://github.com/sujanto-gaws/kelir/issues/168) submit and number, [#169](https://github.com/sujanto-gaws/kelir/issues/169) status, [#170](https://github.com/sujanto-gaws/kelir/issues/170) the entity link, [#171](https://github.com/sujanto-gaws/kelir/issues/171) the list, [#172](https://github.com/sujanto-gaws/kelir/issues/172) the workspace — into files, order, and the decisions each one has to take before it is written. It sits **one level below** the [Sprint Plan](01.%20Sprint%20Plan.md), which settles what is in Sprint 9 and why; nothing here changes that scope, and where the two disagree the sprint plan wins.

It exists for the reason the [Sprint 8 plan](03.%20Sprint%208%20Form%20Renderer%20Construction%20Plan.md) existed and then earned: six items over one aggregate is where a sprint quietly becomes one item with six names. It also carries something Sprint 8's did not — **Sprint 9 is a phase close**, so §10 schedules the independent pass, the demo and the release rehearsal as dated steps rather than as an intention.

Related documents: storage is [Database Schema](../../docs/design/02.%20Database%20Schema.md) §6; the form semantics are [JSON Form Schema](../../docs/schema/JSON%20Form%20Schema.md) v2.0.1 and its two registries; the engineering rules are [docs/standards/](../../docs/standards/), chiefly [coding standard](../../docs/standards/01.%20Coding%20Standard.md) §2.5, §2.9 and [naming convention](../../docs/standards/02.%20Naming%20Convention.md) §4, §5, §6.

## 3. The migration, and the two things it adds

`0023_document.sql`. The tables are all there since `0015_document.sql`; what is missing is the permission catalogue and one counter.

**The permission rows.** `0015` deliberately seeded none for documents — *"a permission row no route checks reads as a control that exists"*. Six routes now exist, so six rows land: `document:create`, `document:read`, `document:update`, `document:delete`, `document:submit`, `document:transition`. The last two are separate on purpose and each has a precedent. `document:submit` is not `document:update`, because submitting takes a number and starts a life; `document:transition` is not `document:update`, which is #99's AC1 restated — *someone who may correct a requisition's line items is not thereby someone who may approve it*. There is no `document:metadata:*`: metadata is part of the document, not a resource beside it, so the resource segment is omitted (naming convention §6) exactly as `document-type:*` omits it.

**`document_ref_sequences`.** `documents.document_ref` is `NOT NULL` and unique per tenant, and Database Schema §6.6 documents its shape as `DOC-2026-000123` — a tenant-wide, year-scoped counter, which nothing in the codebase produces. It is *not* `document_number`: the number is the business identifier a type's rule renders and a submit assigns, and the ref is the internal handle a draft has before it has a number. A draft with no handle is what a user is looking at for the whole of its life before submit.

The counter is the shape `0020_numbering_buckets.sql` already proved — one row per bucket, insert-or-advance in one statement, `RETURNING next_sequence - 1`, no read to race. It is allocated **inside the creation transaction**, so a failed create rolls the counter back with it; the trade is that draft creations within one tenant-year serialise from the allocation to the commit, and a creation transaction is short. If that ever bites, `allocate_committed`'s shape is one function away and gaps in an internal handle cost nothing — which is exactly why this is stated here rather than discovered.

The migration also adds two indexes the list needs and `0015` did not anticipate: `documents (tenant_id, entity_type, entity_id)` for the linked-entity filter, and a `pg_trgm`-free `documents (tenant_id, lower(title))` is **not** added — see §8, which decides what "search" means before an index is chosen for it.

## 4. Item 1 — create a document, store its data, edit the draft (#167)

### 4.1 The form is pinned at creation, and that is what makes D-30 true

`documents.form_id` is nullable and `document_type::service::guard_rebinding` refuses to move a type's binding while any document of it pinned nothing. **Every document this item creates pins the type's `form_id` at the moment of creation**, so the population that guard refuses over stays empty for documents Kelir creates, and the guarantee **D-30** describes stops depending on a comment.

A type that binds no form is still creatable-from — §6.2 permits it — and such a document pins nothing and holds no form data. That is the one row the guard exists for, and it can only arrive from a type with no binding rather than from a document that forgot.

### 4.2 Validated on every write, and `required` is not a refusal on a draft

[#167](https://github.com/sujanto-gaws/kelir/issues/167) AC2: form data is validated server-side **on every write**, not only on submit, because *"a draft holding data its own form would reject is a draft that cannot be submitted, discovered late"*.

Taken literally that makes an empty draft unsaveable, because `required` is precisely the rule an unfinished document breaks. So the rule is stated once, here, and implemented as a mode on the existing pipeline rather than as a second pipeline:

> **A draft write runs every step `secure_payload` runs, and refuses on everything except absence.** A value that is present and wrong — wrong type, too long, out of range, failing a registry rule — is refused on a draft, because it is data the form would reject. A value that is *missing* is not wrong, it is unfinished.

Two detail classes are therefore dropped on a draft write and only on a draft write, matched on the pair `(code, rule)` the evaluation service already emits rather than on message text:

| Dropped on a draft | Why |
|---|---|
| `VALIDATION_FAILED` / `required` | The definition of a draft. `check_validation` short-circuits on an empty value, so this is the *only* verdict an empty field can produce and dropping it removes nothing else |
| `RULE_NOT_ENFORCED` / any | **D-28** refuses an unenforced registry rule because *"this side has nobody below it"*. On a draft it does: the submit. Deferring it here is D-28's own reasoning, not an exception to it |
| `EVALUATION_FAILED` / any | **Added during construction, and it is D-24 applied to the other write.** An average over zero rows fails before the first keystroke, and §5.6 of the [Sprint 8 plan](03.%20Sprint%208%20Form%20Renderer%20Construction%20Plan.md) already settled that the answer *while a form is being filled in* is a blank field rather than an error. A draft is that moment on the server's side of the wire. Nothing the user typed is discarded by it: an undecidable `conditional` resolves to visible |

**Three classes, not two — the third was found while writing §4 and is in the table above.** `RULE_NOT_REGISTERED` still refuses on a draft. A rule name nobody defines is a defect in the *definition* and no amount of finishing the document makes it go away — S8.1.1's arm, unchanged.

**The mode is a parameter on the pure evaluator**, `rad::service::evaluation::Strictness`, so the two paths cannot drift: the submit calls the same function with `Strictness::Submit` and gets today's behaviour byte for byte. A `secure_payload` that a draft called and a submit re-implemented would be two answers to one question, which is the failure §6 of this plan is about in another register.

### 4.3 Metadata is stored apart, and replaced as a set

AC3 asks for metadata *"distinguishable from form data rather than merged into the same object"*. `document_metadata` is that table and it already exists: `metadata_key`, `metadata_value`, `data_type`. The request carries `metadata` as its own object beside `formData`, and a `metadata` that is **sent** replaces the stored set — the shape `document_type::repository::replace_workflows` established for a collection on an aggregate, and the shape `UpdateDocumentTypeRequest` already uses.

### 4.4 What an audit record says about a JSON blob

AC5 requires an update's record to name **only the fields that moved**, and requires this plan to state explicitly what a change to `form_data_json` records, because *"the whole document changed" is not an audit record*.

> **The audit record names the data keys whose values moved, and carries neither the old value nor the new one.** `{"formData": {"changedKeys": ["amount", "line_items"]}}`, both halves of the `ChangeSet` carrying the same list.

Two reasons, and the second is the load-bearing one. A form's data is arbitrary tenant content — salaries, bank details, medical grounds for a leave request — and the audit trail is read through `master-data:audit:read` and its successors by people who hold no permission over the document. **D-12** already refused to hand back a record's field values through its change history without the record's own read permission; copying every keystroke of every form into a table with a different permission would be that finding, at scale, on data nobody classified. The changed-key list is what an auditor actually asks for — *when did the amount last move, and who moved it* — and the values themselves are in `document_versions` behind the document's own permission when FR-DOC-008 lands.

Every other field on the document audits normally, through `ChangeSet::field`, with its values.

### 4.5 Only drafts are editable, and the check is under the lock

AC4. The status is read `FOR UPDATE` inside the same transaction as the write, not on the pool before it — coding standard §2.5, and the shape #133 and #137 were filed for. A submitted document that arrives at `PUT /documents/{id}` is refused with the envelope naming the status it is in.

### 4.6 Routes

| Route | Permission | Notes |
|---|---|---|
| `POST /api/v1/documents` | `document:create` | 201 with the aggregate |
| `GET /api/v1/documents/{id}` | `document:read` | The aggregate, with metadata and the link identifiers (§7) |
| `PUT /api/v1/documents/{id}` | `document:update` | Drafts only |
| `DELETE /api/v1/documents/{id}` | `document:delete` | Soft delete, drafts only — see §6 for why a submitted document is not deletable |

## 5. Item 2 — submit, and take the number in the same transaction (#168)

### 5.1 The order of operations, and where each step can fail

`POST /api/v1/documents/{id}/submission`. A verb sub-resource rather than a status field on the update payload, for #169's reason applied one item early: submit has its own permission, its own audit action and its own preconditions.

1. `document:submit`, before anything is read.
2. Begin. Read the document `FOR UPDATE`. Not a draft → refused (AC5), naming the status.
3. Load the pinned definition. **`Strictness::Submit`** through `secure_payload_with` — the full pipeline, `required` and unenforced rules refusing as D-28 says.
4. Allocate the number through `numbering_service::allocate`, which reads the type's `GapPolicy` and picks: `Gapless` allocates in **this** transaction, `AllowGaps` in one of its own. That is #158's decision and this item behaves the way it decided rather than choosing again (entry criterion 2).
5. Write: `document_number`, `status = 'SUBMITTED'`, `submitted_at`, and the **server's** `form_data_json` — the payload step 3 returned, never the one the client sent.
6. Append the `document_status_history` row.
7. Commit. Audit as `Document.Submitted` / action `SUBMIT`, carrying the number.

**Step 3 before step 4 is the whole item.** Numbering first and validating second is the "number burned by a failed submit" of the issue's own text, and on a `Gapless` rule it is worse than a burned number: the counter is held from step 4 to the commit, so a slow re-evaluation serialises every concurrent submit of that type behind a document that is about to be refused.

### 5.2 The concurrency test, and the naive implementation it is run against

AC3 and AC4 are one test. `N` documents of one type, submitted concurrently at a level **above the pool ceiling** — the level [#118](https://github.com/sujanto-gaws/kelir/issues/118) showed a fix's own tests can fail to reach — asserting `N` distinct numbers and no gaps under a `Gapless` rule.

It is **seen to fail** against allocate-then-submit as two transactions (§2.9), and the pull request cites the red run against the named test. `tests/document_numbering.rs` already holds the isolated allocator's concurrency tests; this one goes in `tests/documents_submit.rs` beside the submit, because what it is about is the submit rather than the allocator.

### 5.3 A second document type is in the fixture, always

Every fixture in §4–§9 that asserts anything is scoped puts a **second document type** in the database, and where a bucket is involved, a second bucket. That is coding standard §2.9 as of Sprint 8 and it is [#218](https://github.com/sujanto-gaws/kelir/issues/218)'s single root cause: one subject cannot distinguish *scoped* from *unscoped*, so an assertion over such a database is green whatever the predicate does.

## 6. Item 3 — the status field and its transitions (#169)

### 6.1 The two status concepts, in the words the module doc has to use

`documents` carries `status`. `mdm_parties` and friends carry `record_status`. They are not the same thing and `modules/document/mod.rs` says so in these terms:

> **`record_status` answers "how far has this record got through governance"** — a master-data record is drafted, approved, active, suspended, archived (FR-MDM-007, #99). It is a property of a *record about a real-world thing that keeps existing*.
>
> **`documents.status` answers "where is this document in its own life"** — drafted, submitted, approved, completed. A document is an *event*: it happens once, ends, and is then history. It has no governance lifecycle because there is no ongoing thing for governance to be about.
>
> A row in `documents` therefore has one and only one lifecycle, and it is this one. Nothing in this module reads or writes `record_status`, and nothing in `master_data` reads or writes `documents.status`.

### 6.2 The legality table, and the six values Sprint 9 may reach

`documents.status`'s `CHECK` names ten values. **Five of them belong to a workflow that does not exist**, and AC5 forbids this item from pre-empting what FR-DOC-012 means. So the legality table is written over all ten and the transitions *into* the workflow-owned states are absent — the shape `RecordStatus::may_move_to` used for `PENDING_APPROVAL`, and for the identical reason: a document put into `PENDING_APPROVAL` today would await an approver that does not exist.

| From | May move to, in Sprint 9 | Owned by |
|---|---|---|
| `DRAFT` | `SUBMITTED` | #168, and **not** this route — see §6.3 |
| `SUBMITTED` | `IN_REVIEW`, `APPROVED`, `REJECTED`, `RETURNED`, `CANCELLED` | this route |
| `IN_REVIEW` | `APPROVED`, `REJECTED`, `RETURNED`, `CANCELLED` | this route |
| `RETURNED` | `SUBMITTED`, `CANCELLED` | this route |
| `APPROVED` | `COMPLETED`, `CANCELLED` | this route |
| `REJECTED` | `CANCELLED` | this route |
| `COMPLETED` | — | terminal |
| `CANCELLED` | — | terminal |
| `ARCHIVED` | — | terminal, and unreachable: FR-DOC-010 is the cut tail |
| `PENDING_APPROVAL` | — | **unreachable**: Phase 5's, and nothing may enter it |

`ARCHIVED` is in the table and reachable from nothing, which is the honest encoding of *"cancel and archive is a `Should` on the cut tail"*: the value exists in the column, the product does not move anything into it, and the table says which. `CANCELLED` is reachable — cancelling a document that has not been archived is not FR-DOC-009's storage question, it is the ordinary end of a request that was withdrawn, and a lifecycle whose only exits are `COMPLETED` and nothing is a lifecycle that traps every abandoned draft forever.

**A draft is cancelled rather than deleted, and `DELETE` is a draft-only soft delete.** Both exist because they answer different questions: deleting a draft is *"I opened this by mistake"*, cancelling a submitted document is *"this request is withdrawn"*, and the second must leave a row an auditor can find.

### 6.3 `DRAFT -> SUBMITTED` is not reachable from this route

The transition route refuses it, naming #168. Submitting is not a status change with a number as a side effect; it is a transaction that takes a number, re-evaluates a payload and moves a status, and reaching the status half through a different door would produce a submitted document with no number — the "submitted but not numbered" outcome #168's own text calls unrecoverable.

### 6.4 The compare-and-swap, and the 409

`PUT /api/v1/documents/{id}/status`, taking `{"status": ..., "reason": ...}`, permission `document:transition`.

The write is `UPDATE ... WHERE status = <the status the legality check read>`, one statement, and `0 rows` is a **409** rather than a silent overwrite (AC3). Record 03 found exactly this untested in the facility arm of the shared transition service (#139), so the test here is the one that was missing there: two transitions from one starting state, one 200 and one 409, and it is **seen to fail** against an unconditional update.

The permission test is likewise seen to fail against a build where `document:transition` is replaced by `document:update` (AC4, AC7).

## 7. Item 4 — link a document to a master-data entity (#170)

### 7.1 The answer is #161's answer, because it is #161's question

**Reading a document hands back `entityType` and `entityId` and nothing else.** No name, no code, no fields. Resolving the link is a sub-resource — `GET /api/v1/documents/{id}/linked-entity` — and it resolves by **calling `master_data::service::get_party` / `get_facility`, which refuse first**. This module writes no permission check for master data at all, which is precisely how #161 made a lookup unable to open what the master-data surface does not: *a lookup cannot open what the master-data surface does not, because it is that surface.*

A caller holding `document:read` and not `master-data:party:read` therefore gets the document, sees that it concerns a party, and gets **403** from the resolution — #161's choice between 403 and an empty answer, taken the same way and for its second reason: refusing leaks nothing the caller does not already hold, because they read the identifier on the document itself.

AC3's test is that caller, asserting no party field appears in either response, and it is **seen to fail** against a build where the sub-resource loads the party through the repository instead of the service.

### 7.2 `entityType` is recorded, never inferred (AC1)

`documents.entity_type` is a `VARCHAR(64)` with no `CHECK`, so the enum is Rust's: `EntityType::{Party, Facility}`, the two entity kinds that have a read endpoint to delegate to. A value outside it is refused at the boundary. Products and services are one variant each, when they have services to delegate to.

The pair is all-or-nothing: `entityType` without `entityId` and the reverse are both refused. A bare id that could mean a party or a facility is AC1's *"bug waiting for the second entity type"*, and Kelir already has the second entity type.

### 7.3 Writing the link, and losing the entity (AC4, AC5)

On write, the entity is checked **in the write's transaction**, under a lock on the row the check read: it exists, it is in this tenant, and it is not soft-deleted. There is no foreign key from `documents.entity_id` — `0015` created it as a bare column because it is polymorphic — so the constraint is this check and nothing else, which is why it is `SELECT ... FOR SHARE` rather than a read on the pool.

**Afterwards, the link is not maintained.** Soft-deleting the party leaves the document readable, its `entityType` and `entityId` unchanged, and the resolution answering **404 naming the entity** rather than the document. That is the decision AC5 asks for rather than a default, and the alternative — cascading, or nulling the link — would rewrite a historical record because a supplier was retired years later. A purchase order that concerned supplier X still concerned supplier X.

## 8. Item 5 — the list, and the visibility rule that does not wait for FR-DTYPE-008 (#171)

### 8.1 The rule, stated once, enforced in the query

> **A caller sees a document when it is in their tenant and they hold `document:read`. There is no third condition in Sprint 9.**
>
> Not the creator, not the department, not a security level. `documents.security_level` exists in the column and **nothing reads it**, because FR-DTYPE-008 is the cut tail and a filter half-honouring a requirement nobody wrote is worse than no filter: it reads as a control and enforces an accident. When FR-DTYPE-008 lands it adds a finer grain **on top of** this floor, and this comment is where it goes.

Enforced in the statement, in the repository, not in the handler (AC2). The cross-tenant test reaches the query rather than asserting around it (AC3) — the #106/#121 lesson, and the fixture holds a second tenant *and* a second document type for #218's reason.

### 8.2 What "search" means, decided before an index is chosen for it

`search` is a case-insensitive substring of the **document number, the document ref, or the title** — the three things a person has in their hand when they are looking for a document. It is **not** a search of `form_data_json`: that is FR-SRH-002's full-text search, unscheduled, and a `LIKE` over a JSONB blob would be a slow, silent, partial version of it that made the real one look like a regression.

No index is added for it in `0023`. A trigram index over three columns is the answer if the list is measured slow, and adding one now would be an index chosen before the query that uses it exists — which the Sprint 6 list did not do either.

### 8.3 Filters, and the bad-page refusal

`documentTypeId`, `status`, `entityType` + `entityId`. Every one respects the same visibility rule by being a predicate in the **same statement**, not a second query — AC4's *"a filter must not become a way to confirm a document exists"* is satisfied by there being nowhere else for it to be answered.

`page` and `pageSize` land in the envelope through `crate::extract::QueryParams`, which is what [#122](https://github.com/sujanto-gaws/kelir/issues/122) is open about and what `RoleViewQuery` already does. This list does not become a fourth instance of the bare 400; it does not close #122 either, and the status report says so rather than implying it.
