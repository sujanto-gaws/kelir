# Phase 5 Close Plan

**Status:** Adopted · **Last updated:** 2026-08-30

This plans the four things standing between `main` as it is today and `v0.5.0` as a tag. It sits **one level below** the [Sprint Plan](01.%20Sprint%20Plan.md), whose Sprint 11 §Exit states the four criteria; nothing here changes them, and where the two disagree the sprint plan wins.

It exists because **Phase 5's scope is complete and the phase is not closed**, and those two facts are one merge apart and easily confused. All six of Sprint 11's construction items are on `main` — #231 through #236 — and the [Sprint 11 status report](../status/12.%20Sprint%2011%20Status.md) is `Draft` rather than `Final` because none of them has been read by anybody who did not write it.

Related documents: the checklist this plan executes is [Release Process](../../docs/standards/04.%20Release%20Process.md) §4 and §7, the rollback rule is its §6, the Definition of Done is [Sprint Plan](01.%20Sprint%20Plan.md) §2, and the verification records this plan produces follow [record 08](../verifications/08.%20Sprint%2010%20Independent%20Pass.md)'s shape.

## 2. The order, and why it is not the order of the list above

**The independent pass goes first, before the demo and long before the tag.** The list in the sprint plan is a list of criteria, not a sequence, and executing it in written order would be a mistake this project has already paid for once.

Sprint 10's pass was run **after** its status report was written and found [#225](https://github.com/sujanto-gaws/kelir/issues/225) — a `DEPARTMENT_ROLE` task decidable from any department, in a surface that had passed 34 mutations at 68%. It found it because the defect was an **absent** predicate: there was no clause to mutate and no test to fail. A pass run after a tag would have found the same class of thing in a released artefact.

So:

1. **§3 — the independent pass.** Its findings change what is demonstrated and what is tagged.
2. **Its blocking findings, fixed.** Not a step that was planned, because a step whose whole purpose is to find what nobody expected cannot have its own consequences scheduled in advance. #259 is the first, and it is fixed; a later finding would insert itself here the same way.
3. **§4 — the demo**, once the findings are closed or accepted.
4. **§5 — the release rehearsal**, against the artefact that will be tagged.
5. **§6 — the tag**, and the release record.

**Steps 1 and 2 may be interleaved if the reader is available before the stack is**, and no other pair may. In particular the rehearsal must not run before the pass: rehearsing a release of code that then changes proves the rehearsal, not the release.

## 3. Step 1 — the independent verification pass

**The criterion is a reader, not a document.** §2's rule is that an item whose author is also its only verifier is `In progress`; what discharges it is somebody else reading the work, and the record is the trace of that.

**Scope: Sprint 11's six items, and the frontend that Sprint 10's pass did not read.** Record 08 covered the Sprint 10 **backend** only and said so; the frontend rows of that sprint have still never been independently read, and four of Sprint 11's items changed the same screens.

| Surface | Why it is in scope |
|---|---|
| #181 history, #182 decide-with-reason, #183 return, #184 delegation, #185 due dates, #186 conditional routing | The sprint's own six |
| The task inbox and task detail screens | Changed by four of the six; never independently read, in either sprint |
| The document workspace's workflow tab | Changed by #181, #184 and #186 |

**Four questions the pass should carry**, chosen because they are where this sprint's work is least likely to be wrong in a way its own tests can see:

1. **Absent predicates**, which is what record 08 found and what mutation testing structurally cannot find. Every new column that something *reads* — `delegated_from_user_id`, `due_at`, `routing_json`, `on_behalf_of_user_id` — and every place that reads it.
2. **The claims in doc comments.** This sprint wrote a great many, several of them reversing earlier ones. A doc comment that describes behaviour the code does not have is the defect #184 found in `TaskStatus::is_open`, whose comment said `DELEGATED` was open when the function said otherwise.
3. **The three-way and four-way record distinctions** — `workflow_history` against `workflow_task_history` against `approval_decisions` against `audit_events`. Four records of one decision, and the sprint asserts in prose that none is derived from another.
4. **Tenant scoping on the new statements**, against the rows rather than the handler — the [#106](https://github.com/sujanto-gaws/kelir/issues/106)/[#121](https://github.com/sujanto-gaws/kelir/issues/121) lesson.

**Output:** `projects/verifications/09. Sprint 11 Independent Pass.md`, in record 08's shape, with §1 stating where its independence stops before it states anything else.

**A finding does not automatically block the tag.** It blocks the tag if it is a security control, a data-integrity rule, or a defect in something Phase 5 claims to have delivered. Anything else is filed and carried, the way [#226](https://github.com/sujanto-gaws/kelir/issues/226) was carried out of Sprint 10 into Sprint 11's #183. **That judgement belongs to whoever runs the pass, and it is written down in the record rather than settled in conversation.**

## 4. Step 2 — the exit demo

**Sprint 11's exit names the whole path in one sentence**, and the demo is that sentence performed: a document type carrying a workflow; a submitted document starting an instance; the task reaching an approver's inbox; a return sending it back for correction; a resubmission keeping its number; an approval closing it; and the history showing every step with its reason.

**Driven through the harness, not clicked**, per the exit's own wording — and `e2e/tests/a-document-is-approved.spec.ts` already covers most of it, because [#182](https://github.com/sujanto-gaws/kelir/issues/182) and [#183](https://github.com/sujanto-gaws/kelir/issues/183) extended it as they went.

**Three of the six items are not in any browser flow**, and this is where that costs something rather than where it is merely noted:

| Item | State in the harness | What the demo does about it |
|---|---|---|
| #184 delegation | No flow | **Add one**, or demonstrate by hand and say so in the record. A window that routes a task is the sprint's least obvious feature and the one most worth seeing work |
| #185 due dates | No flow | The overdue indicator is a rendering decision made from a server flag; a browser is the only place that is observable |
| #186 conditional routing | No flow | The branch is visible in the history's routing trail, which is a screen this sprint added and nothing has looked at |
| #181 history | No flow | Covered incidentally by the approval flow's assertions on the workspace |

**The recommendation is to extend the existing flow rather than add three.** `a-document-is-approved.spec.ts` already builds a document type, a workflow and an approver; delegation, a due date and a branching condition are definition-level changes to the same fixture. Three new specs would rebuild that scaffolding three times.

**Cost, stated rather than discovered:** the harness needs a deployed stack, and so does the rehearsal in §5. Bring the stack up once and do both.

## 5. Step 3 — the release check, rehearsed at the close

§2's rule 3, and it is rehearsed **before** the tag so that a failure is a finding rather than a hotfix.

**The version bump comes first.** `kelir-backend/Cargo.toml` and `kelir-frontend/package.json` both read `0.4.0` and must move to `0.5.0` in a single `chore(release): v0.5.0` commit ([release process](../../docs/standards/04.%20Release%20Process.md) §4 step 3, checklist item 3).

**The `CHANGELOG` section exists and needs curating, not writing.** `[Unreleased]` already holds every Phase 5 entry; it becomes `[0.5.0]` with a date. **The release notes must say `v0.5.0` is not the MVP** — **D-1** put that at `v0.6.0`, and a reader who sees "end-to-end approvals" will otherwise assume it.

**Six migrations are new since `v0.4.0`** — `0024` through `0029` — and the N−1 rehearsal is the point of this step. §6's rule is *rehearse it, don't reason about it*, and one of the six is the reason:

| Migration | The N−1 question it raises |
|---|---|
| `0024_one_live_role_per_party` | **The only one that tightens rather than adds.** A partial unique index on `mdm_party_roles`, and the claim is that `v0.4.0`'s writer cannot reach the violation because it holds the party row under `FOR UPDATE`. That is the claim the rehearsal tests |
| `0025_workflow` | Ten tables `v0.4.0` does not know about |
| `0026`, `0027`, `0028`, `0029` | A `CHECK` on a table nothing writes; one new table; two nullable columns |

**The rehearsal, per §6:** migrate an empty database with the **`v0.5.0`** binary, then start the **`v0.4.0`** image against it and require `/health/ready`. Step 2 is the one that caught this at `v0.2.0` and the one most likely to be skipped. **Record the result either way** — a blank row reads as "passed" to everyone who comes later.

**Then the smoke pass**, from release images rather than the working tree, per §4 step 7: `/health`, `/health/ready`, `/health/live`, `/version` reporting the expected version *and* SHA, and the harness pointed at the address the deploy printed.

## 6. Step 4 — the tag, and the record

Checklist items 5 and 6: an annotated `v0.5.0` on the release commit with the changelog section as its message, then images built **from the tag** with `KELIR_BUILD_SHA` supplied — it is baked in at build time and is what `/version` reports, so it is not optional.

**The release record is `projects/releases/05. Release v0.5.0.md`**, from [the template](../releases/00.%20Release%20Checklist%20Template.md), and it carries the rollback result from §5 under *Staging → Rollback rehearsed* including a failure.

**Checklist items 7 and 8 cannot be satisfied as written.** There is no staging host and no production; **D-9** retired the staging clause in favour of the compose stack, and §4 step 7 says so in the release process itself. The record should say which check stood in for which, rather than leaving two blocking rows looking passed.

## 7. What could stop this, and what to do

| Risk | What it looks like | What to do |
|---|---|---|
| **No independent reader is available** | The pass does not happen, and the tag is cut on author-verified work for the third consecutive phase boundary | **Do not tag.** §2's rule is structural precisely so it is not a judgement call under time pressure. A phase that closes without it closes on nothing |
| **The pass finds something in a delivered claim** | A Phase 5 requirement is not what it says it is | Fix before the tag. That is the difference between finding it now and finding it in a released artefact |
| **The rollback rehearsal fails on `0024`** | The `v0.4.0` binary will not start, or starts and violates the index | It is a real N−1 break and the release notes need a maintenance-window plan (§6). Do not tag around it |
| **The demo cannot be driven because three items have no flow** | The demo becomes a description, which the exit criterion explicitly refuses | Extend `a-document-is-approved.spec.ts` (§4). If that is cut, the record says the three were demonstrated by hand — but it says so |
| **Docker or the compose stack is unavailable** | §4 and §5 both stall | They are the same blocker and the same fix; neither is worth attempting without it |
