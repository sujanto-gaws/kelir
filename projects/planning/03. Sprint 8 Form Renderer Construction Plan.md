# Sprint 8 Form Renderer Construction Plan

**Status:** Adopted · **Last updated:** 2026-08-26

This plan decomposes the three items behind FR-RAD-010 — [#162](https://github.com/sujanto-gaws/kelir/issues/162) render, [#163](https://github.com/sujanto-gaws/kelir/issues/163) evaluate, [#164](https://github.com/sujanto-gaws/kelir/issues/164) submit — into files, order, and the decisions each one has to take before it is written. It sits **one level below** the [Sprint Plan](01.%20Sprint%20Plan.md), which settles what is in Sprint 8 and why; nothing here changes that scope, and where the two disagree the sprint plan wins.

It exists because these three items are the phase's centrepiece and the first frontend work of the project to have a harness pointed at it. The sprint plan's own reason for splitting one requirement into three issues — *a renderer that is wrong about layout and a renderer that is wrong about arithmetic fail differently and should not be debugged together* — only holds if the split survives construction, and a split survives construction when the file list is written down before the first commit rather than after the third.

Related documents: the specification authority is [JSON Form Schema](../../docs/schema/JSON%20Form%20Schema.md) v2.0.1 with its two registries ([validation](../../docs/schema/JFSS%20Validation%20Rule%20Registry.md), [calculation](../../docs/schema/JFSS%20Calculation%20Rule%20Registry.md)); the engineering rules are [docs/standards/](../../docs/standards/), chiefly [coding standard](../../docs/standards/01.%20Coding%20Standard.md) §2.9 and [naming convention](../../docs/standards/02.%20Naming%20Convention.md) §4; the evidence behind the evaluator choice is the [operator-parity spike](../spikes/01.%20JFSS%20Operator%20Parity.md).

## 1. What this plans, and what it deliberately does not

| In | Out, and where it lives instead |
|---|---|
| Rendering every component the meta-schema defines | The form **builder** UI — FR-RAD-004, Phase 7 under **D-2** |
| Evaluating the `validate` and `calculate` expressions a definition carries | The rule **engine** — catalogue, dependency graph, cycle detection, error mapping. FR-RAD-006 in Sprints 14–16 under **D-2** |
| Server re-evaluation of `calculate` and `conditional` before persistence | Documents. FR-DOC-001..007 are Sprint 9 under **D-16** — a form that submits is not yet a document that exists |
| A submission row that proves the re-evaluation persisted | Numbering inside the submit transaction, which is Sprint 9's [#168](https://github.com/sujanto-gaws/kelir/issues/168) |

**The second row is the one that erodes.** Every engine concern can be argued into *"we need a little of it to make this work"*, and §5.2 below states the one place where this plan takes the cheap version on purpose and says what it costs.

## 2. The reference implementation, and what may be taken from it

The product owner named [KopiFormVue](https://gawshub.com/Sujanto/kopiformvue) as the reference for these three items. It is a Vue 3 + TypeScript + shadcn-vue + Tailwind 4 schema-driven form engine by the same author, MIT licensed, on the GAWS Gitea — the web interface requires a sign-in, `git clone` does not.

**It targets JFSS v2.0.0. Kelir is frozen at v2.0.1, and the differences land exactly on the two risky items.** That is not a reason to ignore it; it is a reason to take structure from it and semantics from the specification.

| Concern | KopiFormVue | Kelir, and the authority |
|---|---|---|
| Evaluator | `json-logic-js`, with `sum`, `map` and `filter` registered by hand in JavaScript | `@goplasmatic/datalogic-wasm` 5.2.0 through `lib/jsonlogic.ts` — **D-10**, JFSS errata **E-2** |
| Hidden fields | Payload carries visible keys only, and the validator **rejects** a hidden key that is present | S10.1.1 errata'd that as *not implementable*: every data key is submitted, the server discards hidden values |
| `calculateMode` | Absent | S4.2.3 Case B/C and S8.1.1: implementations MUST branch on the declared mode, never infer it |
| Error envelope | `{key, rule, message}` | S10.3: `{path, rule, code, message}`, dot-notation path for array rows |
| Validation | `zod` | Not a dependency of `kelir-frontend`, and adding one is a decision rather than an import |

**Two things are worth porting** — the recursive role dispatch in its `JfssRenderer.vue`, which is #162's mapping problem already solved, and its `useFormComponents` provide/inject registry, which decouples a renderer from a UI kit and gives #161's lookup component somewhere to register.

**Two defects come with them, and are fixed in the port rather than after it:** `JfssForm.vue` uses `JFSSArrayComponent` at three sites without importing the type, and the renderer formats a display component with a hard-coded currency prefix and two decimal places — formatting decided inside the renderer, which is #162's AC3 stated as an anti-pattern.

**One file is a checklist and not code.** Its `backendValidator.ts` is a browser-side *simulation* of a server, and §6.3's order of operations is that file's order with the v2.0.0 semantics corrected. Its unknown-rule branch returns `true`; S8.1.1 requires `400`.

## 4. Item 2 — render a published form definition (#162)

| File | Purpose |
|---|---|
| `src/types/jfss.ts` | JFSS **v2.0.1** types, from `jfss-meta-v2.0.1.json`. Carries `calculateMode`, the `columns` and `tabs` child-container shapes, `defaultValue` and `sequenceKey` — every one of which the v2.0.0 reference types lack |
| `src/api/rad.ts` | `getForm(id)`, thin through the shared client per the `api/auth.ts` pattern |
| `features/rad/renderer/registry.ts` | The **one place** mapping component `type` to component, and the explicit list of what is not yet rendered |
| `features/rad/renderer/JfssRenderer.vue` | Recursive dispatch over the four roles |
| `features/rad/renderer/useFormComponents.ts` | The provide/inject component registry |
| `features/rad/fields/*.vue` | Text, number, select, checkbox, textarea, date, **lookup** (over #161's endpoint), datagrid |
| `features/rad/layout/*.vue` | Section, columns, tabs, fieldset |
| `features/rad/FormRenderPage.vue` | The page the harness drives, plus its router entry |

**AC1 gets a mechanism rather than an intention — and its premise needed correcting first.** The criterion reads *"every component type the JFSS meta-schema defines"*, and **the meta-schema defines none**: it validates `type` as a bare `string`, because JFSS §4.4 makes it *"an open vocabulary defined by each implementation's component registry"*. So there is no upstream list to check against, and the walk-the-meta-schema test this plan first described would have enumerated nothing and passed forever. **Kelir's registry is the vocabulary**, which is the same position the backend takes for lookup sources when it calls its own check "a registry-level constraint… This is Kelir's registry".

What is checkable is the property the criterion is after: **no type used anywhere in the repository is undeclared.** `registry.spec.ts` discovers every JFSS fixture, walks each for every `type` it uses — through all three of §4.3.1's container shapes, so a narrowed walk goes red rather than quiet — and asserts each is either mapped or named in the not-yet-rendered list with a reason. That is the [Sprint 6 retrospective](../retrospectives/04.%20Sprint%206%20Retrospective.md)'s eighth action applied: *a test asserting a project-wide property discovers its subjects instead of listing them*. Adding a fixture that uses a new type fails the suite until the registry has an opinion about it.

**AC2 is a discipline, and its failure mode is specific.** The renderer must not become a second validator that disagrees with #156. It renders what was stored; it does not re-check the document against the meta-schema. An unrecognised `type` at runtime renders a visible placeholder naming that type — not a silent omission, which reads to a user as a form that is merely short, and not a refusal to render the whole form, which is #156's job and already done at save time.

**The evaluator is not imported in this pull request.** Not for layout, not for a conditional, not for a display component. This is what keeps the sprint plan's split real, and it is what makes #163's lazy-load criterion measurable rather than already violated.

**Verification (AC4, AC5):** `e2e/tests/render-a-form.spec.ts`, seeding the published definition over the API and asserting in the browser, per the arrange-over-API/assert-in-browser rule `e2e/support/api.ts` states. The harness drives the deployed stack rather than a dev server, so the spec needs `deploy/staging/deploy-local.sh` up — a real per-item cost, budgeted here rather than discovered.

## 5. Item 3 — the rendered form evaluates its own rules (#163)

`lib/jsonlogic.ts` is merged (PR #190) and does the hard part: it loads the engine on demand, registers `sum` as the single custom operator, and throws `EvaluationError` where the engine rejects an unknown operator. New work is `features/rad/renderer/useFormEvaluation.ts` and `features/rad/renderer/validation.ts`.

**#163 also carries D-24's configuration change, and carries it first.** It is folded in here rather than taken as its own branch because the composable's behaviour depends on it: written against `ReturnNull` and re-pointed afterwards, §5.6's blank-field rule would be tested against a `10.5 / 0` that silently returns `0`, which is the case the rule does not cover.

| File | Change |
|---|---|
| `modules/rad/evaluator.rs` | `DivisionByZeroHandling::ThrowError` in `jfss_config()` |
| `lib/jsonlogic.ts` | `division_by_zero: 'throw_error'` in `JFSS_ENGINE_CONFIG` |
| `evaluator.rs` tests | `a_fractional_division_by_zero_normalizes_to_zero` inverts to assert a refusal and is renamed to say so; `integer_division_by_zero_throws_rather_than_normalizing` loses the "rather than normalizing" it was named for, since the two paths now agree |
| `parity/` corpus | The four division cases, so the change is asserted by the gate rather than by one side's unit tests |

**The window this leaves is real and is named rather than hidden:** the registry states v1.6.0's requirement from 2026-08-26, and the code delivers it at #163 — so #162 is built and merged against an evaluator that still carries the old setting. Nothing in #162 evaluates anything (§4), so nothing in #162 can observe the difference; that is what makes the window safe rather than merely short.

### 5.1 Branch on the declared mode, never infer it

S4.2.3 Case B: `calculateMode: "derived"` — the default — makes the field *Derived State*. It is `readOnly`, re-evaluated whenever a dependency changes, and the computed value wins over runtime input, existing payload and `defaultValue` alike. Case C: `"generated"` resolves once, and a persisted value is **never** recomputed.

**This is net-new on both sides.** `calculateMode` appears in the meta-schema and in nothing else — no Rust reads it, no fixture carries it — so #163 and #164 are its first consumers and its test data is authored rather than borrowed. S8.1.1 states why inference is forbidden: it would require every language to maintain an identical operator classification, and the Calculation Rule Registry does not carry one.

### 5.2 No dependency graph, and what that costs

Re-evaluate **all** `derived` fields in definition order whenever any value changes. On a form of tens of fields that is a few dozen evaluations per keystroke, which is affordable, and it does not smuggle in the dependency graph **D-2** reserves for Sprints 14–16.

**Stated with its cost attached, because the cheap version is the right one only while it is written down as cheap.** A form of several hundred computed fields would need the graph; no form has that shape yet, and Sprint 14 should replace this having seen it rather than having discovered it.

### 5.3 An unrecognised rule name is an error

AC3 exists because the parity spike found the previously-named crate returning unknown operators instead of rejecting them. The engine now covers that case. **What #163 adds is the other half:** a validation *rule name* absent from the Validation Rule Registry must raise, not skip. The default branch in `validation.ts` throws.

The reference implementation has the wrong version of exactly this line — an unknown server rule returns `true`, commented as failing open. A rule that fails open is a rule that is not there, reported as a rule that passed.

### 5.4 `sum` comes from one place

Calculation Rule Registry §4.3 forbids reimplementing standard operators, and AC2 requires the `sum` #154 registers rather than a local one. A test asserting that no operator registration exists outside `lib/jsonlogic.ts` costs one grep and holds the property for every field component added later.

### 5.5 The bundle condition is a build assertion, not a unit test

**D-10** accepted 588 KB gzipped on one condition: the engine stays off the first-load path. No unit test can observe that. A CI step reading the Vite build manifest and asserting the engine chunk is not reachable from the entry chunk can — and that is the form the condition should take, per the [Sprint 7 retrospective](../retrospectives/05.%20Sprint%207%20Retrospective.md)'s judgement that the actions which held were encoded in a standard and in a test, and the ones that failed were encoded in a retrospective.

### 5.6 A calculation that fails renders blank

Per **D-24** (§8), a division by zero fails evaluation rather than yielding `0`, and an absent operand into `min` already did. **On a zero-filled payload both happen before the user's first keystroke** — `{"/": [{"var": "total"}, {"var": "count"}]}` fails while `count` is still the `0` S12.4 put there.

So a computed field whose expression fails renders **blank**, and nothing about it blocks typing: no error styling, no message, no invalid state. The refusal belongs at submit (§6.3), where the user has finished and the answer is either right or refused. **A form that greets its user with three red fields it filled in itself is a worse failure than the one D-24 prevented.**

The distinction §5.3 draws still holds and is not softened here: an unrecognised *rule name* is a defect in the definition and raises loudly at render. A *calculation over data the user has not entered yet* is the normal state of a form being filled in.

**Verification (AC5):** `e2e/tests/a-form-calculates-and-validates.spec.ts` — a quantity and a price typed into a real browser, the total seen to update, a required field left empty and the submit seen to be blocked with the message the definition supplies.

## 6. Item 4 — submit, and the server re-evaluation behind it (#164)

### 6.1 Where a Sprint 8 submit lands

The sprint exit requires the server to persist its own answer and AC3 requires a **stored row**, while every document item is explicitly Sprint 9's. **Decision: a RAD-owned submission table**, `0021_rad_form_submissions.sql` — `0020` is the current head — carrying the base fields naming convention §4.2 requires plus `form_id`, `form_revision`, `payload_json` and `submitted_at`.

`payload_json` holds **the server's answer and never the client's**. The two alternatives were considered and rejected: writing into `documents.form_data_json` pulls a slice of [#167](https://github.com/sujanto-gaws/kelir/issues/167) forward against the sprint plan's explicit exclusion, and a stateless evaluate endpoint satisfies neither AC3 nor the sprint exit without amending both first.

### 6.2 The split that Sprint 9 depends on

| File | Purpose |
|---|---|
| `modules/rad/service/evaluation.rs` | **Pure.** Definition plus submitted payload in, secure payload or error envelope out. No database, no permission check |
| `modules/rad/service/submission.rs` | Permission, tenant scope, calls the above, persists |
| `modules/rad/domain/submission.rs`, `modules/rad/repository/submission.rs` | The row |
| `modules/rad/handlers.rs` | `POST /api/v1/rad/forms/{id}/submissions` |

**The separation is the deliverable, not a preference.** Sprint 9's entry criterion says its item 2 *submits through* #164's re-evaluation; that sentence is true only if the re-evaluation is callable from inside [#168](https://github.com/sujanto-gaws/kelir/issues/168)'s numbering transaction without dragging a submission row along with it.

### 6.3 The order of operations

1. Accept a payload carrying **every** data key, hidden ones included. **Do not reject a hidden key that is present.** That is the reference implementation's conditional rejection, and S10.1.1 errata'd it as not implementable — it turns a legitimate submission into a `400` whenever one hidden field's conditional depends on another.
2. Zero-fill missing keys per S12.4, in the form errata **E-1** restated for `serde_json`: a missing key resolves to `Value::Null`, not to a typed zero.
3. Re-evaluate every `conditional` against the **complete** payload, and **discard** the values of components computed as hidden. Discard, not reject.
4. Re-evaluate every `calculate` by declared mode — `derived` overwrites unconditionally, `generated` only where the stored value is null or absent.
5. Run `validation` and the `rules` scoped `server` or `both`. An unknown rule is a `400` (S8.1.1), never a pass.
6. Persist. An evaluation failure is a 4xx carrying the S10.3 envelope with a dot-notation `path`, never a partial write. **This is where a division by zero lands** (**D-24**, §8): blank on the screen while the form is being filled in, a named refusal when it is submitted.

### 6.4 The security-control test, and the gate that will make it lie

AC3 and AC4 are one thing: a test that posts a total the rules do not produce, asserts the stored row holds the computed value, and **has been seen to fail** against a build without the overwrite. Coding standard §2.9 makes the red run the evidence, cited against the named test.

**The mutation will come back green if the fixture does not reach step 4, and that is the likely outcome rather than a remote one.** It is what §2.9 calls a gate; it is what happened to #106 across six queries in Sprint 6; and it happened again on #161 this month, where removing one permission check left a lookup test passing because a second check below it absorbed the mutation. A caller without the submit permission, a form that is not `PUBLISHED`, or a definition in another tenant all refuse before any expression is evaluated, and every mutation beneath them then reports coverage that does not exist. **The fixture is built to reach step 4**, and the pull request states which steps its mutations covered and which they did not.

A second control test and a second mutation cover AC2's hidden-field case: a value submitted for a field the conditional hides is absent from the stored row.

### 6.5 Client and server agree, or the submission is refused

AC5 extends the existing corpus — `tests/jsonlogic_parity.rs` and `src/lib/jsonlogic.parity.spec.ts` over [`parity/`](../../parity/README.md) — from expressions to whole-form submissions. Where the two disagree the submission is refused with the error envelope rather than silently corrected: **a form that changes your number without saying so is its own defect**, and the spike's grand total of 0 in place of 42 is what the silent version looks like.

### 6.6 Frontend

`api/rad.ts` gains `submitForm`. The renderer submits every data key per S10.1. S10.3 errors map through the existing `composables/useFormErrors.ts` by `path`, which is why the envelope names it `path` and not `key`.

## 7. Sequence and verification

**#162 → #163 → #164, strictly.** #163's browser criterion needs #162's page to drive; #164's parity criterion needs #163's displayed value to compare the server's answer against.

**The mid-sprint independent pass runs between #163 and #164, not after #164.** It is the [Sprint 7 retrospective](../retrospectives/05.%20Sprint%207%20Retrospective.md)'s first action and a Sprint 8 entry criterion, and its whole content is that an allowance cannot be spent on findings that arrive last. Placing it after the security-critical item would reproduce exactly the Sprint 7 shape it was written to prevent: seven findings filed at the close, none closed.

Each of the three items carries a harness criterion, and none of their status rows may read `verified by inspection only` — #162's AC5 makes that a finding rather than a formatting choice.

## 8. Decisions

**Division by zero is settled as D-24, 2026-08-26: every division by zero is an evaluation error.** Both sides configure the engine with `ThrowError` in place of `ReturnNull`, so `10 / 0`, `10.5 / 0`, `0 / 0` and `10 % 0` behave identically rather than splitting on whether the numerator happens to be fractional. The uniform `0` the Calculation Rule Registry asked for from v1.0.0 was never reachable by configuration — the engine's integer division path throws under every available setting — and `0` is the wrong answer besides: an average over zero scores is not zero. Recorded in [Product Backlog](02.%20Product%20Backlog.md) §6.1, applied to the registry at **v1.6.0** and to [`parity/README.md`](../../parity/README.md).

**What that leaves this plan to build**, in three places rather than one:

- §5 — a field whose calculation fails renders **blank** and does not block typing. It is not an error state on a form the user has barely started, because on a zero-filled payload an average field fails before the first keystroke.
- §6.3 step 5 — the same failure at submit is a refusal, with the S10.3 envelope naming the field.
- The configuration change on both sides, its two pinned tests and the parity corpus cases are **folded into #163 and taken first within it** — §5 lists the four files and says why the order matters. The registry states v1.6.0's requirement from today and names that gap until they land.

[#201](https://github.com/sujanto-gaws/kelir/issues/201), which the sprint plan's second entry criterion left owed at this sprint's planning, is **closed**: a multi-argument `sum` is refused rather than silently zero, so #164 can no longer confirm the zero that criterion warned about.
