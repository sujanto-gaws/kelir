# Party Surface Verification — 2026-08-21

**Status:** Final · **Last updated:** 2026-08-21

**Subject:** the master-data party surface delivered by #80 and #81 (PRs #91, #92, #93, #94) · **Issue:** #96 · **Outcome:** seven defects, three of them release-blocking for `v0.3.0`

> **First record of its kind.** [Sprint plan](../planning/01.%20Sprint%20Plan.md) §2 makes an item whose author is also its only verifier `In progress` rather than Done, so records like this one will recur. The shape below is provisional — a template belongs here once there is a second instance to generalise from, not before.

## Why this pass happened

Sprint 5 delivered the party surface and **verified it with the agent that wrote it**. It filed zero issues against itself, against Sprint 4's twelve. The [Sprint 5 retrospective](../retrospectives/03.%20Sprint%205%20Retrospective.md) recorded that a zero read that way measures nothing: it is consistent with clean work and equally consistent with nobody having looked.

This pass establishes which. **It was nobody having looked.**

## Method

The verifier was independent of the author and worked from #96's brief. It read all 55 `sqlx::query*` invocations in `repository/`, the service's permission gates and transaction boundaries, the route bindings, the migrations' unique indexes, and all 49 tests in the four master-data binaries. It wrote 15 route-level probes against a real PostgreSQL through the real router, and ran **18 mutations** against the existing suite — each compiled, each executed, each reverted before the next.

Baseline before and after: 188 unit tests and 107 integration tests green across 17 binaries, working tree byte-identical.

**Six mutations came back STILL GREEN**, in two clusters. Those are findings F6 and F7.

## Findings

| # | Finding | Severity | Issue |
|---|---|---|---|
| F1 | Deleting a party leaves its roles and profiles live, permanently burning the supplier / customer / employee number | **High** — unrecoverable data integrity | [#103](https://github.com/sujanto-gaws/kelir/issues/103) |
| F2 | `PUT .../roles/{roleTypeId}` returns every profile — bank account, credit limit — to a caller without `master-data:party-role:read` | **High** — authorization bypass | [#104](https://github.com/sujanto-gaws/kelir/issues/104) |

| F6/F7 | Four tenant and soft-delete tests assert a query they never exercise, hiding at least six queries including `list_parties` | **High as a coverage defect** — the code is right today and nothing would catch it changing | [#106](https://github.com/sujanto-gaws/kelir/issues/106) |
| F4 | A reused party code silently re-targets stored references to a different legal entity | Medium | [#107](https://github.com/sujanto-gaws/kelir/issues/107) |
| F5 | Unscoped joins, latent behind today's write paths — and a module doc that promises every query is scoped | Medium | [#108](https://github.com/sujanto-gaws/kelir/issues/108) |
| F8 | An over-long `purposeTypeId` returns 500 where the contract promises 422 | Low | [#109](https://github.com/sujanto-gaws/kelir/issues/109) |

Every finding was **re-confirmed against the source by the main session** before being filed. None rests on the verifier's report alone.

Two of them the author had already written the rule for and then broken elsewhere: `remove_role` documents that an orphaned profile would hold a number the next party needs, and `delete_party` orphans one (F1); the service documents `master-data:party-role:read` as existing because profiles carry bank accounts, and one of three routes ignores it (F2). **Stating an invariant in a comment is not enforcing it.**

## What was checked and found sound

Recorded because absence of findings only means something with a boundary around it.

- **`replace_contact_mechs` orphan cleanup** — the specific two-party shared-mechanism case was built. The mechanism survives for the party still using it. Correct as written.
- **Transactionality** — three separately injected mid-operation failures all rolled back with no partial state, including `write_profile` and a failed `create_party`.
- **`deny_unknown_fields`** — all 17 request structs carry it; five were exercised through the router beyond the one that had a test.
- **Route-to-permission binding** — three mutations red. The permission tests are real.
- **Server-side derivation of `display_value`** — mutation red.
- **Every other profile leak path** — the list summary, the audit `new_value`, the 409 message, the OpenAPI examples, `create_party` and `update_party`. F2 is the only leak, and it is real.

## What was not reached

- The frontend — there is none for parties yet.
- `mdm_facilities`, `mdm_products`, `mdm_services`, `master_data_source_references` — created by `0008`, unused by any Sprint 5 path.
- Concurrency on `replace_contact_mechs`. The role-assignment race was proven; this one was not attempted.
- Whether F5's unscoped joins are reachable from a module written before Sprint 5. Every Sprint 5 write path was read and they are not.

## What this changes about how the project verifies

**A single passing probe is not evidence.** The verifier's first concurrency probe passed and F3 was nearly recorded as sound; it surfaced on the thirtieth run, and only against a role type with no profile table — the profile's unique index was masking the duplicate into a spurious 409. Mutation gave a signal that could be trusted. One green run did not.

**The dud test pattern is habitual, not incidental.** #94 found one test that could not fail and treated it as a one-off. It is in four tests across two files, and the mechanism is always the same: the assertion is aimed at a route that refuses early, so the gate absorbs every mutation beneath it. F6 was not on the author's list of suspects and is the more dangerous of the two clusters, because `list_parties` is the module's highest-traffic read.

**The independence was the whole difference.** The author ran twenty mutations over this surface and found one gap. The independent pass ran eighteen and found seven defects. The author's mutations were aimed where the author already believed the risk was.
