## 3. Findings

### Finding 1 — the pattern refusal closes three silent divergences and leaves at least three open, and two documents say the question is resolved. **Not blocking.**

**`caf\b` matches `café` in the browser and does not on the server; `[[:digit:]]` and `\p{Nd}` are the same defect in the other direction; all three are stored without a word.**

Item 3's `PATTERN_CLASS_NOT_PINNED` exists because a construct that **compiles on both sides and means different things** is worse than one only the server enforces — [ADR-0038](../../docs/architectures/adr/0038.%20Kelir%20Patterns%20Are%20the%20Linear-Time%20Subset.md) §1 and the [Validation Rule Registry](../../docs/schema/JFSS%20Validation%20Rule%20Registry.md) §1 Semantic Parity requirement in their own words. `rad::domain::validation::unpinned_class` implements it as a scan for `\d`, `\D`, `\w`, `\W`, `\s`, `\S` and nothing else.

**Executed on both engines, then against the save seam:**

| Pattern | Subject | ECMA-262 (`node -e`) | `regex` crate | `POST /api/v1/rad/forms` |
|---|---|---|---|---|
| `caf\b` | `café` | **`true`** | **`false`** | **`201 Created`** |
| `^[[:digit:]]+$` | `12` | **`false`** | **`true`** | **`201 Created`** |
| `^\p{Nd}+$` | `12` | **`false`** | **`true`** | **`201 Created`** |
| `^\d{4}$` | `١٢٣٤` | `false` | `true` | `422` `PATTERN_CLASS_NOT_PINNED` |

The last row is the one the sprint closed. **The first three are the identical failure — two runtimes, opposite verdicts, one input, nothing raised on either side — and the definition is stored.** `\b` is the sharpest of them because it is ordinary: ECMA-262's `\b` is defined over the ASCII word set and this crate's over the Unicode one, so any pattern anchoring on a word boundary in a form that accepts non-ASCII names diverges. `unpinned_class` cannot see it, because `\b` is not one of the six letters it looks for.

**The cause is in the decision, not in the scan.** [ADR-0038](../../docs/architectures/adr/0038.%20Kelir%20Patterns%20Are%20the%20Linear-Time%20Subset.md) §2 defines the dialect as *"what the `regex` crate compiles, with character classes written out"*, and registry 1.4.0 says the params schema is *"constrained to what the Rust `regex` crate honours"*. **That definition is a superset of ECMA-262 in exactly the directions parity is about**: POSIX bracket expressions and `\p{…}` are constructs the crate compiles and a browser cannot read at all, and the decision invites them. §4's *Consequences* names lookahead and backreferences as the cost and says nothing about the constructs the widening admits.

**Why this is not blocking.** The sprint moved the situation strictly forward: the loud half is fixed, the commonest silent case is refused, and the alternative — `fancy-regex` — is correctly rejected on the NFR. Nothing here is a regression. **What is wrong is the claim of completion**: registry 1.4.0's changelog says the open question is *resolved*, ADR-0038 is `Adopted`, and §1's Semantic Parity requirement is still violable by a pattern the product accepts today.

**The probe.** `kelir-backend/tests/zz_probe_pattern_dialect.rs` (deleted): a `#[test]` building each pattern with `regex::RegexBuilder` and printing `is_match`, and a `#[tokio::test]` posting each as a `regex` rule's `params.pattern` through `POST /api/v1/rad/forms` and printing the status and the S10.3 `code`s. The ECMA-262 column is `node -e '/caf\b/.test("café")'` and its three siblings, run against the same engine `validation.ts` uses.

### Finding 2 — the `v0.7.0` upgrade notes tell a deployment that nothing new breaks, and something does. **Blocking.**

**A form that works today, with `^\d{4}$` on a field, cannot be published again after this upgrade — and the changelog says such a pattern "was already rejecting every value at submit time".** It was not. It was matching.

[`CHANGELOG.md`](../../CHANGELOG.md) `## [0.7.0]` → *Upgrade notes*, third bullet, in full:

> **A stored pattern that this backend cannot compile is now refused when the definition is saved.** A form whose `regex` rule or `validation.pattern` uses lookahead, a backreference, **or a bare `\d`, `\w` or `\s`** was accepted before and is refused now, as `PATTERN_NOT_COMPILABLE` or `PATTERN_CLASS_NOT_PINNED`. **Such a pattern was already rejecting every value at submit time** — the evaluator maps a compile error to *no match* — so this moves an existing failure to the moment it can be fixed rather than creating one.

**The antecedent of *such a pattern* is all three forms, and the gloss after the dash is true of one of them.** `matches_pattern` maps a compile error to `false`; `^\d{4}$` does not produce a compile error. Executed: the crate builds it and `is_match("1234")` is `true`. **So for the `PATTERN_CLASS_NOT_PINNED` half there is no existing failure to move, and the sentence's conclusion — *rather than creating one* — is false in the only direction that costs an operator anything.**

**What actually happens, driven end to end.** A definition was written straight into `rad_forms` the way `v0.6.0` would have stored it, with `^\d{4}$` on a `regex` rule, and the publish seam asked:

```
PROBE publish stored-bare-d => 422 Unprocessable Entity
{"error":{"code":"VALIDATION_ERROR","details":[{"code":"PATTERN_CLASS_NOT_PINNED",
"message":"`code`'s pattern `^\\d{4}$` uses `\\d`, …","path":"definition.components.0.rules.0.params.pattern"}]}}
```

`rad::service::form::publish_form` re-validates the **stored** definition — deliberately, and rightly ([#338](https://github.com/sujanto-gaws/kelir/issues/338)) — so the refusal reaches every draft that predates the check. `create_revision` copies the source definition when a request carries no new one, which means **a title-only revision of a live form produces a draft that cannot be published.** A published revision is immutable, so the form is not broken; it is frozen at its current revision until somebody rewrites the pattern.

**And the remedy the note gives is itself a behaviour change.** `[0-9]` is not what `\d` was doing on the server: `^\d{4}$` matches `١٢٣٤` under the `regex` crate and `^[0-9]{4}$` does not. **Rewriting the pattern narrows what the server accepts on a form that already has data behind it**, which is a decision a deployment should be told it is taking.

**Why blocking.** The upgrade notes are the one place a deployment is told what this release asks of it, and this is the release that makes the change. The note is not merely incomplete — it states the opposite of the case, and it does so under a heading that says *three things a deployment does at this upgrade*. **The accurate statement already exists sixty lines further down**, in *Added*: *"A bare `\d`, `\w` or `\s` is refused too … it compiles on both sides and means different things."* The two sentences describe the same change and only one of them is true. The fix is one paragraph and no code; the reason to hold the tag for it is that a changelog is read once, at the upgrade, by somebody who will not read the *Added* section.

### Finding 3 — the release gate is defeated by three edits, each one character to one line wide, and none of its four rules notices. **Not blocking, and one of the three will be exercised this week.**

**A `Final` `v0.7.0` record can cite a verification record that does not exist, and the suite stays green.**

`releases_are_independently_verified.rs` was attacked with four synthetic records written into `projects/releases/`, one at a time, each followed by `cargo test --test releases_are_independently_verified`. **The positive control was run last and reddened**, which is what says the other three results are the gate not firing rather than the probe not arriving.

| # | The record | Result |
|---|---|---|
| A | `08. Release v9.9.9.md`, `**Status:** Final`, citing `../verifications/99.%20A%20Pass%20That%20Was%20Never%20Written.md` | **6 passed, 0 failed** |
| B | `09. Release 9.9.10.md` — the `v` dropped from the file name — `Final`, citing nothing | **6 passed, 0 failed** |

| **Control** | `08. Release v9.9.9.md`, house separator, `v` in the name, `Final`, citing nothing | **`a_governed_release_cites_a_verification_record` FAILED** |

Each is a different door into the same room:

- **A — `citations()` never asks whether the file exists.** It matches the substring `verifications/`, takes up to the first `)`, space or newline, and keeps it if it ends `.md`. A novel string satisfies rule 2 because it is novel, not because it resolves. The module doc's *What this deliberately does not check* names two limits — whether the pass ran, and whether it read this release — and **this is a third one it does not name, and a larger one: those two admit a pass of unknown quality, this one admits no pass at all.**
- **B — `version_in()` requires the literal `Release v`.** A record whose name says `Release 9.9.10` is not in `release_records()`, so it is governed by nothing *and rule 4 cannot see it either*. Rule 3's three floors are exactly slack enough to let it through: `all.len() >= 6` against seven real records, `governed.len() >= 4` against four, `cited.len() >= 4` against six. **The floors are constants that do not grow with the directory**, so every release after the fourth widens the gap between what the walk governs and what it would still accept.
- **C — `header_status()` truncates at `·` and `says_final` compares to the exact string `Final`.** Any other separator leaves the rest of the line inside the status, so the comparison fails and the record is ungoverned — while rule 4 passes, because a status *is* stated. **This is the hole rule 4 was written to close, in the shape rule 4 does not cover: rule 4 makes the line mandatory and says nothing about what is on it.**

**None of these is an accusation of carelessness — the file is the most carefully argued test in the repository, and `#407` was itself a fix to this detector found the same way.** The point is narrower and is the one `#406`'s own note makes: *a control that reads a document is a control a document can trip*. Three more ways remain.

**Why one of them matters immediately.** Door A is not a hypothetical evasion; it is the ordinary failure mode of a hand-written link. [Record 07](../releases/07.%20Release%20v0.7.0.md) has to cite this record by typing a percent-encoded relative path, and **if that path is typed wrong the gate goes green anyway and `v0.7.0` tags on a citation that resolves to nothing.** The single-line fix is to `stat` each cited path and fail on one that does not exist; door B costs a filename convention asserted rather than assumed; door C costs comparing against a vocabulary rather than a string.

**Why not blocking.** The gate does its job against the honest case — the control proves that — and it has already produced its intended effect once, in [record 07](../releases/07.%20Release%20v0.7.0.md)'s blocking row. Nothing here is a reason to tag without a pass; it is a reason to close the doors before the next release leans on it harder.

### Finding 4 — the first release the gate governs is about to be unblocked by a record that fails §2's own criterion, and nothing in the tree can notice. **Blocking, as a claim rather than as code.**

**§2's criterion is a `git log` fact; the gate reads a citation string. This record satisfies the second and, for five commits including all four of the release run, fails the first.**

**What is and is not compromised.** Five of the six items and `#398` were read by a session with no trailer in their commits, and §3's findings 1, 3 and 5 land on three of those. **Why blocking, and what would discharge it.** The tag is the thing §2 attached the requirement to, so a tag taken on a record that fails §2's stated criterion is the rule being satisfied in form and not in substance — on its first outing, which is the outing that sets what it means. Two ways out, and the choice is the product owner's:

1. **A reader with no trailer in `d755a4f..191662e` reads item 6 and the four release commits** and adds a record, or a section to this one. That is the criterion met.

That is the criterion consciously waived, which is a decision. **What must not happen is the third thing: the gate goes green, the record is cited, and the shortfall is discoverable only by somebody who runs `git log` themselves.** This section exists so that cannot be what happens.

#### Finding 6 — the rewritten upgrade note gives a false reason for refusing `\s`. **Blocking, as a one-clause correction — made in the change that adds this section.**

**The note says a bare `\d`, `\w` or `\s` is refused because *"ECMA-262's classes are ASCII, this crate's are Unicode."* For `\s` that is false.** ECMA-262 defines `\s` by its WhiteSpace and LineTerminator productions, which take in every Unicode space separator. Executed on both engines:

| Subject | ECMA-262 `^\s$` | `regex` crate `^\s$` |
|---|---|---|
| U+0020 space | true | true |
| U+00A0 no-break space | **true** | true |
| U+3000 ideographic space | **true** | true |
| U+2028 line separator | **true** | true |
| U+0085 next line | false | **true** |
| U+FEFF byte order mark | **true** | false |

The `u` flag changes none of these. **`\d` and `\w` do behave as the note says** — U+0663 and `é` are `false` in ECMA-262 and `true` in the crate.

**So the refusal is right and its stated reason is wrong.** `\s` does diverge — at exactly two code points, in opposite directions — which is enough to break Semantic Parity and to earn `PATTERN_CLASS_NOT_PINNED`. What the note gets wrong is *how*, and *how* is what an operator acts on. Taken at its word, the ASCII rewrite of `\s` is `[ \t\r\n]`, and that narrows **the browser as well as the server**: a no-break space pasted into a field stops counting as whitespace on both sides, where both counted it before. The note warns that `[0-9]` narrows `\d`; it gives no such warning for `\s`, because its premise says there is nothing to narrow.

**Why blocking, by this record's own standard.** §3 held the tag for finding 2 because the upgrade notes are the one place a deployment is told what the release asks of it. This clause sits in the paragraph rewritten to discharge finding 2, written after the pass by the session finding 4 is about — **it is the case for this section in one example.** The same clause stands in *Added*, and §3 quoted that sentence as *the accurate statement* and stopped one clause short of this one: the pass read it and did not run it, and `node -e` settles it in a line.

**Where else it stands, and what is not touched here.** The same sentence is the message of the S10.3 detail the product returns — the `PatternRefusal::UnpinnedClass` arm in `rad::domain::engine`: *"ECMA-262's classes are ASCII and this crate's are Unicode … Write the class out: `[0-9]` rather than `\d`"*. It is sent for `\s` and `\w` too, so **an author whose pattern uses `\s` is told to write `[0-9]`**. That is item 3's code, product text rather than release text, and it needs a change with its own reader; it is recorded here and belongs with [#413](https://github.com/sujanto-gaws/kelir/issues/413). It does not block — it is a wrong explanation attached to a right refusal. The doc comments on the same code (`validation.rs:150` and `:408`, `validation.ts:154`, `engine.rs:98`), ADR-0038 §1 and the registry's note all say `\d` alone, and are correct.

**Corrected in this change**, in both places in `CHANGELOG.md`: `\d` and `\w` are ASCII in ECMA-262 and Unicode here; the two `\s` sets are both Unicode and differ at U+0085 and U+FEFF; and writing `\s` out as an ASCII class narrows both sides. **That correction is this session's own text, and nobody else has read it.** It is three clauses, each resting on the table above, which is the most that can be said for it.
