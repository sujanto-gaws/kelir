## 3. Findings

### Finding 1: a resubmit during a task path deadlocks, and one side answers 500. **Blocking. [#663](https://github.com/sujanto-gaws/kelir/issues/663).** Answers subject 1, through a foreign key the subject did not name.

**The two orders are opposite.**
- **A resubmit** takes the document `FOR UPDATE` (`document/service/submit.rs:205`), then the instance `FOR UPDATE` (`:556`).
- **Every task path** takes the instance, then the task (`lock_instance_then_task`, `workflow/service/task.rs:790`; `decide`, the same pair), then inserts a `workflow_task_history` row. **That row's `document_id` references `documents`** (`0025_workflow.sql:324`), so the insert takes `FOR KEY SHARE` on the document.

**P1**:
1. A document was returned, so its instance waited at `RETURNED` on the owner's correction task.
2. The test held the target role, so an administrator's reassign of that task parked after it had locked the instance and the task.
3. The owner's resubmit was seen blocked in `lock_instance`'s `FOR UPDATE`.
4. The role was released.

**The reassign answered 200, and the resubmit answered `500 INTERNAL_ERROR`**: *"deadlock detected"*, with `pg_stat_database.deadlocks` going from 0 to 1.

**The claims.** ADR-0042 §2 says *"Lock order: the instance, then the task, then the role … The instance is taken whether the path names it or not: the `workflow_task_history` row's foreign key to `workflow_instances`"*. Database Schema §7.7 says *"An insert here takes the instance"*. Record 20's finding 2 split the earlier version of the same claim, so **this is the second split, and sprint plan §2 (a) strikes the claim rather than narrowing it a third time.** `CHANGELOG.md`'s #619 entry names only the three paths during a reassign, and it is still true.

**How far it reaches.** Only a state with an open task and an editable status. **In that shape a resubmit whose next state raises a task is refused with a 409 anyway (finding 5)**, so there the deadlock turns a 409 into a 500. A resubmit to a state with no task is not refused, and there either side can be the one aborted.

### Finding 2: texts say metadata addresses are never allowed, and seven translated forms pass. **Blocking, as a claim. [#664](https://github.com/sujanto-gaws/kelir/issues/664).** Answers subject 6.

**The texts.**
- User Manual §11.5: *"Loopback, link-local and cloud metadata addresses never are."*
- The `EGRESS_REFUSED` text (`test-call-outcome.ts:56`) says the same.
- ADR-0043 §4: *"The server cannot be pointed at its own loopback, … the four metadata addresses §2 names"*.

**P5**: with no allow-list, `check` answered `Ok(())` for each of these:
- `64:ff9b::a9fe:a9fe` and `64:ff9b:1::a9fe:a9fe` (NAT64);
- `64:ff9b::7f00:1` (NAT64, loopback);
- `2002:a9fe:a9fe::1` (6to4);
- `2001:0:4136:e378:8000:63bf:5601:5601` (Teredo);
- `::ffff:0:a9fe:a9fe` (IPv4-translated);
- `64:ff9b::6464:64c8` (NAT64, Alibaba's metadata address).

**D-103 made this a stated limit, and the brief says that restating it is not blocking.** These three texts do not restate it: they say the opposite, which is the brief's blocking case. **The texts row 17 dated do state it plainly**: ADR-0043 §2 and §6, SDD §9.3.6, Installation §7.1, the `CHANGELOG` and record 09. The IPv4-mapped and IPv4-compatible forms are unwrapped and refused.
