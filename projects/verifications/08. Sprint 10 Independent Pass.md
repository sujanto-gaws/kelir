## 3. F1 — a `DEPARTMENT_ROLE` task is decidable from any department

**[#225](https://github.com/sujanto-gaws/kelir/issues/225), `Must` — closed 2026-08-28, before Sprint 11's construction began.**

[JWSS §5.3](../../docs/schema/JSON%20Workflow%20Schema.md) names the column this assignee type resolves against: *"`roles` plus `user_roles.department_id`, which has carried a department-scoped grant since `0002`"*.

`assignment::resolve` honours it — reads the `departmentScope`, resolves `REQUESTED_DEPARTMENT` / `OWNER_DEPARTMENT` / a literal code, refuses a code naming no live department, and writes `candidate_department_id` onto the task. **Nothing after it does.** `repository::task::holds_role` filters `user_roles` on tenant, user, role and validity window and not on department; it is what both `decide` and `claim_task` authorize against. `repository::inbox`'s candidate arm matches `candidate_role_id` with the same four predicates.

The column is written, selected and rendered, and **appears in no `WHERE` clause anywhere in the backend**. A task the definition offered to Finance's approver is visible to, and decidable by, any holder of that role in any department or in none.

**Demonstrated rather than argued.** `a_department_scoped_task_is_not_decidable_from_another_department` in `tests/workflow_engine.rs`: an approver whose `user_roles` grant is Procurement's approves a task scoped to Finance and the document reaches `COMPLETED`. 200 where the test demands 403.

**Why the campaign could not reach it.** The defect is an **absent** predicate. There is no clause to mutate, and a campaign over existing clauses is structurally blind to it. The existing tests point the same way: `DEPARTMENT_ROLE` is covered in `workflow_definitions.rs` (save-time validation) and in `assignment.rs`'s unit tests (normalization — that a rule *becomes* a principal carrying a department). The half that was built is tested; the half that was not, is not.

**It is not an exotic path.** `DEPARTMENT_ROLE` is the assignee type JWSS §5.1's own worked example uses, and the one §5.3 recommends as the replacement for the refused `MANAGER_OF_OWNER` — *"Use `DEPARTMENT_ROLE` with the approving role, which is what a manager approval means in terms Kelir can resolve."*

**Closed.** `holds_role` takes the task's `candidate_department_id` and filters on it; `lock_task` and the by-instance lock now read the column, because a check made against a field the locked row did not fetch is a check made against the pool. The three candidate arms in `repository::inbox` became correlated `EXISTS` clauses carrying the same predicate, so the queue and the decision answer identically. **D-39** records the question the fix had to answer first — what a grant naming no department means — and why it is the broader reading.

Three tests, each seen red against its own predicate removed and green against the other's: the original quarantined one, `a_department_scoped_task_is_decidable_by_that_department` (so the fix cannot be *refuse everyone*), and `a_department_scoped_task_is_listed_only_to_that_department` for the inbox arm. **The inbox one was vacuous when first written** — it matched on `taskId` where the payload says `id`, so the negative assertion passed against nothing. It is the [#106](https://github.com/sujanto-gaws/kelir/issues/106)/[#121](https://github.com/sujanto-gaws/kelir/issues/121) shape one more time, caught here only because the positive assertion beside it failed.

## 4. F2 — a transition's `allowedBy` is stored, validated, and never enforced

**[#226](https://github.com/sujanto-gaws/kelir/issues/226), `Should`, open.**

JWSS **S5** requires `allowedBy` on every non-`AUTO` transition. Kelir parses it into `Transition::allowed_by`, validates its assignee type at save beside the task assignment's, and projects it to `workflow_transitions.allowed_by_json`. That column appears exactly once in the backend — in the `INSERT` that writes it. Neither `service::engine` nor `service::task` mentions `allowedBy` at all, including in a comment.

**Not currently exploitable, and that is the reason to fix it now.** `engine::fire` has one caller, `service::task::decide`, so every transition today is fired through a task decision gated by the *task's* assignment. Where the two name the same principal they agree. JWSS's own §8 example has them differ — `RETURNED → MANAGER_APPROVAL` on `RESUBMIT`, `allowedBy: OWNER`, out of a state declaring **no task** — and [#183](https://github.com/sujanto-gaws/kelir/issues/183), Sprint 11's return action, is what builds that edge. Filing before #183 is the point: one call site to fit a check to now, a retrofit across return, delegate and resubmit later.

**The disclosure half is separate and also missing.** `service::engine`'s header is scrupulous about this exact class of thing — it has a section for `guards`/`actions` being stored and not executed, and another for `AUTO` transitions not firing, both closing on *"a stored handler must not read as evidence that it runs."* `allowedBy` is in that position and is named in neither the header nor JWSS §5.3.

## 5. What held

Reported because an absence of findings means something only with an edge round it.

- **`get_task` does not leak past the list's filter.** It calls `inbox::is_visible_to` — the same predicate the list filters on, reaching the rows rather than re-deriving — and 404s before reading. The failure this shape usually has is not here.
- **`OWNER` handles the null case.** A document with no `created_by` refuses at resolution with a message naming why, rather than resolving to nobody and stalling.
- **The status projection is tenant-scoped** and round-trips the spelling: `parse_document_status` rejects a `mapsToDocumentStatus` that does not survive `from_db`/`as_db`, so a typo in a definition is an internal error rather than a document silently sent back to draft.
- **`holds` matches the specification.** JWSS §4 says a transition is eligible *"only when it evaluates `true`"*, so `as_bool().unwrap_or(false)` is strict-`true` by intent rather than a truthiness bug — the reading that first looked like one.
- **The lock ordering is real.** Instance before task on every path, stated in two module headers and held by the one call site that takes both.
