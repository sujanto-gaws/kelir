## 3. Findings

### Finding 1 — a definition can publish and then 500 ([#259](https://github.com/sujanto-gaws/kelir/issues/259)), blocking

**The meta-schema does not bound what the columns bound.** Three instances, one root cause, each confirmed end to end against a real database:

| Definition contains | Save | Publish | Run time |
|---|---|---|---|
| a transition whose `from` equals its `to` | 201 | 200 | **500** on the decision that fires it |
| `taskDefinitionKey` over 64 characters | 201 | 200 | **500** on the submit |
| `taskName` over 200 characters | 201 | 200 | **500** on the submit |

`0027` added `ck_workflow_history_moved CHECK (from_state IS DISTINCT FROM to_state)`; `0025` declares `VARCHAR(64)` and `VARCHAR(200)`. **No §8 rule and no meta-schema keyword corresponds to any of the three.** `stateCode` carries `maxLength: 60` and is safe — which shows the bound was considered for one field and not its neighbours.

**A self-transition is not an exotic input.** "Send it round again" is an ordinary thing to model: a conditioned edge back into the same state, with a fallback that moves on. It satisfies S3, S6 and S7. The engine selects it, moves the instance, and the database refuses the history row.

**The two length instances are the worse pair**, because they fail the **submit** rather than a decision — an ordinary user cannot file the document, and nothing near the failure names the definition that caused it.

**Why it is blocking.** [#240](https://github.com/sujanto-gaws/kelir/issues/240) AC7 blocks the tag on a defect in something Phase 5 claims to have delivered. `v0.5.0`'s headline is a workflow engine whose definitions are validated at save and at publish; a definition that passes both and cannot be executed is that claim failing.

**Fixed on 2026-08-30, and the fix found three more instances than this pass did.** Working the root cause rather than the three symptoms meant sweeping every column the definition JSON feeds, and `states[].name`, `variables[].key` and `version` are bounded by a column and were bounded by nothing else either. All six were then measured rather than reasoned about, which moved one row of the table above: `states[].name` fails **at the publish**, not at a submit, because the projection is written there.

| Definition contains | Save | Publish | Run time |
|---|---|---|---|
| `states[].name` over 200 characters | 201 | **500** | — |
| `variables[].key` over 64 characters | 201 | 200 | **500** on the submit |
| `version` over 40 characters | **500** | — | — |

`version` is the one case where the caller's own request produced the 500 — `jwss_version` is written by the save.

**The self-transition was settled the other way from the lengths**, which [#259](https://github.com/sujanto-gaws/kelir/issues/259) AC2 asked to be a recorded decision rather than an assumption: `0030_workflow_self_transition.sql` drops `ck_workflow_history_moved` instead of adding a rule refusing the construct. JWSS is the normative document and it does not forbid `from == to`; narrowing the standard to fit a `CHECK` nobody had argued for is the wrong direction. Recorded as **JWSS R-5** with §4.2 and §9.1.

### Finding 2 — a safety comment that names one caller where there are five ([#260](https://github.com/sujanto-gaws/kelir/issues/260)), not blocking

`repository::definition::definition_of_instance` is the only statement in the module that reads a tenant-scoped table **without a tenant predicate**, deliberately, and its doc comment carries the argument: *"Only `super::super::service::engine` calls this, and only with an id it read off a row it had already scoped."*

**Five callers, four outside `engine`** — `document::service::submit`, `workflow::service::{task, inbox, instance}`.

**Every one was traced, and every one passes an id from an already-scoped row.** There is no cross-tenant read. What failed is the guard, not the guarantee: the comment states a constraint that stopped being true, so a reader deciding whether a sixth caller is safe is told the wrong thing about what keeps it safe. It is the shape #184 found in `TaskStatus::is_open` — a comment describing behaviour the code does not have.

## 4. What was checked and found sound

- **The history read** (#181) requires `workflow:instance:read`, scopes by tenant, resolves the document first so an unknown id is a 404 rather than an empty page, and uses the same predicate for its count and its page.
- **It does not bypass a narrower check**, which was the specific worry: `document::service::get_document` applies `document:read` plus tenant and nothing finer, so there is no per-document rule for the history route to route around.
- **Tenant scoping across the module** — every statement but the one above names `tenant_id`.
- **Append-only by construction** (#181 AC6) — `workflow_history` has no `deleted_at`, `updated_at` or `updated_by`, so a soft delete has nowhere to write and an edit nothing to stamp.
- **The comment normalization** (#182) — whitespace becomes absent before `requiresComment` is evaluated, so an edge demanding a reason cannot be satisfied by the space bar.
- **`allowedBy` on the resubmit path** (#183) — the `RESUBMIT` edge goes through `fire`, so #226's enforcement covers it.

### Finding 3 — the Workflow tab says an approval has no steps when the reader may not read tasks ([#263](https://github.com/sujanto-gaws/kelir/issues/263)), not blocking

`service::instance::load_instance` returns the instance with an **empty task list** to a caller holding `workflow:instance:read` and not `workflow:task:read` — deliberately, in #101's shape: *a caller who may read parties and not roles has a working screen, not a forbidden one*. `WorkflowTab.vue` consults no permission at all, so it renders that as an empty `Steps` list under the sentence **"These are the steps this approval has generated."**

Confirmed at both ends. Against a real backend, that caller gets:

| Request | Result |
|---|---|
| `GET /documents/{id}/workflow` | **200**, `tasks: []` |
| `GET /documents/{id}/workflow/history` | **200**, 2 rows |

And mounted with exactly that payload, the tab renders `Steps · These are the steps this approval has generated. How the document moved between them is below.` above nothing — with `How it got here · MANAGER_APPROVAL → REJECTED · REJECT · dina` **directly below it**. The screen asserts the approval generated no steps and then shows a person deciding one.

**The mechanism to fix it is already in the sprint's own code.** `TaskDetailPage.vue` gates its hand-over picker on `auth.can('identity:user:read')` and says in words why the panel is empty. The tab does neither.

**Not blocking**, and the argument rather than the label: no control is bypassed and no row is wrong — the backend's refusal is correct and the history is complete. What fails is a sentence. But **the permission combination is the requester's**, not an exotic one: the person who raised a document plausibly holds `document:read` and `workflow:instance:read` and no task permission at all, because they hold no tasks. **If [#241](https://github.com/sujanto-gaws/kelir/issues/241) demonstrates the requester's view, this is what the demo shows**, which is a reason to fix it before the demo rather than a reason to hold the tag.

### Finding 4 — the task screen tells its holder that engine-only transitions arrive in a later release ([#264](https://github.com/sujanto-gaws/kelir/issues/264)), not blocking

`inbox::get_task` builds `decisions` from `Graph::actions_from`, which returns **every** transition out of the state with no filter, and marks `supported: matches!(action, "APPROVE" | "REJECT" | "RETURN")`. `TaskDetailPage.vue` renders the rest as *"This workflow also allows … Those arrive in a later release."*

Mounted with two `AUTO` edges, the screen renders, verbatim:

> This workflow also allows AUTO → Escalated, AUTO → Archived . Those arrive in a later release.

**`AUTO` is never anybody's to make.** JWSS §4 forbids `allowedBy` on an `AUTO` transition precisely because there is no caller; nothing in the engine fires one, so a state with an `AUTO` out-edge parks the process and tells its holder they will be able to take it later.

**`DELEGATE` is the sharper instance, because the file already knows.** `TaskDetailPage.vue`'s own header says *"#184 built delegation and deliberately did not make it a transition, so a definition declaring a `DELEGATE` edge is declaring one nothing fires."* Sixty lines below, the template tells the person it arrives in a later release. This is [#240](https://github.com/sujanto-gaws/kelir/issues/240) AC3 exactly — a claim in a comment against the code beside it — with the unusual feature that **the comment is the correct half**.

**Not blocking**: no control and no record is affected, and a workflow using neither construct never shows it.

### 6.3 AC4 — the four-way record distinction, verified

[#181](https://github.com/sujanto-gaws/kelir/issues/181) asserts in prose that none of the four records is derived from another. Checked mechanically rather than accepted:

| Record | Written by | Called from |
|---|---|---|
| `workflow_history` | `repository::history::record` | `service::engine` only — two sites |
| `workflow_task_history` | `repository::task::record_task_history` | `service::engine`, `service::task` |
| `approval_decisions` | `repository::task::record_decision` | `service::task` |
| `audit_events` | `modules::audit` | its own call sites |

**One `INSERT` site per table**, and `modules::audit` contains **no statement reading any workflow table** — so the audit row is not derived from the workflow records, which is the direction the claim most needed checking in.

**And nothing reads `audit_events` for a user-facing screen**: the only two readers are the hash chain's own previous-row lookup and the governance read behind `master-data:audit:read`. That is the property §7.11 argued for — *an audit row a feature depends on is an audit row nobody can correct* — and it holds.

**The three workflow records share one transaction.** `service::task::decide` opens it and passes `&mut transaction` to `record_task_history`, `record_decision` and `engine::fire`, which is what writes the history row. So a decision cannot be recorded in one of the three and missing from another.

### 6.4 Also checked and found sound

- **The inbox's overdue axis.** `all ⊃ open ⊃ overdue` is one control, and `isOverdue` is read from the server on both screens rather than compared against the browser clock — which was the specific worry, because a task late on one machine and not another is the bug that requirement exists to prevent.
- **The frontend's open-task vocabulary matches the backend's.** `TaskDetailPage`'s `open` computed is `CREATED | ASSIGNED | IN_PROGRESS`, exactly `TaskStatus::is_open`. This is a duplicated rule and the duplicate is currently correct — worth naming because #184 found the previous version of this exact pair disagreeing.
- **`TASK_STATUS_LABELS` covers every variant** of `TaskStatus`, typed as `Record<TaskStatus, string>`, so a new status cannot render blank.
- **No `v-html` anywhere in the three screens.** Comments and state names are interpolated, so a comment containing markup is text.
