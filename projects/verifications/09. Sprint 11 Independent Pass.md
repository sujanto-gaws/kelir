## 3. Findings

### Finding 1 — a definition can publish and then 500 ([#259](https://github.com/sujanto-gaws/kelir/issues/259)), blocking

**The meta-schema does not bound what the columns bound.** Three instances, one root cause, each confirmed end to end against a real database:

| Definition contains | Save | Publish | Run time |
|---|---|---|---|
| a transition whose `from` equals its `to` | 201 | 200 | **500** on the decision that fires it |
| `taskDefinitionKey` over 64 characters | 201 | 200 | **500** on the submit |
| `taskName` over 200 characters | 201 | 200 | **500** on the submit |

`0027` added `ck_workflow_history_moved CHECK (from_state IS DISTINCT FROM to_state)`; `0025` declares `VARCHAR(64)` and `VARCHAR(200)`. **No §8 rule and no meta-schema keyword corresponds to any of the three.** `stateCode` carries `maxLength: 60` and is safe — which shows the bound was considered for one field and not its neighbours.

**A self-transition is not an exotic input.** "Send it round again" is an ordinary thing to model: a conditioned edge back into the same state, with a fallback that moves on. It satisfies S3, S6 and S7. The engine selects it, moves the instance, and the database refuses the history row.

**The two length instances are the worse pair**, because they fail the **submit** rather than a decision — an ordinary user cannot file the document, and nothing near the failure names the definition that caused it.

**Why it is blocking.** [#240](https://github.com/sujanto-gaws/kelir/issues/240) AC7 blocks the tag on a defect in something Phase 5 claims to have delivered. `v0.5.0`'s headline is a workflow engine whose definitions are validated at save and at publish; a definition that passes both and cannot be executed is that claim failing.

**Fixed on 2026-08-30, and the fix found three more instances than this pass did.** Working the root cause rather than the three symptoms meant sweeping every column the definition JSON feeds, and `states[].name`, `variables[].key` and `version` are bounded by a column and were bounded by nothing else either. All six were then measured rather than reasoned about, which moved one row of the table above: `states[].name` fails **at the publish**, not at a submit, because the projection is written there.

| Definition contains | Save | Publish | Run time |
|---|---|---|---|
| `states[].name` over 200 characters | 201 | **500** | — |
| `variables[].key` over 64 characters | 201 | 200 | **500** on the submit |
| `version` over 40 characters | **500** | — | — |

`version` is the one case where the caller's own request produced the 500 — `jwss_version` is written by the save.

**The self-transition was settled the other way from the lengths**, which [#259](https://github.com/sujanto-gaws/kelir/issues/259) AC2 asked to be a recorded decision rather than an assumption: `0030_workflow_self_transition.sql` drops `ck_workflow_history_moved` instead of adding a rule refusing the construct. JWSS is the normative document and it does not forbid `from == to`; narrowing the standard to fit a `CHECK` nobody had argued for is the wrong direction. Recorded as **JWSS R-5** with §4.2 and §9.1.

### Finding 2 — a safety comment that names one caller where there are five ([#260](https://github.com/sujanto-gaws/kelir/issues/260)), not blocking

`repository::definition::definition_of_instance` is the only statement in the module that reads a tenant-scoped table **without a tenant predicate**, deliberately, and its doc comment carries the argument: *"Only `super::super::service::engine` calls this, and only with an id it read off a row it had already scoped."*

**Five callers, four outside `engine`** — `document::service::submit`, `workflow::service::{task, inbox, instance}`.

**Every one was traced, and every one passes an id from an already-scoped row.** There is no cross-tenant read. What failed is the guard, not the guarantee: the comment states a constraint that stopped being true, so a reader deciding whether a sixth caller is safe is told the wrong thing about what keeps it safe. It is the shape #184 found in `TaskStatus::is_open` — a comment describing behaviour the code does not have.

**Fixed on 2026-08-30, and the fix showed the finding was worth more than it claimed.** This record said *there is no cross-tenant read*, which was true and remains true — but it was true only because every caller happened to be well-behaved. `definition_of_instance` now takes the tenant, fetches the row unscoped and compares, so the property is checked rather than promised.

**The check is load-bearing, and that was measured rather than assumed.** With the comparison removed, an instance pointed at another tenant's definition is decided successfully: `200`, `currentState: "COMPLETED"`, the document moved by rules belonging to somebody else. So the only thing between a broken link and executing another tenant's workflow was the callers' good behaviour.

**A newtype was considered and rejected**, which [#260](https://github.com/sujanto-gaws/kelir/issues/260) AC2 left open. Its producers span `document_type::repository::workflow_binding` and the workflow module's instance reads, so its constructor would have to be visible to both — at which point what the compiler keeps is *somebody wrote a conversion*, not *the id came from a scoped read*.

**The read stays unscoped and is compared afterwards**, because the original reasoning was sound: `WHERE tenant_id = $2` turns a broken link into *no row*, indistinguishable from a definition that never existed. The mismatch is now named in the log with both ends of it, and only then becomes `None`.

**A second inaccuracy in the same comment, which this pass did not catch.** It opened with *"the scope is the instance's"*. On the submit path there is no instance yet — `engine::start` creates one — and the id comes from `document_type_workflows`, read under the tenant. The scope is whichever row named the definition.

### Finding 3 — the Workflow tab says an approval has no steps when the reader may not read tasks ([#263](https://github.com/sujanto-gaws/kelir/issues/263)), not blocking

`service::instance::load_instance` returns the instance with an **empty task list** to a caller holding `workflow:instance:read` and not `workflow:task:read` — deliberately, in #101's shape: *a caller who may read parties and not roles has a working screen, not a forbidden one*. `WorkflowTab.vue` consults no permission at all, so it renders that as an empty `Steps` list under the sentence **"These are the steps this approval has generated."**

Confirmed at both ends. Against a real backend, that caller gets:

| Request | Result |
|---|---|
| `GET /documents/{id}/workflow` | **200**, `tasks: []` |
| `GET /documents/{id}/workflow/history` | **200**, 2 rows |

And mounted with exactly that payload, the tab renders `Steps · These are the steps this approval has generated. How the document moved between them is below.` above nothing — with `How it got here · MANAGER_APPROVAL → REJECTED · REJECT · dina` **directly below it**. The screen asserts the approval generated no steps and then shows a person deciding one.

**The mechanism to fix it is already in the sprint's own code.** `TaskDetailPage.vue` gates its hand-over picker on `auth.can('identity:user:read')` and says in words why the panel is empty. The tab does neither.

**Not blocking**, and the argument rather than the label: no control is bypassed and no row is wrong — the backend's refusal is correct and the history is complete. What fails is a sentence. But **the permission combination is the requester's**, not an exotic one: the person who raised a document plausibly holds `document:read` and `workflow:instance:read` and no task permission at all, because they hold no tasks. **If [#241](https://github.com/sujanto-gaws/kelir/issues/241) demonstrates the requester's view, this is what the demo shows**, which is a reason to fix it before the demo rather than a reason to hold the tag.

### Finding 4 — the task screen tells its holder that engine-only transitions arrive in a later release ([#264](https://github.com/sujanto-gaws/kelir/issues/264)), not blocking

`inbox::get_task` builds `decisions` from `Graph::actions_from`, which returns **every** transition out of the state with no filter, and marks `supported: matches!(action, "APPROVE" | "REJECT" | "RETURN")`. `TaskDetailPage.vue` renders the rest as *"This workflow also allows … Those arrive in a later release."*

Mounted with two `AUTO` edges, the screen renders, verbatim:

> This workflow also allows AUTO → Escalated, AUTO → Archived . Those arrive in a later release.

**`AUTO` is never anybody's to make.** JWSS §4 forbids `allowedBy` on an `AUTO` transition precisely because there is no caller; nothing in the engine fires one, so a state with an `AUTO` out-edge parks the process and tells its holder they will be able to take it later.

**`DELEGATE` is the sharper instance, because the file already knows.** `TaskDetailPage.vue`'s own header says *"#184 built delegation and deliberately did not make it a transition, so a definition declaring a `DELEGATE` edge is declaring one nothing fires."* Sixty lines below, the template tells the person it arrives in a later release. This is [#240](https://github.com/sujanto-gaws/kelir/issues/240) AC3 exactly — a claim in a comment against the code beside it — with the unusual feature that **the comment is the correct half**.

**Not blocking**: no control and no record is affected, and a workflow using neither construct never shows it.

### 6.3 AC4 — the four-way record distinction, verified

[#181](https://github.com/sujanto-gaws/kelir/issues/181) asserts in prose that none of the four records is derived from another. Checked mechanically rather than accepted:

| Record | Written by | Called from |
|---|---|---|
| `workflow_history` | `repository::history::record` | `service::engine` only — two sites |
| `workflow_task_history` | `repository::task::record_task_history` | `service::engine`, `service::task` |
| `approval_decisions` | `repository::task::record_decision` | `service::task` |
| `audit_events` | `modules::audit` | its own call sites |

**One `INSERT` site per table**, and `modules::audit` contains **no statement reading any workflow table** — so the audit row is not derived from the workflow records, which is the direction the claim most needed checking in.

**And nothing reads `audit_events` for a user-facing screen**: the only two readers are the hash chain's own previous-row lookup and the governance read behind `master-data:audit:read`. That is the property §7.11 argued for — *an audit row a feature depends on is an audit row nobody can correct* — and it holds.

**The three workflow records share one transaction.** `service::task::decide` opens it and passes `&mut transaction` to `record_task_history`, `record_decision` and `engine::fire`, which is what writes the history row. So a decision cannot be recorded in one of the three and missing from another.

### Finding 5 — a document with a live approval can be discarded, and the approval survives it ([#278](https://github.com/sujanto-gaws/kelir/issues/278)), not blocking

**Where:** `document::service::document::delete_document` and `repository::document::soft_delete`, against `workflow::service::engine::project_document_status`.

**The precondition is one word in a definition.** A state's `mapsToDocumentStatus` may be `DRAFT`: the meta-schema's `documentStatus` enum carries it, `jwss::DOCUMENT_STATUSES` carries it, and no S-rule narrows the set — S9 constrains only that *some* final state maps to `COMPLETED` or `CANCELLED`. `project_document_status` then writes what the state says, unconditionally and by design, because #178 AC4 requires a new workflow to say what its states mean without a backend change.

**So a document can be `DRAFT` while its approval is running**, holding a number, a live instance and an open task. `delete_document` asks one question about it — `refuse_unless_discardable`, which is `DocumentStatus::is_discardable`, which is `matches!(self, Self::Draft)` — and there is no live-instance check anywhere on the path. The status route has one: `document::service::status` refuses a document being decided, *naming the instance and the action that would move it*.

**The guard exists and is written against the wrong fact.** `soft_delete`'s own comment excludes `RETURNED` and says why, in the words the harm deserves: a returned document *"has a number, a status history and a live process waiting for it to come back. Deleting it would strand the instance that returned it and retire a number an auditor can see was issued."* That is exactly this defect, correctly identified. What guards it is `status = 'DRAFT'`, a **proxy** for *has no live process* — and the projection is what makes the proxy false.

**What is left afterwards.** `documents.deleted_at` is set; the instance stays `RUNNING` and keeps holding the one-live-instance index against that document; the task stays open. `decide` reads the document through `find_document`, which filters `deleted_at IS NULL`, so every later decision answers **404 `Document`** and the process can never be moved again — by anybody, ever, including an administrator.

**Not blocking, and the reason is a fact about the repository rather than about the code.** No definition anywhere — fixtures, integration tests, the e2e flow — maps a state to `DRAFT`; the eight values in use are `PENDING_APPROVAL`, `COMPLETED`, `REJECTED`, `IN_REVIEW`, `CANCELLED`, `ARCHIVED`, `RETURNED` and `APPROVED`. It is a trap laid for the first definition author who reaches for the status that means *editable again* without knowing that `RETURNED` is the one the product was built around.

**What a test would have to reach:** publish a definition whose non-final state maps to `DRAFT`, submit a document against it, then `DELETE /documents/{id}` as the owner and assert it is refused. There is no such test, and there is no predicate for one to make red.

### Finding 6 — the inbox's count and its page apply different rules ([#279](https://github.com/sujanto-gaws/kelir/issues/279)), not blocking

**Where:** `workflow::repository::inbox`, `list_for_caller` against `count_for_caller`.

`list_for_caller` opens with `JOIN documents d ON d.id = t.document_id AND d.deleted_at IS NULL`. `count_for_caller` has **no join to `documents` at all**. So a task whose document has been deleted is counted and not listed.

**The divergence is forbidden by the comment directly above the function that has it.** `count_for_caller` is introduced as *"the same predicate, written once more rather than referenced… It is here because `meta.total` and the page must agree: a count over a wider rule reports rows the page does not show, and a person paging through an inbox that says '23' and ends at 19 has no way to tell a bug from a task somebody else took."* The duplication was understood; what drifted is one join, added to the page and not to the count.

**Reachable today only through Finding 5**, which is why it is filed beside it rather than under it: they are two defects, and closing the first would leave this statement still saying something the other does not. `is_visible_to` — the detail view's gate — also has no `documents` join, so it answers *visible* for such a task while the detail read behind it goes through `list_for_caller` and answers **404**. The three statements that were written to agree disagree in two different directions.

**What a test would have to reach:** any task whose document is soft-deleted, asserting `meta.total` against the length of the page. The cross-user test the comment cites asserts both against each other for the *visibility* rule, which is the pattern this needs and the case it does not cover.

### Finding 7 — a task handed back to the person who handed it out records the decision as taken on its own maker's behalf ([#280](https://github.com/sujanto-gaws/kelir/issues/280)), not blocking

**Where:** `workflow::repository::task::delegate`, and `0028_delegation.sql`'s stated invariant.

`delegate` writes `delegated_from_user_id = COALESCE(delegated_from_user_id, $4)`, and the reasoning is right: the column names *whose authority*, so a second hand-off must not overwrite the first. `a_second_hand_off_still_names_the_person_whose_authority_it_is` asserts it for A → B → C.

**A → B → A is not covered, and it is the one shape where the invariant breaks.** Ani hands her own task to Budi (`delegated_from` becomes Ani); Budi hands it back to Ani (`refuse_self_delegation` compares Budi with Ani and passes; the `COALESCE` keeps Ani). The task is now assigned to Ani and says it is being held on Ani's behalf. When Ani decides, `decide` passes `on_behalf_of: task.delegated_from_user_id`, and the history row is written with `actor_user_id` and `on_behalf_of_user_id` **both Ani**. `WorkflowTab.vue` renders it: *"ani … on ani's behalf"*. The same shape arrives through a window — a window routes Ani's task to Budi, Budi hands it back.

**It is the state `0028`'s header says the schema exists to avoid**, in its own words: *"writing the actor into both columns to avoid a null would make 'acting for themselves' indistinguishable from 'acting for somebody who happens to be them'."* The nullability was chosen to keep those two apart, and this path produces the row it was chosen to prevent.

**The consequence is the record, not the routing.** `assignment::permits` checks `[actor, on_behalf_of]` in turn, so a duplicated candidate is checked twice and widens nothing — there is no authorization defect here. What is wrong is that the history of a decision says something that is not true about who made it, on the one screen #184 AC4 exists to serve.

**What a test would have to reach:** the hand-back, then the decision, asserting `on_behalf_of_user_id IS NULL` on the resulting `workflow_history` row. `an_ordinary_decision_names_nobody_it_was_taken_for` asserts exactly that for the never-delegated case and is the test this one would sit beside.

### 7.4 Also checked and found sound

- **Tenant scoping on all four new statements.** `active_delegate_of` scopes `delegations` by `tenant_id` and joins `users` on `u.tenant_id = d.tenant_id` rather than on the id alone; `delegate`, `end_delegation` and the history insert all carry it. The #106/#121 lesson holds here.
- **A window cannot route work to an account that cannot sign in.** The `users` join inside the routing statement requires `ACTIVE` and not merely undeleted, so deactivating an account stops a window — and the same predicate is what refuses the window at the moment it is opened, which is the pair of checks neither of which can stand in for the other.
- **Two overlapping windows have one answer, and it is the same answer every time.** `ORDER BY (scope = 'DOCUMENT_TYPE') DESC, created_at DESC, id DESC` — most specific, then most recent, with the id as the final tiebreak. Without the last term a task's routing would depend on the plan PostgreSQL happened to pick.
- **One hop, deliberately.** A delegate's own window is not followed; `ck_delegations_not_self` forbids A → A and nothing forbids A → B → A, so following the chain could cycle. Documented where it is implemented.
- **A `dueInHours` no interval can hold drops the deadline and warns**, rather than failing the transition on whoever happened to submit next. The ceiling is documented as a representability bound and not a product rule, which is the honest description of it.
- **A routing condition evaluates the server's payload.** Both call sites build `EvaluationContext` from stored data — the submit from `secure(…, Strictness::Submit)`, which is #164's re-evaluation, and the decision from the document as read. A condition cannot be steered by what a client sent.
- **`document.amount` is absent from the condition context and the comment says so**, with the reason a null would be worse than an omission: a JSON Logic comparison against null is silently false, so a routing rule would take the wrong branch and report nothing. `documents.amount` is a column nothing writes; the limitation is recorded rather than papered over.
