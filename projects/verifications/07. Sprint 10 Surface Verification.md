## 1. Why this pass happened, and where its independence stops

**So this record does not close what §2 asks a record to close.** Every Sprint 10 item is **`author-verified`**, not Done, and the [status report](../status/11.%20Sprint%2010%20Status.md) labels every row that way. It also means the [Sprint 9 retrospective](../retrospectives/07.%20Sprint%209%20Retrospective.md)'s fourth action — *an independent read of `modules/document/` happens in Sprint 10* — is **not done**, and the Sprint 9 rows stay where they are.

**What a self-pass can honestly produce, and what this one produced.** Four of the six findings are **refutations of claims this sprint's own code or documentation made**:

None of that makes the pass independent. What it cannot produce is the defects nobody thought to look for — *twenty mutation runs designed by the agent that wrote the code are strong evidence of what the tests catch and no evidence of what nobody thought to test* ([Sprint 5 retrospective](../retrospectives/03.%20Sprint%205%20Retrospective.md)).

## 3. Findings

### F1 — Two document types whose templates render the same number answered `500`

**Severity: moderate.** Not release-blocking: it is a configuration mistake rather than a defect in a correct configuration, and the write is refused either way. What was wrong was the answer.

`uq_documents_tenant_id_document_number` is **tenant-wide**; a numbering bucket is **per document type** (§6.3.1). Two types both templated `PR-{year}-{sequence}` each count from one, both issue `PR-2026-000001`, and the second submit violates the index. Nothing mapped the violation, so the caller got `INTERNAL_ERROR` with no detail — on a submit the product knows exactly why it refused, and on a configuration whose fix is one field.

**Found by a fixture, not by a reader.** No test before Sprint 10 had put two *numbered* document types in one database. This sprint's engine fixtures do, because coding standard §2.9 requires a second subject wherever a scope is asserted — so the rule found a defect it was not written to find, which is the retrospective's fourth action.

**Closed in the pass.** `document::service::submit::colliding_number` maps it to a 422 naming `documentNumber` and **naming the templates**, because trying again produces the same collision on every document forever. `documents_submit.rs`'s `two_types_whose_templates_collide_are_refused_rather_than_failing` was **seen red** against the mapping removed, reproducing the exact `500`. The uniqueness is deliberately **not** moved to be per type: a document number is a business identifier people quote to each other, and two documents in one tenant sharing one is what the index exists to prevent.

### F2 — A concurrent edit took this sprint's migration number, and nothing noticed until forty tests went red

**Severity: moderate**, and it is a process finding as much as a technical one.

`0025_workflow.sql` was written as `0024`. A bug-fix migration for [#115](https://github.com/sujanto-gaws/kelir/issues/115) was written into the same working tree the same day and took the same number. `sqlx::migrate!` takes the leading digits as the version and `_sqlx_migrations` has that as its primary key, so **every** migration run failed — on a fresh database, with `duplicate key value violates unique constraint "_sqlx_migrations_pkey"`. Every integration test in the suite went red at once and none of them was about migrations.

The harness's own banner is accurate and unhelpful: it says *this is a setup failure, NOT a failed assertion*, names the constraint, and cannot name the two files.

**Closed in the pass, twice over.** The workflow migration was renumbered to `0025` following naming convention §4.3 — a migration takes the next free number when it is written, and an early arrival shifts every unwritten migration below it, which `0021` and `0023` had already done to this one. And `harness.rs`'s `no_two_migrations_share_a_version_number` now asserts it as a filesystem test that names both files. **It caught a live recurrence within the hour**: the campaign's snapshot restore wrote the pre-rename file back beside the renamed one, and the test reported both paths rather than forty unrelated failures.

### F3 — `engine::start` documented a check it did not make

**Severity: moderate.** A document type binding a workflow that was published and later **deprecated** would start a process against a revision nobody stands behind, silently, on every submission — and `start`'s own doc comment claimed it was refused.

[#187](https://github.com/sujanto-gaws/kelir/issues/187) AC2 refuses a *binding* to anything but an `ACTIVE` definition, and a definition can be deprecated afterwards. `definition_of_instance` returned a four-element tuple that did not include the status, which is how the field came to be forgotten: a fifth positional `String` beside three others is a thing a reader skips.

**Closed in the pass.** The read returns an `ExecutableDefinition` record carrying `status`, and `start` refuses a non-`ACTIVE` definition with a 422 naming the workflow. **Approvals already running are deliberately unaffected** — an instance pins its revision, and refusing at the *decision* would strand every approval in flight the moment an administrator retired a workflow. `workflow_engine.rs`'s `a_deprecated_workflow_refuses_the_submit_and_leaves_running_approvals_alone` asserts both halves and was seen red against the check removed.

### F4 — A final state whose status maps to no outcome left the instance running forever

**Severity: moderate**, and the most interesting of the six.

`fire` derived an `outcome` from the target state's `mapsToDocumentStatus` and passed it as the single argument that both recorded the outcome *and* completed the instance. `InstanceOutcome::from_document_status` yields nothing for `DRAFT`, `SUBMITTED`, `IN_REVIEW` or `PENDING_APPROVAL` — and the JWSS meta-schema permits a final state mapping to any of them. Such a state left the instance `RUNNING` with no outgoing transitions: nothing could move it, it held `uq_workflow_instances_live_document` against its document forever, and the document could not be transitioned by hand either, because the seam refuses while a process is live.

**Two facts had been made one argument.** Being final is the fact; the outcome is information.

**Closed in the pass.** `StateMove` carries `final_state` and `outcome` separately, and `move_state` completes on the first. The record type exists for a second reason worth keeping: `from` and `to` are both `&str`, so transposing them compiled — and a compare-and-swap with its two ends swapped is a guard that never matches, which presents as every transition losing a race it was not in.
`a_final_state_ends_the_instance_whatever_its_status_maps_to` was seen red against the two arguments recombined.

### F5 — The task detail read was capped by a page size

**Severity: low**, and invisible below about a thousand tasks.

`service::inbox::get_task` asked `list_for_caller` for a page of a thousand and picked its row out of the result. A caller holding more than a thousand tasks would get **404** for the oldest — on a task the visibility rule says they may see, with no error anywhere.

**Closed in the pass.** `InboxFilters` gained `task_id`, so the read is exact and the visibility rule stays a single predicate rather than two that could disagree.

### F6 — Seven predicates were the only guard on their behaviour, and one doc comment named a test that did not exist

**Severity: low**, and it is [#218](https://github.com/sujanto-gaws/kelir/issues/218)'s category one phase later.

The campaign found six predicates in `repository/definition.rs` and one in `repository/instance.rs` that survived mutation — every green of the ten it completed. Read individually, each was a *wrong answer about another subject* rather than a missing refusal — the shape Sprint 9 closed with tests rather than filing. Worse, `update_draft`'s doc comment **named a test that did not exist**: `workflow_definitions.rs`'s `a_publish_that_lands_first_makes_the_edit_apply_to_nothing`. Coding standard §2.5 offers two options for a second line of defence — a test that reaches it, or a comment saying it is unexercised — and claiming a test that is not there is neither.

**Closed in the pass**, with seven tests rather than a comment:

| Predicate | The test that now holds it |
|---|---|
| `highest_version` · `workflow_key` | `each_workflow_key_numbers_its_own_revisions` — three moves, because two cannot tell *separate* from *shared* |
| `update_draft` · `status = 'DRAFT'` | `a_publish_that_lands_first_makes_the_edit_apply_to_nothing` — the interleaving **arranged**, not raced for |
| `publish` · `status = 'DRAFT'` | `two_publishes_of_one_draft_produce_one_publisher` |
| `lock_bindable_definition` · `tenant_id` | `a_workflow_in_another_tenant_cannot_be_bound` |
| `soft_delete` · `tenant_id` | `a_workflow_in_another_tenant_cannot_be_retired` |
| `move_state` · `current_state` | `a_stale_move_writes_nothing` — driven at the repository, because the task's own guard is a **gate** in front of it |
| `find_definition` · `deleted_at` | `a_retired_workflow_is_not_readable_or_bindable` — and it matters more than a soft-delete test usually does: a retired definition that still *reads* is one an administrator can still **bind**, and a binding routes every future document of a type |

The last is the one worth reading twice. The instance's compare-and-swap looked covered by the concurrency test over twenty-four decisions; it was not, because every one of those decisions is refused by `workflow_tasks`' own predicate a statement earlier. One test appeared to cover two guards and covered the first — the exact failure §2.9 describes.

### F7 — Eleven predicates survived, and eight of them are hidden behind a layer that refuses first

**Severity: low individually, and the pattern is the finding.** Coding standard §2.9 says a green mutation *is a finding, not a nuisance*, and that the usual cause is not a wrong anchor but a **gate**: a first line that refuses before the second is reached, so one test appears to cover two guards and covers one.

Eight of the eleven are exactly that, and the table in §2 names each. They fall into three shapes:

- **A tenant-scoped service read in front of a tenant-scoped statement** (M10, M13, M20). `delete_definition` reads `find_definition` before it calls `soft_delete`; `decide` resolves both the instance and the task on the pool before it locks either. The service's read is itself tested, so the *behaviour* is held — what is unheld is the second line, which exists for the caller nobody has written yet.
- **Two predicates in one statement, either of which suffices** (M17, M18, M24). `claim`'s `assignee_user_id IS NULL` and `status = 'CREATED'` are one `WHERE`: defeat either and the other still refuses all twenty-three losers. M18 is the same relationship *across* statements — the task's guard and the instance's compare-and-swap each refuse the second decision, so neither is the only thing holding it. **That is a good property of the product and a bad one for a measurement**, and it is worth saying which: two independent guards on one outcome is defence in depth, not duplication.
- **A gate this sprint created** (M28). F3's fix made `engine::start` refuse a non-`ACTIVE` definition, which now stands in front of the binding read's own `status = 'ACTIVE'`. Closing one finding hid one predicate.

**Two are single-subject fixtures** (M15, M31) — one instance, one document — which is coding standard §2.9's second-subject rule owed in two more places. They are the cheapest of the eleven to close and the most likely to matter, because they are scope predicates.

**One is expected and should stay green** (M34). `uq_workflow_tasks_open_per_instance` cannot be reached: an instance is in one state, a state declares at most one task, so nothing in the product can attempt a second. The index exists for FR-WF-016 to argue with when parallel approval is scheduled, and until then there is no code path to it. §2.5 permits a comment saying a layer is unexercised, and this is one — stated here and in the migration.

**Not closed in this pass**, deliberately. Six of the seven greens the *first* run found were closed inside the sprint, and that was the right call because each was a wrong answer about another subject. These eight are a different thing: the behaviour behind each is tested through the layer in front of it, and reaching past that layer means a repository-level test per predicate. Sprint 11 should take M15 and M31 first — they are scope predicates with one-subject fixtures, which is the shape that has bitten this project three times.

### F8 — The `.env` completeness check refused a deployment for omitting the one variable its caller supplies

**Severity: high — it stopped the browser job before it started.** Step 0 closed the second carried deployment finding by making `deploy.sh` assert every `KELIR_*` variable `.env.staging.example` declares, on the reasoning that **a duplicated list is only ever correct on the day it is written**. The example declares `KELIR_VERSION`, because an operator driving compose by hand has nowhere else to put it. `deploy.sh` does not read it from there: it takes the version as its argument and exports it over whatever `.env` holds.

So the check refused a deployment for omitting the one value the command line had already supplied. Every deployment made during the sprint passed it, because every `.env` on this machine was copied from that example and carries the line. Continuous integration writes its own `.env` in the workflow file — eight variables, for the length of one run — and does not write that one.

**Closed** by excluding the variable the script itself exports, with the reason in the loop rather than in a commit message. Exercised both ways before it was believed: the browser job's own eight-line `.env` is accepted, and one missing a genuinely operator-supplied variable is still refused by name.

**The finding under the finding is that a fix for a deployment finding was never deployed anywhere but here.** F8 lives in the code that closed step 0's finding, written in the same sprint, and the only `.env` it ever ran against was one generated from the list it was written from. **A check over a list has to be run against a list that is not its own source.**

### F9 — Three of the four pipeline gates failed on the first push, and none of them had been run locally

**Severity: process, and §4 is why this record has to carry it.** The pass ran clippy at `-D warnings`, 1016 backend tests, 426 frontend tests, the type check, the bundle-split check and `sqlx prepare --check`, and §4 says so. It did not run `cargo fmt --check`, `prettier --check` or `scripts/check-commit-messages.sh`. All three run *first* in their jobs, so all four jobs stopped at their opening step and every check after it was skipped — reported as four failures, which is what a pipeline that has verified nothing looks like.

What actually failed was whitespace in six files and a commit header of 126 characters against a maximum of 72. Neither is a defect in the product, and that is the point: **the cheapest gate is the one most likely to be skipped, and a pipeline does not grade on how small the failure was.** A green ratio and 1016 tests were reported by a working copy that could not pass step one.

**Closed** by running all three, and by the [retrospective](../retrospectives/08.%20Sprint%2010%20Retrospective.md) action that names the whole set — `scripts/` included — as what a local pass has to mean.

**One thing it found that is not this sprint's.** The header check runs on pull requests only, and this repository squash-merges, so what lands on `main` is the **pull request title, which nothing checks**. Four of the last eight headers on `main` are over the maximum, the longest at 117 characters. Recorded as **D-38** rather than fixed here. **Which artefact governs is already settled** — [git workflow §4](../../docs/standards/05.%20Git%20Workflow.md) says the title MUST follow the convention because it becomes the squash header — so what is open is enforcement of a rule that is stated, unchecked and violated, which is a decision rather than a patch.

## 4. What was checked and found sound

An absence of findings means something only with a boundary round it, so this is the list.

- **The engine is one function.** `engine::fire` is the only path that moves a process; `start` and `decide` both call it, and nothing else writes `workflow_instances.current_state`. Checked by reading every write to that column in the module.
- **Nothing on the engine path takes a pooled connection.** Every function takes `&mut PgTransaction`; no `AppState` appears below `service::`. That is **D-35**'s defect made uncompilable rather than merely avoided, and it was checked by grepping the module for `state.pool` inside a transaction's scope.
- **The lock ordering is instance-then-task on every path**, which was checked by reading each of the three call sites rather than by inferring it from one.
- **The document status map is nowhere in code.** `mapsToDocumentStatus` is read in one place and never `match`ed on a state code — [#178](https://github.com/sujanto-gaws/kelir/issues/178) AC4's actual requirement, checked by grepping the module for every state literal.
- **A task is assigned to a user or offered to a role and never both**, held by `ResolvedAssignment` having only two constructors.
- **The step-0 items closed before item 1**, all three: `deploy.sh` now derives its required-variable list from `.env.staging.example` (and was exercised against a `.env` copied from an older release, which it refuses naming the variable); `e2e/README.md` names `KELIR_E2E_USERNAME` in the command; and `lock_linked_entity`'s facility arm is red under the copy-paste mutation an unexercised duplicated branch invites.
- **The seam's refusal leaves the row alone.** `a_document_under_a_workflow_cannot_have_its_status_set_by_hand` asserts the document is still where the process put it, not merely that the call was refused.
- **`v0.4.0`'s document surface still passes in full** — every `documents*` suite is green with the seam in place, which is what makes **D-36**'s withdrawal a bounded change rather than a hopeful one.

## 5. The browser flow, and what was not reached

**Run, not described.** `a-document-is-approved.spec.ts` was executed against the **release images** — `kelir-backend:0.5.0-rc1` and `kelir-frontend:0.5.0-rc1`, built from the working tree at `87eadf5` and deployed through `deploy-local.sh` onto its own PostgreSQL. That is the exit clause of the sprint plan's Sprint 10 section: *driven through the harness (#153) rather than described*.

**All ten browser flows pass**, two of them this sprint's:

| Flow | What it decides |
|---|---|
| `a submitted document is approved by somebody else, and its status follows` | The sprint's exit sentence, clause by clause: a type carrying a workflow, a submit that starts a process **in the transaction that numbers it**, a task reaching a *different person's* inbox as unclaimed, an approval moving the instance, and the requester's document showing `Completed` on a page they only reloaded |
| `a document under a workflow cannot have its status set by hand` | **D-36**, from the side a person meets it |

**It drives two browser pages, and that is the point rather than a detail.** An approval one person raises and the same person approves exercises the mechanism and proves nothing about the seam it exists for. The requester never touches the second page; the decider never touches the first.

**One existing flow had to be corrected, and the correction is the assertion.** `a-document-is-created-and-submitted.spec.ts` asserted that the Workflow tab says *"Phase 5"* — true when #172 wrote it and false the moment #178 landed. It now asserts what the tab says for a document whose type binds no workflow: **no approval is running**, which is a state rather than a failure ([#187](https://github.com/sujanto-gaws/kelir/issues/187) AC4). A tab still promising Phase 5 at the end of Phase 5's first sprint would have been a true statement about a broken promise.

### One finding against the deployment path, not release-blocking

`deploy-local.sh` **cannot stand up a pre-release build**. Its smoke test asserts that `/version` reports the version it was asked to deploy, and `/version` reports `CARGO_PKG_VERSION` — so an image tagged `0.5.0-rc1` from a tree whose `Cargo.toml` still says `0.4.0` fails the check *after* bringing the stack up healthily. The assertion is right for a release (release process §4 step 7 is what put it there) and has no way to express "a candidate build". The stack was up and every flow ran against it; what failed was the script's last step.

**Not fixed here**, because the fix is a decision rather than a patch: either the script grows a candidate mode, or a release-candidate bumps the package version first. It is named in the [retrospective](../retrospectives/08.%20Sprint%2010%20Retrospective.md)'s fifth action, which is about the exit demo's environment cost being real work with a duration.
