## Method

The verifier was independent of the authors of all four items.

**Read in full:** `repository/facility.rs`, `service/facility.rs`, `domain/facility.rs`; `repository/record_status.rs`, `service/record_status.rs`, `domain/record_status.rs`; `repository/audit_record.rs`, `service/audit_record.rs`; the master-data route table in `handlers.rs` and the OpenAPI registration in `router.rs`; migrations `0010`–`0012` and the `mdm_facilities` definition in `0008`. On the frontend: `useQueryBackedList.ts`, `views.ts`, `MasterDataListPage.vue`, `api/master-data.ts` and the route entry that guards them.

**8 route-level probes** against a real PostgreSQL through the real router, and **48 mutations** against the existing suite — each compiled, each executed against the four master-data binaries able to see it (`master_data_facilities`, `master_data_record_status`, `master_data_audit`, `master_data_parties`), each reverted before the next.

Every SQL mutation keeps its parameter inside a comparison and defeats the predicate with `OR TRUE` — `(tenant_id = $1 OR TRUE)`. `sqlx::query!` verifies against the live database at compile time, so a predicate replaced by `($1 IS NOT NULL OR TRUE)` leaves the parameter's type uninferable and the crate does not build. A first campaign written that way produced no evidence at all. The shape is recorded so the next pass does not rediscover it.

**Baseline before and after:** 224 unit tests and 199 integration tests green across 18 binaries, one ignored (`identity_users`, deferred by **D-7**), working tree byte-identical.

**Seventeen mutations came back STILL GREEN.** Eight of them are finding F7; the other nine are redundancy no fixture can isolate, listed in [#139](https://github.com/sujanto-gaws/kelir/issues/139) so that nobody writes a test that appears to cover them.

## Findings

| F6 | No Sprint 6 route reaches the OpenAPI document | **High as a Definition-of-Done gate** — release-blocking for `v0.3.0` | [#138](https://github.com/sujanto-gaws/kelir/issues/138) |
| F7 | Eight predicates no test exercises, including the facility transition's compare-and-swap | **High as a coverage defect** | [#139](https://github.com/sujanto-gaws/kelir/issues/139) |

Every finding was reproduced through the router before being filed. None rests on reading alone.

**F1 and F2 are the same corruption by two routes, and the module rules out neither.** `repository/facility.rs` explains its depth bound like this:

> A cycle already in storage would make an unbounded `WITH RECURSIVE` spin until the connection died; stopping at `max_depth` means the worst case is a wrong answer rather than a hung request. **No such cycle can be written through this module**, which is exactly the claim that needs a limit behind it rather than a comment.

The reasoning is right and the sentence in bold is false. F1 writes one by racing the check against the write — 18 of 20 rounds. F2 writes one with no concurrency at all: nothing bounds how deep a tree may be *built*, so at 70 levels the walk up from the proposed parent stops six short of the root, and moving the root under its own descendant answers 200 OK. For the write that decides whether a cycle may exist, "a wrong answer rather than a hung request" is not a safe trade — the wrong answer *is* the cycle.

The consequence is not confined to the shape of the data. Once `A.parent = B` and `B.parent = A`, each is the other's child, `children_of` never reaches zero, and both facilities answer `409 "1 facilities are still under this one"` to every delete, permanently, until someone detaches them by hand.

**F6 is a gate, not a defect in what was built.** Nine handlers carry `#[utoipa::path]` annotations that nothing collects: `paths(...)` in `router.rs:19` still ends at `list_employees`. The published document lists 22 paths and none of the sprint's six route patterns, and `Facility`, `CreateFacilityRequest`, `TransitionRequest` and `AuditRecord` are all absent from its schema map. Definition of Done §2 requires "API changes reflected in OpenAPI", so #98, #99 and #100 do not meet it.

What makes it worth more than its one-line fix is why it survived. `the_openapi_document_lists_every_party_route` tests exactly this property — for parties, by naming routes one at a time. It still passes. A test that enumerates the surface it checks has the same failure mode as the list it is checking: both have to be remembered.

**F7's sharpest instance is the facility transition's compare-and-swap.** Removing `record_status = $3` from the party statement turns the concurrency test red; removing it from the facility statement changes nothing. `transition()` reads as one code path and is two — a `match` over `TransitionTarget` with one `query!` per arm — and the sprint's only concurrency test exercises one of them. `master_data_record_status.rs` has thirteen tests, reads as thorough, and leaves half its own statements untouched.

## What was checked and found sound

Recorded because absence of findings only means something with a boundary around it. Thirty-one of the forty-eight mutations were red.

- **The record-status state machine is the strongest thing in the sprint.** The legality table (`may_move_to`) is red under mutation; `PENDING_APPROVAL` is genuinely unreachable by direct edit and both update requests refuse the field through `deny_unknown_fields`; the lost-race 409 is red; the transition's own permission is red and is not `party:update`. The `CHECK` constraint that makes `RecordStatus::from_db`'s `Draft` fallback unreachable exists on all four tables in `0008`, so that claim holds.
- **The party arm's compare-and-swap works.** Twenty rounds of concurrent transitions never reported two moves from the same state, and removing the predicate is red on that test. The design is correct; F7 is about where it is *tested*, not whether it works.
- **All five facility permissions are red** — list, get, create, update, delete — and each refusal comes before anything is read.
- **The cycle rule works when it runs.** Both `refuse_cycle` mutations are red: within the bound and without a race, moving a facility under its own descendant is refused with a 422 naming the field. The depth bound also genuinely terminates — the test that writes a cycle straight into the table and asserts the walk stops is red under mutation, which is what makes it a test of "this terminates" rather than a comment.
- **The no-cascade delete refusal is red**, as is `children_of`'s soft-delete predicate.
- **Tenant scoping on the facility reads that matter** — `count_facilities`, `list_facilities`, `find_facility`, `find_facility_id_by_code`, `soft_delete_facility` — each red, and soft-delete on `list_facilities` and `find_facility` each red.
- **A duplicate facility code is a 409 rather than a 500**, and the constraint name it keys on is red under mutation.
- **The audit read surface is well covered.** Tenant on both statements, the role-action filter on both, the ordering, the permission, the `include_roles` flag and the record-existence check are all red. Count and list take the same flag, so `meta.total` describes the rows the caller actually sees.
- **The role-action filter list is complete.** Enumerating every `action:` the module writes gives exactly `ROLE_ASSIGNED`, `ROLE_UPDATED`, `ROLE_REMOVED` alongside `CREATE`, `UPDATE`, `DELETE`, `STATUS_CHANGE` and `RECORD_STATUS_CHANGE`. Nothing role-shaped escapes the filter.
- **The hash chain is never selected.** `previous_hash` and `current_hash` appear in no statement in `repository/audit_record.rs`, so #100 AC7 holds by construction rather than by filtering.
- **Field bounds match column widths.** `MAX_NAME_LENGTH` 200 against `VARCHAR(200)`, `MAX_FACILITY_CODE_LENGTH` 64 against `VARCHAR(64)`, so #109's shape — an over-long field reaching the database and returning 500 — does not repeat on this surface.
- **The frontend is sound on the ground covered.** No `v-html`, `innerHTML` or `eval` anywhere in the feature; every filter goes on the wire and nothing is narrowed client-side; the route guard requires `master-data:party:read`, which makes the "fall back to a view the caller may open" branch safe rather than a path to a guaranteed 403; loading, failed and empty are three genuinely distinct states; and the pager trusts the page size the server echoes rather than the one it asked for. Its own suite is 204 tests across 20 files, all green.
- **The migration mapping table is accurate.** Database Schema §4 carries `0010`–`0012` and the shifted `0013_rad.sql` and `0021_plugin.sql`, matching what is on disk.

## What was not reached

- **The frontend beyond reading and its own suite.** No browser was driven, no E2E written, no probe aimed at the UI. The 204 unit tests were run and pass; that is the author's evidence, not independent evidence, and #101 should be read as verified by inspection only.
- **`mdm_products`, `mdm_services` and `master_data_source_references`** — unscheduled, no surface.
- **Whether F1 and F5's shape exists outside master data.** Every check-then-act pair in `modules::master_data` was looked at; identity and auth were not swept. This is the same gap record 02 left about #118, and the rule that would settle both is still owed.
- **Performance.** `list_facilities` is one statement with both references joined rather than resolved per row, which is what NFR-PERF-002 asks for, but no timing was taken and no page was loaded at size.
- **The Docker Compose clause of the Definition of Done.** Nothing was demoed from release images.
- **`address_from`'s lenient read.** `serde_json::from_value(value).ok()` turns a malformed `address_json` into `None`, so a facility would read back with no address rather than an error. Not probed, because nothing that goes through this module can write a malformed one — the same "cannot happen through the API" argument that F2 has just shown is worth checking rather than assuming.
- **Chain verification** (FR-AUD-003, Phase 6) — nothing checks the audit chain, which is why #100 correctly declines to publish it.

## What this changes about how the project verifies

**A shared service is not a shared test.** #99's `transition()` is one function over two entities and two SQL statements, and it reads as a single path. The tests were written per use case — "a party walks the lifecycle", "a facility moves on the same machine" — and the concurrency and tenant tests were written once, against a party. Half the statements in the file have never been exercised. Where a `match` puts one statement per entity behind one function, the test count says nothing about the statement coverage, and the module doc should say which entities its tests actually reach — the convention `master_data_facilities.rs` already applies to `update_facility_fields`, extended from functions to arms.

**A Definition-of-Done clause that no test asserts is not checked.** The OpenAPI clause was met for parties by a test that names party routes, and has been silently unmet for every route added since. The other clauses in §2 are in the same position: "audit/permission checks in place" is carried by tests per surface, and "demoable from the Docker Compose stack" is carried by nobody. A gate enforced by remembering is enforced until someone forgets, and three items in a row forgot this one.

**Check-then-act came back twice in the sprint that was built to avoid it.** #105 was a check-then-act race; #99 was designed against it and got it right, with the reasoning written into `repository/record_status.rs`; and #98 — written by the same agent, in the same sprint, against the same table family — introduced the identical shape twice, in `refuse_cycle` and in `delete_facility`. The lesson was learned in the module where it was taught and did not cross to the module next door. What would have carried it is a rule in the coding standard, the way §2.5 now carries #118's: **a check that guards a write belongs in the same transaction as the write, with the rows it read locked.**

**A claim in a doc comment is not a control, and the confident ones are worth probing first.** "No such cycle can be written through this module" is the sentence that made the depth bound defensible, and it is the sentence that turned out to be false. Both F1 and F2 were found by taking one sentence of module documentation as a hypothesis and trying to break it. Record 01 found its worst defect the same way. The documentation in this project is unusually explicit about what it guarantees, which makes it unusually good raw material for a verification pass — **the strongest claims are the best targets**, because they are the ones nobody has retested since they were written.
