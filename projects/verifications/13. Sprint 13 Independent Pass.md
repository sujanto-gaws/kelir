## 3. Findings

### Finding 1 — a parked master-data record can be deleted, stranding its approval for ever. ~~**Blocking.**~~ **Fixed 2026-09-03.**

**A record with a live change document can be deleted through an ordinary endpoint, and the approval it was waiting for can then never be decided — by anybody, including an administrator.**

`master_data::service::governance::refuse_if_awaiting_approval` has exactly two call sites — `party.rs:276` and `facility.rs:210`, both the **update** path. `delete_party` (`party.rs:504`) and `delete_facility` check their delete permission and nothing else. Meanwhile `repository::governance::move_record_status_in`, which `settle` calls on **both** the approve and the reject branch, carries `AND deleted_at IS NULL`; when it matches nothing, `settle` returns `AppError::Internal`.

**Confirmed end to end**, against a real database:

| Step | Result |
|---|---|
| Raise a governed change against an ACTIVE party, submit it | record parks at `PENDING_APPROVAL` |
| `DELETE /api/v1/master-data/parties/{id}` | **204 No Content** — the delete is not refused |
| The approver decides `APPROVE` | **500 Internal Server Error** |
| The approver decides `REJECT` | **500 Internal Server Error** |
| The process afterwards | `instance=RUNNING task=ASSIGNED` |

The probe was appended to `tests/master_data_governance.rs`, reusing that file's own `approver`, `publish_workflow`, `governed_type`, `party`, `activate`, `change_document` and `submit` fixtures; it seeds `MDM_PROBE`, deletes the party after the submit, then posts both decisions to `/api/v1/workflow/tasks/{task}/decision` and reads `workflow_instances.status` and `workflow_tasks.status` back.

**This is [#278](https://github.com/sujanto-gaws/kelir/issues/278), one module over, in code written after #278 was fixed.** #278 was *a document with a live approval can be discarded*, and its fix commit describes the outcome in words that fit this exactly: *"leaving a process nobody including an administrator could move."* Step 0 fixed the document end of that relationship on 2026-09-01; item 6 built the record end on 2026-09-02.

**And the design record shows the author looking at the wrong end of it.** [ADR-0033](../../docs/architectures/adr/0033.%20A%20Governed%20Record%20Parks%20at%20Pending%20Approval.md)'s consequences name the neighbouring case and dismiss it *by citing #278*:

> **Negative** — a record parked by a change whose document is then deleted would stay parked. […] Nothing in the product deletes a submitted document — the discard path refuses anything but a draft ([#278]) — so this is reachable only by hand, and it is named here rather than left to be discovered.

The relationship has two ends. *Document deleted, record stranded* was considered and correctly found unreachable. *Record deleted, document stranded* was not considered, and is reachable by `master-data:party:delete`, which is an ordinary grant.

**Why blocking.** The sprint plan's exit is the MVP and `v0.6.0`. A permission an administrator hands out routinely can permanently wedge a workflow instance, and the only signal is an unexplained 500. #278 was treated as blocking enough to run *before* item A; this is the same defect with the same consequence.

**Fixed on 2026-09-03, the same day, and the fix is the guard the update path already had.** `refuse_if_awaiting_approval` now runs in `delete_party` and `delete_facility` — **D-60**. Three regression tests in `tests/master_data_governance.rs`: the party delete is refused and the record is untouched; **the approval then settles**, which is the half that says the defect is gone rather than merely refused, and the record is deletable once nothing waits on it; and the facility path, which has its own delete and its own lock order.

**Two mutations, each seen red on exactly its tests** (§2.9): the guard removed from `delete_party` reddens *a parked record is not deleted while its change awaits approval* and *an approval still settles after a delete was refused*; removed from `delete_facility`, it reddens *a parked facility is not deleted either*.

**And one thing a mutation could not reach, recorded because a green mutation is a finding.** Swapping the locking read for an unlocked one on the pool leaves all three green — the guard still refuses the *case*; what the lock buys is the *race*. No test here drives two transactions at once, so the placement rests on the argument that `governance::raise` takes the same `FOR UPDATE` read before it parks a record, and the two therefore serialise on that row. That is an uncovered guarantee rather than an untested statement, and it is named in the test file's own header.

**The suite after all three fixes: 69 targets, 1,256 passed, 28 failed — and all 28 are §5's.** (67 before; `audit_object_types.rs` and `deployment_images_are_pinned.rs` are the sixty-eighth and sixty-ninth, and the count moves by +5 new tests less the one enumerating unit test finding 2 retired.) The six failing targets are `attachment_upload`, `attachment_download`, `attachment_scan`, `attachment_tail`, `activity_and_audit_address` and `document_activity`, every one of which stores bytes. **No master-data, workflow, audit, notification, comment or document test fails**, and the seven master-data targets — 107 tests including the three new ones — were run separately and are green. The count moved from the baseline's 13 because the environment's storage refusal became total rather than intermittent, not because the fix touched anything: the fix is in `master_data`, and `master_data` is green.

**The design record was corrected rather than only the code.** [ADR-0033](../../docs/architectures/adr/0033.%20A%20Governed%20Record%20Parks%20at%20Pending%20Approval.md) §4 now carries what this finding showed: citing #278 to dismiss one direction of a two-ended relationship made the other direction look considered. The ADR also moved `Draft` → `Adopted`, because its header said it was waiting for a second reader and this pass was one.

**What the fix is not.** Adding `refuse_if_awaiting_approval` to the two delete paths closes the reachable case, and is right. It does not close the class: `settle`'s `AppError::Internal` on `moved == 0` is a 500 for a state the product can reach, and by its own comment intends to be loud. Loud to whom is the question — an approver sees `INTERNAL_ERROR`. That half is worth an issue of its own.

### Finding 2 — `EXTERNAL_REFERENCE` audit rows withhold their values from everybody, and the test that should have caught it enumerates its subjects. **Fixed 2026-09-03.**

**Item 5 added an object type that item 3's map does not have an arm for**, so the audit search serves those rows with `valuesWithheld: true` to every caller, and no permission exists that would open them.

`audit::domain::readable_by` has nineteen arms and a `_ => return None` fallback; `redact_for` reads `readable_by(&row.object_type).is_some_and(|p| caller.holds(p))`, so an unplaced type withholds. That is the safe direction and is deliberate. But `attachment::REFERENCE_OBJECT_TYPE = "EXTERNAL_REFERENCE"` is written to `audit_events` at `attachment/service.rs:619` and `:736` — the add and the remove of an external reference — and is **not one of the nineteen**.

**Confirmed with a control**, same caller, same request, same page:

```
PROBE EXTERNAL_REFERENCE valuesWithheld=true  newValue=null
PROBE ATTACHMENT         valuesWithheld=false newValue={"originalFileName":"contract.pdf"}
```

The caller held `audit:read`, `attachment:read`, `attachment:create`, `attachment:reference`, `attachment:delete` and `document:read` — every permission that governs an external reference. The probe was appended to `tests/audit_search.rs` and used that file's own `person` and `audit_row` helpers to write one row of each type and read them back through `GET /api/v1/audit`.

**The consequence is bounded and real.** No disclosure: it fails closed. But FR-AUD-004 is a `Must`, and for one object class the search permanently answers *something happened here and you may not know what* to a compliance reviewer who holds everything. The row is still returned and still counted, so it is visible as a hole rather than silently absent — which is `redact_for` working as designed on a type it was never told about.

**The cause is the test, and it is worth more than the finding.** `audit::domain::tests::every_object_type_this_release_writes_can_be_placed` asserts the property correctly and **lists its subjects**:

> The list is `grep -rn 'object_type:' src/` reduced to its constants and literals. A type added later without a row here withholds its values, which is the safe direction […]; this test is what stops that from happening silently to a type we already have.

The grep was run on 2026-09-01, when item 3 was built. Item 5 added `EXTERNAL_REFERENCE` on 2026-09-02. The list did not grow, and **the test still passes**.

That is **verification rule 6 verbatim** — *"a test asserting a project-wide property discovers its subjects rather than listing them; an enumerating test fails the way the list it checks fails"* — carried unchanged since the Sprint 6 retrospective. And the codebase already holds the correct shape one file over: `router.rs`'s `every_annotated_route_reaches_the_document` reads the source in both directions, and its doc comment explains that it was rewritten that way after eleven party routes were listed and nine went undocumented. **The right pattern, the stated rule and the cautionary tale were all in the repository, and the new test was written the old way.**

Fixing this by adding a twentieth arm leaves the cause in place. The test should derive its subjects the way `router.rs` does.

**Fixed on 2026-09-03 — the arm, the cause, and one thing the cause turned up.** `EXTERNAL_REFERENCE` maps to `attachment:read`, which is what `list_references` requires — **D-61**. The enumerating test is gone, replaced by `tests/audit_object_types.rs`, which walks the crate's source for the three shapes an object type takes (an `…OBJECT_TYPE` constant, an `object_type:` literal, a literal in a `fn object_type(` body) and asserts **both directions** with a count guard.

**Three mutations, each seen red** (§2.9): removing the new arm reddens *every object type this crate writes can be placed*, and its message names `EXTERNAL_REFERENCE` — which is what proves the walk sees the type rather than passing vacuously; adding an arm for `SOMETHING_NOBODY_WRITES` reddens *every arm answers for a type something writes*; narrowing the walk to `modules/audit` reddens **both**, on the count guard.

**Designing the second direction found a dead arm.** `PARTY_ROLE` had a `readable_by` arm and **nothing writes it** — a party gaining the SUPPLIER role is audited as `PARTY`, because `object_id` is the party (`master_data::service::role`, naming convention §7). The arm carried a careful argument about #81 and **D-12**, for rows that do not exist. It is retired, and the argument is kept as a comment where the arm was, so the next author who writes a `PARTY_ROLE` row meets it at the moment direction 1 fails them. **An arm nothing can reach is the same ageing checklist as a list nothing regenerates**, which is this finding restated from the other side.

**What the fix does not close, stated in the test's own doc.** The walk understands three write shapes; a fourth — a type built by `format!`, read from a column, returned by a differently named method — is invisible to it, and here that bluntness runs in the *unsafe* direction rather than the safe one `configuration_reference` enjoys. **The real close is the type system**: an enum for `AuditEntry.object_type` and an exhaustive `match` with no wildcard would make an unplaceable type fail to compile, which is what this project did to `activity::record`'s executor and `scanner::scan`'s outcome. It is 69 construction sites across eleven modules and is recorded in **D-61** as owed rather than done.

### Finding 3 — the release stack pins its language runtimes and not its infrastructure. **Fixed 2026-09-03.**

**Every image Phase 6 depends on is `:latest`, in the compose file `v0.6.0` will be deployed from.**

| Pinned | Floating |
|---|---|
| `postgres:16`, `rust:1.89`, `node:24-alpine` | `minio/minio:latest`, `minio/mc:latest`, `clamav/clamav:latest`, `axllent/mailpit:latest` |

Both `deploy/docker/docker-compose.yml` and **`deploy/staging/docker-compose.staging.yml`** — the release stack — and CI, which starts MinIO as `minio/minio:latest` in its own step and runs ClamAV as a `:latest` service.

**This is not hypothetical; it is how §5 happened.** The MinIO that `docker compose up` pulled on this machine refuses the `object_store` client's signed `PUT` with an empty-bodied `426 Upgrade Required`, and thirteen tests fail with `INTERNAL_ERROR` — which reads as a product defect and is an image change.

**And one instance has a consequence the compose file itself already wrote down.** Beside the `clamav` service:

> **`StreamMaxLength` must stay strictly above `KELIR_STORAGE_MAX_UPLOAD_BYTES`.** clamd's own sample config documents 25M, which is exactly the upload limit; at that value every maximum-size upload is refused by the scanner, recorded FAILED and permanently undownloadable. **This image's effective default is 100 MiB, which is why nothing is set here.**

A deliberate decision to configure nothing, resting on the default of an image that is fetched fresh on every deployment. If a future ClamAV image ships the 25M its own sample config documents, every maximum-size upload becomes permanently undownloadable in a stack whose compose file explains exactly why. **The reasoning is right and the pin it depends on does not exist.**

Sprint 12's lesson was that the deployment is the artefact nothing reads. This is the version of that which no test can reach even in principle, because the artefact changes without the repository changing.

**Fixed on 2026-09-03 — and a test can reach it after all, which is the part this finding got wrong.** All four are pinned in all three places, to **what `latest` resolved to that day**, confirmed by digest before the edit so the change froze the stack rather than moving it: `minio/minio:RELEASE.2025-09-07T16-13-09Z`, `minio/mc:RELEASE.2025-08-13T08-35-41Z`, `clamav/clamav:1.5`, `axllent/mailpit:v1.31` — each byte-identical to the `latest` it replaced. **D-62.**

**Two granularities, because two of the four have no version line.** MinIO and `mc` publish only `RELEASE.<timestamp>` and `latest`, so a bump there is a deliberate edit; ClamAV and Mailpit have patch lines, which is the granularity `postgres:16` already uses.

**`tests/deployment_images_are_pinned.rs` is what makes it hold.** It walks `deploy/` and `.github/workflows/` and fails on a floating tag or an untagged `image:`, comments stripped first so the rule can be explained where it applies. Two mutations, each seen red: returning the staging ClamAV to `:latest` reddens *no deployment file names a floating image tag*, and reducing `postgres:16` to `postgres` reddens *every image key names a tag*. **This is finding 2's lesson applied before it was needed** — a pin nothing regenerates ages exactly the way a list nothing regenerates does.

**Executed, not only edited.** The stack was brought up from the pinned compose file and each service answered its own protocol: `minio-init` exited 0 with its `mc ls` postcondition satisfied, clamd answered `PONG` on the wire — the check `ci.yml` itself uses — and Mailpit and MinIO answered 200 on their health endpoints. The running containers report the pinned tags.

**And the ClamAV consequence is closed as far as a pin can close it.** The decision to configure no `StreamMaxLength` now rests on a version that does not move, and both compose files say that a bump re-checks the default. Setting the value outright would close it further; it needs a `clamd.conf` mount, which changes how the image loads its configuration, and that is a change worth its own issue rather than a rider on this one.

**What this did not do is fix §5.** The local `426` is unaffected, and pinning was never going to: the MinIO this environment refuses uploads against **is** `RELEASE.2025-09-07T16-13-09Z`, the same digest `latest` resolves to. The pin makes the stack reproducible; it does not make this machine work.

## 4. What was read and cleared

Stated because a pass that reports only what it found tells a reader nothing about where it looked.

- **Tenant scoping across the sprint** — §2, dimension 1. 94 statements, one documented exception. Clean.
- **`redact_for`'s direction.** An unplaced object type withholds rather than opens; mutation M2 in `audit_search.rs` covers it. The `_ => return None` arm is right, and finding 2 is a gap in what reaches it, not in what it does.
- **The two `AUDIT_READ` constants.** `audit::AUDIT_READ` is `"audit:read"`; `master_data::service::audit_record::AUDIT_READ` is `"master-data:audit:read"`. A bare-name resolution across the tree collides them and made item 3 look as though it had widened the master-data permission after all. It has not — the two are separate constants in separate modules, and #304's claim of *two surfaces, two questions* holds. Recorded because the near-miss is the shape a careless sweep reports as a finding.
- **Notification recipient scoping.** Every read and write in `notification/repository.rs` carries `recipient_user_id` except three, each correctly so: `holders_of_role` computes recipients, the two channel/template reads are tenant-scoped configuration, and `pending_deliveries` is the worker's read. `mark_delivered` takes its tenant from the row the worker read — #294's lesson applied — and keeps the `status = 'PENDING'` predicate whose mutation first went green.
- **The completed-task visibility rule (item 7).** A role task decided by a holder who never claimed it records that holder: `assignee_user_id = COALESCE(assignee_user_id, $5)` in the statement that completes the task, with a comment saying why. So `scope=completed` cannot show one role holder another's decisions. **This was a hypothesis of this pass and it was wrong** — the code anticipated it. `CANCELLED` is also matched by the completed scope and would not set an assignee, but nothing in this release writes that status to a task; the predicate is defensive, not live.
- **Soft delete on attachments (item 5).** `deleted_at IS NULL` appears in all sixteen reads and both soft-delete writes, including the statement that serves the bytes. The claim that the refusal is *in* the serving statement holds.
- **`safeHref` (item 5, frontend).** Trims, lowercases, requires an `http://` or `https://` prefix, returns the original string. A `javascript:` URL, any casing, any leading whitespace, and any other scheme all yield `undefined`. Paired with `rel="noopener noreferrer"`. Sound.
- **Markup injection on the two new screens.** No `v-html` and no `innerHTML` anywhere in the changed frontend; comment bodies reach the DOM through interpolation. Sound.
- **OpenAPI currency.** `every_annotated_route_reaches_the_document` reads the source in both directions and covers the sprint's new routes. This is the test finding 2 says the audit one should have been.

## 5. What this pass could not execute

**Object storage writes do not work in this environment, so thirteen tests could not be run here.** Every `PUT` from `object_store/0.12.5` is refused with an empty-bodied `426 Upgrade Required`, against both the MinIO that `:latest` currently resolves to and a pinned `RELEASE.2025-04-22`. The request was captured and is an ordinary correctly-signed SigV4 `PUT` with `content-length: 64` and no chunked encoding; `mc` writes to the same bucket over the same network without trouble, and the clocks agree.

**The signature of the failure is what says it is environmental, and it is exact:** in `attachment_upload`, run serially, the three tests that need a successful `PUT` fail and the seven that do not — including `an_upload_whose_bytes_cannot_be_stored_records_nothing`, which *wants* a storage failure — pass. The same holds across `attachment_download`, `attachment_tail`, `attachment_scan` and one activity test. **No test that avoids storing bytes fails anywhere in the suite.**

So: **1,265 of 1,278 executed and green; 13 unexecuted.** They are green in CI, and this pass does not claim otherwise — it claims only that it did not run them. What it withholds is any statement about items A and 5's storage paths beyond what reading them supports, and about the scan-state gate end to end.

**The e2e suite was not run** for the same reason, so status report 14's finding — that no browser flow uploads, downloads or comments — is neither confirmed nor extended here beyond reading `e2e/tests/`.

## 6. A correction to status report 14, produced by this pass

[Status report 14](../status/14.%20Sprint%2013%20Status.md) said the sprint's mutation-campaign evidence was thin and that where it went *"is not recoverable from the repository"*, having counted commit bodies. **That was measuring the wrong artefact, and the conclusion was wrong.**

The evidence is in the **test files**, dated, tabulated, and naming the reddened test for each mutation — which is precisely what [coding standard](../../docs/standards/01.%20Coding%20Standard.md) §2.9 asks for, in a more durable place than a commit message:

| File | Item | Mutations recorded |
|---|---|---|
| `audit_search.rs` | 3 | 6, M1–M6, run 2026-09-01 |
| `notifications.rs` | 2 | 6, run 2026-09-01 |
| `master_data_governance.rs` | 6 | 4, run 2026-09-02 |
| `notification_email.rs` | 8 | 4, run 2026-09-02, one first green |
| `task_inbox.rs` | 7 | 4, run 2026-09-02, plus one that no longer compiles |
| `attachment_tail.rs` | 5 | 3, run 2026-09-02 |
| `configuration_reference.rs` | #316 | 3, run 2026-09-02 |
