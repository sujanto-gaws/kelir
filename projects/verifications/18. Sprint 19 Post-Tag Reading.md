## 3. Findings

**Grading, per the brief §5.** *Blocking* means it blocks plan 16 row 3 (#519) from merging: a defect in the transition transaction's locking or task-raising that row 3 would build on, or a claim in a shipped text that a probe refutes and that users or operators act on. Every non-blocking finding is to be placed **by name in Sprint 21's plan**.

### Finding 1: no test sees the lock `delete_role` takes. **Not blocking. [#528](https://github.com/sujanto-gaws/kelir/issues/528).** Answers lead 9; the mutation was this reader's choice.

#513's lock is right. P1a shows the delete waiting on a transition's `FOR KEY SHARE` and then counting the task. But both race tests in the tree, #513's in `task_inbox.rs` and #514's in `workflow_engine.rs`, **take the delete's half themselves**, as raw `SELECT … FOR UPDATE`. They prove the transition waits. They cannot see what `delete_role` locks. Under M1 every author test stays green. P1a goes red: **no wait, 204, and a task offered to a role deleted in the same instant**. That is lead 1's second outcome, the state D-89 exists to forbid.

**Why not blocking.** There is no defect: the code at `addc924` locks correctly in every order forced here. The gap is regression cover. **It sits in the transaction row 3 extends**, so #528 is worth landing beside row 3 rather than after it. But the brief's bar for blocking is a defect or a refuted claim, and this is neither.

### Finding 2: a claimed task counts as needing a role its assignee no longer needs. **Not blocking. [#529](https://github.com/sujanto-gaws/kelir/issues/529).** From lead 2; the shape is this reader's.

`count_open_tasks_needing_role` counts a task offered to the role *claimed or not*. #513's reason for the claimed half is *"a decision resolves allowedBy again"*, but that is the count's **second** clause (an edge naming the role). A decision checks the caller against the assignee *or* the candidate role, then the edge. P2: with the task offered to Q and its edges `allowedBy` E, deleting Q leaves the claimed task **decidable (200)**, and deleting E does not (422).

Three texts are untrue for that shape: the 409's *"would leave nobody able to decide them"*, User Manual §11.2's *"even after somebody has claimed it"*, and #517's *"every decision on it is refused"*. #517's query lists the task as stranded.

**Why not blocking.** Every one of these texts errs toward refusal. A user who acts on them has the task decided, and an operator who acts on them runs a repair that still works. Nobody is led into a stranded state.

### Finding 3: a claimed task on a deleted role still waits for you. **Not blocking. [#530](https://github.com/sujanto-gaws/kelir/issues/530).** Answers lead 3.

#507's join sits inside the `assignee_user_id IS NULL AND EXISTS (…)` arm. A claimed task reaches its assignee by `assignee_user_id = $2`, whatever became of the role. P3: after GONE is deleted, its holder's **five surfaces all fall from 2 to 1**: the inbox total, `tasksWaiting`, `pendingTasks`, `tasksOverdue` and `overdueTasks`. The one left is the claimed task, whose decision is **422**. **The surfaces agree with one another, and `late_work` agrees with the inbox.** The filter hides nothing still decidable: the unclaimed task it hides cannot be claimed (403). The `[Unreleased]` line *"A task offered to a deleted role is no longer waiting for you"* holds for an unclaimed task only.

**Why not blocking.** Since D-89 the API cannot reach this state (#513 counts a claimed task, P2). Only a pre-D-89 delete leaves one, and #517's query finds it.

### Finding 4: a negated remedy is said to *settle the class*, and splits under `i`. **Blocking for plan 16 row 3, as a claim, not as code. [#531](https://github.com/sujanto-gaws/kelir/issues/531), `sprint:20`.** Answers lead 5.

#505 appends `NEGATED_REMEDY_LIMIT` to the `\D`, `\W` and `\S` reasons: *"A negated class still counts a character outside the BMP, such as an emoji, as two units in the browser and one here, **so this settles the class and not that**"*. **It reads no flags**, which is the defect #505 fixed in the `\p` arm beside it. P5:

- **`i`**: `[^A-Za-z0-9_]`, the `\W` remedy, accepts U+017F ſ and U+212A K in the browser and refuses both on the server. The remedy does not settle the class.
- **`u`**: `[^0-9]` counts an emoji as one unit in the browser, as the server does. The sentence's premise is false.

The remedies themselves are fine. **The sentence is an agreement claim between engines**, and the brief names that kind: *no reason text may reintroduce a claim about a subset, safety, or agreement between engines, in any wording*. **D-88's stopping rule applies: the claim is struck, not narrowed.** A flag-by-flag version of the sentence would be the next claim to split.

Every reason's own worked example held (P5), and so did everything else lead 5 asked:
- **A pattern that trips two constructs** is told about the first. `refuse_pattern` returns one `Divergent` construct, and the author meets the second after fixing the first. That is true, and serial.
- **ADR-0038's row and Registry 1.5.5** match `divergence_reason`: `\p` is refused whatever the flags, with a reason that depends on `u`.

**Why blocking.** It is a claim in a text users act on: a form author reads the refusal and writes the remedy it offers. A probe refutes it. That is §5's second clause. It blocks row 3 only as the brief defines blocking; it touches no code row 3 builds on.

### Finding 5: a refused role delete says how many tasks, never which. **Not blocking. [#532](https://github.com/sujanto-gaws/kelir/issues/532).** Answers lead 4.

The 409 is `CONFLICT` in the envelope with `details: []` and a count. OpenAPI states both the 404 and the 409. `RoleListPage.vue` shows the message verbatim. User Manual §11.2 and the message both say *"have those tasks decided"*. **The only task routes read the caller's own work.** So the administrator who is refused cannot find the tasks, or who holds them. The way out the manual names (a holder decides) exists. The administrator cannot see where it is. #512 is about reassigning or cancelling a task, not finding one, so this is filed on its own.

### Finding 6: the stranded-task query spans tenants and does not say so. **Not blocking. [#533](https://github.com/sujanto-gaws/kelir/issues/533).** Answers lead 7. From reading; the control was not planted.

#517's query has no tenant filter and no tenant column. It identifies rows by `document_number`, `title` and `task_ref`, which are unique per tenant. Its repair then needs the deleted role's **id**, and the query returns its **code**. Every control that *was* planted held (P7). The brief allowed the other-tenant task to be found if the document says why. It does not say.

### Seen in passing, outside the range: a refused decision is told about a task it would not create. [#534](https://github.com/sujanto-gaws/kelir/issues/534).
