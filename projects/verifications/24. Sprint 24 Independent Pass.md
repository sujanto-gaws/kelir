**What *blocking* means here, as the brief defines it.** A finding blocks if a Sprint 25 row that changes one of plan 21 §1.2's six modules should not merge with it. **No finding below meets the bar.** Findings 1 and 2 are in held modules (auth and workflow), and each is a gap no row widens. ### Finding 1: a sign-in during a password change outlives it. **Not blocking. [#788](https://github.com/sujanto-gaws/kelir/issues/788).** Answers subject 2, *is #756's window the only one?*

**#756 is as filed** (§4.2), **and it is not the only window.**
- `sign_in` verifies the stored hash on a blocking thread (`auth/service.rs:166-172`), then `issue_session` (`:215`) inserts the refresh token on the pool through `store_session` (`:519-536`). Nothing after the verify reads the password, or anything that moves with it.
- Every password path revokes with one statement, `UPDATE refresh_tokens … WHERE user_id = $1 AND revoked_at IS NULL` (`identity/repository.rs:386`): the change (`auth/service.rs:636`), the reset (`reset.rs:308`) and the administrator's set-password (`identity/service.rs:313`).
- **So a change that commits while a sign-in is between its verify and its insert leaves the sign-in's token live.** Serially, sign-in-then-change would have revoked it, and change-then-sign-in would have refused the old password. **P1 shows it**: the sign-in answered 200, and its token renewed after the change.
- **The window is the whole Argon2 verify**, wider than #756's one statement.

**Why not blocking.** It is not a regression of the range: #754 split `issue_session` but did not change what the sign-in reads. **No Sprint 25 row widens it.** But **row 6's remedy for #756, a lock between the rotation and every user-wide revoke, does not close it**, because a sign-in holds nothing a revoke waits on. **So row 6's criteria and its ADR should decide both paths**, and #788 says so.

### Finding 2: a publish accepts an unbuilt path read through `reduce` or a computed `var`. **Not blocking. [#789](https://github.com/sujanto-gaws/kelir/issues/789).** Answers subject 1, *does a publish refuse every unbuilt path, and only those?*

**Only those: yes** (§4.1). **Every one: no.**
- `condition_path_errors` (`workflow/domain/jwss.rs:538-587`) reads what `visit_paths` (`rad/domain/engine.rs:257-293`) yields.
- `visit_paths` walks an iterator's first argument only (`:274-281`). **`reduce`'s initial value is evaluated in the outer scope, against the whole context**, and is not walked.
- `var_path` (`:209-216`) yields a path only for a string or an array opening with one. **datalogic-rs 5.2.0 evaluates a `var` whose operand is an expression, and reads the path it computes.** `if` and `var` are both in the conditional tier.
- **P2 and P3 show it**: both shapes evaluate `true` against `document.amount = 7`, and both publish `ACTIVE`. A plain `var` of the same path is refused.
- **#770's own test pins the `reduce` case as accepted**: `condition_path_errors_reads_an_iterators_source_and_not_its_element` (`jwss.rs:1331-1358`) puts `document.amount` in the initial value, and its comment says the value *"is not read either"*.

**Why not blocking.** It needs an author to write one of these shapes in the condition's JSON box, and the effect is #706's silent fallback, not a corruption. **Nothing in Sprint 25 changes the check.** The same walk serves the form engine's dependency graph, where a `calculate` reading a field through `reduce`'s initial value has no edge (read, not probed).

### Finding 3: an options edit turns every option's value into text. **Not blocking. [#790](https://github.com/sujanto-gaws/kelir/issues/790).** Answers subject 6, D-110; from the `schema-guardian` subagent's candidate C1, re-read and probed here.

**Why not blocking.** The saved definition still validates (`options[].value` is `{}` in `jfss-meta-v2.0.1.json`), and it needs an edit of that box. **D-110's own claim holds**: nothing is rewritten on load, on selection or without an edit (§4.6). This is an edit that rewrites what it did not touch.

### Finding 4: #772's texts say more than its table and its caption. **Not blocking. [#791](https://github.com/sujanto-gaws/kelir/issues/791).** Answers subject 9; from the `requirements-analyst` subagent's candidates 1–3, re-read here.

## 4. What was read and cleared

### 4.1 Subject 1: #770, the condition paths, and `role_codes_for_user`

**Does a publish refuse only unbuilt paths?** Yes. `is_built` (`jwss.rs:593-615`) accepts each bare root, `DOCUMENT_FACTS` and `ACTOR_FACTS` under their roots, a numeric index after `actor.roles.`, anything under `formData`, and a declared key under `variables`. **Those are exactly what `EvaluationContext::as_json` (`engine.rs:198-205`), `document_facts` (`:228-240`) and `actor_facts` (`:256-266`) build**, and a unit test holds the two lists to the builders (`the_context_holds_exactly_the_keys_a_publish_accepts`, `engine.rs:1983-2006`). The check is pure, and runs in `publish_definition`'s transaction after the revision's `FOR UPDATE`, so it adds no lock. **Every one**: no, finding 2.

**Do a token's `roles` and `permissions` agree, at sign-in and at refresh?** Yes.
- **Both are built by one function**, `mint_session` (`auth/service.rs:485-501`): `sign_in` reaches it through `issue_session` (`:215`, `:465-474`) and `refresh` directly (`:324`).
- `role_codes_for_user` (`identity/repository.rs:245-266`) and `permissions_for_user` (`:208-233`) now read the same window, `valid_from <= current_date` and `valid_to >= current_date`, inclusive at both ends, and the same live role.
- `/auth/me` returns the token's own claims (`auth/handlers.rs:234-238`), so it agrees with the token by construction.
- **Two things that are not disagreements, stated.** The two reads are two statements on the pool, so a grant changed between them, or a window crossing midnight between them, can split one token. And `role_codes_for_user` has no `DISTINCT`, so two live grants of one role list its code twice in the claim; `actor_facts` deduplicates for the engine. Read, not probed.

**Did anything else read `role_codes_for_user`?** **One reader besides the token**: `read_actor_facts` (`workflow/service/engine.rs:281-298`), the `actor.roles` #770 built, called on the submit, the resubmit and the decision. `grep` over `src/` finds no third. `holds_role` and the bootstrap read their own queries.

**The paths it builds**: `document.documentTypeKey` is the stored `type_code`. `actor` is the person acting, read fresh on the pool before the caller's transaction (plain reads, so record 23 §5 is kept). #755's guard key reads `document.documentTypeKey`.

### 4.2 Subject 2: #754, the rotation transaction

**What the refresh does** (`auth/service.rs:261-352`): a plain read of the token, the user's and the tenant's checks, `mint_session` on the pool, then one transaction: `revoke_refresh_token` guarded by `revoked_at IS NULL`, and if it changed a row, `store_session` and commit. **A rotation that changed nothing rolls back and is refused as the reason it re-reads says** (`refuse_revoked`, `:357-416`): replay evidence sweeps and audits `TOKEN_REUSE`, an administrative revoke is a quiet 401.
- **Of two refreshes at once, only one renews**: the second's `UPDATE` waits on the first's row and changes nothing. #754's race tests ran and passed in the suite (§2).

**Is #756's window as filed?** Yes. `revoke_all_for_user` is one `UPDATE … WHERE user_id = $1 AND revoked_at IS NULL` (`identity/repository.rs:386`). Under READ COMMITTED, a revoke that waits on the rotation's row re-checks that row only, and the rotation's new token, inserted after the revoke's snapshot, is not seen. **Is it the only one?** No: finding 1.

**Does the rotation keep record 23 §5's rules?** Yes. Those rules govern the workflow's rows, and the rotation takes only `refresh_tokens` rows: the presented token's `FOR NO KEY UPDATE` through its `UPDATE`, then the new row's insert, whose foreign keys take the user and the tenant `FOR KEY SHARE`. **No workflow, document, type, role or user row is locked exclusively**, so it closes no cycle with §5's paths.

### 4.3 Subject 3: #743, and the document-type dialog with #727, #740 and #744
