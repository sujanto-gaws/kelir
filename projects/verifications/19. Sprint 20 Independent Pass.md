### Finding 1: a tenant created after `0046` gets every integration permission, and the upgrade note says it does not. **Blocking, as a claim. [#551](https://github.com/sujanto-gaws/kelir/issues/551), `sprint:21`.** Answers lead 7. The mechanism, D-18's provisioning, is this reader's.

`provision_tenant_identity` grants a new tenant's `ROLE-ADMIN` every catalogue permission except the `organization:` family (D-18). `0046` adds eight to the catalogue. **So every tenant created after the upgrade has all eight**, and P7 found the grants and a 200. The `CHANGELOG`'s first upgrade note says *"An administrator of any other tenant does not get them … grant [`integration:credential:read`] separately and deliberately"*. User Manual §11.5 says *"Only the system tenant's administrator starts with these permissions"*. #543's description says the same. Database Schema §12.10 is accurate: it speaks only of a tenant provisioned *before* the migration.

**Isolation itself held** (P7: 404 on every id route, an empty list). The fault is what an operator is told about who can see where secrets are kept.

**Why blocking.** The note is an upgrade instruction, and the first tenant created after the upgrade contradicts it. #551 leaves the direction to the product owner: correct the texts, or withhold the family at provisioning.

### Finding 2: a secret reference is said to be *never a secret*, and `vault://sk_live_…` is stored. **Blocking, as a claim. [#552](https://github.com/sujanto-gaws/kelir/issues/552), `sprint:21`.** Answers lead 8.

The code does what its module comment and SDD §9.3.3 say: **a shape check, which a secret typed as a path segment passes**. P8 stored `vault://sk_live_51HxQ2eKZ8r`, `env://SK_LIVE_51HXQ2EKZ8R`, a 40-character key behind `vault://`, and `vault://erp#hunter2`. Six other texts claim more:

- **User Manual §11.5**: *"Kelir never stores a password, key or token … Anything else is refused, including a value that looks like the secret itself."*
- **`CHANGELOG`**: *"A credential is a reference, never a secret … no response carries a secret."*
- **Database Schema §12**: *"`secret_reference` is never a secret … No column in this section can hold a resolved secret, so no route can return one."*
- **OpenAPI**: the `integration` tag's *"No route carries a secret value"*; *"never a secret"* on the credential list; *"Never the secret."* on `secretReference`.
- **`0046`'s header**: *"Nothing in this schema can hold a resolved one."*
- **#520's AC-5 heading**: *"Secrets never stored as values."*

**D-88's stopping rule applies.** As far as this reading can tell, these sentences were not already split twice. But the rule's reason holds: a narrowed *never* is the next claim to split. So #552 asks for them to be **struck**, leaving SDD §9.3.3's wording.

**Why blocking.** The manual tells the person at the form that Kelir catches a pasted secret. It catches one without a scheme, not one behind `vault://`. Every `integration:credential:read` holder and the audit trail then show it.

### Finding 3: the `\w` remedy is said to be what the browser does, and splits under `i`. **Blocking, as a claim. [#553](https://github.com/sujanto-gaws/kelir/issues/553), `sprint:21`.** Answers lead 14. The arm is this reader's: the lead named #538's negated ones.

`divergence_reason` still says *"Write the class out: `[A-Za-z0-9_]`, **which is what the browser was already doing**"* for `\w`. The `\W` arm keeps the same clause in front of #538's new disclaimer, so it now says both. Under `i`, `compile_pattern`'s `case_insensitive` makes the server's `[A-Za-z0-9_]` match **U+212A K and U+017F ſ**, and the browser's does not (P14). The sides do not match after the remedy.

**#531's *Done when* already covered this**: *"any other reason text that says a remedy settles, agrees or makes the sides match"*. #538's change, and #542's N2/N3, reach only the negated arms. P17 confirms #538's own hunk is held.

**Why blocking.** It is #531's grade, for #531's reason: a form author writes the remedy the refusal offers. D-88: struck, not narrowed.

### Finding 4: an endpoint path carries `?api_key=`, which F1 refuses in a base URL. **Not blocking. [#554](https://github.com/sujanto-gaws/kelir/issues/554), plan 18.** Answers lead 9.

`endpoint::path` allows `?`, and its own test accepts `/orders/{id}/lines?expand=true`. P9 stored `/orders?api_key=sk_live_51HxQ2eKZ8r`. The base URL, under F1's `QUERY_IN_BASE_URL`, still stores a key behind `%3F`, behind `;`, or as a path segment (any incoming-webhook URL), on create and on edit. **No text claims otherwise.** The `CHANGELOG`'s *"so a key cannot ride in `?api_key=`"* is about `baseUrl`, and it holds there. **No text says a base URL *carries no secret*.** It is a product decision F1 did not reach, and #554 puts it to the product owner.

### Finding 5: `QUERY_IN_BASE_URL` is in neither OpenAPI nor the User Manual. **Not blocking. [#555](https://github.com/sujanto-gaws/kelir/issues/555), plan 18.** Answers lead 12.

Of #543's three late changes, `/activate` reached OpenAPI, the manual and the `CHANGELOG`. The credential index is used (P12). **`QUERY_IN_BASE_URL` reached the code and the `CHANGELOG` only.** The string does not occur in the served OpenAPI document, and User Manual §11.5 names only the user-name-and-password refusal. The dialog shows the code's message on the field, so a user sees the refusal. They just cannot read about it.

### Finding 6: an after-hook delivery makes a submission wait, and no document says so. **Not blocking. [#556](https://github.com/sujanto-gaws/kelir/issues/556), plan 18.** Answers lead 1.

**The lock order as found:**
- **A decision**: instance `FOR UPDATE`, task `FOR UPDATE`, then `fire`, which is `history::record`, **then `publish_transition`** (a plain `count(*)` on the history, and an outbox `INSERT` whose only lock is the `tenants` key share), then `enter`, which is record 18 §4's four steps.
- **An automatic advance** writes its event after its history row, at the end.
- **The worker**:
  - The claim is one committed `UPDATE … FOR UPDATE SKIP LOCKED` on outbox rows alone.
  - Then one transaction per event, with plain reads of the instance, definition, document and registry.
  - **Then `document_hook_executions` inserts**, which take `FOR KEY SHARE` on the document, and on a breaker's report a notification insert, which takes key shares on the recipients.
  - Then the fenced settle.

**Record 18 §4 still holds** for the four steps it names. Its prediction that row 3's writes *"sit between steps 2 and 4, or after them"* is wrong for `fire`, where the insert comes before step 1. It is harmless, because that insert conflicts with nothing a transition or `delete_role` holds.

**The edge #537 added**: the worker's key share conflicts with `lock_document`'s `FOR UPDATE`. A submission or resubmission of a document whose event is being delivered waits for the delivery to commit (P1: 18.1 s, forced). The worker waits on nothing a transition holds, so no cycle forms. Three-way interleavings (a role delete beside a held delivery and a waiting resubmission) were not run. **ADR-0041 does not cite record 18 §4**, as the brief expected it to, and nothing states this edge.

### Finding 7: an unclosed fence hides a co-author, and a `Merge` title skips the check. **Not blocking. [#557](https://github.com/sujanto-gaws/kelir/issues/557), plan 18.** Answers lead 15. #485's squash half is open by design, and this is not it.

`unfenced()` drops everything after a fence that never closes, so a Claude co-author written after one is dropped too. Git still parses it as a trailer (`git interpret-trailers --parse`). **The rule #523 added to stop a quoted session line from counting is what hides the co-author.** Separately, `check_header` skips any header starting `Merge `, and the loop then skips the session check, for a non-merge commit as well (P15).

### Finding 8: the kind-mismatch refusal carries runs of 34 spaces. **Not blocking. [#558](https://github.com/sujanto-gaws/kelir/issues/558), plan 18.** From a probe this reader chose.

Both `HANDLER_KIND_MISMATCH` literals in `check_entry` continue across lines without `\`, so the newline and the indentation are in the message (P3b). The unit test reads only the text after *"the handlers that can are "*.

## 4. What was read and cleared

- **At-least-once and the lease fence** (lead 2, P2). The overtaken worker commits none of its consumer writes (campaign gap M25 holds under two real processes), and the new claimant runs the chain again. That is ADR-0041's stated duplicate, and LHCS §5.2 makes it the handler's to tolerate. **Nothing the docs call *exactly once* happened twice.** `concurrent_passes_deliver_each_event_exactly_once` means one *settled* delivery, and that is what P2 shows.
- **A before-only handler in an older definition** (lead 3, P3a). It is never retryable, never dead-lettered, and the rest of the chain runs, as ADR-0041 §2 and the `CHANGELOG` say. It does **open the breaker and notify once**, which `five_kind_errors_open_the_breaker_and_tell_the_administrators_once` holds and the notification's own text explains. The `CHANGELOG` says only *"logs an error"*. That is incomplete, not false, and it is noted here rather than filed.
- **The breaker in a second tenant, end to end** (lead 4, P4): the threshold, who is told, the hold, the cool-down and the single trial, all on real transitions. **Two parts were not driven here**: a trial that *succeeds* and closes the breaker, because no after-capable handler fails on demand (`a_trial_after_the_cool_down_that_succeeds_closes_the_breaker` covers it), and concurrent trials (§5).
- **The envelope** (lead 5, P5). No form data or comment, in a decided transition and in a resubmission. **Sequence**: ADR-0041 and EES §3.1 claim only *"the transition's position in the instance's `workflow_history`"*, and EES §2 claims *monotonic*. Both hold. **It is not gapless as a consumer sees it.** The start row is 1, so an instance's first event is 2, and an instance `0.8.0` moved starts at 3 (P6). Nothing claims otherwise. A rolled-back transition takes its history row with it, so it leaves no gap. Only `start`, `fire` and `advance_automatically` write history, so a history row with no event is always the start, or an event `0.8.0` never wrote. **An automatic advance was not driven here.** `tests/outbox.rs` and `workflow_system_tasks.rs` cover it, and its payload is built by the same `publish_transition`.
- **`0045` and `0046` N−1** (leads 6, 11, P6), against the real `kelir-backend:0.8.0`, as record 17's P5 did with `0.7.0`. Nothing claims that `0.8.0` writes events, and the new binary copes with an instance whose history has none.
- **Tenant isolation on all 15 routes, `/activate` included** (lead 7, P7). All return 404, not 403, matching the house rule.
- **Audit values of credentials** (lead 10, P10). The gate's test asks the same question P10 asked: values withheld per row by `ObjectType::readable_by`. No other route exposes a reference: the system and endpoint responses carry none, and the credential routes need `integration:credential:read`.
- **The composite keys at the database** (lead 11, P11), all eight. **`integration_logs.document_id` is a single-column `REFERENCES documents (id)`**, and a tenant-B log row naming a system-tenant document was accepted. No key in the schema references `documents` compositely, and `documents` has no `(id, tenant_id)` target. `0046` claims tenant-carrying keys only for references to `external_systems` and `webhook_subscriptions`. So this is the project's convention, and it is recorded here rather than filed.
- **The three late changes** (lead 12): `/activate` in every text, and the credential index used, with finding 5 the exception.
- **`register-an-external-system` under #526's rule** (lead 13, P13), and **#526's five specs** past 20 types, roles and tenants (P17). The saves are confirmed by their responses, and the paging helper is exercised: the page-one controls go red.
- **#538's struck claim** (lead 14): no *settles*, *subset*, *safe* or *agree* remains in the negated arms, the Registry, ADR-0038, the `CHANGELOG` or the User Manual. #542's N2 and N3 hold the disclaimer on `\W` and `\S`. Finding 3 is the arm #538 did not reach. The `\B` and `\b` reasons' *"There is no spelling … both sides agree on"* and the `\s` and `\S` *narrower* and *wider* statements are true as written, and no probe here split them.
- **D-92's identity claim** (lead 16, P16), reproduced, together with everything the brief listed as checkable. **The deploy files and `ci.yml` pin by tag, not by digest.** The Installation guide lists the digests as the images' identity and does not claim the files pin them, so this is not a finding.
- **#524 and #526 were seen red** under their controls (P17). The approval-time spec's margins hold on this machine.
- **#523's four refused shapes and #542's S1, S3 and S8** all behave (`check-commit-messages.probe.sh`: *Every probe behaved.*).
