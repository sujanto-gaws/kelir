## 3. Findings

**What *blocking* means here, as the brief defines it.** A finding blocks if a Sprint 24 row that changes `kelir-backend/src/modules/workflow/` should not merge alongside it. **No finding below meets the bar.** Finding 1 is in that module, and its remedy is already written, as #745's AC7 commits.

### Finding 1: a submit racing a deprecate starts on the deprecated revision. **Not blocking. [#747](https://github.com/sujanto-gaws/kelir/issues/747).** Answers subject 1, and the dated note's question on AC7.

**JWSS §9 and #711's own test disagree.** #711 added to JWSS §9 (`docs/schema/JSON Workflow Schema.md:289`): *"An engine MUST NOT start an instance against a `DEPRECATED` revision."* The same PR pins `a_submit_racing_a_deprecate_starts_an_approval_that_runs_to_the_end` (`tests/workflow_deprecation.rs:1604`):
1. a submit reads the bound revision `ACTIVE` on the pool and passes `engine::start`'s check (`engine.rs:229-258`);
2. a deprecate takes the revision `FOR UPDATE`, sets `DEPRECATED`, commits and answers 200;
3. the submit's instance `INSERT`, which waited on the deprecate's lock through its foreign key, then writes the instance.

**The instance is created after the deprecate committed**, and the test asserts the revision is `DEPRECATED` when the submit returns. As a serial order the history is submit-then-deprecate, which is why the test calls it harmless. **JWSS §9 does not say *serially*.**

**Why not blocking.** The running approval ends as one started a moment earlier would, so nothing is corrupted. The remedy is written: #745's AC7 decides the status under the `FOR SHARE` lock its AC2 takes for #712 (§5.3). **This record rules that AC7's commits stay** (§4.1), and #747 closes when they merge.

### Finding 2: a loaded bare `!` given an array operand is saved inverted. **Not blocking. [#748](https://github.com/sujanto-gaws/kelir/issues/748).** Answers subject 6, D-110; from the subagent's candidate C-A1, re-read and probed here.

- A loaded `{"!": {"var": "a"}}` parses as an operator with `bare: true` (`logicTree.ts:319-328`).
- Its operand's **Advanced (JSON)** box (`JsonLogicNode.vue:391-398`) accepts the array `[0, 1]` as an opaque leaf.
- `serialise` emits a bare operator as `{ [op]: operands[0] }` (`logicTree.ts:404`), so the stored rule is **`{"!": [0, 1]}`**.

JSON Logic reads that array as the argument list, so the rule is `!0`. **The C-A1 probe evaluated both forms with `datalogic-wasm`: the stored rule gives `true`, and the one entered gives `false`.** The server checks which operators appear and not their arity, so it saves it.

**Why not blocking.** It is frontend only, and needs a loaded bare `!` and an array typed by hand as its operand. **D-110's own claim holds**: nothing is rewritten without an edit. This is an edit that changes meaning.

### Finding 5: two refreshes of one token at once both renew. **Not blocking. [#751](https://github.com/sujanto-gaws/kelir/issues/751).** Read in passing on subject 3; outside the range, probed here.

`refresh` (`auth/service.rs:251-344`) reads the token on the pool, takes the reuse branch only if that read saw it revoked (`:262`), and rotates with `revoke_refresh_token` (`:334`), an `UPDATE … AND revoked_at IS NULL` whose row count it discards. **So the refresh that loses the race changes no row, and still issues a session.**

**P3 raced two refreshes of one token**, the first held in its rotation by a `BEFORE UPDATE` gate on `refresh_tokens`:

**Why not blocking.** It is in `auth`, not the workflow module, and dates from before Sprint 23. It needs the token presented twice within one request's time. #708 did not cause it, and its check runs before the rotation, so it neither widens nor narrows it.

## 4. What was read and cleared

### 4.1 Subject 1: #711 against record 22 §5.2

**What the deprecate locks** (`service/definition.rs:428-503`):
1. It opens a transaction and takes the revision `FOR UPDATE` (`repo::lock_for_publish`, `repository/definition.rs:270-290`). **Nothing is held before it.**
2. It reads the revision in that transaction (`find_definition`), and refuses a draft or a deprecated one with 409.
3. It writes the row's own `UPDATE` (`repo::deprecate`, `:337-360`): `status`, `updated_by`, `updated_at`, guarded by `AND status = 'ACTIVE'`.
4. It commits. The read-back (`load`) and the `Workflow.Deprecated` audit row run on the pool after the commit.

**Against the four rules.**
- **Rule 1** (an instance before its document) and **rule 2** (a type after the document, a definition after the type): **the route takes no instance, document or type**, so it cannot break either.
- **Rule 3: kept.** The definition is taken exclusively with nothing held, and after it the route takes only its own row. **One lock record 22 §5.1 does not list**: the `UPDATE` sets `updated_by`, whose foreign key to `users` (`0025_workflow.sql:116`) takes the acting user's row `FOR KEY SHARE` when the value changes. The publish does the same through `updated_by` and `published_by`. **No path takes a `users` row in a mode that conflicts with it**: no `SELECT … FROM users … FOR UPDATE` exists in `src/`, a user is soft-deleted, and a non-key `UPDATE` of a user takes `FOR NO KEY UPDATE`, which `FOR KEY SHARE` does not conflict with. So it closes no cycle.
- **Rule 4: kept.** The route takes no role.
- **What record 22 §7 asked row 5 to say.** It locks the revision, with nothing before it and nothing after it but its own row. It touches no bound type: the type stays bound, and its next submit is refused by `engine::start`'s check (`engine.rs:258`), the #187 rule. **A submit racing it may still start an instance**, and #711 pins that in `a_submit_racing_a_deprecate_starts_an_approval_that_runs_to_the_end` (`tests/workflow_deprecation.rs:1604`). That is finding 1.

**Is the race intended?** The brief's dated note asks for a ruling, because #745's AC7 commits reverse the pin.
- **The pin and the text #711 wrote disagree.** The test calls the race harmless, because the result is the state an approval started before the deprecate reaches. In the same PR, JWSS §9 gained *"An engine MUST NOT start an instance against a `DEPRECATED` revision"*. The racing submit's instance row is written after the deprecate commits, because its foreign key waits on the deprecate's `FOR UPDATE` and is satisfied once it commits. The test itself asserts the revision is `DEPRECATED` when the submit returns 200.
- **Read as a serial order**, the submit read `ACTIVE` before the deprecate, so the history equals submit-then-deprecate. **Read as what an administrator sees**, the deprecate answered 200 and an approval started on the revision afterwards. **JWSS §9 is normative, and it does not say *serially*.**
- **So this record rules the race not intended by the text, and #745's AC7 commits should stay.** The lock AC7 reads under is the one #712 needs anyway (§5). Reading the status under it costs nothing, and makes JWSS §9 true as written. **Dropping AC7 instead would need JWSS §9 narrowed**, and that is a claim a reader has not split before, so narrowing it is allowed. It is the worse choice.

**`delete_definition` as it stands** (`service/definition.rs:589-644`). It reads the revision on the pool, asks `has_live_instances` on the pool, and soft-deletes with one autocommit `UPDATE` of `deleted_at`, `updated_by` and `updated_at`.
- **As a lock rule it breaks none of the four.** The `UPDATE` holds nothing before it and takes nothing after it but the acting user's key. It changes no key column, so it takes the row `FOR NO KEY UPDATE`.
- **It breaks the property its check exists for, both racing and not.** P1 and P2 are the evidence, and both went red (§2):
  - **Not racing.** Nothing on the start path reads `deleted_at`. `definition_of_instance` (`repository/definition.rs:593-607`) has no such filter, the status a soft delete leaves is still `ACTIVE`, and the instance's foreign key does not read `deleted_at` either. So a type bound to a deleted `ACTIVE` revision starts approvals on it.

### 4.4 Subject 4: #707 and ADR-0047

**The comparison** (`integration/domain/secret.rs`, `namespaces_overlap`): the two codes' whole prefixes, `KELIR_INTEGRATION_SECRET_<CODE>__`, compared by `starts_with` in both orders.

## 5. What #712 and #667 must keep

**This is stated as record 22 §5.2 stated its rules: what the paths lock, not a complete lock order.** Rules 1–4 stand as record 22 wrote them. Rules 3 and 4 are restated with what this reading found, and rules 5–7 are new. **Each is a rule a later row can break, and §5.3 says which row would.**

### 5.1 Two locks record 22 §5.1 does not list

- **The acting user's row, `FOR KEY SHARE`**, through `updated_by`, `published_by` and every stamping foreign key, when a write changes the value. It is taken after everything a path holds. **Nothing takes a `users` row in a mode that conflicts with it** (§4.1), so it closes no cycle. It stays true only while no path locks a user `FOR UPDATE`, deletes one outright, or changes its id.
- **The reference sequence rows**, `workflow_ref_sequences`. An `INSERT … ON CONFLICT DO UPDATE` takes the tenant's `WFI-<year>` row in `engine::start` (`engine.rs:289`) and its `TASK-<year>` row wherever a task is raised (`:1186`). These are tenant-wide rows, held to commit by every start and every new task.
  - **They close no cycle**, because both paths take them after their document and type.
  - A decision holds its document `FOR KEY SHARE`, through its task history row, before `fire` reaches one. So the only path that holds a document `FOR UPDATE` and then waits, an edit waiting on its type, cannot hold the decision's document while the decision holds a sequence row.
  - **They are a serialisation point for every start and every new task in a tenant**, which nothing states. Read, not probed.

### 5.2 The rules

1. **An instance before its document.** Unchanged.
2. **A document type after the document, and a definition after the document type.** Unchanged. **With #712, `engine::start` takes the revision itself after the type**, as the binding does.
3. **A path that takes a definition row exclusively holds nothing earlier when it takes it, and after it takes only roles `FOR KEY SHARE`, that definition's own row and projection rows, and the acting user's key.** The publish, the deprecate and, with #712, the delete are such paths, and each takes the row `FOR UPDATE` first in its transaction. A draft's edit is one `UPDATE` on the pool. **`has_live_instances` stays a plain read**: a delete that locked an instance after the revision would close a cycle with a submit, which holds the instance on a resubmit and the document and type on any submit before it waits on the revision.
4. **A role is locked exclusively only by `delete_role`, and it waits on nothing after it.** Unchanged, and kept by #711, which takes no role.
5. **A path that takes a definition row in a sharing mode takes it after the document type, and never upgrades it.** The binding takes `FOR SHARE` after the type. A first submit's instance `INSERT` takes `FOR KEY SHARE` after the type. With #712, `engine::start` takes `FOR SHARE` after the type and before the instance `INSERT`.
   - Either mode conflicts with the `FOR UPDATE` rule 3's paths take, which is what serialises a submit against a deprecate and a delete. Those paths hold nothing else, so a submit waiting on one waits on a path that waits on nothing the submit holds.
   - **A start that later took the revision `FOR UPDATE`, or `UPDATE`d it, would deadlock with a second start holding `FOR SHARE`.**
   - **`FOR KEY SHARE` would serve #712 as well as `FOR SHARE`**, since only `FOR UPDATE` must be excluded. `FOR SHARE` also conflicts with a draft's `UPDATE`, which no bound revision can take.
6. **No path of a running approval locks its revision.** A decision, a claim, a hand-off, a reassign and a resubmit read it plain (`definition_of_instance`), so a running approval never waits on a publish, a deprecate or a delete. That is what lets JWSS §9's *"MUST let an instance already running on it run to completion"* hold under load. **It is not a cycle rule**, and #712's AC8 is its test.
7. **A task is locked or written only by a path that already holds its instance.** Every path that does so today takes the instance first: the claim, the hand-off, the reassign and the decision, and with #667, the resubmit. Every `UPDATE workflow_tasks` in `src/` is reached only from one of them. **Because of that rule, a task's place relative to the document, the type and a governed record cannot close a cycle**: two paths that both want one task meet at its instance first.
   - #667 takes the task after the instance, the document, the type and, on a governed change, its record.
   - A decision takes the task, then the document's key, then on a terminal status the governed record. #667 inverts that order. **It is safe only under rule 7**, and a path that locked a task without its instance would make it a deadlock.

### 5.3 What each row must keep, and whether #745 and #746 do

**#712 (row 6) must keep rules 2, 3, 5 and 6.**
- The delete takes the revision `FOR UPDATE` first in its transaction, with nothing before it. It then reads, asks `has_live_instances` plainly, and soft-deletes in that transaction, with the audit row after the commit.
