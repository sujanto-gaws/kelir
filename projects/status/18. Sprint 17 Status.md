### The suite

**Suite: 1,537 backend tests across 78 targets · 657 frontend tests across 53 files · 13 browser specs.**

The backend figure is a full `cargo test --no-fail-fast` against this sprint's merged content with PostgreSQL, MinIO and ClamAV up: **1,537 passed, 0 failed, 2 ignored (doctests), exit 0**, in [run 34741186135](https://github.com/sujanto-gaws/kelir/actions/runs/34741186135) on 2026-09-13 — **78 targets each reporting `ok`**. The frontend suite was run locally the same day: 53 files, 657 passed, 0 failed, 31.9 s. **Browser: 13 specs, unchanged from [status report 17](17.%20Sprint%2016%20Status.md)** — see the row above.

> **The figure is CI's rather than a local run's, and that is recorded rather than glossed.** Three local attempts died at `LNK1104` while linking a test binary — a transient Windows file lock, with 104 GB free and no competing cargo process — and **a fourth succeeded and was then destroyed by the capture**, which piped it through `tail -50` and kept the last fifty lines instead of the totals. **None of the four is a number, and none was written down as one.** [Status report 17](17.%20Sprint%2016%20Status.md) took its figure from CI on the same reasoning; this report does the same and says which run.
>
> **The static count predicted this exactly, and the two claims are still different.** While the run was outstanding this report published **1,537 across 75 + 3 = 78 targets** from the attribute count, and labelled it *an upper bound on what a run can report, and not evidence that the suite passed*. The run returned **1,537 across 78 targets, 0 failed** — so the count was right and **the run is what says the suite is green**. That distinction is this sprint's own item 6, applied to this sprint's own report: [coding standard](../../docs/standards/01.%20Coding%20Standard.md) §2.9 now says a statement of what a thing would be is not a claim that it was run. **This is the fourth commit at which the method has reproduced a runtime figure exactly**, and the first where the prediction was published before the run rather than checked against it afterwards.

#### [Status report 16](16.%20Sprint%2015%20Status.md)'s discrepancy is closed, and the hypothesis was wrong

**[Retrospective 14](../retrospectives/14.%20Sprint%2016%20Retrospective.md)'s fourth action asked for the unexecuted-target hypothesis to be run and the result recorded here either way. It was run. It is refuted.**

The method needed no services: **count `#[test]`, `#[tokio::test]` and `#[sqlx::test]` attributes in `kelir-backend` at each report's own commit**, and count `tests/*.rs` as one target each.

**`#[sqlx::test]` is the attribute that matters, and it is why the question stayed open.** [Status report 16](16.%20Sprint%2015%20Status.md) ran this same count and got 1,458 → 1,466 — **figures that reproduce exactly today** — but counted only `#[test]` and `#[tokio::test]`. The tree holds **11** `#[sqlx::test]` at all three commits, so that narrower count sits a constant 11 below every runtime figure: it could show the delta and never meet a number. **Adding the 11 closes it.**

| Report | Sprint | Commit | Reported | **Static count** | Targets reported | **Static + 3** |
|---|---|---|---|---|---|---|
| [15](15.%20Sprint%2014%20Status.md) | 14 | `427d840` | **1,495** | **1,469** | 73 | 70 + 3 = **73** ✓ |
| [16](16.%20Sprint%2015%20Status.md) | 15 | `d755a4f` | **1,477** | **1,477** ✓ | 74 | 71 + 3 = **74** ✓ |
| [17](17.%20Sprint%2016%20Status.md) | 16 | `191662e` | **1,497** | **1,497** ✓ | 77 | 74 + 3 = **77** ✓ |

**The method reproduces two reports exactly, on both numbers, and fails on exactly one — the one that was wrong.** *(The constant 3 is the lib target, the binary and doctests.)*

**So: [status report 16](16.%20Sprint%2015%20Status.md)'s 1,477 was correct all along and [status report 15](15.%20Sprint%2014%20Status.md)'s 1,495 was an overcount of 26.** The suite never shrank; it grew by exactly the eight tests report 16 said it did — 1,469 → 1,477 — and the per-target diff names them: `rad_list_render.rs` 23 → 28, and `sprint_reports_are_verified.rs` arriving with 3.

**No unexecuted target is involved, and nothing about the run was wrong.** A number in one report was. **Two sprints carried this as *unexplained*, and the check that settled it takes seconds and needs no database** — which is [retrospective 15](../retrospectives/15.%20Sprint%2017%20Retrospective.md)'s second root cause, one document over.

> **[Status report 15](15.%20Sprint%2014%20Status.md) is amended by this change**, at the product owner's direction: its *Suite* line now reads **1,469** with the 1,495 struck, and carries the reasoning above in a note. **A `Final` report from a closed sprint is corrected in place rather than left standing with a footnote elsewhere**, because the number it publishes is the one a reader compares against — which is how this discrepancy survived two sprints in the first place.
>
> **What is not claimed is how the 1,495 arose.** The run happened and exited 0; no per-target output survives, so whether it was mis-transcribed, double-counted across a re-run, or taken from a different working tree **cannot be recovered, and neither report guesses**. The target count of 73 was always correct.
>
> **[Status report 16](16.%20Sprint%2015%20Status.md) came within one regex of solving this itself**, and its note is amended to say so rather than being left as an open question. It ran its own static count, got **+8 across the two sprints — the same delta measured here** — and concluded *the suite did not shrink*, which was right. What it could not do was close the gap between its static figures and the runtime ones, because **it counted `#[test]` and `#[tokio::test]` and not `#[sqlx::test]`**. Widening that one pattern makes the static count reproduce the runtime figure **exactly** for reports 16 and 17, which is what turns *the suite did not shrink* into *report 15's number was wrong*.
