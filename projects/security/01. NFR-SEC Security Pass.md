## 5. The TLS check, once

**Run 2026-10-31 in throwaway containers on a private `--internal` docker network, all removed after.** The Caddy was the pinned `caddy:2.11.4-alpine` (`sha256:6aeddd44…`, `v2.11.4`), with the shipped `deploy/staging/Caddyfile` mounted read-only and unedited, and `KELIR_SITE_ADDRESS=kelir-tls.internal`. A `.internal` name does not qualify for a public certificate, so Caddy took `tls internal` by itself and the file needed no edit: the log says `certificate obtained successfully … "issuer":"local"`, and the served certificate's issuer is `Caddy Local Authority - ECC Intermediate`.

**The client is Python 3.13.16's `ssl` over OpenSSL 3.5.7**, in `python:3.13-slim`, one handshake per protocol, with minimum and maximum set to that protocol and the security level at 0, so TLS 1.0 and 1.1 are really offered. Debian's `openssl.cnf` sets `MinProtocol=TLSv1.2` and `SECLEVEL=2`, which is the client-side refusal AC4 warns of; the explicit settings override it.

| Server | TLS 1.0 | TLS 1.1 | TLS 1.2 | TLS 1.3 |
|---|---|---|---|---|
| **The shipped Caddy, on a hostname** | **Refused**, `TLSV1_ALERT_PROTOCOL_VERSION` | **Refused**, the same alert | **Accepted**, ECDHE-ECDSA-AES128-GCM-SHA256, `HTTP/1.1 502` | **Accepted**, TLS_AES_128_GCM_SHA256, `HTTP/1.1 502` |
| **The control: `openssl s_server -no_tls1_2 -no_tls1_3`, `ALL:@SECLEVEL=0`** | **Accepted**, ECDHE-RSA-AES256-SHA, `HTTP/1.0 200` | **Accepted**, the same | Refused, `UNSUPPORTED_PROTOCOL` | Refused, `TLSV1_ALERT_PROTOCOL_VERSION` |

**The probe can say *accepted*, and the refusal is the server's.** The control took the same client's TLS 1.1, and against Caddy the reason is the server's alert rather than a local one. The 502 is the absent backend, seen over the established connection.

**The Caddyfile does not state the minimum, and the record says why.** The check tried stating it.
- **`tls { protocols tls1.2 }` in the site block breaks the smoke test's shape.** With `KELIR_SITE_ADDRESS=:8080` it starts and validates, and `caddy adapt` shows `tls_connection_policies` on `:8080`, so **the plain-HTTP listener becomes TLS**: an HTTP request is answered `400 Bad Request`. This check knows of no global option for the floor, so a statement would need a second site shape for `:8080`.
- **Caddy cannot be configured lower.** `protocols tls1.1` does not parse: `wrong protocol name or protocol not supported: 'tls1.1'`. So a default of 1.2 is also the lowest value the Caddyfile accepts.
- **The version is pinned**: `deploy/docker/frontend.Dockerfile` names `caddy:2.11.4-alpine`, and `deployment_images_are_pinned.rs` refuses a floating tag. Unlike `trusted_proxies`, whose default moved, a bump here would have to move the floor up to matter, and [#839](https://github.com/sujanto-gaws/kelir/issues/839) asks that the check run again on one.
- **The site still starts with `KELIR_SITE_ADDRESS=:8080`**, unedited: running, and answering plain HTTP.

**NFR-SEC-010 is recorded as met under D-119 C, and its scope is this:**

| Hop | State | Evidence |
|---|---|---|
| Browser → edge | **TLS 1.2 or higher, and lower is refused** | This row's check, on a hostname, once |
| Backend → PostgreSQL, not local | **TLS 1.2 or higher, or no connection.** `require` encrypts and does not verify the certificate; `verify-full` is the operator's setting, as D-119 C has it | Row 39: `database-tls.probe.sh` (a) and (e), and `db.rs`'s tests in §2. rustls speaks nothing lower |
